> Datology's CTO on running trillion-token synthetic pretraining data jobs: rephrase seeded documents, batch S3 metadata calls, checkpoint for GPU failures, schedule CPU and GPU pools atomically, and sweep vLLM flags.

## Summary
Bogdan Gaza (CTO, DatologyAI) describes how Datology generates synthetic pretraining data by rephrasing high-quality seed documents from customer corpora (their "Beyond Web" recipe), and reports claimed gains of a 3B model matching an 8B baseline and roughly 2.7x and 5.3x token efficiency against two public synthetic datasets. The bulk of the talk is engineering lessons from a roughly 12T-token run across web, math and code: moving from a split Slurm-research and Kubernetes-product stack to one Kubernetes setup with Ray, Spark and vLLM; cutting S3 metadata collection from 9 to 11 days to about 2 hours with batched list calls; surviving GPU failures through right-sized partitions and checkpointing with idempotent overwrites; scheduling CPU and GPU requirements as one atomic unit across clusters; and getting about 40% throughput from vLLM/SGLang flag sweeps. Most performance numbers are the speaker's own and are not backed by eval details in the talk. The closing minutes are a hiring pitch.

## Key ideas
- **Synthetic pretraining data works by rephrasing or reframing existing high-quality documents, not by prompting a model from scratch.** — Unseeded prompting only reproduces the modes of the distribution the model was trained on, so each generation is prefixed with a real document from the customer's corpus. Datology's Beyond Web recipe is built on this. ([3:51](https://youtu.be/FQwTqUmcbRg?t=231))
- **The speaker claims a 3B model trained on Beyond Web data matches an 8B model trained on Nemotron Synth data.** — Across 1B, 3B and 8B models, the recipe is compared with Nemotron Synth, Cosmopedia, QA-Wrap and RedPajama. The results are self-reported and the speaker says they are from a late-2025 publication and are now outdated. ([2:30](https://youtu.be/FQwTqUmcbRg?t=150))
- **Two separate clusters, a Slurm research cluster and a Kubernetes product pipeline, made synthetic data slow, error-prone and under-used GPUs.** — Moving data between them was manual, and results had to be backfilled into the data catalog. The fix was one Kubernetes-based setup on AWS EKS on HyperPod H100 nodes, with Spark and Ray on CPU and non-H100 GPUs, plus an in-house job scheduler, so research and product share one code path. ([5:12](https://youtu.be/FQwTqUmcbRg?t=312))
- **Per-object S3 metadata calls were the first bottleneck. Batched list requests cut the work from 9 to 11 days down to about 2 hours.** — Millions of Parquet partitions hit S3 rate limits and slow metadata fetches, leaving GPUs idle. Using list APIs at the maximum page size of about 1,000 requests per call fixed it. The lesson is to load bucket state into the synthetic-data system before scaling up. ([10:10](https://youtu.be/FQwTqUmcbRg?t=610))
- **GPU instability is expected at scale. Large partitions turn a single node failure into hours of lost work, so partitions need to be small enough to retry cheaply, with periodic checkpoints.** — One rephrasing job on one partition can take 8 hours, and a box failing near the end wastes all of it. The fix combines right-sized partitions, periodic checkpoints flushed to S3, idempotent overwrites of checkpoint files, and automatic retries. Multi-day failures became recoverable retries. ([12:55](https://youtu.be/FQwTqUmcbRg?t=775))
- **Scheduling CPU and GPU capacity separately across clusters causes mismatches. The fix is dedicated pools per resource type, scheduled atomically.** — Jobs with CPU needs (Spark, Ray heads) and GPU needs can end up with capacity in only one pool. The speaker frames it as a bin-packing problem and solves it by decoupling the pools and scheduling each job's CPU and GPU needs as one unit. ([15:18](https://youtu.be/FQwTqUmcbRg?t=918))
- **Batch inference tuning for vLLM and SGLang matters. Flag sweeps gave about 40% throughput gains.** — Batch size and speculative decoding settings are central to offline batch inference, which differs from online serving. The speaker recommends a benchmark harness that only varies serving parameters and runs a grid search. ([17:34](https://youtu.be/FQwTqUmcbRg?t=1054))
- **Scale went from about 30B synthetic tokens in 2024 to roughly 7T web tokens plus about 5T math and code tokens by the end of the following year.** — The growth came from the infrastructure changes above, not from a single model change. The speaker says the next work is ablating domain coverage for web, multilingual, math, code and legal data. ([19:02](https://youtu.be/FQwTqUmcbRg?t=1142))

## Techniques
- **Seed-based document rephrasing for synthetic pretraining data** — Select high-quality documents from the target corpus, prefix each with a rephrasing or reframing prompt, and generate with one or more models on GPUs. Do not prompt for free-form samples, because that only reproduces the source distribution. *When:* When you need more pretraining tokens than the web provides, or need to add higher-quality data for a domain.
- **Batched S3 metadata listing at maximum page size** — Replace per-object metadata requests with S3 list calls at the maximum page size (about 1,000 entries per request). Load the bucket state into the data catalog or orchestration system before launching large jobs. *When:* When pipelines touch millions of Parquet partitions, metadata fetches are rate-limited, and workers sit idle waiting on metadata.
- **Right-sized partitions with checkpointing and idempotent retries** — Keep partitions small enough that losing one to a node failure costs little. Periodically checkpoint progress to S3, overwrite checkpoint files idempotently, and retry failed jobs automatically. *When:* For multi-hour GPU jobs on hardware that fails, where a single failure should cost minutes, not days.
- **Atomic CPU and GPU scheduling with dedicated pools** — Give each resource type its own pool (CPU pools for Spark and Ray heads, GPU pools for workers). Schedule a job's CPU and GPU requirements together across clusters so neither side sits stranded. *When:* When one job spans CPU and GPU resources across multiple clusters or clouds, and capacity in one pool blocks the other.
- **Grid search over vLLM and SGLang serving parameters for batch inference** — Build a benchmark harness that changes only serving parameters (batch size, speculative decoding settings and similar flags), measures throughput for each setting, and picks the best grid point. *When:* For offline batch generation jobs where throughput per GPU drives cost. Tune before scaling, and rerun when the model or hardware changes.
- **One workflow for research and product in the same infrastructure** — Express synthetic data generation, Spark curation, training and evals as steps in one orchestrated workflow on one Kubernetes-based code path, instead of separate research and production stacks. *When:* When research experiments are slowed by manual data movement and divergent codebases between the research and product teams.

## Hot takes
- Headline efficiency numbers (3B matches 8B, 2.7x and 5.3x fewer tokens) are the speaker's own, from a 2025 publication. The talk gives no eval details, and the speaker says they are outdated.
- The 9-11 days to 2 hours metadata result is a single anecdote from one pipeline, not a benchmark.
- The 'data wall' motivation is asserted without a cited source.
- Closing minutes are a hiring pitch, though the engineering lessons are concrete and reusable.
- Synthetic rephrasing of seed documents is the core claim and is more specific than generic 'make synthetic data' talks.
