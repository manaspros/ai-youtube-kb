> Walkthrough of running BMAD-planned stories in parallel with git worktrees and one Claude Code instance per subtask, with a QA agent review loop. The 90% title claim is not backed by the numbers shown.

## Summary
The speaker argues that AI coding is slowed by long sequential story runs, and proposes splitting BMAD-generated stories into non-conflicting subtasks that run in parallel. Planning starts with BMAD planning agents producing a PRD and architecture doc, from which the Scrum Manager agent generates stories. A custom prompt asks that agent to split each story into parts that do not conflict. Each part gets its own git worktree, managed in the Conductor app, with a Claude Code dev agent running in it. A QA agent then reviews each story, and the dev agent fixes the issues it reports. Each story is merged to main through a PR. The demo timings show about 20 minutes of wall-clock time for three parallel tasks, against about 40 minutes if run sequentially. The video is a sponsored walkthrough with one small demo project, so the evidence is anecdotal.

- **BMAD planning produces a PRD and an architecture document first, and stories are generated from them.** — The planning agents are bundled in one file that can be dropped into Claude Desktop or ChatGPT. Each story includes the commands and the code placement, which the speaker says reduces hallucination. ([2:36](https://youtu.be/xckU9n9r8Rs?t=156))
- **Each story runs through a dev agent and then a QA agent in a check loop.** — A BMAD dev agent implements each story through a slash command. - **Story splitting is done by a custom prompt to the Scrum Manager agent, which breaks each story into non-conflicting subtasks.** — The prompt asks the agent to check whether each story can be divided into subtasks that do not conflict, and to mention git worktrees and the merge back at the end. ## Techniques
- **BMAD planning-first pipeline** — Brainstorm the idea with the BMAD planning agents (bundled into one file, usable in Claude Desktop or ChatGPT). Save the resulting PRD and architecture docs to a docs folder. Have Claude Code generate stories from those two documents. Implement each story with the BMAD dev agent via a slash command, then run the BMAD QA agent on it. Re-run the dev agent with the QA feedback if needed. The exact slash command names are shown on screen and are not spelled out in the transcript. *When:* Greenfield projects where you want a structured plan, short stories, and a review loop before code is merged.
- **Prompt the story generator to split stories into non-conflicting parallel subtasks** — Use a custom prompt on the Scrum Manager (SM) agent that tells it to examine each story and split it into subtasks that do not conflict. Tell it that git worktrees are the isolation mechanism and that everything merges back at the end. Keep stories that would conflict as single tasks. The speaker says the prompt is in his resources, which are not in the transcript. *When:* Before running a batch of stories, when some stories touch separate files or layers and can be built in parallel.
- **One git worktree per subtask, managed through Conductor** — Create a Conductor workspace for each split subtask and name it after the story. Each workspace is a fresh copy of the codebase where its own Claude Code instance runs independently. Start the dev agent in each workspace and tag the story to run. Requires a git repo synced with GitHub. *When:* Running several Claude Code instances on one repo at once, when the subtasks do not conflict.
- **QA review then fix loop per story** — After the dev agent finishes a story, run the QA agent's review-story command. Then re-run the dev agent so it reads the QA feedback and fixes the issues. Repeat until the review passes. *When:* Any story where agent output needs an independent check before merge. The speaker found major issues in 2 of 3 stories on the first pass.
- **PR per story, merged by Claude Code** — Once a story is complete, create a PR for it and ask Claude Code to merge it into main. Merge the stories in order, one at a time, so later stories can build on earlier ones. *When:* Team or solo projects where each story should land as its own reviewable change on main.
