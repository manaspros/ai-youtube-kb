> Eric Allam (Trigger.dev) argues that replay-based durable execution breaks for long-running agent loops, and proposes splitting agent durability into an append-only context log plus VM snapshot/restore of the execution state.

## Summary
Eric Allam, co-founder of Trigger.dev, traces backend history from CGI and LAMP through shared-nothing architecture to replay-based durable execution (workflow engines that cache each step). He argues that agents break the replay model: every LLM call and tool call becomes a journal step, so the log grows large and replaying it becomes fragile, and code versioning gets harder. He reframes an agent as a session with two kinds of state: the context (an append-only message and tool log) and the execution environment (files, installed packages, running processes). The context can live in any durable append-only store, which lets the harness be upgraded without losing history. The execution environment is captured by snapshotting the whole machine while idle and restoring it when the next user message arrives. He describes how Trigger.dev moved from CRIU-based process checkpointing to Firecracker microVMs, shrank snapshots from a 512 MB default to about 14 MB compressed, and is preparing an open-source Docker-like CLI called fcrun. The talk ends with a product pitch, so the vendor framing should be discounted, but the recovery model and the snapshot engineering details are concrete.

## Key ideas
- **Replay-based durable execution fits workflows but breaks for agent loops** — Replay caches each side effect as a step and re-runs the function on resume. Once an LLM calls tools in a loop, every LLM call and tool call becomes a journal entry. The log grows with each turn until it hits entry-count or entry-size limits, and journal versioning gets tricky when code is redeployed. ([4:54](https://youtu.be/svCnShDvgQg?t=294))
- **An agent is a session, not a transaction, so split its durability into two parts** — Workflows start and end, but agent sessions last as long as the user wants. Durability should cover the context (system and user messages, tool calls and results, assistant replies) and the execution layer (files, memory, subprocesses). ([6:17](https://youtu.be/svCnShDvgQg?t=377))
- **Store the context as an append-only log in any durable store** — The log can sit in a database, object storage, or a distributed file system. Because the history is kept outside the harness, the harness can be upgraded or the machine can crash and the agent can still resume from the same context. ([7:45](https://youtu.be/svCnShDvgQg?t=465))
- **Execution state cannot be rebuilt from a log, so snapshot and restore the machine** — A cloned repo, installed packages, a running dev server, or a sandboxed subprocess is expensive or impossible to replay. Keeping the machine running while waiting for the next user message is too costly, so the machine is snapshotted to disk, shut down, and restored when the message arrives. ([9:14](https://youtu.be/svCnShDvgQg?t=554))
- **Pick the recovery path by failure type** — A transient LLM outage (e.g., a long retry-after) should snapshot the machine, wait without holding memory, and restore to retry. A machine crash or a bad deploy is handled by rebuilding from the context log. Both guarantees together give recovery in each case. ([10:16](https://youtu.be/svCnShDvgQg?t=616))
- **Process-level checkpointing (CRIU) was not enough, so they moved to Firecracker microVMs** — The speaker says the CRIU-based approach (shipped 2024, millions of restores since) is transparent to the process but only captures processes, cannot handle things like FFmpeg or a running Chrome, only keeps open files, and is slow through container registries. Snapshotting the whole VM avoids those limits. ([11:51](https://youtu.be/svCnShDvgQg?t=711))
- **Make VM snapshots cheap with seekable compression and lazy page restore** — A naive 512 MB snapshot is costly in network transfer, storage, and unused memory. Seekable compression lets the restore decompress only the pages it needs, and layered snapshots cut the size further, down to about 14 MB compressed. Compression level is a tunable trade-off between size and restore speed. ([13:20](https://youtu.be/svCnShDvgQg?t=800))
- **Expose the snapshot engine as a Docker-like CLI (fcrun)** — fcrun is a drop-in replacement for the Docker run command that runs containers in Firecracker VMs and can snapshot, restore, and fork them. The speaker says it will be open-sourced soon and will power Trigger.dev's future compute layer. ([14:45](https://youtu.be/svCnShDvgQg?t=885))

## Techniques
- **Two-layer agent durability** — Persist the conversation and tool history as an append-only log in a durable store. Separately snapshot the execution environment (filesystem, processes, installed packages) so the agent resumes with the same machine state. Reconstruct the context from the log when the harness changes. *When:* Long-running agent sessions that wait between user turns or must survive harness upgrades and machine failures.
- **Snapshot on idle, restore on next message** — When the agent is waiting for input or a retry window, snapshot the VM to disk, shut it down, and restore it when the trigger arrives. Hold no compute while idle. *When:* Sessions with long gaps between turns, or when a retry must wait a long time (e.g., rate limits or provider outages).
- **Recovery by failure class** — For provider or LLM errors, snapshot the execution state and retry after the wait. For machine or deployment failures, rebuild from the context log onto a new machine. *When:* Designing error handling for agents where a retry should not lose the workspace, and a crash should not lose the conversation.
- **Seekable compression with lazy page restore** — Compress VM memory snapshots with a seekable format and decompress only the pages a restore touches. Layer snapshots and tune the compression level to trade size against restore latency. *When:* Snapshotting many VMs where most allocated memory is unused and storage or transfer cost dominates.
- **Whole-VM snapshot instead of process checkpoint** — Use microVM snapshots (Firecracker) instead of process-level checkpointing (CRIU) so that the running processes, open files, and subprocesses such as Chrome or FFmpeg are captured without the process participating. *When:* Agents that run arbitrary tools or subprocesses inside sandboxes and need full-machine resume.

## Hot takes
- Replay-based durable execution (the workflow-engine model) is the wrong primitive for agent loops.
- Agents are forcing backend infrastructure to move from stateless compute back to stateful compute.
- Agent durability is two separate problems: the context needs a log, and the execution environment needs snapshots.
