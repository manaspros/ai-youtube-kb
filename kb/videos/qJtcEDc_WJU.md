> Anthropic's live demo and Q&A on Claude Managed Agents covers multi-session orchestration, scheduled deployments, outcome rubrics, and "dreaming," a memory-store self-improvement pass that the speaker says still needs your own evals.

## Summary
This is part 3 of a 4-part Claude Managed Agents series, a 26-minute workshop with a live demo followed by audience Q&A. The demo shows a main agent that dispatches one session per financial artifact (two tickers) through a custom tool, with each session running collaborative sub-agents, outcome definitions for self-supervision, and shared memory stores. Deployments wrap an agent definition with a schedule, initial messages and attached resources (memory stores, GitHub repos, files), so recurring runs can be triggered from the console or a custom UI. Dreaming is a research-preview pass that picks a memory store, a model and a window (the demo used the last 30 days of sessions), spins up sub-agents to review transcripts, and rewrites the memory store; in the demo it found gaps in a skill's wording. The Q&A gives the speaker's positions on harness definitions (tool loop, context and session state), tenancy (workspaces, not bring-your-own-key), skills versus multi-agent setups, and eval-gating dreaming. Several answers admit gaps: no RBAC beyond workspaces, no graph UI for topologies, and no on-prem option yet.

## Key ideas
- **Multi-session orchestration as the pattern** — A main agent decides it has enough information, then calls a custom dispatch tool that starts one session per item (two tickers in the demo). Each session can run its own sub-agents, has outcome definitions for self-checking, and can use memory stores to learn from other sessions. ([0:08](https://youtu.be/qJtcEDc_WJU?t=8))
- **Deployments make recurring agent work an API object** — A deployment holds an agent definition, a schedule (e.g. monthly or daily), starting messages, and attached resources such as memory stores, repos or files. Everything is API-first, so custom UIs can list, search, and trigger deployments. ([1:26](https://youtu.be/qJtcEDc_WJU?t=86))
- **Dreaming is self-improvement over past sessions** — The user picks a memory store, model, optional instructions and a time window. Sub-agents analyze the transcripts for missed information, repeated problems, and instruction gaps, then update the memory store. The demo showed a skill gap being patched by a memory note. The speaker says it will extend to skills, agent prompts and sub-agent prompts. ([2:48](https://youtu.be/qJtcEDc_WJU?t=168))
- **Compaction is handled by the platform so sessions can be very long** — The platform runs compaction, and the speaker reports 10-hour production sessions. The answer implies a daily agent could run for months without manual memory maintenance. ([5:27](https://youtu.be/qJtcEDc_WJU?t=327))
- **Tenancy: use workspaces, not bring-your-own-key** — The speaker says BYOK loses observability because runs bill to the end customer's key. Workspaces are the current tenancy primitive, with one workspace per customer or one shared workspace plus your own mapping. RBAC is on the roadmap, and everyone in a workspace currently has access to all of its agents. ([19:08](https://youtu.be/qJtcEDc_WJU?t=1148))
- **Harness means the tool loop; orchestration is a separate layer** — In this product, a harness means the tool loop plus context and session-state management. The speaker says builders use the word for coordinating several sessions as one unit of work. The session is the primitive offered, and the user builds the orchestration on top. ([9:25](https://youtu.be/qJtcEDc_WJU?t=565))
- **Outcomes replace hand-steering with a rubric and an iteration cap** — You write an exact rubric for the desired outcome and set max iterations. The agent keeps working until the rubric passes, using a verifier agent. The speaker recommends this together with your own evals. ([10:41](https://youtu.be/qJtcEDc_WJU?t=641))
- **Skills versus multi-agent is an open question, and the speaker expects skills to thin out** — The speaker says skills are a good abstraction today and that model-side capability will absorb more of what they cover over time. An audience member's view was that multi-agent setups look more useful. The speaker says there is a constant pull between constraining the model and letting it choose its own topology, which they say ends up performing better. ([12:08](https://youtu.be/qJtcEDc_WJU?t=728))
- **Dreaming needs evals before you trust it** — A single session might say a memory is wrong while another says it is right, so the speaker recommends running evals on dreaming's output before adopting a new memory store. Customers reported significant eval gains with this approach, but the speaker calls dreaming early research-preview work. ([13:29](https://youtu.be/qJtcEDc_WJU?t=809))

## Techniques
- **Fan-out one session per entity via a dispatch tool** — Give the main agent a custom tool that starts an independent managed session for each item (ticker, customer, document). Each session runs its own sub-agents and returns a result to the parent. *When:* Several independent analyses that need their own context and can run in parallel.
- **Scheduled deployment of a standing agent** — Create a deployment from an agent definition plus a schedule, initial messages, and attached memory stores, repos or files. Trigger runs on schedule, from the console, or from your own UI through the API. *When:* Recurring reports or monitoring, such as a weekly memo or a daily pass over a watchlist.
- **Outcome rubric with a max-iteration cap** — Write an exact rubric for the required result and set a max iteration count. The agent keeps iterating, with a verifier checking the rubric, until it passes or the cap is hit. *When:* Tasks with checkable acceptance criteria where you want self-supervision and a bounded loop.
- **Offline dreaming pass over past transcripts** — Choose a memory store and a window of past sessions, then run a sub-agent review that flags gaps, repeated failures, and instruction problems and proposes memory or instruction updates. Gate the adoption of those updates with your own evals. *When:* Improving a memory store or skill set from accumulated session history, not from a single failure.
- **Workspace-per-tenant isolation instead of BYOK** — Separate customers into workspaces and grant access per user group. If you keep one workspace for all customers, keep your own mapping from agent to customer. *When:* Multi-tenant products where you want to keep platform-level observability and billing.
- **Memory store as a separate attachable resource** — Keep the memory store as its own entity and attach it to whichever sessions need it, rather than tying it to one session. *When:* Shared knowledge that several sessions or agents should read and write.

## Hot takes
- The speaker says letting Claude choose its own agent topology outperforms human-constrained topologies, and that guardrails should keep being removed as models improve.
- Skills are a good abstraction today, but the speaker expects them to thin out as models absorb what skills currently encode.
- Bring-your-own-key is the wrong multi-tenant model because it removes your observability.
- Dreaming output should not be trusted without an eval set; one session may contradict another, and eval results are what tell you which to keep.
