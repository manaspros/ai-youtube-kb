> Uber's engineers walk through six building blocks (model gateway, MCP gateway, agent devpods, skills marketplace, context graph, Cortana) behind its managed software factory, then show one feature built end-to-end by an agent.

## Summary
Uber's Uday Kiran Medisetty and Adam Huda describe the platform pieces behind Uber's managed software factory, with an emphasis on shared infrastructure rather than any single agent. The first half covers six building blocks: a model gateway, an MCP gateway, pre-provisioned agent environments, a managed skills marketplace, a context graph, and Cortana, the company AI assistant. Adam then follows one feature (a World Cup stadium pickup-location idea) from a Slack idea through business research, Figma mockups, and a Minion coding agent that produces a draft PR. The validation story moves checks into an inner loop (simulator screenshots against Figma, staging integration, smaller-model review) so CI sees less load, and a self-healing CI step handles remaining failures. The talk closes with maintenance: managed, scheduled skills that run on Sunday to clean up things like feature flags, with bounded diff counts and reviewer outcomes fed back as labels. The speakers say the remaining bottlenecks are CI capacity, experiment throughput, and the decision of what to build. Most numbers are self-reported internal figures with no methodology given.

## Key ideas
- **Put all model traffic behind one OpenAI/Anthropic-compatible gateway** — Every internal tool and external use goes through one endpoint, which runs identity, PII redaction and safety checks before the request reaches a vendor. Each request is attributed to a project, user and team, so spend and guardrails can be managed across the portfolio. ([1:12](https://youtu.be/17-YSUHo6Lk?t=72))
- **Agent tool access is a token-cost problem as well as an auth problem** — Many MCP servers add up to a large token tax. Uber moved from direct MCP connections to one discovery MCP, then to CLI wrappers so tool output stays out of context, and finally to an auto-installed skill that writes Python for the most token-heavy use cases. ([3:58](https://youtu.be/17-YSUHo6Lk?t=238))
- **Agents need pre-warmed, isolated environments with repos and indexes ready** — Agent work runs in pre-provisioned Kubernetes pods that already have repositories snapshotted and search indexes built, so an agent can start in seconds. A combined cross-repo environment serves agents and engineers who work across several repos. ([5:27](https://youtu.be/17-YSUHo6Lk?t=327))
- **Treat skills as a managed lifecycle, not loose files** — Skills go through lint checks and automated review before reaching a marketplace, and personas auto-install defaults. The next step is collecting traces and comments as continuous evals to feed skill improvements. ([6:21](https://youtu.be/17-YSUHo6Lk?t=381))
- **A single context graph replaces many per-system context-gathering calls** — Context that was scattered across 20 to 30 systems is joined into one graph with 150 node and edge types. The speaker reports lower tokens, fewer turns and lower latency with the graph on an internal eval. ([7:44](https://youtu.be/17-YSUHo6Lk?t=464))
- **Move checks into an inner loop so CI runs fewer, better-prepared changes** — The agent validates visual output in a simulator against Figma and checks front-end and back-end integration in staging before pushing. The team says this is to protect CI capacity and avoid pushing unvalidated work through it. ([14:17](https://youtu.be/17-YSUHo6Lk?t=857))
- **Give reviewers evidence of the agent's self-checks on the PR itself** — Each autonomous PR carries a table listing the checks it passed, including screenshots, so the human reviewer can see the work was refined beyond the first generation. ([15:29](https://youtu.be/17-YSUHo6Lk?t=929))
- **Maintenance runs as managed, bounded scheduled loops** — Teams opt in through one managed surface. Runs happen on Sunday when CI has spare capacity, and diff volume is capped so engineers are not flooded on Monday. Landed or rejected diffs and reviewer comments become labels for improving the skill. ([15:29](https://youtu.be/17-YSUHo6Lk?t=929))

## Techniques
- **Single gateway with middleware chain and project attribution** — Route all LLM traffic through one compatible endpoint. Add middlewares in order: workload identity, a PII anonymizer (20-plus types), and a guard built from several small safety models, with a strict latency budget (under 100 ms). Require a project ID on every call for attribution and caching. *When:* When many teams or harnesses call models and you need per-team cost tracking, PII controls and guardrails without changing each client.
- **Progressive MCP projection (direct, discovery, CLI, generated code)** — Auto-crawl internal APIs and SaaS tools into MCP servers behind one gateway that handles token exchange. Then use one discovery MCP that finds and invokes other tools, project the most-used tools into CLI calls so results stay out of context, and generate Python scripts for the heaviest use cases. *When:* When the tool count is in the hundreds to thousands and MCP schema overhead or large tool responses dominate token spend.
- **Pre-warmed agent workspaces** — Keep a pool of pods with repos already snapshotted and search indexes already built. Hand one to an agent when a task starts, so the task does not wait for a clone or index build. *When:* When agents need quick, isolated, parallel environments on large monorepos.
- **Skill marketplace with lint, review and trace feedback** — Gate skills through lint and automated review, make discovery and install a single command, auto-install persona defaults, and log skill traces and comments to build continuous evals for each skill. *When:* When many engineers write overlapping skills and quality and duplication become a problem.
- **Shared context graph queried before tool calls** — Put structure from many systems (code, services, data lake, docs, tickets, incidents) into one graph with typed nodes and edges. Let skills query the graph first to find services, owners and table relations, then compare tokens, turns and latency with and without the graph. *When:* When agents spend many turns finding context across many systems before doing the actual work.
- **Split review between an inner loop and an outer loop** — In the inner loop, run a smaller, faster model for quick review before pushing. In the outer loop at CI or the PR gate, run a larger reasoning model with a deeper review skill. Also run visual and integration checks before CI. *When:* When review cost and latency matter and CI capacity is limited.
- **Managed scheduled maintenance loops with bounded output** — Make loops opt-in through one managed surface. Schedule them for low-load times such as Sunday, cap the number of diffs reaching engineers per cycle, and record which diffs landed to label the skill's quality. *When:* When automated cleanup such as flag removal or migrations should run company-wide without flooding reviewers.

## Numbers
- More than 70% of PRs are now produced by local or cloud agents; lines of code per engineer doubled year over year (self-reported, few thousand engineers across 12 sites) ([0:12](https://youtu.be/17-YSUHo6Lk?t=12))
- More than 250 automated migrations covering roughly 9 million lines of code ([0:12](https://youtu.be/17-YSUHo6Lk?t=12))
- Model gateway: 800-plus internal projects, more than 100 million model requests per day, PII redaction across 20-plus types, guard runs in under 100 ms ([1:12](https://youtu.be/17-YSUHo6Lk?t=72))
- 1,000-plus MCP tools; more than 40% fleet-wide token savings from the MCP optimizations ([3:58](https://youtu.be/17-YSUHo6Lk?t=238))
- Skills marketplace holds about 2,500 skills with more than 20,000 skill executions per day ([6:21](https://youtu.be/17-YSUHo6Lk?t=381))
- Context graph: 150 unique node and edge types and about 40 million entries; tokens, turns and latency all improved on internal evals with the graph ([7:44](https://youtu.be/17-YSUHo6Lk?t=464))
- Cortana: 300 unique personas created in the last month and more than 20,000 sessions per day ([10:33](https://youtu.be/17-YSUHo6Lk?t=633))

## Hot takes
- The speaker says the real bottleneck is no longer whether teams can build something but whether they should build it.
- The speaker frames many MCP servers as a 'token tax' and argues that projecting tools into CLIs keeps tool output out of the agent's context.
