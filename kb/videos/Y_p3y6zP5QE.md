> Google DeepMind's Jack Wotherspoon demos Gemini managed agents: a cloud sandbox, harness and API in one call, with reusable environments for multi-agent handoff, credential-injecting proxies, and scheduled triggers.

## Summary
The speaker argues that coding or research agents should run in a cloud sandbox rather than on a laptop, since local runs collide with the user's browser and machine and do not scale or share well. Building that yourself means managing containers or VMs, writing a harness, and handling networking and firewall rules. Google's Gemini managed agents reduce this to one API call. The offering uses the Antigravity harness inside a sandbox, with built-in tools for web search, file I/O and code execution, plus custom functions and remote MCP servers. Two stateful primitives matter: interactions hold conversation turns (chained by ID), and environments hold the sandbox filesystem, which different agents can reuse for handoffs. Credentials are injected by an egress proxy so the sandbox only sees placeholder tokens, and triggers (schedules or webhooks) can run agents on a timer. The talk ends with live demos of a three-agent SEC-filing, quant and report pipeline and a stock-analysis app, all of which are vendor showcase examples with no benchmarks or pricing shown.

## Key ideas
- **Run coding agents in a cloud sandbox instead of on the local machine** — Local runs can hijack the laptop browser and pop-ups during verification, and local setups (skills, customized agents) are hard to share with colleagues or embed in customer-facing apps without using a personal subscription. A sandboxed cloud agent avoids these problems. ([0:08](https://youtu.be/Y_p3y6zP5QE?t=8))
- **Self-hosting a managed agent stack is tedious; the managed offering collapses it to one API call** — Doing it yourself means spinning up a container or VM, building your own harness inside it, and handling networking, firewall rules and security. The managed version bundles sandbox, harness and scaling, so more agents means more API calls. ([2:30](https://youtu.be/Y_p3y6zP5QE?t=150))
- **Interactions API plus environment=remote is the entry point** — The agent-first Interactions API (GA earlier this year) replaces the single model input/output call with a multi-step agent call. Setting environment to remote tells the platform to provision a cloud sandbox for the base Antigravity agent. ([3:43](https://youtu.be/Y_p3y6zP5QE?t=223))
- **Two separate server-side primitives: interactions (conversation) and environments (filesystem)** — An interaction ID can be passed to the next call to continue a conversation. An environment ID persists the sandbox files, so later agents can pick up work from earlier ones. ([8:50](https://youtu.be/Y_p3y6zP5QE?t=530))
- **Multi-agent handoff through a shared environment with fresh context windows** — Agent A writes files (for example filings and metrics JSON) into an environment. Agent B starts with a fresh context window but the same environment ID and reads those files. This keeps each agent narrow and makes its work checkable. ([10:11](https://youtu.be/Y_p3y6zP5QE?t=611))
- **Secrets never enter the sandbox** — A proxy between the sandbox and the API puts a placeholder token in the sandbox. When an outbound call hits a matching API host (for example GitHub), the proxy swaps in the real secret. The agent cannot find or leak credentials it never holds. ([12:10](https://youtu.be/Y_p3y6zP5QE?t=730))
- **Triggers and fan-out make managed agents schedulable and composable** — Triggers can run an agent on a cron-like schedule (for example a pre-market financial analysis) or via webhook (for example posting to Slack or querying a Jira board). One managed agent can call other managed agents through the API to fan out work. ([13:12](https://youtu.be/Y_p3y6zP5QE?t=792))
- **Step traces make the agent's actions inspectable** — Each action (function result, file write, code execution) is saved as a step trace. The speaker suggests using these traces to tighten workflows over time. ([14:41](https://youtu.be/Y_p3y6zP5QE?t=881))

## Techniques
- **Single-call managed agent** — Call the Interactions API with the base Antigravity agent and set environment to remote, then send normal input. Set the model with a one-line parameter in the agent config. Upload files such as agents.md or skills into the sandbox, and load a GitHub repository at startup. Save a tuned configuration with agents.create and invoke it later by agent ID. *When:* When you want a cloud-run coding or research agent without building sandbox and harness infrastructure yourself, or when you need to call the same agent repeatedly from an app.
- **Chain turns with the interaction ID** — Save each interaction's ID and pass it into the next interaction call to continue the same conversation. *When:* Multi-turn work where the same agent needs prior conversation context.
- **Hand off work between agents via a shared environment ID** — Run agent A with an environment; it writes intermediate artifacts (filings, metrics.json, a Markdown analysis). Start agent B with the same environment ID and a fresh conversation, so it reads the files and continues. Repeat for a third report-writing agent. *When:* Pipelines where each stage should have a clean context window but must reuse prior outputs without re-sending them in the prompt.
- **Narrow single-purpose agents with fan-out** — Split the job into agents with one purpose each (SEC researcher, quant analysis, report writer). Let a coordinating managed agent call the others through the API to fan out subtasks, and inspect each run through its step traces. *When:* When a broad prompt gives you no way to measure what the agent is doing, and you want each stage to be testable.
- **Placeholder credentials with egress injection** — Store the real token only in the platform proxy. Give the sandbox a dummy token. The proxy matches outbound requests by target API host and injects the real credential, so the agent never holds it. Credentials and MCP OAuth can be injected this way per service. *When:* Any agent that calls third-party APIs from an untrusted sandbox and must not be able to exfiltrate or discover secrets.
- **Scheduled and webhook-triggered runs** — Create a trigger on the managed agent with a schedule (for example before market open) or a webhook. The agent runs its input, writes its output, and can post results to Slack or another service. *When:* Recurring briefings, monitoring, or report generation that should not depend on someone starting a session.

## Numbers
- Typical model output token cap is about 64k tokens; Gemini long decode shares the 1M-token context window across input, thinking and output. ([7:31](https://youtu.be/Y_p3y6zP5QE?t=451))
- The new Gemini frontier model (named Gemini 4 Argonne in the talk) was released the day before the talk. The speaker cites strength on financial tasks and math benchmarks, but shows no numbers. ([7:31](https://youtu.be/Y_p3y6zP5QE?t=451))
- Trigger example: a morning financial analysis scheduled before market open (8:30 a.m. in the example). ([6:02](https://youtu.be/Y_p3y6zP5QE?t=362))

## Hot takes
- Vendor talk for a Google product: the demos are showcase examples, and no latency, cost, pricing or benchmark numbers are given for managed agents.
- The 'secrets never enter the sandbox' claim is stated, not demonstrated, and the proxy's scope (which hosts, how matching works, what happens with non-HTTP protocols) is not explained.
- 'Anything you can do on your own coding agent, you can turn into a managed agent' is an overreach. Local access, interactive use and cost are not covered.
- Long-decode and benchmark claims for the new model are asserted without any figures on screen.
