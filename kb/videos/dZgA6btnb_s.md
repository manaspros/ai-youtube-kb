> Kepler's CEO explains how its finance research platform stops LLMs from inventing numbers: models cite pre-registered SEC facts, deterministic code does the math, and any unverifiable number is stripped.

## Summary
Vinoo Ganesh, CEO of Kepler, presents the architecture behind a financial research tool where every number must trace to a source. The core rule is that the model cites numbers but never writes or computes them; deterministic code handles arithmetic and the citation registry. Kepler pre-processed the SEC corpus (30M+ documents) into a registry of citable facts with typed annotations (value, unit, scale, period, entity). Retrieval combines BM25 with approximate-nearest-neighbour search in a Turbopuffer namespace (the speaker says zero-entropy embeddings, 1280 dimensions), then reciprocal rank fusion, trust-weighted re-ranking and a cross-encoder. Every hit is re-authorised at document level in Postgres for tenant isolation. A post-processing filter strips any number that cannot be matched to the registry, and the speaker claims about a third of citations from unfiltered model output were numbers the model made up. He says a baseline RAG stack would have had many numbers refused in evals, though the transcript figures are garbled. The talk is a product walkthrough with a vendor-partner stage, so the architecture is concrete but the performance claims are unverified.

## Key ideas
- **Models should cite numbers, never write them. Arithmetic (growth rates, margins, multiples) goes to deterministic code written by humans, and the LLM only plans and references source IDs.** — The speaker's core architecture claim: LLMs are probability machines and do not reliably do math, so the platform makes arithmetic impossible for the model to produce directly. ([3:37](https://youtu.be/dZgA6btnb_s?t=217))
- **Pre-process the whole source corpus into a fact registry before answering queries.** — Kepler processed 30M+ SEC documents and registered citable anchors (income statement and balance sheet facts, MD&A figures). Roughly 21,000 citations were extracted by the filter. ([3:37](https://youtu.be/dZgA6btnb_s?t=217))
- **A bare number is meaningless without typed metadata, so every fact needs value, unit, scale, currency, period and entity.** — A '1' or '17' in a 10-K is ambiguous. A 2023 revenue figure in a 2025 filing has to be annotated as 2023 data. Kepler stores the stored value separately from a display value so output can be re-scaled or re-currencied while staying traceable. ([6:17](https://youtu.be/dZgA6btnb_s?t=377))
- **Use the LLM to plan and dereference pointers. Deterministic tools retrieve, compute, build tables and register each result into a citation registry.** — A user question leads to a plan (retrieval steps, citation filter, computation). Filters and references go to the LLM to resolve against the registry; numbers with no registry match are stripped. ([4:50](https://youtu.be/dZgA6btnb_s?t=290))
- **Search wide, then re-rank in layers: hybrid ANN + BM25, then reciprocal rank fusion, then source-trust re-ranking, then a cross-encoder.** — Recall is kept high by pulling about 60 candidates, then trusted sources (10-K over an earnings-call sentence) are preferred. Conflicting sources are kept and de-conflicted, not silently merged. ([10:02](https://youtu.be/dZgA6btnb_s?t=602))
- **Re-authorise every retrieval hit at document level and scope tokens per query, so one desk's research cannot leak to another.** — Each hit is checked against Postgres permissions, every computation adds a filter, and only the auth service can mint a scoped query token. Internal sources (SharePoint, Box, OneDrive, Outlook) live in the same namespace. ([11:26](https://youtu.be/dZgA6btnb_s?t=686))
- **About a third of citations pulled from unfiltered model output were numbers the model produced from its training data, not from a source.** — Historical figures are the worst case, since a 2005 revenue number cannot be traced back to the right year and scope. This is the failure the registry is designed to catch. ([12:54](https://youtu.be/dZgA6btnb_s?t=774))
- **Strip unverifiable numbers by default, with citation repair only in some cases.** — Stripping makes the platform less creative (the speaker says it is the wrong tool for marketing content). Some unmatched citations go to an agentic repair step that tries to link them to a source; the speaker declines to explain that step. ([14:16](https://youtu.be/dZgA6btnb_s?t=856))

## Techniques
- **Cite-don't-write with post-filter** — Constrain the LLM to output source IDs (not raw figures). Resolve each ID against a registry of facts. Render the display value from the deterministic store. Strip any numeric claim that has no registry match before the answer is shown. *When:* Any answer that must be numerically correct and auditable: finance, legal, reporting, internal analytics.
- **Typed fact registry** — Give every fact a unique ID plus value, unit, scale, currency, period, entity and source document. Store the stored value separately from display formatting so units can change without losing traceability. Use entity resolution so the same company maps to one ID. *When:* Extracting figures from filings or other documents where a number without its period or scale is ambiguous.
- **Search wide, then re-rank in stages** — Hybrid retrieval: ANN plus BM25 in one namespace. Pull roughly 60 candidates. Fuse with reciprocal rank fusion. Re-rank by source trust (e.g. filing over call transcript). Final pass with a cross-encoder before returning to the model. Make re-embedding cheap so the index can be refreshed as new documents arrive. *When:* Retrieval where precision matters more than latency, and where the corpus changes often.
- **Per-hit document authorisation** — Re-check permissions for every retrieved hit at query time, not only at index time. Mint scoped query tokens from the auth service only. Add a permission filter at each computation step so filters accumulate. *When:* Multi-tenant retrieval where users must not see each other's research or data.
- **Keep conflicting sources and de-conflict** — When sources disagree (an earnings-call figure vs a 10-K figure), store both as separate facts with provenance. Choose or annotate at answer time instead of merging at ingest. *When:* Financial or any data where restatements and sources of different authority coexist.
- **Measure recall and idempotency as guarantees** — Track recall on an eval set. Run the same query repeatedly and check for identical results. Count how many numbers the filter refuses against a baseline RAG stack. *When:* Turning a RAG prototype into something you can claim is accurate.

## Hot takes
- Claims that hooking Claude or ChatGPT to a vector DB is not enough for numerical accuracy, and that many finance RAG startups that are ChatGPT wrappers cannot be trusted (vendor opinion, no independent benchmark shown).
- Says Kepler is 'the most granular form of any tool on the market' in traceability, a claim the talk does not verify.
- Predicts this cite-don't-write architecture 'will become the standard' for financial research tools.
- Kepler is 'not a super useful tool' if you rely on hallucinations, and creative or marketing work is out of scope. The speaker is candid about the trade-off.
- The talk is a vendor walkthrough on a Turbopuffer partner stage. Key numbers (eval refusals, citation counts) are garbled in captions and the citation-repair step is deliberately kept vague, so treat the architecture as a useful pattern and the metrics as unverified.

## Tools mentioned
Kepler (finance research platform), Turbopuffer (vector and BM25 search, namespaces), Zero Entropy embeddings (as stated; 1280 dimensions), Postgres (per-document authorisation), Cross-encoder re-ranker (model not named), XBRL (structured filings data, cited as ~10% incorrect), SEC filings: 10-K, 10-Q, 8-K, S-1, investor presentations, earnings call transcripts, Claude and ChatGPT (used as baseline in evals), Gemini 4 (mentioned, not evaluated)
