> Sourcegraph's agent advocate argues DevRel must now serve AI agents as users and recommenders, and shows how to measure agent friction and recommendation rates.

## Summary
Stephanie Jarmak, an agent advocate at Sourcegraph, argues that developer advocacy is not dead but its audience has changed: agents now read docs, call APIs, install libraries and recommend tools on a developer's behalf. She describes a benchmark (CodeScaleBench) of hundreds of SDLC tasks, run with and without Sourcegraph's code navigation MCP tool, where trace analysis exposed agents guessing wrong parameter names and wasting a turn on each error. She reports a GEO (generative engine optimization) pilot where Sourcegraph's product was recommended about 65% of the time on comparative prompts but never on pain-point prompts. She warns that training data goes stale and that old-model output compounds on the web, so newer models can repeat outdated product claims. Her prescriptions are fresh, quotable and structured content (llm.txt, charts, FAQs), presence in MCP registries and marketplaces, and low friction from discovery to install. She splits the role into engineering, product and marketing flavors and closes with a "curb cut" argument that serving agents also makes the human path clearer. The talk is practitioner-level with some product promotion.

## Key ideas
- **Agents are now a user of your product and a recommender of it, so DevRel has to serve them as well as developers.** — An agent reads docs differently from a human, calls APIs, hits errors and recovers from them. It also picks and installs libraries on the developer's behalf. The speaker says developers increasingly orchestrate fleets of agents, so the audience has widened. ([2:19](https://youtu.be/Lrw0jqBNaw0?t=139))
- **Trace analysis of agent tool use reveals fixable friction in tool descriptions.** — The speaker's agents guessed a parameter name (read line instead of start line) from training-data bias. The error message let the agent recover, but it cost a full turn. Fixing the description removes that cost. Token use and speed are also measures a buyer may use. ([5:49](https://youtu.be/Lrw0jqBNaw0?t=349))
- **Recommendation rate depends heavily on prompt intent.** — On comparative shopping prompts the product was recommended about 65% of the time. On pain-point prompts, which the speaker argues are the more typical moment of need, it got zero mentions. Prompt sets should be designed around the buyer's real problem, not only the comparison. ([8:27](https://youtu.be/Lrw0jqBNaw0?t=507))
- **Stale training data and model-generated web content can keep repeating old product information.** — A newer model (4.6) pitched an older product even more than the older model did. The speaker says old-model output is compounding on the internet, so authoritative sources (llm.txt) and real-time retrieval with provenance are needed to bury the noise. ([10:52](https://youtu.be/Lrw0jqBNaw0?t=652))
- **Make agent-facing content quotable, current and easy to act on.** — Agents favour current examples, charts and FAQs they can quote. Be listed in marketplaces and MCP registries. Remove steps such as multiple demos or sales calls, because an agent will not recommend a tool that requires them. ([11:48](https://youtu.be/Lrw0jqBNaw0?t=708))
- **Split agent advocacy into engineering, product and marketing work.** — Engineering builds the MCP interfaces, evals and instrumentation. Product owns the end-to-end agent experience and its rubrics. Marketing owns how agents enter the funnel and surface recommendations. Community and credibility also need to account for agents, including privacy when agents join Discord. ([13:51](https://youtu.be/Lrw0jqBNaw0?t=831))
- **Serving agents clarifies the human path too (curb-cut argument).** — The speaker notes agents show a bias toward content generated by agents, so credibility with each audience must be earned separately. She argues that structured, machine-readable content helps humans as well, the way curb cuts help everyone. ([16:23](https://youtu.be/Lrw0jqBNaw0?t=983))

## Techniques
- **Agent friction logging from traces** — Collect agent traces for real tasks, find tool calls that fail or retry, and read the error text to see what the agent expected. Then fix the tool description, parameter names or docs. *When:* After shipping or changing any tool or API that agents will call.
- **With-and-without-tool agent benchmark** — Build hundreds of SDLC-shaped tasks and run agents once with your tool and once without. Compare outcomes, tokens used and time, then investigate where the tool helps or fails. *When:* To prove a tool helps agents, or to find where it breaks.
- **Intent-split GEO prompt experiments** — Write two prompt sets: one for comparative shopping and one for pain points. Count mentions and recommendations of your product for each. Change your content and rerun to measure lift. *When:* To test whether agents surface your product at the buyer's moment of need.
- **Agent experience report** — Point a coding agent at your docs, have it attempt tasks, and review the transcript for friction. Write up the findings as an agent experience report. *When:* As a cheap first step for DevRel or docs teams.
- **Machine-readable authoritative content** — Publish llm.txt pages and keep examples, FAQs and charts current. Keep your listing in MCP registries and marketplaces, and cut signup steps between discovery and install. *When:* When you want agents to find and cite accurate current information about your product.

## Hot takes
- Developer advocacy is not dead; the audience now includes agents, and the core of DevRel still holds.
- Agents recommend tools mostly from training data, so pain-point content is what gets a product surfaced at the moment of need.
- Agent-facing content can be full of em dashes if it is structured, because the credibility bar for agents is different from humans.
- Make sure your tool does not need demos or sales calls before use, because an agent will not recommend a tool that does.
