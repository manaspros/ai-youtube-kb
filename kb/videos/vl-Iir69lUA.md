# I Switched from tRPC to oRPC (Here’s Why)

> Better Stack walks through switching a Next.js app from tRPC to oRPC, covering the same procedure/router/client setup and what oRPC adds: first-party OpenAPI with Scalar docs, typed error classes, and contract-first APIs.

## Summary
The presenter migrates a small Next.js demo from tRPC to oRPC and shows that the core developer experience (procedures, a router object, a catch-all route handler, a typed client with autocomplete) is nearly identical. The main differences he highlights are first-party OpenAPI generation with a Scalar interactive reference UI, a typed error system (a specialized error class plus per-procedure error definitions and a safe() wrapper that returns a tuple), and contract-first design where you define input/output contracts before implementing them. He also mentions built-in plugins for caching, batching, retries and rate limiting, plus TanStack Query support beyond React (Vue, Svelte, Solid). The talk is a concise code walkthrough with no benchmarks; its tone is enthusiastic and it leans on "absolute must switch" framing, though the code shown is concrete. He admits he rarely uses the contract-first approach himself.

## Key ideas
- **oRPC is a near drop-in mental model for tRPC users** — Procedures, a plain-object router, a handler, and a typed client with autocomplete map one-to-one, so a tRPC user can port quickly. The presenter says the setup differs mainly per integration (he uses Next.js). ([0:00](https://youtu.be/vl-Iir69lUA?t=0))
- **Next.js wiring is a catch-all API route plus an RPC link** — A single RPC handler receives the router and forwards GET/POST/PUT/PATCH/DELETE requests with a prefix option (he uses /rpc). The client uses an RPC link pointed at the server URL, and the client is typed from the router's type. ([0:52](https://youtu.be/vl-Iir69lUA?t=52))
- **Builder pattern for public vs. protected procedures** — A base procedure carries database middleware, and a protected procedure extends it with authentication middleware, so every procedure built on it is authenticated. ([2:02](https://youtu.be/vl-Iir69lUA?t=122))
- **First-party OpenAPI is the main differentiator** — Procedures can be exposed as REST-style endpoints with a route method/path, summary and tags, and output schemas drive spec generation. A Scalar block on a Next.js route gives an interactive reference with a built-in test client. He says the older tRPC OpenAPI route was an unmaintained plugin. ([3:28](https://youtu.be/vl-Iir69lUA?t=208))
- **Typed errors on both server and client** — Throwing a specialized oRPC error with a code is the baseline. Declaring errors per procedure with a data schema makes the server throw side typed, and the client's safe() wrapper infers the error union so narrowing on error.code gives typed data (e.g. retryAfter as a number). ([4:41](https://youtu.be/vl-Iir69lUA?t=281))
- **Contract-first is available only in oRPC** — You define contracts (inputs, outputs, errors, constraints) with the contract builder and no implementation, then implement them with the implement function. A mismatch between implementation and contract becomes a type error. The presenter says he seldom uses this pattern himself. ([7:09](https://youtu.be/vl-Iir69lUA?t=429))
- **Built-in plugins and broader query-library support** — He lists plugins for caching, batching, retrying and rate limiting, and TanStack Query integration for Vue, Svelte and Solid as well as React. He mentions Pinia Colada for Vue but gives no detail. ([8:33](https://youtu.be/vl-Iir69lUA?t=513))

## Techniques
- **Minimal oRPC procedure with Standard Schema input validation** — Import os from the orpc server package, then .input() with a Zod schema (any Standard Schema library such as Valibot or ArkType also works) and .handler() containing business logic. The handler receives the validated input. *When:* Replacing a tRPC procedure with a typed endpoint where you already use Zod or another Standard Schema library.
- **Router as a plain object and Next.js catch-all route** — Build a router object mapping names to procedures (e.g. hello -> helloProcedure). Create an RPCHandler with the router, then in a Next.js catch-all route under app/rpc call handler.handle(request, { prefix: '/rpc' }) for each HTTP method (GET, POST, PUT, PATCH, DELETE). *When:* Standing up oRPC in a Next.js app router; the prefix must match the client URL.
- **Typed client via RPC link** — Create an RPC link from the fetch client pointed at the server URL (http://localhost:3000/rpc in the demo). Create a client typed with the router client type, and use the router's type for the generic. Call procedures as methods on the client with the input object. *When:* Calling server procedures from the frontend with full autocomplete and inferred return types.
- **Public/protected procedure chain** — Define a base public procedure with database middleware attached. Derive a protected procedure from it by adding authentication middleware. Use the protected procedure for every endpoint that needs auth. *When:* Enforcing auth and shared context (DB handle) across many procedures without repeating middleware.
- **OpenAPI route metadata and Scalar reference** — Call .route({ method, path, summary, tags }) on each procedure and declare an output schema so the spec can be generated. Attach the Scalar reference block to a Next.js route (the demo serves it at /api). Use the Zod smart-coercion plugin so inputs are coerced without .coerce() on every field. *When:* Publishing a public REST-style API with generated OpenAPI docs and an interactive test client from the same procedures.
- **Typed error definitions** — Throw new ORPC error with a code (e.g. NOT_FOUND) and a message for ad hoc errors. For typed errors, declare them on the procedure with .errors({ CODE: { message, data: zodSchema } }), then in the handler throw errors.CODE({...}) for autocomplete and checked data. On the client, wrap the call in safe(), which returns a tuple, check isDefined or narrow on error.code, and read the typed data. *When:* Expressing expected failures (not found, rate limited) that clients must handle with type-checked fields instead of catching untyped exceptions.
- **Contract-first definition** — Define each route as a contract using the oc builder from the contract entry point, listing only input, output and errors. Group contracts in a router-shaped object. Implement with os.<group>.<contract>.handler(...) using the implement function from the server entry point, then assemble the implementations into a router. Mismatched outputs raise a type error. *When:* Freezing a shared API interface between separately developed client and server code, or when you want TDD-style API design.

## Hot takes
- Framed as an "absolute must switch" and a recommendation to replace tRPC; the evidence is a feature checklist on one demo app with no benchmarks or migration cost.
- Claims the tRPC OpenAPI plugin is unmaintained and that oRPC is the only option with first-party OpenAPI and contract-first; not verified in the video.
- Says he rarely uses the contract-first approach, which he presents as a headline differentiator.
