> Walkthrough of Solid 2's breaking changes: async becomes part of the reactive graph, effects and JSX are reworked, a Rust compiler ships, and the Vite plugin's start mode makes Solid Start unnecessary.

## Summary
The presenter walks through the Solid 2 release candidate, the largest Solid update in a while. The headline change is that async is part of the reactive graph: computations can return promises directly, createResource is removed, and Suspense, ErrorBoundary and SuspenseList are renamed to Loading, Erred and Reveal. Promises are consumed into the graph at creation, so downstream code reads plain values and loses the null/undefined checks, while the UI updates as data arrives. Writes get an action-based optimistic flow (createOptimistic, createOptimisticStore) with automatic rollback on error, and stores take drafts so produce and createMutable go away. Effects are split into a tracked compute function and an untracked apply function, cleanup is returned rather than registered, and writes commit on the next microtask (flush() forces them through). JSX moves closer to HTML (class accepts strings, objects or arrays, attr:/bool: prefixes and on:/on:capture are gone, index is replaced by keyed={false}, and a Repeat component renders by count). On tooling, a new Rust compiler built on Oxc is claimed to be much faster, and the Vite plugin gets a start mode that handles full app builds, optional SSR, server functions and file-system routing, which the presenter argues makes Solid Start redundant. The video ends with a recommendation to use the migration guide, possibly with a coding agent, and a short anecdote about Claude Code picking up the changes.

## Key ideas
- **Async becomes first-class in the reactive graph** — createResource is removed. A computation such as createMemo can return a promise directly, and downstream code treats the result as an async memo. Suspense becomes Loading (fallback only when there is no data yet), with isPending to track refetches. ErrorBoundary becomes Erred and SuspenseList becomes Reveal. Presenter says this is more than renaming, since the promise is consumed into the graph rather than blocking UI at the consume site. ([0:00](https://youtu.be/sr4q-Jj7uiM?t=0))
- **Consuming promises into the graph removes null/undefined checks** — In Solid 1, resource values had loading and undefined states that had to be checked everywhere. In Solid 2 the promise enters the graph on creation, and downstream components only see plain values. Nested components can be presentational, and a Loading boundary decides when the UI shows. The presenter frames this as solving the old trade-off between developer experience and user experience. ([2:05](https://youtu.be/sr4q-Jj7uiM?t=125))
- **Optimistic updates use action plus optimistic stores with automatic rollback** — The resource mutate function is replaced by createOptimisticStore and an action. The action writes the optimistic change, calls the save API, then refreshes from the server. Optimistic changes last only for the action's lifetime, so an error reverts the UI to the authoritative value without manual rollback code. Stores now hand out drafts, so produce and createMutable are removed (a path helper remains for the old behavior). ([3:25](https://youtu.be/sr4q-Jj7uiM?t=205))
- **Effects split into a tracked compute and an untracked apply** — Solid 1 effects combined dependency tracking and side effects in one function. Solid 2 uses compute (tracked, returns a value) and apply (untracked, receives the value and does the work). This replaces on(), which becomes an option on the effect, including defer. createComputed is removed in favor of memo or a split effect. Cleanup is returned from apply instead of registered with onCleanup, and onMount becomes onSettled, which fires after async work under it resolves. ([3:25](https://youtu.be/sr4q-Jj7uiM?t=205))
- **Signal writes commit on a microtask and batch is gone** — Writes are staged and committed on the next microtask, so reading a signal right after setting it returns the old value. flush() forces the update synchronously. batch is removed because consecutive writes already share a batch by default. ([4:32](https://youtu.be/sr4q-Jj7uiM?t=272))
- **JSX moves closer to HTML** — classList is removed; class takes strings, objects or arrays, so conditionals are objects. The attr: and bool: prefixes are gone, booleans follow HTML presence rules, and on:/on:capture are replaced by camelCase event props (use ref callbacks plus addEventListener for native listener options). Directives become ref callbacks and directive factories, and ref accepts an array to stack directives. For lists, index is removed and keyed={false} gives index-style behavior. A new Repeat component renders by count and start index, and each row reads its own store slot. ([4:32](https://youtu.be/sr4q-Jj7uiM?t=272))
- **New Rust compiler on Oxc is the Vite plugin default** — Solid 2 ships a Rust compiler toolchain built on Oxc (auto-captions say 'Box C'), and the Vite plugin uses it by default with no config change. The presenter cites vendor benchmarks, not independent measurements. ([5:56](https://youtu.be/sr4q-Jj7uiM?t=356))
- **Vite plugin start mode replaces Solid Start** — The plugin can now run a full app build on plain Vite with no index.html or entry files. The default output is client-only static files. SSR can be enabled for a server bundle, use server is a core feature, and a router-neutral package adds file-system routing, code splitting and HMR. Deployment targets any platform that accepts a web-standard fetch handler (Cloudflare Workers, Netlify, Nitro, Bun, Deno), with no Solid-specific adapter. Solid Start 2 is still receiving maintenance updates. ([7:08](https://youtu.be/sr4q-Jj7uiM?t=428))

## Techniques
- **Async data with an async memo and a Loading boundary** — Replace createResource(fetchUser) with createMemo(() => fetchUser(id)). The memo is async and downstream code reads a plain value. Wrap the consumer in <Loading fallback=...> so the fallback only shows before the first value. Use isPending to show refetch state. Keep children presentational with no undefined checks. *When:* Any component that reads async data in Solid 2, especially when you want reads to render as soon as each piece is ready instead of blocking on the parent.
- **Optimistic mutation with action and createOptimisticStore** — Create an optimistic store seeded from the server-fetched source of truth. In an action, write the new item to the optimistic store (it is a draft, so mutate directly), call the save API, then call refresh() from the server. If the API call throws, the optimistic override is discarded and the UI shows the authoritative value. *When:* Write paths where the UI should update instantly and roll back automatically on failure, replacing manual rollback logic from Solid 1 resource mutate.
- **Split effect into compute and apply** — Put reads in the tracked compute function that returns a value. Put side effects in the untracked apply function, which receives that value and returns its cleanup. Use the defer option for the old on(..., {defer: true}) behavior. Use onSettled for work that should run after async children resolve. *When:* Any side effect that depends on reactive state, to keep dependency tracking separate from the work done in response.
- **Read a just-written signal with flush()** — After a write, call flush() before reading if you need the new value in the same tick. Do not rely on reads immediately after writes, since commits are staged to the next microtask. *When:* Code that writes and then reads the same state synchronously, such as validation or DOM measurement.
- **Index-style list rendering and count-based Repeat** — Use <For> for identity-keyed lists (the default). Set keyed={false} for position-keyed behavior. Use <Repeat start={...} count={...}> when rendering N rows from store slots, so updating one row does not touch others. *When:* Lists where item identity or per-row store slots matter, such as large tables or grids.
- **Migrate with the official migration guide and a coding agent** — Give the Solid 1 to Solid 2 migration guide to a coding agent and ask it to migrate the codebase. The presenter reports Claude Code used the guide to pick up the API changes, but this is a single anecdote with no details shared. *When:* Upgrading a Solid 1 codebase with many API renames and removals, where the guide serves as the spec for a mechanical migration.
- **Deploy a Solid 2 app via the Vite start mode** — Build a client-only static site by default with the Vite plugin's start mode. To ship SSR, enable SSR in the plugin and deploy the server bundle, which exports a web-standard fetch handler. Deploy with the platform's own tooling (Cloudflare Workers, Netlify, Nitro, Bun, Deno) and no Solid-specific adapter. Config keys and exact plugin options are not shown in the video. *When:* New Solid 2 projects that do not need a meta-framework, or when moving off Solid Start.
