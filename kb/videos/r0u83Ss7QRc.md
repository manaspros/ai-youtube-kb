> Better Stack commentary on Shopify dropping React Native for native apps, with Shopify's Helix checkpoint-gated agent loop and headless app logic for fast agent testing. Opinion-led, relays Shopify's blog post.

## Summary
Better Stack reports that Shopify, a long-time React Native backer, has moved its apps back to native Swift and Kotlin and is handing off or abandoning its open-source RN packages. The presenter attributes the switch to coding models improving enough that building the same feature twice, once per platform, no longer costs what it did. Shopify's approach is an in-house system called Helix that breaks agent work into small checkpoints. Each checkpoint must pass tests, a visual match against the running app, two adversarial code reviews, and a human sign-off before the next one starts, with reviewer feedback remembered across the migration. The second half covers testing speed: Shopify keeps business logic headless and drives it through a CLI so agents iterate in milliseconds without simulators. The presenter compares this to out-of-process XCUITest, which he calls slow and flaky. He concedes that teams still maintain two apps and predicts cross-platform frameworks will lose value. Most of the substance is secondhand from Shopify's article, and the video itself adds little verifiable detail.

## Key ideas
- **Shopify is moving its apps back to native and abandoning its open-source React Native packages, citing AI as the reason.** — The presenter's core claim: the cross-platform benefit (one codebase, one language) no longer outweighs the cost, because agents can port a feature between Swift/Kotlin and the RN code cheaply. He says Shopify's article is the source and that Shopify's own 2025 stance was pro-RN. ([0:00](https://youtu.be/r0u83Ss7QRc?t=0))
- **One-shot porting with an LLM does not work. Shopify's answer is Helix, a loop where an imperfect attempt cannot advance.** — Even with extensive context gathering, spec and task files, a single pass produces large unmaintainable code. Helix expects the first attempt to be wrong and gates progress on quality instead. ([2:08](https://youtu.be/r0u83Ss7QRc?t=128))
- **Helix breaks a screen migration into ordered checkpoints that are small enough to review in minutes.** — Workflow: point Helix at a screen, it reads the RN code, proposes a sequence of checkpoints, then builds one at a time. Each checkpoint must prove behavior with tests, match the running app visually, survive two adversarial code reviews, and get human approval before commit. ([2:08](https://youtu.be/r0u83Ss7QRc?t=128))
- **Review feedback is remembered, so the loop should need less human input as the migration proceeds.** — Feedback from each review stage is stored and reused, which the presenter describes as making the process more autonomous over time. The transcript gives no mechanism for this. ([2:08](https://youtu.be/r0u83Ss7QRc?t=128))
- **Slow native build and test cycles, not model quality, are the real bottleneck for agents on mobile.** — Agents edit in seconds but native compile and test takes several minutes, so iteration becomes manual. The presenter argues a faster test loop matters more than a better model here. ([3:15](https://youtu.be/r0u83Ss7QRc?t=195))
- **Shopify keeps business logic decoupled from the UI and drives it headlessly through a CLI, so agents can test in milliseconds.** — App state lives in a plain store and actions update it, with the UI only rendering that state. Agents can drive the app without reading the accessibility tree or tapping elements. The presenter likens this to a JSON state store with actions in web development. When UI rendering is needed, interactions can still be driven from the CLI. ([3:15](https://youtu.be/r0u83Ss7QRc?t=195))
- **The presenter argues this beats XCUITest, which he calls slower and flakier because it walks the accessibility tree and re-queries after each tap.** — The comparison is the presenter's characterization, not a benchmark. He says the Shopify approach is fast in real time and shows a demo, though the demo is not sped up. ([4:22](https://youtu.be/r0u83Ss7QRc?t=262))
- **The caveat: a big company still ships two apps, so the gain is in agent throughput, not in removing platform maintenance.** — The presenter concedes teams still maintain two native codebases. He argues the economics will keep shifting as models improve, and that this erodes RN's value over time. ([4:22](https://youtu.be/r0u83Ss7QRc?t=262))

## Techniques
- **Checkpoint-gated agent migration (Helix pattern)** — Have the agent read the source screen and propose an ordered list of small checkpoints that a human can review in minutes. For each checkpoint: write tests that prove the behavior, compare the result visually against the running app, run two adversarial review passes, then require a human approval before committing. Only then start the next checkpoint. Store reviewer feedback and reuse it in later checkpoints. The transcript gives no config or commands. *When:* Porting or re-implementing features across codebases or platforms, or any large agent-written change where a single-shot attempt produces unmergeable code.
- **Headless state plus CLI driver for agent testing** — Keep all business logic and app state in a plain store that does not depend on the UI. Expose state-changing actions through a CLI. The UI only renders the state. Agents iterate by dispatching actions and reading state, skipping simulators and accessibility-tree inspection. When UI rendering must be checked, drive the same interactions from the CLI. *When:* Mobile or UI-heavy apps where simulator or emulator build-and-test cycles are slow enough to stall an agent loop.
- **Avoid out-of-process UI automation for agent verification** — The presenter argues against XCUITest-style testing for agents, which runs out of process, walks the accessibility hierarchy, synthesizes taps and re-queries the tree to verify. He recommends driving state and actions directly instead, using the UI only where needed. *When:* Agent-driven verification of mobile apps, where UI-driven tests are flaky and slow.
