> Optiver's head of AI engineering on running an AI platform where every decision shows up in P&L within hours: same-day model adoption, token-spend control, and narrowly scoped agents on a shared gateway.

## Summary
Noyan Tokgozoglu, head of AI engineering at the trading firm Optiver, explains how the company scales AI when the feedback loop is daily P&L. Decisions are measured within hours, so the platform is built around modularity, measurement at every layer, and benchmarks on internal golden sets. A new frontier model is benchmarked immediately and, if it adds value, is wired into the inference gateway, harnesses and support rotations on the same day. Spend grew quickly after coding agents took off, and the team cut it by trimming default context (about 200k tokens in fresh sessions), replacing MCP calls with CLIs, tuning prompt caches, giving teams their own alert and limit controls, and routing work to cheaper models. The company also built an internal web portal for agent sessions and multiplayer rooms, which traders now extend through PRs. The Q&A covers two open problems: point-in-time replay of tool calls for evals, which they handle with a confidence score per invocation and a proxy around MCP servers, and the decision to keep agents scoped to one task each rather than bloating a single agent. The talk is a corporate case study with few hard numbers, but the operational detail is specific.

## Key ideas
- **Trading gives a same-day P&L feedback loop, which changes how AI is measured and scaled** — Changes rolled out to traders show P&L impact within hours, so a missed opportunity is costly. The team needs to decide quickly, measure efficiently, and have a bias for action. The speaker contrasts this with consumer products that compete for attention. ([1:29](https://youtu.be/aGIUg8zKI8A?t=89))
- **Modular platform, measure every layer, and adopt new paradigms only when measured as valuable** — Each new model or paradigm (loops, swarms, graphs) is measured, then adopted if it adds value. Internal benchmarks are kept because the data distribution differs from public benchmarks. ([2:46](https://youtu.be/aGIUg8zKI8A?t=166))
- **Self-service needs good defaults, backed by forward-deployed AI engineers** — High-agency traders get a self-service platform. Without defaults that becomes chaotic, so AI engineers sit with traders, learn how they work, and bring the learnings back to the platform. ([2:46](https://youtu.be/aGIUg8zKI8A?t=166))
- **Layered AI stack: models, inference gateway, agent platform, agent gateway, user surfaces** — Third-party and self-hosted open models sit behind an inference gateway that handles routing, per-model spend, budgets and failover. Above it are a registry of agent skills, plugins and tools, an agent gateway as a single ledger for identity and orchestration, and user-facing surfaces. Everything runs on-prem except third-party inference, which is under zero-data-retention agreements. ([5:11](https://youtu.be/aGIUg8zKI8A?t=311))
- **Same-day adoption pipeline for new frontier models** — Teams contribute golden benchmark sets. A new model is run on them immediately and results are shared company-wide. If it adds value it goes through gateway registration, API and interface checks, cost setup, harness updates, and a round-the-clock support rotation across regions. ([6:13](https://youtu.be/aGIUg8zKI8A?t=373))
- **Token growth was controlled by changing defaults, not by restricting usage** — Spend spiked around the Claude Code era and the summer frontier releases, then was brought under control with optimizations. Fresh sessions often began with roughly 200k tokens of context because everyone dumped MCPs and knowledge into them. Fixes included MCP tool search, CLI wrappers in place of MCP calls, cache-invalidation analysis, and moving content from giant system prompts into a knowledge base. ([10:09](https://youtu.be/aGIUg8zKI8A?t=609))
- **Visibility plus self-managed limits keeps teams spending sensibly** — Telling teams what they spend, adding alerting, and letting them set their own limits led most teams to set reasonable ones. Open-source models are offered as cheaper replacements where they fit. Routing and frontier-plans with smaller-model implementation are under exploration. ([12:30](https://youtu.be/aGIUg8zKI8A?t=750))
- **Meet users where they are with an internal session portal, then open it to contributions** — People had bespoke tmux setups and hacky web UIs. The company built one portal for sessions, chat, artifacts and collaborative docs. Traders now send PRs to it, and it has grown into multiplayer rooms that mix people and agents, plus a Slack client. ([13:28](https://youtu.be/aGIUg8zKI8A?t=808))
- **Eval replay of tool calls is an open problem, handled by point-in-time snapshots with a confidence score** — All tool inputs and outputs are logged via OpenTelemetry into the eval system. Replaying a support-bot agent with a different model is hard because tool results depend on world state at the time. Where a system supports point-in-time reads (such as a trading backtest database) this is easy. For systems like Slack, each invocation gets a confidence value for how well it can be replayed. A proxy around MCP servers serves snapshots, and recording everything is the imperfect fallback. ([19:26](https://youtu.be/aGIUg8zKI8A?t=1166))
- **Scope agents to one task and version them, rather than merging capabilities into one agent** — Merging two teams' agents produced a complex, poorly working agent. The current direction is versioned agents, small incremental capability pushes, and narrowly scoped agents coordinated through the agent gateway ledger. Bloated agents make some capabilities improve while others regress, which is hard to measure or tune. ([21:36](https://youtu.be/aGIUg8zKI8A?t=1296))

## Techniques
- **Golden-set benchmarking on day zero** — Partner with each key team to collect its benchmark cases. When a new model ships, run it on those sets right away, publish the metrics internally, and gate adoption on the result. *When:* When models change frequently and a generic public benchmark does not match your data distribution, as with trading or domain workloads.
- **Gateway-first model onboarding checklist** — Register the model in the inference gateway, make sure the required API interfaces are supported, configure cost tracking and budgets, update harnesses, then launch with support rotations and a recommendation message to the company. *When:* Whenever a new model or provider is added, so that it is portable across harnesses and can be swapped out if a provider fails.
- **Replace default MCP context with tool search and CLI wrappers** — Add MCP tool search so tools load on demand. Where agents only need a few MCP servers, expose a single CLI that wraps several MCPs, which the agent calls through shell access instead of loading every MCP schema. *When:* When fresh sessions start with very large context (the speaker cites ~200k tokens) because every MCP and knowledge base is loaded by default.
- **Analyze cache invalidation before tuning cache TTLs** — Study when prompt caches are invalidated in each harness. Decide whether TTLs should be set globally, per workload, or dynamically, then tune each team's harness with that data. *When:* When cached-token spend is high or cache hit rate is low, and the cost per session needs to fall without hurting latency.
- **Move reference material out of the system prompt into retrieval** — Keep the system prompt short and put reference content into a knowledge base that the agent retrieves from. This also reduces the context actually retrieved per task. *When:* When system prompts have grown with documents, runbooks or tool docs that only some tasks need.
- **Per-team alerts and self-managed spend limits** — Give each team visibility into its own model spend, configurable alerting, and the ability to set its own budget limits, then let teams tune them. *When:* When you want to control cost without a central approval bottleneck, and teams are high-agency enough to manage their own budgets.
- **Point-in-time tool snapshots with per-invocation confidence** — Log every tool call's input and output through OpenTelemetry. Where the backend supports point-in-time reads, replay against that point. Otherwise, store a confidence score for how replayable the call is, and serve recorded results through a proxy around MCP servers when re-running evals. *When:* When re-running an agent eval with a different model or prompt, and tool results depend on external state that has since changed.
- **Scope agents narrowly and version them** — Give each agent one task it does well and version it. Ship small capability increments as new versions. Let agents hand work to each other through the shared gateway ledger instead of building one agent that does everything. *When:* When one agent is growing many unrelated capabilities and regressions become hard to attribute or measure.
- **Ship internal portal with contributions via PRs** — Build one internal web surface for agent sessions, chat, artifacts and shared docs. Let power users open PRs against it, then add multiplayer rooms that mix human and agent participants. *When:* When employees are building bespoke tmux, web or chat wrappers around agents, and centralizing them would improve productivity.

## Hot takes
- Self-hosting and building an in-house agent platform beats managed agents from vendors, mainly because of vendor lock-in and roadmap speed (the speaker cites a gateway provider that moved slowly on a needed model).
- Knowledge bases are underrated for cost control, because retrieving only the right context is cheaper than large system prompts.
- Vector search, markdown files and hybrid approaches all have trade-offs. The speaker says they are not happy with their current memory solution and would like to explore graph databases.
- Letting teams set their own spend limits works better than central caps when the teams are high-agency.
- Point-in-time replay of tool calls has no perfect solution beyond recording everything.
