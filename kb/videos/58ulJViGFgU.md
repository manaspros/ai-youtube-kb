> Keycard's Kamil Potrec argues agents need their own authenticated identities, short-lived scoped credentials via OAuth-style delegation, and a gateway that injects credentials outside the agent's reach, so every request is attributable and revocable.

## Summary
The speaker, a product engineer at Keycard, frames agent authentication as the unsolved gap in agent systems. Today agents reuse user personal access tokens or static service-account keys, so an MCP server cannot tell whether Alice or an agent made a call, and credentials can be copied and abused. He proposes giving each agent its own identity (possibly per session), issuing scoped short-lived credentials on demand, and expressing delegation and approval policy explicitly, with audit of who authorized each action. He argues SDKs alone fail here because agents can read credentials from their own execution environment, so credentials should be held in a vault and injected by a gateway that can enforce policy, attenuate requests and revoke instantly. He is candid about gateway costs: extra latency, the need to force all traffic through it, no coverage for local tool execution, and becoming a high-value target. Keycard sells a control plane covering identity, federation, policy, audit, client and service SDKs, and an optional gateway. Treat the product pitch as vendor framing; the architectural argument is the useful part.

## Key ideas
- **Today agents usually pass a user's personal access token through or use static keys, so the MCP server sees the user as the actor and cannot tell an agent from the user's own CLI.** — Shared tokens are unattributed and hard to revoke. Service accounts that aggregate permissions over many users are a privileged bucket, and non-deterministic agents make their behavior hard to predict. ([1:58](https://youtu.be/58ulJViGFgU?t=118))
- **The invoice example: an agent reads a pending invoice and sends it, and nothing in the system records whether Alice or the agent made the request.** — Prompt injection or over-helpfulness turns data returned by a tool into an action. Attribution is the core failure to fix. ([3:14](https://youtu.be/58ulJViGFgU?t=194))
- **Agent authentication needs agent identities separate from whoever launched them, plus explicit delegation semantics that say which users may act through which agents.** — Identities could be per agent or per session. Credentials must be scoped and short-lived, with no master key. ([7:44](https://youtu.be/58ulJViGFgU?t=464))
- **Reuse OAuth-style dynamic credentialing: the agent discovers what authorization a remote service needs, fetches a scoped token for that interaction, and discards it afterward.** — The speaker's argument is that the same pattern as for users applies to software, and that workload identity federation, private-key auth, certificates or URL-based authorization can prove the agent's identity first. ([5:16](https://youtu.be/58ulJViGFgU?t=316))
- **SDKs are a weak fit for agent credentials: adoption gaps, per-language coverage, unmodifiable tools such as Claude Code, bug propagation, and client-side code that agents can read or bypass.** — Agents are persistent and may try to get around controls, so credentials should stay outside the agent's execution environment. ([10:54](https://youtu.be/58ulJViGFgU?t=654))
- **A gateway in the request path can authenticate the caller, check policy against the authorization server, fetch the credential from a vault, inject it, and forward the request.** — Gateways enable instant revocation because every request is checked. They can also attenuate scope, for example allowing read but blocking send, and give observability without changing downstream services. ([12:15](https://youtu.be/58ulJViGFgU?t=735))
- **Gateways have real costs: an extra hop, agents able to bypass them without strict network controls, no help for local tool execution, a concentrated high-value target, TLS interception issues, and config sprawl for routes and policies.** — Gateways do not solve agent identity by themselves, since agents still need credentials to present to the gateway. ([14:40](https://youtu.be/58ulJViGFgU?t=880))
- **Use open standards and interoperable components, and do not let an LLM write the auth implementation unreviewed.** — Auth code should be security-reviewed. Build with open standards so the system is not locked to one vendor. ([17:26](https://youtu.be/58ulJViGFgU?t=1046))

## Techniques
- **Per-agent (or per-session) identity with explicit delegation** — Issue each agent its own identity, separate from the launching user. Record which users may act through which agents, and which agents may act on behalf of other users. *When:* Any system where agents call APIs or MCP servers on a user's behalf and actions need attribution.
- **Just-in-time scoped, short-lived credentials via OAuth-style dynamic credentialing** — Authenticate the agent first (workload identity federation, private-key JWT, certificates or URL-based auth). Then, for each remote call, discover the required authorization, obtain a token scoped to that interaction, use it, and let it expire. *When:* Replacing static API keys, service accounts or shared PATs for agent-to-tool calls.
- **Credential brokering through a gateway** — Route agent traffic through a gateway. The gateway authenticates the caller, checks policy in the runtime authorization service, fetches the credential from a vault and injects it into the outgoing request, so the agent never holds the secret. *When:* When credentials must stay out of the agent's execution environment and revocation must be immediate.
- **Request attenuation at the gateway** — Inspect each request and allow or deny it by method and resource. For example, allow reading email while blocking sending, even when the upstream token has broader scope. *When:* Legacy APIs that only offer coarse admin, read or write scopes.
- **Human-approval policy for sensitive actions** — Express in policy which actions need a human to approve and which agents may run without approval. Log who authorized each request for audit. *When:* Write, send, delete or payment actions taken by agents.
- **Legacy credential exchange through an adaptive broker layer** — Put a broker between agents and legacy systems that exchanges identities just in time for the legacy system's own credential types, instead of waiting for those systems to adopt new auth. *When:* Integrating the many older services that cannot change their auth.

## Hot takes
- Shared tokens and service accounts are the default in the industry today, and the speaker says that is an unacceptable risk once agents act autonomously.
- Gateways are the practical control point for instant revocation and per-request policy, but they come with latency, bypass and single-point-of-compromise costs.
- Do not rely on LLMs to write auth code (YOLO warning), and audit any generated security code.
