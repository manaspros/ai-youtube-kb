> Two Anthropic Applied AI engineers explain how long-running agent harnesses evolved, and how a planner, generator and evaluator loop with rubric grading builds multi-hour apps that a single agent loop cannot finish.

## Summary
Ash Prabaker and Andrew Wilson (Anthropic Applied AI) trace how Claude Code and the Agent SDK gained the primitives needed for agents to run for hours, from early computer use and MCP through skills, server-side compaction, agent teams and 1M-token context. They name three limits of long runs: finite context (amnesia, context rot, late-context anxiety), weak planning, and models overrating their own output. Their main pattern splits the work into a planner, a generator and an evaluator, each in its own context, where the evaluator uses Playwright to test the live app and grades it against a four-criterion rubric (design, originality, craft, functionality). Before building, the generator and evaluator negotiate a sprint contract in files on disk, and the evaluator grades against that contract. A worked example compares a solo run with the harness on the same retro-game prompt: the solo run looked done but failed under use, while the harness run (about $200 and six hours) produced a playable game. The speakers say out-of-the-box Claude is a poor QA agent, so the main tuning method is reading agent traces line by line. They also say harness pieces should be removed as each model improves, as with dropped context resets and less frequent evaluation on Opus 4.6.

## Key ideas
- **Three limits stop agents from running for hours: finite context, weak planning, and poor self-judgment** — Context is finite, so a new session means amnesia, and deep sessions show context rot. Models may also get 'context anxiety' near the end of the window and rush to finish. Out of the box they build half a feature and stop, or call a feature done when its backend does not exist. The speaker says the fixes come from both model training and harness changes. ([2:22](https://youtu.be/mR-WAvEPRwE?t=142))
- **Self-evaluation is a trap, so split generator and evaluator into separate contexts** — Borrowing the GAN idea, one agent builds and another grades, with adversarial pressure between them. The speakers say a standalone critic is easy to tune to be harsh, while a builder that is self-critical is hard to tune. They compare it to critiquing a meal versus cooking one. ([18:18](https://youtu.be/mR-WAvEPRwE?t=1098))
- **The evaluator tests the live app instead of reading diffs** — The evaluator opens pages with Playwright, clicks around, screenshots, scores against criteria, and writes a critique back to the generator. The speakers contrast this with the common pattern of one session told to check its own work. Each example took about four hours and 5 to 15 rounds of calibration. ([19:11](https://youtu.be/mR-WAvEPRwE?t=1151))
- **Taste can be graded if you write it down as a rubric** — They use four criteria: design, originality, craft and functionality, weighted toward design and originality. The weights shift by model; Opus 4.6 was already good at functionality. A few reference examples and anti-examples (for example, purple gradients or generic AI-slop aesthetics) calibrate the evaluator's taste. ([20:35](https://youtu.be/mR-WAvEPRwE?t=1235))
- **A pivot beats patching when one criterion stays low** — If the generator keeps scoring low on originality, the harness discards the whole attempt and starts again. A single pass or a Ralph loop keeps patching the same thing. The speakers call this the course correction that breaking up roles makes possible over long horizons. ([23:03](https://youtu.be/mR-WAvEPRwE?t=1383))
- **Planners should specify high-level scope, not granular technical details** — The planner turns a one-line prompt into sprints of product scope. It avoids technical detail because an early mistake would cascade through every sprint and grow over a multi-hour run. The speakers liken the structure to a PM, IC and QA org. ([23:03](https://youtu.be/mR-WAvEPRwE?t=1383))
- **Generator and evaluator agree on a testable contract before building** — The generator proposes what to build and how to verify it. The evaluator pushes back on scope and weak tests, and they iterate in markdown files on disk until both agree. Grading then uses this contract rather than the planner's original spec. The speakers say this turns vague user stories into testable assertions, which the Ralph loop lacked. ([24:27](https://youtu.be/mR-WAvEPRwE?t=1467))
- **Harness value comes from scaffolding, shown by a side-by-side run** — The same prompt (build a retro game maker) on the same model: the solo run had a plausible UI, but arrow keys and space did nothing. The harness run took about six hours and cost about $200. It named the product, added an AI level assistant from a vague spec line, and the evaluator had 27 contract criteria and caught bugs such as route ordering and a delete-key logic error. ([28:48](https://youtu.be/mR-WAvEPRwE?t=1728))
- **Harnesses should shrink as models improve, so re-check what each release makes unnecessary** — Opus 4.5 had context anxiety, so context resets were needed. Opus 4.6 did not, so one continuous session with compaction was enough. Sprint decomposition and per-sprint evaluation were dropped because Opus 4.6 could hold a two-hour build coherently. The speakers say the harness was right for 4.5, and the frontier moved. ([33:50](https://youtu.be/mR-WAvEPRwE?t=2030))

## Techniques
- **Generator-evaluator loop with a live-app evaluator** — Run the generator and evaluator in separate contexts. The evaluator uses Playwright (or Chrome MCP, or computer use for native apps) to navigate, screenshot and test the running app, scores each criterion, writes a critique to a file, and hands it back. Repeat until the rubric passes. *When:* Web apps and UI work, where 'looks done' differs from 'works', and tasks that run for hours.
- **Rubric-as-taste with calibrated examples** — Write a small set of weighted criteria (the talk uses design, originality, craft, functionality). Calibrate the evaluator with a few reference examples and anti-examples, and tune weights per model. *When:* Any fuzzy quality target (design, API style, code quality) where you can describe 'good' in writing.
- **Sprint contracts negotiated in files** — Before any code, the generator writes a proposal of what it will build and how to verify it. The evaluator marks up scope and test gaps. Both iterate through markdown files on disk until they agree. Grading then uses that contract, not the original spec. *When:* Multi-hour builds where a vague spec would drift, and where you want testable done-criteria.
- **Thin planner that stays high level** — Turn a one-line prompt into a broad spec split into sprints. Leave technical detail to the builder and the contract step, so planning errors do not cascade. *When:* Open-ended product builds where early technical mistakes would multiply later.
- **Structured state on disk with JSON feature lists and progress files** — The initializer writes a feature list as JSON (models overwrite markdown more often than JSON), a progress file, an init script and a git repo. Each loop starts a fresh context, reads the state, runs the init script, picks one unfinished feature, verifies it, commits, and flips its pass flag. *When:* Long builds that span context windows or sessions, and any work that another model or a human must pick up later.
- **Breadcrumb logs for later pickup** — Prompt the loop to write learnings to a JSON or timestamped log: what was tried, what the evaluator found, the fix, and whether it worked. Keep a live high-level doc of the file structure. A later model or human can then iterate from these. *When:* Work that will be resumed days or weeks later, or handed from an agent to a human.
- **Read full traces, then tune prompts from them** — Read the whole agent transcript line by line to see where its judgment differs from yours, then tune the evaluator or generator prompt. Pipe transcripts to files and let another agent suggest prompt changes as a first pass. *When:* Tuning evaluators, which are biased toward generous grading out of the box.
- **Ralph-style stop-hook loop with exit criteria** — Run a single Claude Code session and set max iterations and a safe word. A stop hook intercepts each attempt to stop and continues unless an exit criterion is met. The speakers note this relies on compaction, not fresh context windows. *When:* Simple repeat-until-done tasks where a fixed iteration cap is an acceptable failure mode.
- **Hooks for human check-ins** — Add a stop condition, for example from the evaluator, that hands control back to a human, accepts a developer message, then resumes the loop. *When:* Long runs where you want to steer at intervals rather than wait for the end.
- **Split model roles for cost** — Use a stronger model (Opus) for planning and a cheaper one (Sonnet, and Haiku in the family) for execution, sub-agent loops, or workhorse coding. Use evals to check each sub-agent's performance on its task. *When:* When cost matters and planning quality is the bottleneck.
- **Put the human-readable spec back into long sessions** — Insert the main product spec into builder and evaluator sessions at intervals so the work keeps a reference point, while the planner stays out of the loop. *When:* Long builds where scope creep or drift from the original goal is a risk.

## Hot takes
- Self-evaluation is a trap; use an adversarial evaluator.
- Compaction does not equal coherence; lossy summaries drift.
- Subjective quality is gradable if you write the rubric down.
- Out of the box, Claude is a bad general QA agent: it is sycophantic and generous about bugs.
- Harness design is not dead; it shrinks and changes with each model release.
- Models throw away a failing attempt and restart more readily than the generator restarts its own work.
- Reading full agent traces by hand is the most important debugging skill for agent builders.

## Relevance to our work
- **prosharness** (3/3): ProsHarness already has checkpoint/resume and a plan to critique loop. The talk gives a concrete contract step, a file-based handoff, and a feature-state JSON pattern that fit those directly. → *Add a contract step to ProsHarness's plan phase: the builder and a critic agent write a done-contract file, the critic grades only against that file, and feature state is kept in a JSON file so resume is cheap and inspectable.*
- **agentos** (1/3): The talk's evaluator-with-rubric idea could support EvolveCraft and SkillForge, which are self-improvement loops that need a success signal. It is a pattern to borrow, not an infrastructure change. → *In an EvolveCraft spike, have a separate evaluator grade each self-improvement attempt against a written rubric and accept changes only when they pass, then measure how often the evaluator's verdicts agree with a human reviewer.*
