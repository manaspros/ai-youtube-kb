> Nico Albanese (Vercel) live-builds a coding-style agent with AI SDK 6: a tool loop, web search, a persistent named sandbox running bash, file-based memory and self-written scripts, plus notes on context pruning and subagents.

## Summary
This is a live workshop that builds an agent step by step on the Vercel AI SDK 6 and AI Gateway. It starts with a tool loop agent defined once and reused, adds a provider-executed web search tool, and renders tool calls in the UI with end-to-end types. The main part gives the agent a Vercel Sandbox through a named, persistent sandbox that snapshots when idle, and a bash tool that is the only tool it needs. Memory is a memories.md file injected into the system prompt on each run, and the agent is nudged to save repeatable tasks as scripts. The speaker argues against per-step message trimming, because it breaks the input cache, and prefers subagents that return short summaries plus a handoff tool over compaction. He reports internal production numbers for a similar agent, which is a hedged, partly product-promotional talk with the code shown live.

## Key ideas
- **Agent building blocks in 2026 are a runtime (loop and context handling), tools, a computer or sandbox filesystem for state and code execution, and instructions.** — The speaker argues the system prompt is still central and should be used together with tools and a filesystem, not dismissed as an old technique. ([17:46](https://youtu.be/wflNENRSUb4?t=1066))
- **Provider tools come in three kinds: custom tools you execute, provider-defined tools the model is post-trained to use (such as bash or computer use), and provider-executed tools that run on the provider's servers (such as web search).** — Provider-executed tools need no execution code, but they tie you to one provider. The speaker opts in through the OpenAI provider's web search tool. ([19:13](https://youtu.be/wflNENRSUb4?t=1153))
- **A filesystem scratchpad with a plan file improved long-task completion more than adding tools did. The plan has the objective at the top, the agent checks off steps, and it re-reads the plan on each step.** — The speaker's internal data agent went from using 5 to 10 tools and hallucinating answers to finishing full tasks. The plan file keeps the objective from being lost in a long context. The output is an artifact that shows what work was done. ([28:15](https://youtu.be/wflNENRSUb4?t=1695))
- **Named persistent sandboxes solve the ephemeral-sandbox problem. You reference a sandbox by name, the platform routes each session to an active instance or starts one, and on idle it snapshots the filesystem so the next request resumes the same state.** — The speaker had built his own tarball-to-blob save and restore before this and says the platform version is much simpler. The feature was in beta at the time of the talk. ([32:02](https://youtu.be/wflNENRSUb4?t=1922))
- **Context pruning by trimming message history per step (prepareStep) breaks the input cache. The speaker prefers keeping the full history and relying on subagents and handoffs, because a 1M-token window makes compaction less necessary.** — Earlier he trimmed tool calls to stay within 40 to 60 percent of the window. He moved away from that because each trim invalidates the cached prefix. He also says LLM summarization is lossy and cites an incident where auto-compaction dropped the user's instruction. ([39:20](https://youtu.be/wflNENRSUb4?t=2360))
- **Per-request dependencies such as a sandbox or customer tier are passed as typed call options, then injected into a runtime context (like React context) that tools read in their execute function.** — The call option schema is validated per invocation. The context is set once on the first call, so tools receive the sandbox without threading it through prompts. A newer SDK version is planned to type this context on the top-level agent. ([45:45](https://youtu.be/wflNENRSUb4?t=2745))
- **Memory can be a plain memories.md file in the sandbox that is read deterministically and injected into the system prompt on each run. Writing instructions as positive rules matters, because negative instructions such as 'do not record greetings' made the model act oddly.** — The speaker used a short 'do not save trivial interactions' prompt that worked better. He also says conflicting instructions are common and the model follows them literally. ([1:00:03](https://youtu.be/wflNENRSUb4?t=3603))
- **Self-extension: when a task repeats, have the agent write a script for it, then record the script's description in memories.md so it reuses the script next time. The demo built a weather script in one turn and reused it on the next request.** — This works because bash gives the agent a build-run-check loop, which he compares to a compiler or REPL for coding. He presents it as the base for an agent that learns over time. ([1:03:23](https://youtu.be/wflNENRSUb4?t=3803))

## Techniques
- **Single-definition tool loop agent** — Define the agent once (model, instructions, tools) in a shared lib file. Route handlers only pass in messages and stream the result with the agent's UI stream helper. Use the AI SDK global provider so plain model strings route through AI Gateway. *When:* When the same agent is used from several entry points, or when route handlers have grown to thousands of lines of inline tools and prompts.
- **Typed UI messages from the agent definition** — Use the infer-UI-message helper on the agent type, then pass that type to the chat hook and the route handler. Render each tool part by its name (for example tool-web search or tool-bash) with its typed input and output, including pending states. *When:* When building a chat UI that shows tool calls live and needs type safety for tool inputs and outputs.
- **Named persistent sandbox per session** — Create or get a sandbox by a stable name (for example tied to a user or session ID). The platform reuses the active instance or starts a new one from the snapshot. Your code never manages sandbox lifecycle. *When:* When an agent needs files and state to persist across many requests but you do not want to run your own save and restore logic.
- **Bash-only tool for a coding-style agent** — Expose one bash tool whose execute function runs the command in the sandbox and returns stdout, stderr and exit code. Keep the description detailed, since the model uses it to decide when to call the tool. Add instructions on when to use it. *When:* When the agent works on files or code, and a single general tool covers most needs.
- **Call options plus runtime context injection** — Define a Zod schema for per-call inputs (sandbox, customer tier). Pass it to the agent and set context in a prepare-call hook that runs once per agent run. Tools read the context from the execute function's second argument. *When:* When the same agent definition needs different resources or model choices per request, such as per-customer model tiers.
- **File-backed memory injected into the system prompt** — Store facts in memories.md in the sandbox. In the prepare-call hook, read the file and append it to the instructions under a clear heading. Tell the agent what to save, what not to save, and what counts as a repeatable task. *When:* When you want simple, inspectable, editable long-term memory without a vector store.
- **Per-step hook for message slicing** — Use the prepare-step hook, which runs before every model step and receives the full aggregated messages. Return a modified message list, for example the last five messages after step 20. The hook is a pure function, so the full history is still available at the end. *When:* When a long run needs a hard cap on context. The tradeoff is that the input cache is invalidated each time you trim history.
- **Subagents and handoff instead of compaction** — Run self-contained sub-tasks in a subagent with its own context. Return only a short summary (about 1,000 tokens) to the main thread. Add a handoff tool that lets the agent pass curated context into a new thread. *When:* When tasks can be split off, and when summarization or compaction of the main thread would be lossy.
- **Plan file with objective and checkboxes** — Have the agent create a plan file in the sandbox with the objective at the top, followed by steps it checks off as it goes. Keep a research directory for collected material. The agent re-reads the plan each step. *When:* For long multi-step tasks where the agent loses track of its goal as the context grows.

## Numbers
- Coding agent ran a single turn for 104 minutes, with 316 tool calls, 29 files changed, and used 32% of the GPT-5.4 context window with zero compaction (speaker's own agent, one example run). ([39:20](https://youtu.be/wflNENRSUb4?t=2360))
- Speaker reports a 95% cache-token read ratio on his coding agent after about four months of daily use (14 hours a day). ([43:25](https://youtu.be/wflNENRSUb4?t=2605))
- Internal background agent used by 23 people and about 3.8 billion tokens in roughly one to two months, with about 91% cache read and about 350 PRs (the PR count excludes some closed PRs). ([1:07:45](https://youtu.be/wflNENRSUb4?t=4065))
- A subagent used about 30,000 tokens of work and returned about 500 tokens to the main thread, keeping the main thread near 7,000 tokens. ([1:07:45](https://youtu.be/wflNENRSUb4?t=4065))
- A customer support agent reduced support tickets by about 90% (the speaker said 'I think 95%', so the exact figure is uncertain). ([29:42](https://youtu.be/wflNENRSUb4?t=1782))
- Speaker suggests subagent summaries be about 1,000 tokens each. ([40:48](https://youtu.be/wflNENRSUb4?t=2448))
- Earlier context trimming kept the window between 40% and 60% used. ([39:20](https://youtu.be/wflNENRSUb4?t=2360))

## Hot takes
- Bash is all you need for most agent tooling in practice.
- Memory is a file in the sandbox plus deterministic injection into the system prompt, not necessarily a vector store.
- With million-token windows, compaction and per-step pruning cost more in cache loss than they save; prefer subagents.
- Negative instructions ('do not do X') in agent prompts backfire; phrase rules positively.
- The system prompt is not a 2023 technique; it is still one of the core levers in 2026.
