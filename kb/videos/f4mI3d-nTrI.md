> Walkthrough of the MCP 2026-07-28 spec, which makes the protocol stateless: no handshake, no session IDs, explicit state handles, input-required round trips, and official tasks for long-running calls.

## Summary
The host explains MCP's 2026-07-28 spec release, which removes the initialize/initialized handshake and the MCP session ID header so every request is self-contained. He walks through the old failure mode: a session pinned to one instance causes 400 "session not found" errors behind a load balancer, and sticky sessions or a shared Redis store add latency and cost. With stateless requests, plain round-robin load balancing and failover work, and servers on platforms like Cloudflare Workers or Cloud Run can scale to zero. The spec also adds MCP method and MCP name HTTP headers for gateways and firewalls, plus TTL and cache-scope hints on list calls. Handshake data now rides in a per-request meta field, with an optional serverDiscover method for capability discovery. For state, the recommended pattern is an explicit handle the tool mints and the model passes back. Server-initiated questions become an input-required result that the client answers and retries with echoed request state. Long-running calls use the tasks extension, now official. The breaking changes come with a 12-month minimum deprecation window, and SDKs have moved to v2 with a codemod for renames. The video is a spec changelog walkthrough with no code shown and no benchmarks; the claims are the spec's, not independently tested.

## Key ideas
- **The old stateful MCP ties a client to the instance that issued its session ID, so scaling out breaks requests with 400 'session not found' errors.** — The initialize call mints a session ID that every later request must carry. Behind a load balancer with three instances, follow-up requests can land on an instance that never saw the session. Sticky sessions or a shared Redis store were the workarounds, and both add latency and cost. ([0:00](https://youtu.be/f4mI3d-nTrI?t=0))
- **The 2026-07-28 spec removes the handshake and the session ID header, so each request is independent.** — Two proposals do this: one removes the initialize and initialized handshake, the other removes the MCP session ID header and the protocol-level session. The captions show the proposal IDs as SCP-2575 and SCP-2567. ([0:58](https://youtu.be/f4mI3d-nTrI?t=58))
- **Stateless requests unlock plain round-robin load balancing, transparent failover, and scale-to-zero deployment.** — Any container can serve any request, so a standard load balancer works and a crashed instance is skipped without the client noticing. Servers on Cloudflare Workers or Cloud Run no longer need to hold connections open, so they can scale to zero. He cites Cloudflare saying MCP no longer needs Durable Objects. ([2:17](https://youtu.be/f4mI3d-nTrI?t=137))
- **Protocol info moves into a per-request meta field, and MCP method and MCP name headers let gateways decide without parsing the body.** — Protocol version and client capabilities ride in a meta field on each request. A server can describe itself through an optional serverDiscover method. The new MCP method and MCP name HTTP headers let a gateway, rate limiter or firewall route on those headers without reading the JSON body. List calls also gain TTL and cache-scope hints. ([2:17](https://youtu.be/f4mI3d-nTrI?t=137))
- **State is now an explicit application concern: a tool mints a handle and the model passes it back as an ordinary argument.** — Examples given are a basket ID or browser ID. The protocol does not manage state, which he calls more flexible. Authorization is also said to have been hardened in this release. ([3:09](https://youtu.be/f4mI3d-nTrI?t=189))
- **Server-initiated questions become a multi-round-trip flow instead of an open push stream.** — The server returns an input-required result with a typed prompt, such as a boolean 'are you sure?', plus a request-state payload with the serialized call context. The client asks the user, then reissues the original call with the answers and the echoed request state. Any instance can resume the work, and the motivation given is that unsolicited prompts were a UX and security problem. ([4:12](https://youtu.be/f4mI3d-nTrI?t=252))
- **Long-running tools use the official tasks extension: write the job to a store as working, return immediately, and let the client poll or subscribe.** — The example is a refund tool. The task state is stored in a database, the async job starts, and the response tells the agent it is running. The client then uses tasks get or a subscription to track progress and fetch the result. ([5:10](https://youtu.be/f4mI3d-nTrI?t=310))

## Techniques
- **Stateless MCP tool calls** — Drop the initialize and initialized steps and the session header. Send each tool call as one self-contained request. Put protocol version and client capabilities in the per-request meta field, and optionally use serverDiscover to read server capabilities. *When:* Building or upgrading an MCP server that runs behind a load balancer, or one that should scale to zero on serverless.
- **Explicit state handle** — Have a tool create a handle such as a basket ID or browser ID and return it. The model passes that handle back as a normal argument on later tool calls. Keep the state store in your own backend, not in the protocol. *When:* A workflow needs multi-step state across calls, and the server runs on several instances or restarts.
- **Input-required round trip** — When the server needs confirmation, return an input-required result with a typed question (for example a boolean) and a request-state payload holding the serialized call context. The client collects the answer and reissues the same call with the input responses and the echoed request state. Any instance can handle the retry. *When:* Destructive or sensitive tool calls, such as deleting a file, that need a human yes/no without a persistent push channel.
- **Async tasks for slow tools** — Write a task record with status working to a database, start the background job, and return at once with a message saying the work is running. The client polls with tasks get or subscribes to updates, then reads the final result. *When:* Tool calls that take longer than a reasonable blocking request, such as refunds or batch jobs.
- **Gateway routing on MCP headers** — Read the MCP method and MCP name HTTP headers in the proxy, rate limiter or firewall to route, throttle or allow requests without parsing the JSON-RPC body. *When:* An MCP gateway or proxy that applies per-tool policy and needs lower latency.
- **Cache hints on list calls** — Use the TTL and cache-scope hints on tool, prompt and resource list responses so the client knows how long a list stays fresh and whether it can be shared across users. *When:* Serving tool lists to many clients, or deciding whether a cached list can be shared across tenants.
- **SDK migration** — Move to the v2 SDKs. For TypeScript, use the separate server and client packages in place of the monolithic package, and run the codemod for the standard API renames. Plan for the minimum 12-month deprecation window on the old features. *When:* Upgrading any existing MCP server or client before the old features are removed.
