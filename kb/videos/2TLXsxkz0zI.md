> Chris Parsons runs a live workshop on Ralph loops: re-running Claude Code on fresh context until work ships, fed by ticket files, a sequential queue, and reversibility limits on unattended agents.

## Summary
Chris Parsons (Cherrypick) argues that agents are already loops (read, decide, call a tool, repeat), and that skills plus loops beat complicated n8n-style workflows that were brittle to maintain. He traces the "Ralph loop" to Jeffrey Huntley: give the same prompt again after the agent says it is done, because re-runs often catch missed work, and recent models (he says from about late 2025) make this work. The live demo is a toy Pomodoro CLI with flat-file tickets; he shows a stop-hook version failing, then a bash while-loop that starts a fresh Claude session per ticket. His biggest lesson: pointing six or seven parallel agents at a dependency graph of tickets produced duplicated work, so he switched to "pick the next most important ticket" run one at a time, with the AI working out dependencies itself. The rest of the talk covers the prompt as the real lever (definition of done, recovery checks, TDD, a simplify pass, git discipline), using a fresh-context subagent to review instead of self-review, and a reversibility rule for unattended work (draft but never send, stop and report at irreversible steps). He ends with personal-scale loops (a 15-minute heartbeat, a 6am briefing, a project-based worker), his views that spec-driven development risks fossilising today's workflow and that the real bottleneck is human review, and a theory-of-constraints point about fixing release and review first.

## Key ideas
- **An agent is already a loop: it reads context, picks a step, calls a tool, and repeats until it decides it is done.** — He argues that a skill-driven Claude Code session replaced a brittle multi-node n8n newsletter workflow that failed every Monday. The better pattern is a simple loop with good context, not orchestration graphs. ([6:11](https://youtu.be/2TLXsxkz0zI?t=371))
- **Ralph loop: re-run the same prompt after the agent claims completion.** — The idea comes from Jeffrey Huntley. A re-run often finds a missed step, such as a status update or a test. He says newer models (GPT-5.x and Claude Opus/Sonnet 4.6 onward) are much better at noticing they are actually done, which made this practical. ([8:34](https://youtu.be/2TLXsxkz0zI?t=514))
- **Use a fresh context per unit of work.** — A stop hook that re-runs the same command kept stopping early. A bash while-loop that starts a new Claude session per ticket works better, because state lives in repo files (tickets, git, tests) rather than chat history. ([17:29](https://youtu.be/2TLXsxkz0zI?t=1049))
- **Do not hand a dependency graph to parallel agents; run one ticket at a time and let the AI pick the next most important one.** — Six or seven parallel agents over a complex ticket graph duplicated work and fought over shared tickets, which he likens to 1990s waterfall requirement handoffs. The AI can work out dependencies on the fly. Parallelism is not the bottleneck; the human keeping up is. ([23:53](https://youtu.be/2TLXsxkz0zI?t=1433))
- **The prompt and the feedback loop are the real levers.** — The loop has no magic. Improve it after each run: say what done means for this project, how to run tests, when to stop, and how to check git state. Add a simplify/refactor pass at the end. Keep the prompt in a skill under git so each change is versioned. ([32:32](https://youtu.be/2TLXsxkz0zI?t=1952))
- **Self-validation in the same context confirms the agent's own work; use a fresh subagent to review.** — A review step in the same context just pats itself on the back (confirmation bias). A subagent starts with a small, clean context and finds more problems. Claude's bundled simplify skill runs three subagents over recent changes. ([54:55](https://youtu.be/2TLXsxkz0zI?t=3295))
- **Give unattended agents a reversibility rule and a stop-and-report contract.** — Rule: if an action is not reversible without embarrassment, do not do it. Agents draft emails and posts but never send. Workers stop at irreversible steps or when context runs low, write status into the project file, and never close projects themselves. ([1:06:18](https://youtu.be/2TLXsxkz0zI?t=3978))
- **Automated feedback (tests, end-to-end checks, screenshots) is what lets a human step out of the loop, and review remains the bottleneck.** — He trusts AI for linting and tests but still reads diffs for security or customer-data code. Playwright end-to-end tests and screenshot checks help, though UI checks worked about 50% of the time for him. Adversarial reviewer agents still leave him reviewing a large backlog. ([1:42:41](https://youtu.be/2TLXsxkz0zI?t=6161))

## Techniques
- **Bash while-loop over fresh Claude sessions** — A shell loop calls claude once per iteration with a fixed prompt, such as 'implement the next most important ticket using TDD, mark it done, commit'. Each run starts with a clean context. A git reset lets you restart from a known point. *When:* Sequential backlog work on a project with tests, where you can watch and stop the run. Not for production without observability.
- **Next-most-important-ticket selection over flat markdown tickets** — Keep tickets as markdown files in the repo with a status field. Prompt the agent to read all tickets, choose the next most important one (dependencies included), implement it, mark it done, and commit. Avoids hand-written dependency graphs. *When:* Small to medium backlogs where a human cannot keep a dependency graph current, and when running one agent at a time.
- **Recovery check for mid-flight work** — On start, check git state. A dirty tree with passing tests may be finished but not marked done. A dirty tree with failing tests is probably mid-flight and broken, so discard or treat it differently. *When:* Any loop that can crash or be interrupted and restart without a human looking at state.
- **Reversibility gate with stop-and-report** — Put a rule in the loop's skill: reversible actions proceed, irreversible ones (send email, post, deploy, close) are only drafted. The agent writes its status and questions into the project file for human review, then stops. *When:* Unattended agents that touch external communications or production state.
- **Fresh-subagent adversarial review** — After the dev agent finishes, start a separate reviewer subagent with a small context and the spec. Pass its findings back to the dev agent for another iteration. Do not let the same context review its own output. *When:* Any agent-written change where confirmation bias could hide defects.
- **Claude /loop for timed repetition** — Inside Claude Code, /loop with an interval (for example every minute or every hour) uses a cron-style scheduled task. Each tick runs a prompt such as 'build the next ticket' or 'check Linear for new bug reports'. The session can run for days and needs refreshing. *When:* Recurring background work in one session, and when you do not want to write your own shell loop.
- **Resume a project in an interactive session** — A shell alias starts Claude with a project's context file loaded. The agent interviews the human to extract the information needed for a piece of writing or spec, and the output is saved back into the project. *When:* Work that needs human judgement or taste, where you want the AI to draw out your thinking instead of drafting for you.
- **Simulated audience personas run in parallel subagents** — Build personas from transcripts and survey responses. Run each persona as a parallel subagent to critique a draft from a different viewpoint, then ask for improvements. *When:* Editorial feedback on content, or any review where a fresh perspective helps.
- **Nightly session digest** — A nightly job reads all of the day's Claude sessions across machines and writes a JSON file plus a short paragraph per session, for tracking work and improving the system. *When:* When you run many agent sessions and need an audit trail or a record of what was done.

## Hot takes
- Spec-driven development at the extreme takes us back to waterfall; prefer just-in-time specs.
- Pointing parallel agents at a big dependency graph is a waterfall recreation; run one sequential loop first.
- Do not give agents tokens to burn for speed; with a Max plan, optimise for your own time rather than token cost.
- Parallel agent orchestration (for example Gastown) solves a problem most teams do not yet have; the bottleneck is spec and review.
- Do not trust AI with security or customer data; still read the diffs.
- If your team is slow with AI, the constraint is probably release or review, not coding speed; fewer, smaller teams may help.
