> Breakdown of the eMudra CA incident: eight intermediate CA private keys were trivially guessable (one was just 4). Browsers blocked them, but non-browser TLS clients that trust on-disk CA bundles stayed exposed.

## Summary
On October 17, 2026, a researcher reported that the private keys of eight eMudra intermediate CAs were compromised. Six were TLS issuing CAs and two were code-signing CAs, all created in April 2025 and cross-signed by Sectigo. The keys are P-384 EC keys that were 47 zero bytes followed by one byte, so each could be found by computing k*G for small k until it matched the public key. The speaker reproduced this with a short Python script; all eight were recovered in under a second. The cause, per eMudra's incident report, was a key-ceremony test that created a second key pair on the HSM with a similar name, and the wrong one was used to issue the certificates. Warning signs existed from June 2025, when Sectigo reported invalid signatures on eMudra's revocation lists and eMudra re-signed them with the weak keys instead of investigating. Browsers are protected because none of these certificates appeared in Certificate Transparency logs and browsers require CT logging. Non-browser tools (curl, Python, Node, Go, Git) trust whatever CA bundle is on disk and generally do not check CT or revocation, so a forged api.stripe.com certificate was reportedly accepted on the Linux and macOS machines a researcher tested. Remediation so far: Chrome, Firefox and Safari blocked the intermediates within hours, Apple and Microsoft followed within three days, Cloudflare shipped client updates with no signs of exploitation, Go shipped an emergency release that blocks the intermediates, and Mozilla is removing the eMudra root (Chrome follows on October 27). About 30,000 certificates must move before sites break. The speaker's main lesson is that cryptography cannot detect missing randomness, so a process must verify that the key in a certificate is the one intended.

## Key ideas
- **The compromised eMudra keys were not brute-forceable in theory but were trivial in practice.** — A random P-384 private key has roughly 10^115 possibilities, but these keys were 47 zero bytes plus one byte, so only 256 values existed. Recovery means computing 1*G, 2*G, 3*G and so on until the public key matches. ([1:09](https://youtu.be/yW1RnJ5oaMk?t=69))
- **The eight recovered keys were 4, 56, 66, 115, 155, 156, 230 and 237.** — A key of 4 is still a valid point on the curve and passes structural checks, so the certificates look normal. Certificate validation alone does not reveal the problem. ([2:12](https://youtu.be/yW1RnJ5oaMk?t=132))
- **The root cause was a key-ceremony mistake on the HSM, not a cryptographic weakness.** — Per eMudra's incident report on Mozilla's bug tracker, a ceremony changed to test key export created a second key pair with a similar name, and the wrong one was used when generating the certificate. ([2:12](https://youtu.be/yW1RnJ5oaMk?t=132))
- **Warning signs were ignored for about 16 months.** — In June 2025 Sectigo reported invalid signatures on eMudra's revocation lists, because they were signed with strong keys that did not match the weak keys in the certificates. eMudra re-signed the lists with the weak keys instead of investigating. ([2:12](https://youtu.be/yW1RnJ5oaMk?t=132))
- **Browsers were protected by Certificate Transparency, but the rest of the software ecosystem was not.** — None of these intermediates appeared in CT logs, and Chrome, Firefox and Safari reject unlogged certificates. Curl, Python, Node, Go and Git trust whatever CA bundle is on disk and do not check CT or revocation. A researcher reportedly forged an api.stripe.com certificate that these tools accepted on Linux and macOS. ([3:40](https://youtu.be/yW1RnJ5oaMk?t=220))
- **Devices that never receive updates stay exposed until the certificates expire.** — Smart TVs, routers and similar devices may trust these intermediates until July 2039, since they cannot be patched. ([3:40](https://youtu.be/yW1RnJ5oaMk?t=220))
- **The lesson is process verification, not better cryptography.** — Cryptography cannot warn you when randomness is missing. The real protection is a process that confirms the key in a certificate is the one that was meant to be generated, and mismatched signatures should be treated as an emergency. ([6:18](https://youtu.be/yW1RnJ5oaMk?t=378))
- **Remediation has been broad but uneven.** — Cloudflare shipped updates to WARP, the 1.1.1.1 app and Tunnel on October 20 and found no signs of exploitation. Go pushed an emergency release that blocks the intermediates in its standard library. Mozilla is removing the eMudra root, and Chrome follows on October 27. About 30,000 certificates need to move within about a week. ([5:07](https://youtu.be/yW1RnJ5oaMk?t=307))

## Techniques
- **Check EC public keys for small private keys** — For an EC public key Q on a known curve, compute k*G for k = 1, 2, 3, ... and compare each result to Q. A match within a small range means the private key is trivially recoverable. The speaker used a short Python script on the certificates from Mozilla's announcement and recovered all eight keys in under a second. *When:* Auditing any CA, certificate or EC key you did not generate yourself, or screening intermediates after a suspected key-generation incident.
- **Upgrade on-disk CA bundles and the Go toolchain, then rebuild** — Bump the Python certifi package to 2026.10.19 (the captions read 'certified'; verify the package name), upgrade Go to 1.27.3, and rebuild container images so the fixed trust store is baked in. *When:* CI runners, build containers and servers where tools like curl, Python, Node, Go and Git rely on the system or bundled CA store, since these clients do not get browser-side CT or revocation protection.
- **Verify client trust against a known-bad test host** — Run curl against the test host under g3bemudra.wehaveaproblem.com (the auto-captions garble the exact hostname, so confirm it from the video description or Mozilla's report). A certificate error means the client now rejects the bad chain, and the speaker says that means the client is safe. *When:* After patching machines, containers or CI images, to confirm that outbound TLS clients reject the compromised intermediates.
- **Verify key provenance during CA and HSM key ceremonies** — Before signing, confirm that the key pair on the HSM used for issuance is the one intended for that certificate, by checking identity and public key, not just name. Compare the certificate's public key with the expected key from the ceremony record. *When:* Running or auditing a CA, or any HSM-backed signing process where similarly named key pairs can exist.
- **Treat signature mismatches on revocation lists as incidents** — If a CRL or similar list fails to verify against the issuing key, halt and investigate the key mismatch. Do not re-sign the list with whatever key is available. *When:* Monitoring CA-published revocation data, or operating any signing system that publishes trust artifacts.

## Hot takes
- Browsers are fine because of CT and revocation, but almost everything else (curl, Python, Node, Go, Git, CI runners holding cloud credentials) trusts on-disk CA bundles without those checks.
- Re-signing revocation lists with the weak keys after a verification failure is described as the line between an honest mistake and gross negligence (a Hacker News quote the speaker partly endorses).
- Cryptography cannot detect missing randomness, so the real protection is a process that confirms the certificate's key is the intended one.
