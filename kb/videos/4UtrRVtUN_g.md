> Greptile co-founder Daksh Gupta walks through building a production AI code review agent: sandboxed test runs, historical bug catalogs, model inversion, a living code wiki for context, and tiered model routing to cut per-PR cost.

## Summary
Daksh Gupta (co-founder of Greptile) lays out what breaks when a team builds its own AI pull-request review agent and how to fix each failure. The naive setup (sandbox, agent, webhook, post comments) misses bugs, lacks codebase context, costs $3 to $25 per PR, and leaves nitpicks that coding agents then over-apply. His fixes are a specific bug-type catalog, a historical-PR eval set, reviewing code with a different model family than the author, a knowledge base indexed by flow instead of grep, feeding in docs and tickets, computer-use end-to-end testing in dependency-rich sandboxes, and routing about 20% of work to frontier models with cheap models for the rest. The talk is practitioner content from a vendor, so the numbers are self-reported and the Greptile pitch is explicit.

## Key ideas
- **A naive review agent (sandbox, agent, PR webhook, post comments via GitHub review API) runs quickly but fails on four counts: it misses bugs, lacks codebase context, costs $3 to $25 per PR, and produces nitpicks.** — Speaker says the first version takes about five minutes to return feedback. Bugs are called 'fractally infinite'. Per-PR cost is quoted as $3 to $25 for coding-agent review. Nitpicks matter for two reasons: they bury real issues for human readers, and coding agents over-apply them, leaving defensive code. ([2:38](https://youtu.be/4UtrRVtUN_g?t=158))
- **Prompt fixes come first: list the specific bug types that have caused incidents, and tell the model explicitly to skip nitpicks.** — Mine past outages and incidents to find the bug classes the codebase is most prone to, then write those into the prompt. Name nitpick categories (for example, defensive error handling) to exclude. Small prompt edits can swing comment volume a lot, so you cannot tell whether a missed bug is a real absence. ([5:06](https://youtu.be/4UtrRVtUN_g?t=306))
- **Build a historical PR eval set: replay past incident-causing PRs through each agent version and measure catch rate.** — Bugs are rare, about 1 in 1,000 PRs has a catastrophic bug per his data. Without a labeled set you will not notice regressions for a long time. About 80 to 90% of bugs repeat prior mistakes, but novel failure modes need a continuously updated set. ([7:48](https://youtu.be/4UtrRVtUN_g?t=468))
- **Use model inversion: review code with a different model family than the one that wrote it.** — He says Claude-written code has about 3x more one-off errors and GPT models produce more auth bypasses, which he attributes to post-training. Same-model review misses bugs that fail in the same way at generation time. He reports a 10% higher catch rate when the models are flipped. Detect the author model from fingerprints such as Codex branch prefixes or Claude co-author lines, and fall back to heuristics or telemetry for the rest. ([9:03](https://youtu.be/4UtrRVtUN_g?t=543))
- **Replace grep-and-read-files context gathering with a pre-built knowledge base indexed by subsystem (flows, diagrams, file lists).** — He argues grep is imprecise and token-heavy. Most coding-agent tokens are repeated grep, file-read and cache-write operations. Auth bypass detection needs concrete knowledge of whether a code path is authenticated. His KB stores each subsystem with its flows and involved files, so the agent reads only what it needs. ([11:19](https://youtu.be/4UtrRVtUN_g?t=679))
- **Ambiguous intent causes correct-looking but wrong code, so supply docs and tickets as context too.** — He names Jira, Linear, Confluence and Notion as the sources that matter most. Greptile's approach is a living wiki that unifies code knowledge, production telemetry, logs and roadmap, and is used both to supply context and to narrow code search. ([12:43](https://youtu.be/4UtrRVtUN_g?t=763))
- **Test the change end to end: run the app in a dependency-rich sandbox and let a computer-use agent click through the flows.** — Reading the diff can miss UI bugs, such as a button hidden on iPhone. You need a dev box, PR-branch dependencies, a simple build script that brings up the stack, and a flow map documenting auth and signup. He says computer use has become good enough that end-to-end QA is nearly solved, and he notes this setup is the hardest part to get right. ([14:07](https://youtu.be/4UtrRVtUN_g?t=847))
- **Cut cost by routing: frontier models for the roughly 20% of critical steps, smaller models for exploration, context selection and file reads.** — Greptile runs about 20 subtasks, each with its own model choice. Examples: a small model finds context, a lightweight computer-use model drives user flows, and a frontier model analyzes bugs, runs the review and submits. He says 70 to 80% of the savings come from swapping out simple tasks for simple models. He warns that without a large eval set you can silently lose bug-catching quality. ([16:28](https://youtu.be/4UtrRVtUN_g?t=988))

## Techniques
- **Prompt the reviewer for a catalog of bug types, not generic review** — Analyze past outages and incidents to find the bug classes this codebase produces most often. Put that catalog in the review prompt, and state explicitly that nitpicks (style, pedantic error-handling critiques, 'defense in depth' suggestions) must not be reported. *When:* First fix to try, before any infrastructure work, once you have incident history.
- **Historical-PR regression eval for the review agent** — Collect PRs that caused past incidents. Run each version of the review agent over the set and measure how many it catches. Re-run on every prompt or model change. Keep updating the set as new bug types appear. *When:* Before tuning prompts or swapping models, so the change is measured instead of guessed.
- **Model inversion for reviews** — Detect which model wrote the PR from fingerprints: Codex branch naming, Claude co-author trailers in commit or PR text. Choose a reviewer from a different model family. Where no fingerprint exists, fall back to heuristics or dev-machine telemetry. *When:* When you run the same models for authoring and review, and the author model can be identified for most PRs.
- **Codebase knowledge base indexed by subsystem** — Walk the codebase and catalog each subsystem, for example authentication. For each, record how it works, its flows (a diagram helps), and every file involved. The review agent consults the entry first and reads only the listed files. *When:* When grep-based exploration is burning tokens or missing context such as auth state.
- **Dependency-rich sandbox with computer-use end-to-end tests** — Give each PR its own sandbox (Firecracker, or a vendor sandbox) with the stack started from a simple build script and the PR branch's dependencies. Write a flow map of the app. Let a computer-use agent with vision run the flows and check layouts, for example at iPhone widths. *When:* For UI or user-flow changes that reading the diff cannot verify.
- **Tiered model routing across review subtasks** — Split the review into subtasks such as context retrieval, file-relevance re-ranking, computer-use testing, bug analysis and submission. Use a frontier model for bug analysis and submission, and a cheap or small model for retrieval, re-ranking and exploratory reads. Keep the eval set in place so cheaper models do not quietly lower the catch rate. *When:* When review cost is too high, and you have an eval set to confirm the cheaper models still catch bugs.
- **Model-agnostic harness for the review agent** — He recommends a model-independent open-source harness (he names OpenCode and Pi) instead of a single vendor's coding CLI, so the model can be swapped per subtask. *When:* When you plan to route between model families or inversion needs both families available.

## Numbers

## Hot takes
- Grep is not a solution for codebase context. The speaker argues it is imprecise and burns tokens, and that a pre-built subsystem index is better.
- Same-model review is worse than model inversion. He says reviewers fail the same way authors do when the model is the same.
- End-to-end QA through computer use is nearly solved for the first time (his claim, 'nearly solved').
- The talk is a vendor pitch with an explicit ask. Greptile offers to build review agents for companies free when they are a poor fit, and the close steers viewers toward its paid product. Use the technical content, but treat the figures as self-reported.
