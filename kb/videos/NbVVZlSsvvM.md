> Step-by-step Node.js tutorial for OpenTelemetry: NodeSDK bootstrap, auto-instrumentation, manual spans, metrics and Winston logs, then switching exporters to an OTLP collector and a Better Stack backend.

## Summary
The presenter walks through instrumenting a small Express dice-roll API with OpenTelemetry in Node.js (ESM, run with tsx). They first bootstrap the NodeSDK in a separate instrumentation.ts file and load it before the app with a --import flag, using console exporters for debugging. They then show what the getNodeAutoInstrumentations() package produces for free (HTTP/Express spans and a request-duration histogram) and add manual spans, nested spans, attributes, span events, error status and recordException. Next come custom metrics (a counter and a histogram) and Winston logs that pick up trace context automatically. The last third swaps the console exporters for OTLP exporters, runs an OpenTelemetry Collector in Docker with a Better Stack exporter config, and builds a dashboard chart from the custom counter. The content is practical and reproducible, but the backend walkthrough is a Better Stack product tour, and the speaker notes the JS logs API is still under development.

## Key ideas
- **Bootstrap everything in one instrumentation file that runs before the app** — NodeSDK in instrumentation.ts takes traceExporter, a PeriodicExportingMetricReader, instrumentations, resource and logRecordProcessors, then calls sdk.start(). It must load before app code so it sees the whole lifecycle (node --import for ESM, --require for CommonJS). ([2:12](https://youtu.be/NbVVZlSsvvM?t=132))
- **Console exporters are for diagnostics only** — ConsoleSpanExporter, ConsoleMetricExporter and ConsoleLogRecordExporter just print telemetry. For anything beyond local debugging, the speaker switches to OTLP exporters that send to an OpenTelemetry Collector. ([2:12](https://youtu.be/NbVVZlSsvvM?t=132))
- **Auto-instrumentation gives HTTP and Express telemetry with one line** — getNodeAutoInstrumentations() covers many popular libraries (Express, HTTP, Redis, AWS Lambda, logging libraries). With no custom code, the speaker's first request already produced an HTTP span with URL, method and status, plus a request-duration histogram. ([4:36](https://youtu.be/NbVVZlSsvvM?t=276))
- **Get tracers and meters per logical unit, not one exported global** — The OpenTelemetry tip the speaker repeats: call trace.getTracer(name, version) or metrics.getMeter(name, version) where a unit of work lives (for example dice-lib in dice.ts), instead of exporting one shared instance. The name is the instrumentation scope. ([11:16](https://youtu.be/NbVVZlSsvvM?t=676))
- **startActiveSpan handles context and parent-child links** — tracer.startActiveSpan sets the span as active so nested calls become children automatically. The speaker wraps roll-once inside a per-roll span, passes the loop index in for a readable span name, and calls span.end() before returning. ([13:39](https://youtu.be/NbVVZlSsvvM?t=819))
- **Errors need both a status and a recorded exception** — Spans default to UNSET. Set ERROR explicitly (with a message) for failures, and call span.recordException(e) so the exception shows up as a span event. OK is reserved for explicit success. ([18:32](https://youtu.be/NbVVZlSsvvM?t=1112))
- **Counters and histograms cover custom metrics, and the periodic reader exports them** — meter.createCounter(...).add(1) gives a monotonically increasing count. meter.createHistogram(name, {description, unit, valueType}).record(ms) gives a distribution. Values appear on the periodic export interval, not per call. ([27:50](https://youtu.be/NbVVZlSsvvM?t=1670))
- **Winston logs get trace context from auto-instrumentation** — With the Winston auto-instrumentation and the OTel logs SDK installed, plain logger.info calls come out with service name, version and host/process attributes injected. The speaker says the JS logs API is still under development but expects the pattern to hold. ([26:45](https://youtu.be/NbVVZlSsvvM?t=1605))
- **Export via OTLP to a collector, which forwards to the backend** — Swap each console exporter for its OTLP equivalent (trace, metric, log). The collector runs in Docker with a config that has an OTLP receiver, an exporter for the Better Stack source token, and an optional Prometheus receiver that scrapes the collector's own metrics. ([31:21](https://youtu.be/NbVVZlSsvvM?t=1881))

## Techniques
- **NodeSDK bootstrap file loaded with --import** — Create instrumentation.ts. Import NodeSDK from @opentelemetry/sdk-node. Pass traceExporter (ConsoleSpanExporter for now), metricReader: new PeriodicExportingMetricReader({exporter: ConsoleMetricExporter}), instrumentations: [getNodeAutoInstrumentations()], and resource: new Resource({[ATTR_SERVICE_NAME]: 'dice roll app', [ATTR_SERVICE_VERSION]: '1.0'}) using semantic-convention constants. Add logRecordProcessors: [new SimpleLogRecordProcessor(new ConsoleLogRecordExporter())]. Call sdk.start(). Run with `tsx --import ./source/instrumentation.ts source/app.ts` (the directory is spoken as 'source'). For Node without TypeScript use `node --import`; for CommonJS use `--require`. *When:* Any Node service you want traced, metered and logged. Load it before any application code so every module is instrumented.
- **Manual span per unit of work with startActiveSpan** — In the module: const tracer = trace.getTracer('dice-lib'). Wrap the logic: return tracer.startActiveSpan(`roll dice ${i}`, (span) => { const result = ...; span.end(); return result; }). Nested calls made inside the callback become child spans automatically. The speaker also shows passing a config object with an attributes key as the second argument to startActiveSpan. *When:* Business logic that should show up as its own step in a trace, such as one roll or one DB call inside a request.
- **Attributes and events on spans** — span.setAttribute('dicelib.rolled', result.toString()) for one attribute. Or startActiveSpan(name, {attributes: {'dicelib.rolls': rolls.toString()}}, fn) for several up front. Use semantic-convention keys where they exist. span.addEvent('some log', {'log.severity': 'error'}) adds a timestamped, human-readable event, which the speaker calls a primitive log. *When:* Recording inputs, outputs or notable moments without making a separate log line.
- **Error status plus recorded exception** — try { throw new Error('error') } catch (e) { span.recordException(e); span.setStatus({code: SpanStatusCode.ERROR, message: 'An error happened'}) }. Leave OK for explicit success and rely on the default UNSET otherwise. *When:* Any operation that can fail, so the trace shows an error status and the exception message in the span's events.
- **Counter and histogram with the meter API** — const meter = metrics.getMeter('dice-lib', '1.0'). Counter: const counter = meter.createCounter('dice-lib.rolls.counter'); then counter.add(1) in the loop. Histogram: const h = meter.createHistogram('http.server.duration', {description: 'distribution of http or server response time', unit: 'milliseconds', valueType: ValueType.INT}); time the function with Date.now() before and after; h.record(endTime - startTime). Use an UpDownCounter if the value can decrease. *When:* Business counts (rolls, jobs, retries) and latency distributions that you want on a dashboard. Counters for totals, histograms for latency percentiles.
- **Winston logs with auto-instrumented trace context** — npm install winston, the OTel logs SDK, and @opentelemetry/winston-transport. Keep logRecordProcessors in the NodeSDK config. In app code: const logger = winston.createLogger({...}) (no custom transport needed) and replace console.log with logger.info. The auto-instrumentation attaches the OTel transport and injects service and resource context. *When:* Adding correlated logs to an existing Winston-based service without changing the logger setup.
- **Switch exporters to OTLP and run an OpenTelemetry Collector** — Install the OTLP exporter packages for traces, metrics and logs (command shown on screen, not spoken). Replace ConsoleSpanExporter with OTLPTraceExporter, ConsoleMetricExporter with OTLPMetricExporter, and ConsoleLogRecordExporter with OTLPLogExporter. With default config they target a local collector; set a URL only if the collector is elsewhere. In the collector config, keep the OTLP receiver and replace the exporters section with the Better Stack exporter config (endpoint and source token pre-filled from the Better Stack docs). Optionally add a prometheus receiver for the collector's own metrics and list it under metrics receivers. Run the collector image in Docker with the config mounted (exact docker flags not spoken). *When:* Sending telemetry off the process to a real backend, instead of printing to the console.
- **Dashboard chart from a custom counter** — In the backend's chart builder, drag in the counter metric (dice-lib rolls counter total), set the aggregation to last value instead of average or rate, and save it to a dashboard. The speaker then shows the value rising from 80 to 148 after more requests. *When:* Verifying that custom metrics arrive end to end, and watching business counters over time.

## Hot takes
- The backend in the last third is a Better Stack product walkthrough, and the setup assumes a Better Stack account and source token. The speaker frames it as free to start, and there is no sponsor disclosure in the transcript.
- The speaker says the OpenTelemetry JavaScript logs API is still under development but expects the Winston pattern to keep working. Treat the logs setup as less stable than traces and metrics.
- Advice to call getTracer and getMeter where needed instead of exporting one shared instance is presented as an OpenTelemetry tip.
- The tutorial stays at the single-service level. It covers no sampling, no production config, no batch or retry tuning, and no collector pipeline beyond a default OTLP receiver and one exporter.
