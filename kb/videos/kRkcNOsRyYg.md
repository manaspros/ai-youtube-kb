> Neo4j workshop on graph shapes for agents over a lakehouse: a metadata semantic layer over the warehouse, a deterministic document-tree-plus-links graph, and Leiden community "themes" built without LLM labels.

## Summary
Zach Blumenfeld (Neo4j) runs a hands-on workshop, driven by Claude Code and a Neo4j course, on giving agents context over a lakehouse, with a fictional auto-repair chain as the scenario. He presents three graph "shapes": a connection shape that holds only BigQuery metadata and join paths as a semantic layer, an outline shape that loads documents as a containment tree with hierarchical URIs and link edges, and a themes shape that runs Leiden community detection over the document links. The core argument is that graphs answer estate-level questions (what is missing, what patterns recur) that semantic search cannot, because search only finds things that exist. He pushes a deterministic, non-LLM document load for structured manuals, and says it is idempotent and often faster than entity-extraction GraphRAG. He also recommends giving the agent the Neo4j CLI and vendor Cypher/GDS skills rather than relying on text-to-Cypher from model memory. The talk is heavily product-oriented (NeoCarta, Virtual Graph, Neo4j platform), no benchmarks are run, and he admits the agent sometimes takes a slow exhaustive path instead of the outline traversal.

## Key ideas
- **Three context shapes for a lakehouse: connection (semantic layer over structured warehouse tables), outline (document containment tree plus link edges), and themes (global clusters). Each answers a different question type.** — The speaker frames them as the course structure. The first is the structured side, the second a navigable table of contents over PDFs, the third a global view across the document graph. ([6:03](https://youtu.be/kRkcNOsRyYg?t=363))
- **Graphs are for estate-level questions, not single lookups. Semantic search can only match what is present, so it cannot prove a gap or a negative and struggles with corpus-wide pattern questions.** — Examples given: what documentation is missing for codes that occur in the field, and which recall groupings keep recurring. He says vector search can complement the graph but does not replace it. ([4:59](https://youtu.be/kRkcNOsRyYg?t=299))
- **Put only metadata in the graph for the warehouse case. The graph holds tables, columns and primary/foreign-key join paths, and the agent reads them to write SQL against data that stays in place.** — No ETL of rows. Full ETL into a graph is justified when you need graph-native performance (deep recursive joins, graph algorithms, embeddings). Security posture and sync cost often rule out moving operational data. ([26:31](https://youtu.be/kRkcNOsRyYg?t=1591))
- **Load already-structured documents deterministically with no LLM extraction. Containment edges, next-section ordering and named link edges come from parsing the documents, using regex in the demo.** — The speaker's claims: the load is idempotent (same docs give the same graph), often faster, and good enough when manuals share a consistent structure. He says messier sources may need GLiNER or an LLM. ([44:56](https://youtu.be/kRkcNOsRyYg?t=2696))
- **Hierarchical URIs act as node IDs and a navigation tool. Prefix matching gives subtree scoping, and a depth parameter gives subtree traversal, so the agent can walk the library like a book's table of contents.** — Full-text search runs first on document and section nodes, then a starts-with filter on the URI narrows results to a subtree. Folder nodes are kept out of the Lucene index. ([46:20](https://youtu.be/kRkcNOsRyYg?t=2780))
- **Themes come from Leiden community detection on the document-link graph, with no LLM labels. Labels are just the top shared link targets and most central documents, so output is stable across reruns on unchanged data.** — Sections are collapsed to document level before projection. Tightness is measured with conductance. Granularity is tuned with the gamma parameter (13 groups at default, 14 at gamma=2). The trade-off: labels are only as good as the existing titles and link names, and reruns on changed data can shift IDs. ([1:23:37](https://youtu.be/kRkcNOsRyYg?t=5017))
- **Spec-first agentic query writing. The author writes a markdown spec for the output shape and has the agent write Cypher against it using the Cypher and GDS skills. The spec also covers parameters such as traversal depth.** — He says this is how he writes complicated Cypher. The agent then emits a reusable script with the depth exposed as a parameter, not a hand-built tool. ([54:22](https://youtu.be/kRkcNOsRyYg?t=3262))
- **Use the vendor CLI and maintained skills instead of text-to-Cypher from model memory. The speaker warns that model memory returns outdated query patterns, while the skills carry current syntax and let the agent read the schema before querying.** — He says improvement over text-to-Cypher from a year or six months ago is large. The skills are installed through the Neo4j agent client in the dev container. ([1:39:03](https://youtu.be/kRkcNOsRyYg?t=5943))
- **Agents do not always take the efficient path. In one estate-level run the agent did an exhaustive full-text crawl instead of using the outline traversal, so shape guidance in the prompt matters for speed.** — He observed that when the outline was used, the run came back faster. He also says a graph is not a replacement for vector search, and a production system would combine lexical, vector and graph retrieval. ([1:51:28](https://youtu.be/kRkcNOsRyYg?t=6688))

## Techniques
- **Metadata-only semantic layer graph** — Pull warehouse schema metadata (tables, columns, PK/FK join paths, optional representative values) into a graph, expose it through an MCP server or CLI, and have the agent read join paths before writing SQL. Rows stay in the warehouse. *When:* Many tables with look-alike schemas where the agent gets joins wrong, and where moving the data is blocked by sync cost or security.
- **Deterministic document-structure graph** — Model library, folder, document and section nodes with a containment edge, a NEXT_SECTION ordering edge, and named LINKS_TO edges taken from in-document references. Parse with regex or simple NLP. Keep relationship names short and uniform (for example a single containment name for every level). *When:* Documents already have consistent structure and cross-references, and you want a fast, idempotent, LLM-free graph before considering entity extraction.
- **Hierarchical URI IDs for scoped search and traversal** — Encode the containment path into every node ID. Run a Lucene full-text query over document and section nodes, then apply a starts-with filter on the URI to scope the search to a subtree. Use a variable-length path query with an exposed depth parameter to fetch subtrees. *When:* You need cheap subtree-scoped search over a large document set without many extra graph hops, or you want the agent to navigate like a table of contents.
- **Semantic query expansion for full-text search** — Have the model generate synonyms or related failure terms (for example misfire or rough idle for an engine symptom), then search across those terms in the Lucene index. *When:* Users describe symptoms in different words than the documents use, and you want to avoid running several vector stores.
- **Structure-only community themes** — Project the document-level link graph into memory (collapse section-level links to documents), run Leiden, and label each cluster only with its top shared link targets, most central documents and conductance. No LLM summarisation. *When:* You need a stable, reproducible global view of a corpus that is cheap to run and can be rerun as data changes. Add LLM summaries only if the budget allows and the labels are too opaque.
- **Spec-driven Cypher generation with a vendor skill** — Write a markdown spec of the desired output shape and parameters, point the coding agent at the spec plus the vendor Cypher and GDS skills, and have it emit a parameterised script you can rerun. *When:* A non-trivial graph query is needed and you do not want to hand-write Cypher.
- **Agent with a database CLI for ad hoc graph reasoning** — Give the coding agent a CLI that runs queries and dumps the schema, so it can write custom queries for questions nobody anticipated. Keep the prebuilt shape scripts as fast paths. *When:* Questions span several shapes and the fixed tools are not enough.
- **Partial re-sync of a deterministic graph** — Re-ingest only changed documents, but also update inbound link references, because renaming a document changes URIs that other documents point to. *When:* The corpus changes often and a full reload is too slow. The speaker says he has tested this but did not show it.

## Hot takes
- Semantic (vector) search cannot prove that something does not exist, so estate-level gap questions need graph traversal.
- Text-to-Cypher from model memory produces outdated, bad Cypher; use vendor-maintained skills and the CLI instead.
- Plain regex is enough for consistently structured manuals, and LLM-based entity extraction is not always needed for a useful graph.
- Explicit node types for every entity (for example a parts node) matter less now that agents infer entities, but ontology-heavy domains such as life sciences still need them.
- Moving operational data into a graph is harder than it looks because of sync, bulk, and security posture; a metadata-only graph is often the better first step.
