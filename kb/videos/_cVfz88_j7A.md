> Risa Labs (oncology) walks through automating prior-authorization workflows end to end, using confidence-gated multi-agent routing so only some orders skip human review.

## Summary
Anant Shankhdhar of Risa Labs describes automating oncology prior-authorization: intake, eligibility and benefits verification, classifying each drug as no-auth-required (NAR), auth-on-file, or auth-required, then clinical review and submission to payers. The goal was to remove the human from some orders, but only where confidence is high. The system uses four agents (eligibility, auth, medical necessity, submission) with a deterministic decision engine in front. Payer-portal data is normalized and browser-automation (RPA) configs are generated by an LLM from a library of reusable actions, with a self-healing loop for production breakage. LLM-based drug classification is treated as non-deterministic, so it is only trusted when corroborated by two independent sources (prior authorization letters and a payer-rule knowledge base). Auth-required cases go through a medical-necessity agent that answers policy criteria from a patient biomarker graph and attaches confidence, escalating low-confidence cases to a clinician. The talk gives no accuracy, volume or cost numbers, so the "no touch share is growing" claim is unquantified.

## Key ideas
- **Scope of the workflow** — Prior auth runs as intake, eligibility and benefits verification, then a per-drug pathway decision (NAR, auth-on-file, or auth-required), then clinical review and payer submission. Bots run the steps, but a human reviewed every order before submission. The problem was finding which orders could go with no human touch. ([0:00](https://youtu.be/_cVfz88_j7A?t=0))
- **Four agents with a deterministic gate** — EV agent (eligibility), auth agent (drug pathway), necessity agent (clinical reasoning for auth-required drugs), and submission agent. Deterministic rules run first and halt orders that cannot proceed, so they never reach an LLM step. ([1:58](https://youtu.be/_cVfz88_j7A?t=118))
- **Unified portal and API layer plus LLM-generated RPA configs** — Insurance data is scattered across dozens of portals, APIs and documents. A coverage orchestrator picks the API or RPA path and returns a normalized coverage result. A repository of custom and popular actions lets an LLM generate the portal config, which cut development time. A self-healing loop detects broken automations during production and mitigates them. ([4:45](https://youtu.be/_cVfz88_j7A?t=285))
- **LLM classification is not trusted alone** — LLM extraction over patient notes is non-deterministic and was unreliable when the source data was thin. They added evidence: prior authorization letters from earlier runs, and a payer-level NAR knowledge base. Only when sources agree do they mark a drug auth-on-file or NAR. Some orders were eliminated completely this way. ([6:13](https://youtu.be/_cVfz88_j7A?t=373))
- **Payer-rule knowledge base as a SQL store** — The NAR knowledge base is a SQL database built from three inputs: LLM extraction over time-stamped payer documents (configurable per document type), historical behaviour per payer and drug, and regular portal checks. Each entry gives a drug-by-payer rule for a time period. All of it is configurable so a bad case can be overridden. ([9:59](https://youtu.be/_cVfz88_j7A?t=599))
- **Medical-necessity agent answers criteria with supporting and contradicting facts** — For auth-required orders the agent reads patient notes and the policy criteria. It queries a patient biomarker graph for each criterion, then an LLM produces an answered questionnaire listing supporting and contradictory facts, with a confidence score per answer. Only high-confidence answers move forward. The rest go to a clinician. ([11:33](https://youtu.be/_cVfz88_j7A?t=693))
- **Reuse beyond one workflow** — The necessity agent was generalized to answer any patient-level question for any workflow, and the other agents are being generalized the same way. The stated conclusion is that automation share grows per order, with reasoning added only for the auth-required cases. ([15:26](https://youtu.be/_cVfz88_j7A?t=926))

## Techniques
- **Deterministic-first gating before LLM steps** — Run rule-based checks (eligibility, coverage active or not) first and stop the order if it fails. Only pass the remaining orders to LLM steps. Unverifiable cases are flagged early, not guessed. *When:* Multi-step pipelines where cheap, certain checks can remove many items before expensive or non-deterministic steps.
- **Corroboration across independent sources before automating** — Treat an LLM extraction as a candidate. Mark it as final only when a second independent source (for example a prior approval letter, or a reference rule table built from documents and portal checks) agrees. Keep disagreeing cases in human review. *When:* Classifications where a wrong automated decision is costly and single LLM extractions are unreliable.
- **Confidence-gated escalation to humans** — Each automated answer carries a confidence score. Above the threshold it proceeds. Below it, the case goes to a clinician or reviewer. Every automated rule is configurable, with an override path so a bad case can be stopped. *When:* High-stakes decisions where the goal is to reduce review volume, not remove review entirely.
- **Evidence-structured questionnaire answering** — For each criterion in a policy, query a structured fact store (here a patient biomarker graph) for relevant facts. Pass those facts plus the source notes to an LLM. Ask for an answer with the supporting facts, the contradictory facts and a confidence score, not a bare yes or no. *When:* Checking free-text documents against structured policy criteria, where auditability matters.
- **LLM-generated integration configs from a reusable action library** — Keep a library of tested custom and common automation actions for portals. Have an LLM compose the per-portal config from those actions, not write integrations from scratch. Reuse the same pattern for submission integrations. *When:* Building many brittle third-party integrations where each one would otherwise be custom code.
- **Self-healing loop for production automations** — Monitor automations during production runs to detect failures (breakage), then apply a mitigation. The talk does not describe the mechanism beyond detect and mitigate. *When:* Browser or RPA automations that break whenever a portal changes.

## Hot takes
- Human-in-the-loop is kept, but only for low-confidence cases. The talk argues that automation should be gated by evidence and confidence, not by LLM output alone.
- The talk says LLM extraction is non-deterministic and cannot be blindly tested, which undercuts 'no touch' for any single-model classification. The corroboration step is the real safeguard.
- Results are unquantified: no accuracy, error rate, percent of orders auto-submitted or escalation rate. Treat the 'no touch share is growing' claim as anecdotal.
