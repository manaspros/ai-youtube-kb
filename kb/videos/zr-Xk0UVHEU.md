> Better Stack podcast with Warp DevRel Ben Holmes on why GUI-style wrappers around coding agents will beat TUIs, plus practical patterns for agent code review, cloud agents, and multi-agent delegation.

## Summary
Ben Holmes, a developer-relations lead at Warp and former Astro maintainer, talks with the Better Stack hosts about where AI developer tools are heading. He argues that the model matters more than the harness, and that terminal UIs are a fast but limited way to wrap CLI agents, so a GUI around the agent is the likely next step, though not a full IDE. He describes Warp's strategy of owning the scaffolding around third-party harnesses (file tree, diff view with line comments, voice input) rather than the agent itself. The second half covers Oz, Warp's cloud-agent platform: agents triggered from GitHub Actions, Slack or Linear, running in Docker-based environments that can span several repos. The guest shares his own solo workflow (two clones of a repo, Codex for implementation, a fresh-session review pass, and a "get it working, then get it right" review lens) and experimental sub-agent orchestration with message passing and a shared delegation document. Much of the material is product-adjacent and self-reported, and several numbers are rough estimates.

## Key ideas
- **The model matters much more than the harness** — Routing the same question through different harnesses makes only a small difference in the guest's experience. He later puts it at roughly 90% model and 10% harness, and calls this an estimate, not a measurement. He also says people pick models for how they feel to work with, not for benchmark scores. ([0:00](https://youtu.be/zr-Xk0UVHEU?t=0))
- **TUIs are the quickest way to bolt tooling onto CLI agents, but they are a poor rendering layer** — Tmux wrappers and vertical-tab wrappers give quick extras without leaving the terminal. The guest argues TUIs redraw the whole screen, which causes flicker and limits what can be displayed, so a native GUI is better for diffs and rich interaction. He expects the GUI to be agent-first, with diff and file views as secondary panels rather than a full IDE that waits to index. ([21:15](https://youtu.be/zr-Xk0UVHEU?t=1275))
- **Warp's bet is to own the scaffolding around the agent, not the agent** — Warp adds a file tree, a diff view where you can comment on a line and send the comment to Claude Code or Codex CLI, LSP hints, and a voice button. These are progressive-disclosure panels that you can hide to use it as a plain terminal. The guest contrasts this with Cursor, which owns the whole stack end to end. ([17:24](https://youtu.be/zr-Xk0UVHEU?t=1044))
- **Agent-legible APIs and code are still worth the effort** — The guest estimates that a well-designed API could cut a two-hour agent job to 10 to 20 minutes. He expects the value of API design to fall as compute gets cheaper, but says it still matters in the next year or two. He also argues for short READMEs or CLAUDE.md files (around 20 lines) where the code explains itself and docs sit at module boundaries. ([13:38](https://youtu.be/zr-Xk0UVHEU?t=818))
- **Use a separate review pass, ideally in a fresh session** — The guest has one agent write the code and another review it. In practice he starts a new conversation in the same directory with a saved prompt that asks the agent to review the work, make sure it is PR-ready, and simplify where that makes sense. Whether a different model reviews better than the writer is still an open question for him, and he cites a possible self-review bias. ([25:00](https://youtu.be/zr-Xk0UVHEU?t=1500))
- **Agents satisfice, so they need a simplify or review pass** — The guest argues that agents are trained to reach mission accomplished with just enough quality. They skip simplification and abstraction, so code review or a simplify skill is needed. He suggests two lenses: a first pass for get it working, then a second for get it right, which could be built as a hook, a skill, or baked into post-training. ([1:06:58](https://youtu.be/zr-Xk0UVHEU?t=4018))
- **Cloud agents suit repetitive and last-mile work** — Local agents do not fit code review or small tickets you can kick off from anywhere. Oz lets you trigger agents from a GitHub Action, Slack or Linear, and the guest describes the target workflow as starting an agent from a phone and getting a PR link back. The platform's REST API and SDK sit behind those triggers. ([39:57](https://youtu.be/zr-Xk0UVHEU?t=2397))
- **Environments are Docker-defined and can span several repos** — A cloud environment is set up from a Dockerfile plus the repos you clone into it. Warp's internal environments clone four or five repos (schema, server, client, docs) so one agent run can open PRs across all of them. The platform detects PR URLs and shows links instead of making you dig through logs. ([44:08](https://youtu.be/zr-Xk0UVHEU?t=2648))
- **Multi-agent orchestration is an early experiment: delegation plan, message passing, and a shared live doc** — A teased slash-orchestrate-style prompt asks the agent to produce a delegation plan and spawn sub-agents, which can message the main agent when blocked or done. A live delegation document lets every agent see the plan. The guest says this is untested against single-agent quality, and he cites a skeptical article saying sub-agents lose the main agent's context. ([55:13](https://youtu.be/zr-Xk0UVHEU?t=3313))

## Techniques
- **Fresh-session review pass** — Open a new conversation in the same repo directory, paste a saved review prompt that asks the agent to review the code the other agent wrote, check that it is PR-ready, and simplify where sensible. Optionally switch to a different model for the review. The guest says he could turn this prompt into a skill. *When:* After an agent writes a change and before a human reviews it. Use it to catch things the writer missed, such as needless complexity or missing abstractions.
- **Ask why, do not accuse** — When output looks wrong, ask the agent why it made a specific choice, for example why it used a particular pattern or what constraint it was working around. Do not tell it that it is dumb. Its answer often names the library or edge case behind the choice. *When:* When code looks odd, the agent's choice seems wrong, or you need to understand a constraint before you change the code.
- **Two-lens review passes** — Run one review pass with the lens get it working, then a second with the lens get it right. The guest cites Claude Code's /simplify command as a similar idea and says the pattern could be implemented as a skill, a hook, or training data. *When:* After an agent implements a feature or fix, to catch the gap between code that runs and code that is well made.
- **Agent review as a GitHub Action** — Trigger a cloud agent from a GitHub Action when a PR opens. The agent reviews the diff just in time and comments on it. Warp has open-sourced its review skill, which can be applied to other tools as well. *When:* When you want automatic review on every PR and do not want to run the reviewer locally.
- **Keep READMEs and CLAUDE.md thin** — Keep the top-level doc around 20 lines. Put detailed explanations at the touchpoints of each module, split modules at real boundaries, and let the code speak for itself. Avoid one huge CLAUDE.md that describes the whole codebase. *When:* When an agent struggles to navigate a codebase or burns compute looking up documentation.
- **Two clones instead of worktrees for parallel agents** — Keep two full clones of the repo, run one agent in each, and switch between the two dev servers to check output. The guest says he does not use git worktrees, calls them overrated (and admits he may not have tried them enough), and caps parallelism at two because agents step on each other in an early codebase. *When:* Solo work on an early project where you want two agents in parallel without the overhead of worktrees.
- **Cloud research, then fork locally** — Start a cloud agent on a GitHub repo to research a question and produce an initial implementation. Use the fork-locally action in Oz to pull the session down and resume it on your machine, instead of creating another clone or worktree. *When:* For research or a first pass that you want to finish locally without setting up another checkout.
- **Multi-repo sandbox environment** — Define one environment with a Dockerfile that clones every repo the work touches (for example the database schema, the server, the client and the docs). Let the agent run across all of them and open PRs in each, then have the platform detect PR URLs and show links. *When:* When one change spans several repos and you do not want to trigger one agent per repo.
- **Route by task complexity** — Send simple terminal questions and one-step commands (for example reverting a commit) to a small model, such as Haiku or Sonnet per the guest, and send planning or long-horizon coding to a reasoning model. The guest's Warp auto mode exposes three tiers: cost-efficient, responsive and genius. *When:* When a tool serves many request types and you want to cut cost and latency without asking users to pick a model.
- **Tune the harness per model** — Adding a model name to a harness is not enough. Codex needed its own tool-call handling because it is strict about the tool calls it expects, and it searched the web for minutes without updating the user. The team had to tune the harness for Codex to match the Codex CLI. *When:* When a new model underperforms in a harness that works well with another model.
- **Figma for design, agent for implementation** — The guest designs visuals (gradients, shadows) in Figma himself, then hands implementation to Codex. He says this moved his side-project split from about 10 percent design and 90 percent implementation to roughly even. *When:* For UI-heavy side projects where taste matters but the implementation is tedious.

## Hot takes
- Models will matter more than harnesses; the harness is the last 10 percent of the difference.
- Terminal UIs are the quickest way to extend CLI agents but are a poor rendering layer; the future is a GUI, though not an IDE.
- Agents are trained to do the bare minimum to reach mission accomplished, so review or simplify passes are required; the guest does not think agents can self-merge yet.
- Git worktrees are overrated, but the guest admits he has not tried them enough to be sure.
- The guest is a Warp employee and the segments on Warp and Oz are product pitch. Claims about Warp's architecture, pricing and results are self-reported and unverified.
