> Browserbase's Shubhankar Srivastava shows an auto-research loop in which a doer agent and a teacher agent iterate on a strategy file until browser-agent tasks converge into reusable skill.md files that cut cost and latency.

## Summary
The speaker argues that browser-agent reliability is an engineering problem about tools, skills and harness rather than model capability, and that agents never learn from their production runs. He adapts Karpathy's auto-research idea into an "auto-browse" loop with two Claude Agent SDK agents: a doer that browses with the browse CLI, and a teacher that reads the doer's traces and appends learnings to a strategy.md file injected into the next iteration. The loop has no preset iteration count, success rate or budget, and it ends when it converges on a skill.md file of site-specific tricks such as pre-filled query URLs, blocked paths and JavaScript for drags. Live and replayed examples show cost falling several-fold and, in one OpenTable case, latency dropping from 189 to 27 seconds. The talk sets two preconditions for such loops: a replayable environment and a verifiable, quantifiable outcome, with binary success checks preferred and few guardrails in the evals. He also describes publishing skills on Browse.sh, healing skills through production-failure triggers and scheduled checks, and a three-layer security model. Much of the evidence is a vendor demo with cherry-picked numbers and no published eval method, though the pattern itself is concrete and reusable.

## Key ideas
- **Browser-agent reliability is treated as a harness problem: the tools, skills and infrastructure around the model matter more than the model itself.** — The speaker says recent frontier models are already smart; failures come from drag interactions, anti-bot blocks and agents forgetting to finish. He frames reliability as something to engineer around the model. ([2:27](https://youtu.be/p7gaxmCUiIU?t=147))
- **Agents are 'geniuses that never learn': each run starts from zero and production traces are not used to improve later runs.** — Site-specific tricks live outside the agent. Fine-tuning per site is called unscalable, so he wants learning from production traces instead. ([5:08](https://youtu.be/p7gaxmCUiIU?t=308))
- **Auto-browse loop: a doer agent browses while a teacher agent reads the traces and writes learnings into a strategy.md file that is injected into the next iteration.** — Both are Claude Agent SDK agents on Opus 4.8. The teacher looks at screenshots, logs and JSON trace files, then appends what went wrong and what to do instead. No iteration count, success rate or token budget is set; the loop runs until it converges. ([8:15](https://youtu.be/p7gaxmCUiIU?t=495))
- **A converged loop outputs a skill.md file, a portable markdown artifact that encodes site tricks and can be used by any agent or SDK.** — Examples include a pre-filled URL being mandatory, a known calendar reopen bug to avoid, JavaScript injection instead of mouse drags, and blocked paths that return access denied. He says the skill is not tied to Browserbase or Stagehand. ([10:25](https://youtu.be/p7gaxmCUiIU?t=625))
- **The loop needs two preconditions: a replayable environment and a verifiable, quantifiable outcome.** — Coding agents fit well because a Docker image or EC2 snapshot can be replayed. Knowledge work is harder because of human-in-the-loop steps. Binary success (booked or not) is the easiest verifier; fuzzy quality like best flight is harder. ([21:03](https://youtu.be/p7gaxmCUiIU?t=1263))
- **Infrastructure is part of the optimisation: login cookies, residential proxies and anti-captcha handling at the browser layer strongly affect success.** — Cookies can be saved and reused across runs. Captchas are solved at the Chrome binary layer, not by an LLM. He says infrastructure quality matters most in adversarial settings. ([29:27](https://youtu.be/p7gaxmCUiIU?t=1767))
- **Production reliability uses healing loops and scheduled checks, not daily re-learning.** — A production failure triggers an auto-research run that opens a pull request for a human engineer. Alternatively, a sample run on a schedule (every 2 to 3 hours, or a daily cron on a managed agent) checks the skill and notifies on failure. ([37:24](https://youtu.be/p7gaxmCUiIU?t=2244))
- **Loops should tolerate failures and not over-index on them, and the objective (success, latency or turns) is chosen by the teacher's criteria.** — Failures can appear after successes, so loop design should absorb them. Optimising for latency can lead the loop to reverse-engineer an API that answers in about 500 ms instead of driving the browser. ([24:30](https://youtu.be/p7gaxmCUiIU?t=1470))

## Techniques
- **Teacher-doer auto-research loop with strategy file** — Run a doer agent with browser tools and a teacher agent with the doer's traces and the previous strategy. The teacher appends learnings to strategy.md, which is injected into each new doer run. Loop until convergence, with no fixed iteration count or budget. *When:* Repeatable tasks on messy or changing UIs where the outcome can be checked automatically and the run can be replayed.
- **Converged output as a skill.md artifact** — When tricks stop improving, write a portable markdown skill covering when to use it, fast paths (encode the full query in the URL), blocked routes, workarounds for known bugs, JavaScript for hard interactions, and wait times for slow pages. *When:* When the same site or workflow will be run many times and per-run learnings should not be lost.
- **Binary success verifier with minimal guardrails** — Define success as a checkable end state (for example, the reservation exists or the flight is booked), and avoid adding many extra rules to the eval. Let the loop find its own tricks. *When:* When a clear outcome exists. For fuzzy quality, the speaker says verifier design is harder and needs more thought.
- **Scheduled sample runs and failure-triggered healing** — Run the skill on a cron (for example, every 2 to 3 hours or daily) on a managed agent. On failure, notify and start an auto-research loop to heal the skill, then open a PR for a human to review. *When:* When websites change often and rerunning the loop continuously would waste tokens.
- **Three-layer security for learned skills** — (1) Control what queries enter the system. (2) Run generated skills through a security-reviewer agent before publishing. (3) At the infrastructure layer, use a browser safe mode that allowlists URLs and actions (always allow, allow once, or allow any action). *When:* When learned skills will run unattended or be shared with others, especially against prompt injection in page content.
- **Objective choice in the teacher's criteria** — Decide whether the loop optimises for success only, latency, or number of turns. The teacher then trades off steps and time to match that objective. *When:* When cost or latency matters as well as correctness.

## Numbers
- Demo task: cost fell from $12 (iteration 1) to $3 (iteration 2), about 4x cheaper; iteration 3 used fewer turns and had lower latency but failed once. ([11:44](https://youtu.be/p7gaxmCUiIU?t=704))
- Earlier 'hill climbing AI Engineer talks' demo run: cost improved about 7.4x across iterations even though all iterations passed. ([13:04](https://youtu.be/p7gaxmCUiIU?t=784))
- OpenTable access-denied task: cost went from $6.22 to $0.51 (about 12x cheaper), and time from 189 seconds to 27 seconds, after the agent used a query-parameter search URL and avoided blocked paths. ([14:18](https://youtu.be/p7gaxmCUiIU?t=858))
- Published results quoted by the speaker: up to 16x cheaper, 12x and 3x on different tasks. He says bottlenecks differ by task. ([16:05](https://youtu.be/p7gaxmCUiIU?t=965))
- One complex auto-browse loop costs roughly $30 to $40, and up to about $100 for very complicated ones. He says the cost is amortised. ([28:02](https://youtu.be/p7gaxmCUiIU?t=1682))
- Speaker claims in his own evals that a cheaper model (Sonnet) with more iterations can match Opus with fewer iterations at lower total cost. No figures are shown. ([28:02](https://youtu.be/p7gaxmCUiIU?t=1682))
- Some loops find a solution that runs in about 500 ms by calling a reverse-engineered API instead of driving the browser. ([40:23](https://youtu.be/p7gaxmCUiIU?t=2423))

## Hot takes
- Browser-agent reliability is an engineering problem about tools, skills and harness, not model intelligence.
- Browser agents are geniuses that never learn, and every run restarts from zero.
- Let the bitter lesson apply: use few guardrails in evals and let the loop discover tricks that humans would miss.
- A replayable environment matters as much as a verifiable outcome, and is often underrated.
- A cheaper model run for more iterations can beat a stronger model run for fewer iterations on cost.
