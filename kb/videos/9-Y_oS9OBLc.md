> imec's AI lead benchmarks coding agents on open-weight models vs. APIs and finds that concurrency, GPU utilization and harness choice, not just accuracy, decide when self-hosting pays off.

## Summary
Steven Latré of imec, a Belgian semiconductor research nonprofit, describes moving from closed APIs toward self-hosting open-weight models and renting or owning GPUs. He frames model routing as the first cheap optimization and self-hosting as the next phase, where the design space expands to models, harnesses, hardware and KV cache. His team ran thousands of long-horizon coding runs on SWE-Bench Pro, varying three coding harnesses (Codex, Pi, Claude Code), model size and hardware. The talk reports resolve rates by model tier, GPU rental cost differences, and how many concurrent users a single machine can serve comfortably. Concurrency is presented as more binding than accuracy, and the break-even point for self-hosting depends heavily on GPU utilization. The speaker also finds that the harness can roughly halve token output and GPU wall time at equal accuracy. The data is not yet published; the team promises a public benchmark dataset and a software-hardware alliance.

## Key ideas
- **Cost optimization moves through phases: model routing first, then self-hosting open-weight models, then leasing or owning infrastructure.** — Model routing is called low-hanging fruit. Once token consumption grows, owning the stack (open-weight hosting, GPU leasing, eventually on-prem) becomes the next lever. Owning infrastructure adds decisions about model trust, harness, hardware architecture, CPU:GPU balance and KV cache. ([2:08](https://youtu.be/9-Y_oS9OBLc?t=128))
- **The comparison should be at the task level and expressed as total cost of ownership, not per-token price.** — They measured agentic coding tasks rather than chat. Long-horizon tasks are the argument for owning infrastructure, since interactive use with idle time makes the economics different. The benchmark covered accuracy, latency and cost across API and self-hosted setups. ([4:22](https://youtu.be/9-Y_oS9OBLc?t=262))
- **Model quality and hardware cost are a stepwise function, not a linear one.** — Qwen and DeepSeek reached similar task performance, but the hardware needed for Qwen cost about 4x more to rent. Moving from GLM to Kimi K3 gave roughly 20% more accuracy for about 15% more GPU rental cost. Picking a slightly different model can change the hardware tier entirely. ([8:57](https://youtu.be/9-Y_oS9OBLc?t=537))
- **Concurrency, bounded by memory for weights plus per-user KV cache, can matter more than accuracy.** — Each concurrent user adds KV cache, so comfortable concurrency fell sharply even on larger hardware. Kimi K3 could reliably serve about four concurrent users and was about 3x slower than the Claude Code baseline. The speaker says concurrency is more important than accuracy for big models on long tasks. ([10:02](https://youtu.be/9-Y_oS9OBLc?t=602))
- **Self-hosting beats the API only above a GPU utilization threshold that depends on hardware tier.** — For low-tier models on smaller hardware, the GPU needs about 89% utilization to beat the API, which is infeasible for most teams. On large systems (a B200-class system is mentioned), about 15% utilization is enough. GLM-class models were the threshold sweet spot, with about 25% total cost saving for the coding-assistant workload. ([12:37](https://youtu.be/9-Y_oS9OBLc?t=757))
- **Harness choice does not change accuracy much but can change GPU cost by about half.** — All three harnesses reached similar accuracy across models. With GLM, Codex generated about half the tokens of the other harnesses, which halved wall time on the GPU. On self-hosted infrastructure, the harness is a cost lever even when API-based benchmarks show no difference. ([14:57](https://youtu.be/9-Y_oS9OBLc?t=897))
- **The next steps are a public benchmark dataset and a cross-industry alliance.** — The team is building a benchmark pipeline into a public dataset to track a fast-moving target of new models and hardware. They are forming an alliance of software and hardware people with customers and chip and infrastructure providers, arguing the two worlds should work more closely together. ([17:18](https://youtu.be/9-Y_oS9OBLc?t=1038))

## Techniques
- **GPU-utilization break-even check for API vs self-host** — Estimate the token spend on the API for your workload. Compare it with the hourly cost of the GPU tier you would need, multiplied by the utilization you can realistically reach. Self-hosting only wins above that utilization. The speaker's numbers were about 89% for low-tier models and about 15% for large systems. Use measured tokens per task, not list prices. *When:* Before committing to self-hosting open-weight models for agentic work, or when comparing a rented GPU against API spend.
- **Concurrency ramp test on a single inference box** — Run an increasing number of simultaneous long-horizon agent sessions against one model server. Record latency and task success per level. Stop at the point where latency degrades or the tasks fail, and treat that point as the comfortable concurrency. Compare it with the API baseline, not just the model's accuracy. *When:* When sizing a self-hosted model for multiple users, or before claiming a number of supported concurrent users.
- **Task-level benchmark grid across harness, model and hardware** — Run a fixed set of long-horizon coding tasks (SWE-Bench Pro in this study) across a grid: coding harness (Codex, Pi, Claude Code), model (API plus several open-weight sizes), and hardware tier. For each cell, record resolve rate, latency, tokens generated, and GPU wall time, then compute cost. *When:* When choosing a stack for agentic coding, or when comparing harnesses on your own infrastructure instead of relying on leaderboards.
- **Measure harness token output and wall time on a paid GPU** — For the same task and model, log output tokens and wall-clock time per harness. Treat token count as a proxy for GPU bill when the GPU is paid for by the hour. Pick the harness with lower token output if accuracy is comparable. *When:* When the GPU is rented or owned, and accuracy is similar across harnesses.
- **Map model choice to hardware tiers** — Check how the hardware requirement changes between candidate models before choosing between them. Small differences in model size can move you to a much more expensive GPU configuration, so pick the model at the top of the tier you can afford. *When:* When choosing among open-weight models of similar quality for self-hosting.

## Numbers

## Hot takes
- Concurrency matters more than accuracy when self-hosting big models on long tasks (speaker's conclusion from one hardware set and one benchmark).
- The harness can halve the GPU bill even when accuracy is identical, so harness choice is an infrastructure decision.
- The 86% Kimi K3 result may reflect training-set overlap with SWE-Bench, which the speaker says himself.
- Results come from one benchmark (SWE-Bench Pro coding) and one organization; the full dataset is not yet public, so the numbers are not yet independently checkable.
