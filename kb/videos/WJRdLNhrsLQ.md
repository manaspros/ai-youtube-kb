> Maven Clinic's CTO-level account of becoming an "AI-native" health company: AI in internal work and product, shorter planning cycles, changed code review, and tiered reliability bars with rubric-based evals.

## Summary
Dan Feng from Maven Clinic, a digital health platform for women and families, describes two years of moving from a traditional tech company to an AI-native one. He defines AI-native in three parts: using AI for internal work, building AI into the product, and changing culture and process to fit. He describes adoption across early, middle and slow adopters, and says hiring and performance reviews now reward AI-leveraged impact and product understanding. On planning, he argues for one-year directional vision, two-to-four-week delivery sprints and short design docs. On code review, engineers now produce thousands of lines a day, so Maven lets engineers skip review for simple PRs (with accountability), caps PRs at 500 lines, and stacks PRs for large features. For reliability, he says each feature should define acceptable failure rates; high-stakes flows use multi-model agreement and human escalation. Pre-release, integration tests run many times with a pass-rate bar of about 90%, and post-launch conversations are scored against rubrics and spot-checked by people. The talk is high-level, with few hard numbers.

## Key ideas
- **AI-native means three things: AI used for internal work, AI built into the product, and changed culture and process** — Maven does not treat AI-native as a fixed playbook. Internally, the test is whether a task done by hand today could use AI, including tasks you would otherwise hand to someone else. Externally, AI goes into the product for user experience and cost. Culture and process have to change too. ([0:08](https://youtu.be/WJRdLNhrsLQ?t=8))
- **Adoption works best when you build shared infrastructure for the middle majority and listen to them** — Early adopters need only tools and a push to share what they learn. The majority needs shared infrastructure and easy tools. Slow adopters need their concerns heard and a clear statement of where the company is going. Tool preferences changed within a year, from Cursor to Claude Code, so support has to cover both. ([2:36](https://youtu.be/WJRdLNhrsLQ?t=156))
- **Senior engineers now implement their own designs with AI, so delegating implementation costs more than it saves** — Previously a senior engineer scoped a problem and handed implementation to others in parallel. Now engineers who understand the problem build it directly with AI. Hiring looks for people who are curious about AI, work across the PM and engineering boundary, and can solve ambiguous problems alone. Performance reviews ask what someone did with AI. ([5:19](https://youtu.be/WJRdLNhrsLQ?t=319))
- **Planning moves to a one-year direction, two-to-four-week delivery commitments, and short 1-2 page docs** — The one-year plan is a directional wish list that assumes models will keep improving. The real commitment is what ships in the next 2-4 weeks, and a wrong sprint decision can be reversed quickly. Three-to-six-month plans are hard to make because model capability changes so fast. Long PRDs and TDDs are replaced by short documents used to communicate and iterate. ([6:35](https://youtu.be/WJRdLNhrsLQ?t=395))
- **Adoption of AI coding tools started with low-risk tasks, which built rules, skills and guardrails before the whole team was asked to use them** — Maven began with unit tests and documentation because they are easy to verify and low-risk. That built team confidence and produced shared rules, skills and guardrails. Only then did the company ask all engineers to use the tools for implementation. Engineers now focus on review, architecture and evaluation. When someone declines to use the tools, leaders ask why, to learn. ([10:21](https://youtu.be/WJRdLNhrsLQ?t=621))
- **AI-written volume has broken code review, so Maven relaxes the gate and enforces accountability** — A good engineer can now write thousands of lines a day, not hundreds. Engineers may self-identify a PR as simple enough to merge without review, and they are held accountable for it. If they do request review, PRs should stay under about 500 lines and large features should be stacked. Rubber-stamp approvals are the worst case because they create false confidence. AI review tools helped a little but were not trusted alone. ([10:21](https://youtu.be/WJRdLNhrsLQ?t=621))
- **Reliability is set per feature by deciding which failures are acceptable, not by trying to remove hallucinations entirely** — Failing one scheduling request in a thousand is tolerable because the user can retry. A reimbursement with the wrong amount causes an escalation, so it needs extra checks. Those checks include running a receipt through several models and proceeding only when they agree. If they still disagree, the system offers a human agent. ([13:05](https://youtu.be/WJRdLNhrsLQ?t=785))
- **Pre-release tests run many times against a pass-rate bar, and post-launch conversations are scored against rubrics and spot-checked** — Hundreds of integration tests cover known use cases, and each case runs multiple times, requiring about a 90% pass rate, because the model is non-deterministic. After launch, an automated system scores conversations against rubrics, and a dedicated team reviews samples. Reviews rise to about 20% of conversations when a new feature launches. The reviews also check whether the rubrics are too strict or too loose. ([15:21](https://youtu.be/WJRdLNhrsLQ?t=921))

## Techniques
- **Staged AI-coding adoption from low-risk tasks** — Start with unit tests and docs, where output is easy to verify. Turn what the team learns into shared rules, skills and guardrails. Then expand to implementation, with engineers spending their time on review, architecture and evaluation. *When:* Rolling out coding agents to a whole engineering org that has not yet built trust in them.
- **Self-declared review tiers with accountability** — Engineers decide whether a PR needs review, merge simple ones themselves, and remain accountable for them. Keep a size cap around 500 lines for PRs that do get review, and stack PRs for large features so reviews stay meaningful. *When:* Review volume from agents exceeds what humans can read meaningfully, but you still want a human signal.
- **Repeated-run pass-rate gating for non-deterministic tests** — Run each integration test many times and require a set pass rate, around 90%, instead of one pass. Keep adding cases for each use case you learn about. *When:* Releasing an LLM-driven feature where a single green run does not show the behaviour is stable.
- **Rubric scoring plus human spot-checks on live conversations** — Define rubrics for good and bad outputs. Score production conversations automatically, then have a dedicated team sample them. Use the human results to adjust the system and also to tune the rubrics. Raise the sample rate to about 20% for new features. *When:* After launch, when you need to catch quality drift and check that the evaluator itself is calibrated.
- **Per-feature failure tolerance with multi-model agreement and human fallback** — Decide how much failure each feature can tolerate. Where failure is costly, such as money, run the same input through several models and proceed only on agreement. Route disagreements to a human agent. *When:* Designing an AI feature that handles money or other high-stakes actions.

## Hot takes
- Dedicating implementation work to other engineers now costs more overhead than it saves, because AI lets the person who understands the problem build it directly.
- Long PRDs and TDDs are a waste of time now. One or two pages that get iterated on are enough.
- Eliminating hallucinations completely is often too costly and sometimes unnecessary. Decide which failures are acceptable for each feature.
- The worst code review outcome is a rubber stamp, because it creates false confidence that the code was reviewed.
