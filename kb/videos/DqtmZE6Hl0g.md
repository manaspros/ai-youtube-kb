> Dominik Tornow (Resonate) argues the spec, not the code, becomes the product: agents should design a system via deterministic simulation before writing the production implementation.

## Summary
Dominik Tornow, founder and CEO of Resonate (a durable execution platform), argues that bespoke implementations will be generated on demand from a shared specification, so value moves from implementation to specification. He describes building Resonate's server on NATS.io and noting that a direct abstract-spec-to-implementation prompt produced a system that only worked on the happy path. Adding a human-driven concrete specification with target-specific decisions (schema, indices, SQL, transaction boundaries) fixed the production build but still left the agent without a design role. The approach that worked was a deterministic Python simulator that injects legal behaviour such as stale KV reads and enforces optimistic concurrency, so the agent can discover correct algorithms under partial failure. The simulator also records hidden ground truth (whether a read was stale and the latest value) in trace events that the production code cannot see, which lets the agent explain why its algorithm failed. The pipeline becomes abstract spec, simulation, concrete spec, implementation, and the talk closes with the claim that the prompt is the platform and the spec is the product.

## Key ideas
- **Value moves from implementation to specification** — Bespoke implementations can be generated on demand from a spec, so the protocol/spec is the product and reuse moves upstream to the spec. ([1:02](https://youtu.be/DqtmZE6Hl0g?t=62))
- **A direct abstract-spec-to-implementation prompt fails on hard distributed code** — The agent built a Rust server on Postgres that passed the happy-path tests but broke on concurrency, process failure and network failure. It was closer to a prototype than production. ([4:14](https://youtu.be/DqtmZE6Hl0g?t=254))
- **Insert a concrete specification as an intermediate artifact** — Derive a concrete spec interactively, with the human driving, that makes target-specific decisions explicit: data schema, indices, SQL queries and transaction boundaries. The agent then built a production system from it, but it helped build the system rather than design it. ([5:23](https://youtu.be/DqtmZE6Hl0g?t=323))
- **Give the agent a deterministic simulator so it designs before it builds** — The agent first builds a simulated implementation, which is executable design rather than the product. Its job is to find the correct algorithm under partial order and partial failure. Only after that comes the concrete spec and then the production code. ([7:34](https://youtu.be/DqtmZE6Hl0g?t=454))
- **Keep the protocol minimal and map it onto the target's own primitives** — Three years of removing abstractions left two objects (a durable promise and a durable task). These are expressed using only NATS primitives: queues, a key-value store and delayed or scheduled messages. Simplicity is the finish line, not the starting point. ([8:40](https://youtu.be/DqtmZE6Hl0g?t=520))
- **Stale reads are legal target behaviour, and the implementation must handle them** — A versioned KV store can return an older version on read. The stale read is only revealed when a write with the old version fails, so correctness must hold when the target behaves legally, not only when it behaves conveniently. ([9:46](https://youtu.be/DqtmZE6Hl0g?t=586))
- **Agents need explanatory, immediate feedback** — Feedback must say which stale value was returned, which logic ran, which write failed and which invariant broke. The simulator makes runs repeatable, so the agent can reproduce an exact failing execution and repair its algorithm against the trace. ([12:06](https://youtu.be/DqtmZE6Hl0g?t=726))
- **Expose hidden ground truth to the agent but not to the algorithm (forbidden fruit)** — The simulator records every read as fresh or stale and includes the latest value that the production code never sees. The algorithm cannot depend on this, but the agent can use it to see that a decision was made from a stale view, which explains the failure rather than just reporting it. ([14:20](https://youtu.be/DqtmZE6Hl0g?t=860))

## Techniques
- **Intermediate concrete spec between abstract spec and implementation** — Write an abstract spec with no implementation assumptions. Then derive a concrete spec with the agent, making target-specific choices explicit (schema, indices, queries, transaction boundaries). Only then generate the implementation from the concrete spec. *When:* When a one-shot agent build passes the happy path but fails under concurrency or failure, and you want one spec to produce several target-specific implementations.
- **Simulation-first design loop for the agent** — Abstract spec, then a simulated implementation (executable design, not the product), then discover and verify the algorithm in simulation, then a concrete spec, then the production implementation. Humans stay in the design loop, with the agent as driver. *When:* When the design space is a distributed protocol with partial failure and the agent needs to discover the algorithm, not just code it.
- **Deterministic simulation of target dependencies with legal fault injection** — Re-implement only the parts of the target you depend on (here a NATS KV store) in plain Python. Keep full version history per key. Use a seeded RNG so GETs sometimes return older versions. Enforce optimistic concurrency on UPDATE so stale writes raise. Keep it deterministic so runs can be replayed. *When:* When production bugs depend on timing, reordering or stale reads that are hard to reproduce, and you want an agent to iterate against them.
- **Forbidden-fruit trace events** — Log simulator-only ground truth on each operation (e.g. read type fresh/stale and the hidden latest value) as trace events. Keep these out of the code path under test, so the algorithm cannot branch on them, and show them to the agent when debugging. *When:* When an agent needs cause-and-effect explanations of why a distributed algorithm failed, not just which invariant broke.
- **Shrink the protocol and build on target primitives** — Keep removing abstractions, properties and relationships until the protocol is small. Express it only with the target platform's own primitives (queues, KV, scheduled messages) and do not introduce new concepts. *When:* When a protocol's state and behaviour space is already complex and each extra concept multiplies the cases an agent must get right.

## Hot takes
- The prompt is the platform and the specification is the product; implementations become disposable and generatable.
- Coding agents will retire the need for many general-purpose software platforms, replacing them with bespoke, generated implementations.
- Agents fail at distributed-systems work when they only see the happy path; they need a deterministic simulator to design correct algorithms.
- Minimalism and simplicity are the finish line for a protocol, not the starting point.
