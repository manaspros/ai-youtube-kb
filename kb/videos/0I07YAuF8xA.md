> Reducto's CEO on why document ingestion decides agent quality: decompose parsing into specialised tools, verify rather than regenerate, store table forms split by job, and eval every pipeline stage.

## Summary
The speaker (Reducto, an agentic document processing company) argues that PDFs and other messy documents are still a hard input problem, and that agents amplify bad inputs across multi-step pipelines. He describes splitting parsing across tools: small CPU-friendly layout models for structure, VLMs for semantics, and an agentic OCR step that corrects only the tokens that are wrong instead of letting a model rewrite the page. He shows that a structured parse fed alongside the original PDF improves end-LLM accuracy and cuts reasoning tokens across several model families. He covers table representation (Markdown for simple tables, HTML for merged cells, plus a natural-language rendering for embedding retrieval). For long packets he recommends classifying and splitting before extraction. For hard cases such as line charts and large forms, he describes agent harnesses with a code interpreter, visual self-checking, and parent agents that set validation criteria for subagents. He closes with evals at each stage and a shift toward agents navigating a file system through a CLI.

## Key ideas
- **PDFs are hard because the format was built for faithful printing, not for machine reading. Agents need a markdown-like representation of content.** — The speaker says PDF was designed in the 1990s to print what was on the page. Real inputs also include slides, merged-cell tables, handwriting and charts, so the long tail is where failures happen. ([5:11](https://youtu.be/0I07YAuF8xA?t=311))
- **Use the right tool per layer: small CV models for layout, VLMs for semantics.** — Sub-100M-parameter detection models find document layout, run on CPU at scale, and show where the hard regions are. VLMs add semantic correction and handle handwriting. VLMs are not a one-size-fits-all replacement, because determinism and cost still matter at hundreds of millions of documents. ([8:00](https://youtu.be/0I07YAuF8xA?t=480))
- **Agentic OCR should make targeted token-level corrections, not a free-form rewrite.** — Asking a strong model to re-OCR nicely introduces new errors. The model 'fixes' values faithfully to what it thinks is right, for example summing a table to correct a total the human got wrong. The fix is a verification layer that edits specific tokens such as a period versus a comma or zero versus O. ([9:11](https://youtu.be/0I07YAuF8xA?t=551))
- **Store the same table in two forms, one for each consumer.** — Simple tables go to Markdown and complex merged-cell tables to HTML, because HTML tags waste tokens on simple ones. For retrieval, the speaker also writes a natural-language description of each table, since embedding models match human questions like 'how did revenue change' poorly against raw HTML. The HTML goes to the LLM for reasoning and the description goes to the index. ([11:48](https://youtu.be/0I07YAuF8xA?t=708))
- **Better parse inputs improve end-task LLM accuracy and cut reasoning cost.** — Passing a structured parse with the original PDF raised results across Gemini, Anthropic and OpenAI models on a PDF benchmark from Surge. The speaker says frontier models with good parses beat a frontier model on raw PDFs, and need fewer reasoning tokens. The frontier score on that benchmark was about 30%. ([13:13](https://youtu.be/0I07YAuF8xA?t=793))
- **Classify and split documents before extraction, instead of dumping everything into context.** — Long mixed packets such as paper mail, with hundreds of pages and interleaved content, distract the model from the actual extraction. Routing each page or section to the right pipeline, and passing only relevant snippets, gives more headroom than larger context. ([14:32](https://youtu.be/0I07YAuF8xA?t=872))
- **Frontier models are precise but silently drop rows; a harness is needed for recall.** — On a benchmark released that morning, frontier models with max reasoning rarely hallucinate a row they extracted, but they omit many rows. Dedicated document services are less precise but better at recall. An agent harness with validation reached a better precision and recall balance. ([18:39](https://youtu.be/0I07YAuF8xA?t=1119))
- **Evals should run at every pipeline stage plus production monitoring.** — Evaluate parsing, retrieval and final formatting separately, because perfect parsing with bad retrieval still fails. Off-the-shelf sets are not enough, since production data differs from contrived test sets. ([18:39](https://youtu.be/0I07YAuF8xA?t=1119))
- **Let the agent navigate documents through a file-system-style CLI.** — Customers increasingly give the agent a CLI over the document store and let it decide which tools to call. Each document has a content field the agent reads on demand, and a separate metadata field with bounding boxes for citations. This replaces a fixed end-to-end pipeline. ([20:08](https://youtu.be/0I07YAuF8xA?t=1208))

## Techniques
- **Decomposed parsing stack** — Run a cheap detection model for layout and region difficulty, a VLM only on hard regions for semantics, and a verification pass that edits specific tokens against the source image. *When:* Parsing documents at scale where cost, determinism and accuracy all matter, and the document mix is varied.
- **Targeted verification instead of regeneration** — Have a checker propose token-level edits to the OCR output. Do not ask the model to re-transcribe the whole page, because it will silently correct values to what it expects. *When:* Extracting numbers or identifiers where the model's prior might override what the document actually says.
- **Dual table representation** — Store an HTML or Markdown table for the reasoning model and a natural-language description of the same table for embedding retrieval. Choose the format per table by complexity: Markdown for simple, HTML for merged cells. *When:* Building RAG over documents that contain tables, where users ask questions in plain language.
- **Classify and split before extraction** — Run a classifier that routes pages or sections of a mixed packet to the right extractor, and pass only the relevant snippets to the LLM. *When:* Inputs are long, mixed or interleaved, such as scanned mail packets or multi-form bundles.
- **Agent harness for chart reconstruction** — Give the agent a code interpreter and a way to render its own reconstruction, so it can compare the output to the source chart and loop until mismatches are gone. *When:* The task needs pixel-level accuracy that one-shot vision models cannot provide, such as reading line charts into tables.
- **Parent-subagent validation criteria** — A parent agent defines explicit validation rules for each subagent's output, for example field counts or row checks, before accepting results. *When:* Extracting very large structured forms where silent drops of rows or fields are the main failure.
- **Per-stage evals** — Measure parsing, retrieval and final-answer quality separately, and track end-agent performance as the final metric. Add production monitoring on real traffic. *When:* Building a multi-step RAG or agent pipeline where failures can come from any stage.

## Hot takes
- Asking a strong VLM to OCR nicely is the wrong design, because capable models 'correct' documents toward what they expect.
- VLMs are not a one-size-fits-all replacement for traditional CV in document pipelines.
- Better parsing often beats a bigger model: a frontier model with raw PDFs can lose to weaker models given structured inputs.
