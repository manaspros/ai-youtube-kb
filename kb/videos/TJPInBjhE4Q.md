> Sachin Gupta (eBay) argues coding agents create unmeasured review debt and offers a deterministic 0-100 PR review-burden score built from five signal families, plus a rollout plan.

## Summary
The speaker says PR volume from coding agents is rising faster than human review capacity. He cites GitHub, DX and Pharos AI data showing commits and PRs rising while review comments fall and median review time climbs sharply. He calls PR count, PR size and cycle time vanity metrics. He defines review debt as the gap between agent-produced code and code humans have actually reviewed and understood, and says it compounds through agent learning from the codebase, reviewers ceding architecture decisions, and leadership resetting throughput expectations. His fix is a deterministic score with no LLM judge, so it stays stable and defensible, built from five signal families: depth/size/coupling, test evidence gap, directory and ownership spread, AI authorship indicators, and evidence/rationale gaps. He shows PRs scored 0, 7 and 60 and a scan of 524 PRs across three public repos. He recommends a rollout of backfill, threshold, non-blocking PR comments, weekly per-team aggregation and tracking the slope. It is a framework pitch with no live demo, and the weights are the speaker's defaults.

## Key ideas
- **Review capacity is falling behind agent-driven PR volume** — GitHub data cited: commits up about 25% YoY while commit comments fell about 27%. Pharos AI cohort: median review time up about 441.5% and 31% more PRs merged with no review. ([0:00](https://youtu.be/TJPInBjhE4Q?t=0))
- **Common PR metrics are vanity metrics** — PR count rises when one change is split into seven PRs. Bigger median PR size is bloat. Falling cycle time can mean reviewers stopped pushing back. These measure production speed, not delivery speed. ([2:54](https://youtu.be/TJPInBjhE4Q?t=174))
- **Review debt compounds like financial debt, paid in human attention** — Three loops: the agent learns from under-reviewed code and grounds future PRs on it; reviewers stop making architecture calls when most of a PR was generated; leadership raises throughput expectations, leaving no slack to hire reviewers or pay the debt back. ([4:25](https://youtu.be/TJPInBjhE4Q?t=265))
- **Keep the score deterministic, with no LLM judge** — An LLM judge can drift when the model changes, and a score that cannot be traced to a computation is hard to defend in an engineering review or to leadership. Every check is computable from the PR and repo. ([5:24](https://youtu.be/TJPInBjhE4Q?t=324))
- **Test evidence gap is weak on its own, because agent tests lock in behavior** — The ratio of test lines to production lines only shows whether tests exist. Agent tests often assert what the code does, including bugs, rather than what it should do. ([7:53](https://youtu.be/TJPInBjhE4Q?t=473))
- **Evidence and rationale gaps are the fastest way to destroy reviewability** — A PR with a one-word title, an 18-character body and an 'updates' commit message cannot be reviewed. A good PR states the what in the title and the why, symptom, diagnosis and benchmark in the body. ([11:19](https://youtu.be/TJPInBjhE4Q?t=679))
- **AI authorship is an information-only signal, not a penalty** — Detection uses co-author trailers (strongest), agent branch-name prefixes, and body or commit phrases such as 'generated by'. Across 524 PRs, AI indicators fired on 5-20% of PRs weekly, and none of them landed disproportionately in high-burden bands. Complexity, not authorship, drove burden. ([15:17](https://youtu.be/TJPInBjhE4Q?t=917))
- **Score bands drive a conversation, and the advice is what changes behavior** — Bands: 0-24 low burden, 25-49 normal, 50-74 needs author evidence before senior review, 75+ high (split or request context). Each report lists why, reviewer focus and author next actions. Healthy PRs produce almost no output. ([12:43](https://youtu.be/TJPInBjhE4Q?t=763))

## Techniques
- **Deterministic review-burden score** — Compute about 10 checks across five families (size/depth/coupling, test evidence gap, directory and ownership spread, AI authorship indicators, evidence/rationale gaps) and combine them into one 0-100 score with weights. No model is involved. Output includes why, reviewer-focus and author-next-action lists. *When:* Need a repeatable, auditable PR quality signal for agent-written code that can be shown to leadership without an LLM judge changing the number.
- **Backfill calibration** — Run the scorer over the last ~200 merged PRs, check whether the scores feel right against team judgment, and adjust weights before using the score. *When:* Before adopting any new scoring weights, since the speaker says the defaults should be calibrated to your team.
- **Non-blocking rollout ladder** — Backfill, set a threshold (e.g. 50 requires an author comment), post the score as a PR comment on every PR without blocking merges, aggregate weekly per team, and discuss the slope in retros and planning. *When:* Introducing a review-burden metric to a team without creating a gate or an anti-AI reaction.
- **Shape rules for agent PRs** — One logical change per PR; the human author confirms tests assert intended behavior, not current behavior; keep changes inside one owner's territory and split cross-team work; the human writes the PR body's why, not the agent. *When:* Reviewing or prompting coding agents so that output stays reviewable.
- **Authorship detection as a weak amplifier** — Flag agent involvement from co-author trailers, agent branch prefixes and body phrases, and use it only as a small additive term so that other signals dominate. *When:* Wanting to surface agent-assisted PRs for extra attention without penalizing agent use.

## Hot takes
- Vanity metrics: PR count, median PR size and cycle time look like wins but hide the real cost.
- Do not use an LLM as judge for review scores; determinism is what makes the number defensible.
- Measure review debt before building tooling: score 20 PRs from last week by hand, then track the weekly slope rather than the level.
- Authorship should be a small amplifier, not a penalty; complexity drives burden, not who or what wrote the code.
- Approve-with-comment merges and LGTM-only reviews are the anti-pattern to stop.
