## Summary
The host argues that coding agents now produce most implementation, so the developer's job shifts to planning intent up front and reviewing and testing output at the end. Planning is treated as the main job: refine the plan until it is right, then let the agent run in a single implementation pass with bypass-permissions mode. Specs should be split into separate documents (risks, mitigations, tech specs, constraints and trade-offs) so the agent can navigate them. Context engineering is named as the next core skill, built from CLAUDE.md, a change log, slash commands, skill.md files, plugins, MCP servers, and a Slack feedback loop. For verification, the host describes a test-driven flow where tests are written first in a fresh context and must not be edited during implementation, followed by black-box user-story testing via the Claude Chrome extension and white-box XML-guided architecture review through a slash command. The talk is mostly opinion, with a Dart AI sponsor read and a plug for a paid tier, and the concrete artifacts are not shown in the transcript.

## Techniques
- **Refine the plan, then run one-shot implementation** — Write the feature spec and ask the agent's planning mode to draft a plan. Iterate on the plan until it matches intent, then turn on bypass-permissions mode and let the agent implement the spec in one run. Use the Claude Code creator's plan-mode-first habit as the model. *When:* Features where the spec is clear and well documented. The host says earlier agents hallucinated despite good plans, so verify output after the run.
- **Split spec into per-concern documents** — Create separate files for risk assessment, mitigations, technical specs, and a constraints and trade-offs file that states acceptable performance, cost, and time limits. Point the agent at these files so it can navigate them without loading one large document. *When:* Any project large enough that a single spec mixes concerns, so the agent can load only the relevant part.
- **Test-first with a context reset and locked tests** — (1) Ask the agent to write tests for the feature without writing implementation code. (2) Clear the context and start a new window so the implementer does not know how the tests were written. (3) Ask the agent to run the tests and confirm they fail. (4) Ask it to implement the feature, with an explicit instruction not to modify the tests. Let the failing tests be the target it iterates against. *When:* Features with clear acceptance criteria. Use after the spec is settled and before the implementation pass.
- **Black-box testing from user stories with a browser agent** — Write user stories that describe how real users interact with the app, including the interactions likely to trigger errors. Have the Claude Chrome extension work through each story section by section, testing functionality against the requirements without reading the code. *When:* Checking end-user functionality and UI flows after implementation.
- **White-box review with an XML test plan and a slash command** — Write an XML document with sections and subsections of tests that tell the agent how to read the code and look for architectural and performance problems. Put a slash command in a testing folder that (a) gives initialization instructions, (b) logs results to a structured file, and (c) generates a final report. The host does not show the file contents. *When:* Reviewing architecture and performance, which black-box testing does not reach.
- **Layered project structure for agents** — Keep a CLAUDE.md with project guidance, maintain a change log, add reusable slash commands and skill.md files that bundle scripts and references, extend with plugins and MCP tools, and connect a Slack channel so users can report errors into the agent loop. *When:* Any multi-session project using Claude Code where agents keep ignoring constraints.
