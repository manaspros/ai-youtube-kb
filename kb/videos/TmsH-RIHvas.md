## Summary
The AI LABS team lists ten Claude Code practices from daily use on development, research and pipeline work. They start with Claude's built-in insights report over past sessions, which surfaced friction such as a main agent polling a task list for too long in agent-team sessions, and they encode the fix in CLAUDE.md. For context, Claude writes a PRD, architecture.md, decision.md and a feature.json with completion criteria and a passes flag, and Context7 MCP supplies current library docs. Hooks are the enforcement layer: a PreToolUse hook exits with code 2 to block edits to test paths, and an experimental MCP CLI mode moves MCP tools out of the context window and into on-demand bash calls. For parallelism, each agent works in its own git worktree and the outputs are merged afterward. Quality checks include strict TypeScript, user stories written before implementation, and an adversarial pair where a fact-checker agent verifies a research agent's draft. Verification uses Claude in Chrome, Puppeteer MCP, or Vercel's Agent Browser, which reads the accessibility tree at roughly 200 to 400 tokens per page. The last tip is asking Claude to predict failure modes, which the team says surfaced 18 production-risk issues their testing missed. Most tips are concrete, though the numbers are anecdotal.

## Key ideas
- **Use Claude Code's insights report over past sessions to find friction, then write the fix into CLAUDE.md so it carries forward.** — The team's example is a main agent that polled the task list for a long time during agent-team work. The fix was an instruction in CLAUDE.md telling Claude not to poll indefinitely. ([0:00](https://youtu.be/TmsH-RIHvas?t=0))
- **Have Claude write the project's planning docs, and keep feature status in a machine-readable file.** — Four docs: PRD (scope), architecture.md (data formats, file structure, APIs), decision.md (decisions made, as a reference), and feature.json (features with completion criteria and a passes key). The speaker calls feature.json the most important, since it is token-efficient and tracks what is implemented. ([1:20](https://youtu.be/TmsH-RIHvas?t=80))
- **Use Context7 MCP so agents read current library docs instead of relying on training data.** — The speaker says this reduces dependency-mismatch errors and closes the gap between what the model knows and the current library versions. ([1:20](https://youtu.be/TmsH-RIHvas?t=80))
- **Hooks enforce behavior through exit codes. Exit 0 proceeds, exit 2 blocks and returns the error to the agent, and other codes are non-blocking.** — The team's example is a pre-tool-use hook that checks the target path. If it is a test directory or contains the word test, it prints that modifying test folders is not allowed and exits 2. In their demo, a failing-test run tried to edit the tests and the hook blocked it. ([2:48](https://youtu.be/TmsH-RIHvas?t=168))
- **An experimental MCP CLI mode stops MCP tool schemas from filling the context window.** — With the flag on, MCP servers are reached through bash-invoked MCPCLI info and MCPCLI call commands and loaded on demand. The team reports the MCP tools disappeared from context. The exact flag key is not shown in the video. ([3:55](https://youtu.be/TmsH-RIHvas?t=235))
- **Run parallel agents in separate git worktrees, not branches, then merge the outputs.** — Branches share one working directory, which makes checkout-switching hard for agents. Worktrees give each agent its own directory so overlapping feature work does not collide until the merge step. ([5:13](https://youtu.be/TmsH-RIHvas?t=313))
- **Enforce strict TypeScript and write user stories before implementation.** — Strict mode moves error checking to compile time, which the speaker frames as useful because agents lack built-in runtime error detection. Claude writes user stories with priority and access level, and the team has the agent implement the optimal path first, then the edge cases. ([6:13](https://youtu.be/TmsH-RIHvas?t=373))
- **Pair a research agent with an adversarial fact-checking agent, which the team says caught inaccuracies the research agent had made.** — The fact-checker is blocked until the first draft exists, then verifies it. The speaker says the same pattern works for implementation, with one agent building a feature and another reviewing it against the plan. This is a single anecdote from one research task. ([8:44](https://youtu.be/TmsH-RIHvas?t=524))
- **Give agents a way to verify their own runtime behavior. The team's preference is Agent Browser, which uses the accessibility tree rather than screenshots.** — Each element gets a reference, and the speaker says a page snapshot drops from thousands of tokens of DOM to about 200 to 400 tokens. CLAUDE.md tells Claude to try Agent Browser first and fall back to MCP-based testing. Other options mentioned are the Claude in Chrome extension (DOM capture, console logs) and Puppeteer MCP, which runs in an isolated browser. ([10:00](https://youtu.be/TmsH-RIHvas?t=600))
- **Ask Claude to predict where the app could fail, using patterns from other apps.** — The team says this review found 18 issues that could have been harmful in production and that their multi-layer testing had missed. The speaker gives no detail on the method or the issues. ([11:25](https://youtu.be/TmsH-RIHvas?t=685))

## Techniques
- **Session insights review into CLAUDE.md** — Run Claude Code's insights command (named as such in the video; exact invocation not shown). It analyzes past sessions over a chosen period and reports friction points and suggested features. Copy the prompt or rule that fixes a recurring problem into CLAUDE.md. The example is a rule telling Claude to stop polling the task list indefinitely when using agent teams. *When:* After many sessions, when the same friction keeps recurring, especially in multi-agent runs.
- **Claude-authored planning docs as context** — Give Claude one prompt containing the project idea and ask it to produce PRD.md-style scope, architecture.md (data formats, file structure, APIs), decision.md (decisions made, for later reference), and feature.json. Each feature in feature.json has a completion-criteria field and a passes boolean that is updated as work lands. The speaker's file names are PRD, architecture.md, decision.md and feature.json. *When:* Starting a new project, or splitting a large task into sections the agent can finish one at a time.
- **Context7 MCP for current library docs** — Install the Context7 MCP server. Agents then call its tools to fetch up-to-date library documentation before writing code that depends on that library. The speaker gives no config snippet. *When:* Using fast-moving frameworks or libraries where training data may be stale or cause dependency mismatches.
- **Exit-code-2 PreToolUse guard for protected paths** — Write a PreToolUse hook script that reads the intended target path. If the path is a test directory or contains the word test, print a message such as 'modifications to test folders are not allowed' and exit with code 2. Exit 0 lets the action proceed. Other non-zero codes are logged in verbose mode but do not block. The hook config keys were not shown. *When:* TDD workflows, where the agent might edit tests to make failing tests pass. The same pattern can gate any path or action the agent should not touch.
- **MCP CLI mode to keep tool schemas out of context** — Set the experimental MCPCLI flag to true (flag key not shown). Claude then discovers MCP servers via MCPCLI info and runs their tools via MCPCLI call from bash, rather than loading every tool schema into context up front. *When:* Many MCP servers are connected and their tool definitions are bloating the context window.
- **One git worktree per parallel agent** — Give each agent a separate worktree and one feature to build. Have the agents work in parallel without shared branch checkouts. Afterward, ask Claude to merge the worktree outputs into one working directory. *When:* Several features can be built in parallel with overlapping but separable file edits. Avoid branches for this, since agents share one working directory when using branches.
- **Strict TypeScript and user stories before implementation** — Set strict to true in the TypeScript config so null and implicit-type errors fail at build time. Ask Claude to write user-story files, each covering one feature, its priority, and the access level, including edge cases. Then have Claude implement the stories one at a time, starting with the optimal path and then the edge cases. *When:* Building a TypeScript project with agents, or any project where the spec should be fixed before code is written.
- **Adversarial researcher and fact-checker agents** — Start a research agent. Start a second agent that is blocked until the first draft exists, then checks each claim in the draft and calls out errors so the two agents exchange corrections. The same structure can pair a builder with a reviewer that checks the implementation against the plan. *When:* Research or implementation where the model hallucinates facts or misses requirements and a manual check is costly.
- **Agent Browser for self-verification, with CLAUDE.md fallback order** — Install Vercel's Agent Browser CLI (named Versal in the transcript). Let the agent navigate, screenshot, and read the accessibility tree, where each element has a reference, at about 200 to 400 tokens per snapshot. In CLAUDE.md, instruct Claude to use Agent Browser first and fall back to MCP-based testing only if needed. The speaker also mentions the Claude in Chrome extension and Puppeteer MCP as alternatives. *When:* Verifying frontend behavior that terminal-based agents cannot observe on their own, where DOM dumps would exhaust the context window.
- **Failure-prediction review pass** — After implementation and tests, ask Claude to inspect the code and list areas where the app could fail in production, drawing on failure patterns from other apps. Treat the output as a review checklist. The speaker gives no prompt text. *When:* Late in a project, to catch production risks that tests and review have missed.
