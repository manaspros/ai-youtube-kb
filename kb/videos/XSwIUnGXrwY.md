## Summary
The presenter walks through Python's stdlib logging model (loggers, handlers, formatters, with filters skipped) using a small script, then builds a Django LOGGING dictConfig in settings.py. The config uses a catch-all empty-string logger, a file handler and a console handler, with formatters going from simple to verbose. Log level and file path move into a .env file read with django-environ, so they vary per environment. The video then covers named loggers (core.views) and how child loggers propagate to parents, and how propagate=False stops that. The last part sends logs to Better Stack via its Python source and logtail-python handler, and shows live tail, severity and level filters, source filtering, and a SQL-based dashboard chart. It is a vendor-produced tutorial, so the Better Stack parts are a product walkthrough, but the Django and stdlib logging material is practical and reproducible.

## Key ideas
- **Python logging has four parts: loggers are named entry points that carry a level, handlers decide where records go, formatters decide how they look as text, and filters (not covered) can narrow which records pass.** — Loggers are the entry points and use a level (debug, info, warning, error, critical) to set the minimum severity they handle. Handlers are the output engines (console, file, HTTP endpoint). Formatters are format strings over record attributes such as name, time, level and message. ([2:11](https://youtu.be/XSwIUnGXrwY?t=131))
- **One logger can have several handlers, and every record it accepts is sent to all of them.** — The script attaches a stream handler to stdout and a file handler to logs.txt, so the same error shows up on the console and in the file. A formatter is set on each handler separately. ([5:22](https://youtu.be/XSwIUnGXrwY?t=322))
- **Django configures logging with a LOGGING dictionary in settings.py using dictConfig, with version 1 and disable_existing_loggers set to False.** — The dict has handlers, loggers and a root entry, plus named formatters. The file and console handlers reference the logging.FileHandler and logging.StreamHandler classes, each with its own level and formatter. ([8:51](https://youtu.be/XSwIUnGXrwY?t=531))
- **A logger keyed by the empty string is a catch-all that receives records from every logger. A logger keyed by a specific name only receives records from that logger.** — The demo uses the catch-all to send all Django and app output to general.log. It then uses a named logger to limit output to one module. ([12:46](https://youtu.be/XSwIUnGXrwY?t=766))
- **Use logging.getLogger(__name__) in each module so logger names follow the module path (core.views). The names form a hierarchy, and records propagate from child to parent logger.** — Logging to a parent logger named core also captures core.views records, so both files get the line. Setting propagate to False on the child keeps its records out of the parent's handlers. ([28:35](https://youtu.be/XSwIUnGXrwY?t=1715))
- **Keep log level and log file path out of settings.py by reading them from a .env file with django-environ.** — The presenter explains that hard-coded file names and levels are poor practice, and that per-server environments need different levels, such as debug in development and warning-and-above in production. The values are read from the env object and used in the file handler, console handler and logger definitions. ([22:55](https://youtu.be/XSwIUnGXrwY?t=1375))
- **Assume logs can be read by anyone, and keep credentials, emails, passwords and card data out of them.** — This is the only security point in the video, but it is the one that matters most for any log pipeline that ships to a third party. ([7:39](https://youtu.be/XSwIUnGXrwY?t=459))
- **Ship logs to an aggregator with a per-source token and a handler class, then filter by level, severity and message text, and chart them with SQL.** — The Better Stack source token goes into the env file, the logtail-python handler replaces the local file handler in the loggers, and live tail, severity filters, source filters and SQL dashboards are shown. Filters are equality and greater-than checks on the integer severity, which is between 1 and 5 for Python logs. ([35:42](https://youtu.be/XSwIUnGXrwY?t=2142))

## Techniques
- **Module-scoped loggers** — In each module, `logger = logging.getLogger(__name__)`. Use the returned logger for all messages in that file, and name a logger in settings.py with the same dotted path to target that module only. *When:* Any multi-module Python app where you want to filter or route logs per module, and to read logs by source file.
- **Python stdlib setup without a framework** — Create a logger, then add logging.StreamHandler(sys.stdout) and logging.FileHandler('logs.txt'). Create a logging.Formatter with name, asctime, levelname and message attributes, call setFormatter on each handler, and add each handler to the logger. Call logger.error(...) inside the except block for the failure case. *When:* A standalone script that needs console output and a file at the same time, or as a base for understanding what Django's config does.
- **Django LOGGING dictConfig** — In settings.py, define LOGGING = {'version': 1, 'disable_existing_loggers': False, 'formatters': {...}, 'handlers': {...}, 'loggers': {...}}. Handlers use class logging.FileHandler (with filename, level, formatter) or logging.StreamHandler (with level, formatter). A loggers entry keyed '' takes level plus a handlers list to act as a catch-all. The presenter also sets a 'root' key. *When:* Any Django app that needs one shared logging config for console and file output, with different outputs per environment.
- **Formatter styles** — Use style '{' so format strings use str.format placeholders such as {levelname} and {message}. The 'simple' formatter carries levelname and message. The 'verbose' formatter adds asctime, name, module and lineno. Point each handler at the formatter it needs, for example verbose for the file and simple for the console. *When:* When log lines need to carry enough context (time, module, line) to trace an error in a file, but a short format suits the terminal.
- **Env-driven log config with django-environ** — Install django-environ and import environ. Create an env object, then call the env read-env helper against a .env file in BASE_DIR (the presenter uses the pathlib base dir form from the quick start). Replace hard-coded file names and levels in the LOGGING dict with env lookups. The captions do not state the variable names verbatim; they are described as a Django log level and a Django log file, probably DJANGO_LOG_LEVEL and DJANGO_LOG_FILE. *When:* Any settings file where the log level or log path differs between dev, test and production, or where you want one config for many servers.
- **Named-logger propagation control** — Define a parent logger 'core' and a child 'core.views'. Give the child its own handler, such as a FileViews file handler. By default records also propagate to the parent. Set 'propagate': False on the child to stop that. *When:* When a noisy module should write to its own file and stay out of the main log, or when one logger should not double-write to a parent.
- **Shipping logs to Better Stack** — Create a source in Better Stack for the Python platform and copy its source token. Store the token in the .env file (the presenter calls it the Better Stack source token; the exact variable name is not spoken). Run pip install logtail-python. Add a handler using the LogtailHandler class with the source token passed as source_token (the import path is not spoken; logtail.LogtailHandler is the likely form). Add the handler to the core and root-level loggers. *When:* When you want logs from one or more apps in a hosted search and dashboard tool, without running your own log stack.

## Hot takes
- Vendor tutorial: the Better Stack parts are a product walkthrough and the only aggregator shown is their own SaaS. The self-hosted options are not discussed.
- The only security guidance is 'don't log sensitive data and assume logs can be read by anyone'. There is no redaction or scrubbing example, even though logs are shipped off-box.
- Filters (logging.Filter) are explicitly skipped, so per-record filtering is not covered.
- Replacing the local file handler with the Better Stack handler in the loggers means logs go only to the remote service in the final demo. That's a choice, not a best practice.
