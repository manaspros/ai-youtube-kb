> Giving an agent every tool schema on every request breaks accuracy, latency and cost as the catalog grows; the fix is semantic routing that injects only the top-K relevant tools per query.

## Summary
The speakers argue that the common "fat agent" design, where every tool definition is sent with every model call, works in demos with about 10 tools but degrades as the catalog grows. They report tool-selection accuracy falling from roughly 78% at 10 tools to about 13.6% at 741 tools, and about 127,000 tokens of tool descriptions per request at that size. Their proposed fix is semantic routing: embed tool descriptions offline into a vector index, embed the user query at runtime, retrieve the top K tools (they default to K=5), and inject only those schemas into the model call. They describe this as just-in-time context injection, comparable to lazy loading, and cite Anthropic's on-demand MCP tool loading as a real-world signal. Their benchmark protocol runs the same queries and answer key in both modes across catalog sizes up to about 1,000 tools, sweeping K at 3, 5 and 10. They also give a six-step production checklist, list the main risks (router misses, weak descriptions, rare tools) with mitigations, and caution that routing is unnecessary for small catalogs (under about 20 tools). The talk is practitioner-level with concrete numbers, though the benchmark methodology is only sketched.

## Key ideas
- **Giving an agent every tool at once works in demos but degrades as the catalog grows: slower, more expensive, less accurate.** — The speakers call this the '100-tool agent trap'. The failure is architectural: every request carries the whole catalog, so the model picks from too many similar tools and confuses them, even when individual tool definitions are well written. ([0:01](https://youtu.be/vh2VGuQ3zhY?t=1))
- **The problem is the architecture, not the prompt or tool quality.** — They say a rising error rate as tools are added does not automatically mean the prompts are bad. Forcing the model to reason over irrelevant tools on every call is the root cause. ([2:27](https://youtu.be/vh2VGuQ3zhY?t=147))
- **Tool descriptions alone can consume the context before the user's question is read.** — With 741 tools, the schemas take about 127,000 tokens per request. Accuracy falls from about 78% at 10 tools to about 40% near 100 tools and 13.6% at 741 tools. The speakers attribute this partly to lost-in-the-middle attention effects. ([3:50](https://youtu.be/vh2VGuQ3zhY?t=230))
- **Semantic routing is RAG applied to tools: index descriptions offline, retrieve top-K per query, inject only those schemas.** — Each tool gets a clear description, which is embedded and stored in a vector index when the catalog is built or changed. At runtime the query is embedded with the same model, the nearest K tools are returned (K=3 to 5 typical), and only their schemas go into the model call. ([9:37](https://youtu.be/vh2VGuQ3zhY?t=577))
- **Just-in-time context injection waits until the query is known before loading context.** — The fat-agent approach loads everything before understanding the query. Just-in-time injection reverses that and loads only what the current request needs, the same principle as lazy loading and on-demand resource loading. ([10:55](https://youtu.be/vh2VGuQ3zhY?t=655))
- **A routed model keeps a small working set, so accuracy and time to first token stay roughly flat as the catalog grows.** — The speakers report routed accuracy above 83% across catalog sizes, and time to first token nearly flat. Their point: the catalog can grow, but the model's working set should stay small. ([14:56](https://youtu.be/vh2VGuQ3zhY?t=896))
- **Routing also removes wrong tools from the choice set, which is an underrated benefit.** — For 'what is the weather in Paris', the router returns weather tools and no flight tools are exposed at all, so the model cannot pick them by mistake. ([19:00](https://youtu.be/vh2VGuQ3zhY?t=1140))
- **Routing failures need fallbacks, and descriptions must be written for the embedding step.** — For router misses, they suggest widening K, running a second retrieval pass, or routing to a broader tool group. Descriptions should use the words users actually say and include intent, action and key entities. Rare tools need monitoring of misses and description rewrites. ([25:04](https://youtu.be/vh2VGuQ3zhY?t=1504))
- **Routing is not worth it for small catalogs.** — Under about 10 to 20 tools, static loading is probably fine. They say routing starts to be justified past about 50 tools in production, when prompt size, latency or tool confusion becomes a real problem. ([25:04](https://youtu.be/vh2VGuQ3zhY?t=1504))

## Techniques
- **Semantic tool routing (tool RAG)** — Offline: store each tool's name, description, schema, owner and version, and embed the description into a vector index. Per request: embed the user query, run nearest-neighbour search, take top K (default 5), fetch those schemas, and pass only them as the tools parameter of the model call. Log which tools were selected. *When:* When the tool catalog is large (the speakers suggest past about 50 tools) and prompt size, latency or wrong-tool picks are real production problems. Works with any embedding model and vector store (they mention Qdrant, Chroma, Pinecone).
- **Just-in-time tool and context injection** — Do not load tool schemas or other context before the query is understood. Load only what the current request needs, the same way lazy loading works in software. *When:* For real-time products where first-token latency matters, and any agent whose context is dominated by static definitions that are rarely used per request.
- **K-sweep routing evaluation** — Run the same test queries with the same answer key in two modes (all tools vs. routed). Sweep K at 3, 5 and 10. Measure tool-selection accuracy, time to first token, input tokens per request and estimated cost per 1,000 calls. Pick the smallest K that meets the accuracy target. *When:* Before choosing a K or deciding whether routing pays off. Use synthetic tool pools to scale the catalog size.
- **Router miss fallbacks** — If the model cannot finish the task with routed tools, widen K, run a second retrieval pass, or route to a broader tool group. *When:* To cover recall gaps in the router without giving every request the full catalog.
- **Description writing for retrieval** — Write tool descriptions in the words users use. Include the intent, the action and the key entities. Monitor misses and rewrite the descriptions of tools that rarely score high. *When:* When building or maintaining a tool catalog that is routed by embeddings.
- **Routing observability** — Log the query, the selected tools, the final tool call, failures and fallback use. Re-embed a tool whenever its description or schema changes. *When:* In production, so the K value and the descriptions can be tuned from real data.

## Numbers
- Fat-agent tool-selection accuracy about 78% at 10 tools, about 40% near 100 tools, and 13.6% at 741 tools (roughly 1 correct tool in 8). Semantic routing stays above 83% across catalog sizes. ([3:50](https://youtu.be/vh2VGuQ3zhY?t=230))
- 741 tool schemas take about 127,000 tokens per request, before the user's question is included. ([3:50](https://youtu.be/vh2VGuQ3zhY?t=230))
- Routing injects 3 to 5 schemas, about 1,000 tokens: roughly a 99% reduction in tool-context tokens. The speaker says 100,000 requests a day would otherwise send billions of tokens just for tool descriptions. ([5:11](https://youtu.be/vh2VGuQ3zhY?t=311))
- Fat-agent time to first token can exceed 5 seconds with about 500 tools (speaker's estimate). Routed time to first token stays nearly flat. ([6:36](https://youtu.be/vh2VGuQ3zhY?t=396))
- Anthropic's on-demand MCP tool loading reportedly cut token usage from about 150k to about 2k, a 98.7% reduction (cited by the speaker). ([12:24](https://youtu.be/vh2VGuQ3zhY?t=744))
- Default K=5. K was swept at 3, 5 and 10. Benchmark synthetic pools scaled to about 1,000 tools (transcript says 1041 once and 741 elsewhere). ([13:27](https://youtu.be/vh2VGuQ3zhY?t=807))
- Runtime overhead is one embedding call plus one vector search per request. ([16:27](https://youtu.be/vh2VGuQ3zhY?t=987))
- Routing is worth considering above about 50 tools in production. Below about 20 tools, the router may be unnecessary. ([8:10](https://youtu.be/vh2VGuQ3zhY?t=490))

## Hot takes
- The 100-tool agent is a trap: sending the whole catalog on every request is an architecture bug, not a prompt bug.
- Large tool catalogs should not be dumped into every prompt; they should be retrieved when needed.
- Tokens are both cost and latency, and tool catalogs can add tens of thousands of tokens before the user's request is handled.
- Do not over-engineer small systems: with 10 to 15 tools, static loading may still be fine.
