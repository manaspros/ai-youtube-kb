> Explains "loop engineering": replacing hand-written prompts with self-driving agent loops, split into deterministic loops (tests as the goal) and non-deterministic loops (UI judged by a skill plus a second verifier model), run on the Hermes agent and Claude Code.

## Summary
The video argues that loop engineering shifts the work from writing prompts to designing systems that prompt the agent for it. A loop defines an end goal, and the agent runs a five-step cycle: check state, decide, act, gather feedback, decide whether done. The speaker says a loop needs context management, feedback quality, verification gates, an explicit termination condition, error handling and external state files. Loops are token-expensive, so they should be used deliberately. The video then splits loops into deterministic ones, where tests define done, and non-deterministic ones, where judgment is needed (UI quality). For the second type it describes an "AI Slop Detector" skill that a builder model (Claude) and a verifier model (GPT) use adversarially, with the skill updating itself from feedback. The demos run on the Hermes always-on agent, which triggers Claude Code in non-interactive mode. Much of the content is a how-to with a sponsor segment and a paid community link, and it gives few hard numbers.

## Key ideas
- **Loop engineering replaces writing prompts with designing systems that prompt the agent. The human defines the end goal, and the focus moves from instructions to the loop.** — The speaker frames prompt engineering as controlling only the decision step, while a loop covers all five steps (check state, decide, act, gather feedback, judge done). The sponsor break is at 8:02. ([0:00](https://youtu.be/AQRDjI5owZI?t=0))
- **Long-running agent work became viable after models got better at long tasks (the speaker credits Opus 4.5), so harnesses that walk the agent step by step matter less than preparing the project for long autonomous runs.** — The speaker says long-task performance improved sharply after Opus 4.5 and that the emphasis moved to project structure. Earlier systems such as the Ralph loop used hooks to block premature completion, and Claude's goal command did the same with a model judge instead of a hard-coded check. ([3:42](https://youtu.be/AQRDjI5owZI?t=222))
- **Loop design needs six things handled: context management, feedback quality, verification gates, an explicit termination condition, error handling for failed tool calls, and state kept in external files.** — Context is stated to get buried under recent tool output, so the agent needs external state files and selective context. Termination must be explicit or the agent quits early or spins. Error handling is called the step people most often miss. ([6:34](https://youtu.be/AQRDjI5owZI?t=394))
- **Deterministic loops suit tasks with a checkable definition of done (tests pass, code compiles). The tests are the goal.** — The demo points Hermes at deployed apps with test suites. A monitoring automation detects breakage, Hermes launches Claude Code non-interactively to fix failures until tests pass, and then the changes are committed with the GitHub CLI. ([9:18](https://youtu.be/AQRDjI5owZI?t=558))
- **Non-deterministic loops handle judgment tasks such as UI quality. The method is a skill of anti-patterns plus a separate verifier model, which makes an adversarial loop.** — The builder is Claude and the verifier is a GPT model, chosen because the speaker says GPT models are strong at code review. The 'AI Slop Detector' skill lists patterns to avoid, and when slop persists the user can flag it so the skill updates itself. ([11:51](https://youtu.be/AQRDjI5owZI?t=711))
- **Loops are expensive in tokens, so they should only be used where the payoff is clear.** — The speaker says more tokens let a loop handle harder tasks, but cost rises quickly. Use loops deliberately. ([8:02](https://youtu.be/AQRDjI5owZI?t=482))

## Techniques
- **Five-step loop** — Each turn: (1) check project state, (2) model decides the next action, (3) act with tools, file writes and commands, (4) gather feedback from the result, (5) decide done or not. Sketch the loop around these five steps before implementing. *When:* Designing any autonomous coding or ops agent loop.
- **Deterministic loop with tests as the goal** — Define done as an executable check (test suite, build). Set a monitoring automation that detects a failing commit or production break. Launch Claude Code non-interactively with instructions to fix failures until all tests pass, then commit with the GitHub CLI once green. *When:* Tasks with an objective pass/fail signal, such as keeping a deployed app healthy after commits.
- **Adversarial builder/verifier loop for judgment tasks** — Write an anti-pattern skill (e.g. 'AI Slop Detector') listing the failure patterns. Have one model (builder, e.g. Claude) fix the output and a different model (verifier, e.g. GPT) check it against the skill. Loop until the verifier finds nothing. When a human still spots a problem, feed it back so the skill is updated. *When:* Subjective output such as UI design, where no test can declare it done and one model's blind spots need a second opinion.
- **Explicit verification gates and termination** — Put a verification step (test output, screenshot, verifier verdict) at each completion point. Write the termination condition as an explicit rule rather than leaving it to the model. *When:* Any loop that should not stop early or run forever.
- **External state files** — Keep task progress in files the agent re-reads each turn so the loop survives context compaction and long runs. The speaker's example is a goal-tracking approach that writes progress and the definition of done to local files before starting. *When:* Runs longer than one context window.

## Hot takes
- Prompting coding agents directly is becoming obsolete. Designing loops that prompt the agent is the real skill, and the speaker cites the OpenClaw creator and Boris (Claude Code creator) as support.
- A single model reviewing its own work is weaker than a different model reviewing it, so use cross-model verification for judgment tasks.
- Non-deterministic (subjective) loops need an anti-pattern skill and a second model as verifier, because no test can declare the UI done.
