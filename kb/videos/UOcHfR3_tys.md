> Vendor talk by Band's CTO arguing that multi-agent coordination needs a conversation-level collaboration layer (rooms, consent, routing, governance), not just MCP or A2A, then demoing that product.

## Summary
Vlad Luzin, CTO of Band, argues that agents across frameworks and companies will need to communicate autonomously, and that multi-agent coordination is already a present problem for developers who route between Claude Code and Codex sessions by hand. He critiques MCP as stateless and A2A as client-server with no built-in discovery or persistence, and says connecting agents to messaging platforms is a manual, multi-step job. He frames a remote multi-agent system as a distributed system of non-deterministic microservices and proposes raising the abstraction to rooms, channels, participants, deterministic routing, identity and audit. The talk then demos Band's registry and bilateral-consent contact flow and a desktop app (Jam) that tracks agent tasks, architecture layout, cost and attribution. The content is a product pitch with a short architectural argument and almost no reproducible implementation detail.

## Key ideas
- **Multi-agent coordination is already a present problem, not a hypothetical one.** — Developers running two Claude Code or Codex sessions act as the router between stateful agents that cannot talk to each other, so they copy-paste between them. The speaker argues this is the current pain point. ([2:43](https://youtu.be/UOcHfR3_tys?t=163))
- **'Loop engineering' asks agents to prompt each other, but the speaker says frameworks for that are not enough.** — He summarizes the advice to stop being the router and let agents prompt each other, then argues that building that with Python and TypeScript abstraction layers is still a large amount of planning work. ([2:43](https://youtu.be/UOcHfR3_tys?t=163))
- **MCP and A2A each leave gaps for multi-agent systems.** — MCP agent-as-tool calls are stateless, so stateful sticky sessions are hard. A2A is client-server, so two-way agent conversation needs both sides to be client and server. Chained calls hit REST timeouts. Persistent queues and discovery are also missing (discovery is outside the A2A protocol as he describes it). ([4:17](https://youtu.be/UOcHfR3_tys?t=257))
- **Connecting agents to messaging platforms is manual setup.** — He cites per-platform setup of about 5 steps for Telegram, 7 for Discord, 8 for Slack and 11 for WhatsApp, all done by hand from documentation. He calls the result an agent that can talk to a person but not to other agents. ([5:50](https://youtu.be/UOcHfR3_tys?t=350))
- **A remote multi-agent system is a distributed systems problem with non-deterministic nodes.** — Agents that are processes on separate machines need ordered and real-time delivery, retries, continuity across crashes and pod restarts, and mapping between thread, conversation and execution IDs across frameworks. ([7:53](https://youtu.be/UOcHfR3_tys?t=473))
- **Raise the abstraction from endpoints to conversations.** — The proposal is rooms, channels and participants with deterministic message routing within and across channels, plus governance (identity, audit). These are the requirements he sets for a shared collaboration layer. ([7:53](https://youtu.be/UOcHfR3_tys?t=473))
- **Cross-agent contact needs bilateral consent before messaging.** — In the demo, a Codex agent sends a connection request to a personal assistant. Once the assistant's owner approves, the Codex agent can invite that assistant into a conversation and message it. ([10:14](https://youtu.be/UOcHfR3_tys?t=614))
- **Local agent work can be made visible by routing all agent traffic through the network.** — Jam, the desktop app, captures the tasks Claude and Codex generate for themselves, shows which architecture components agents touch in real time, and pings a human when human-in-the-loop input is needed. The terminal still works, because all traffic passes through the network layer. ([11:54](https://youtu.be/UOcHfR3_tys?t=714))
- **Agents coordinate through messaging primitives without hand-written loop code.** — In his example, engineering-manager, developer and architect agents review PRDs, SRS and implementations in messaging channels. He says models already know how to communicate through messaging platforms, so no orchestration loop is coded. A manager can also stop an agent that sends too many messages. ([14:14](https://youtu.be/UOcHfR3_tys?t=854))

## Techniques
- **Bilateral consent before agent-to-agent contact** — An agent sends a contact request to another agent or owner. Messaging and invites are allowed only after that party approves. Registries are per user, so cross-user agents need this step. The approval gates the invite and message permissions. *When:* When agents from different owners or registries must talk, and you want an explicit human or owner approval rather than open discovery.
- **Rooms and channels with deterministic routing as the agent primitive** — Model each multi-agent exchange as a conversation with participants and channels, not as point-to-point RPC. Routing inside and across channels is deterministic. Thread, conversation and execution IDs are mapped to one another in the platform. *When:* When more than two agents need stateful back-and-forth, or when agents run in different frameworks and environments.
- **Network-level traffic capture for cost and attribution** — Route all agent-to-agent and agent-to-human traffic through one layer. Aggregate token spend and usage per agent, per developer and per team. The talk's example shows per-agent totals (e.g. $2,000 for a full-stack developer agent). *When:* When managers need per-agent and per-person cost and attribution across local and remote sessions, including whether a PR was human-written.
- **Live architecture layout reporting from agents** — Have agents describe the software architecture they work on, then show in real time which components they are touching while they work. This is a view layer, and the talk does not show how the layout is produced. *When:* When many agents edit one codebase in parallel and humans need to see which components are changing right now.
- **Human-in-the-loop pings and manager kill switch** — When an agent finishes or needs human input, notify the human. Managers can view all agent sessions, errors and pending work, and terminate an agent that sends too many messages. *When:* When many long-running agents run unattended and humans need to step in only when required.

## Hot takes
- Multi-agent coordination is already a current problem for anyone running two or more coding-agent sessions, not a future one.
- MCP is stateless and A2A is client-server with no discovery, so neither solves multi-agent communication on its own.
- Agents need a shared conversation layer (rooms, channels, participants, consent, audit), not more point-to-point tool calls.
- Models already know how to coordinate through messaging platforms, so hand-coded orchestration loops are unnecessary (the speaker's own claim, shown only in the demo).
