> Johan Lajili (Poolside) argues agent trust comes from verification: give agents a CLI to drive and test the app, make them reproduce bugs before fixing, and make the codebase easy for AI to check.

## Summary
Johan Lajili of Poolside explains why AI coding results vary so much between users. The main difference he gives is the feedback loop: greenfield work goes well because the agent's intuition is usually right, while brownfield code has dead ends and parts the agent never read. An agent saying "it works" only means it works as far as it knows, so the real gap is whether the agent can verify its own work. He built an internal CLI that lets an agent drive a VS Code extension the way it would drive a web page, with token-compressed UI snapshots, log extraction, service restarts, and chained UI actions. His key rule is that the agent must reproduce a bug before it is allowed to fix it, which he calls the first step to trust and a prerequisite for unattended overnight runs. He argues that engineers' main job is shifting from building product features to making the codebase and tooling easy for the AI to work in and verify. He also prefers human-like, ephemeral testing over rigid automated tests, lets the AI notice problems itself rather than being told, and suggests periodically asking the agent to review its own logs for smells and repeated manual steps. The talk is short (about 10 minutes) and has no benchmarks, so its value is in the workflow advice.

## Key ideas
- **The gap between AI enthusiasts and skeptics comes from the feedback loop, not from greenfield vs brownfield alone.** — Greenfield work goes well because the agent's intuition about the code is usually right. Brownfield code has dead ends, unused code, and parts the agent never read, so surprises are common. Agents report success based only on what they can check, so verification is the real difference. ([1:08](https://youtu.be/iRcX54EO5g8?t=68))
- **An agent saying it is done only means done as far as it can tell.** — Skeptics see the failure at once and blame the model. Users who keep going ask the agent to check logs and try again. The speaker wants the loop to be tighter so the agent verifies itself. ([2:19](https://youtu.be/iRcX54EO5g8?t=139))
- **Build a CLI that lets the agent drive the app, not just the code.** — Poolside's app is a VS Code extension, not a web page, so an extra step is needed. The CLI can take compressed UI snapshots, pull logs from front end and back end, restart services, open menus, send chat messages and wait for replies, and upload images. Commands can be stacked. ([3:45](https://youtu.be/iRcX54EO5g8?t=225))
- **Make the agent reproduce a bug before it changes anything.** — Agents are eager and will claim a fix without testing it. The speaker does not trust a fix until the bug has been reproduced first. He calls this the first step to trust, and it is what makes unattended overnight runs possible. ([4:53](https://youtu.be/iRcX54EO5g8?t=293))
- **The engineer's new job is to make the product easy for the AI to work on and verify.** — This includes improving the codebase so it is easier to change, improving knowledge bases, and presenting the AI's work so it is easy to check. The tool can be a CLI, a skill, or an MCP server; he chose a CLI for simplicity. He compares it to putting your own oxygen mask on first: the investment slows you down now and pays off once you run agents over time. ([5:57](https://youtu.be/iRcX54EO5g8?t=357))
- **Prefer human-like, ephemeral tests to rigid automated tests, and let the AI notice problems itself.** — He finds scripted tests brittle and hard to maintain. Instead he wants something that tests the way a human would. When he sees a problem, such as a button sitting slightly off, he steps back and tries to make the AI find that problem on its own instead of telling it. ([7:25](https://youtu.be/iRcX54EO5g8?t=445))
- **Run a regular review loop over the agent's logs and repeated work.** — After many iterations, ask the AI to scan its logs for issues and smells, such as calling sleep(15) in many places. Also look for repeated manual steps, such as running storybooks, that should be automated. Consider whether the product itself is legible to AI, for example an ASCII view of a 3D scene or easy access to logins and permissions. ([8:50](https://youtu.be/iRcX54EO5g8?t=530))

## Techniques
- **Reproduce-first gate** — Require the agent to write a failing reproduction of the bug and show it fails before any fix is accepted. Treat a fix without a reproduction as unverified. *When:* Bug fixing, especially in brownfield code, and before letting an agent run unattended overnight.
- **App-driving CLI for non-web apps** — Wrap the app in a CLI with high-level commands: open a menu, navigate to a page, send a chat message and wait for the reply, upload an image, pull logs from a given service, and restart a service. Let the agent chain these commands. *When:* The app is not a web page (for example a VS Code extension) and the agent needs end-to-end checks.
- **Token-compressed UI snapshot** — Give the agent a very compact text version of the current UI state instead of screenshots, similar to a page snapshot, so it can read state cheaply. *When:* Agents need to inspect UI state repeatedly without spending many tokens on images.
- **Let the agent discover its own UI problems** — Do not point out visual problems directly. Step back, work out what observation would let the agent see the problem itself, and give it that observation. *When:* Interactive sessions where you would otherwise keep correcting small UI issues.
- **Periodic self-review of logs and repeated actions** — Ask the agent to scan its logs and recent work for issues and code smells, and for manual steps it keeps repeating. Turn the repeated steps into commands or tools. *When:* After many agent iterations on the same codebase.
- **Human-like exploratory testing by the agent** — Have the agent test the app the way a human would, rather than writing and maintaining brittle scripted tests. *When:* UI and integration checks where scripted tests break often as the product changes.

## Hot takes
- Most of the gap between AI enthusiasts and skeptics comes down to whether the agent can verify its own work.
- Engineers' main job is shifting from building product features to making the codebase and tooling easy for the AI to work on and check.
- Scripted automated tests are too rigid for this work; agent-driven, human-like testing is preferable.
- Do not trust an agent's bug fix until it has reproduced the bug first.
