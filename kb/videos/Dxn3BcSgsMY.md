> Better Stack walks through Google DeepMind's DiffusionGemma, a diffusion-style text model that refines a 256-token canvas in parallel, and tests its speed on an H100 via RunPod and OpenCode.

## Summary
Andrus from Better Stack explains why autoregressive LLMs are memory-bound when serving a single user, and how DiffusionGemma tries to fill that idle compute by generating a 256-token block in parallel. The model starts from a canvas of random placeholder tokens and refines all positions over a few passes, using uniform-state diffusion so every position always holds a token that can be revised. Architecturally it is built on the 26B Gemma 4 model with an encoder mode that caches the prompt and a denoiser mode that keeps per-position confidence scores and uses bidirectional attention. The speaker says the trade-off is quality for speed, and that the model is strongest at infill, code fill-in-the-middle, and puzzles like Sudoku. He ran it on an RunPod H100 with a template, pointed OpenCode at the server, and saw about 700 tokens/s averaged in the logs during reasoning, lower during output, well short of the 1000+ tokens/s marketing claim. Single-prompt demos (a finance dashboard with a partly broken expense flow, and a arcade game generated in 14 seconds) are the only evidence; no quality benchmark is shown.

## Key ideas
- **Autoregressive decoding is memory-bound for a single local user: the GPU spends most of each step loading weights for one token, while cloud servers amortize that load across hundreds of batched users.** — The speaker's framing for why DiffusionGemma targets single-user setups: the idle compute is what the model tries to reclaim by producing many tokens per weight load. ([1:20](https://youtu.be/Dxn3BcSgsMY?t=80))
- **DiffusionGemma generates a fixed 256-token block at once by refining a canvas of random placeholder tokens over a few passes, instead of writing left to right.** — Each pass re-predicts all positions; confident tokens act as context for the messier ones. The number of passes is much smaller than the 256-token count, which is where the speed comes from. ([2:18](https://youtu.be/Dxn3BcSgsMY?t=138))
- **Text diffusion needs a different corruption than images, so the model uses uniform-state diffusion rather than masking.** — Training replaces real words with random ones. Mask diffusion locks in committed tokens, while uniform-state keeps a token in every position so the model can revisit and swap a word it accepted several steps earlier. ([4:49](https://youtu.be/Dxn3BcSgsMY?t=289))
- **The architecture is an encoder/denoiser patch on top of the existing 26B Gemma 4 model, switching modes during generation.** — In encoder mode the prompt is read and its context stored in the KV cache, which is handed to the denoiser. The denoiser keeps the per-position confidence scores that normal LLMs discard and swaps causal attention for bidirectional attention. ([4:49](https://youtu.be/Dxn3BcSgsMY?t=289))
- **The speaker frames DiffusionGemma as a quality-for-speed trade: standard Gemma 4 remains the pick for maximum-quality work.** — He recommends it for inline editing, code filling, and rapid iteration, and highlights non-linear tasks such as filling the middle of a code block and solving Sudoku, where left-to-right models are weak. ([7:12](https://youtu.be/Dxn3BcSgsMY?t=432))
- **On his own H100 run, throughput fell well short of the 1000+ tokens/s claim.** — The server logs averaged about 700 tokens/s during the reasoning phase, with the output phase lower. He suspects the RunPod template or prompt settings could be tuned, and did not verify the gap. ([9:04](https://youtu.be/Dxn3BcSgsMY?t=544))
- **The only quality evidence is three single-prompt demos, and they show gaps.** — A finance dashboard generated quickly, but adding an expense did not update the expense totals. An arcade game generated in 14 seconds and worked. No benchmark or quality comparison is shown. ([10:00](https://youtu.be/Dxn3BcSgsMY?t=600))

## Techniques
- **Parallel canvas refinement (non-autoregressive decoding)** — Initialise a fixed-length block (256 tokens in this model) with random placeholder tokens. Run a small number of denoising passes where every position is re-predicted at once, keeping per-position confidence. Confident tokens serve as context for less confident ones on the next pass. Stop after a few passes instead of one pass per output token. *When:* Single-user or low-batch serving where the GPU is memory-bound and the workload is fill-in-the-middle, inline edits, or constrained puzzles. Not a fit where the highest possible quality matters, per the speaker.
- **Uniform-state corruption for text diffusion** — Train by replacing some real tokens with random ones (uniform-state), instead of masking them. Each position always holds some token, so the model can later revise a token it accepted earlier. The speaker contrasts this with mask diffusion, where committed tokens are locked. *When:* When designing or evaluating a text diffusion model and you want self-correction across passes rather than one-way commitment.
- **Encoder/denoiser mode split with bidirectional denoising** — Encoder mode reads the prompt and writes its context to the KV cache. Denoiser mode reads that cache, keeps the full per-position logits, and attends bidirectionally (every token sees every other) instead of causally. *When:* When adapting an existing autoregressive model into a denoiser without retraining from scratch, as described for the Gemma 4 patch.
- **Run DiffusionGemma on RunPod and read the endpoint** — 1) Pick the H100 container on RunPod. 2) Select the DiffusionGemma template the speaker published (linked in his description) and attach a volume disk. 3) Click deploy on demand and wait a few minutes. 4) Open the pod logs and wait for 'application startup complete'. 5) The server listens on port 8000; copy the pod's URL. Opening it in a browser shows a 'detail not found' response, which the speaker says means the server is up. *When:* Quick evaluation of the model without local GPU hardware. The exact template name and pod URL format are not shown in the transcript.
- **Point OpenCode at the remote DiffusionGemma server** — The speaker runs a command that opens the OpenCode config file (command and config keys are not shown on screen), sets the remote server's URL, selects the diffusion Gemma model, saves the file, and starts OpenCode. He then prompts it to build an app and watches streaming speed. *When:* Using a coding agent terminal with a self-hosted OpenAI-compatible endpoint. The transcript does not show the exact config keys, so check the OpenCode docs before copying.
- **Local serving with vLLM in Docker** — The speaker says Google's Hugging Face release has a vLLM recipe for Docker that can run on a large local GPU such as an RTX 5090. The exact recipe, image, and flags are not shown. *When:* Running the open weights locally. Check the Hugging Face model card for the recipe.
- **Read throughput from the server logs** — Watch the inference server's log output for average tokens/s. The speaker reads about 700 tokens/s during reasoning and lower during output from the logs, rather than from client-side timing. *When:* A quick way to check whether the claimed speed reproduces on your own hardware and template. Separate reasoning and output phases if they report different rates.
