> Divakar Kumar shows how to add an agent tier for gray-zone fraud decisions in an event-sourced system, feeding agents a semantic read layer built from CDC and broker events.

## Summary
The speaker argues that AI agents pay off inside business workflows, using real-time fraud decisions as the example. A rule engine and an ML model stay as tier 1, and only uncertain "gray zone" transactions escalate to an agent tier 2. The agents lack context, so the team built a semantic layer (projections or materialized views) fed by change feeds and message broker events from the transaction, account, device and payment contexts. Cross-context communication runs through a saga-style orchestrator, and two specialist agents (risk and behavior) run in fan-out, with a third agent reconciling their outputs into a verdict. Agent memory is short-term and in-memory because the transaction path must finish under 500 ms, and the reasoning loop has an explicit break condition. The talk is architecture-level with a live demo on synthetic data that was still loading, and it gives no accuracy, false-positive or latency measurements.

## Key ideas
- **Agents belong in business workflows, not only chatbots or coding assistants.** — The speaker uses real-time fraud detection as the workflow. The value comes from putting agents into a live decision path. ([0:08](https://youtu.be/o6U_2vd967Y?t=8))
- **Keep the existing rule and ML engines as tier 1 and escalate only gray-zone cases to agents.** — Most transactions are clear-cut and the existing engines handle them. Agents take only the uncertain middle band, so the existing system is not replaced. ([5:00](https://youtu.be/o6U_2vd967Y?t=300))
- **The real gap is missing context, not model choice.** — Rule and ML engines lacked real-time cross-domain data. The fix was to gather that data from several bounded contexts into one place the agent can query. ([2:14](https://youtu.be/o6U_2vd967Y?t=134))
- **Build a semantic layer (materialized view) from change feeds and broker events.** — Each bounded context pushes its events through CDC or the message broker into projections. A worker process reshapes them, and agent tools query the result instead of the write stores. ([10:27](https://youtu.be/o6U_2vd967Y?t=627))
- **Event sourcing stores business facts, and change feeds drive several read models.** — Commands are appended as events to Cosmos DB and never mutate state. The change feed feeds read models for timelines, customer info and fraud indicators. ([9:03](https://youtu.be/o6U_2vd967Y?t=543))
- **Use a saga-style orchestrator as the only cross-context path, with the agent inside it.** — All integration events pass through the orchestrator. Tier 1 and tier 2 are sub-orchestrators, and the agent tier sits behind the same message flow. ([7:44](https://youtu.be/o6U_2vd967Y?t=464))
- **Fan out to specialist agents and reconcile with a verdict agent.** — A risk analyzer and a behavior analyzer run in parallel. The speaker says a metric-based verdict repeated the rule engine's false positives, so a third agent weighs both outputs. ([13:52](https://youtu.be/o6U_2vd967Y?t=832))
- **Set a hard stop on agent reasoning loops and use short-term memory under a latency SLA.** — The loop breaks after a configured limit to avoid infinite loops, and the limit varies by use case. Memory is in-memory only because a transaction must finish in under 500 ms. ([11:34](https://youtu.be/o6U_2vd967Y?t=694))

## Techniques
- **Tier-2 escalation for gray-zone cases** — Keep the deterministic rule engine and ML scorer as the first pass. Send only cases between the approve and block thresholds to an agent layer. *When:* An existing decision system is mostly right, but a known band of uncertain cases needs richer reasoning.
- **Semantic layer built from CDC and broker events** — Each bounded context publishes integration events. A worker process reshapes them into per-domain projections, and agent tools read only those projections. *When:* Agents need data from several services, but the services must not share databases and the agents must not query write stores.
- **Fan-out to specialist agents with a verdict agent** — Send one event to parallel specialist agents, each with its own tools. A third agent reads their outputs and returns a single verdict event. *When:* A decision depends on several signals that are better handled separately, such as risk history and behavior patterns.
- **Saga-style orchestrator as the sole cross-context router** — Route every integration event through an orchestration layer. The layer forwards events to the contexts that need them and emits the final outcome to the broker. *When:* Bounded contexts must stay decoupled and a multi-step workflow needs one place to track the sequence.
- **Hard cap on the agent reasoning loop** — Set an explicit break condition (for example, an iteration or budget limit) per use case so the loop cannot run forever. *When:* Any agent that loops over tool calls in a latency-sensitive or costed path.
- **In-memory short-term agent memory under an SLA** — Keep only per-request context in memory and do not use long-term memory when the response budget is tight. *When:* The decision must be returned within a strict latency target, such as 500 ms.

## Numbers
- Example purchase: a $3,500 laptop declined on two attempts, then a verification call (anecdote, not a metric). ([1:08](https://youtu.be/o6U_2vd967Y?t=68))

- Transaction processing SLA is under 500 ms, which is why memory is short-term and in-memory. ([11:34](https://youtu.be/o6U_2vd967Y?t=694))

- Three read models in the transaction context: timelines, customer information, fraud indicators. ([9:03](https://youtu.be/o6U_2vd967Y?t=543))
- Tier 2 runs two parallel specialist agents (risk, behavior) plus one verdict agent. ([13:52](https://youtu.be/o6U_2vd967Y?t=832))

## Hot takes
- Agents are most valuable inside business workflows, not as chatbots or coding assistants.
- A metric-based verdict over agent outputs can recreate the rule engine's false positives, so a reasoning verdict step is worth its cost.
- Long-term memory is the wrong default when the transaction SLA is under 500 ms.
