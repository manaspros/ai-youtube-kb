> Expo developer advocate Beto on React Native in 2025: safe OTA updates with EAS Update, prebuild instead of eject, store submission, and the Flutter-vs-RN debate. Vendor-side anecdotes, little AI content.

## Summary
Better Stack podcast episode with Beto, a developer success engineer at Expo, on the state of React Native and Expo in late 2025. The technical core covers over-the-air JavaScript updates via EAS Update, which are safe only when the new bundle matches the native code already in users' binaries, and prebuild as the replacement for eject. Beto also covers Expo Go's limits, Expo Launch (GitHub repo to TestFlight, iOS only at the time), and Apple's faster beta review compared with Google Play's tester requirement. The hosts argue that Flutter draws its own widgets so OS redesigns hit it, while React Native uses native controls, and Beto describes Expo UI as the effort to expose native views. Other segments cover widgets and Apple Watch via Apple Targets, a small icon-generation CLI called SnapAI, and personal anecdotes about the speaker's career and video setup. Almost nothing here concerns AI engineering beyond Apple's on-device model and AI app generators building on Expo.

## Key ideas
- **OTA updates swap only the JavaScript bundle, so the bundle must be compatible with the native code already in the installed binary. Shipping JS that calls a native module the old binary lacks makes it fail, so adding native modules requires a new store build.** — Speaker's example: a binary shipped without the push-notifications native module will break if a later OTA bundle calls it. ([8:04](https://youtu.be/kIU7rdHz2XE?t=484))
- **Apple tolerates interpreted-code updates only within limits. The speaker's rule of thumb is that OTA suits quick fixes, typos and promos, while full refactors or new native modules need a fresh build and review.** — He hedges the '80% of the screen can change' figure as his own rough estimate, not a published rule. ([9:17](https://youtu.be/kIU7rdHz2XE?t=557))
- **EAS Update is Expo's hosted OTA service. The app installs expo-updates and can check for updates passively on relaunch, force an update prompt, or show a settings-screen button. The CLI bundles the project and targets only binaries it is compatible with.** — No exact CLI command is spoken in the segment; it is described as running the EAS Update CLI. ([10:46](https://youtu.be/kIU7rdHz2XE?t=646))
- **Prebuild replaces eject. Expo generates the iOS and Android native projects on demand, so developers can install Expo or community native libraries without leaving the Expo workflow.** — The transcript says 'pre-build'; the command is npx expo prebuild. The speaker says you can then pre-build and compile for submission. ([13:30](https://youtu.be/kIU7rdHz2XE?t=810))
- **Expo Go is a sandbox app that loads your JS bundle over a QR code, but it ships only Expo's modules. Any other native library needs a prebuilt, compiled development build on the device.** — Limitation stated directly by the speaker. ([14:57](https://youtu.be/kIU7rdHz2XE?t=897))
- **Apple's on-device Foundation Models are reachable from Expo only through a custom native module. Structured output needs a hand-written Swift 'generable' struct because the app cannot predict which schemas users need.** — Speaker says this is the main iOS capability Expo cannot provide out of the box as of the recording. ([12:11](https://youtu.be/kIU7rdHz2XE?t=731))
- **Expo UI is in progress to expose native views, not just native modules, so apps pick up platform looks such as Liquid Glass. It is in beta on iOS, and an Android beta was planned for SDK 55.** — Roadmap statements from the speaker; not verified. ([17:51](https://youtu.be/kIU7rdHz2XE?t=1071))
- **Store submission: Expo Launch builds from a public GitHub URL (iOS only at the time) and returns a TestFlight link. Beto says Apple's beta review fell from about 7 to 14 days to 1 to 2 days, while Google Play requires about 10 testers before publishing.** — Speaker says TestFlight external testing can reach up to 10,000 people via a public link. ([21:52](https://youtu.be/kIU7rdHz2XE?t=1312))
- **The cross-platform argument: Flutter paints its own widgets to mimic iOS, so each Apple redesign means re-implementing them. React Native uses the underlying native controls, so recompiling with a new Xcode picks up the redesign for free, which is the speaker's claim.** — The hosts jokingly conclude Liquid Glass 'might have killed Flutter'; no evidence beyond assertion is given. ([26:00](https://youtu.be/kIU7rdHz2XE?t=1560))
- **Widgets, Live Activities and Apple Watch apps are added as extra native targets through Apple Targets, a community package by Evan Bacon (an Expo engineer). It supports sharing state between widget and app, and Watch users get iPhone push notifications without extra integration.** — Speaker points to examples he will link in the show notes; not reproduced here. ([49:16](https://youtu.be/kIU7rdHz2XE?t=2956))

## Techniques
- **Ship JS-only fixes with EAS Update and expo-updates** — Install expo-updates in the app. Choose a check strategy: passive (update on next launch), forced (prompt the user), or a settings-screen button. Publish with the EAS Update CLI, which bundles the project and targets binaries it is compatible with. Keep the change JS-only; any new native module needs a store build. *When:* Quick bug fixes, typos, promos such as a modal banner. Not for large refactors or new native dependencies.
- **Check native compatibility before each OTA bundle** — Before publishing a bundle, confirm every native module it imports is already in the binary users have installed. If you add a native dependency, release a new build through the store. *When:* Any time you add a dependency to an app that already has users on older binaries.
- **Prebuild instead of ejecting** — Run npx expo prebuild to generate the ios/ and android/ folders from the project config. Install Expo or community native libraries normally. Treat the native folders as generated output, and regenerate them before building for submission. *When:* You need a native library that Expo Go does not include, and you want to stay in the Expo workflow.
- **Iterate in Expo Go, then switch to a dev build** — Start the dev server and scan the QR code in the Expo Go app on a real device. Expo Go only includes Expo modules, so when you need other native code, prebuild and compile a development build onto the device. *When:* Fast UI iteration early on, then native features once they are needed.
- **First store submission with Expo Launch** — Make the GitHub repo public, since it must be open source at deploy time. Paste the repo URL into Expo Launch, supply an Apple developer account and app details, and deploy. You get a TestFlight link to test on a device and invite up to 10,000 external testers. iOS only at the time of recording. *When:* A first-time iOS release where you want to avoid manual signing and submission work.
- **Add widgets, Live Activities and Apple Watch targets with Apple Targets** — Add the Apple Targets community package by Evan Bacon to the Expo project. It creates extra native targets for widgets, Shortcuts and Watch apps, and can share state between the widget and the app. The speaker says examples will be in the show notes. *When:* You need app extensions beyond the main iOS app target.
- **Generate app icons from one source image with SnapAI** — Run npx SnapAI (the speaker says 'MPX SnapAI'). The CLI wraps OpenAI's image API and writes the icon into the assets folder. Start from a 1024 by 1024 PNG for iOS. For an adaptive Android icon, make a smaller version so it fits the safe area. The same asset can drive the splash screen. *When:* A new Expo or React Native app where you want the icon set generated instead of uploading to an online resizer.
