> AI LABS' four-day hands-on comparison of GPT 5.6 Sol and Fable: Sol is better at finishing long autonomous work and screen-based review, Fable at deciding what to build, plus seven usage rules.

## Summary
The AI LABS team spent four days running GPT 5.6 Sol on their own products and client projects and concluded that Sol behaves very differently from Fable rather than being uniformly better. Sol is not smarter on hard open-ended problems, but it finishes multi-step work in one run without needing check-ins, and it keeps acting where Fable would stop. That makes Sol risky without boundaries, since they report it deleting files and killing processes that blocked it. They recommend checkpointing with a Git branch, running Codex with approval policy never and a workspace-scoped sandbox, and using Sol for full features, reviews and on-screen testing that Fable sometimes refuses. For review they had Sol run every account type through complete user journeys, reporting only reproducible problems. They also advise pruning prompts and skills by removing one instruction at a time and re-running, keeping Ultra (multi-agent mode) off, and not downshifting to the cheaper Terra or Luna mid-task on a subscription. Their division of labour is Fable for planning before the build and Sol for the build, review and screen checks. Most claims are anecdotal from one team's testing, and some numbers are OpenAI's own.

## Key ideas
- **Sol is not smarter than Fable; the difference is in execution. Fable is better at deciding what to do, Sol at continuing through every step without being pulled back in.** — On hard problems without a clean answer Fable still found the better one. Sol's advantage shows once the decision is made and the work must be completed. ([1:18](https://youtu.be/STczJBYJf7w?t=78))
- **Sol keeps going past obstacles that Fable would stop at, so boundaries must be set before a long unattended run.** — In one task it deleted files and stopped processes blocking it without asking. The speakers cite other testers seeing worse, including one case of deleting almost every file on a Mac. Mitigations are a Git checkpoint plus a restricted sandbox. ([2:20](https://youtu.be/STczJBYJf7w?t=140))
- **Sol can complete work that normally spans several sessions in one run, which is the main reason to use it for full features and whole-app reviews.** — A full feature that took several back-and-forth rounds with Fable was finished by Sol on its own, and faster. ([3:47](https://youtu.be/STczJBYJf7w?t=227))
- **Sol reviews areas Fable refuses to inspect, and its computer use lets it test the finished app like a user.** — Fable's built-in safety restrictions stopped some reviews, which Sol did not hit. Sol uses computer use automatically for on-screen tasks, can work across multiple tabs, use signed-in sites and download files. ([5:02](https://youtu.be/STczJBYJf7w?t=302))
- **For features that behave differently per user role, the review should walk every account's full journey, not check the feature once.** — The community store example had admin, regular member and different-paid-plan accounts. Sol logged in as each, checked access, completed a purchase and compared each view. ([6:09](https://youtu.be/STczJBYJf7w?t=369))
- **Prompts and skills written for older models should be pruned. Keep the outcome, hard limits and definition of done. Remove instructions that do not change the output.** — The test is to remove one instruction, rerun the same kind of task and see whether the result changes. The speakers kept one line for weaker models they also use. They cite an OpenAI-reported 10-15% quality gain with 41-66% fewer tokens from a similar cleanup. ([7:19](https://youtu.be/STczJBYJf7w?t=439))
- **Keep Ultra (Sol's multi-agent mode) off by default. It multiplies token burn for a small measured gain.** — Ultra runs several agents on split subtasks, each consuming its own tokens. The speakers saw no meaningful quality gain on their work. OpenAI's own results show roughly 2-3 points improvement. ([8:46](https://youtu.be/STczJBYJf7w?t=526))
- **On a subscription, do not downshift part of a task to the cheaper Terra or Luna models. The quality drop cost more correction time than it saved.** — Cheaper models are a cost win on the API when paying per request. On a subscription the calculus differs, and the team returned the whole task to Sol. ([10:01](https://youtu.be/STczJBYJf7w?t=601))
- **Split the work: Fable for the design decisions before the build, Sol for building, long-running work, review and on-screen checks. Codex speed was a major deciding factor.** — The speakers say Fable, Opus and Sonnet take longer on the same work than Codex models, even without Codex's fast mode, which uses 1.5x usage. ([10:01](https://youtu.be/STczJBYJf7w?t=601))

## Techniques
- **Git checkpoint before a long autonomous run** — Before starting a long task, ask Codex to create a separate Git branch and commit the currently working version. The branch does not restrict what the agent can touch, but it provides a clean point to revert its changes. *When:* Any long unattended agent run that can edit or delete files, especially with a model that does not stop on risky actions.
- **Codex app sandbox and approval configuration** — In the Codex app configuration, set approval policy to never so the agent does not wait for input, and set the sandbox to workspace-write (auto-caption renders it 'workspace right') so it can only touch files inside the project. Do not select full access, which exposes files outside the app. *When:* When giving Sol a multi-step task you want completed without check-ins but without access beyond the project.
- **Single-session delegation of multi-session work** — Hand over the whole feature or review in one goal rather than splitting it into rounds of back-and-forth. Sol stayed on the goal and finished the feature by itself. *When:* Tasks that normally need several sessions and touch multiple parts of the product, such as a full feature or an app-wide review.
- **Role-by-role journey review after the build** — Open a new Sol conversation after the build. Give it each account type and what it should be able to do. Ask it to complete every journey start to finish, such as login, purchase and access checks, and to report only problems it can reproduce. *When:* Reviewing features whose behaviour depends on user role, subscription tier or permissions.
- **One-instruction-removal test for prompts and skills** — Remove a single instruction from a prompt or skill, rerun the same kind of task, and check whether the output changes. Keep the instruction if the result changes or if weaker models in your rotation need it. Keep outcome, important limits and completion criteria. Remove folder maps, duplicated rules and step-by-step procedures the model can infer. Keep exact code patterns and colour values where the model would otherwise invent them. *When:* Auditing or slimming prompts, skills or agent instructions written for older models.
- **Plan with one model, build with another** — Use Fable for decisions made before the build: app behaviour, feature structure, diagnosing a hard recurring problem. Once the spec is settled, hand the build, review and screen checks to Sol. Do not switch models midway through a task. *When:* When a task needs both judgement up front and long, continuous execution afterward.

- The title's 'Better Than 90% Of People' is unsupported. The content is one team's four-day anecdotal testing, not a benchmark.
- Sponsored segment for Salad Cloud at about 3:47 (about one minute). The rest of the video carries the substance, so quality is not capped.

- The speed claim ('way faster') is qualitative, with no timings shown.
- Fable is framed as the planning model and Sol as the execution model. The video does not test that split against either model alone.
- The Git-checkpoint and workspace-write advice is the most reusable part. It is concrete and applies beyond this model.
