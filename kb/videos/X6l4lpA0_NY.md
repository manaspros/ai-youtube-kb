> Drew Knox of Tessl on building a "software factory" through harness engineering: three loops (inner, outer, meta), a three-layer setup order, and how Tessl's skills registry and automation support it.

## Summary
Drew Knox, head of product and design at Tessl, defines a software factory as an agentic system where agents create the shipped product and engineers build and improve that system. He frames progress as autonomy (how much humans correct the agent), then automation (how much you trust it to run unreviewed), with quality held constant. He argues the payoff is higher quality over time, not only faster shipping, because the backlog of fixes and refactors shrinks. The core practice is harness engineering, which he splits into three loops: a cheap inner loop while the agent works, an expensive outer loop run once a PR is up, and a meta loop that mines logs, PRs, issues and user feedback to fix recurring mistakes. He says raw harness engineering is hard because the field changes weekly, the work is unplanned, and the useful data sits in local logs or people's heads. His recommended build order is control plane first (issues to headless sandboxed agents to PRs, so every touchpoint is recorded), then the "Agent IT" grab bag of access, governance and execution environments, then improvement loops. The second half pitches Tessl's skills registry with governance, Linear-to-GitHub connectors, a Tessl Agent that mines repeated tasks into scheduled workflows, and a launch command that runs Codex, Claude Code or Gemini in sandboxes. The talk gives no benchmarks and little measured evidence, so most of its value is the framework.

## Key ideas
- **Software factory: agents build the shipped product, engineers build the factory** — No strict definition. The speaker's working version is any agentic system where all shipped product is agent-made and the engineering team's job shifts to making the factory more autonomous, automated and high-quality. ([2:32](https://youtu.be/X6l4lpA0_NY?t=152))
- **Autonomy and automation are different, and autonomy comes first** — Autonomy = how often humans must correct or nudge the agent. Automation = how much you can let it run unreviewed. An agent can one-shot tasks (high autonomy) and still be reviewed line by line (low automation), so you build autonomy before you remove review. ([2:32](https://youtu.be/X6l4lpA0_NY?t=152))
- **The payoff is quality, not just velocity** — Speed gains from factories are short-term. Once the backlog of bug fixes, test-quality work and refactors is cleared, the team has capacity to raise code quality, and non-technical staff can contribute ideas more easily. ([3:56](https://youtu.be/X6l4lpA0_NY?t=236))
- **Three loops map to phases of development** — Inner loop: fast, cheap checks the agent runs on its own while working on a PR, which improves autonomy. Outer loop: expensive checks run once when the PR opens (example: agentic QA, mutation testing), with the agent iterating on the results. Meta loop: sits outside the process, watches agent logs, PRs, issue tracker and user feedback, and feeds fixes back into the inner and outer loops. ([6:47](https://youtu.be/X6l4lpA0_NY?t=407))
- **The meta loop is where a team becomes more AI-native** — The meta loop finds mistakes that either reached users or had to be fixed by hand, then writes them back into checks and skills so they do not recur. The speaker presents investing here as the main lever for raising AI-nativeness. ([8:10](https://youtu.be/X6l4lpA0_NY?t=490))
- **Why raw harness engineering fails in practice** — Three reasons: the practice changes so fast that teams become AI researchers just to keep up, best practices turn into anti-patterns within weeks, and the work is unplanned and competes with shipping deadlines, so it gets skipped. Useful signals are also hidden in local agent logs or people's heads. ([9:36](https://youtu.be/X6l4lpA0_NY?t=576))
- **Build a legible control plane first** — The first layer is making all agent touchpoints recorded and queryable. At Tessl, work starts as a tracker issue, goes to a headless agent in a sandbox, opens a PR, and engineers respond with review comments. Because every step is saved on shared surfaces, tools can later mine it. ([11:01](https://youtu.be/X6l4lpA0_NY?t=661))
- **Agent IT is the unplannable part, and the improvement loops take the most time** — Agent IT covers CLI and API access, service governance, production log access, compliance, and an execution environment for the agent's code. Each item may take a week or two. The loops are the largest ongoing area: repo sweeps, playbooks for common changes, automating repeated tasks, and reviewing output quality to update skills. ([13:26](https://youtu.be/X6l4lpA0_NY?t=806))
- **Turn repeated work into a skill, then into a scheduled automation** — The Tessl Agent mines PRs and issues for repeated tasks (example: a weekly flaky-test hunt), codifies one as a skill, and runs it as a scheduled GitHub Action. Out-of-the-box weekly scans cover architecture quality, duplication, test-suite quality and security. ([17:12](https://youtu.be/X6l4lpA0_NY?t=1032))
- **Track human-intervention metrics to measure progress** — Watch manual takeovers and human PR comments per PR. Over time, the share of PRs started with no human input should rise. Hold quality constant first, then push it up. ([19:20](https://youtu.be/X6l4lpA0_NY?t=1160))

## Techniques
- **Three-tier loop design for agent quality** — Put cheap checks in the inner loop so the agent runs them on every iteration. Put expensive checks (agentic QA, mutation testing) in the outer loop, run once when the PR opens, and let the agent iterate on the results. Run a meta loop over logs, PRs, issues and user feedback to find recurring mistakes and update the inner and outer loop checks. *When:* Once coding agents reliably handle easy and medium tasks in a few parallel sessions, and you want fewer human corrections and fewer review hours.
- **Issue-to-PR control plane for agents** — Start all agent work from a tracked issue. Run a headless agent in a sandbox that opens a PR. Keep human review on the PR. Store every step on a shared surface so later tooling can pull the data. *When:* Before building improvement loops, so the signals needed to improve agents exist in one place.
- **Governed skills registry** — Publish workflows as versioned skills, with security and quality reviews on each publish, and permissions on who can publish or update. Install the skills into agent workflows. *When:* When several teams need shared agent playbooks and you need controls over what gets changed.
- **Mistake-to-skill feedback** — When a reviewer corrects an agent, decide whether the playbook or skill should change, then update it so the same error stops recurring. *When:* During routine PR review, as the cheapest form of the meta loop.
- **Repeated task to scheduled skill** — Mine PRs and issues for tasks done again and again, write them as a skill, then run that skill on a schedule (for example a weekly GitHub Action) or hand it to a coding agent in a sandbox that can open PRs and respond to comments. *When:* For recurring chores such as flaky-test hunts, duplication scans or security sweeps.
- **Human-intervention metrics as the factory KPI** — Track manual takeovers, human PR comments per PR, and the share of PRs created without human input. Keep quality flat while these numbers improve. *When:* To measure progress toward a software factory without relying on velocity alone.

## Hot takes
- Speed gains from software factories are a short-term effect, and the lasting payoff is higher code quality.
- Harness engineering is unplanned work that competes with shipping, so teams skip it and stay stuck at local maxima.
- Agent IT is 'worse than you think': every assumption about CLI, API and environment access breaks when a non-local agent has to run the work.
- Meta-loop investment is the main lever for becoming AI-native.
