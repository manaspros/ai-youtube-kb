> Kai Explains tests whether four 2017 Tesla V100s can beat 2025 DGX Sparks and RTX Pro 6000 boxes on local LLM inference; the answer is yes for decode speed, but the software and power economics are the real constraints.

## Summary
The host walks through a claim that four 2017 NVIDIA V100s (128 GB total, NVLink) generate text about 2.5x faster than two 2025 DGX Sparks running the same 125B-class Qwen model under vLLM (155 vs about 60 tok/s). He explains the split between prefill (compute-bound, the two machines tie at about 3043 vs 3062 tok/s on llama.cpp) and decode (memory-bound, where V100's 900 GB/s HBM2 beats the Spark's 273 GB/s, giving 129 vs 57 tok/s). He shows that adding GPUs over PCIe can slow decode, while NVLink lets the V100s scale. The big speedup comes from a community vLLM fork (OneCat) that went from 49 to 201 tok/s in one release on identical hardware, with NVFP4 weights unpacked to FP16 because Volta has no 4-bit hardware. He then covers the support cliff (CUDA 13 dropped Volta, the driver branch ends mid-2028, PyTorch 2.14 is the last prebuilt wheel) and a payback model: about 14.5B generated tokens to recoup a $3,500 rig against hosted pricing, roughly 3 years of 24/7 use or 9 years at 8 hours a day. His verdict is that the setup only makes sense with free power, constant use and Linux comfort, and that the hardware is fine but the software is the fragile part.

## Key ideas
- **Inference has two phases with different bottlenecks. Prefill (reading the prompt) is compute-bound and favors tensor-core throughput. Decode (writing output) is memory-bound because all weights are read from memory for every generated token.** — This explains why an old card with high memory bandwidth can out-generate a newer card with more compute. Prefill is roughly tied between the two machines, while decode follows memory bandwidth. ([3:30](https://youtu.be/eckOsa0kBkY?t=210))
- **Decode speed tracks memory bandwidth on this benchmark. The V100 has about 3x the bandwidth of the DGX Spark (900 vs 273 GB/s), and on llama.cpp it generates 129 tok/s vs 57 tok/s, while prefill is about tied (3043 vs 3062).** — The speaker notes that the Spark's design trades bandwidth for other features, so the result is a consequence of that tradeoff and not a mistake. ([4:49](https://youtu.be/eckOsa0kBkY?t=289))
- **Multi-GPU scaling depends on the interconnect. An 8x RTX Pro 6000 PCIe box got slower as cards were added (58 tok/s on 4 cards, 37 on 8), because every generated token requires all-to-all communication between cards.** — NVLink at roughly 300 GB/s let the V100s keep scaling with more cards. The speaker says he had overlooked interconnect and focused on teraflop numbers. ([6:13](https://youtu.be/eckOsa0kBkY?t=373))
- **Consumer cards with good bandwidth on paper can still lose if the software does not use that bandwidth. A GTX 1080 Ti has more bandwidth than an RTX 5060 but is about a third slower, because it has no tensor cores and the software reaches only about half its bandwidth.** — The speaker's framing is that the V100 wins because someone is still writing optimized code for it, not only because the memory is fast. ([7:31](https://youtu.be/eckOsa0kBkY?t=451))
- **Software changes can move performance more than hardware does. The OneCat vLLM fork (built for SM70) went from 49 tok/s at 32k context (v1.50) to 201 tok/s (v1.5.1, Oct 3) on the same four V100s. The retention implementation alone was about 4x faster.** — The speaker's takeaway is that the gap between hardware capability and what software uses can be very large, which matters even for people who never buy a V100. ([8:58](https://youtu.be/eckOsa0kBkY?t=538))
- **Volta has no 4-bit hardware, so NVFP4 weights are read from memory and unpacked to 16-bit values for the tensor cores. The 2017 chip runs a 2025-format model through this software conversion.** — This is the reason the V100 can run a model designed for the Spark at all. ([10:17](https://youtu.be/eckOsa0kBkY?t=617))
- **Platform support is ending. CUDA 13 removed Volta, driver branch 580 is the last one for these chips (supported until mid-2028), and PyTorch 2.14 is the last official prebuilt build for Volta. Future model architectures will depend on community forks.** — The speaker counts at least four active community projects and no NVIDIA-maintained ones, and says upgrade paths have already changed even though current setups still run. ([11:33](https://youtu.be/eckOsa0kBkY?t=693))
- **The economics depend on use and power cost. At 700 W and 155 tok/s, one million output tokens cost about $0.23 of electricity at $0.18/kWh versus $0.47 hosted. The $3,500 rig breaks even after about 14.5B tokens, which means about 3 years of 24/7 use or about 9 years at 8 hours a day, roughly the same window as driver support.** — The speaker's conclusion is that the setup only makes sense with cheap or free power and near-constant use. Image and video generation are much slower on these cards, and parallel agents scale worse than on the Sparks. ([12:43](https://youtu.be/eckOsa0kBkY?t=763))

## Techniques
- **Split inference cost into prefill and decode** — Estimate decode throughput from memory bandwidth, since each generated token reads all weights, and estimate prefill from compute. Compare hardware on the metric that matches your workload: many short replies are decode-bound, while long-document ingestion is prefill-bound. *When:* When choosing or comparing GPUs for local inference, or explaining why a benchmark result looks inverted.
- **Check interconnect before adding GPUs** — Benchmark with 1, 4 and 8 cards before assuming more hardware helps. With tensor parallelism, every generated token requires all-to-all traffic, so PCIe links can make throughput fall as cards are added. NVLink avoids this for the cards that support it. *When:* Before buying or renting multi-GPU setups for decode-heavy serving.
- **Break-even math for owned GPUs versus hosted tokens** — Compute hardware cost divided by the per-million-token savings (hosted price minus electricity cost per token). Electricity per million tokens = (watts / tok/s) x (1e6 / 3600) / 1000 x price per kWh. Compare the result with the expected time the hardware will remain supported. *When:* When deciding whether to self-host versus rent tokens, especially for older hardware with an end-of-support date.
- **Pick a fork that still targets your hardware generation** — When official serving stacks drop an architecture (here SM70/Volta), check for a maintained community fork built for it. Track its release notes, since a single release changed throughput by about 4x in this talk. *When:* When running legacy GPUs whose vendor support is ending.

## Hot takes
- The V100 is a fast decode card only because of recent community software. The speaker calls it 'missing software, not silicon' and warns that the setup could stall if the fork maintainers move on.
- Owning this rig pays back only at near-constant use with cheap or free power. For a single user with an occasional chat, hosted tokens are the better deal.
- A reader cannot rely on the 2.5x headline for other workloads. Prefill is tied, image and video generation are much slower, and multi-agent parallel work scales worse than on the Sparks.
- Adding GPUs over PCIe can make decode slower, which contradicts the common assumption that more hardware always helps.
- Sources are mostly community benchmarks and reproductions (one Reddit post, one cloud rental, one X post), not controlled tests. The host is candid about this.
