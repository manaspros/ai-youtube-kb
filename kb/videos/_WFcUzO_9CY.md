> Tutorial on scheduling Node.js functions with node-cron (crontab syntax, validation, start/stop control) and wrapping a SQLite backup job with a Better Stack heartbeat so missed runs alert someone.

## Summary
The presenter walks through node-cron, a Node package that schedules plain JavaScript functions using crontab-style expressions. He installs it with npm, schedules a dummy export function, and shows how to check an expression with cron.validate before using it. He then passes data into scheduled jobs with a closure, round-robining through an array of report names, and shows how to create tasks that start unscheduled and can be started and stopped in code. The second half applies this to a every-minute SQLite database backup script. The last section covers monitoring: a Better Stack heartbeat with an expected interval and grace period, a secret ping URL stored in .env, and a ping sent only after the backup awaits successfully. He then demonstrates a missed heartbeat that triggers an incident and its resolution. The core node-cron material is solid and reproducible, but the Better Stack section is a product walkthrough, so the monitoring half should be read as one vendor's implementation of a general pattern.

## Key ideas
- **node-cron schedules ordinary JavaScript functions with crontab syntax: cron.schedule(expression, fn).** — No special job framework is needed. Expressions can be checked and explained with crontab.guru, and the presenter suggests asking an LLM for an expression and then verifying it there. ([0:00](https://youtu.be/_WFcUzO_9CY?t=0))
- **Cron fields are easy to get wrong. */5 means every five minutes, and a bare 5 in the minute field means minute 5 of every hour, not every five minutes.** — The presenter demonstrates this with crontab.guru and the next-run times it shows. He also notes that node-cron accepts an extra seconds column, which allows sub-minute schedules such as every five seconds. ([1:24](https://youtu.be/_WFcUzO_9CY?t=84))
- **Validate expressions at runtime with cron.validate() when they come from env vars or config.** — It returns true or false. The presenter's approach is to check the value and throw or branch when it is invalid, before calling cron.schedule. ([2:38](https://youtu.be/_WFcUzO_9CY?t=158))
- **Scheduled jobs can take data through normal closures. A round-robin over an array uses a run counter, with runs = (runs + 1) % names.length.** — This is the presenter's shorthand for cycling back to index 0 after the last report name. Each tick exports the next report. ([5:09](https://youtu.be/_WFcUzO_9CY?t=309))
- **cron.schedule returns a task object. Passing { scheduled: false } creates it without starting it, and task.start() and task.stop() control it later.** — Without a running task, the Node process exits right away. The presenter stops a five-second task with a six-second setTimeout to show that stop works. ([7:40](https://youtu.be/_WFcUzO_9CY?t=460))
- **Gate task.start() on preconditions such as reports existing or the database being reachable.** — The presenter suggests this as the intended use of deferred start, though he does not implement it in the video. ([9:55](https://youtu.be/_WFcUzO_9CY?t=595))
- **A backup can be made recurring by wrapping the existing function in cron.schedule, with no change to the function itself.** — The example runs a SQLite backup every minute (* * * * *) by moving the call into the scheduled callback. The process must stay running for the schedule to keep firing. ([11:10](https://youtu.be/_WFcUzO_9CY?t=670))
- **For a job whose success matters, monitor it with a dead-man-switch heartbeat rather than by reading logs. The service expects a ping on a schedule and alerts when it does not arrive.** — The heartbeat has an expected period matching the cron interval and a grace period for run time and latency. Alerts go to whatever channels are configured. The presenter uses Better Stack. ([13:39](https://youtu.be/_WFcUzO_9CY?t=819))
- **Ping the heartbeat only after the job has finished, using await. Keep the ping URL secret, store it in .env, and check response.ok.** — The ping is an ordinary fetch. If the job throws, the ping is never sent, and a missed ping is what triggers the alert. ([14:56](https://youtu.be/_WFcUzO_9CY?t=896))
- **The demo shows the full cycle: stopping the process produces an incident after the grace period, an email arrives, and restarting the process resolves the incident after the next successful ping.** — This is the practical value of the pattern: a crashed scheduler gets noticed without anyone checking the server or the file system. ([18:41](https://youtu.be/_WFcUzO_9CY?t=1121))

## Techniques
- **Basic node-cron schedule** — npm install node-cron. Then import cron from 'node-cron' and call cron.schedule('<expr>', () => exportData(name)). The second argument should be a wrapper arrow function, not the bare function reference. Use a six-field expression for seconds, e.g. */5 * * * * * for every five seconds (the video adds a column to a five-field expression; the exact field position is not spelled out, so check the node-cron docs). *When:* Any recurring Node job: report exports, emails, DB backups, cache refreshes.
- **Validate a cron expression before scheduling** — const isValid = cron.validate(expression); if (!isValid) { /* throw or fall back */ } then call cron.schedule(expression, fn) only when valid. *When:* The expression comes from an env var, a config file, or an LLM, rather than being hard-coded.
- **Round-robin job state with a closure** — let runs = 0; const names = ['report1', 'report2', 'report3']; cron.schedule(expr, () => { const name = names[runs]; runs = (runs + 1) % names.length; exportData(name); }); *When:* Each tick should process the next item in a fixed list, wrapping around.
- **Create a deferred, controllable task** — const task = cron.schedule(expr, fn, { scheduled: false }); task.start(); later, task.stop(). The process stays alive while a task is running. In the demo, setTimeout(() => task.stop(), 6000) stops a five-second task. *When:* Start a job only after a precondition (data present, DB connected), or stop it on a condition or signal.
- **Schedule an existing function without modifying it** — Leave backupDatabase() unchanged. Wrap the call site: cron.schedule('* * * * *', async () => { await backupDatabase(); }). Run node backup.js once, and leave the process running under a supervisor or on the server. *When:* You have a working one-off script and want it to run periodically.
- **Dead-man-switch heartbeat monitoring** — Create a heartbeat in the monitoring service, with a period matching the cron interval (the video uses 1 minute) and a grace period longer than the job's run time plus latency. Store the ping URL in .env with HEARTBEAT_URL=... and add import 'dotenv/config' at the top. Make the job async, wrap it in try/catch, and after await backupDatabase() run: const response = await fetch(process.env.HEARTBEAT_URL); if (!response.ok) throw new Error(response.statusText). Log errors with console.error. *When:* A scheduled job is critical enough that a silent failure matters: backups, billing syncs, data pipelines. Alerts should fire when the job stops running, not only when it throws.
- **Set heartbeat grace from measured duration** — Measure how long the job takes. Set the grace period to that duration plus margin for server latency. The presenter's own guidance is about 30 seconds or a bit more for a job that takes around 30 seconds, although he first sets 10 seconds in the UI. *When:* Choosing the grace period for any heartbeat or missed-run alert.

## Hot takes
- The node-cron section is a practical, correct intro. The Better Stack section is mostly a product walkthrough with no sponsorship label, so treat it as vendor-specific. The same pattern works with any dead-man-switch monitor.
- The grace-period guidance is inconsistent: the presenter sets 10 seconds and then recommends about 30 seconds or more for a job that takes around 30 seconds.
- The video never shows the exact seconds-field expression or where the optional seconds column goes; check the node-cron docs before copying.
- The video's own point is that a process crash can silently stop a job. A process supervisor such as systemd or pm2 is not covered, so the setup still assumes the Node process stays up.
