> Step-by-step build of a Django middleware that logs request method, IP, path, status and duration, then ships the logs to Better Stack with structured fields.

## Summary
The video builds a class-based Django middleware in a new core/middleware/logging.py file. It explains Django's request/response hook model: code before get_response runs before the view, and code after it runs on the way back out. The logger is configured in the same file with a StreamHandler, a Formatter, and an INFO level. Before the view it logs request method, client IP (from REMOTE_ADDR) and path. After the view it logs the status code and a duration measured with time.time(). The middleware is registered by dotted path in settings.MIDDLEWARE. A Better Stack source token is then wired in through the Logtail Python handler, which runs alongside the stream handler. Passing the dict as extra= makes its keys filterable fields in Better Stack's live tail instead of a stringified message. The closing caveat is that shipping logs over the network inside middleware adds latency to every request. The speaker suggests file-based shipping with Vector or FluentD, Celery, or Python's QueueHandler/QueueListener as alternatives.

## Key ideas
- **Django middleware wraps the view. A request passes through the MIDDLEWARE list in order, the view builds the response, and the response passes back out through the same middleware.** — This flow diagram is the mental model for the rest of the video. Each middleware can change the request on the way in and the response on the way out. ([1:13](https://youtu.be/_FZfjYVhnwA?t=73))
- **A middleware is a callable that takes a request and returns a response. The class form needs __init__ and __call__.** — __init__ receives get_response, which Django injects. __call__ does the work: code placed before get_response runs before the view, and code after it runs after the view returns. ([3:33](https://youtu.be/_FZfjYVhnwA?t=213))
- **Logger setup is done in the middleware module. A module-level logger gets a StreamHandler and a Formatter, and its level is set to INFO.** — INFO means INFO and anything more severe is emitted. The speaker skips dictConfig for this single-module case and mentions a separate Django logging video for that. ([7:26](https://youtu.be/_FZfjYVhnwA?t=446))
- **Request data is logged before get_response, and response data after. The request side includes method, REMOTE_ADDR and path. The response side includes status code.** — Two logger.info calls, one per phase. The response dict is built from the response object after get_response returns. ([9:52](https://youtu.be/_FZfjYVhnwA?t=592))
- **Duration is measured by taking a timestamp before get_response and subtracting it from a second timestamp after.** — This is per-request latency at the Django layer, which the speaker suggests for finding slow URLs or views. ([13:29](https://youtu.be/_FZfjYVhnwA?t=809))
- **Adding a Better Stack handler sends the same logger output to a remote source. Logs go to both the terminal and Better Stack.** — The source token is pasted directly into the file in the video, which the speaker says should not happen in real code. The handler is added with logger.addHandler, next to the existing stream handler. ([18:12](https://youtu.be/_FZfjYVhnwA?t=1092))
- **Passing the dict as extra= lets Better Stack index its keys as searchable fields. Without it, the message is only a stringified dict.** — Each request-data and response-data call gets an extra= argument with the same dict. The live tail then shows separate fields such as method and IP. ([20:40](https://youtu.be/_FZfjYVhnwA?t=1240))
- **Field-level search in Better Stack supports equality, contains, not-equal and does-not-contain. Level filtering is one click.** — Example: method equals GET. The speaker notes that contains is for string data. ([22:02](https://youtu.be/_FZfjYVhnwA?t=1322))
- **Network log shipping inside middleware runs on every request and can add latency to the application.** — The speaker's options are: write to a file and let Vector or FluentD ship it, offload to a Celery worker, or use QueueHandler and QueueListener to take the network call off the request path. ([23:18](https://youtu.be/_FZfjYVhnwA?t=1398))

## Techniques
- **Class-based request/response logging middleware** — Create core/middleware/__init__.py and core/middleware/logging.py. Define class LoggingMiddleware with __init__(self, get_response) storing self.get_response = get_response, and __call__(self, request). In __call__, build a request dict (method=request.method, ip=request.META['REMOTE_ADDR'], path=request.path), log it, call response = self.get_response(request), build a response dict (status_code=response.status_code, duration), log it, and return response. *When:* Per-request observability in Django where you need a consistent log line for every request, with no changes to individual views.
- **Register middleware by dotted path** — In settings.py, append the string 'core.middleware.logging.LoggingMiddleware' to the MIDDLEWARE list. The path is app package, then subfolder, then module, then class. *When:* Adding any custom Django middleware. Order in the list matters because the request passes through it top-down.
- **In-module logger with stream output** — logger = logging.getLogger(__name__). handler = logging.StreamHandler(). formatter = logging.Formatter(...) with time, level name and message fields. handler.setFormatter(formatter). logger.addHandler(handler). logger.setLevel(logging.INFO). The exact format string is not shown verbatim in the video. *When:* Quick setup for one module. Use dictConfig in settings.py (the speaker's Django logging video) once several modules log.
- **Per-request duration with time.time()** — Record start = time.time() at the top of __call__. After response = self.get_response(request), compute duration = time.time() - start and add it to the response dict. *When:* Finding slow URLs or views at the Django layer without a full APM.
- **Structured fields with extra=** — Pass the same dict as the message and as extra=: logger.info(request_data, extra=request_data). A structured log backend can then index each key as a field. *When:* Any log destination that can filter on fields, so you can query by method, IP or status code instead of parsing a string.
- **Adding a Better Stack Python handler** — Create a source in Better Stack (named 'Django Demo', platform Python) and copy its source token. Install the Better Stack Logtail Python package with pip (the video follows the package name on Better Stack's Python logging docs). Import the handler class from it, instantiate it with source_token=<token>, and call logger.addHandler(). Keep the token in an environment variable or .env file, not in the source. *When:* Shipping logs from a Django app to Better Stack for live tail and search.
- **Moving network log shipping off the request path** — Options named in the video: (a) write logs to a file and run Vector or FluentD to ship them; (b) send log calls to a Celery worker; (c) use Python's QueueHandler to enqueue records and a QueueListener thread to forward them. *When:* The Better Stack or any remote handler adds per-request latency in middleware, which runs on every request.
