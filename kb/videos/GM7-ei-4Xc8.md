> How a small AI-coding team runs Claude Fable 5 in Claude Code: keep effort at low-high, plan big and implement small, test-first with a separate test author, and layered code and security review subagents.

## Summary
The presenter from AI LABS argues that Anthropic's Fable 5 prompting guide only covers in-app use, and that workflow rules for coding with the model need to come from practice. Their main claims are that effort should stay between low and high because max and xhigh produced the same output in their testing while costing far more usage, and that a large model should write a PRD while a smaller model implements features that are not too big. They describe subagent model routing (ranking models by cost, intelligence and taste), using OpenAI's Codex plugin for Claude Code mainly as a reviewer, and running Ponytail, a rules set that makes agents write less code, but only on a codebase with tests written first. Tests are written by a dedicated TDD test-author subagent, because an implementing agent tends to write tests that pass its own bugs. For verification they run a code-quality reviewer and parallel security reviewers across parts of the platform, which they say found far more bugs than one whole-repo security pass that came back clean. They end with two habits: mock each feature in HTML before building it, and have the model quiz the developer on the changes before merging. The video contains a sponsored Veed segment and several unverified anecdotes, so the evidence is single-team experience rather than measured results.

## Key ideas
- **The Fable 5 prompting guide covers in-app use only; coding workflow rules have to be learned from using the model in real projects.** — The presenter says the guide does not explain how to use the model inside your own coding workflow, and that their team has run it for days across their own products and client work. ([0:00](https://youtu.be/GM7-ei-4Xc8?t=0))
- **Keep effort between low and high on Fable 5. Max and xhigh gave the same output as high in their testing, so they only add usage.** — Speaker's claim that lowering effort cuts usage roughly in half with no quality loss. Ultracode is described as a Claude Code skill layered on top of the effort level, which they say has not produced anything worthwhile. ([0:00](https://youtu.be/GM7-ei-4Xc8?t=0))
- **Plan with the large model and implement with a smaller one, using a PRD per feature.** — Fable or another large model writes a PRD from a project-specific template stored in a per-feature subfolder. The template asks how the feature affects other parts of the app. A smaller model implements it if the feature is not too large. The speaker says this pattern recurs with every new model release, and that the earlier advice was to use Sonnet 5 for smaller tasks. ([1:22](https://youtu.be/GM7-ei-4Xc8?t=82))
- **Route subagents by cost, intelligence and taste, and use Codex mainly for review.** — A CLAUDE.md model ranking (credited to Theo) rates models on cost, intelligence and taste for orchestrating subagents. Codex models are only reachable through the CLI, so OpenAI's Codex plugin for Claude Code supplies commands for them. The team uses Codex as a reviewer because they think it is better at reviewing other models' work, though they have not compared it with Fable 5. ([4:18](https://youtu.be/GM7-ei-4Xc8?t=258))
- **Ponytail makes agents write less code, but only safely with tests in place.** — Ponytail is described as a list of older coding rules that reduce code volume. Without tests, the refactors could break existing users. The team trusts Ponytail refactors because the test suite passes after each change. ([5:24](https://youtu.be/GM7-ei-4Xc8?t=324))
- **A separate TDD test-author subagent writes the tests before the implementing agent writes code.** — The implementing agent is not allowed to write its own tests, because it tends to write tests that pass its own faulty code. Tests are unit tests for each part of the app, for example a test that the settings icon opens its menu. All tests run on every change. The speaker says the test author prompt sits in a skill file and can be pasted into CLAUDE.md. ([6:46](https://youtu.be/GM7-ei-4Xc8?t=406))
- **Layered review subagents beat a single whole-repo security review.** — A code-quality review subagent checks architecture drift (adapted from a Cursor skill called Thermonuclear Code Quality Review). A security reviewer (adapted from the Claude Code security review GitHub Action) first returned clean on a new feature. Running six Fable 5 security reviewers in parallel, each over one part of the platform, found many bugs, which the team says they patched. ([9:06](https://youtu.be/GM7-ei-4Xc8?t=546))
- **Mock each feature in HTML first and quiz the developer before merging.** — Each feature is first added to an HTML mock-up in a design/mocks folder. The mock is a one-to-one prototype of the site. Before merging, the model is prompted to quiz the developer on the changes, so the developer keeps context on the codebase and can steer later agent work. ([10:34](https://youtu.be/GM7-ei-4Xc8?t=634))

## Techniques
- **Keep effort between low and high** — On Fable 5, set the effort level to low, medium or high in Claude Code and avoid xhigh, max or the ultracode skill by default. The speaker did not show the exact setting command. *When:* Default coding sessions where the team wants lower usage cost. Their testing found no output difference between high and max.
- **PRD-first planner/implementer split** — Create a subfolder per feature with a PRD written by the large model from a project-specific template. The template asks how the feature affects other parts of the app. Hand the PRD to a smaller model for implementation. *When:* Features that are not too large. Use the large model for planning and the smaller one for execution.
- **Subagent routing tiers in CLAUDE.md** — Write a model ranking into CLAUDE.md that rates each model on cost, intelligence and taste, and tell the orchestrating session which tier to use for each subagent. Use the Codex plugin for OpenAI models, which needs the Codex CLI installed. *When:* Multi-model setups where the main session spins up subagents on different models, with Codex reserved for review work.
- **Ponytail with a test net** — Install Ponytail as a Claude Code plugin. The speaker says only the prompt in its SKILL.md is needed, which can go into CLAUDE.md or be pasted before a Fable 5 coding session. Run it only after tests exist, then refactor and rerun tests after each change. *When:* Refactoring or trimming code in an app that already has users and a passing test suite.
- **Separate test-author subagent (TDD)** — Before implementation, a separate subagent writes unit tests from the PRD, one set per unit (for example, the dashboard). The implementing agent must not write its own tests. Run the full suite on every change. *When:* Any new feature, so that agent-written code can be checked against tests written by a different agent.
- **Parallel scoped security review** — Split the codebase into parts and run one security reviewer subagent per part in parallel, rather than one review of the whole repo. The reviewer is adapted from the Claude Code security review GitHub Action: give the repo link to Claude Code and ask it to convert the action into an agent. *When:* Before shipping, especially after large features. The speaker says the single whole-repo review came back clean while the split review found many bugs.
- **Architecture review subagent** — Run a code-quality reviewer subagent built on a Cursor skill called Thermonuclear Code Quality Review to check architecture direction after each feature. Apply its suggestions. *When:* After each feature, to catch drift in how the codebase is structured.
- **HTML mock-up before build** — Keep a design/mocks folder. Before coding a feature, add it to an HTML prototype that clones the whole site one-to-one, so the change can be seen first. *When:* Any UI-facing feature. The speaker notes this as the one new habit from Anthropic's field guide to Fable.
- **Pre-merge comprehension quiz** — Add a prompt that makes the model quiz the developer on the changes before a merge. The speaker says the prompt is in the Fable field guide. *When:* Before merging agent-written branches, so the developer keeps enough context to steer the codebase.

## Hot takes
- Higher effort settings (xhigh, max) are a usage trap on Fable 5, and the ultracode skill has produced nothing worthwhile. This rests on the team's own anecdotal testing.
- A benchmark claiming Fable got worse at coding because it routes to Opus is dismissed as untrustworthy, since it ranks Sonnet 5 first in reasoning. The speaker reports no rerouting in coding tasks, only when asked to explain reasoning.
- Ponytail is described as old coding rules with nothing new, but it is only safe on a codebase with tests.
- Agents writing tests for their own code is unsafe; a separate test-author agent is the fix.
- A single security review is not enough; parallel scoped security reviewers catch far more bugs.
- Quality is capped at 2 because the video has a sponsored Veed segment, and the rest is largely anecdotal team experience without measured results.
