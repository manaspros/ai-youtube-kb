> Two Meta infra engineers argue LLM inference is now a distributed-systems and orchestration problem, so teams should optimize cost per successful task and build a control plane, not just faster tokens.

## Summary
The speakers, both from Meta's efficiency and inference infrastructure team, frame inference as a hyperscale workload that is growing faster than any they have seen, and compare it to the cloud's move from VMs up to orchestration. They argue agentic workloads break microservice capacity planning, since demand scales with users times calls per user times tokens per call, so teams need elasticity, workload-aware scheduling and admission control. LLM serving differs from microservices in request size, the need for continuous batching, large per-request KV-cache state, expensive GPUs and costly restarts. A prompt crosses many hops (gateway, router, cache, scheduler, serving runtime), each with its own SLO and failure modes, so the speakers treat it like a distributed transaction and say reliability belongs in the control plane. They propose a four-quadrant framework for optimizations (avoid, share, move, delay the work), argue the KPI should be cost per successful task rather than cost per token, and describe cascading-failure defenses such as circuit breakers, queue-depth load shedding and retry budgets. They close by saying inference needs an orchestration layer that senses telemetry and adapts automatically.

## Key ideas
- **Inference is following the cloud's path: value and complexity move up to the orchestration layer.** — The speakers compare the 2008 VM era to today, arguing that after serving frameworks, the next layer (routing, KV-cache management, disaggregated prefill/decode, multi-model multiplexing) is where the value now sits. ([0:12](https://youtu.be/7c9FSUVcXR0?t=12))
- **Agent demand does not scale like web traffic, so capacity planning in a spreadsheet no longer works.** — Capacity now scales with users times calls per user times tokens per call. The speakers give rough call counts: 1 per chatbot turn, 10 to 20 for copilots, about 50 for research agents, and thousands of search calls for autonomous workloads. They recommend elasticity and workload-aware admission control. ([1:43](https://youtu.be/7c9FSUVcXR0?t=103))
- **LLM requests break the assumptions that microservice serving relies on.** — Request sizes range from about 50 to 100,000 tokens. Continuous in-flight batching is required, or throughput collapses. Per-request KV-cache state is expensive to build and to discard. GPUs cost far more and are slower to acquire, and a mid-decode failure can drop thousands of in-flight tokens. ([2:44](https://youtu.be/7c9FSUVcXR0?t=164))
- **Only one step in a request's path needs the model; the rest is infrastructure.** — Auth, model choice, region choice, admission control, cache lookup and batching all run outside the model, so the speakers argue that economics, reliability and user experience sit mostly in infrastructure. ([4:11](https://youtu.be/7c9FSUVcXR0?t=251))
- **Layers that were separate are now coupled, so a change in one can shift the others.** — They give a chain: a routing decision changes cache hits, which changes batch composition, which changes GPU utilization, which changes autoscaling. Regressions therefore need a top-to-bottom analysis. ([5:38](https://youtu.be/7c9FSUVcXR0?t=338))
- **Inference is a distributed transaction, and partial failure is the hard case.** — Every hop can retry, time out or fail, and tokens are already streaming to the user. If a host is preempted after 200 tokens, a plain retry is not enough. The speakers say reliability has to live in the control plane, because only the control plane sees the whole workflow. ([7:33](https://youtu.be/7c9FSUVcXR0?t=453))
- **Schedulers need to be workflow-aware, not just placement-aware.** — The speakers list the factors a scheduler should weigh: GPU type, HBM headroom, KV-cache state, model warm or cold status, tenant priority, workflow context (step number and spend so far) and latency budget. In their example, a failure at step 3 of a workflow wastes the compute already spent on steps 1 and 2, so admission, priority and retry decisions should account for that. ([9:01](https://youtu.be/7c9FSUVcXR0?t=541))
- **Use four quadrants to classify any optimization: avoid, share, move or delay the work.** — Avoid = caching (prefix, response, semantic). Share = batching, chunked prefill, speculative decoding. Move = routing to a smaller model or cheaper region. Delay = admission control and deadline-aware queuing. The speakers say this framework applies across vLLM, SGLang and TensorRT and helps compare stacked optimizations. ([9:58](https://youtu.be/7c9FSUVcXR0?t=598))
- **Optimize cost per successful task, not cost per token or per request.** — Cost includes retries, storage, failures, network and operations. The speakers say the product KPI should drive the optimization, because that is what users actually experience. ([11:25](https://youtu.be/7c9FSUVcXR0?t=685))
- **Cascading failure is the real failure mode, and KV-cache warm-up makes recovery slow.** — A degraded GPU raises latency, clients retry, queues grow, and the healthy GPUs saturate. Cold pools must warm up before they can take traffic, so rerouting is not a quick fix. Defenses they name: circuit breakers at routing, admission control that rejects rather than queues, load shedding keyed to queue depth rather than CPU or memory, and retry budgets. ([12:22](https://youtu.be/7c9FSUVcXR0?t=742))
- **Observability is the input signal for an automated control loop.** — Metrics they name: time to first token, memory-versus-compute utilization ratio, success per dollar, and end-to-end latency. Their trade-off triangle is latency, cost and throughput: larger batches raise throughput but can hurt tail latency, speculative decoding cuts latency but adds compute, and smaller models are cheaper and faster but lower quality. Retries push cost back up. ([15:36](https://youtu.be/7c9FSUVcXR0?t=936))
- **Inference needs its own control plane, and the design should assume one exists.** — Routing, batching, caching, scheduling and reliability converge into a layer that treats models, GPU, KV-cache, tokens and latency as schedulable resources. The speakers draw an analogy to Kubernetes for VMs. They say a team can build this layer, adopt open source, or buy a vendor product. ([17:05](https://youtu.be/7c9FSUVcXR0?t=1025))

## Techniques
- **Four-quadrant optimization check** — Sort every serving optimization into avoid (caching), share (batching, chunked prefill, speculative decoding), move (routing to a smaller model or cheaper region) or delay (admission control, deadline-aware queues). Then check how the chosen optimizations stack. *When:* When choosing or comparing serving optimizations, regardless of which runtime is in use.
- **Workflow-aware scheduling and retries** — Pass workflow context to the scheduler: step index, spend so far, latency budget and tenant priority. Use it to decide admission, priority and whether to terminate or retry a step, rather than treating each request in isolation. *When:* Multi-step agent workflows where a late-step failure wastes earlier compute.
- **Cascade breakers: queue-depth shedding, circuit breakers and retry budgets** — Shed load based on queue depth, not CPU or memory. Use circuit breakers in the routing layer and cap retries with a budget, so degraded GPUs or cold pools do not trigger a retry storm. *When:* When latency rises on a subset of GPUs or a region, and clients begin retrying.
- **Cost per successful task as the KPI** — Measure total cost per task that completes successfully, including retries, failures and network costs, and use it to judge serving changes instead of cost per token. *When:* Deciding whether a cheaper model, routing change or batching change is actually a saving.
- **Telemetry-driven control loop** — Collect TTFT, memory-versus-compute utilization, success per dollar and end-to-end latency. Feed them back into routing and scheduling decisions and repeat, so the platform adapts on its own. *When:* Operating a multi-model or multi-tenant inference fleet at scale.
- **Latency, cost and throughput trade-off triangle** — Treat each serving knob (batch size, speculative decoding, model size) as a move within the latency, cost and throughput triangle. Set the knobs against your SLO rather than tuning any one of them alone. *When:* Choosing batch size, speculative decoding or a smaller model under an SLO.

## Hot takes
- Inference is no longer a model problem; it is an orchestration problem.
- Stop optimizing cost per token and optimize cost per successful task.
- Agents cannot be capacity-planned the way microservices were.
- Reliability cannot be built at the edge; it must be a property of the control plane.
- Adding GPUs hides infrastructure problems rather than solving them.
