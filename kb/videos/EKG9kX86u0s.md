> Walkthrough of Google's new Rust Workspace CLI for agents: OAuth setup pain, CLI vs MCP token trade-offs, and design choices (nested JSON, runtime schema lookup, field masks) that keep context use low.

## Summary
Better Stack walks through Google's Rust Google Workspace CLI (GWS CLI), which lets an agent such as Claude Code call any Workspace API (Gmail, Drive, Slides, Sheets, Calendar). The presenter says it was built for agents: commands are generated at runtime from the API so they stay current, and it uses few tokens. Setup is the hard part: a Google Cloud project, the gcloud CLI, an OAuth client ID, a redirect port that must match exactly, and your email added as a test user while the app is in test mode. In demos, Claude drove the CLI to read recent emails, write a draft, build a slides deck and fill a Sheet and a calendar, using about 9% of context for the email task and about 15% for the slides task. The presenter credits the design: nested JSON params, help and schema queryable at runtime so the agent can look up exact parameters, and field selection to trim responses. He concludes that MCP is not obsolete, since MCP lets agents call functions directly and chain steps more easily, while CLIs are cheaper in tokens, portable and easy to reproduce. He also lists rough edges he hit: typos in generated URLs, localhost redirect confusion, and a token-refresh bug.

## Techniques
- **Agent-discoverable CLI with runtime help and schema** — Expose hierarchical subcommands (service, resource, sub-resource, method). Let the agent call --help once to see the tree, then a schema command for service/resource/method to get exact parameter names and types. Build commands from the API's own definitions at runtime so they do not go stale. *When:* Wrapping a large API for an agent, where a full tool list would cost too many tokens or drift out of date.
- **Nested JSON params flag for complex calls** — Accept a --params flag that takes nested JSON, instead of many flat flags. The agent builds the JSON directly. Per the presenter, that is easy for agents but hard for humans to type. *When:* Designing CLI or tool inputs that an LLM will generate, especially for APIs with deep structures.
- **Field selection to trim API responses** — Let the caller name the fields it needs, so the API returns only those. The presenter says this cuts response tokens because the agent does not receive unused data. *When:* Any API response the agent reads into context, such as email lists, file lists or sheet data.
- **Layer skills on top of the CLI for guidance** — Keep the CLI as the mechanical layer. Add skills for helpers, personas and multi-step recipes (e.g. block focus time, reschedule a meeting). Skills supply guidance that --help does not. *When:* Multi-step workflows where the agent needs the procedure, not just the command syntax.
- **Google Workspace OAuth setup for a CLI** — 1) Install the gcloud CLI (Homebrew on macOS in the video) and the Workspace CLI. 2) In the Cloud console, create or pick a project. 3) Run the CLI's setup command: sign in with your email, pick the GCP project, and select the APIs. Choose scopes deliberately; the presenter selected everything, which he says is not ideal. 4) Under APIs & Services > Credentials, create an OAuth client ID (web or desktop). 5) Copy the localhost port from the auth URL the CLI prints. 6) Under OAuth consent screen > Clients, add that port to the authorized redirect URIs. 7) Under Audience, add each user's email as a test user. 8) Retry until the CLI shows success. The exact subcommand name is not shown in the transcript. *When:* Setting up the GWS CLI for a Google account in test mode, or any similar Google OAuth desktop-style flow.
- **Choose CLI vs MCP by token and portability trade-offs** — Use a CLI when token budget, portability across harnesses, or reproducible commands matter. Use MCP when the agent must chain complex function calls or when no terminal is available. Some tools offer both (the Workspace CLI has an MCP mode). *When:* Deciding how to expose a service to a coding agent.

## Hot takes
- MCP servers are not out. CLIs are cheaper in tokens, but MCP handles direct function calls and chained steps better, so the choice depends on the use case.
- Google's OAuth setup for a CLI was the hardest part of the whole experience, harder than using the tool.
- Token numbers come from a few single-run demos, not a controlled benchmark, so they show direction, not precision.
- The presenter chose the broadest scopes ('everything') in setup and says that is not ideal for production use.
