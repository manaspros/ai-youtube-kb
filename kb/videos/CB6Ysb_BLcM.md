> Better Stack's walkthrough of the Clawdbot (Moltbot) personal agent: how its gateway, channels and state fit together, and why exposing it on a VPS and prompt injection are the main risks. Ends with a sponsor read.

## Summary
The host explains Clawdbot (also called Moltbot), an open-source personal assistant that runs an agent behind messaging apps and can act on the user's accounts. He sets it up on a cheap VPS under a non-root user rather than on a personal machine. He walks through the architecture: a gateway daemon with a dashboard and WebSocket server, channel adapters built on channel-specific libraries, an agent runtime built on Pi, and a state directory holding config, auth tokens and session transcripts. His first VPS deployment was brute-forced, so he moves the gateway behind Tailscale, disables public SSH and reaches the dashboard over the tailnet or an SSH tunnel. He calls prompt injection the biggest risk, since an agent with full system access will execute instructions hidden in PDFs, emails or links. He still finds the project impressive but says he is not comfortable giving it personal data. The video ends with a sponsor segment for Better Stack.

## Key ideas
- **Clawdbot (also called Moltbot) is a personal assistant that runs behind messaging apps and can act on the user's accounts, such as checking email, booking meetings and trading. It was created by Peter Steinberger about three months before the video and is not affiliated with Anthropic.** — The host frames the appeal as an always-on assistant with persistent memory and a configurable identity (called a 'soul'). He describes it as having full system access, which is the root of the risk. ([0:00](https://youtu.be/CB6Ysb_BLcM?t=0))
- **Full system access makes prompt injection the core threat. A malicious instruction in a PDF, email or web page can make the agent run commands and expose data.** — He cites someone who used the bot to download malware from a pull request via encoded instructions hidden in a URL. The speaker says this is the biggest security issue, bigger than the exposed-server risk. ([0:00](https://youtu.be/CB6Ysb_BLcM?t=0))
- **Isolating the agent on a cheap VPS under a non-root user with sudo is the workaround for people without a spare Mac Mini. The VPS is still internet-facing, so it needs hardening.** — A single install command sets up skills (1Password and Google Calendar are named) and model API keys. Telegram is the only channel he calls production-ready; WhatsApp worked but felt odd because it looked like talking to yourself. ([1:24](https://youtu.be/CB6Ysb_BLcM?t=84))
- **The architecture has four layers: the gateway daemon, channels, the agent runtime and the state store. Only the gateway talks to the model providers, and the state store is what needs protecting.** — The gateway daemon holds the dashboard, a WebSocket server and clients (terminal UI and web chat). Nodes add camera and canvas on native apps. Channels use per-platform libraries (Grammy for Telegram, Discord.js for Discord). The Pi-based runtime manages in-memory sessions, skills, tools and per-session queues, and a router handles multi-agent messages. Config, auth tokens and transcripts sit in a .clawdbot directory. ([2:40](https://youtu.be/CB6Ysb_BLcM?t=160))
- **Exposing the gateway on a public IP lets anyone reach the bot, and his first deployment was brute-forced. Running the gateway locally removes most of this exposure.** — For a VPS, he recommends Tailscale so only his own machines can reach the server, which also lets him disable public SSH. ([4:03](https://youtu.be/CB6Ysb_BLcM?t=243))
- **Remote access to the dashboard is best done over a private network: a Tailscale address, Tailscale serve, or an SSH tunnel. Each of these keeps the admin UI off the public internet.** — He suggests letting the bot configure Tailscale for the dashboard and WebSocket, but notes you must sign up and connect each machine yourself. ([5:31](https://youtu.be/CB6Ysb_BLcM?t=331))
- **Mitigations he lists are dedicated API keys for the bot, scrubbing sensitive data from chat history and the CLI's security-fix command. He says none of them stops prompt injection.** — Dedicated keys can be revoked if compromised. Transcripts in the state directory keep any sensitive data shared in chat, so scrubbing them limits the damage if the store is compromised. ([5:31](https://youtu.be/CB6Ysb_BLcM?t=331))
- **Second-hand anecdote: a friend's agent read a wife's email asking for EDM on Spotify and played it, because it had Spotify access. This shows how easily an agent can act on untrusted instructions.** — The story is attributed to a YouTuber called LowLevel and is not verified by the speaker. It supports his conclusion that the agent needs careful scoping of what it can reach. ([6:50](https://youtu.be/CB6Ysb_BLcM?t=410))

## Techniques
- **Isolate a self-hosted agent on a dedicated VPS** — Provision a cheap VPS, create a non-root user with sudo, and run the agent under that user. Keep the agent off your main machine so a compromise does not reach your personal files. The speaker names no specific provider or hardening steps beyond this. *When:* Running an always-on personal agent with broad tool access, where you do not have a spare machine to isolate it on.
- **Put the agent gateway on a private network with Tailscale** — Install Tailscale on the server and on each client machine so that only enrolled devices can reach the server. Disable public SSH and rely on SSH from inside the tailnet. Reach the dashboard via the Tailscale address, Tailscale serve, or an SSH tunnel. Connect the devices manually, since the bot cannot add them for you. *When:* Any gateway or admin UI on a public IP. This is the step he took after his first server was brute-forced.
- **Use a separate API key for each agent** — Create API keys used only by the agent, not your main provider key. Revoke and rotate one if it leaks, without affecting your other tools. *When:* Giving an agent provider credentials it will hold in its state store.
- **Scrub sensitive data from agent transcripts** — Review stored session transcripts, which the speaker says live in the agent's state directory, and remove any personal or secret data shared in chat. Treat the transcript store as sensitive data in its own right. *When:* After any chat that included personal data or credentials, and as part of routine hygiene for a messaging-based agent.
- **Run the agent CLI's security command** — The speaker says the CLI has a security command that fixes some issues automatically. He does not name it on screen, so check the CLI's help output before running it. *When:* As a first pass after setup, before exposing any endpoint. It does not address prompt injection.
- **Give the agent an identity file** — Set a persona or identity for the model, which the speaker calls its 'soul' and compares to a business card. The file name and format are not shown in the video. *When:* When you want a consistent personality across messaging channels. He presents it as a UX feature and does not discuss its security impact.
