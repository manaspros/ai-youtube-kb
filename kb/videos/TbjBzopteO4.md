> Better Stack's tour of Vercel's AI SDK for TypeScript: it builds a Next.js chat app with streaming, file input, reasoning display, manual, provider and MCP tools, and streamed structured output, all in about 17 minutes.

## Summary
The host argues the Vercel AI SDK is the easiest way to build AI features in TypeScript, because one API covers many model providers. He walks through a Next.js chat app, starting with a one-shot generateText call and moving to streamText, then UI messages with convertToModelMessages, and the useChat hook. He covers file uploads (images and PDFs), turning on OpenAI reasoning summaries through provider options, and smoothing bursty streams with smoothStream. The tool section compares three kinds: a hand-written image-generation tool, provider-defined tools (Google search and URL context), and external tools via Tavily plus an MCP server. The video ends with streamObject and useObject for partial structured output. It is a feature tour with little measurement, and several claims about tool behavior are stated without being shown.

## Key ideas
- **One SDK, many providers: a model is selected by a string routed through the Vercel AI Gateway (one key, one bill, fallbacks), or by a provider package such as Anthropic, OpenRouter or Google.** — The gateway route lets GPT-5 be called as a plain string. Switching to a provider package makes Claude Sonnet 4 the model, called straight from Anthropic. The speaker says non-streaming generateText can take over 20 seconds, which is why he moves to streaming. ([1:08](https://youtu.be/TbjBzopteO4?t=68))
- **The SDK splits into AI SDK Core (server: generateText, streamText, generateObject, streamObject) and AI SDK UI (client hooks: useChat, useObject, useCompletion). The UI hooks support React, Svelte and Angular only.** — On other frameworks, the backend functions are used with a hand-written frontend. ([3:32](https://youtu.be/TbjBzopteO4?t=212))
- **The app's state is the UI message, not the model message: a role plus parts (text, reasoning, tool calls, tokens). Before calling the model, the messages are converted with convertToModelMessages so UI-only data stays out of the context window.** — The backend returns toUIMessageStreamResponse. The client gets status values submitted, streaming, ready and error, and sendMessage appends to the message array. ([3:32](https://youtu.be/TbjBzopteO4?t=212))
- **Reasoning summaries are provider-specific and off by default. For GPT-5 they are enabled through providerOptions (summary auto/concise/detailed, reasoning effort medium), and the reasoning then streams to the UI.** — The speaker says the provider docs list all options, and warns that a model or provider's options differ. ([7:05](https://youtu.be/TbjBzopteO4?t=425))
- **There are three tool kinds: a manual tool you write (zod input schema plus execute), provider-defined tools (Google search and URL context, which the speaker says lock out other tools), and external tools from a service (Tavily search and extract) or an MCP server, which work across all models.** — All tools go into one tools object on streamText. In the UI, a tool part is keyed as tool-<toolName>. He chose Tavily over Google's built-in tools because they work with any model. ([9:25](https://youtu.be/TbjBzopteO4?t=565))
- **Tool loops need a stop condition. stopWhen with stepCountIs(20) caps the agent at 20 steps, so search followed by page-fetch chains cannot loop forever.** — The speaker says the default step count is one, but he hedges ('I believe'), and he does not show the default. ([14:02](https://youtu.be/TbjBzopteO4?t=842))
- **Fast models send big chunks, which look bad in a chat UI. experimental_transform smoothStream adds an artificial per-chunk delay and a chunking strategy (word, line, regex or custom); he judges the default best.** — Side-by-side comparison of no smoothing, default and line chunking is shown at 9:25. ([8:29](https://youtu.be/TbjBzopteO4?t=509))
- **Structured output streams partial objects. streamObject takes a zod schema (with .describe() hints per field), and the client useObject hook takes the same schema for validation and gets a partial object that fills in as it streams.** — Demonstrated with a task-breakdown schema (subtasks with descriptions and time estimates, plus an overall estimate) on the prompt 'clean the kitchen'. ([15:16](https://youtu.be/TbjBzopteO4?t=916))

## Techniques
- **Streaming chat endpoint** — Server: read messages from the POST body, convert with convertToModelMessages, call streamText({model, messages, ...}), return toUIMessageStreamResponse(). Client: useChat gives messages, sendMessage and status; the default transport is /api/chat (overridable). Render each message's parts (text as markdown, reasoning in its own component, tool-<name> parts as custom components). *When:* Any user-facing chat in a React or Next.js app. Use the convert step so UI-only fields (tokens, reasoning, tool UI state) never reach the model.
- **Per-provider options for reasoning** — Pass providerOptions to streamText. For OpenAI GPT-5 the speaker sets a reasoning summary (auto, which resolves to detailed; or concise) and reasoning effort medium. Reasoning parts then stream to the UI. *When:* Reasoning models where the user should see the thinking steps. Check the provider page, since names and values differ by provider.
- **Manual tool with zod schema** — Use tool({description, inputSchema: z.object({...}) with .describe() on each field, execute: async (input) => ...}) and add it to the tools object of streamText. Image generation used experimental generateImage with the gpt-image-1 model. Render the result in the UI from the tool-<key> part, showing a placeholder until the output arrives. *When:* Give every model the same custom capability (image generation, a internal API). Behavior is the same across providers because the tool runs your code.
- **External search and page-fetch tools** — Wrap Tavily's search function as a web-search tool and its extract function as a URL-context tool, both with descriptions and zod input schemas, then pass them in the tools object. The speaker's example asked for formula1.com headlines on GPT-5 and the model scraped the page. *When:* You need web tools that work with any model. The speaker prefers this over provider-defined tools, which he says lock out other tool types.
- **Provider-defined tools plus source output** — Switch to the provider (here Gemini 2.5 Flash) and add google.tools search and URL context to the tools object. Turn on the response option that sends sources, then render source components from the message parts. Provider-defined tools may disable other tool calls (speaker's claim, not shown). *When:* A quick single-provider prototype where built-in grounding is enough and cross-provider portability is not needed.
- **MCP server as tools** — Create an HTTP client transport with the MCP SDK and the server URL. Create the client with experimental_createMCPClient({transport}), then await client.tools() and spread the result into the tools object. stdio and SSE transports also work. The demo used a GitHub code-search MCP server. *When:* You want a remote MCP server's tools available to the model without writing wrappers. The feature is marked experimental in the video.
- **Agent loop step cap** — Set stopWhen: stepCountIs(20) on streamText, or pass a custom condition. The helper stepCountIs is part of the SDK. *When:* Any run where the model may call several tools in sequence, such as search then fetch then fetch again. The cap prevents runaway loops.
- **Smooth streaming** — Pass experimental_transform: smoothStream({delayInMs: 10, chunking: <word default | 'line' | regex | custom detector>}) to streamText. *When:* A fast model streams in big chunks and the UI feels jumpy. Choose delay and chunking to match the target chat feel.
- **Streamed structured output** — Server: streamObject({model, prompt, schema: z.object({...})}) with .describe() hints, returned as a text stream response. Client: useObject({api, schema}) with submit(prompt). Render the partial object as it fills in. *When:* A UI should show structured results (plans, task breakdowns, forms) as they generate, instead of waiting for the full JSON.
- **Local dev with an AI gateway** — Use a gateway such as the Vercel AI Gateway to pass a model string ('openai/gpt-5' style) with one API key, and rely on its provider fallbacks. Swap in a provider package when a provider-specific feature (such as Anthropic's direct API) is needed. *When:* Many models to try, one bill, and failover, with direct provider packages kept for provider-specific features.

## Hot takes
- The speaker calls the AI SDK 'the best way to build AI powered apps in TypeScript'. This is opinion, and the video only compares it to the individual provider SDKs.
- He claims that using Google's provider search tool locks out every other tool call. This is stated, not shown, and he gives no version or doc link.
- He says the default stopWhen step count is one, hedged with 'I believe'. He does not show the default, so treat it as unverified.
- 'About 10 minutes' to build the full feature set is a hype framing. The video is a feature tour, so the real time depends on the reader's stack.
- The content is mostly API surface shown in one app with little on error handling, cost, evals, or how behaviour changes across models. Quality is capped at 3, since the value is the feature map, not depth.
- The video includes a self-promo pointer to a separate AI Elements video. It is not a sponsored segment.
