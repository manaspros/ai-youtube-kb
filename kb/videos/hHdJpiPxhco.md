> Qwen 3.8 27B ships an MTP draft head inside its weights; enabling it can roughly double or triple local decode speed with the same output, but only on a current runtime build, with a tuned draft depth and temperature, and only if the model fits in VRAM.

## Summary
The host argues that Qwen 3.8 27B already contains a multi-token-prediction (MTP) head that gives speculative decoding for free, and that most local runtimes leave it off. Decoding is memory-bandwidth bound, so drafting several tokens and verifying them in one pass recovers idle GPU time, and the full model verifies every draft, so he says output quality is unchanged. He says a llama.cpp flag rename on May 13, 2026 made older spellings silently ignored, which cost him three days and roughly halved his throughput. He then covers draft depth (throughput peaks around 4-5 rather than the common 2-3), sampler temperature (lower temperature raises draft acceptance), and gains per hardware: NVIDIA 3090/4090, Blackwell-only NVFP4, AMD Vulkan vs ROCm, Apple Silicon, and a laptop where CPU offload over PCIe makes the flag useless. Setup is summarized for llama.cpp, vLLM, SGLang and Ollama. Every benchmark is a single measurement he himself caveats as a ceiling.

## Key ideas
- **The MTP draft head is already inside the Qwen 3.8 27B weights, so speculative decoding needs no separate drafter model or extra download.** — Ollama's 4-bit MTP tag is about 18 GB with the head and about 18 GB without it. A separate drafter would normally add a few GB of resident memory and config work. ([2:34](https://youtu.be/hHdJpiPxhco?t=154))
- **Decoding is limited by memory bandwidth, not arithmetic. Each token re-reads the full weights, so the GPU is mostly waiting.** — Speculative decoding attacks that waste: a cheap guesser proposes several tokens, and the full model verifies them in one pass. Wrong guesses are discarded, so the output is unchanged by design. ([1:25](https://youtu.be/hHdJpiPxhco?t=85))
- **A llama.cpp flag rename on May 13, 2026 silently broke the old spelling. The old name is still accepted but ignored, so throughput quietly drops.** — The host ran about 70 tok/s for three days on a stale flag. A write-up on a 4090 reports about 140 tok/s falling to about 70 when speculation is off. The exact flag spelling is garbled in the captions, so confirm it against your build's help output. ([3:58](https://youtu.be/hHdJpiPxhco?t=238))
- **Draft depth has a throughput peak in the middle, not at the lowest value. Acceptance falls with depth, but throughput does not follow it down.** — Reported acceptance is 81% at depth 2, 56% at depth 5 and 40% at depth 8. Throughput climbs to about 115 tok/s at depth 5. Common recipes at 2-3 leave up to 27% of available throughput unused. ([4:57](https://youtu.be/hHdJpiPxhco?t=297))
- **Sampler temperature strongly affects draft acceptance. Qwen's recommended temperature of 1 cut acceptance from about 85% to about 65% in one researcher's runs.** — A hotter sampler flattens the next-token distribution, which makes the drafter's guesses miss more often. Lowering temperature raised acceptance and speed, but it is a real trade-off against the author's recommended setting. ([6:25](https://youtu.be/hHdJpiPxhco?t=385))
- **Gains depend heavily on task and hardware. The same card and file gave 93 tok/s on standard prompts and 167 on agent turns.** — The 206 tok/s NVFP4 headline only runs on Blackwell, so it is unreachable on 3090/4090 cards. On AMD, the vendor's figures were measured on Vulkan rather than ROCm, and independent tests put Vulkan 20-30% ahead for generation. Apple Silicon gained about 2.45x on average with a ported drafter. ([7:48](https://youtu.be/hHdJpiPxhco?t=468))
- **Speculation cannot fix a transfer bottleneck. If the model spills to system RAM over PCIe, the flag adds drafter overhead with no gain.** — A 12 GB laptop got 4.5 tok/s with 4-bit plus the flag and 12.8 tok/s with 2-bit and no flag. The host's advice is to buy VRAM for the quantization first, because MTP multiplies existing speed and cannot create it. ([10:29](https://youtu.be/hHdJpiPxhco?t=629))
- **This model is dense, so expert-offload flags do nothing. The correct setup is plain layer offload plus the speculative flag.** — The host says the flag that pushes experts to the CPU has no effect on a dense model. ([3:58](https://youtu.be/hHdJpiPxhco?t=238))

## Techniques
- **Enable MTP in llama.cpp** — Use a llama.cpp build from after May 13, 2026. Set the speculative-decoding type flag to MTP. The host's caption-garbled name reads like 'speculative NGPU layers in the spec type flag'. Confirm the exact spelling with the build's --help output, because the old spelling is silently ignored. Use plain layer offload (not expert offload) for this dense model. Start the draft depth at 4 or 5, then sweep. *When:* Running Qwen 3.8 27B locally on llama.cpp on a GPU that holds the quantized model.
- **Enable MTP in vLLM** — Speculative decoding is configured as a JSON-style config key in the serving configuration, not a command-line flag. Read the speculative decoding section of the vLLM docs for the exact version you run, and set the draft depth there. *When:* Serving the model with vLLM on a single GPU, including the RTX 5090 setup described in the video.
- **Enable MTP in SGLang** — Set the speculative algorithm parameter. The host says the flag exists on older cards with lower ceilings. He did not give the exact key name. *When:* Serving the model with SGLang.
- **Enable MTP in Ollama with a tag** — Pull one of the three MTP-marked tags instead of the default tag (4-bit is about 18 GB with the head). No config editing is needed. *When:* You want the simplest setup and are on Ollama.
- **Sweep draft depth and find your peak** — Benchmark draft depths from 2 to 8 on your own card and workload. Record tokens/s and draft acceptance at each depth. Pick the peak rather than copying 2-3 from community recipes. The host's example peak is near 5. *When:* Before deploying speculation on any new hardware, model or task mix.
- **Tune sampler temperature for draft acceptance** — Sweep the temperature downward and log acceptance and throughput alongside output-quality checks. Lower temperature raised acceptance in the host's runs. Decide explicitly between the author's recommended temperature (1) and a lower temperature for speed. *When:* Speculation is on and acceptance is lower than expected.
- **Benchmark by task type, not one number** — Measure agent-style turns (short context, predictable structure) separately from standard prompts. Report both, since the same setup gave 167 vs 93 tok/s in the host's test. *When:* Reporting or comparing speculative-decoding throughput.
- **Check the memory path before enabling** — If the model spills to system RAM over PCIe, measure before and after. Speculation does not hide transfer latency and can cost throughput. Prioritize VRAM for the quantization level. *When:* The model does not fully fit on the GPU.

## Hot takes
- The title '3X Faster' rests on one best-case single-card comparison. The host himself says every figure is a ceiling measured with conditions cropped off, so the real gain on a given setup can be much smaller.
- The claim that output is 'token for token identical' and 'mathematically guaranteed' is stated strongly from one benchmark. Speculative decoding is lossless in principle, but the host also shows that sampler settings change acceptance, so verify on your own prompts.
- The most reusable point is operational, not the speedup: a silently ignored flag can halve throughput with no log warning. Verify your build reads the flag.
