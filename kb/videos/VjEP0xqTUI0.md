> Arman Vaziri (Ramp) on building go-to-market orchestration: an internal CDP, durable background agents on Temporal, scoped retrieval, and an MCP that turns employee experiments into productized use cases.

## Summary
Arman Vaziri, who leads product and sales-led growth engineering at Ramp, describes go-to-market orchestration as describing a campaign in plain intent and having it distributed across outbound, ads, web and in-app channels. He argues the bottleneck is coordination after the idea, not the idea itself, and that the fix starts with a consistent data foundation. Ramp built an internal customer data platform on Postgres with Kafka for real-time signals, batch enrichment jobs, and a warehouse path via dbt, Snowflake and reverse ETL. The team solved one concrete workflow first (pre-meeting briefs for account managers) and then reused its pieces for other teams. The agent layer runs durable threads on Temporal, scopes tools per agent, supports human-in-the-loop pauses, and retrieves account-specific context from a vector store (TurboPuffer) using combined vector, attribute and keyword search. Nightly background agents fan out per account, combining system-owned skills with user-written instructions. Employees reach the same tools through a GTM MCP server, and the usage traces show which problems people are solving so the team can productionize them. The talk gives no benchmarks; its numbers are scale and history statements.

## Key ideas
- **The bottleneck is coordination after an idea exists, not idea generation** — Teams across product, data, engineering and GTM have many ideas. The hard part is finding the audience, getting people to follow the playbook, and producing the enablement material, so the goal is to cut coordination cost. ([1:04](https://youtu.be/VjEP0xqTUI0?t=64))
- **Build a consistent data substrate before any agent work** — Ramp's first problem was messy, inconsistent source-of-truth data across CRM, product, enrichment, web and buying signals. They built an internal CDP on Postgres that keeps transactional guarantees and referential integrity across entities and records where each fact came from and when it arrived. ([5:17](https://youtu.be/VjEP0xqTUI0?t=317))
- **Solve one team's problem first, then extend horizontally** — Pre-meeting briefs for account managers came first. Teams share common workflows (outbound, meeting prep), so patterns built for one team are mirrored to others, and each new team needs its own skills and data integrations. ([3:52](https://youtu.be/VjEP0xqTUI0?t=232))
- **Durable execution with each model and tool call as a checkpointed activity** — Every agent thread runs on Temporal, with each tool call and model call as an activity. If a worker dies, the thread resumes from the last completed step with its accumulated state instead of reprocessing from the start. ([9:35](https://youtu.be/VjEP0xqTUI0?t=575))
- **Scope retrieval to the account instead of loading the raw corpus** — Enablement material, playbooks and call transcripts are chunked, embedded and stored in a vector store. Agents combine vector, attribute and keyword search filtered to one account, which avoids pulling the full corpus into context. The speaker says this is both inefficient and expensive otherwise. ([11:01](https://youtu.be/VjEP0xqTUI0?t=661))
- **Run nightly background agents and let users customize them in text** — A nightly job fans out one agent per account. Each agent uses system-owned meeting-prep skills plus custom instructions users write as text, which drove adoption because people can express their preferred brief format. ([12:27](https://youtu.be/VjEP0xqTUI0?t=747))
- **Expose the same tools to employees and use their MCP traces to find what to productionize** — A GTM MCP server gives employees the same tools the background agents use. Usage traces show the problems people are solving, and the team turns the best of those prompts and skills into shared, productionized use cases. ([13:58](https://youtu.be/VjEP0xqTUI0?t=838))
- **Use multi-armed bandit thinking and guardrails for multi-channel campaigns** — Campaigns run across channels with consistent audience targeting. Agents balance exploring new campaigns against exploiting known returns, and guardrails enforce compliance, rules of engagement, and avoiding repeated outreach. ([17:20](https://youtu.be/VjEP0xqTUI0?t=1040))
- **Small teams should start with narrow automations and stitch them together** — The speaker's advice to a small company is to pick one very specific problem and automate it, as Ramp did with automated outbound when it had two people and GPT-3.5. A perfect architecture built over a year is not practical; vertical solutions get connected later. ([18:24](https://youtu.be/VjEP0xqTUI0?t=1104))

## Techniques
- **Durable thread with checkpointed activities** — Run each agent job as a workflow (Temporal here). Wrap every model call and tool call as its own activity so a restart resumes from the last completed activity with saved state. *When:* Long-running or background agent jobs where a worker can die mid-run and re-running from scratch would be slow or costly.
- **Account-scoped hybrid retrieval** — Chunk and embed unstructured sources (transcripts, emails, playbooks). At query time, filter by entity (account) and combine vector, attribute and keyword search, returning only scoped snippets. *When:* Large unstructured corpora where the agent needs context for one entity and loading everything would be too big or too expensive.
- **Per-agent tool scoping with human pause and resume** — Give each agent its own set of tools, integrations and skills. Include a pause point that waits for human input, then resumes the run. *When:* Agents that touch different systems per role, or any step that needs human sign-off such as a CRM write.
- **System skills plus user text instructions** — Ship owned skills at system level and let users add their own formats or preferences as plain-text instructions that the agent combines at run time. *When:* Output formats differ per user and adoption depends on people shaping the output.
- **Nightly per-entity fan-out** — A scheduled job starts one agent per account, each with tools, data access and skills, and writes the precomputed artifact (e.g. a meeting brief) for the user to read. *When:* Recurring prep work where results can be computed ahead of time and reused by many downstream consumers.
- **Persist derived entity matches** — Map noisy identifiers (for example attendee emails to accounts) once with fuzzy matching, store the result, and let every downstream consumer read it instead of recomputing. *When:* Entity-resolution steps that are expensive or ambiguous, such as emails shared across several businesses.
- **Shared tool surface via MCP plus usage mining** — Expose the same tools that background agents use through an MCP server for employees. Use the remote tool-call reasoning to find repeated problems and promote the best prompts and skills into shared use cases. *When:* An internal platform where teams build their own agents and the platform team wants to learn which problems to productionize next.
- **Explore vs exploit with guardrails across channels** — Keep several campaign options live, allocate traffic with a bandit-style explore/exploit rule, and enforce compliance and contact-frequency rules in the guardrail layer. *When:* Multi-channel outreach where the same audience can be reached from several campaigns.

## Hot takes
- You can't spend a year building a perfect system architecture. Build vertical solutions first and stitch them together.
- The most valuable data a company holds is unstructured (call transcripts, emails, notes), so retrieval over it matters more than most structured pipelines.
- Usage of an internal MCP is a product signal. The prompts and skills people build on it show what to productionize.
