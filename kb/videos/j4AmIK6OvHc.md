> LiveKit's Jesse Hall argues voice-agent latency is a budget to spend on human-like behavior, not raw speed, and shares audio-based turn detection, perceived-latency metrics, async tool handling and an outcome-scored simulated-caller benchmark.

## Summary
The talk starts from the claim that voice agents should feel human, so latency should be treated as a fixed budget rather than something to minimize. Voice agents are usually a cascade of speech-to-text, LLM and text-to-speech, and leaderboard scores measured on clean audio miss the errors that flow between stages (for example, a wrong date from STT leads to a confidently wrong booking). The speaker says the metrics most teams track are misleading: TTS time-to-first-byte can hide hundreds of milliseconds, up to about 0.75s, of silence, and LLM time-to-first-token ignores that TTS needs a full first sentence. Tool calls of 2 to 40 seconds need to be handled asynchronously, with the agent speaking while the tool runs, as a receptionist would. For turn-taking, LiveKit built an audio-based end-of-turn detector and reports lower interruption rates than the best alternative at the same latency. The pipeline overlaps work by running the LLM on a provisional transcript and starting TTS on the first complete sentence. The benchmark runs a real hotel-booking agent against hundreds of simulated callers who interrupt and change their minds, scoring real database outcomes and penalizing gameable completions. The talk ends with a vendor launch of a tuned Gemma 4 31B model on LiveKit Inference.

## Key ideas
- **Latency is a budget; the goal is human-like behavior, not speed alone** — Speed by itself does not make a voice agent feel human. The speaker frames the goal as an agent that listens while it talks, tells a finished thought from a pause, and handles mid-sentence changes. Model choice and pipeline configuration matter more than shaving milliseconds. ([1:10](https://youtu.be/j4AmIK6OvHc?t=70))
- **Leaderboards score components, but you ship a cascade (the leaderboard trap)** — STT, LLM and TTS are scored on clean audio. In production an STT error (Tuesday the 3rd heard as the 30th) propagates downstream, and the layers below cannot detect it. The real question is which stack to ship, not which model is best. ([3:52](https://youtu.be/j4AmIK6OvHc?t=232))
- **Measure perceived latency (time to first audible audio), not TTFB or TTFT** — Some TTS providers emit hundreds of milliseconds, up to about 0.75s, of silence before audio starts. Time to first token is a text metric, and TTS needs a full first sentence, so the fastest-streaming model is not necessarily the one that finishes its first sentence soonest. ([4:52](https://youtu.be/j4AmIK6OvHc?t=292))
- **Tools need async handling so the agent keeps the conversation going** — A tool can take 2 to 40+ seconds. The speaker's pattern: a normal tool whose first status update hands the turn back to the agent while the work continues in the background. The conversation and the tool stop sharing one thread. The demo agent handled interruptions and a mid-booking date change without awkward pauses. ([7:43](https://youtu.be/j4AmIK6OvHc?t=463))
- **Turn-taking should use the audio signal, not only the transcript** — Humans negotiate turns in a few hundred milliseconds using tone and intonation. LiveKit's turn detector reads the audio itself. At the same latency budget the best alternative cut users off 9.9% of the time, versus 4.5% for theirs. The eval harness is open source. ([10:17](https://youtu.be/j4AmIK6OvHc?t=617))
- **Overlap the pipeline: speculative LLM on a provisional transcript, TTS on the first sentence** — End-of-turn fires from audio before the final transcript lands. The LLM starts on a provisional transcript and is kept if the final words match, which saves about half a second. TTS starts on the first complete sentence, so the first audible byte arrives when the human stops waiting. ([10:17](https://youtu.be/j4AmIK6OvHc?t=617))
- **Treat about 1.5s end to end as the ceiling and about 600ms as the target** — Within roughly 1.5 seconds the conversation still holds, but that is the edge. Near 600ms it starts to feel human. The design question becomes what is the most human-like agent that fits inside the window. ([11:40](https://youtu.be/j4AmIK6OvHc?t=700))
- **Benchmark with simulated callers and score outcomes against a human bar** — Hundreds of simulated callers interrupt, mumble and change their minds. Scoring covers whether the correct reservation was written, whether the caller was cut off, whether names and dates are right, and whether there were invented tool calls or leaked personal data. Completion alone is gameable, so unnecessary questions and extra steps are penalized. ([11:40](https://youtu.be/j4AmIK6OvHc?t=700))
- **Swap components while holding the scenario inputs identical** — The same agent and the same scenarios run with different models, and every model sees byte-for-byte identical input. Benchmarks are per agent, so teams are invited to run their own agent through the same method and set of eval sets. ([13:00](https://youtu.be/j4AmIK6OvHc?t=780))

## Techniques
- **Perceived-latency metric** — Instrument the time from the end of the caller's speech to the first audible audio sample at the caller, not the provider's TTFB or the LLM's TTFT. Track per TTS provider, since some emit leading silence. Set the budget on this number. *When:* Any real-time voice or streaming UI where a provider dashboard looks fast but users report lag.
- **Async tool with early turn release** — Write the tool as a normal tool, but have its first update return control to the agent so it speaks (for example, 'give me a sec, I'm looking up your account') while the tool keeps running. Keep the conversation thread and the tool's work separate. *When:* Tools that may take seconds or tens of seconds (booking, lookups, long jobs) inside a conversational agent.
- **Audio-based end-of-turn detection** — Run a turn detector on the raw audio (prosody, pitch, intonation) to decide when the caller has finished, instead of waiting for the final transcript. Evaluate it against a baseline at the same latency budget on the rate of users cut off mid-thought. *When:* Voice agents where interruptions and premature cut-offs damage the experience.
- **Speculative LLM on provisional transcript, TTS on first sentence** — Start the LLM when end-of-turn fires on the provisional transcript. Keep the response if the final transcript matches the provisional one, otherwise regenerate. Send text to TTS at the first complete sentence rather than waiting for the full response. *When:* Cascaded STT-LLM-TTS voice pipelines where latency is dominated by waiting for full transcripts and full responses.
- **Outcome-scored simulated-user benchmark** — Build a simulator that interrupts, mumbles and changes its mind. Score end-state outcomes (correct DB write, no truncation, correct entities, no invented tool calls, no leaked PII) against a human-equivalent bar. Add penalties for unnecessary questions and redundant steps so that a guessed completion scores lower. Feed byte-identical inputs to each model under comparison. *When:* Choosing STT, LLM or TTS models for a specific agent; regression testing an agent after a model or prompt change.
- **Stack-level model selection** — Do not pick components by leaderboard rank. Swap one component at a time (or a whole stack) inside a complete working agent, run the simulator, and choose the stack that wins on outcomes and perceived latency within the budget. *When:* Before shipping a voice agent, and whenever a new model appears.
- **Checklist for voice agents** — In order: set the latency budget first; measure perceived latency; spend remaining budget on model quality, not on speed that does not matter; move anything over about 1 second to async handling so the conversation never stops; test the whole conversation, not each component; keep testing in production. *When:* Planning or reviewing any real-time voice agent.
