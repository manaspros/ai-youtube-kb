## Summary
AI LABS sets up Andrej Karpathy's autoresearch-style loop on their own app and reports one change they made to it. They first explain the original pattern (one editable file, a locked scoring file, a plain-English program.md, keep-or-undo per round) and list four conditions a task needs before a loop is worth building. Their Claude Code setup uses skills for project context, writing checks, and the build run, and a script that freezes the checks in a folder the agent cannot edit. Each feature is handed to a feature-builder subagent with fresh context, and each round is logged to a results file. The main addition is an outer "auto loop" that reads the results file, finds recurring failures, and rewrites the how-to-work section of program.md, without touching the checks. The demo is one feature built in about 6 minutes and a three-round test on a second app, with no baseline timing or repeated runs to support the 10x headline. Part of the video is a sponsor segment for Upstash Box.

## Key ideas
- **Loops only pay off for tasks that repeat, have a machine-checkable score, tolerate the token cost of failed rounds, and let the agent run what it built. One-off jobs are better done with one good prompt. Never let a whole app be built in one loop.** — The host lists four conditions. A loop takes time to build, so the task must recur. Failed rounds still burn tokens, so a long loop on a $20 plan can hit the usage limit before the work is done. The score must come from code, not a human. The agent must be able to run the app and see what broke. They only loop on single features or a simple version of the app. ([2:32](https://youtu.be/qLfSDQ5NGh0?t=152))
- **The Karpathy autoresearch pattern: the agent may edit only one training file, a separate scoring file is off limits so the agent cannot make the score easier, and program.md gives plain-English rules. A change is kept if the score improves and undone otherwise.** — Karpathy's run covered about two days, about 700 experiments, and about 20 speedups. The host also cites a Shopify CEO who ran the same kind of loop overnight, with 37 experiments and a model 19% better by morning. ([0:00](https://youtu.be/qLfSDQ5NGh0?t=0))
- **Freeze the checks before building. Checks are written first, the user reviews them in plain language, a script moves them into a locked folder, a Claude Code settings rule blocks edits to that folder, and the checks are committed to git.** — The point is that the loop cannot make its own tests easier to pass. The host says a commit adds a second layer of protection. The exact settings key is not shown. ([5:00](https://youtu.be/qLfSDQ5NGh0?t=300))
- **Keep each feature's context clean. A project-context skill stores what the app is, its pages, conventions, and things to avoid. The build run hands each feature to a feature-builder subagent that starts fresh, and each round is written to a results file.** — The host chose a skill over a plain file because only a skill's short description stays in context all the time, and the full text loads only when needed. ([4:00](https://youtu.be/qLfSDQ5NGh0?t=240))
- **A passing score can miss integration gaps. In the demo, all 11 checks passed in round one, but the checks only covered the ordering rules. The loop still had to build the order form the guest uses and connect it to those rules before it marked the feature done.** — The host added a guest-email check, which took the list from 10 to 11 checks. The check verified that the email is a real address. The build took about 6 minutes. ([7:36](https://youtu.be/qLfSDQ5NGh0?t=456))
- **Agent habits do not persist across rounds, so the same mistake recurs in each new feature. The fix is an outer loop, the auto loop, which reads the results file, finds recurring problems, and rewrites the how-to-work section of program.md. It is not allowed to edit the checks.** — The host frames this as the Karpathy program.md step, but the agent writes the program.md rules rather than a person. ([8:38](https://youtu.be/qLfSDQ5NGh0?t=518))
- **Run the outer loop one feature at a time and review after each. Two habits came out of the test on a project-management app: wire each feature into the live app in the same round its checks pass, and find every existing code path that already does the job and update it.** — The shared-database feature passed all 10 checks but never saved anything, which is the failure that led to the first habit. The mentions feature broke an older code path that still read @ the old way, which led to the second. ([9:55](https://youtu.be/qLfSDQ5NGh0?t=595))
- **The checks catch real errors in the test. Round 1 broke mentions and was undone. Round 2 split shares 33/33/33, which sums to 99, and failed the check. Round 3 passed all 10 checks.** — The host ends with a report that says where the agent went wrong, how it was fixed, and how the workflow changed. The whole test covers one app. ([11:23](https://youtu.be/qLfSDQ5NGh0?t=683))

## Techniques
- **Loop-fit test before building a loop** — Check four things before setting up a loop: the task recurs often, the token budget covers failed rounds, the result can be scored by code with no human, and the agent can run the app and see failures. If any fails, use one prompt instead. *When:* Before deciding whether to build any loop for a coding task.
- **Project-context skill as app memory** — Ask the agent to create a skill that records the app's pages, conventions, and do-not-do list. Keep it updated as the app grows. Store it as a skill, not a plain file, so only its short description sits in the context window. *When:* When a loop or agent needs per-app knowledge without loading all of it into every task.
- **Write, review, approve, lock, and commit checks** — A write-checks skill generates the checks before any feature is built. The agent lists each check in plain words, and you iterate until coverage is right (the demo added an email-validity check). An Approve Checks script moves the checks into a locked folder. A Claude Code settings rule blocks the agent from editing that folder. Then commit the checks. The video does not show the settings key. *When:* In any loop where the agent could otherwise weaken its own tests to pass.
- **Fresh feature-builder subagent per feature, with a results file** — The build skill runs one pass per feature and never builds in its own context. It delegates each feature to a feature-builder agent that starts fresh. Every round writes to a results file recording kept or undone, what was tried, and which checks still fail. End with a report. *When:* Multi-feature builds where context carry-over causes drift or contamination.
- **Karpathy-style keep-or-undo loop with program.md** — Give the agent one editable file. Put the scoring file out of its reach. Write the rules in program.md in plain English, with a fixed-rules section and a how-to-work section. Keep a change if the score improves, and undo it otherwise. *When:* Any task with a numeric or pass/fail score that the agent can run repeatedly.
- **Outer auto loop that rewrites instructions from failures** — After each feature, read the results file and group failures that recur across rounds. For each habit, record the rounds that show it. Rewrite only the how-to-work section of program.md for the next feature. The checks stay read-only to this loop. Run one feature at a time, with a review after each. *When:* When the inner loop repeats the same mistake across features and the fix should carry forward.
- **Wire-up and sweep instructions** — Add two rules to the instructions. Connect each feature to the live app in the same round its checks pass. Find every existing place that already does the job and make each one follow the new rule. *When:* When features pass unit-style checks but stay unreachable from the app, or old code paths keep using the previous behaviour.
