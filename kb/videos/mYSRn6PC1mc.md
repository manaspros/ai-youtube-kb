> Workshop on building a deep-research agent (MCP server plus Claude Code skills) that feeds a separate LinkedIn writer workflow with evaluator-optimizer review and a calibrated LLM-judge eval loop.

## Summary
Three Towards AI instructors walk through a two-part system: a research agent that gathers sources and writes research.md, and a deterministic writing workflow that turns that file plus a human-written guideline into a LinkedIn post. The research agent is a FastMCP server exposing tools (deep research via Gemini grounding, YouTube analysis via Gemini's direct video understanding, and a compile step), prompts and resources, driven from Claude Code. The speakers argue for the simplest architecture that works: a fixed-step workflow where possible, an agent only where branching is needed, and one agent with tools-as-specialists rather than many agents for tightly coupled work. The writer uses three static style profiles, a few few-shot examples, and an evaluator-optimizer loop where the reviewer runs in a fresh context window and returns Pydantic-structured feedback, with a fixed number of iterations instead of a score threshold. The eval section builds a 20-post dataset, generates synthetic inputs (never outputs), labels pass/fail with critiques, and calibrates an LLM judge with F1 on dev and test splits. The live demo shows the judge overfitting in practice: it passed every online trace despite labels saying otherwise. The talk is a long hands-on workshop, mostly practical and candid about what did not work.

## Key ideas
- **Pick the simplest architecture: prompt, then context or retrieval, then a fixed-step workflow, and only then an agent. Agents are for steps that must branch or react to the environment.** — The speakers use an autonomy slider. A support-ticket flow with the same six steps in fixed order is a workflow, because an agent would add overhead and uncertainty. Agents fit when the system must choose tools or branch dynamically. ([9:46](https://youtu.be/mYSRn6PC1mc?t=586))
- **For tightly coupled sequential tasks, use one decision-making agent with tools as specialists instead of splitting the work across several agents.** — Splitting a marketing-content task across agents caused hand-off errors and lost context. Tools can carry their own system prompt, validation logic, or LLM calls, so the global context stays in one agent. ([14:41](https://youtu.be/mYSRn6PC1mc?t=881))
- **Context rot starts well before the window limit, around 200k tokens, so the context budget has to be managed actively.** — The speaker ties this to long-context training that teaches needle retrieval more than whole-context reasoning. Remedies are summarizing, retrieving selectively, compaction, and delegating to tools or sub-agents that have their own context. ([17:32](https://youtu.be/mYSRn6PC1mc?t=1052))
- **Split exploratory research from constrained writing, and let the two agents communicate only through files.** — The research agent writes research.md and the writer reads it. They run sequentially from a plain script with no orchestration framework, and sit in one project so a coding agent can maintain both. ([26:30](https://youtu.be/mYSRn6PC1mc?t=1590))
- **A human-written guideline with less freedom gives better results. The guideline states the topic, angle, key points, and links.** — The speakers found that the more the goal was defined, the better the output. Links are scraped, YouTube is analysed directly, and GitHub is ingested, and then the agent fills gaps with its own searches. ([28:31](https://youtu.be/mYSRn6PC1mc?t=1711))
- **Run the reviewer in a separate context window from the writer so it does not favour its own draft. Feed the reviewer the guideline, the research, and the style profiles, and have it return structured objects.** — Each review is a Pydantic object with location and comment fields, and each field description explains what goes there. The editor applies the reviews with the same context the writer had. Feedback is prioritised as guideline first, then research, then profile. ([1:21:14](https://youtu.be/mYSRn6PC1mc?t=4874))
- **For subjective creative output, loop a fixed number of times instead of stopping on a score threshold, and keep every version so a human can pick.** — Scores on creative work are noisy and the threshold is hard to set. The speakers ran 3 to 4 review-edit rounds and kept v0 through v4 on disk. ([1:23:35](https://youtu.be/mYSRn6PC1mc?t=5015))
- **Build the eval dataset by having an LLM generate inputs only, then run your real system for outputs and label them pass/fail with a short critique, stopping at the first failure.** — Generating outputs with an LLM would test the wrong thing. The speaker labelled 20 posts this way and noted that 100 would be a better size for a real eval. ([1:40:22](https://youtu.be/mYSRn6PC1mc?t=6022))
- **Calibrate an LLM judge against labels with a dev/test split and F1. A perfect dev score with a low test score means the judge is overfitted.** — Tune the judge prompt and few-shot examples on dev until F1 converges, then run the test split once as a final check. The speaker used only about 5 samples per split, so the perfect scores are not meaningful. ([1:43:27](https://youtu.be/mYSRn6PC1mc?t=6207))
- **A judge that looks good offline can fail on live traces. The speaker's online simulation had the judge pass every trace, so the eval set needs to grow.** — The fix proposed is to add failing live cases to the dev split and repeat calibration. The speaker is candid that this part did not yet work. ([1:53:56](https://youtu.be/mYSRn6PC1mc?t=6836))

## Techniques
- **Autonomy-ladder architecture choice** — Ask in order: does the model already know enough (prompt, few-shot)? Can context fit in the prompt (use caching)? Does it need retrieval? Are the steps fixed (workflow)? Only then consider an agent. *When:* Before designing any LLM feature, to avoid building an agent where a workflow is enough.
- **Tools as specialists inside one agent** — Keep one planner agent with the global context. Wrap specialised work such as format validation or channel-specific writing as tools, each with its own prompt or LLM call. *When:* Tightly coupled tasks where splitting into separate agents would cause hand-off errors.
- **Delegation to keep context lean** — Send heavy sub-tasks to tools or sub-agents that run in their own context window, and return only summaries to the main agent. *When:* When the main context grows past roughly 200k tokens, or when there are more than about 20 tools.
- **Files as the inter-agent contract** — One agent writes a markdown artifact such as research.md, the next reads it. Run the steps from a plain script in the same repo. *When:* Sequential pipelines where the handoff can be inspected, and when no orchestration framework is needed.
- **Guideline plus static style profiles** — Keep a per-piece human brief (topic, angle, key points, constraints) as input. Keep static profiles for structure, terminology and banned words, and character. Let the brief override the profiles when needed. *When:* Generating many pieces of content with a consistent voice.
- **Start with many few-shot examples, then trim** — Begin with a large set of varied examples, then remove them one at a time until quality drops. Put back the last one that mattered. *When:* Few-shot prompts that are always sent, where cost and latency grow with prompt size.
- **Evaluator-optimizer with fresh context and typed feedback** — Writer produces a draft. A reviewer in a new context returns Pydantic objects with location and comment, with field descriptions. The editor applies them and loops a fixed number of times. Prioritise feedback sources. *When:* Content that must follow a spec and avoid hallucination, where self-review is biased.
- **Synthetic eval inputs, real outputs, binary labels with critiques** — Generate the input conditions with an LLM. Run the real system to produce outputs. Label each pass/fail with 2-3 sentences of critique and stop at the first failure. *When:* Building an eval dataset for a generative workflow without ground truth.
- **Judge calibration with dev/test F1** — Use the judge's few-shot examples from the train split. Tune on dev until F1 converges. Check the test split once. Treat a perfect dev score as a warning sign. *When:* Before trusting any LLM-as-judge in regression tests or production monitoring.
- **MCP server exposes tools, prompts and resources; skills wrap prompts for progressive disclosure** — Put actions in MCP tools, instructions in MCP prompts, and static data such as model names and flags in resources. Register the server in a project .mcp.json that runs it via uv. Convert repeated prompts into skills, which load only the front matter until invoked. *When:* Packaging agent capabilities for a coding agent such as Claude Code, and sharing logic across a team without ad-hoc installs.
- **Trace-based debugging with threads and traces** — Log every LLM and tool call with inputs, outputs, latency, tokens and cost in Opik. Group runs into threads and inspect traces to find where a run went wrong. *When:* Multi-step agent or workflow runs that are too hard to debug from terminal logs.

## Hot takes
- Most agents clients want are simple workflows, so start with a fixed-step workflow and add agency only where branching is needed.
- Never ask an LLM to generate the outputs of your eval set. Generate the inputs and run the real system.
- Use a reviewer in a separate context window to avoid self-preference bias, and loop a fixed number of times rather than chase a noisy score threshold for creative work.
- Few-shot examples should be cut to the smallest set that works, because they are sent on every call; fine-tuning is the only real way to shrink that load.
