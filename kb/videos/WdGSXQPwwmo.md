> Better Stack walks through self-hosting Multica on a VPS to turn Claude Code and OpenCode into assignable, scheduled agents, then judges it technical to set up and less suited to dialogue-style work than managed alternatives.

## Summary
The presenter installs Multica, an open-source tool that wraps local coding-agent CLIs (Claude Code, OpenCode, Codex CLI, Hermes) as assignable agents with system prompts, skills, issues, and schedules. He skips the intended local-daemon-plus-cloud-UI setup and self-hosts the three-container stack (Go backend, Next.js frontend, Postgres) on a Hetzner VPS via Docker. He documents two setup pitfalls: email verification and connecting a runtime through an API token and a daemon. He then demos an issue-driven workflow (agent starts on assignment and parks work in In Review), a daily scheduled "autopilot" that digests three RSS newsletters, and direct chat. His verdict is mixed: he likes the scheduling and self-hosting, finds the Kanban model poor for his one-or-two-project dialogue style, and warns that the setup is technical and that exposing it to the internet is risky, recommending Tailscale. The video is a single-product walkthrough with no benchmarks or pricing, and the "10x better" title is not substantiated.

## Key ideas
- **Multica wraps existing terminal coding agents (Claude Code, OpenCode, Codex CLI, Hermes) as named agents with their own system prompts, skills, task assignment, status updates, alerts, and recurring schedules.** — The presenter frames it as an open-source take on Claude Routines and Managed Agents. Its intended setup is a local daemon connected to the Multica Cloud UI; he deliberately self-hosts instead. ([0:00](https://youtu.be/WdGSXQPwwmo?t=0))
- **Self-hosting is a three-container Docker stack: a Go backend, a Next.js/TypeScript frontend, and Postgres for session data.** — He installs it on a fresh Hetzner VPS with one install command, so Docker is the only prerequisite named. ([0:56](https://youtu.be/WdGSXQPwwmo?t=56))
- **Email-code login is the main self-host friction point; he works around it by avoiding the Resend email path.** — The presenter says the resend-code step gave him the most trouble and recommends configuring the server env rather than relying on email. The exact mechanism is garbled in the captions. ([0:56](https://youtu.be/WdGSXQPwwmo?t=56))
- **Runtimes are per machine. A daemon on each box checks for installed harness binaries, polls Multica for tasks, and spawns agents in git worktrees. One UI can aggregate several VPSs, each connected with its own API token.** — Connecting needs an API token from Settings, then a login step, then a daemon restart. Without an installed CLI, the runtime shows an error. ([2:11](https://youtu.be/WdGSXQPwwmo?t=131))
- **Assigning an issue to a bot starts work immediately, so the issue text must be finished first.** — Agents move finished work to In Review rather than Done, and they will not move a card back to In Progress on their own. The human closes the loop. ([4:30](https://youtu.be/WdGSXQPwwmo?t=270))
- **Autopilot is the open-source counterpart of Claude Routines: a prompt, an agent, and a frequency. It has time-based triggers only, with no API or GitHub event triggers.** — His example fetches the latest issues of three newsletters via RSS and picks the best 10 articles for a YouTube video, daily at 9 a.m. London time. He tests it with Run Now. ([5:56](https://youtu.be/WdGSXQPwwmo?t=356))
- **His critique: the Kanban task-board model does not suit how he works, which is one or two projects in an ongoing dialogue where he watches tools run and debugs with the agent.** — He values the scheduling and self-hosting, and says Multica is cheaper than Claude Managed Agents or Routines when using other models. Managed services win on connectors (Slack, Telegram, Discord) and on not having to run the infrastructure. ([8:29](https://youtu.be/WdGSXQPwwmo?t=509))
- **Self-hosting trades managed-service convenience for security responsibility. He recommends reaching the server over Tailscale rather than exposing it publicly, and keeping Multica up to date.** — He also notes the UI can run fully locally with no internet exposure. ([9:28](https://youtu.be/WdGSXQPwwmo?t=568))

## Techniques
- **Self-host Multica with Docker on a VPS** — Install Docker on the VPS, run Multica's Docker install command (not shown in the video), then confirm three containers are running: backend, frontend, and Postgres. Run `multica setup self-host` afterwards. *When:* You want an always-on, self-controlled agent host that you can later reach from several machines.
- **Log in without the emailed code** — In the server directory's .env file, set the app environment to development and leave the Resend API key empty. Restart the containers from the same directory so the new env is loaded. The presenter says this lets him log in with the code shown in the app. The exact mechanism is unclear from the captions. *When:* Your self-hosted instance cannot send email, and you are the only user.
- **Connect a machine as an agent runtime** — 1) Install the CLI harness you want on the box (he uses Claude Code and OpenCode). 2) In the Multica UI: Settings, then API tokens, then create a token. 3) Run `multica login --token <token>`. 4) Stop any running daemon, then start `multica daemon`. 5) Check `multica daemon status` and the Runtimes page. *When:* Each machine that should execute agent tasks. Repeat per VPS with its own token to aggregate machines into one UI.
- **Define an agent** — Create an agent with a system prompt, optional skills (CLI-installed skills are inherited, and skills can also be added in the UI), an environment, and custom CLI arguments such as a model flag. With no model flag, it uses the default model of the installed CLI. *When:* Making a specialised agent, such as a personal-data assistant with a fixed prompt, or pinning a model per agent.
- **Issue-driven task flow** — Write the full issue prompt first and set priority or due date if needed. Assign the agent last, because assignment starts it. Watch progress on the issue, read the execution history for tool calls, reply in comments, and move the issue to Done yourself after the agent parks it in In Review. *When:* Discrete, auditable tasks where you want a review gate before work counts as done.
- **Scheduled autopilot (recurring agent run)** — Open Autopilot, choose Start from scratch, select an agent, write the prompt, and set the recurrence (daily at 9 a.m. in his example). Use Run now to test. Results land as new issues. *When:* Recurring research or digest jobs, such as the RSS-to-YouTube-ideas example. Note there is no API or webhook trigger.

## Hot takes
- The 'makes Claude Code 10x better' title is not substantiated. The video shows a task-tracker wrapper around existing CLIs and no measured productivity gain.
- The presenter says Kanban and task-board workflows (Multica, Paperclip, Vibe Kanban) do not fit his preferred one-or-two-projects dialogue style, so his praise is conditional on the scheduling and self-hosting features.
- Self-hosting an agent host on the public internet is risky. The better default is a private network such as Tailscale, or a fully local UI.
- Managed Claude Routines and Managed Agents are easier and safer for most people because connectors (Slack, Telegram, Discord) and infrastructure are handled for you. Multica is worth it mainly for cost with non-Anthropic models and for self-hosting.
