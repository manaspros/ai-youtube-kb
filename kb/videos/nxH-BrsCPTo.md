> Better Stack walkthrough of Varlock, an open-source tool that replaces plaintext .env files with a typed, committable schema whose secrets resolve at runtime from 1Password and similar vaults.

## Summary
The host introduces Varlock (the transcript says "Varlot"), an open-source tool that keeps environment variable definitions in a typed schema file (.mschema) that can be committed publicly, while the actual values are resolved at runtime from local config or password managers such as 1Password, Bitwarden, AWS and GCP. The demo starts with a root decorator that flips the default from sensitive to non-sensitive, then adds typed items (string, number, port) and a required item, and uses `varlock load` to validate the schema. It then runs an app through `varlock run` to inject the variables into the process, which the host says works for any language. The 1Password section covers installing the plugin, creating a service account token in a dedicated vault, and pulling a field into the schema, with fingerprint unlock suggested for local development. The closing section lists limitations the host hit: no offline use, startup latency on remote fetches, fewer providers, and a name-collision bug where a shell variable silently overrode the vault value. The video is a short tutorial with no benchmarks and no sponsor segment shown.

## Key ideas
- **Replace the .env file with a committable schema that declares every variable, its type and whether it is sensitive, while the values stay out of the repo.** — The host frames two problems: onboarding onto a repo that needs an untracked .env from a teammate, and AI agents fetching secrets they should not see. The schema is the source of truth and is meant to be committed to a public repo. ([0:00](https://youtu.be/nxH-BrsCPTo?t=0))
- **Variables are sensitive by default; a root decorator flips the default so values are visible when validated.** — The host adds a root-level decorator that sets default sensitive to false for the whole file, then shows that validation output reveals values only after this change. ([1:22](https://youtu.be/nxH-BrsCPTo?t=82))
- **`varlock load` validates the schema and catches type and required-value errors before the app runs.** — Changing a string item's type to number produces a validation error because the value is not a number. Removing a value from a required item also fails validation. ([1:22](https://youtu.be/nxH-BrsCPTo?t=82))
- **`varlock run` injects resolved variables into a child process, so any language or framework picks them up with no code change.** — The demo runs the frontend dev script through varlock run and the app reads the port from the injected environment variable. The host says Python, Go and Rust work the same way, and a standalone CLI exists for non-npm setups. ([2:41](https://youtu.be/nxH-BrsCPTo?t=161))
- **Secrets can be resolved from a password manager through a plugin, with a dedicated vault for the service account.** — The host says to put the service account in a new vault rather than a personal one, because the vault scopes what the token can reach. The 1Password plugin adds its own root and item decorators, and the token is typed as a sensitive 1Password service token. ([3:56](https://youtu.be/nxH-BrsCPTo?t=236))
- **Local developers can avoid a stored 1Password token by unlocking with the desktop app or CLI and fingerprint auth.** — The host raises the question of whether the token itself is safe to commit or store, and answers that local developers with the desktop app or CLI can unlock with a fingerprint instead. ([5:18](https://youtu.be/nxH-BrsCPTo?t=318))
- **The host lists real limitations: offline use fails, remote fetches add startup latency, provider coverage is incomplete, and a shell variable with the same name overrides the vault value.** — The host says the name-collision bug caused a local shell variable to win over the 1Password value. He also notes there is no Dashlane support and that the tool is actively developed. ([6:45](https://youtu.be/nxH-BrsCPTo?t=405))

## Techniques
- **Commit a typed env schema instead of a .env file** — Create a .mschema file at the project root and declare each variable: a name and value (e.g. APP_ENV=testing), a type (string, number, port), and item decorators such as required. Add a root decorator (a line starting with #, placed above the variables) to set default sensitive to false where values are safe to show, and keep secrets sensitive. Run `varlock load` to validate. The exact decorator syntax is shown on screen and is not spelled out in the transcript; check the Varlock docs. Syntax highlighting exists only for VS Code. *When:* When a repo needs env config that is both shared and version-controlled, and you want validation errors on bad types or missing required values before the app starts.
- **Inject config at process start with varlock run** — Prefix the normal start command with `varlock run` (the host runs `varlock run` followed by the package.json script). Variables are resolved from the schema and sources and placed in the child process environment. The Varlock CLI can be used directly without npm. *When:* When the app reads config from environment variables and you want resolution to happen at runtime rather than from a file on disk, for any language.
- **Pull a secret from 1Password into the schema** — Create a vault for the project and a developer service account connected only to that vault. Generate a token and put it in the schema as a sensitive item typed 1PasswordServiceToken. Load the 1Password plugin via a root decorator and call its init decorator. Reference the secret with the plugin's 1Password function using vault, item and field (the demo uses vault 'test', item 'OpenAI', field 'credential'). Verify by changing a local value and re-running `varlock load`, which should now show the vault value. *When:* When API keys or other secrets should live in a password manager and the repo should hold only references, not values.
- **Unlock 1Password with biometrics for local development** — If the 1Password desktop app or CLI is installed, use the configuration the host shows to unlock with fingerprint, avoiding a service token on disk. The exact configuration is shown on screen and is not spelled out in the transcript. *When:* On a developer laptop, where a long-lived service account token would otherwise sit in a local file.

## Hot takes
- Varlock lets your .env be committed publicly and is 'safe for AI' (0:00). The video does not show a threat model for an agent that can read its own process environment after varlock run injects values, so this rests on the speaker's framing.
- Offline use is dismissed as a limitation nobody has (6:45): 'who's really coding without the internet?'
- The speaker says he plans to replace his local shell files with schema files and does not want agents to scrape his information (8:03).
- A name collision between a schema entry and a local shell variable silently prefers the shell value, which the host calls a bug (6:45).
