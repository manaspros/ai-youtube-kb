> Seven practical npm/pnpm/bun supply-chain hardening steps: release-age gating, disabling install scripts, blocking git deps, pre-install scanners, lockfile checks, frozen CI installs, and dependency habits.

## Summary
The Better Stack host argues that npm package compromises are frequent enough that developers should lock down their install setup, and walks through seven changes across npm, pnpm and bun. The first is release-age gating: refuse versions published more recently than a chosen window (days for npm, minutes for pnpm, seconds for bun). Next, turn off install scripts, since most supply-chain attacks run code right after install, and use explicit allow lists for the few packages that need them. He then recommends blocking git and other non-registry dependencies, with pnpm's no-downgrade trust policy as a bonus. The fourth tip is to alias package-manager commands through a pre-install scanner, naming MPQ and Socket Firewall. The fifth covers lockfile tampering in PRs, with pnpm described as less exposed and lockfile-lint suggested for other managers. The sixth is using clean/frozen installs in CI, and the last is behavioural: upgrade deliberately, use fewer dependencies, and pin exact versions while accepting that transitive ranges remain. The content is practical and mostly config-level, with several unverified claims about bun and tool behaviour.

## Key ideas
- **Release-age gating is the cheapest defence: most malicious versions are caught within hours, so refusing to install versions newer than a window avoids most of them.** — Each package manager sets this differently: npm in days via npmrc, pnpm in minutes via its config or workspace file (default of one day since pnpm 11, per the speaker), bun in seconds via bunfig.toml. The speaker's own window was one week. Caveat: npx and bunx do not respect the setting. ([0:00](https://youtu.be/Wq6yMdt11LM?t=0))
- **Install scripts are the main execution vector for supply-chain attacks, so disable them and allow-list the few packages that need them.** — pnpm and bun already block install scripts by default; npm needs it turned off. pnpm approve-builds writes an allow-builds setting to the workspace file, and bun uses trustedDependencies in package.json. Bun also has a curated default allow list. Speaker reports that an empty trustedDependencies array fails to override that default list, and that adding one entry works around it. ([2:06](https://youtu.be/Wq6yMdt11LM?t=126))
- **Git and other non-registry dependencies bypass registry checks and can re-enable lifecycle scripts, so block or restrict them.** — npm allow-git can be set to none (block all) or root (only those declared in the root package.json). pnpm has a block-exotic-subdeps option. Bun has no equivalent yet, per the speaker. The git-dependency trick was reportedly used in the recent TanStack compromise. ([3:30](https://youtu.be/Wq6yMdt11LM?t=210))
- **pnpm trust policy set to no-downgrade fails installs when a package's trust level drops between releases.** — For example, a package previously published by a trusted publisher that now has only provenance or no trust evidence will fail to install. This is aimed at publishing-process bypass attacks. ([4:44](https://youtu.be/Wq6yMdt11LM?t=284))
- **Pre-install scanners can screen packages before they reach the machine; the speaker favours Socket Firewall.** — MPQ checks Snyk's vulnerability database, flags packages under 22 days old, detects typosquats, verifies signatures and provenance, warns on install scripts, and reports metadata such as downloads, README, license, repo and maintainer domain. Socket Firewall blocks human-confirmed malicious packages and warns on AI-detected ones, and covers uv, pip and cargo as well as JavaScript. Both are aliased over the normal package-manager commands. ([4:44](https://youtu.be/Wq6yMdt11LM?t=284))
- **Lockfile edits in PRs can silently redirect downloads, and most teams do not review lockfiles.** — An attacker can change a resolved URL and matching integrity hash to point at their own server. The speaker says pnpm is not exposed because it does not keep tarball sources in the lockfile and will not install packages present only in the lockfile. For other managers he suggests lockfile-lint as a dev dependency, which checks that resolved hosts are trusted, URLs match package names, and integrity hashes are valid. ([5:58](https://youtu.be/Wq6yMdt11LM?t=358))
- **Use clean installs in CI and production so the lockfile is authoritative, and commit the lockfile.** — npm ci installs exactly the lockfile and errors if package.json disagrees. Bun and pnpm use a frozen-lockfile flag or a CI alias; pnpm enables this automatically when it detects CI. ([7:13](https://youtu.be/Wq6yMdt11LM?t=433))
- **Behavioural habits matter as much as config: upgrade deliberately, depend less, and understand what pinning does and does not cover.** — Avoid blanket npm update runs. Fewer dependencies means less attack surface, and agentic coding makes writing small helpers easier than adding libraries such as lodash or axios. Exact pins only lock top-level dependencies; transitive dependencies can still float within their ranges, which is why release-age gating still matters. ([8:26](https://youtu.be/Wq6yMdt11LM?t=506))

## Techniques
- **Release-age gating per package manager** — Set the minimum release age in npmrc (npm, in days), in the pnpm global config.yaml or per-project workspace file (pnpm, in minutes; defaults to one day since pnpm 11), or in bunfig.toml (bun, in seconds). Set globally or per project. After this, installs resolve to the newest version older than the window, e.g. TanStack's React Start package installs the newest version that is at least one week old. Bypass with an explicit version on the command line when a fix must be installed. Watch for LLMs that bypass the gate by requesting latest. *When:* On every machine and repo that installs third-party packages, and especially for agent-driven installs. Do not rely on it for npx/bunx, which ignore it.
- **Disable install scripts and allow-list exceptions** — npm: turn off install scripts in config (speaker did not name the key) and use an allow-scripts list in package.json (he mentioned the lavamoat allow-scripts tool). pnpm: run pnpm approve-builds when a package such as esbuild reports pending build scripts; this writes the workspace allow-builds config. Also accepts an allow-builds flag on install. bun: install scripts are off by default; add trustedDependencies to package.json; list untrusted packages with bun pm untrusted and trust one with bun pm trust. Disable them globally in bunfig with install scripts set to false. Workaround for the empty-array bug: keep one entry in trustedDependencies so the default list is ignored. *When:* For every project. Only enable scripts for packages with a clear need, such as native compilation or binary downloads.
- **Block git and exotic dependencies** — npm: set allow-git to none to block all git URL dependencies, or to root to allow only those declared in the root package.json. pnpm: enable block-exotic-subdeps so only direct dependencies can use git or tarball URLs. Also set pnpm trustPolicy to no-downgrade so installs fail when a package's trust level drops from its previous release. *When:* Any project where dependencies could be pulled from git repos or URLs, and especially where a transitive dependency could ship its own npmrc.
- **Scan packages before install via alias** — Alias npm, pnpm, bun (and uv, pip, cargo for Socket) to MPQ or Socket Firewall so every install passes through the scanner. Speaker's choice is Socket Firewall. After installing the tool, clear the package-manager cache so already-cached packages are re-checked. Review MPQ's interactive report before confirming installs. *When:* On developer machines and any environment where agents run installs. Pair with release-age gating, since scanners catch known-bad packages while gating covers the brief window before detection.
- **Lockfile hygiene with lockfile-lint** — Commit the lockfile (do not gitignore it). Add lockfile-lint as a dev dependency and run it to check that every resolved URL points to a trusted host such as the npm registry, that each URL matches the package name, and that integrity hashes are valid. The install fails if tampering is suspected. Review lockfile changes in PRs. pnpm is described as not vulnerable to resolved-URL swaps. *When:* In any repo that accepts external PRs, and for non-pnpm managers.
- **Frozen installs in CI and production** — Use npm ci instead of npm install. For bun and pnpm, use the frozen-lockfile flag or the CI alias. pnpm enables this automatically when CI is detected. The install fails if package.json and the lockfile disagree. *When:* Every CI job, container build, and production install.
- **Dependency hygiene habits** — Review each dependency upgrade rather than running blanket update commands. Replace trivial dependencies such as lodash helpers with small local snippets, and use the built-in fetch instead of axios. Pin exact versions for top-level dependencies, while accepting that transitive ranges remain and that release-age gating covers them. *When:* Ongoing, especially when an agent is adding dependencies, since agents can usually write small helpers directly.

## Hot takes
- LLMs have been seen bypassing release-age gating by installing the latest version directly, so agent-driven installs need enforcement beyond a CLI flag.
- npx and bunx ignore the release-age setting, and an open Bun PR is said to address it.
- pnpm is described as immune to lockfile resolved-URL swapping, while bun is said to be unverified.
- Agentic coding makes writing small helper functions cheaper than adding dependencies, which the speaker says makes dependency minimisation more relevant.
- The three package managers chose three different units and defaults for the same release-age setting, which the speaker presents as typical of the ecosystem.
