> Oracle workshop on memory-aware agent harnesses for AML: treat the harness (loop, memory tiers, skill retrieval, context budget) as the thing to engineer, not the frontier model.

## Summary
Nacho Martinez (Oracle) runs a hands-on workshop on building agent harnesses around a fraud and anti-money-laundering agent that reads bank transactions and drafts suspicious activity reports. He argues the model is a fixed reasoning core, while the harness (agent loop, memory, tool and skill retrieval, context assembly) is where teams have control and where results actually change. He covers the agent stack, the files-versus-databases question for shared state, and a short-term versus long-term memory split (episodic, procedural, semantic). His main claim is that large context windows degrade performance, so tools, skills and memory should be retrieved on demand through vector search and hybrid retrieval, with compaction or summarization for old context. He also explains instruction hierarchy (system prompt, then user, with skills lowest), prompt-prefix caching economics, and why a pre-vetted SQL/tool surface beats free-form SQL generation. He closes by advising people to start from a minimal harness and strip it down rather than adopt a large one. The talk is practitioner-level and includes some vendor framing about Oracle's stack.

## Key ideas
- **The harness, not the model, is the lever.** — He says the frontier model is largely fixed, while the harness controls tool use, memory and perception. He claims the same model can do better or worse on a task depending only on harness configuration. ([11:15](https://youtu.be/KtBivPzmOM8?t=675))
- **Concurrent writers to one file need a database-style solution.** — Git worktrees are the workaround agents use for multiple writers to one file. He says file writes lack transactional guarantees, so ACID databases already solve this problem and should be reconsidered for shared agent state. Files stay good for unstructured data. ([14:35](https://youtu.be/KtBivPzmOM8?t=875))
- **Memory split into short-term and long-term tiers, with long-term split into episodic, procedural and semantic.** — The context window is short-term memory and is lost when a conversation ends. Long-term memory holds episodes and tool logs (episodic), skills and workflows (procedural), and user preferences and facts (semantic). He suggests starting with only two structures. ([16:49](https://youtu.be/KtBivPzmOM8?t=1009))
- **More context makes the model worse even inside the advertised limit.** — He cites studies showing a problem solved from near-zero tokens beats the same problem with 256k tokens already loaded. He says the context budget should stay small, and treats the 1M figure as a KV-cache-driven ceiling, not a target. ([18:28](https://youtu.be/KtBivPzmOM8?t=1108))
- **Retrieve tools and skills on demand instead of loading them all.** — Skills run roughly 3,000 to 5,000 tokens each, so a library of around a hundred would exhaust the window. He embeds tool and skill descriptions in a vector store and pulls the top-k (default 3) for each loop iteration. He says there is no reranker by default, but one can be added. ([20:45](https://youtu.be/KtBivPzmOM8?t=1245))
- **Promote memory by writing raw text first, then add a recall step in the loop.** — Keep memories as plain text in long-term storage, vectorize later, and add a recall step between observe and reason. Recalled items enter the context only if their vector distance falls under a threshold. ([41:00](https://youtu.be/KtBivPzmOM8?t=2460))
- **Hybrid retrieval beats either keyword or semantic search alone.** — He combines embedding search with keyword search and fuses the rankings with Reciprocal Rank Fusion (RRF). He admits this costs more compute and says it improves retrieval quality. ([46:03](https://youtu.be/KtBivPzmOM8?t=2763))
- **Start from a minimal harness and strip it down.** — He says building from scratch lets you cut around 90% of what a general harness includes. He compares a minimal harness with about 6k tokens in its first request against others near 30k to 40k, and says constrained unattended agents need automatic summarization and a hard step limit. ([37:36](https://youtu.be/KtBivPzmOM8?t=2256))

## Techniques
- **Two-tier memory with promote-to-long-term** — Keep short-term memory as the context window. When something is worth keeping, write it as raw text to a long-term store, then vectorize it. Recall it through an explicit recall step between observe and reason, and inject it only when vector distance is under a threshold. *When:* When you are starting an agent with memory and want to avoid premature abstraction; begin with two structures and add complexity only when retrieval fails.
- **Vector-indexed skill and tool box with top-k retrieval** — Embed the descriptions of every tool and skill. On each loop iteration, run a similarity search and load only the top-k (default 3) into context. Optionally add a reranker to narrow to the single most relevant item. *When:* When the catalogue of tools or skills is too large to load into the context window.
- **Hybrid keyword plus embedding retrieval with RRF** — Run BM25-style keyword search and embedding search over the same corpus, then fuse the two ranked lists with Reciprocal Rank Fusion. *When:* When pure semantic search misses exact terms or pure keyword search misses meaning, and extra compute per query is acceptable.
- **Compaction or summarization of old context** — Summarize the conversation into a short digest that replaces it, or chunk old turns into a database or file under an ID and retrieve them later by ID plus offset, the way you would read a file. *When:* For long-running or unattended agents where the context would otherwise grow past the point where quality holds.
- **Skill distillation from past runs** — After a good run, write a SKILL.md capturing the approach and preferences, and add it to the skill box. It is then found by vector search the next time a similar task appears. *When:* When the same kind of task recurs (for example front-end work) and your style preferences should carry over.
- **Pre-vetted query tools instead of free-form SQL** — Expose a fixed set of tested SQL queries as tools through MCP or a similar interface, so the agent selects a query rather than writing new SQL that may fail on a particular engine. *When:* When an agent queries a database whose SQL dialect has subtle engine-specific behavior.
- **Bounded agent loop for unattended runs** — Cap the loop at a fixed number of iterations (eight in the workshop) and a per-iteration reasoning time (60 seconds), so a background agent cannot run up unbounded cost. *When:* For agents that run 24/7 without a human in the loop.
- **Stable request prefix for caching** — Keep tool definitions and skill text identical from one request to the next so the provider can serve the large shared prefix from cache, and keep the varying user input at the end. *When:* When each request repeats a large block of tools and system text and cost matters.

## Numbers
- Skill definitions run about 3,000 to 5,000 tokens each, so loading a hundred skills would exceed the context window. ([20:45](https://youtu.be/KtBivPzmOM8?t=1245))
- In some cases tools and skills take more than 50% of the context window. ([21:51](https://youtu.be/KtBivPzmOM8?t=1311))
- He says the advertised 256k or 1M windows still degrade badly, and that a problem solved from near-zero tokens does better than one with 256k already loaded. ([18:28](https://youtu.be/KtBivPzmOM8?t=1108))
- Tools and skills make up about 80% of each API request, which is cached on the provider side. ([35:22](https://youtu.be/KtBivPzmOM8?t=2122))
- He estimates the request would cost four to five times more without that caching. ([36:29](https://youtu.be/KtBivPzmOM8?t=2189))
- Tool outputs and retrieved docs take about 35,000 to 100,000 tokens per request in his description. ([37:01](https://youtu.be/KtBivPzmOM8?t=2221))
- The minimal Pi harness sends about 6,000 tokens in the first request, versus about 30,000 to 40,000 for other harnesses. ([37:36](https://youtu.be/KtBivPzmOM8?t=2256))
- Default top-k for tool and skill retrieval is 3. ([39:19](https://youtu.be/KtBivPzmOM8?t=2359))
- Workshop agent loop limits: maximum 8 iterations and 60 seconds of reasoning per iteration. ([20:09](https://youtu.be/KtBivPzmOM8?t=1209))
- Embeddings used for skill search are described as 384 to over 1,000 dimensions. ([45:28](https://youtu.be/KtBivPzmOM8?t=2728))

## Hot takes
- Files are good for unstructured data, but shared writes to files reinvent a database problem that was solved about 30 years ago.
- A bigger context window is not free: performance drops as context grows, so keep it small even when a large limit is available.
- Most teams should not build a full harness; they should build small, task-specific harnesses and start from scratch to strip out what they do not need.
- Skills sit at the lowest level of the instruction hierarchy, below system prompt and user messages, so they should be treated as a plug-in pool rather than always-on instructions.
