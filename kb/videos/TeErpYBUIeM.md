> Langfuse co-founder on moving agent improvement from manual trace review to an AI-driven loop, where agents propose fixes and dataset/evaluator updates while humans set goals and gate changes, with a changelog-writer case study.

## Summary
Marc Klingen (transcribed as "Mark") argues that agent quality now comes from a loop joining online traces with offline datasets, experiments and evaluators, and that teams are moving from doing this loop by hand to letting AI drive most of it. He describes a layered view of loops, where humans stay involved in setting goals, aligning datasets and evaluators, and reviewing proposed fixes so agents do not overfit. A live example is Langfuse's own changelog writer: merged PRs trigger a drafted doc change, a human GitHub PR review produces approvals and change requests, and those review decisions become eval signal. The agent found the draft factually correct but low in clarity and leaking internal jargon, then proposed new datasets and evaluators, and a v2 candidate was backtested against the v1 baseline before merging. He closes by arguing that agent workloads become read-heavy, so teams should own their trace data long term rather than sample or short-retain it. The talk gives no benchmark numbers and is mostly a conceptual pitch with a demo, with Langfuse as the speaker's product.

## Key ideas
- **Agent improvement needs one loop that joins online traces with offline datasets and evals** — Tracing production alone misses benchmarks, and offline benchmarks on stale data drift from real usage. Teams need both, plus a deploy-and-learn step after each change. ([1:33](https://youtu.be/TeErpYBUIeM?t=93))
- **Humans should stay on the goals and the boundary, and let AI automate the tedious layers** — The speaker's target is a middle ground: people set direction and approve dataset, evaluator and failure-definition changes, while agents do the trace review and fix proposals. Fully manual work is bottlenecked by human time, and fully automated loops burn tokens without useful output. ([6:42](https://youtu.be/TeErpYBUIeM?t=402))
- **Today the most common AI role is proposing fixes against a fixed evaluation boundary** — Teams keep the optimization target fixed and use AI mainly to propose implementation changes such as prompts or context. Recently some teams also let agents maintain datasets and evaluators, but humans still review those changes because they define the target for later agents. ([5:17](https://youtu.be/TeErpYBUIeM?t=317))
- **The target is not known up front, so goals get refined from error classes** — Starting from a vague goal such as automating customer support, the team learns what to measure from the failures they see. Each change exposes new error classes, which lets the team adjust the top-level goal. ([6:42](https://youtu.be/TeErpYBUIeM?t=402))
- **Review decisions on agent output are a training signal for the next loop** — In the changelog example, GitHub approvals and change requests on the agent's PRs feed the observability and eval store, so the agent can learn from what reviewers actually changed. ([10:59](https://youtu.be/TeErpYBUIeM?t=659))
- **A candidate change is checked by backtesting it against a baseline on the updated dataset** — The v2 candidate kept format compliance and accuracy, improved user-facing language, and showed a positive delta on the new dataset. The speaker says low-stakes internal repos can merge this way, since the agent only raises PRs. ([13:52](https://youtu.be/TeErpYBUIeM?t=832))
- **Errors found in production can be turned into new evaluators, such as one for internal jargon leaks** — The changelog review found that the draft leaked implementation terms such as ingestion pipeline and batched eval queue. The fix was a dataset and an evaluator for user-domain language, then a context or skill change to the writer agent. ([12:26](https://youtu.be/TeErpYBUIeM?t=746))
- **Agent loops shift the data system toward heavy reads, so keep trace data long-term** — Historically the stack was write-heavy for ingesting traces and evals. Agents read far more history, so the speaker argues teams should own the data layer, keep old traces, and avoid sampling or short retention. ([15:17](https://youtu.be/TeErpYBUIeM?t=917))

## Techniques
- **Online plus offline eval loop** — Trace production runs, collect user feedback and labels, keep datasets aligned with real usage, run experiments on them, deploy, and repeat. Treat the two halves as one system. *When:* Any production agent where benchmark data drifts away from real traffic.
- **Agent-proposed fix with human gate** — The agent reads failing traces and evals and proposes a change to a prompt, context or skill. A human reviews the diff and the failure definition before it merges, to limit overfitting. *When:* Agents whose improvements are driven by recurring, well-understood failure classes.
- **PR review decisions as eval signal** — Agent drafts go out as GitHub PRs. Approvals and requested changes are logged with the trace, then used to find where edits are high and to build new evaluators. *When:* Agent output that already passes through a code review or approval step.
- **Backtest candidate against baseline** — Run the old version (v1) and the new candidate (v2) on the same updated dataset. Check for regressions on existing metrics and for gains on the new target before merging. *When:* Before shipping a prompt or skill change, especially on low-stakes internal agents.
- **Agent-maintained evaluators from error patterns** — Reproduce a recurring production error on an offline dataset, then have the agent propose a new evaluator and dataset rows that test for it. Keep a human in the review loop. *When:* When the same kind of error keeps reappearing, such as jargon leaks or wrong-language replies.
- **Scheduled batch loop over labeled production data** — Run the improvement agent as a cron job on each day or week's batch of labeled traces and annotations, not on each event. *When:* When feedback arrives in batches and changes to the agent are not urgent.

## Hot takes
- Teams should stay in the loop on goals and on dataset and evaluator changes, because letting agents edit all of that just creates more slop.
- Trace history is valuable context for agents, so teams should own their data and not let it sit in a system that samples or expires it.
- Internal agents that only open PRs can merge candidate changes after a backtest, since nothing ships to production without a human step.
