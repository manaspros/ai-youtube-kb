> Review of Strata, a new engine that runs a 125B-parameter MoE model on a 12 GB GPU plus 64 GB RAM. The headline "6x" is inflated; the honest gain is about 2 to 2.5x, with a quality trade-off and a real RAM cost.

## Summary
The speaker tried running Qwen's 125B-parameter model locally with llama.cpp and got about 15 tokens/s with a multi-minute wait on long prompts. Strata, a one-person project launched September 24, claims about 93 tokens/s on a 12 GB GPU by splitting a mixture-of-experts model across VRAM and system RAM. The engine keeps a profile-seeded cache of hot experts on the GPU, computes the cold experts on the CPU in parallel per layer, and uses the model's built-in multi-token-prediction draft head to verify up to three guessed tokens per pass. The speaker says the output matches the non-speculative path token for token per the paper, with minor numeric differences on IQ builds. The "6x" title compares the 2-bit build to the slowest 3-bit llama.cpp baseline; like-for-like gains are about 2.1x (3-bit vs 3-bit) and 2.4x (3090 test), so expect roughly 2 to 2.5x. Quality costs are real: LiveCodeBench drops from 87.4 at full precision to 86.3 for IQ3 and 81.1 for Q2. Hardware matters: 64 GB of RAM is the practical threshold, DDR5 bandwidth bounds the CPU side, and enabling XMP/EXPO helps. The speaker concludes that the engine gap is being closed by llama.cpp pull requests, and the bigger shift is a model designed for offloading. He also argues that buying 64 GB of DDR5 just for this is hard to justify when a hosted API costs about $0.47 per million output tokens.

## Key ideas
- **Only a small slice of a MoE model is touched per token, which makes offloading viable. The Q2 file is 66 GB, but each token reads about 4 GB (about 10 of 512 experts per layer across 48 layers, plus always-on weights).** — Each layer routes to 10 experts plus one shared expert. The ~34 GB of expert data is split into 24,576 blocks, and the always-on parts are about 3.5 GB. The speaker frames this as 6B active parameters out of 125B. ([3:17](https://youtu.be/m0VHx73SAG0?t=197))
- **The core trick is a hot-expert cache on the GPU. The GPU holds about 4,500 experts (seeded from a usage profile) and runs them directly, while the CPU computes the rest from system RAM in parallel at each layer, then the results are summed.** — One 12 GB card holds about 4,500 of 24,576 experts. Hit rate starts near 50% from the profile and climbs to about 72% as the cache swaps in the experts this conversation keeps needing. A full pass is about 34 ms, with GPU ~15 ms and CPU ~13 ms. ([5:59](https://youtu.be/m0VHx73SAG0?t=359))
- **Multi-token prediction is the second big speedup. A small draft layer shipped with the model guesses up to three tokens, and one full verification pass keeps the agreeing ones and adds one of its own.** — On average each full pass yields 2.4 to 3.2 tokens. On the same machine without this, throughput was 47 to 57 tok/s versus 82 to 92 tok/s with it. The paper reports 1.6 to 1.8x from MTP alone, because the expert cache keeps the extra cost low. ([7:16](https://youtu.be/m0VHx73SAG0?t=436))
- **The 6x headline is inflated by comparing against the slowest baseline. Like-for-like comparisons are about 2.1x (3-bit vs 3-bit) and 2.4x on an RTX 3090 with a 3.5-bit build against a current llama.cpp.** — The speaker says the author compared the 2-bit Strata result (93 tok/s) against a 15 tok/s, 3-bit run from earlier that had been tuned to 29 tok/s. The speaker estimates the realistic gain at roughly 2 to 2.5x. ([9:39](https://youtu.be/m0VHx73SAG0?t=579))
- **Quality trade-off by quantization: the speaker's practical split is 3-bit for code and 2-bit for chat, and the 2-bit build gives up about 6 LiveCodeBench points.** — LiveCodeBench: full precision 87.4, IQ3 86.3, Q2 81.1. On SWE-Bench Pro, full Flash Next scores 62.5 against 61.7 for the 27B model, so the lead is under one point. ([12:03](https://youtu.be/m0VHx73SAG0?t=723))
- **System RAM bandwidth, not the GPU, is the real bottleneck for the CPU half. RAM is the decisive hardware variable, and XMP/EXPO is a free fix.** — The CPU pulls about 42 GB/s on DDR5. DDR4 has about half that, so each layer's CPU share takes roughly twice as long. The test machine ran DDR5 at 5200 MT/s with the memory profile off. The 2-bit build needs about 34 GB for experts plus ~10 GB for the OS, so 64 GB is the practical minimum. ([10:59](https://youtu.be/m0VHx73SAG0?t=659))
- **The economics are the strongest argument against buying RAM for this. If you already own 64 GB of DDR5, local is effectively free. If you would have to buy it, the hosted API is much cheaper.** — A 64 GB DDR5-6000 kit was listed at $913 in late September (all-time low $159). The hosted model costs $0.47 per million output tokens, so $913 buys about 1.9B tokens, or about 242 days of continuous local output at 93 tok/s. ([13:09](https://youtu.be/m0VHx73SAG0?t=789))
- **Mainline llama.cpp is catching up in public. Multi-token prediction merged on October 1, but expert offload is still an open draft PR, and MTP can hurt when the model spills into system RAM.** — With the whole model in VRAM, MTP moved decoding from 28 to 44 tok/s (about 1.55x). The draft expert-cache PR has been open since August 28 and was measured at 18.4 tok/s, rising to 24.2 on a different setup (transcript garbled). ([14:35](https://youtu.be/m0VHx73SAG0?t=875))

## Techniques
- **Hot-expert GPU cache with CPU cold path** — Route each token through the router first. Run experts that are resident in VRAM on the GPU and compute the rest on the CPU from RAM, in parallel within the same layer. Sum the two outputs before the next layer. Seed the resident set from a per-expert usage profile gathered across many conversations, then swap experts in over time based on the live conversation's usage (hit rate rose from about 50% to 72%). *When:* A MoE model is too large for VRAM but its per-token active experts are a small fraction of the total, and you have enough system RAM with good bandwidth.
- **Use multi-token prediction with a trained draft head** — Let the model's built-in small draft layer guess up to 3 tokens ahead. Run the full model once to verify all guesses in one pass, keep the prefix that matches, and append one token of its own. Expect about 2.4 to 3.2 tokens per expensive pass. Only enable it where it helps: the speaker reports slower results on llama.cpp when the model spills into RAM without an expert cache. *When:* Decoding is memory-bound and the model ships an MTP head. Benchmark with and without it on your actual memory split before keeping it on.
- **Keep big embedding tables on SSD and read only the rows needed** — The model's roughly 51B-parameter lookup table is indexed by the last three tokens, so the engine knows which 16 rows it needs before it needs them. It reads about 23 KB per token straight from disk, instead of keeping the 29 GB table in memory. *When:* A large lookup table is indexed by recent context and per-token reads are small and predictable.
- **Choose quantization by workload** — The speaker's practical split: use the 3-bit (IQ3) build for coding, where it scores 86.3 on LiveCodeBench, and the 2-bit (Q2) build for chat, where it is about 6 points lower but about 1.5x faster (93 vs 62 tok/s). The 2-bit build fits in 64 GB of RAM, and 32 GB systems can use the coder variant with half the experts removed. *When:* You are picking a quant for a local 125B-class model on a 12 GB GPU with 64 GB RAM, and you can tolerate some quality loss.
- **Tune the host before blaming the engine** — Enable XMP (Intel) or EXPO (AMD) in BIOS so DDR5 runs at its rated speed (the test machine ran 5200 MT/s with the profile off). The CPU side is limited by RAM bandwidth, so DDR4 roughly doubles the per-layer CPU time. *When:* Local MoE inference is slower than expected and the CPU is doing a large share of the expert work.
- **Benchmark speed claims fairly** — Compare the same quantization against the same quantization, use the tuned baseline rather than an old run, and enable the baseline's own speed features (e.g. the speculative path) before concluding. The speaker recommends measuring first-token latency on a long prompt (a 20,000-token example took 3m11s to first word in the baseline). *When:* Evaluating any local inference engine's claimed speedup, or writing one of your own.
- **Point a coding agent at a local Anthropic-compatible endpoint** — The engine serves the same API endpoints as OpenAI and Anthropic, so a tool such as Claude Code can be pointed at the local server. The transcript does not show the exact config keys, so check the Strata docs for the base URL and model name. *When:* You want a fully local, offline or private backend for an agent CLI, and can accept the throughput of about 60 to 90 tok/s on a 12 GB GPU.

## Hot takes
- The title's 6x is misleading: it compares the 2-bit Strata result to the slowest 3-bit baseline. Realistic gain is about 2 to 2.5x, which the speaker says is still significant.
- Buying 64 GB of DDR5 just to run this is hard to justify. A hosted API at $0.47 per million output tokens costs far less. If you already own the RAM, local is effectively free.
- The 2-bit build is roughly three times faster but noticeably dumber. Calling it dumb is harsh, but not completely wrong.
- The engine gap is closing through public llama.cpp pull requests. The more lasting shift is a model designed from the start for offloading (bytes moved per token), rather than the engine itself.
