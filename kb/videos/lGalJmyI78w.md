> Practitioner checklist for setting up Claude Code harnesses on large codebases: layered CLAUDE.md, hooks, path-scoped skills, plugins, LSP, MCP, sub-agents, and periodic pruning.

## Summary
The speaker argues that agents break down as codebases grow and that the harness around the model matters as much as the model. He contrasts embedding-based RAG retrieval, which he says has been replaced, with the filesystem navigation (find, grep, bash) that Claude Code uses. He then walks through five harness pieces: a short CLAUDE.md (about 300 lines, with per-subdirectory files in monorepos), hooks that enforce behavior (including a Stop hook that writes session learnings back to CLAUDE.md), skills that load on demand and can be path-scoped, plugins that bundle skills, hooks and MCP servers for a team, and LSP for IDE-like code navigation. Last, he covers custom MCP servers for internal systems, sub-agents with their own context (including overriding the built-in Explore agent with a project map), per-directory test suites, a codebase map for unconventional languages, and reviewing the setup every few months. The video is a checklist of practices with no benchmarks, and it is a secondhand summary of an Anthropic talk it does not link.

## Key ideas
- **Filesystem navigation beats embedding RAG for coding agents at scale** — Speaker says RAG (embed the codebase, retrieve similar chunks) fails on large repos and causes hallucinated modules, while Claude Code uses bash find/grep to narrow down and load only the needed snippets. He claims RAG has been 'completely replaced' without offering evidence. ([0:00](https://youtu.be/lGalJmyI78w?t=0))
- **The harness matters as much as the model** — Output quality depends on the harness combined with the model (he names Claude Code, Codex and Gemini CLI). A strong model in a weak harness does not help, so build a project-specific harness rather than relying on defaults or open-source harnesses such as superpowers. ([2:15](https://youtu.be/lGalJmyI78w?t=135))
- **Keep CLAUDE.md short and layer it per directory** — CLAUDE.md is loaded at session start and stays in context, so it should hold only cross-cutting conventions and knowledge, about 300 lines at most. In monorepos, each subdirectory gets its own CLAUDE.md so the agent loads focused instructions only where it is working. Revisit it as models change, since instructions written for older models waste tokens. ([3:18](https://youtu.be/lGalJmyI78w?t=198))
- **Hooks enforce behavior that CLAUDE.md instructions cannot guarantee** — Instructions in CLAUDE.md can get lost in attention, while hooks force an action. Session-start hooks load context, exit-code-2 hooks feed errors back to Claude to iterate, pre-tool-use hooks can block edits to protected files, and a Stop hook prompts Claude to reflect and update CLAUDE.md with the session's learnings. ([4:46](https://youtu.be/lGalJmyI78w?t=286))
- **Put project procedures in path-scoped skills, not CLAUDE.md** — Skills use progressive disclosure: they load only when needed. Project-specific procedures belong there, and a skill's description can name a path (e.g. a deployment directory) so it never loads elsewhere. He says skill-creator is now built into Claude Code. ([6:07](https://youtu.be/lGalJmyI78w?t=367))
- **Bundle team configuration as a plugin** — A plugin packages skills, hooks and MCP servers into one distributable unit so teammates get the same context on install. Plugins can be uploaded manually or synced from a GitHub repo, installed with the plugin command, and browsed in marketplaces; Claude Code ships with official plugins (frontend design, code review, code simplifier, Playwright). ([7:21](https://youtu.be/lGalJmyI78w?t=441))
- **Set up LSP before writing code, especially for unusual languages** — LSP gives the agent the same definition and import navigation a developer gets in an IDE. Without it, the agent pattern-matches on text and can land on the wrong symbol. Speaker says this matters most for unconventional languages and should be configured before the project starts. ([8:25](https://youtu.be/lGalJmyI78w?t=505))
- **Build internal MCP servers only after the app works** — MCP servers can expose internal docs, analytics, APIs or write actions that the agent cannot otherwise reach. Build and share them for the team, but configure them only once the base app runs, or the MCP implementation may fail. ([9:41](https://youtu.be/lGalJmyI78w?t=581))
- **Sub-agents protect the main context; override built-ins with project-specific ones** — Sub-agents have isolated context windows and return only their final output, so the main orchestrator stays lean and independent tasks can run in parallel. You can set their tools, model and instructions, and override built-in agents such as Explore with one that describes your project layout. ([10:57](https://youtu.be/lGalJmyI78w?t=657))

## Techniques
- **Layered CLAUDE.md** — Keep the root CLAUDE.md to cross-cutting conventions (about 300 lines or fewer). Add a CLAUDE.md in each monorepo subdirectory that follows the same rules, so it loads only when the agent works there. *When:* Large monorepos or codebases with several architectures, where one root file floods the context with irrelevant detail.
- **Stop-hook learning loop** — Configure a Stop hook (a shell script) that runs after each session and prompts Claude to reflect on what was done, then write the learnings into CLAUDE.md so the same mistakes are not repeated. Speaker does not show the config. *When:* When the same agent mistakes recur across sessions and you want the harness to capture lessons automatically.
- **Hooks for enforcement** — Use a SessionStart hook to load context (for example, which files to read). Use a PreToolUse hook to block edits to files Claude should not touch. Use a hook that exits with code 2 to send its error message back to Claude so it iterates. Hooks can also run lint and tests. Speaker shows no config keys, so use the names as given. *When:* When a rule must always be followed and CLAUDE.md wording is being ignored, or when the agent needs an automatic feedback loop.
- **Path-scoped skills** — Move project-specific procedures out of CLAUDE.md into skill files. Put the target directory path in the skill description so the skill activates only when work touches that path. Create skills with the built-in skill-creator, then restart the session to load them. *When:* When a procedure matters only for one part of the repo, such as deployment, and should not consume tokens elsewhere.
- **Team plugin distribution** — Bundle skills, hooks and MCP servers into a plugin. Distribute it by manual upload or by syncing a GitHub repo. Teammates install it with the plugin command, and extra marketplaces can be added with the add-marketplace command. Speaker gives no exact command syntax. *When:* When several engineers work on the same repo and need identical agent context.
- **LSP before code** — Configure a language server for every language the project uses before any code is written, so the agent navigates by symbol and definition rather than by text match. *When:* Projects in unconventional or less-common languages (he names C++ as an example for the codebase map), and any project where the agent resolves symbols wrongly.
- **Custom sub-agents with an overridden Explore agent** — Define sub-agents with their own tools, model and instructions. Create one named Explore whose instructions describe your directory layout; it overrides the built-in Explore agent. Have the main agent orchestrate and delegate to sub-agents, which can run in parallel. *When:* Large projects where generic exploration wastes tokens and parallel work speeds things up.
- **Per-subdirectory tests and codebase map** — Keep test suites separate per subdirectory so they can be scoped and avoid timeouts when everything runs together. Write a codebase map file, acting as a table of contents, that records where each file lives. Skip the map for React or Next.js, which agents already know well. *When:* Large repos, and unconventional languages where the model lacks prior knowledge of the layout.
- **Quarterly harness pruning with ignore files** — Review the whole setup every few months and remove CLAUDE.md lines, hooks or other pieces the newer model no longer needs. Use .gitignore and .agentignore to keep the agent and version control away from files they should not touch. *When:* Whenever the model changes or the setup has grown stale.
