> Philipp Schmid (Google DeepMind) rebuilds one GitHub PR-review agent three ways, moving from a hand-written Python loop to a hosted sandboxed harness driven by markdown files, and argues to delete orchestration code as models improve.

## Summary
The speaker builds the same GitHub PR-review agent three times and removes code each round. Version one is a hand-rolled Python loop that parses function calls, dispatches tools, and manages state, and it can only do what its tools allow. Version two uses an agent framework (Google ADK) that derives tool schemas from function signatures, which removes boilerplate but keeps the Python tools and hosting. Version three runs on Google's Antigravity harness through the Gemini Interactions API, with a hosted sandbox, a GitHub CLI, and a single API call per turn, and it is configured mostly with agents.md and skills.md files. The talk claims that adding capabilities then means adding files rather than code, and cites several teams (Cursor, Manus, LangChain, Vercel) that removed large amounts of orchestration code. The closing advice is to stop micromanaging execution paths, expose general tools, and own the instructions, workflows and evals. Most of the content is a Google product walkthrough with live demos that were single runs, and the case-study numbers are secondhand.

## Key ideas
- **Working definition and framing** — An LLM agent is tools run in a loop until the goal is met. The talk rebuilds one GitHub PR-review agent three ways and deletes code at each step. ([0:12](https://youtu.be/fjF8EKnxKCU?t=12))
- **Interactions API replaces turn-based history** — Instead of user/model turns, the API uses a typed step timeline (user input, reasoning, function call, function result), so tool output no longer has to be passed back through the user role. It also offers server-side state and background execution. ([1:18](https://youtu.be/fjF8EKnxKCU?t=78))
- **The hand-rolled loop is the baseline cost** — You write JSON schemas, parse whether the model returned a function call or text, match and dispatch tools, feed results back, and manage state. The resulting agent is limited to the tools you wrote. ([2:32](https://youtu.be/fjF8EKnxKCU?t=152))
- **Frameworks remove loop boilerplate, not the tools** — ADK handles the tool loop, retries and error handling, and builds schemas from function signatures. You still own the Python tool code and the environment where tools run. ([5:07](https://youtu.be/fjF8EKnxKCU?t=307))
- **Remote harness with a per-request sandbox** — The Gemini API agent reuses the Antigravity harness, but it is a general-purpose agent with its own system instruction and tools, so the same harness does not mean the same agent. An environment parameter gives a hosted isolated Linux sandbox with bash and file storage, populated from a GitHub repo, a GCS bucket, or inline files. ([7:43](https://youtu.be/fjF8EKnxKCU?t=463))
- **Credentials stay outside the sandbox** — A network proxy around the sandbox injects tokens into outbound requests, so the agent never sees the secret. Domains can be allowlisted, but an empty list currently means all domains are reachable. An Agents API stores a named agent (custom ID) that bundles a system instruction, base agent and environment. ([8:48](https://youtu.be/fjF8EKnxKCU?t=528))
- **Version three has no custom tools** — agents.md tells the agent that the GitHub CLI and bash are available. A bootstrap script installs gh on the first turn if it is missing. The agent explores the sandbox and uses its own knowledge of the CLI. It also answered an out-of-scope weather question by using the built-in Google Search tool. ([10:00](https://youtu.be/fjF8EKnxKCU?t=600))
- **What developers still own, and the orchestration-deletion trend** — Developers still own instructions (agents.md), capabilities (skills.md) and evals. Compaction and session state are handled server-side. The speaker cites Cursor replacing about 12k lines of TypeScript with about 200 lines of agent files, and Manus, LangChain and Vercel simplifying their harnesses. Adding a feature is now a markdown file, not code. ([13:54](https://youtu.be/fjF8EKnxKCU?t=834))
- **Files as memory and handoff** — Agents can write preferences and rules to files and reuse them in later sessions. In long sessions, the agent can write a handoff file so that a later session picks up the work. ([16:01](https://youtu.be/fjF8EKnxKCU?t=961))

## Techniques
- **Agents-as-files layout** — Keep the agent's role, rules and behavior in agents.md and its capabilities and CLI usage hints in skills.md. Put any CLIs the agent needs in the sandbox environment. Add a capability by adding a markdown file, not code. *When:* When every new capability currently requires new tool schemas and Python glue, and the model can already reason with generic bash and filesystem tools.
- **Bootstrap script for CLI dependencies** — On the first turn, a small script checks whether the required CLI (the demo uses gh, the GitHub CLI) is installed. If it is not, the script downloads and installs it, and the agent then uses the CLI normally. *When:* When the sandbox does not preinstall the tools the agent needs.
- **Credential injection through a network proxy** — Register a token per host: github.com for git operations and the API host for HTTP calls. The proxy adds the token to outbound requests, so the agent only knows that it can call the API. Set a domain allowlist to restrict outbound access; leaving it blank allows all domains, which is the default. *When:* When an agent runs code that should use secrets but must not read or leak them.
- **Single-call agent turn with server-side loop** — Send one request containing the user input, a reference to the sandbox environment, and the previous interaction ID to continue multi-turn sessions. Use streaming so that function calls and results show up during long runs. The API executes the tool loop server-side. The talk does not show exact parameter names. *When:* When replacing a hand-written tool-calling loop and you want the platform to handle loop control, state and compaction.
- **Named custom agent** — Create an agent with a custom ID that bundles the system instruction, base agent and environment. Call it by that ID in the same way you call a model. *When:* When you want a reusable configured agent shared across code paths or teams.
- **File-based memory and handoffs** — Tell the agent to record rules and preferences in a file, and to read that file in later sessions. For a long session that branches into other work, have the agent write a handoff file that a new session can pick up. *When:* For multi-session work, or when context needs to survive a context-window reset.
- **Build-to-delete audit** — At each harness change, list the orchestration code and ask whether the model can now do the step from instructions or generic tools. Delete the code and keep evals as the contract for behavior. *When:* When each model upgrade seems to require more harness code, which the speaker reads as a sign the harness is over-engineered.

## Hot takes
- Mostly a Google product pitch. It promotes Antigravity, the Interactions API and the Agents API, and closes with a QR code to AI Studio and a free tier that is not yet available.
- The architecture claim does not transfer cleanly. The speaker says the same harness does not mean the same agent, since the Gemini API agent has different instructions and tools than the IDE agent.
- The case-study numbers (Cursor 12k to 200 lines, Manus, LangChain, Vercel) are secondhand, unverified and given without benchmarks or error rates.
- Demos are single anecdotal runs. The talk gives no evals, failure rates or cost numbers, even though it tells developers to own evals.
- Dropping typed tools moves the security contract onto the model and the proxy. The default network policy is unrestricted, and the talk does not discuss prompt injection through repo or web content.
- The 'build to delete' principle is sound and the markdown-first pattern is a useful prompt for a harness audit. Quality is capped by the vendor framing rather than by the substance.
