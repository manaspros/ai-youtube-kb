> Better Stack walkthrough that shrinks a React/Node Docker image from 1.2 GB to 10 MB using Alpine bases, layer ordering, .dockerignore, single-RUN cleanup, multi-stage builds and the slim tool.

## Summary
The video takes one React app packaged with a Node base image (over 1 GB) and reduces it step by step. Switching to the -alpine variant of the base image cuts the built app to about 250 MB. Copying package.json and installing dependencies before copying source lets Docker reuse the dependency layer on code-only changes, and a .dockerignore keeps node_modules and secrets out of the build context. The presenter then explains that deleting files in a later RUN does not shrink the image because layers are immutable, so cleanup must happen in the same RUN as the work that creates the files. The biggest win is a multi-stage build: Node builds the static assets and only those assets are copied into a small Nginx image, giving 57 MB. Finally, Dive is recommended for inspecting layers and slim (slim build) is used to minify the image to 10 MB without changing the Dockerfile. The speaker notes that Alpine can cause native-module compatibility issues and that distroless images are a stricter option he does not demo.

## Key ideas
- **The base image is the largest lever: the full Node image is over 1 GB, while the -alpine variant is about 155 MB and brings the built app to about 250 MB.** — Speaker says appending -alpine is about seven characters and gives roughly 80% reduction. Alpine strips the image to essentials, but it uses different system libraries, so native modules may break. Use the full image for development if needed and a minimal one for production. ([0:00](https://youtu.be/t779DVjCKCs?t=0))
- **Distroless images are the most minimal option (no OS, no shell, no package manager), but they are harder to set up, so the video does not use them.** — Presented as Google's minimal-image line. Speaker chooses Alpine for the demo and links distroless in the description. ([1:17](https://youtu.be/t779DVjCKCs?t=77))
- **Order Dockerfile instructions from least to most frequently changing, so dependency installs stay cached when only source code changes.** — Copy package.json (or requirements.txt in Python) first, install dependencies, then copy the source. Speaker lists three cache invalidators: changes to a copied file, changes to a Dockerfile instruction, and changes to any earlier layer. ([2:31](https://youtu.be/t779DVjCKCs?t=151))
- **A .dockerignore keeps local artifacts and secrets out of the build context.** — node_modules is copied from the host even though the image reinstalls dependencies. The build output reports how much context is transferred, and excluding node_modules and secrets cuts that amount. The speaker does not show exact ignore entries. ([3:42](https://youtu.be/t779DVjCKCs?t=222))
- **Deleting files in a later layer does not shrink the image, because each layer is immutable and earlier layers keep the data.** — Separate RUN commands that remove cache, temp files, or node_modules leave the image unchanged in size. A secret copied and then deleted in a later layer can still be recovered from the image, which is a security concern as well as a size one. ([3:42](https://youtu.be/t779DVjCKCs?t=222))
- **Multi-stage builds are presented as the single most important Dockerfile tip. Build in a full Node stage and copy only the built output into a small runtime stage.** — The Node toolchain, node_modules and source are discarded with the builder stage. Static HTML from the React build is served by a final Nginx image. This only works when the runtime does not need node_modules, which is the case for a static build. ([4:54](https://youtu.be/t779DVjCKCs?t=294))
- **After the Dockerfile is optimized, use Dive to inspect layers and slim to minify the image further without touching the Dockerfile.** — Dive shows each layer, which helps find waste. Slim is described as able to minify containers up to 30x and also offers x-ray and linting to help author better Dockerfiles. Running slim build brings the image to 10 MB. ([6:15](https://youtu.be/t779DVjCKCs?t=375))

## Techniques
- **Switch to a minimal base image variant** — Use the -alpine tag of the language base image (the speaker does this with node, and says Python works the same way). Use the full image for development and a minimal one for production. For the most minimal option, distroless images contain no shell or package manager. *When:* When the base image is over a few hundred MB and most of its contents are unused. Check native-module compatibility first, since Alpine uses different system libraries.
- **Dependency-first layer ordering** — In the Dockerfile, copy only the dependency manifest (package.json, or requirements.txt for Python) and install dependencies before copying the rest of the source. Put stable layers at the top and frequently changing ones at the bottom. *When:* For any image where a code change currently rebuilds and reinstalls all dependencies. Docker reuses the cached dependency layer unless the manifest, the instruction, or an earlier layer changes.
- **.dockerignore to trim the build context** — Create a .dockerignore listing node_modules and secret files such as .env. Compare the build context size reported by docker build before and after. *When:* When developing locally with host-installed dependencies, or when the project directory holds secrets, build outputs or VCS data that the image does not need.
- **Do cleanup in the same RUN as the install or build** — Put cache cleaning, temp-file removal and deletion of build-only folders in the same RUN instruction that creates them, so they never land in a committed layer. *When:* When build-only artifacts or secrets are created during the image build. Removing them in a later RUN leaves them in earlier layers, so it does not reduce size or remove the secret from the image.
- **Multi-stage build: build in one stage, serve from a small stage** — Use a first FROM stage based on the full Node image to install and run the build. Add a second FROM stage based on Nginx, then copy only the built static files from the first stage into it. The stage that holds Node, npm, node_modules and source is discarded. The transcript does not show the exact copy syntax. *When:* When the build output is static files (for example a React build) or a compiled binary that runs without the toolchain. Not suitable if the runtime needs node_modules, as the speaker found when he deleted them.
- **Inspect layers and minify with Dive and slim** — Run Dive against the built image to browse each layer and find large or unneeded files. Then run slim build against the image; the speaker says this needs no changes to the image or Dockerfile. Slim also offers x-ray and linting commands for authoring Dockerfiles. *When:* After the Dockerfile is already structured well, to find remaining bloat or to shrink an image further without rewriting the build.

## Hot takes
- The 10 MB endpoint is a static React build served by Nginx. It does not show how a Node server or a backend service would shrink, so the headline number does not generalize to most agent or API containers.
- The 'up to 30x' figure for slim is the tool's own claim and is not measured in the video; only the one before/after result is shown.
- The title says 'BEST practices', but the content is one walkthrough on one app with no benchmarks across images or rebuild timings. The layer-cache speedup is described but not timed.
- Alpine is presented as a safe default for most images, but the speaker also warns it can break native modules, so it needs testing before adoption.
