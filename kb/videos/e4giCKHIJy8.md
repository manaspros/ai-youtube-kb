> A walkthrough of Google Antigravity as a coding agent, using Cursor's published harness principles: plan-first with commented revisions, on-demand context, TDD, Git as knowledge base, and skills-based debug mode.

## Summary
The host argues that Antigravity (Google's AI code editor, running Gemini 3 and free to use) became worth taking seriously once its agent harness was tuned, and applies principles from Cursor's published harness article to it. A harness is described as three parts: built-in instructions and rules, the tools the agent can call (file edit, search, terminal), and how the user prompts and follows up. The main workflow is plan-first: review a detailed generated plan, comment on lines to revise it, and re-plan rather than patch with follow-up prompts. Context should come from the agent's own grep and semantic search rather than manual file tagging, and a new conversation should start for each logical unit of work or when the agent gets confused. Rules live in .agent/rules as markdown and skills in .agent/skills as SKILL.md files, loaded on demand. The host also uses TDD with tests committed to Git before implementation, screenshots as UI input, Git commits and reusable workflows, watching agents and reviewing with an agent, parallel agents on separate branches, and a debug-mode skill. About a quarter of the runtime is a sponsored segment for an unrelated AI video tool. The evidence is one user's experience, with no benchmarks.

## Key ideas
- **A harness is three things: built-in instructions and rules, the tools the agent can call, and how the user prompts and follows up. It should be tuned to the model, because models differ (for example, shell-trained models prefer grep).** — Different models respond differently to the same prompt. Some do better with XML prompts and others with markdown, so the harness should match the model in use. The speaker credits a tuned harness for Antigravity's recent improvement, but the source for that claim is Cursor's article, which is not shown. ([1:07](https://youtu.be/e4giCKHIJy8?t=67))
- **Plan first, then revise the plan instead of patching the output.** — Planning mode analyzes the instructions and existing codebase and produces a detailed plan. The user comments on any line that does not match the goal, and the agent folds those comments into a revised plan. If the implementation is wrong, go back to planning mode and edit the plan rather than sending follow-up prompts. ([2:35](https://youtu.be/e4giCKHIJy8?t=155))
- **Do not tag files by hand. Let the agent pull context on demand with grep and semantic search.** — Tagging a 200+ line component loads the whole file, when the task may need only one 50-line function. Agents can grep for the specific function they need, which keeps the context window smaller. ([3:58](https://youtu.be/e4giCKHIJy8?t=238))
- **Start a fresh conversation for each logical unit of work or when the agent starts repeating mistakes. Use the agent's results as the signal for when to reset.** — Keep the same conversation only when continuing the same feature, reusing its context, or debugging what the agent just built. Old chats can be referenced by name, so the agent reads only the parts it needs. ([3:58](https://youtu.be/e4giCKHIJy8?t=238))
- **Rules and skills extend the agent and are loaded only when relevant.** — Project or global rules are markdown files in the .agent folder (rules subfolder). Skills follow Anthropic's open standard: a SKILL.md with a name and description, plus referenced scripts and references. The agent loads a skill only when it decides the skill applies, which keeps context under control. ([5:25](https://youtu.be/e4giCKHIJy8?t=325))
- **TDD with agents works because the tests give a clear target. Lock the tests in Git before the agent writes code.** — The agent writes tests from described inputs, outputs and behaviors, with no implementation code. The tests are run first and fail. They are committed so the agent cannot quietly change them, and the agent is told not to modify tests while it writes the endpoint, iterating until everything passes. ([7:50](https://youtu.be/e4giCKHIJy8?t=470))
- **Git is a knowledge base for the agent and a safety net. Wrap repeated Git tasks in reusable workflows.** — Commits give the agent history, mark stable versions and allow reverts. Structured commit messages are enforced by a workflow that includes examples, and security and review checks run before commit. Similar workflows cover PRs, worktrees and branches, and dependency updates. ([8:58](https://youtu.be/e4giCKHIJy8?t=538))
- **Watch the agent and interrupt it when it drifts. Then run a review pass with the agent, plus automated PR review bots.** — The review workflow sorts issues by severity, lists the checks to run, and can run linters and tests. The host also uses PR bots (called bugbots) and names CodeRabbit, Sentry and GitHub's built-in review as options. ([10:26](https://youtu.be/e4giCKHIJy8?t=626))
- **Run several agents in parallel, each on its own branch. Shared workspaces are not isolated.** — Antigravity's agents share one workspace, so the host has each agent work on a separate branch and merges only after the project's checks pass. Different models are assigned to the tasks they suit best. ([11:42](https://youtu.be/e4giCKHIJy8?t=702))
- **Debug mode is a skill, since Antigravity has no native one. It works evidence-first, with hypotheses, logging and a multi-phase plan.** — The skill's SKILL.md and its scripts and references guide the agent to add logging, form hypotheses and check them against evidence before changing code. The host says this beats guessing at fixes. ([12:34](https://youtu.be/e4giCKHIJy8?t=754))

## Techniques
- **Comment-driven plan revision** — Switch the agent to planning mode and read the full generated plan. Comment on each line that misses the goal, let the agent regenerate the plan, and repeat until it matches. Only then tell the agent to implement. If the result is wrong, edit the plan and re-plan rather than sending follow-up prompts. *When:* Any non-trivial feature, or whenever an agent's output drifts from what was wanted.
- **On-demand context instead of manual file tagging** — Describe the target function or behavior and let the agent grep or run semantic search to load only the needed segments. Do not attach whole files to the prompt. *When:* Large files or codebases where tagging whole files would fill the context with unused lines.
- **Conversation reset policy** — Open a new conversation per feature or per logical unit of work. Reset when the agent repeats mistakes or gets confused. Keep one conversation only for the same feature, shared context, or debugging what was just built. To reuse earlier work, reference the old conversation by name. *When:* Long sessions where accumulated context starts causing errors.
- **Project rules as markdown in .agent/rules** — Write one markdown file per guideline (for example, WCAG compliance for frontend work) in the project-scope .agent/rules folder. Antigravity supports local and global scope. The agent folds the rule into its plans, for example adding labels to form inputs. *When:* Standards that must hold on every task, such as accessibility or style conventions.
- **Skill folders following Anthropic's open standard** — Create a folder under .agent with a SKILL.md (name, description, instructions) plus optional scripts and reference files. Invoke it by naming the skill and the task, as in asking for a test-specialist skill to write tests. The agent loads it only when relevant. *When:* Repeatable specialized workflows such as testing plans, debugging or domain checks.
- **TDD with a committed test baseline** — Step 1: ask the agent to write tests from described inputs, outputs and behaviors, and tell it not to write implementation code. Step 2: run the tests and confirm they fail. Step 3: commit the tests to Git. Step 4: ask for the implementation while forbidding changes to the tests. Step 5: repeat verification until all tests pass. *When:* Adding endpoints or features where the success criteria can be written as tests before code exists.
- **Screenshot as design and bug input** — Paste a screenshot of the target section into the agent and ask for an exact implementation. For UI bugs, paste a screenshot of the problem rather than describing it in words. *When:* Matching a visual design, or fixing UI issues that are hard to describe in text.
- **Git workflows as reusable commands** — Wrap repeated Git steps (structured commit messages with examples, pre-commit security and review checks, PR, worktree and branch handling, dependency updates) in named workflows the agent runs in one step. Name the workflow in the prompt to execute it. *When:* Projects where commit format and review checks should be consistent across many agent-driven commits.
- **Agent-run code review with severity sorting** — After the agent finishes, run a custom review workflow that groups issues by severity, lists the checks to perform, and includes linters and tests. Add an automated PR review bot on every pull request. *When:* Reviewing agent-written code before merge.
- **Parallel agents on separate branches** — Give each agent a different task and a different branch, since they share a workspace. Assign each model the tasks it does best. Merge only after each branch passes the project's checks. *When:* Several independent features or fixes that can run at the same time.
- **Skill-based debug mode** — Build a debug skill (SKILL.md, scripts and references) that tells the agent to gather evidence, generate hypotheses, add logging statements and follow a multi-phase plan. Invoke it whenever a bug is hard to pin down. *When:* Unexpected behavior where guessing at fixes has not worked.
- **Watch the agent and redirect early** — Monitor the agent while it runs. Interrupt when it heads the wrong way and redirect it toward the goal. *When:* Any long-running agent task.
