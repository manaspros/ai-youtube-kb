> Tutorial on nuqs, a type-safe URL search-param state hook for React frameworks. It keeps UI state in the query string so it survives refresh, bookmarks and back/forward, and covers parsing, throttling, history mode and server-component sync.

## Summary
The presenter argues that URL search parameters are a usable persistent state store for React apps, and that useState loses state on refresh, bookmark or navigation. The demo swaps useState for useQueryState from the nuqs package (transcribed as "Nux"), with a query key and a default value. nuqs needs a framework adapter in the root layout; the demo uses the Next.js App Router. The video covers typed parsers (parseAsBoolean and friends, JSON via Zod, custom parsers) because all query values arrive as strings. It explains that browsers rate-limit history updates, Safari most severely, and that nuqs queues URL writes while keeping local UI state responsive. Further options cover a throttle for expensive fetches, history set to replace or push, and shallow routing, which is on by default and must be turned off to sync values to server components through a shared search-params cache. The video closes by pointing to serialize, URL key aliasing and SEO guidance in the docs. Coverage is a single-library walkthrough with no benchmarks or comparisons.

## Key ideas
- **URL search params as persistent state** — Component state held in useState resets on refresh and is lost on bookmark, share or back/forward. Storing the same values in the query string makes them survive all of these, so the URL becomes a state store. ([0:00](https://youtu.be/t4d1cJarJqs?t=0))
- **Swap useState for useQueryState with a key and default** — nuqs's useQueryState has the same call shape as useState. It takes a query key (e.g. size) and a default (e.g. medium). The presenter's size and color examples persist and restore correctly after a refresh. ([1:05](https://youtu.be/t4d1cJarJqs?t=65))
- **Query values are strings, so parsing needs to be explicit** — Every query param arrives as a string. A boolean default for a modal breaks types, and a truthy string like 'true' or any random string makes the modal stay open. nuqs parsers (parseAsBoolean with a default) fix the type and reject invalid values. ([2:20](https://youtu.be/t4d1cJarJqs?t=140))
- **Browsers rate-limit history updates** — The history API throttles frequent URL writes, and the limit differs by browser, with Safari the worst. Naive per-keystroke URL updates are therefore unreliable. nuqs queues URL updates and keeps the UI state updating immediately. ([3:27](https://youtu.be/t4d1cJarJqs?t=207))
- **Throttle expensive reactions to param changes** — The default throttle is fine for local UI state. If each change triggers a server request or fetch, raise the throttle. The demo sets 5000 ms so a fast-typing input sends one update after the pause instead of a request per change. ([4:28](https://youtu.be/t4d1cJarJqs?t=268))
- **history option controls back-button behavior** — The default is replace, which rewrites the current history entry, so pagination back-button skips earlier pages. push adds a history entry per change, which suits navigation like pagination or modals, but would be noisy for a text input. ([5:37](https://youtu.be/t4d1cJarJqs?t=337))
- **Shallow routing is on by default and blocks server sync** — shallow defaults to true, so param changes are client-only and server components never see them. Setting shallow to false sends each change to the server, but that requires a server-side cache to read the values. ([6:47](https://youtu.be/t4d1cJarJqs?t=407))
- **Share parser definitions between server and client** — The server uses a search-params cache from nuqs/server (createSearchParamsCache) built from the same parser object as the client, and parses the page's searchParams with it. The client hook reuses the same parser definitions, so both sides agree on types and defaults. ([8:08](https://youtu.be/t4d1cJarJqs?t=488))

## Techniques
- **Install and wrap the framework adapter** — Install nuqs with your package manager. For Next.js App Router, import the nuqs adapter in layout.tsx and wrap the app with it. Docs have adapters for React Router, Remix and Vite-based React setups. TanStack has its own first-party type-safe search params, so the presenter says to use nuqs only if you are not on TanStack. *When:* Set up once per project, before any useQueryState call, so routing integration works.
- **Replace useState with useQueryState plus a parser** — Replace const [size, setSize] = useState('black') with useQueryState using a key name and a default value. For typed values, pass a parser such as parseAsBoolean, then call .withDefault(...) (presenter: 'parse as Boolean, with default, parse back false'). Use the same call shape as useState for reads and writes. *When:* Any UI state that should survive refresh, be bookmarkable or shareable: selected options, open modals, filters, page numbers.
- **Throttle URL writes for fetch-triggering params** — Pass an options object as the second argument (for useQueryState, or to the parser's .withOptions() when using the traditional hook). Set the throttle milliseconds option, shown as 5000. The presenter notes the UI stays responsive while the URL and server request wait for the throttle. *When:* A text input or slider changes a param that triggers a server request, a server-component re-render or a fetch.
- **Choose history mode per param** — Use history: 'push' for params that represent navigation (page number, open modal) so the back button steps through them. Keep the default replace for fast-changing input values so the back button is not flooded. *When:* Pagination, modals or tabs (push). Text inputs and search boxes (replace, the default).
- **Sync params to server components** — 1) Set shallow: false on the client hook. 2) Define parsers on the server side with createSearchParamsCache from 'nuqs/server' (import from nuqs/server to avoid a 'use client' boundary). Use parseAsFloat for lat/lng, and set defaults. 3) In page.tsx, await cache.parse(searchParams) with the Next.js searchParams. 4) In nested server components, read cache.all() (destructure) or cache.get(key). 5) On the client, reuse the same parser object so both sides agree. *When:* Next.js or other server-rendered apps where a server component must read the same value the client changed. The presenter notes this is only needed when the server must see params; client-only state can skip it.
- **Use serialize and URL keys for links** — Use the documented serialize function to build query strings for links that should carry state. Use URL keys to alias long param names to short query keys. The docs also cover SEO and reusing hooks, which the presenter does not demo. *When:* Generating deep links to filtered or paginated views, or shortening long URLs.

## Hot takes
- Title 'The BEST Type-Safe URL State Manager' is hype: the video makes a single-library walkthrough and claims no comparison or benchmark.
- Presenter says the 'best state manager' is search query parameters, a framing that overstates the case; the library is one implementation of a well-known pattern.
- Presenter says TanStack already has first-party type-safe search params, which undercuts the 'best' claim for TanStack users.
