> A three-level walkthrough of "loop engineering" in Claude Code: spec-as-/goal for one feature, a queue-driven software factory with a separate adversarial reviewer per branch, then phone control of the loop. Substantive, with the skills and steps shown.

## Summary
The speaker argues that agent loops only work when the verification criterion is defined in advance and owned by a person, and that loops pay off for work needing lots of back-and-forth (such as animation-heavy UI) but not for an undefined MVP. Level 1 turns a feature spec into a Claude Code /goal with an explicit verification method; a small model judges after each turn whether the goal is met. The landing page run took 38 minutes and needed one human correction (blinking mascots) that screenshot-based checks could not catch. Level 2 plans several features, builds clickable HTML prototypes first, and tracks them in a queue markdown table run under /goal, with a sub-agent building on a git branch and a fresh-context adversarial review agent verifying it, looping until the row is done. A human approves each feature through a pull request that contains screenshots, after roughly three hours of overnight-style running. Level 3 uses the Paseo app to drive the same Claude Code setup from a phone or a Mac mini, with a mobile-preview skill that deploys HTML mocks to Vercel. The setup section covers connecting GitHub, Supabase and Vercel through their CLIs. The video is practical but light on measurements, and one segment is a sponsor read.

## Key ideas
- **A loop is an agent working unattended, and the piece the human must keep is the verification check that decides whether the agent is done.** — The speaker splits a loop into a start trigger, the work loop, and a verification check. The check needs to know the correct output, and the person has to own it, because that is what decides whether the agent stops. ([0:00](https://youtu.be/PLyRe6Zk--8?t=0))
- **Loop only where the work needs repeated back-and-forth, not on an MVP whose definition of done is still unknown.** — Rule of thumb given: if a task needs a lot of back-and-forth with the agent, it is a good loop candidate. A first MVP is built by hand because a done condition cannot be written before the product direction is clear. ([4:11](https://youtu.be/PLyRe6Zk--8?t=251))
- **In Claude Code, /goal is the loop-engineering primitive, not /loop.** — /loop reruns a prompt on a timer whether or not anything changed. /goal keeps working until a stated condition holds, and after every turn a smaller model reads the conversation and decides whether the condition is met. ([5:30](https://youtu.be/PLyRe6Zk--8?t=330))
- **Level 1 spec files double as the goal and the verification checklist.** — Each feature folder holds a spec file and an initially empty verification folder that fills up during the run. The spec names the skills to use (GSAP for animation, an optimize skill to recover page speed), an image reference, and a screenshot-based visual check. ([6:57](https://youtu.be/PLyRe6Zk--8?t=417))
- **Screenshot-based verification misses timing-dependent defects.** — The landing page run took 38 minutes and came back with one error, a blinking mascot. The speaker says a screenshot only captures a single moment, so the gap between blinks is too short for it to catch. A human correction prompt was still needed. ([8:25](https://youtu.be/PLyRe6Zk--8?t=505))
- **Level 2 is a software factory: a feature queue, a builder sub-agent on a branch, and a separate adversarial reviewer.** — The main agent picks the next item from the queue and hands it to a sub-agent working on a git branch. The rule stated is that the agent that does the work should never verify it. A fresh-context review agent is told to assume there is a bug, and any failure sends the build agent back around the loop. ([12:47](https://youtu.be/PLyRe6Zk--8?t=767))
- **Prototype the UI as a clickable HTML mock before building, and reuse the mock as a verification oracle.** — The mock is a non-functional clone of the app with only the changed parts shown. The speaker gives two reasons: it tests whether the imagined feature is what is wanted, and it gives the looping agent a reference to verify its build against. ([14:15](https://youtu.be/PLyRe6Zk--8?t=855))
- **The pull request is the single human approval gate in the factory.** — Each finished feature produces a PR with a summary and screenshots. The reviewer can check out the branch locally and merge. Merging to main is what ships to the Vercel deployment. ([18:37](https://youtu.be/PLyRe6Zk--8?t=1117))
- **Level 3 removes the laptop dependency by running the same Claude Code setup behind a phone-accessible app.** — Paseo runs Claude Code on the laptop or a connected Mac mini, with the same skills, CLIs and slash commands including /goal. The speaker notes Claude Code's built-in remote control feature lacks a skill menu. The mobile-preview skill publishes HTML mocks to Vercel links so the phone user can click through them. ([21:33](https://youtu.be/PLyRe6Zk--8?t=1293))

## Techniques
- **Spec file as a /goal with explicit verification** — Create features/<feature>/ containing spec.md (what to build, skills to use, reference image, how to verify) and an empty verification/ folder. Run /goal with that spec and an explicit statement of how completion is verified (the speaker's example uses a screenshot tool from the global CLAUDE.md, which is faster than opening a full browser each time). Use a grill-me style skill first so the agent asks clarifying questions before the spec is written. *When:* Single UI or animation features that need several visual check-and-fix passes, where the back-and-forth is the expensive part.
- **Queue-file tracker for overnight multi-feature runs** — Keep one markdown table listing features with a status column (to do, building, done). A feature-batch skill appends rows and writes each feature's spec folder. Run /goal against the queue file with the stop condition that no row is left in to do or building. *When:* A batch of several features that should run unattended for hours without stopping after the first one.
- **Builder and adversarial verifier split** — For each queue item, the main agent spawns a builder sub-agent that works on a dedicated git branch. When it finishes, a separate review sub-agent with a fresh context window reviews the branch, instructed to assume a bug exists. If it fails, the main agent restarts the build agent. Repeat until the row is marked done. *When:* Any autonomous build where the agent that wrote the code should not be the one judging it.
- **Clickable HTML mock per feature as planning and verification oracle** — A functional-UI skill creates one mock/ folder with an HTML prototype the first time it is needed. Each feature adds a mock showing only the changed part of the cloned app, with views for each role (here, customer and receptionist). Check the mock against the feature spec, then point the verifier at it. *When:* Before building a new feature, so the imagined behaviour is confirmed and the loop has a concrete target to verify against.
- **PR as the human approval gate** — The agent opens a pull request per feature with a summary and screenshots. The human optionally checks out the branch locally, then merges. Only merged work reaches the main branch that Vercel deploys. *When:* Any autonomous loop whose output reaches users; keep the final permission step with a person.
- **CLI-based platform setup driven by the agent** — Create free accounts on GitHub, Supabase and Vercel with Google login. Ask the agent to set up the Next.js app and give a CLI install command for each platform. Run each command in a second terminal, approve the browser login, then let the agent create the repo, database project and deployment. Install the Vercel deploy skill and the Supabase skill (and its best-practices skill) so the agent invokes them automatically. *When:* Bootstrapping a new app so the agent can create and deploy the infrastructure instead of the human clicking through dashboards.
- **Minimal CLAUDE.md that points at AGENTS.md** — CLAUDE.md contains only a pointer to AGENTS.md, since most agents read AGENTS.md as their rules file and only Claude Code reads CLAUDE.md. Put shared project instructions in AGENTS.md so multiple agents can run in the same repo. *When:* A repo where more than one coding agent may be used.
- **Mobile control of a laptop-resident Claude Code session** — Install the Paseo app on the laptop, open a workspace folder per project, and start chats that run Claude Code there, including /goal and custom skills. Pair a Mac mini if one is available. Drive the session from a phone, with generated mock images shown inline and HTML mocks opened via a mobile-preview skill that deploys preview links. *When:* Running long factory loops away from the desk, while keeping the local files, skills and logged-in CLIs on the machine that already has them.

## Hot takes
- The agent that does the work should never verify it; verification goes to a fresh-context adversarial reviewer.
- Only the human should own the verification criterion; a loop can run but cannot hand off the decision of when it is done.
- Screenshot-based checks cannot catch timing or animation defects (the blinking mascot), so one human correction was still needed.
- Loop engineering should not be applied to an MVP, because you cannot define done before you know the product direction.
