## Summary
Better Stack tests Caveman, a community skill for Claude Code (and Codex) that makes the model answer in telegraphic prose to cut output tokens. In a 5-minute demo on a fake-auth Next.js app, the skilled answer opens with the key fact and drops filler, em dashes and full sentences. Across 10 simple technical prompts (for example, git rebase vs merge), the presenter measured 45% fewer output tokens than a baseline and 39% fewer than a plain "be concise" instruction. The catch is that the skill file adds input tokens, so on a single small prompt total cost averaged about 10% higher than baseline. With follow-up questions and prompt caching, he reports a 39% total cost saving. He also cites an unnamed "study this year" claiming brief answers improved accuracy by 26% on some benchmarks, which the video does not source. The video walks through the skill's rules, its intensity levels, and companion skills for commit messages, one-line code review comments and compressing instruction files.

## Techniques
- **Terse-output skill file** — Load a markdown skill into Claude Code that sets the rules: drop articles, filler, pleasantries and hedging; prefer short synonyms (big not extensive, fix not implement a solution for); keep technical terms, code blocks and error text unchanged; answer in the shape thing, action, reason, next step; pick an intensity level (light, full (default), ultra). The video shows the rule text on screen but the install command is not legible in the captions (the speaker says to install via a skills package and run a command). *When:* Technical Q&A where facts matter more than readable prose and the sessions are multi-turn. Avoid for one-shot cheap prompts, where the skill file's input tokens can exceed the output savings, and for onboarding or explanation text that needs full sentences.
- **Three-arm token A/B** — Run the same prompt set through three arms: baseline, a plain 'be concise' instruction, and the skill. Record output tokens and input tokens separately, then compute total cost. Repeat with follow-up questions to capture prompt caching effects. *When:* Deciding whether a prompt-overhead change (a skill, an instruction file or a system prompt) pays off. Measuring output tokens alone overstates the saving.
- **Count the instruction file as input cost** — Treat the size of the skill or instruction file as a per-turn input cost. Compare the per-turn overhead with the expected output savings, then multiply by expected turns per session, taking prompt caching into account. *When:* Any time a large instruction, skill or CLAUDE.md-style file is loaded into every request.
- **Compressed instruction files** — The presenter mentions a companion compress skill that rewrites natural-language instruction files into a terse form so they cost fewer input tokens. Output is not shown in the video. *When:* Large always-loaded instruction or skill files where input tokens dominate the cost.
- **Terse commit and review outputs** — Companion skills in the same family: a caveman-commit skill writes terse messages in conventional-commits format; a caveman-review skill writes one concise line per code review finding. Prompt text is not shown in the video. *When:* Git and PR workflows where short, exact messages and one-line findings are the goal.
