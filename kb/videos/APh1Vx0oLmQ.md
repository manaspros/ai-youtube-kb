> Nishant Gupta (Meta Superintelligence Labs) argues that agent reliability is an infrastructure problem: treat models as probabilistic, keep the platform deterministic, and let infrastructure validate and enforce what the model proposes.

## Summary
The speaker says the challenge with autonomous agents has moved from model intelligence to reliability, because agents now plan tool calls and act on production systems. He argues cloud infrastructure was built for short, deterministic requests, while agents are stateful, long-running, and make decisions dynamically, which he calls the "great mismatch." He names the failures he sees as mostly infrastructure failures, such as retry loops and retry amplification, context corruption, and memory poisoning, where a small model mistake becomes an outage. His main architecture rule is that the model only proposes actions, infrastructure validates them, a policy engine refines them, and an enforcement gateway applies them. He describes an emerging "agentic control plane" for scheduling, memory coordination, policy, and monitoring, and says traces must capture planning and tool-call decisions, not just logs. He also covers layered safety, keeping humans as exception handlers, and reusing distributed-systems patterns such as circuit breakers, rate limits, and quotas. The talk gives no benchmarks or measured results; it is a conceptual, practitioner-level framing.

## Key ideas
- **The challenge with agents is reliability, not intelligence, once they plan tool calls and affect production systems.** — He says the field spent years on bigger models and better reasoning, but organisations moving from chatbots to autonomous agents now face a reliability problem. He describes agent systems as fundamentally probabilistic and says infrastructure is not allowed to be. ([0:03](https://youtu.be/APh1Vx0oLmQ?t=3))
- **The 'great mismatch': agents break the assumptions cloud infrastructure was built on.** — Cloud systems assume short-lived requests, roughly deterministic services, known execution paths and bounded failures. Agents are stateful, long-running, make dynamic decisions and may take different paths for the same input. Production goals are reliability at scale, safe recovery, and acceptable cost and latency, not just capability in a demo. ([1:06](https://youtu.be/APh1Vx0oLmQ?t=66))
- **Most agent incidents are infrastructure failures that start from a model mistake.** — He names recursive reasoning loops, retry amplification, context corruption and memory poisoning. His example: a tool returns an error, the agent sends a slightly different invalid request, and each retry consumes more compute until a minor API error becomes a compute incident. He says hallucinations are often the least interesting failure mode. ([2:06](https://youtu.be/APh1Vx0oLmQ?t=126))
- **Never let the model directly control production systems.** — His strongest recommended principle: the model generates proposals, infrastructure validates them, a policy engine refines them, and an enforcement gateway enforces them. The model suggests, the platform decides. This keeps the system reliable even when the model stays probabilistic. ([2:06](https://youtu.be/APh1Vx0oLmQ?t=126))
- **An agentic control plane is the new layer, and traces must capture decisions, not just events.** — He compares it to Kubernetes for containers and service meshes for microservices. It covers scheduling, memory coordination, policy enforcement, monitoring and workload routing. Logs show what happened; agent traces need to show why, including planning decisions, tool calls, memory lookups and state transitions. ([3:30](https://youtu.be/APh1Vx0oLmQ?t=210))
- **Shared agent memory brings consistency problems, and many multi-agent failures are really consistency failures.** — Once several agents share state, stale reads, conflicting updates and context drift appear. He says this is harder when memory is probabilistic and retrieval-based, so failures that look like reasoning errors are often consistency errors. ([4:33](https://youtu.be/APh1Vx0oLmQ?t=273))
- **Use layered safety and keep humans as exception handlers.** — Safety stack: prompt-level controls, tool permissions, policy validation, human approval and audit. Each layer catches a different failure class. He argues humans should stay in the loop permanently, handling ambiguous and novel cases and giving calibration signals, with attention spent where it adds the most value. ([4:33](https://youtu.be/APh1Vx0oLmQ?t=273))
- **Map classic distributed-systems patterns onto agents instead of inventing new ones.** — Circuit breakers become tool isolation, rate limits become agent limits, controlled retry becomes controlled recovery, and resource quotas become cost governance. Observability becomes agent tracing. AI workloads also look like cluster scheduling, with variable reasoning depth and runtimes from minutes upward. ([5:36](https://youtu.be/APh1Vx0oLmQ?t=336))

## Techniques
- **Propose, validate, enforce split** — The model only emits proposed actions. A validation layer checks them, a policy engine refines them, and an enforcement gateway applies them. The model never writes directly to production systems. *When:* Any agent that can change production state or call tools with side effects.
- **Tool isolation with circuit breakers** — Wrap each tool call in a circuit breaker so repeated failures isolate that tool instead of letting the agent keep retrying it. *When:* Agents that retry failing tool calls, where retries multiply compute and downstream load.
- **Controlled recovery instead of open retries** — Cap retries and recover in a bounded way, so an agent that keeps producing slightly different invalid requests stops before compute grows. *When:* Tool errors that make the agent regenerate near-identical invalid requests.
- **Decision-chain tracing** — Record planning decisions, tool calls, memory lookups and state transitions per run, and read the chain when debugging, not only the final output. *When:* Debugging long-running or multi-step agent workloads where the final output hides the cause.
- **Per-agent limits and cost quotas** — Apply rate limits per agent and resource quotas as cost governance, reusing standard distributed-systems controls. *When:* Multi-agent or high-volume agent workloads where one run can consume unbounded compute.
- **Layered defence for agent actions** — Combine prompt-level controls, per-tool permissions, policy validation, human approval and audit logging, expecting each layer to catch different failures. *When:* Agents with access to real systems where no single guard is enough.
- **Humans as exception handlers** — Route ambiguous or novel cases to a human, and feed those decisions back as calibration signals rather than treating human review as temporary. *When:* Agent systems where the cost of a wrong autonomous action is high.

## Hot takes
- Hallucinations are the least interesting AI failure in production; infrastructure failures are the real problem.
- Many multi-agent failures are consistency failures that look like reasoning failures.
- The most successful agent systems will stay human-supervised, with humans acting as exception handlers rather than a temporary crutch.
- Models and prompts are commoditising, so the competitive advantage is moving to infrastructure: the organisations with the most reliable systems will win, not those with the best prompts.
