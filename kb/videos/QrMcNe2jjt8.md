> Gus Iwanaga (commercetools) on intent-driven generative UI: an orchestrator picks data and components, and the LLM emits a validated declarative UI spec, not free-form UI. Main lessons are on placement, the component catalog as contract, and changing team roles.

## Summary
Gus Iwanaga, GM at commercetools, argues that most SaaS UIs are still static and that the cognitive load of learning many apps should move to the software. He demos a generative UI product where a query like "create a sales report for Q1" makes an orchestrator extract intent, pull data from first- and third-party tools (including MCP servers), and hand that context to a UX agent. Early prototypes were inconsistent: the same query in four phrasings produced different layouts and dates, which he judged unshippable. He lays out three control levels for rendering (pick a component from a catalog, declarative UI spec, or open HTML in a sandboxed iframe) and says his team chose the declarative middle. The pipeline validates the spec against a Zod component catalog and renders native React components so output stays on the design system. The hard problems he names are information architecture (solved with an atomic-design-style layout hierarchy of templates, slots, sub-slots and components) and treating the catalog and its curation as the central asset. He also says the team no longer designs pixels, and that the work moved to schema curation, rules, and synthetic query-to-component data.

## Key ideas
- **Most SaaS UI is still static, so users carry the cognitive load of learning many apps. Generative UI can move that load to the software.** — Speaker frames the problem through screenshots of complex CRM-style screens and onboarding costs. The claim is that AI makes it possible to change the interface per intent instead of per app. ([2:46](https://youtu.be/QrMcNe2jjt8?t=166))
- **Generative UI from a free-form prompt is not shippable as is. The same query phrased four ways gave different time ranges and layouts.** — His early prototype turned 'Q1' into January to March and changed the KPI cards and charts between runs. He judged it unfit for production. Consistency across turns is treated as a hard requirement. ([6:38](https://youtu.be/QrMcNe2jjt8?t=398))
- **An orchestrator separates intent extraction, tool selection and data assembly from rendering.** — It extracts intent, locates first- or third-party tools (agents or MCP servers), and gathers the outputs as context. A separate UX agent then decides how to render that context. ([8:52](https://youtu.be/QrMcNe2jjt8?t=532))
- **There are three control levels for generated UI: pick from a catalog, declarative spec, or open HTML.** — Pick-from-catalog gives the most control and suits booking-style flows. Full autonomy means the LLM writes the layout (his example: an org chart). Open-ended means an MCP tool returns HTML rendered in a sandboxed iframe. He picked the declarative middle, citing B2B configuration complexity and the need for control. ([11:39](https://youtu.be/QrMcNe2jjt8?t=699))
- **The declarative path keeps output on the design system: the LLM emits a UI spec that is validated against a Zod component catalog, then rendered as native React components.** — Mapping goes from retrieved entities to eligible catalog components. The orchestrator broadcasts a UI description that must conform to the protocol and the catalog schema. Because the LLM does not write the copy or the native components, dates and wording stay fixed. Named protocols include A2UI (Google), JSON Render (Vercel) and OpenUI. ([15:14](https://youtu.be/QrMcNe2jjt8?t=914))
- **Placement (information architecture) is the first hard problem once the agent picks components. The fix was a layout hierarchy and templates.** — They borrowed atomic design and built layout, then slots, sub-slots and components. Because the orchestrator produces components first, they flip the order at mapping time: components map to sub-slots, sub-slots to slots, slots to templates. The UX agent is taught a template catalog, which codifies the team's UX knowledge. ([17:47](https://youtu.be/QrMcNe2jjt8?t=1067))
- **The catalog is the contract between agent and UI, so every property and the layout's own components need curation. He calls it the heartbeat of the system.** — Because the catalog defines what the agent can say, schema attributes matter. Curation of the catalog is what turns a demo into something meaningful. ([20:26](https://youtu.be/QrMcNe2jjt8?t=1226))
- **The team stopped designing pixels. Their work shifted to schema, catalog curation, rules, synthetic query generation and interaction patterns, and this change also affected PMs and designers.** — Synthetic queries are generated to map to each component. He stresses people, product and process as the three levers, with a lightweight process. ([21:49](https://youtu.be/QrMcNe2jjt8?t=1309))

## Techniques
- **Declarative UI spec validated against a component catalog** — The LLM outputs a UI description that references catalog components and their props. Validate it against a schema (Zod in their case) and render native components from the design system. Do not let the model write raw markup. *When:* When output must follow a design system and copy, dates or numbers must not drift between runs.
- **Three-tier control spectrum for generated UI** — Pick the rendering mode by how much control the business needs: (1) agent picks a catalog component and it renders as-is; (2) declarative spec validated against the catalog; (3) MCP tool returns HTML rendered in a sandboxed iframe, with full LLM control. *When:* Choose per product. Booking-style flows fit tier 1, B2B configuration-heavy flows fit tier 2, and open-ended exploration fits tier 3.
- **Intent-to-UI orchestration pipeline** — Stage 1: extract intent from the query. Stage 2: locate and call tools, including MCP servers, and collect their outputs as context. Stage 3: map retrieved entities to eligible catalog components. Stage 4: a UX agent produces the UI spec. Stage 5: render natively. *When:* When one query should assemble data from several systems into a dashboard-like view.
- **Layout hierarchy with templates, built bottom-up** — Model the page as layout to slots to sub-slots to components, plus a library of templates. Map components upward to sub-slots, then slots, then templates, so the agent picks a template and fills slots. *When:* When an agent chooses components but placement must stay consistent with UX rules.
- **Synthetic query-to-component data for curation** — Generate example queries that should map to each catalog component, and use them to test and tune the mapping logic. *When:* When the catalog grows and you need coverage checks on how queries map to UI components.

## Hot takes
- The software should adapt to people, not people to the software, and AI makes that possible now.
- Fully delegating UI to an LLM is risky for companies because you cannot control output or outcome. Keep designers in control.
- Non-deterministic UI needs a per-product choice of control level, and most teams should not choose full autonomy.
- The team no longer designs pixels. The main work is catalog curation and rules, and the non-technical roles change too.

## Relevance to our work
- **agentos** (1/3): AgentOS is infra for agents. The talk's declarative spec plus schema validation is an output-contract pattern that could fit an agent UI surface, but AgentOS does not yet render UI. → *If AgentOS ever returns UI, have agents emit a catalog-validated spec, not raw HTML, and log which catalog components were chosen.*
- **prosharness** (1/3): ProsHarness has phone-driven approvals. A validated spec of approval cards (catalog-limited) could be safer than free-form content when the agent drives the UI. → *When designing phone approval cards, define a small component catalog with a schema the agent must fill, and validate it before rendering.*
- **general** (1/3): The catalog-as-contract idea (the tool or component schema bounds what the model can emit, and curation drives quality) applies to any agent-to-UI or agent-to-tool boundary. → *Read the talk's topic on generative UI protocols (A2UI, JSON Render, OpenUI) before choosing a UI output format for any agent feature.*
