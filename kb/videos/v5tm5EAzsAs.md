> A five-step regression loop for agents built on production traces, evaluators and CI gates, so a prompt or policy change is judged on numbers before it merges. Vendor-led demo of Arize.

## Summary
Sofia Jakovcevic (Arize AI) argues that agent regressions show up at runtime, not in the code diff, so a one-line prompt change can improve one metric and quietly hurt another. Her example: a security-driven "confirm before acting" line raised action safety by 17 points but cut task completion by 17 points, netting zero on average. She proposes a five-step loop: build a dataset from production traces, define evaluators (LLM-as-judge, code, or ML based), run a baseline experiment, make one change and compare, then run the experiment as a required CI check on every PR. Every production failure should be added back to the regression set. The second half argues that agents, given access to traces through skills, should investigate failures and propose fixes themselves, with humans as the bottleneck. Most of the content is a live walkthrough of the Arize UI (prompt and agent playgrounds), so treat the product claims as vendor claims. The regression framing itself is practical and reusable with any tracing backend.

## Key ideas
- **Agents fail at runtime, not at the code level, so the diff shows what changed but only traces show what the agent actually does.** — A one-line system prompt edit changes trajectories: more steps, different sub-agent handoffs, different tool calls. Those trajectories exist only in the observability backend, which the speaker calls the new source of truth. ([4:16](https://youtu.be/v5tm5EAzsAs?t=256))
- **A single-dimension improvement can net to zero or worse for the agent as a whole.** — Example: action safety +17 points, task completion -17 points, because the agent now asks for confirmation before every action and sessions are left unfinished. Average is net zero. Per-metric evals catch what a code review cannot. ([3:18](https://youtu.be/v5tm5EAzsAs?t=198))
- **Build the regression dataset from real production traces in four buckets.** — Include representative average workflows, known failures (errors, low metric scores), edge cases that are rare but important, and successful workflows you want to protect. Including the successful ones is what catches a fix that breaks something that already worked. ([6:33](https://youtu.be/v5tm5EAzsAs?t=393))
- **Turn subjective quality dimensions into numeric scores with evaluators.** — Hallucination, accuracy, tool trajectory and step efficiency are scored by LLM-as-judge, which can give binary or 0-5 labels. Code evaluators suit deterministic checks and ML-based evaluators are also possible. Use code for deterministic checks and LLM judges for non-deterministic ones. ([7:45](https://youtu.be/v5tm5EAzsAs?t=465))
- **Run a baseline, change one thing at a time, and compare before deploying.** — Run the agent over the whole dataset with the evaluation suite to get a baseline. Then change one thing (prompt, handoff, tool, or model) and rerun. This also gives an ROI test for switching to a more expensive model, judged on eval results rather than intuition. ([10:02](https://youtu.be/v5tm5EAzsAs?t=602))
- **Make the experiment a required CI check on every pull request.** — Each PR runs the experiment workflow (the speaker shows GitHub Actions) and does not merge until it meets the regression criteria listed for the team. ([11:16](https://youtu.be/v5tm5EAzsAs?t=676))
- **Every production failure should become a new regression test.** — Failed production traces go back into the dataset, so the regression suite grows with each incident. ([16:15](https://youtu.be/v5tm5EAzsAs?t=975))
- **Humans are the bottleneck in the loop, so the speaker proposes agents investigate traces and propose fixes.** — Coding agents that open PRs without access to production traces are working blind. Connecting coding agents to observability through skills lets them check real runtime behavior before proposing a change. This is the speaker's forward-looking claim, not a result she measured. ([17:18](https://youtu.be/v5tm5EAzsAs?t=1038))

## Techniques
- **Five-step trace-driven regression loop** — 1) Pull production traces into a dataset (representative, known failures, edge cases, protected successes). 2) Define evaluators per metric. 3) Run a baseline experiment: the agent over all dataset rows, then score with the evaluators. 4) Change one thing (prompt, model, tool, handoff, policy), rerun, and compare to baseline. 5) Put the experiment in CI so each PR must pass the criteria. Feed failed production traces back into the dataset. *When:* Before merging any change to prompts, policies, tools, models, or multi-agent wiring, especially one-line prompt edits that seem harmless.
- **Four-bucket dataset composition** — Sample from real traffic and deliberately include: typical workflows, failing or low-scoring runs, rare edge cases, and successful runs you want to protect from regression. The speaker's demo used a 100-row dataset built this way. *When:* When building the first regression set, or when a new incident should be captured as a test.
- **LLM-as-judge plus code evaluators** — Write a judge prompt that labels each span or trace (binary 0/1 or a 0-5 scale), for example task completion (complete or incomplete) and action safety. Use code evaluators for deterministic checks such as security or format rules. Keep the rubric in the judge prompt so scores are reproducible. *When:* When a quality dimension (hallucination, task completion, efficiency) is hard to check by hand but you need a number to gate on.
- **Side-by-side prompt versions in a playground** — Load prompt v1 from the prompt hub, duplicate it, edit one line, and run both versions against the same dataset with the same evaluators. Compare score deltas per metric, then check latency, cost, and error rate on the run. *When:* When iterating on a prompt change and you want to see its per-metric effect before any deploy.
- **Agent playground against a remote agent** — Expose the multi-agent system over HTTP and register it as a remote agent in the eval tool. Each dataset row then calls the full system, and the evals score the end-to-end output. The speaker says this lets you test changes to how sub-agents talk to each other directly in the codebase. *When:* When the failure is in orchestration (handoffs, sub-agent calls) and single-prompt testing would miss it.
- **Run experiments from coding agents through skills** — Install the vendor's public agent-skills repository so a coding agent can run datasets, experiments and trace queries through the SDK, REST, or CLI. The agent then sees production traces while writing the change. *When:* When you want coding agents to check real runtime behavior before opening a PR.
- **CI gate on experiment results** — Add a GitHub Actions job (or equivalent) that runs the experiment against the team's evaluators on each PR and fails when the regression criteria are not met. *When:* Once the loop works locally and you want it enforced on every change.

## Hot takes
- Traces, not diffs, are the real source of truth for agent behavior.
- Every production failure should become a permanent regression test.
- Coding agents that open PRs without production trace access are 'pushing PRs blind.'
- The next frontier is agents investigating their own traces and proposing fixes, with humans no longer the bottleneck (a forward-looking claim, not shown with results).
- Vendor-led talk: the live demo is mostly the Arize UI, and the platform's built-in evaluators and skills are presented as the way to do this. The loop itself does not need Arize.

## Tools mentioned
Arize (Arize AI observability backend and platform, incl. prompt hub, prompt playground, agent playground, experiments, datasets), Arize agent skills repository (public, for coding agents), GitHub Actions (CI example), Arize SDK / REST / CLI (run experiment), LLM-as-judge evaluators (pre-built: hallucination, user frustration, security checks; custom evaluators supported)
