> Walkthrough of GoLive, an early agent skill plus Node CLI that takes a repo live (Vercel, Supabase, Resend, Stripe) via plan, approve, apply, verify gates, with candid caveats about consent and credential storage.

## Summary
The Better Stack host demos GoLive, a skill-plus-Node-CLI that deploys an app built with Claude Code to hosting, a database, email and Stripe test-mode webhooks. It runs in stages: detect what the app needs, write a plan with an ID, the user approves that exact plan, the changes are applied, and then the webhook is verified with an unsigned request (must be rejected) and a signed test event (must pass). Auth is borrowed from the user's existing CLI logins, with Stripe as the exception. Destructive, DNS and live-production steps sit behind separate confirm flags, and actions that cost money are refused outright. The host argues these confirm flags are agent-supplied arguments, so nothing records a human consent, and an agent logged into a provider can bypass GoLive entirely. Other caveats include a plaintext Stripe key file, unsigned releases, incomplete teardown (databases are left behind), and only two hosts and two databases supported. The project is single-author and very new, and the host cannot verify its star count. The closing framing is that agent tools should be judged on what they are allowed to do and whether their actions can be proven and reversed.

## Key ideas
- **Taking an app live is many coupled pieces (hosting, database, DNS, verified email domain, Stripe webhook with its own signing secret), and a mistake in one is often silent until a customer hits it, such as a payment with no receipt.** — The host's own pattern is getting five of six right and missing one, discovered only after deploy. ([0:00](https://youtu.be/HTscIrJhjDs?t=0))
- **GoLive treats deployment as a pre-flight checklist rather than autopilot: detect needs, write a plan, the user approves that exact plan, apply it, then verify the result.** — The approval is bound to the plan itself (the plan gets an ID), so approval covers the exact plan shown. ([1:02](https://youtu.be/HTscIrJhjDs?t=62))
- **The first run only produces a plan: Vercel for hosting, Supabase for the database, Resend for email, and Stripe in test mode, with a plan ID. Nothing deploys until the plan is approved.** — Demo invoked as the /go live slash command in Claude Code with the prompt to use test resources and watch first (command spelling as spoken in the video). ([2:19](https://youtu.be/HTscIrJhjDs?t=139))
- **Post-apply verification is concrete: an unsigned webhook request must be rejected, a properly signed test event must get through, and an end-to-end test-card payment must clear before the run is considered good.** — The final output is a live URL plus a written report of what was created, with no secrets in the report. ([2:19](https://youtu.be/HTscIrJhjDs?t=139))
- **Architecture is a skill file (the agent's instruction manual) plus a small Node CLI that does the work. It is not an MCP server, and the author says it is verified only on Claude Code and Codex.** — It borrows the logins the user already has for providers rather than creating new credentials; Stripe is the stated exception. ([3:28](https://youtu.be/HTscIrJhjDs?t=208))
- **Gating is layered: plan ID required before apply, separate confirm flags for destroy, DNS changes and anything live on production, and paid actions (buying a domain, upgrading a plan, signing up for accounts) are refused outright, not just warned about.** — Teardown deletes only resources that can prove GoLive created them. ([3:28](https://youtu.be/HTscIrJhjDs?t=208))
- **Positioning: narrower coverage than Vercel/Netlify integrations, Terraform or SST, or AI app builders, but it works on any repo with your own accounts, one conversation, and a written report of changes.** — The host frames the value as automating the boring part without assuming every action should be automated. ([4:25](https://youtu.be/HTscIrJhjDs?t=265))
- **The confirm flags are not a hard lock. They are arguments the agent passes on the user's behalf, nothing records that a human actually said yes, and an agent already logged into a provider can write there without going through GoLive.** — The host cites the maintainer's own trust document for this point. ([4:25](https://youtu.be/HTscIrJhjDs?t=265))

- **Framing for agent tooling: the question has moved from 'can the agent do it' to 'what should the agent be allowed to do, and can you prove what happened afterwards'. ## Techniques
- **Plan-then-approve-then-apply with a plan ID** — Have the agent detect infrastructure needs and write an explicit plan with an ID. Apply only when that plan ID is passed, so the approval is bound to the exact plan shown. Show the plan with no changes made first (GoLive's first run only produced a plan). *When:* Any agent-driven change to hosting, DNS, databases or payment config, where a silent mismatch between the plan and the applied change would be costly.
- **Verify webhooks both negatively and positively after deploy** — Send an unsigned request to the webhook endpoint and assert it is rejected. Send a correctly signed test event and assert it is accepted. Then run an end-to-end test-mode payment (test card 4242 4242 4242 4242 in the demo) and confirm it clears. *When:* Any deploy that depends on signed webhooks such as Stripe, where a wrong signing secret otherwise only shows up when a real customer pays.
- **Separate confirm flags for destructive, DNS and production-live actions** — Require an explicit flag for each high-risk class: confirm destroy for deletes, confirm dns for DNS changes, confirm live for anything on production. Note the flags are agent-supplied arguments, so they are a speed bump, not proof of human consent. Pair them with a real human-approval step if consent matters. *When:* Designing agent tool surfaces for infrastructure, where the goal is to make risky steps deliberate rather than to prevent a determined agent.
- **Refuse-list for paid or account-creating actions** — Do not implement paid steps at all: buying a domain, upgrading a plan, signing up for a new account. The user brings those and the tool stops at that boundary. *When:* Agent tools with access to billing or account creation, where a warning is not enough and the cost is real.
- **Ownership-tagged teardown** — Tag each resource at creation and, on teardown, delete only resources that carry the tool's tag. The video says GoLive removes the host project, webhooks, email keys and tagged DNS records, but not databases. *When:* Any tool that creates cloud resources and later needs to clean up without deleting things the user owns.
- **Borrow existing CLI logins instead of minting credentials** — Use credentials the user already has for each provider's CLI, so the agent does not create new keys. Stripe was the stated exception, and the storage of its key in a plaintext file is a caveat to avoid copying. *When:* Local agent tooling where minimizing new long-lived secrets matters more than a central credential vault.
- **Post-run written report with no secrets** — After applying, write a report listing what was created and the live URLs, with secret values excluded. *When:* Any agent-driven provisioning, so a human can audit what changed later.
- **Skill file plus a small CLI, not an MCP server** — Ship the agent's instructions as a skill file and put the deterministic work in a small Node CLI that the skill invokes. Verify only on the agents you have tested (the author says Claude Code and Codex). *When:* When you want a portable, scriptable tool whose behavior is deterministic and does not depend on an MCP server running.

## Hot takes
- The confirm flags (confirm destroy, confirm dns, confirm live) are not a hard lock: they are arguments the agent passes itself, nothing records human consent, and an agent logged into a provider can bypass GoLive.
- Stripe keys sitting in a plaintext home-config file (user-locked, not keychain, not encrypted) with unsigned releases is a poor fit for handling payment secrets.
- The 1,000-star count in a few days from a one-author repo is suspicious and unverified; the host says to treat it as very early.
- The most useful framing: judge agent tools on what they are allowed to do and whether actions can be proven and reversed, not just whether they can do the task.
