## Summary
A 1h43m live workshop, "Vibe Engineering Effect Apps" (Michael Arnaldi, Effectful), starts from an empty Bun repo and builds a to-do HTTP API with Effect v4 beta, using GPT-5.4 in OpenCode. The speaker's core thesis is that models are trained on code, not docs, so the agent should get the actual library source (cloned as a git subtree) rather than MCP docs or node_modules. He makes every TypeScript diagnostic an error, writes AGENTS.md with commands and a no-watch-mode rule, and adds custom ESLint rules each time he sees a bad pattern (for example banning `as`, `any`, and `unknown`). Pattern docs (http-api, sql, testing) are generated from the upstream repo so each team can self-select what it uses. Implementation runs as a bash loop where each iteration takes one small task from a markdown spec and exits, giving fresh context. He also argues for fewer tools (a single execute tool that writes TypeScript transforms), per-model prompt tuning, and evals for pattern quality. The session ends by pointing to durable workflows (Effect Cluster) for long-running LLM steps, but does not build them.

## Key ideas
- **Models are trained on code, not docs, so give the agent the real source repo** — The speaker says agents are post-trained on code, so MCP doc servers are a weak fit for undocumented library code. He says agents look at node_modules less often than project code and skip gitignored folders, so he clones the library repo (as a git subtree, squashed) into a visible folder. He calls this the only approach that works reliably across languages. ([11:01](https://youtu.be/Wmp2Tku2PrI?t=661))
- **Context is a fixed array, and more context can confuse the model** — Models do not learn from one session to the next. Memory has to be engineered by writing knowledge into files. He argues a 1M-token window is not automatically useful, since extra content can confuse the model on other tasks in the same context. ([7:47](https://youtu.be/Wmp2Tku2PrI?t=467))
- **Strict diagnostics are back pressure for AI-written code** — He sets every TypeScript diagnostic to error and turns on format-on-save, so the model cannot pass with warnings or near-misses. He treats this as the baseline for any project where AI writes most of the code. ([29:46](https://youtu.be/Wmp2Tku2PrI?t=1786))
- **Every lint rule should map to a mistake the model actually made** — He bans `as`, `any` and `unknown` with custom ESLint rules. When he banned `unknown`, the model switched to `as never as X`, since `never` is a bottom type. He then banned `as` entirely and pushed the model toward schema validation and branded constructors at the edge. ([31:06](https://youtu.be/Wmp2Tku2PrI?t=1866))
- **Spec in a markdown file, then a bash loop with fresh context per small task** — He discusses the spec with the model and saves it as markdown. Then a bash loop tells the model to pick up one small task, implement it, and exit. Each iteration starts with a clean context window. He says plan mode is weaker because it restricts tools. ([33:43](https://youtu.be/Wmp2Tku2PrI?t=2023))
- **Fewer tools can give better results** — He describes experiments with a single `execute` tool that runs TypeScript. The model cannot patch files directly and must write AST-style TypeScript transforms. He says this reduced the agent's room for mistakes, though he gives no measured numbers. ([45:11](https://youtu.be/Wmp2Tku2PrI?t=2711))
- **Generate pattern docs per library, then choose which to use** — He asks the agent to explore the upstream repo and write pattern files (http-api.md, sql.md, testing.md) listed in AGENTS.md. Teams can take only the patterns they want, which matters in brownfield code. He notes generated docs may not match what a skilled author would write. ([42:24](https://youtu.be/Wmp2Tku2PrI?t=2544))
- **Prompt style differs by model family** — He writes in lowercase because he says GPT models get passive when shouted at. Claude pays closer attention to emphasized sentences. He suggests generating pattern docs per model family, though he admits it is hard to maintain. ([1:01:22](https://youtu.be/Wmp2Tku2PrI?t=3682))
- **Evals and reference checks keep pattern docs honest** — The Effect team plans daily evals that compare human-written code, generated code, and an LLM judge. He estimates a 80/20 human split on style judgments, so evals will not give a single truth. A linter plugin that checks file references in pattern docs runs in CI. ([1:31:05](https://youtu.be/Wmp2Tku2PrI?t=5465))
- **Long-running LLM steps need durable workflows** — He argues LLM calls take minutes, so server crashes mid-process become likely. A registration flow that writes to a database and then sends email can fail between steps. He points to Effect Cluster/Workflows, which resume a started procedure after a crash, though this part is still unstable in Effect and was not built in the session. ([1:38:29](https://youtu.be/Wmp2Tku2PrI?t=5909))

## Techniques
- **Clone the library source into the repo** — Add the upstream repo as a squashed git subtree in a visible folder (for example repos/effect), then tell AGENTS.md where it lives. Avoid node_modules or gitignored folders, which agents read less. *When:* Working with a library that has poor docs or no docs the model was trained on, or in brownfield codebases.
- **Strict diagnostics plus lint as back pressure** — Set all TS diagnostics to error. Write custom ESLint rules that ban shortcut patterns (type assertions, any, unknown). Ban the escape hatch too (for example `as` in general), and push validation into schemas and branded-type constructors. *When:* Any repo where an agent writes most of the code and you want it to fail fast instead of passing with near-misses.
- **AGENTS.md as a living rulebook** — Start with a short file listing run, typecheck and test commands, plus a list of pattern files. Explicitly forbid watch mode and dev servers. Add a rule each time a bad pattern appears, and ask the model why it did something before accepting the change. *When:* Any project where the agent repeats the same mistakes across sessions.
- **Spec file plus Ralph-style loop** — Agree on a spec in markdown. Run a bash loop where each iteration gives the model one small task, lets it implement the task, then exits so the next run starts with a new context. *When:* Long implementation runs where context pollution degrades later tasks.
- **Self-selected pattern docs** — Ask the agent to explore an upstream repo and write one markdown file per feature area, such as http-api, sql, or testing. Reference them from AGENTS.md. Use only the ones you want. *When:* Adopting a framework partially, or when a team has conventions different from upstream defaults.
- **Single execute tool instead of many tools** — Expose one tool that runs TypeScript code (which can call bash). The model writes a transform script rather than editing files directly. *When:* Bulk codebase transforms, where you want deterministic, reviewable changes instead of free-form edits. Claimed benefit, not measured in the talk.
- **Per-test rollback transactions for DB tests** — Run each test inside a transaction and roll it back when it finishes, so tests do not leak state and do not need a fresh database each time. *When:* Test suites against a real database that would be too slow with a new instance per test.
- **Test layers with it.layer** — Provide shared service layers in Vitest with the Effect test helpers instead of custom wrappers that call layer.build or effect.scoped. *When:* Effect-based test suites where agents keep writing custom layer setup.
- **Lint reference checks in CI for pattern docs** — Use a linter plugin to check that file paths mentioned in pattern docs still exist, and run it in CI. *When:* Pattern or docs folders that refer to repo files and drift as code changes.

## Hot takes
- The best way to give an agent library knowledge is to clone the repository, not to use MCP docs or node_modules.
- Less is more: fewer tools, simpler loops, and smaller contexts beat complex context-management architectures.
- The zero-to-one problem only matters for the first hours of a project; the important work is setting up the repo so the model can act at scale.
- Ban type assertions outright, because models will find a loophole in any narrower ban (like `never`).
- Skills are useful for narrow, team-specific patterns, but loading a skill for every framework internal pollutes the context.
- Models respond differently to prompt style: shouting helps Claude and makes GPT passive.
