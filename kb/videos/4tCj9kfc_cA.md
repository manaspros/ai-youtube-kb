> A 30-minute AWS CloudWatch setup tutorial covering EC2 agent logs, Lambda, API Gateway access logs, RDS log exports, alarms, canaries, and forwarding logs to Better Stack.

## Summary
The video walks through CloudWatch's core model (log groups as folders, log streams as sources) and then sets up logging for four AWS services: EC2 custom application logs via the CloudWatch agent, Lambda (automatic), API Gateway access logs, and RDS log exports. It then covers metric alarms with SNS notifications and synthetic canaries for endpoint uptime. The last roughly seven minutes switch to Better Stack, showing how to route CloudWatch alarms into its incident tool through an SNS webhook and how to forward log groups to it with a Lambda subscription filter. The AWS steps are reproducible console procedures with concrete IAM, agent, and log-format details. The Better Stack portion is a vendor pitch and makes unsupported claims about cost and ease of use. Nothing in the video concerns AI or agents directly, so its value to our projects is as general observability background.

## Key ideas
- **CloudWatch data model: a log group is a folder sharing retention and access settings; a log stream is one source inside it, such as a single RDS instance's error log.** — Live Tail can filter by log group, stream, or event text, including JSON field matching. Extra instances of the same kind of source go in the same group as new streams. ([1:20](https://youtu.be/4tCj9kfc_cA?t=80))
- **Metric alarms compare a metric to a static threshold and fire actions on state change, typically via an SNS topic that emails or calls other services.** — The demo alarms on EC2 CPUUtilization above 50%. The speaker notes that actions can also be Lambda functions, Auto Scaling, or EC2 restarts. ([4:48](https://youtu.be/4tCj9kfc_cA?t=288))
- **Custom application logs on EC2 need an IAM role with the CloudWatch agent server policy attached as the instance profile, then the agent installed and configured with a wizard.** — The wizard asks which user runs the agent (root in the demo), whether to enable statsd or collectd (no), which log file to tail and what log group name to use, and whether to store the config in SSM (no). ([6:45](https://youtu.be/4tCj9kfc_cA?t=405))
- **Lambda creates its log group automatically, while API Gateway needs an account-level CloudWatch role, a log group, and per-stage logging and access-log configuration.** — The access log format is a custom one, and the speaker uses AWS's generic example format. Requests must be made after logging is enabled before logs appear in Live Tail. ([11:30](https://youtu.be/4tCj9kfc_cA?t=690))
- **RDS log exports are opt-in: audit, error, general, and slow query logs are chosen in the instance's Additional configuration section, and the log groups appear only after logs are generated.** — The demo restarts the database to produce startup and shutdown entries in the error log before the log group shows up. ([16:48](https://youtu.be/4tCj9kfc_cA?t=1008))
- **Synthetic canaries are scheduled scripts that hit endpoints, ideally along the routes a customer would use, to detect outages before users do.** — The default script loads the URL, optionally takes a screenshot, and checks for a 200 response. Schedules can be continuous, cron-based, or run once. Canary names must be lowercase. ([5:49](https://youtu.be/4tCj9kfc_cA?t=349))
- **Alarm-to-incident routing: create an HTTPS SNS subscription to the vendor's webhook, then attach that topic to both the ALARM and OK actions on each alarm.** — Adding the OK action lets the incident tool see the recovery as well as the breach. In the demo, the first incident appears only after a forced alarm. ([24:52](https://youtu.be/4tCj9kfc_cA?t=1492))
- **Forwarding CloudWatch logs to a third-party tool uses a vendor-supplied Lambda plus a subscription filter on each log group, with JSON log format and a source token in an environment variable.** — The subscription filter is created from the log group's Actions menu. The speaker says logs appear with the same fields but a nicer UI in the vendor's Live Tail. ([28:04](https://youtu.be/4tCj9kfc_cA?t=1684))

## Techniques
- **EC2 custom log shipping to CloudWatch** — 1) IAM: create a role for the EC2 service and attach the CloudWatch agent server managed policy (named 'CloudWatchAgentServerPolicy' in the console; the speaker calls it 'CloudWatch agent server policy'). Name it, e.g. 'EC2 CloudWatch'. 2) Attach it to the instance as the IAM instance profile at launch (Advanced details) or via Modify on an existing instance. 3) On the instance: sudo yum install amazon-cloudwatch-agent. 4) Run the config wizard (command shown on screen, not spoken): user root; statsd no; collectd no; add the app log path (demo: index-out.log); accept the default log group name; add no more files; enable X-Ray traces; do not save to SSM. 5) Start the agent with -c pointing at file:/opt/aws/amazon-cloudwatch-agent/bin/config.json and check status (exact ctl command is on screen only). *When:* Shipping an application's file logs and host metrics from EC2 to CloudWatch without a third-party agent.
- **API Gateway access logging** — 1) Create a CloudWatch log group for gateway logs and copy its ARN. 2) IAM: create a role for the API Gateway service with the managed policy 'Amazon API Gateway Push to CloudWatch Logs'. Copy its role ARN. 3) In API Gateway account settings (Edit logging), paste the role ARN and save. 4) Per API, go to Stages, then Logs and tracing, Edit. Pick a logging level (errors only, errors and info, or full request and response) and enable custom access logging. 5) Paste the log group ARN into the access log destination, removing the trailing ':*' (the speaker stresses this), and use AWS's generic access log format. *When:* Debugging request and response behaviour, status codes, or latency at the API edge.
- **RDS log exports to CloudWatch** — RDS > Databases > select the instance > Modify > Additional configuration > Log exports. Tick the log types to publish (demo: audit, error, general, slow query), then Continue and Modify. Log groups appear once the database writes logs; restart the instance to force a startup-log entry. *When:* Tracing slow queries or database errors in the same place as application logs.
- **Static-threshold alarm with a test trigger** — CloudWatch > Alarms > Create alarm > select metric (EC2 per-instance CPUUtilization, statistic Average) > Static threshold, greater than 50 > notification to a new SNS topic with your email (confirm the subscription email) > name the alarm > create. To test the path, edit the threshold to 0, wait for the ALARM state, then restore it. *When:* Validating the full alarm to notification path before relying on it.
- **Alarm to incident tool via SNS webhook** — In the incident tool create an integration for CloudWatch alarms and copy its webhook URL. In SNS create a topic, then add an HTTPS subscription with that URL as the endpoint. Edit each alarm's actions: add the topic for the 'In alarm' state and again for the 'OK' state. Save and force a test alarm. *When:* Routing CloudWatch alarms into an on-call or incident product so breaches and recoveries are both tracked.
- **Log forwarding with a vendor Lambda and subscription filter** — 1) In the log tool create a source for the CloudWatch platform and copy its source token. 2) Lambda: create a function from scratch on Node.js 18 and x86_64, upload the vendor-provided zip, and set an environment variable holding the token (key shown as better_stack_source_token; exact casing not confirmed). 3) In CloudWatch Logs, select a log group, Actions > Subscription filters > Create Lambda subscription filter. Choose the function, log format JSON, and a filter name. 4) Check in the vendor's Live Tail. *When:* Correlating CloudWatch logs with telemetry in a separate log store or UI.
- **Synthetic endpoint canary** — CloudWatch > Application Signals > Synthetics canaries > Create canary. Give a lowercase name, the endpoint URL, and optionally screenshots. Keep the default script, which loads the URL and checks for a 200 response, or edit it to follow a real user path. Choose continuous, a cron schedule, or run once, and start immediately. *When:* Detecting outages or broken endpoints from outside the system before users report them.
