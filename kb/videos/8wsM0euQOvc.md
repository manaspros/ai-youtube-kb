> AI LABS sorts Claude Code agent loops into five types (stateless, learning, multi-agent review, verification, workflow-improvement) with setup steps; anecdotal, with a sponsor segment.

## Summary
The AI LABS team argues that agent loops only waste tokens when the wrong loop type is used for the job. They describe the loops they run on coding work: a stateless loop (the goal command and the Ralph loop) that stops when the agent says it is done, a learning loop that repeatedly improves a reusable skill and records lessons in a learning.md file, a multi-agent review loop run by an orchestrate command with four specialist critics, and a verification loop where an implementer is scored by a read-only reviewer. A workflow-improvement loop adds a process-optimizer agent that critiques the run itself, not just one skill. Each section gives the commands and file conventions they use and when each type fits. Tests and rubrics recur as the mechanism for deciding that work is finished. A mid-video sponsor segment for Minimax M3 makes unverified claims. The evidence is anecdotal, with no benchmarks or measured token costs.

## Key ideas
- **Loop type should match the job. Token blowup comes from using the wrong loop type, not from loops themselves.** — The speaker frames loop engineering as moving from writing prompts to building a system that writes the loop, and says the cost problem is a mismatch between loop and task. ([0:00](https://youtu.be/8wsM0euQOvc?t=0))
- **Stateless loops hold no memory or self-improvement. The goal command and the Ralph loop are examples, and they stop when the agent decides it is done.** — In the earlier video the speaker split loops into deterministic (outcome known, agent can check itself) and non-deterministic (no solid check). This video names the stateless loop as the simplest building block. ([1:06](https://youtu.be/8wsM0euQOvc?t=66))
- **Stateless loops only work well when completion can be checked concretely, such as with tests written before the feature.** — After the main agent claims done, a smaller model (Haiku in Claude Code) checks the work against the prompt's requirements and re-prompts if something is missing. The speaker calls out the weakness: the loop relies entirely on model judgment with no standard to measure against. ([2:12](https://youtu.be/8wsM0euQOvc?t=132))
- **Ask the agent to save every working version so it can roll back when autonomous work breaks the app.** — The speaker recommends one line in CLAUDE.md telling the agent to save each working version. Rollback then replaces trying to undo changes from memory. ([2:12](https://youtu.be/8wsM0euQOvc?t=132))
- **A learning loop improves a reusable skill across rounds and keeps a lesson record inside the skill.** — Each round the skill improver runs the skill, tests it across areas, and makes changes. The loop repeats until no improvements are left. The speaker says the same pattern works for any repeated workflow. ([4:54](https://youtu.be/8wsM0euQOvc?t=294))
- **Measure a skill's impact by running the task with and without it, and keep the results in a learning.md journal.** — Each round launches a separate background Claude session that runs the task twice, once with the skill and once without. learning.md records what was tried, both results, and the lessons across rounds. It lives inside the skill directory. ([6:22](https://youtu.be/8wsM0euQOvc?t=382))
- **Split review across perspectives, using separate agents for factual, domain, safety and style, coordinated by an orchestrator that runs multiple rounds.** — The four agents are a factual checker with web search, a domain-relevance checker, a safety critic (sensitive content, security, policy), and a style critic. The orchestrator is chosen over a direct agent-team setup because one agent must hold context across rounds. ([7:49](https://youtu.be/8wsM0euQOvc?t=469))
- **Verification loops pair an implementer with a scorer and are costly. Only use the dynamic-workflow version on a mature, large app.** — The implementer reads a PRD and builds. A read-only thermonuclear code reviewer returns a score and writes findings to a JSON file. The dynamic workflow fans review out to many sub-agents, which takes a long time and many tokens. The speaker suggests a plain reviewer agent as the cheaper option. ([9:17](https://youtu.be/8wsM0euQOvc?t=557))
- **A workflow-improvement loop improves the process itself, not one skill. A process optimizer agent reviews each run and drops steps that are not needed.** — Three agents run under an iterate command: a builder that delivers one requirement per run, a scorer that grades against a rubric out of 100 and logs scores to JSON, and a process optimizer that suggests changes to the workflow. The iterate all variant implements the entire app in parts inside one workflow. ([11:26](https://youtu.be/8wsM0euQOvc?t=686))

## Techniques
- **Goal-command loop with tests as the acceptance criterion** — Write the tests for a feature before asking Claude to build it. Then run the goal command with a description such as getting the feature to pass all tests. The agent writes code, runs tests, and keeps going until they pass, then marks the goal complete. A Haiku check re-prompts the agent if the requirements are not fully met. *When:* Features whose requirements can be checked concretely. Weak fit when there is no hard standard for done.
- **Save-every-working-version rule in CLAUDE.md** — Add one line to CLAUDE.md telling the agent to save every working version. If later changes break the app, roll back to the last working version and continue from it. *When:* Any long autonomous run where the agent may break working code.
- **Skill-improvement loop (learning loop)** — Create a command, named skill loop in the video, that calls a skill-improver agent repeatedly until no improvements remain. The improver assesses skill quality, tests across areas, and watches for issues. Each round: run checks after changes, start a background Claude session with the prompt and no permission prompts, run the task with and without the skill, make the changes, and append results and lessons to learning.md inside the skill folder. *When:* A skill that is reused often and needs evidence that it works and what changed.
- **Multi-agent review loop with an orchestrator** — Create four agents: factual correctness (with web search), domain relevance, safety critic (sensitive content, security, policy), and style critic. Write an orchestrate command with instructions to spin up all four each round, collect their feedback, and coordinate. The main agent applies all fixes from round N, then respawns all four for round N+1. *When:* Reviews that span several dimensions where one agent would miss blind spots. Use the orchestrator when agents need shared context across rounds. Use the agent-team workflow from an earlier video when agents should talk directly.
- **Implementer vs. scorer verification loop** — Create an implementer agent that reads the PRD and builds the features, and a read-only reviewer agent with no edit tools that returns a score. A review loop command starts round one by understanding the app's goal and running a thermonuclear review. Findings go to a JSON file, the implementer fixes them, and the loop repeats until the score is high enough. *When:* A mature app that needs a thorough review. For cost, prefer a normal reviewer agent over the dynamic-workflow version.
- **Workflow-improvement loop with a process optimizer** — Create an iterate command that orchestrates three agents: a builder that delivers one requirement per run, a scorer that grades against a rubric out of 100 and logs each round to a JSON file, and a process optimizer that reviews the conversation and proposes workflow changes. Run iterate all to build the whole app in parts inside one workflow. *When:* When you want the workflow itself tested and refined, and each step validated as necessary.
