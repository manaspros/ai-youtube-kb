> Imad Touil (QuantumBlack) argues org know-how should live in governed agent skills: a central registry with owners, versions, access control and evals. Ungoverned skills bring duplication, quality decay, security risk and wasted tokens.

## Summary
Touil describes an agentic software stack with two loops: an inner coding-agent harness (context, tools/MCP, memory, skills) and an outer workflow loop (skills, subagents, MCP servers, hooks), supported by enablement components such as sandboxes, MCP and model gateways, a knowledge graph and a workflow marketplace. He argues that most real know-how sits at the skills level, and that skills should be designed like microservices: reusable, modular, specialized, composable, consistent and cheap on context via progressive disclosure. Without governance he expects four failures: duplication, quality decay, no discoverability or ownership, and security/permission gaps (prompt injection in skill scripts, sensitive business logic). His proposed fix is a centralized skills platform with a searchable metadata catalog, an MCP server and CLI to pull skills, dependencies, versioning and lifecycle, access control, and evaluation/observability, governed by domain owners such as architects, engineering, infra and cyber leads. He illustrates the payoff with a simulation of 15 teams over six months, which is illustrative rather than measured data. He closes by pointing to skills registries, static skill tests against Anthropic's best practices, and auto-evolving skills with guardrails as next steps. The talk is conceptual, with no real benchmark numbers beyond a qualitative SkillsBench reference.

## Key ideas
- **Agentic stack has two loops: an inner coding harness and an outer workflow loop** — The inner loop holds the context manager, tools/MCP, memory/state and skills. The outer loop holds workflows, which combine skills, subagents, MCP servers and hooks. Enablement sits underneath: sandbox, MCP gateway, model gateway, knowledge graph (IT systems, code, skills registry) and a workflow marketplace. Workflows are described as harness blueprints that shape the coding harness at runtime. ([1:14](https://youtu.be/M05vON8i0aI?t=74))
- **Real delivery is far more than specify, plan, tasks, implement** — He says the common four-step coding-agent loop covers only one product increment. Full lifecycles add product strategy, market research, discovery, data product delivery, platform/ops and incident handling. Organizations also run many different SDLCs (mobile, internal, customer-facing), so one generic workflow does not fit all. ([2:12](https://youtu.be/M05vON8i0aI?t=132))
- **Skills hold the know-how, so skill structure decides whether a workflow is deterministic** — He argues hooks, MCP servers and subagents are commodity pieces, and MCP servers are often supplied by vendors the org does not own. Subagents mainly limit context use. Without well-structured skills, the workflow is not deterministic. ([6:11](https://youtu.be/M05vON8i0aI?t=371))
- **Design skills like microservices: modular, specialized, composable, consistent, cheap** — Skills should be discoverable, portable across workflows and harnesses (he says the shared open standard means a Claude Code skill should work in Cursor), and specialized to one task rather than a monolith. Composition avoids duplication and conflicts. Progressive disclosure loads only the skills needed for the current step, which cuts token use. ([8:48](https://youtu.be/M05vON8i0aI?t=528))
- **Regulation as a composed skill catalog, pulled at runtime into a review workflow** — Example: a data retention policy skill plus disclosure standards, GDPR rules and filing templates. A regulatory disclosure review workflow pulls them automatically and outputs a stored audit report and a loopback to improve the code base. He presents this as deterministic. ([9:57](https://youtu.be/M05vON8i0aI?t=597))
- **Ungoverned skills create a new class of technical debt** — He lists four risks: duplication across teams that rebuild the same skills, quality decay when skills are not re-tested against new models, no discoverability without governance, and no owner to maintain them. He also flags security (skills can carry prompt injection and scripts) and access control for sensitive skills. ([11:27](https://youtu.be/M05vON8i0aI?t=687))
- **Central platform = searchable catalog + pull path + lifecycle + access control + evals** — Components: a catalog with metadata, an MCP server that searches it, a CLI that pulls skills into the IDE or sandbox, dependency tracking, versioning and lifecycle (agents can detect and pull the latest version), access control, and evaluation/observability. Governance is owned by architects, engineering, infra and cyber leads per domain. He compares this to a Backstage-style IDP service catalog. ([13:43](https://youtu.be/M05vON8i0aI?t=823))
- **Simulation suggests governed skills reduce cost and vibe-coding loops, but is illustrative only** — He simulates 15 teams of 5 to 12 people over six months, tracking skills per engineer, average daily skill pulls, duplication ratio and quality/security ratio. Ungoverned teams show high cost even when productivity is medium. Governed teams converge on shared skills. The numbers are a model he built, not observed data. ([15:07](https://youtu.be/M05vON8i0aI?t=907))
- **Next steps: registries, static skill tests, guarded auto-evolution** — He recommends a skills registry (likely via existing IDP tooling), static tests of skills against Anthropic's best practices (invocation and structure) as the easiest evaluation step, and warns that auto-evolving skill loops need governance guardrails before they run. ([18:54](https://youtu.be/M05vON8i0aI?t=1134))

## Techniques
- **Skill catalog with metadata and an MCP search front end** — Publish skills to a central catalog with owner, version, dependencies and access rules. Expose search through an MCP server and pull skills into IDE or sandbox with a CLI. *When:* When several teams build similar skills and need discovery, ownership and version tracking.
- **Microservice-style skill design** — Keep each skill to one task, make skills composable so they do not duplicate or conflict, and keep their behaviour deterministic and consistent. *When:* When building a skill library that will be shared across workflows and harnesses.
- **Progressive disclosure of skills** — Load only the skills relevant to the current step instead of putting all know-how in context. *When:* When context or token cost is growing with the number of skills or instructions.
- **Runtime composition of regulatory skills into a review workflow** — Keep policy, standard and template skills in a catalog. A workflow pulls the relevant ones on each run and writes a stored audit report with findings and a loopback to the code base. *When:* For compliance checks (data retention, privacy regulation) that must be repeatable and auditable.
- **Static skill tests before any evaluation** — Check that each skill is well structured and invoked as intended, measured against the vendor's published best practices, before running heavier quality evals. *When:* As the first quality gate for skills in a registry.
- **Individual-to-team-to-platform promotion path** — Engineers create, test and improve skills locally, share them with the team, then publish to the central platform. Improvements flow back the same way. *When:* When rolling skills out across an organization without a big-bang governance project.

## Hot takes
- Skills are the unit of organizational know-how and need a registry with owners, like a service catalog.
- Auto-evolving skill loops are the current hype, and they are unsafe without governance guardrails.
- Ungoverned skill creation burns tokens, slows delivery and degrades quality and security.
