> AI LABS hands-on test of Moonshot's Kimi K2.5: open-weight, not open-source; agent-swarm migration was not faster on a large codebase, while a Notion-clone-from-video test worked after one follow-up prompt.

## Summary
The AI LABS team tests the two claims Moonshot makes for Kimi K2.5: that it was trained to orchestrate swarms of up to 100 sub-agents, and that it can turn a visual or video input into working UI. The presenter first argues that the model is open-weight rather than open-source, since only the weights are released. He then explains the mixture-of-experts design (1T total parameters, 32B active) as the reason for its speed and cost. In a migration test with the Kimi Code CLI, the agent converted a ShadCN project to Material UI using about five parallel agents, but it took around 15 minutes and was not faster than a single agent would be. The CLI also spawned more agents than expected, which the team attributed to a bug. The agent cleaned up unused components and dependencies and used about 25% of the context window. In a second test, a short screen recording of Notion was passed in as a file path, and the agent produced a functional-looking clone, though slash commands only worked after a follow-up prompt. The video is a single 9-minute team test with a sponsored segment, not a benchmark.

## Key ideas
- **Open-weight is not open-source: Kimi K2.5 releases only final weights, not training code or training data, so it fails the Open Source Initiative definition.** — The presenter's definition: open source means code, data and methods are public so anyone can inspect, modify and distribute. Open-weight means you can fine-tune or deploy the weights only. ([0:00](https://youtu.be/D4ICNmfXmwI?t=0))
- **Moonshot claims Kimi K2.5 was trained from the ground up to orchestrate agent swarms of up to 100 sub-agents, with RL rewarding how well work is parallelized.** — The presenter frames the claim as something worth testing, because the creators themselves made it, not third-party users. ([0:00](https://youtu.be/D4ICNmfXmwI?t=0))
- **Speed and cost come from mixture-of-experts sparsity: 1T total parameters but only 32B activated per query.** — The architecture is described as similar to DeepSeek's MoE design. The presenter says the total-vs-active gap is the main reason the model is cheap and fast. ([1:17](https://youtu.be/D4ICNmfXmwI?t=77))
- **The swarm is a learned orchestrator, not just prompting: the model is rewarded for creating sub-agents, assigning tasks and coordinating results, across up to 1500 coordinated steps.** — The orchestrator has built-in tools to create sub-agents, assign tasks and collect their results before it assembles a final answer. Compared with Claude, which also spawns sub-agents, the difference claimed is that parallelization is part of the training reward. ([2:45](https://youtu.be/D4ICNmfXmwI?t=165))
- **Vendor claims are an 80% cut in end-to-end runtime and better results than Opus 4.5 on long-horizon benchmarks. These come from Moonshot's internal evaluations and were not checked by the team.** — The presenter reports the vendor's comparison set (Opus 4.5 and Kimi without the swarm) as stated claims only. ([4:04](https://youtu.be/D4ICNmfXmwI?t=244))
- **In a real migration, the swarm was not faster on a large codebase. Five agents took about 15 minutes, and the presenter concluded that parallel agents do not always win.** — The team had expected parallel page-level work to be faster. The CLI also spawned more agents than expected, which the presenter said was a CLI bug. ([4:04](https://youtu.be/D4ICNmfXmwI?t=244))
- **The agent finished the migration with its own cleanup pass, removing unused components and ShadCN dependencies, including test files, and used only about 25% of the context window.** — Most agents leave dependencies behind, which the presenter flagged as a common failure mode. The UI was otherwise nearly identical, except the hero section was stacked vertically. ([5:32](https://youtu.be/D4ICNmfXmwI?t=332))
- **Kimi's vision was claimed to be trained jointly with text rather than added afterwards. Video input can be used to generate code, which the team tested by cloning a Notion screen recording.** — Practical caveat from the team: images and video fill the context window fast, so large media files need care. ([6:37](https://youtu.be/D4ICNmfXmwI?t=397))
- **The Notion clone was accurate in layout and features, but slash commands did not work at first. One reiteration prompt led the agent to self-iterate, check results and fix the feature.** — The presenter concluded the claims largely held up, and that Kimi's plans may be a cheaper alternative to Claude Code, which he did not measure. ([8:04](https://youtu.be/D4ICNmfXmwI?t=484))

## Techniques
- **Parallel per-group migration with a sub-agent per page group** — Give the agent a single instruction that names the migration (ShadCN to Material UI across the whole project) and tell it to use agents for each page. The agent explores the directory, writes a to-do list of every page to convert, groups similar pages (e.g. signup, login and forgot-password as auth), and spawns one agent per group. Check the number of agents it spawns, since the CLI spawned more than expected. *When:* Large mechanical refactors with independent units (pages, routes, components). Expect the speedup to be unreliable on big codebases; measure wall-clock time against a single-agent run before assuming it is faster.
- **Post-migration cleanup pass** — After the main change, ask the agent to remove components no longer imported, uninstall the replaced library's dependencies (ShadCN here, including test files), update the remaining dependencies and validate the build and tests. *When:* Any library swap, where agents tend to leave unused components and dependencies behind and bloat the project.
- **Video-as-input UI cloning** — Record a short screen capture of the target UI and keep it small (the Kimi docs state a 40 MB video limit). Pass the file path in the prompt and ask for a clone of the website shown. Do not describe the recording; the agent identified it as a Notion-like interface from the video alone and used its read-media-file tool to analyze it. *When:* Reproducing an existing UI from a recording when no design file or source is available. Watch the context budget, since large videos or images can bloat the context window quickly.
- **Iterate on broken features with a follow-up prompt** — When the first pass has gaps (here, slash commands did not work), name the broken behavior in one follow-up prompt. The agent then implemented fixes, checked the results and kept iterating without further prompts. *When:* Interactive UI clones where the first pass gets the layout right but misses behaviors. One targeted reiteration was enough in this test.

## Hot takes
- Open-weight is not open-source: only final weights are released, with no training code or data.
- The swarm was not faster on a large codebase in this test, which undercuts the parallel-agent pitch.
- Vendor benchmark claims (80% runtime cut, beating Opus 4.5) are repeated but not verified. The team's own test was one migration and one clone.
- Sponsored segment (Opera Neon) at about 1:17 to 2:45, so quality is capped at 2 per the rules. The hands-on substance is still useful.
- The 'cheaper than Claude Code' pricing claim is asserted, not measured.
