> OpenAI's hands-on Codex workshop walks through context, computer use, long-running goals, subagents, hooks and automations, then shows the app server for embedding Codex in your own product.

## Summary
Two OpenAI developer-experience engineers run a live "cooking" workshop on Codex, structured as six steps: give context, build, take action with computer use, collaborate on long tasks, make loops repeatable, and embed Codex everywhere. Most of the talk is live demos, and much of it promotes product features (Codex app, remote mobile, plugins, Sites, Chronicle), so the signal sits in the patterns rather than the product tour. The strongest concrete material is about long-running work: goals with verifiable success criteria, progress dashboards, side threads for unblocking, subagents versus visible thread handoffs, and hooks for deterministic checkpoints. The talk ends with heartbeat and scheduled automations that spawn worktree threads and PRs, and with the App Server protocol as an open-source base for custom UIs. Speaker claims about native compaction and multi-hour runs are unbenchmarked and come from demos.

## Key ideas
- **Context is the first ingredient. Plugins (Slack, Gmail, Linear), app screenshots that carry embedded text, dictation, AGENTS.md and opt-in memory all feed the agent before it builds.** — The speakers argue that most of the leverage comes from giving the agent personal and team context (conversations, docs, tickets), not from clever prompts. They describe the 'have you asked Codex' habit as the entry point. ([5:42](https://youtu.be/FwiS44-xyYw?t=342))
- **Verifiable success criteria are what make a long goal work. Vague criteria lead to technically-compliant but wrong results.** — The speaker says to write criteria that can be checked. The agent evaluates itself against them every turn and decides whether to keep going. He compares an unclear goal to a 'monkey's paw' outcome. ([43:52](https://youtu.be/FwiS44-xyYw?t=2632))
- **Long runs need external visibility. The agent writes a goals file and a progress dashboard HTML so the human can see what is done, active and blocked.** — For a 7-hour port, the agent split the work into milestone goals in a goals file and built a progress dashboard. It also spawned separate threads at each milestone for code review and a goal audit that nudges the main thread if it drifts. ([31:48](https://youtu.be/FwiS44-xyYw?t=1908))
- **Subagents and thread-to-thread handoff serve different audiences. Subagents hide work from the user to keep context separate. Handoffs keep work visible when the human wants to watch or steer.** — The rule of thumb: if the delegation only needs to be visible to the model, use a subagent. If the human needs to see or intervene, use a thread. Subagents can be customized with their own instructions and model size, such as a light model for a fast reviewer. ([45:13](https://youtu.be/FwiS44-xyYw?t=2713))
- **Side threads are a way to unblock and steer a running agent. They are ephemeral, so anything that must persist has to be written back to the main thread.** — The speaker asks a side thread for a status summary, blockers and next steps, then has it update the main thread. He also notes that blocked tasks surface in the UI and can be answered from a side chat. Credentials are passed through a secure path rather than pasted into chat. ([34:33](https://youtu.be/FwiS44-xyYw?t=2073))
- **Hooks give deterministic checkpoints where a model-based instruction is not enough. Examples are secret scanning before a prompt leaves, allowlist checks before a tool call, and tidy-up scripts at end of turn.** — Hooks are configured in config.toml in the Codex home directory. The speaker's advice is to give the agent as many boundaries as possible and let it work within them, with hooks enforcing the boundaries that matter. ([47:46](https://youtu.be/FwiS44-xyYw?t=2866))
- **Automations turn one-off runs into a loop. A heartbeat automation keeps re-checking inside a thread until a condition is met, and a scheduled automation can spawn new threads that go all the way to a PR.** — Heartbeat example: poll a provisioned droplet every five minutes until ready. Scheduled example: every 30 minutes, classify Slack feedback, and for bug fixes open a worktree thread, make a PR, and request review. The speaker frames this as an early software factory. ([51:28](https://youtu.be/FwiS44-xyYw?t=3088))

## Techniques
- **Verifiable goal with milestone files** — Give a long task a verifiable completion criterion. Ask the agent to split it into a series of goals in a goals markdown file and to build a progress dashboard HTML. Use the 'define goal' skill from the OpenAI skills repo. *When:* Multi-hour greenfield builds, migrations, large refactors and experiment loops where the human will not watch every step.
- **Milestone-triggered review and goal-audit threads** — Have the main agent spawn separate threads at each milestone to run code review and a goal audit. The audit checks whether the main thread has drifted from the original plan and nudges it back. *When:* Long runs where the plan may drift and you need an independent check without interrupting the main thread.
- **Side-thread unblock and status query** — While a run is going, open a side thread on the same project and ask for what was done, what is next and what is blocked. Then tell it to push the fix or decision back to the main thread. Write any lasting decision into the main thread. *When:* Runs that stall on a credential, an approval or a wrong direction, especially when the human is away from the keyboard.
- **Subagent vs thread handoff split** — Use subagents for focused delegation the human does not need to see, with custom instructions and model size per role. Use a visible thread for work the human wants to inspect or steer. Tell agents in AGENTS.md to check with a named role, such as a creative director thread, before finishing. *When:* Choosing between hidden context separation and visible multi-agent coordination.
- **Hook-based deterministic guardrails** — Configure hooks in config.toml to run scripts at fixed points: before a prompt is sent (secret scan), before a tool call (whitelist check), and at turn end (linter, custom validation, repo tidy-up). *When:* Checks that must run every time, where a model instruction in AGENTS.md is not reliable enough.
- **Heartbeat automation for external waits** — Create an in-thread automation with a timer that re-checks a condition (for example, is the infrastructure ready) and takes the next step when it passes. *When:* Waiting on a provisioning step, a deploy pipeline or an event that takes minutes to hours.
- **Scheduled triage that spawns worktree threads to PRs** — Run a scheduled automation that reads a feedback channel, sorts items into categories, and for safe bug fixes opens a worktree thread that makes a PR and requests human review. Add a follow-up reminder if approval does not arrive. *When:* High-volume feedback where routine fixes can be drafted for review without manual triage.
- **Choosing a control surface: computer use vs Chrome extension vs in-app browser** — Use computer use for desktop and legacy apps with no API, running in the background without taking the cursor on macOS. Use the Chrome extension when the agent needs the user's signed-in session. Use the in-app browser for local web app layout and interaction testing. *When:* Deciding how an agent should drive a UI, based on whether auth state, legacy software or deep rendering inspection matters.
- **Embedding via the App Server protocol** — Build a custom UI or product on the open-source App Server, which exposes the same harness used by the Codex app, CLI and VS Code extension, including tool calls, plugins and compaction. Computer use and other local-only features are not included. *When:* Building a product that wraps Codex or a unified layer over several agent providers.

## Hot takes
- Prompt engineering in the magic-phrase sense is gone; clarity and context are what matter.
- A verifiable success criterion is the single most important input to a long-running goal.
- Everyone is becoming a manager of parallel agent threads.
- The goal is to take the human out of routine loops, such as API key setup, and build the machine that builds the machine.
- Compaction is solved enough that long threads spanning many compactions are reliable (speaker and quoted users).
