> Uber's Uber Eats image pipeline (routing, enhancement, publish QA) and how they keep it aligned with human labels through offline evals, auto-tuning and a diagnoser that closes the production feedback loop.

## Summary
Uber's computer vision team describes a production multimodal agent that improves merchant food photos on Uber Eats. The flow is an image-understanding and routing agent, then an enhancement agent that loops with a QA gate, then a final publish-ready QA. Every run is logged as one flat JSON trace so both engineers and non-engineers can inspect cases and aggregate them. Offline, human labels on a representative golden set are the source of truth, with recall as the guardrail for the router. Online, sampled production outputs are re-labelled by humans, a diagnosis agent localises mismatches, and a reflect-and-synthesize prompt optimizer auto-tunes the config, which is benchmarked and registered without a human in the loop. Enhancement is scored with pass@K and a pairwise yes/no/unsure judge whose criteria were agreed with product, design, policy and legal. A higher-level diagnoser takes feedback from dogfooding, thumbs up/down and merchant free text and routes it to the agent that needs changing. Changes are checked by replaying flagged examples and then tracked in production by segment, with conversion as a key metric.

## Key ideas
- **Constrain agency with guardrails instead of choosing rules or free agents** — Rule systems are brittle at marketplace scale and unconstrained agents break safety rules. The team aims for a balance: the agent has creative freedom, inside explicit guardrails on safety and authenticity. ([4:11](https://youtu.be/31GUkCBD-Uc?t=251))
- **Start with logging, because you cannot optimise or self-learn without it** — Each run is one flat JSON structure covering all agents in the end-to-end flow. Technical and non-technical staff can inspect single cases or roll them up in aggregate. ([6:39](https://youtu.be/31GUkCBD-Uc?t=399))
- **Treat the router as a classifier and pick its guardrail metric by the cost of each error** — The router is scored with a confusion matrix. Recall is the guardrail because a bad image that slips through is costly. A false positive wastes compute and can degrade a good photo. A false negative can make the enhancer hallucinate missing items, such as extra wings, to match the menu text. ([8:03](https://youtu.be/31GUkCBD-Uc?t=483))
- **Offline golden set from human labels with objective guidelines is the reference for shipping** — Samples are chosen to cover cuts such as geography, dish type and image quality. Labelers follow an objective guideline to reduce subjective bias. An agent version ships only when it meets the guardrail metrics on this set. ([8:03](https://youtu.be/31GUkCBD-Uc?t=483))
- **Static offline models drift, so production sampling and auto-tuning keep the system current** — Production data is sampled on a schedule and re-labelled by humans. A diagnosis agent finds where the agent and labels disagree and triggers an auto-tuning pipeline. The new version must pass the golden set before it is registered. The speaker says this loop is config-driven and needs no human in the loop. ([10:41](https://youtu.be/31GUkCBD-Uc?t=641))
- **Auto-tuning is a prompt optimizer built from two sub-agents, reflect and synthesize** — Reflect looks at the mismatches, removes noise and finds systemic issues in the data. Synthesize updates the agent config from that feedback and benchmarks again. Passing versions are registered in a config store that production reads from. Guardrail observability and quick rollback are in place. ([12:08](https://youtu.be/31GUkCBD-Uc?t=728))
- **Score the enhancement loop with pass@K and feed QA rejections back as input** — Each step generates an image-specific prompt, edits the image, and runs a multidimensional QA gate covering plating, faithfulness and colour. A failed output goes back to the prompt generator with the QA feedback. Images that never pass after K iterations are not enhanced, which costs coverage. ([13:32](https://youtu.be/31GUkCBD-Uc?t=812))
- **Judge enhancement with pairwise comparison, and bake in criteria agreed with product, design, policy and legal** — The judge compares input and output and returns yes, no or unsure. Criteria include faithfulness, completeness, naturalness and realism. Recurring failures are added shrimp, removed sauce, a plate hiding the dish, and a wonton count that cannot be verified. Reward hacking shows up as the editor becoming overly conservative after overcorrecting. ([14:59](https://youtu.be/31GUkCBD-Uc?t=899))
- **Use redundant final QA, Swiss-cheese style, and treat its catches as upstream signal** — A publish-ready gate runs policy and quality checks after the earlier QA. It is deliberately redundant. It also flags issues that should have been caught earlier, so each failure can be traced back to the step that missed it. ([17:46](https://youtu.be/31GUkCBD-Uc?t=1066))
- **A diagnoser generalises feedback from many sources and routes each signal to the agent that needs to change** — Inputs include internal dogfooding thumbs up/down, merchant and design-team free-text feedback, and production signals. The diagnoser decides which agent or agents to tune. Before a config is pushed, flagged good and bad examples are replayed and the metrics are benchmarked. ([18:48](https://youtu.be/31GUkCBD-Uc?t=1128))
- **Judge changes in production by segment, not only in aggregate** — Production data can be sliced by geography, device type and dish type, so improvements and regressions can be seen per segment and tuned per segment. Conversion (add-to-cart and order completion) is the example marketplace metric. ([20:11](https://youtu.be/31GUkCBD-Uc?t=1211))

## Techniques
- **Flat per-run JSON trace across the whole agent chain** — Log every agent step (description, structured output, router decision, edit, QA verdict) in one flat structure per run, so one record can be inspected or aggregated. *When:* Before building any evals or self-learning loop, and so that non-engineers can diagnose cases.
- **Router as a classifier scored by a confusion matrix, with an N-by-N extension** — Compare the router's decisions with labels in a confusion matrix. Choose the guardrail metric by error cost (recall here). For multi-branch routing, use an N-by-N matrix to see correct routing per branch. *When:* When an agent routes inputs to a skip path or to one of several model tiers (for example, a cheaper, lower-latency model).
- **Golden human-label set plus ship gate** — Build a representative labelled set across slices, using an objective guideline to reduce labeller bias. Ship a new agent version only when it passes the guardrail metrics on that set. *When:* Offline, as the first model release gate, and again for every candidate config.
- **Production drift loop: sample, re-label, diagnose, tune, benchmark, register** — Sample production at a fixed cadence and send it to human labelers. Compare agent outputs with labels. A diagnosis agent localises mismatches and writes config changes, which are benchmarked on the golden set before a new version is registered in a config store. *When:* When the static offline model is no longer enough and the system must keep adapting to drift without a human in the loop.
- **Reflect-and-synthesize prompt optimizer** — One sub-agent reflects on the mismatched cases, removing noise and naming systemic issues. A second sub-agent rewrites the agent config from that feedback, and the result is benchmarked again. *When:* To auto-tune any agent's prompt or config from labelled mismatches.
- **Generate-edit-QA loop scored with pass@K** — Generate an image-specific edit prompt, edit, run a multidimensional QA gate, and pass the rejection reason back to the generator. Report the pass rate at each iteration K. Images that do not pass by K are not published. *When:* For iterative generation or editing where QA feedback can be used to retry, and where the budget caps retries.
- **Pairwise judge with yes/no/unsure and product-agreed criteria** — Give the judge the input and output and ask whether the output is better on defined criteria (faithful, complete, natural, realistic, plus policy-driven ones). Use yes/no/unsure rather than a forced choice. *When:* When absolute scores are hard to calibrate and a clear better-or-worse call is needed, especially with policy criteria.
- **Redundant Swiss-cheese final gate** — Add a final holistic QA and policy gate after earlier QA on purpose. Record the failures it catches as upstream gaps. *When:* When a single bad output reaching production is costly and each layer has blind spots.
- **Diagnoser as a routing layer over all feedback** — Feed thumbs, free-text, dogfooding and production signals to a diagnoser that decides which agent's config to optimise, one or many. *When:* When a system has several agents and several feedback sources, so the tuning target is not known in advance.
- **Replay flagged examples before releasing a config** — Replay the examples that were flagged as good or bad through the new config version, benchmark the metrics, then push. *When:* Before every production config change, as a regression check.
- **Per-segment production metrics** — Slice online metrics by geography, device, dish type and so on. Tune for segments that are weak, and watch for regressions in any single segment. *When:* When aggregate metrics can hide segment-level regressions at large scale.

## Hot takes
- Logging is the first thing to build, because without it there is nothing to optimise and no self-learning loop is possible.
- A static offline model will not hold up in production. The loop that re-labels and re-tunes production data is what keeps the system working.
- Consumers distrust AI-generated food photos, so authenticity is a hard constraint on image editing, not a nice-to-have.
- Reward hacking appears in image editing: after an overly creative edit fails QA, the agent overcorrects into a generic, conservative result that barely changes the image.
