> Walkthrough of Google's EGM, a spec-first workflow where zero-context goldfish sub-agents critique a plan before any code is written, with install, bootstrap, review and drift steps for Claude Code. A sponsor segment caps quality.

## Summary
The presenters introduce EGM (Elephant Goldfish Model), a free Google-developed, spec-driven method for planning a feature in full before an agent builds it. The main agent (the elephant) holds project context and writes the plan, while sub-agents (the goldfish) review it with zero chat context so they cannot simply agree with the author. The human makes the final calls on the reviewers' notes. The video demonstrates installing it into Claude Code, where the installer wrote a CLAUDE.md line that the presenters found wrong and had the agent correct after testing. It then walks through bootstrap (per-folder README generation), brainstorm (six goldfish reviewers producing a concept brief), draft (a design doc saved to docs/designs), a five-round review, and a drift report that found a real rule violation in their demo app. The presenters say the method is worth it only for large, costly features, not small fixes. Evidence is one demo on a fashion app, and the video includes a sponsor segment.

## Key ideas
- **EGM is Google's spec-driven method: write a complete plan first, then have the agent build from it, so gaps surface before any code exists.** — Presented as free, hosted on Google's GitHub, and attributed to an article by Dave Rensen. It is contrasted with ordinary plan mode, which usually produces a plan that misses issues found later and needs revision. ([0:00](https://youtu.be/xxf6D9jynFw?t=0))
- **Two agent roles: the elephant holds full project context and writes the plan; the goldfish are sub-agents with zero context that only see the plan and the code.** — Goldfish never see the planning chat, so earlier discussion cannot bias them. Each goldfish reviews from a different angle: a simpler alternative or existing app feature, a newcomer reading the plan cold, scale and concurrent-use failures, and whether a model could implement it without guessing. ([1:27](https://youtu.be/xxf6D9jynFw?t=87))
- **Isolation is the point: in plan mode the critic shares the author's chat, so it tends to agree with its own earlier reasoning.** — The presenters cite Google's view that models stick to their own wrong idea and tell the user what they want to hear, so the reviewer is deliberately kept out of the chat. ([2:55](https://youtu.be/xxf6D9jynFw?t=175))
- **A human is the third role: reviewers deliberately produce many notes, and the user keeps what is useful.** — Review checklists are written rules for what a good plan contains. One orchestrating sub-agent fans out to other sub-agents and returns a single merged report, which keeps the main agent's context from filling with raw reports. ([3:59](https://youtu.be/xxf6D9jynFw?t=239))
- **The installer wrote a CLAUDE.md line claiming Claude Code sub-agents cannot start sub-agents. The presenters found it wrong, the agent tested it, and corrected the line.** — The presenters say nothing in the repo told the agent to write that line. Newer Claude Code allows nested sub-agents, which the review design relies on. They advise checking CLAUDE.md after install. ([5:27](https://youtu.be/xxf6D9jynFw?t=327))
- **Bootstrap writes a README per code folder so the elephant understands the existing app. READMEs are written for humans, so agents will not read them by default.** — In the demo, bootstrap wrote 28 new READMEs and updated the main README. Folders without code get none. The presenters list three fixes for the agent-visibility gap, covered in the techniques. ([6:55](https://youtu.be/xxf6D9jynFw?t=415))
- **The workflow runs as separate commands: brainstorm produces a concept brief after six goldfish review, draft produces a design doc with per-section approval, review runs five rounds, and drift compares code to READMEs.** — Brainstorm asks questions until the problem is clear, then gives a best-guess approach and offers goldfish review. Draft writes one section at a time and waits for approval. The final plan is saved in docs/designs and is what a later build session should reference. ([9:50](https://youtu.be/xxf6D9jynFw?t=590))
- **The review stage uses five numbered rounds, each checking the plan one way, with a report per round and a status change at the end.** — The first sub-agent is a zoom-out check for easier existing approaches. Rounds are numbered 5 to 9. After the last round the plan status moves from in review to proposed. ([12:45](https://youtu.be/xxf6D9jynFw?t=765))
- **The drift report caught a real bug: the app let shop owners delete sold products, though the rule says sold products can only be hidden.** — Drift checks the built app against the per-folder READMEs and reports mismatches. The user then decides which to fix. The presenters say competing tools mostly check one feature right after it is built, while this one re-checks the whole app. ([14:12](https://youtu.be/xxf6D9jynFw?t=852))
- **Use the heavy process only for large features where a mistake is costly, not for small changes an agent can finish in one pass.** — The presenters say planning and reviewing slow down small fixes. They also mention a simpler, less in-depth version of the workflow that is available. ([15:40](https://youtu.be/xxf6D9jynFw?t=940))

## Techniques
- **Isolated-context plan critique** — Run critics as sub-agents that receive only the plan file and the code, never the planning conversation. Do not let the reviewer share the author's chat history. *When:* Before building any large or costly feature, when the plan was written by the same agent that has been agreeing with you.
- **Multi-lens rubric reviewers** — Give each reviewer sub-agent one lens and a written checklist: simpler or existing alternative; cold read by a newcomer; scale and concurrent-use failures; implementable without guessing; and plan structure. Brainstorm review uses six such goldfish. *When:* When a single review pass misses edge cases, and you want findings grouped by angle.
- **Fan-out with a single merged report** — Have one orchestrator sub-agent launch the reviewers and return one combined report, so the main agent context stays small. The user reviews only the merged report. *When:* When many reviewers would otherwise flood the main context.
- **Staged plan authoring with per-section approval** — Run brainstorm (question loop, then best-guess approach, then optional goldfish review, producing a concept brief in the project root), then draft (design draft written one section at a time with approval after each: problem and scope, critical user journeys for tests, technical plan, alternatives considered, step-by-step build plan). Save the result under docs/designs/<feature>.md. *When:* For a feature that needs a written, reviewed spec before a fresh build session.
- **Round-based review gate** — Run review as numbered rounds, each applying one check. After each round write a report and update the plan file, then either proceed or request changes. When all rounds finish, set the plan status from in review to proposed. *When:* To force each class of issue to be checked separately before implementation.
- **Drift check against per-folder docs** — After a build, run the drift report with a scope (for example all folders). It starts sub-agents per app area, compares code to the READMEs, and lists mismatches. You then choose which to fix. *When:* To catch code that has drifted from documented rules, including rule violations such as deleting records that must only be hidden.
- **Make per-folder docs agent-readable** — Use one of three options: (1) add a CLAUDE.md next to each README telling the agent to read the README (AGENTS.md for Codex); (2) re-run bootstrap with the setting that creates CLAUDE.md files from the start; (3) add one line in the root CLAUDE.md telling the agent to read the README of every folder it edits. *When:* After bootstrap, because READMEs are written for humans and agents will not read them unless told to.
- **Verify the installer's CLAUDE.md edits** — After install, check CLAUDE.md for the line claiming sub-agents cannot spawn sub-agents. Test whether nested sub-agents work in your Claude Code version, and ask the agent to correct the line if it does not hold. *When:* Right after installing any tool that edits CLAUDE.md, before relying on nested sub-agent review.
- **Install by agent-specific command or by prompt** — Use the per-agent install command from the repo (it avoids CLAUDE.md conflicts), or paste the word install followed by the repo link into the agent. It creates three folders under the .claude directory (Agents, EGM, Skills). The transcript's caption reads .clawed, which is a misspelling of .claude. *When:* To set up EGM in a project for Claude Code, Codex or another agent.
- **Command sequence** — EGM bootstrap (for more than 15 folders it asks before writing all READMEs), then EGM brainstorm with a feature description, then EGM draft, then the review command (the caption reads view; it runs the five-round review), then EGM drift report (asks which scope to check). Build in a fresh chat from the file in docs/designs. *When:* End-to-end use on an existing app, one step at a time as listed in the GitHub repo.
