> Better Stack walks through Qdrant's open 10B-vector FineWeb benchmark dataset, which ships exact nearest-neighbor ground truth, and reruns a 1M slice against four vector engines. Lesson: test on your own data with brute-force truth.

## Summary
The host argues that vendor vector-DB benchmarks are hard to trust because small datasets hide scale effects and approximate or synthetic ground truth is common. He presents Qdrant's FineWeb dataset: 10 billion documents embedded twice (dense and sparse) with GTE Multilingual Base, 120k queries, and exact top-10,000 ground truth computed by brute force, with the tooling under Apache 2.0. Because he cannot store the full 24.5 TB, he builds a 1M-vector slice, recomputes exact ground truth over that slice, and runs Qdrant, Milvus, Elasticsearch and PGVector in Docker one at a time. He sweeps each engine's search-effort setting across five values and compares latency at matched recall. Elasticsearch is fastest at about 94% recall but tops out near 95%, while Qdrant and Milvus reach 98%. He repeatedly says the results are a vendor-curated, single-run slice and may not hold at 10B scale.

## Key ideas
- **Small vector benchmarks mislead because at about 1M vectors everything fits in RAM, hiding memory pressure, index build time and tail latency that appear at 100M+ scale.** — The earlier Qdrant benchmarks used 1M (DBpedia OpenAI) and 10M (Deep Image 96) vectors. The host argues a 1M test says little about production behavior at much larger scale. ([1:04](https://youtu.be/6Uj6GXIpX9s?t=64))
- **Recall needs exact ground truth, and computing it is the hard part.** — Recall is the share of true nearest neighbors an engine returns. Exact answers require scanning every vector for every query. At 10B vectors and 120k queries this is over 10^15 distance computations, so most benchmarks use approximate ground truth or synthetic random vectors, which lack real clustering structure. ([2:03](https://youtu.be/6Uj6GXIpX9s?t=123))
- **Qdrant's dataset is built to cover realistic query types: dense, sparse and filtered queries over a real web corpus.** — Corpus is FineWeb (10B documents). Each document is embedded twice with GTE Multilingual Base, once dense and once sparse, so hybrid retrieval can be tested on the same data. The 120k queries are 100k dense (MS MARCO), 10k sparse and 10k filtered. Filtered search is singled out as a common failure point that few benchmarks test. ([3:26](https://youtu.be/6Uj6GXIpX9s?t=206))
- **Storing the top 1,000 (or 10,000) exact neighbors per query lets one ground-truth run serve any smaller k.** — Ground truth is sorted best-first to depth 10,000. Top-5 for chatbot retrieval, top-20 for a results page and top-1000 for reranker candidates all come from truncating the same list, so separate exact runs are unnecessary. ([4:33](https://youtu.be/6Uj6GXIpX9s?t=273))
- **The ground truth is verifiable, which makes it a stronger claim than a vendor's benchmark number, even though the benchmark is still vendor-chosen.** — The host says Qdrant picked the corpus, embedding model, queries and harness, so results depend on those choices. Brute-force ground truth has no tuning knobs, so anyone with GPU budget can recompute it and check. The tooling is open source under Apache 2.0. ([5:35](https://youtu.be/6Uj6GXIpX9s?t=335))
- **Published ground truth does not apply to a slice of the dataset, so you must recompute exact truth over the vectors you actually loaded.** — Qdrant's answers come from all 10B documents, so scoring a 1M slice against them looks broken. For slice testing, exact brute force over the loaded slice gives valid recall, but it answers 'does this index find what exhaustive search finds in my data' rather than 'does it match Qdrant's 10B result'. ([6:58](https://youtu.be/6Uj6GXIpX9s?t=418))
- **Use a sweep of search-effort settings and compare latency at matched recall, not one number per engine.** — Each engine has a knob that trades speed for recall. The host measured five settings per engine, producing a recall-vs-latency curve, and asked which engine is faster at the same accuracy. Engines ran one at a time in their own containers with the same loaded vectors and ground truth so they did not compete for CPU. ([9:16](https://youtu.be/6Uj6GXIpX9s?t=556))
- **Elasticsearch was fastest at about 94% recall, but it cannot pass about 95%, while Qdrant and Milvus reach 98%.** — The host calls this a trade-off: Elasticsearch is the fastest way to be roughly right, and Qdrant is the only one of the four that is both fast and most precise. He also notes that Elasticsearch surprised him, since it is usually a keyword engine with vectors added. He cautions that these are million-vector results. ([10:20](https://youtu.be/6Uj6GXIpX9s?t=620))
- **The 1M-slice results may not carry over to 10B, so each team should run the same method on its own corpus.** — The host ends by calling the dataset and toolchain the takeaway, not his numbers. The toolchain covers embedding generation, database loading and load testing, and can be pointed at any corpus. ([11:05](https://youtu.be/6Uj6GXIpX9s?t=665))

## Techniques
- **Exact brute-force ground truth on your own slice** — Load the subset of vectors into the engines under test. Compute exact top-K for each query with a no-index scan over exactly those loaded vectors. Score each engine's approximate results as recall = overlap with true top-K. Do not reuse published ground truth for a subset. *When:* Any retrieval or ANN evaluation on a subset of your corpus, or any time you need recall numbers you can defend.
- **Store deep ground truth and truncate for smaller k** — Compute exact neighbors once to a large depth (the video uses 1,000 to 10,000), store them sorted best-first, then take the first k entries to get ground truth for top-5, top-20, or top-1000 reranking candidate sets. *When:* When one corpus must serve several k values, such as RAG context (small k), result pages (about 20), or a reranker stage (hundreds to thousands).
- **Recall-vs-latency sweep per engine** — For each engine, vary its search-effort parameter over several values (the video uses five). Record recall and latency at each value, then compare engines by latency at a matched recall target (e.g. 94%, 98%) instead of by a single setting. *When:* Choosing between engines or index settings, or comparing against a service-level recall target.
- **Sequential, isolated engine runs over the same loaded data** — Start one engine's container, load the identical vectors, run the same queries against the same ground truth, record results, tear it down, then move to the next. Engines do not share CPU during measurement. *When:* Fair side-by-side benchmarks on a single machine.
- **Benchmark filtered and sparse/hybrid queries separately** — Build separate query sets for filtered search (metadata constraint plus vector similarity), sparse, and dense queries, each with their own exact ground truth. Use dense and sparse embeddings from one model over the same documents so hybrid comparisons change only the retrieval method. *When:* Evaluating hybrid retrieval, or any workload with metadata filters, where engines often differ most.

## Hot takes
- Most vector-DB vendor benchmarks are unreliable because they use small datasets, approximate ground truth, or synthetic vectors.
- Elasticsearch beat three dedicated vector databases on latency at about 94% recall in this single small test (the host calls this surprising).
- A brute-force, parameter-free ground truth on a public dataset is a stronger basis for trust than a vendor's own numbers, but the dataset, embedding model and queries were still chosen by a vendor (Qdrant).
- The 1M-slice results are a single run and may not hold at 10B scale; the host says so repeatedly.
- The 'Most Vector DB Benchmarks Are Wrong' title is more hype than the video supports; the substance is a dataset announcement plus a small, caveated experiment.
