> AI LABS shows how to attach Claude Code hooks (formatter, linter, build, stop-sound) to settings.json, and how to have a general LLM draft per-language hook rules. Mostly a SwiftUI demo with a sponsor segment.

## Summary
The presenter argues that AI-written code needs deterministic checks, not only instructions in a markdown file, and proposes Claude Code hooks for this. He demos a SwiftUI recipe app built from an implement.md task file, run with the dangerously-skip-permissions flag. Hooks on Edit, MultiEdit and Write for .swift files run swift-format, SwiftLint and a terminal build, and failures go back to Claude, which fixes them. A stop hook plays a system sound when Claude finishes. He then describes a pipeline: give ChatGPT a tools.md reference of Claude Code tools and their hook points, have it draft per-language rules, save them to rules.md, and use a slash command from a "claude code rule to hook" repo to generate settings.json hooks, excluding unwanted ones such as git commit and CI. He admits the generated config used an outdated hooks.json format and needed fixing. The sponsor segment and the hype title lower the substance.

## Key ideas
- **Hooks run commands at fixed points in Claude Code's work, so checks happen regardless of whether the model follows instructions. The presenter contrasts this with rules written in a .md file.** — He frames hooks as hardcoded commands rather than suggestions. He also says this means no chance of failure, which overstates it: a hook guarantees the command runs, not that the code is correct. ([0:00](https://youtu.be/ytn0aXK2gzE?t=0))
- **A stop hook can notify you when Claude stops producing output, for example by playing a system sound.** — Demoed by creating hello.md and hearing a sound once Claude finished. Useful for long unattended runs. ([2:01](https://youtu.be/ytn0aXK2gzE?t=121))
- **Hooks can be scoped to file types, so a formatter or linter runs only on the files it applies to.** — The presenter's hooks fire only for Edit, MultiEdit or Write calls that touch .swift files. Prettier is his example of a formatter for another language. ([3:01](https://youtu.be/ytn0aXK2gzE?t=181))
- **His settings.json has three commands after each Swift write: swift-format with a config file, SwiftLint with swiftlint.yml, and a terminal build of the app.** — Formatting keeps code clean, which he says makes it easier for Claude to re-read and reduces hallucination. This is his claim and was not measured. ([4:24](https://youtu.be/ytn0aXK2gzE?t=264))
- **Errors from the checks are fed back into the loop. Lint violations and build errors printed to the terminal are fetched by Claude and fixed without a human pasting them in.** — The build step is what lets the agent catch runtime problems such as missing data or broken connections. He also added an accessibility audit as a hook, and Claude fixed the failures it reported. ([5:51](https://youtu.be/ytn0aXK2gzE?t=351))
- **Rules can be generated by asking a general LLM. Give it a tools.md reference of Claude Code tools and hook points, ask for per-language rules, then have Claude implement them as hooks.** — Steps: write tools.md, ask ChatGPT for rules for the stack, save the output to rules.md, run the slash command from the rule-to-hook repo, tell Claude to web-search the current commands, and write hooks into settings.json. ([7:05](https://youtu.be/ytn0aXK2gzE?t=425))
- **Generated hook configs need checking. The presenter had to update an outdated hooks.json format and add missing tools.** — He also excludes unwanted hooks, such as auto-commit and CI/CD triggers, by stating them in the instructions. ([8:27](https://youtu.be/ytn0aXK2gzE?t=507))

## Techniques
- **Post-edit hooks as hard quality gates** — In project settings.json, add hooks that run after Edit, MultiEdit and Write. Restrict each hook to the file type it applies to (the presenter used .swift). Chain the formatter, the linter and the build command. The presenter did not show the exact hook schema on screen. *When:* When code must pass formatting, lint and build checks no matter how closely the model follows its instructions.
- **Feed check output back to the agent** — Have each hook print its errors to the terminal so Claude reads them and fixes the code. The presenter relied on the build's stdout and on lint violations for this loop. *When:* For stacks with fast local builds or linters, so broken code does not need to be pasted back by hand.
- **Stop-event sound notification** — Configure a hook on Claude Code's stop event that plays a system sound. The presenter did not show the command. *When:* During long autonomous runs where you want to know when Claude has finished without watching the pane.
- **Generate hooks from a rules file** — 1) Write a tools.md listing Claude Code tools and their execution points. 2) Give it and the stack to a general LLM and ask for lint, format and test rules per language. 3) Save the answer as rules.md. 4) Run the rule-to-hook slash command so Claude web-searches the current commands and writes settings.json hooks. 5) List any hooks to exclude, such as git commit or CI triggers. 6) Review the output for outdated formats. *When:* When adopting a new language or framework and you do not know its lint and format conventions.
- **Accessibility audit as a hook** — Add an accessibility test or audit step to the post-edit hooks for UI code. Claude fixes the failures it reports. The presenter did not show the audit tool. *When:* For UI projects where accessibility regressions would otherwise slip through.
- **Autonomous run from a task file** — Write an implement.md task list. Start Claude Code with --dangerously-skip-permissions and say the base app is set up. Claude builds its own to-do list and works through it. The presenter used this for a demo. *When:* Only in throwaway or sandboxed projects. The presenter did not discuss the risks of skipping permissions.
