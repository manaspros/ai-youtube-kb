> Netflix's playbook for using coding agents on production profiling data to find CPU hot spots, open reviewed fixes, and grow a shared pattern catalog, with a canary gate and an autonomy ladder.

## Summary
Rajat Shah (Netflix AI platform) argues that coding agents write code fast but not necessarily efficient code, and that human performance engineering does not scale. He ran an experiment in which an LLM agent read production profiler output (call stacks with self and inclusive CPU), recognised common anti-patterns such as O(n^2) loops and repeated allocations, checked out the exact production commit, traced the call path, and drafted a code review in under five minutes. The same anti-pattern was then found in seven services through cross-repo search. He proposes a central, git-hosted markdown catalog of patterns and anti-patterns, where confidence rises as services confirm an entry, so agents can reuse past findings. Fixes still go through a canary comparison (old vs new code on split traffic, about 10 minutes) and an engineer's approval. He recommends moving the catalog earlier in the lifecycle, to reviewer agents and to coding agents while they write code, and starting with a fixed, scheduled workflow before giving agents more autonomy. It is a practitioner playbook with a few concrete numbers and no published eval method.

## Key ideas
- **Coding agents ship code fast but not always efficient code, because they do not know the platform's frameworks and internal patterns.** — The speaker says authoring speed rises about 10x while compute cost rises at a similar pace. Agents reuse generic patterns or invent new ones that the team did not intend. ([1:31](https://youtu.be/CgsWxRUY5Eo?t=91))
- **Profilers in any language emit similar structured data (call stack, self CPU, inclusive CPU, sampled at high frequency), which an LLM can read.** — The speaker's key assumption is that the output format is consistent across Java, Python, Go and others, so one agent approach can cover many services. ([5:45](https://youtu.be/CgsWxRUY5Eo?t=345))
- **An LLM can spot known anti-patterns from the profile alone, without reading the code first.** — Examples are O(n^2) loops, loop invariants computed each iteration, repeated object allocation and poor batching. In the talk's example the agent saw a quadratic call path inside a tensor merge method. ([6:42](https://youtu.be/CgsWxRUY5Eo?t=402))
- **The agent turns a profile hit into a fix by following a fixed chain: find the production commit, clone the repo at that commit, locate the code, trace the call path, then open a review.** — The speaker says this took under five minutes on a large codebase with a capable agent. In the O(n^2) case the function used 8.8% of CPU in the profiling window. ([9:29](https://youtu.be/CgsWxRUY5Eo?t=569))
- **Once a pattern is found in one service, cross-repo code search finds the same pattern elsewhere.** — The counter-object-per-iteration pattern appeared in seven services. The speaker estimates fixing all of them would save 0.5 to 4.6% of CPU. ([13:10](https://youtu.be/CgsWxRUY5Eo?t=790))
- **Agent memory can be a plain markdown catalog in a central git repo, not a vector database.** — Each entry lists trigger symbols, the services that confirmed it, and a confidence level that rises as more services confirm it. The catalog is kept central and generalised so it is not tied to one team. Public sources such as TorchFix and Jeff Dean's C++ optimisation notes can seed it. ([15:28](https://youtu.be/CgsWxRUY5Eo?t=928))
- **Keep a human approval step: agents open code reviews but do not push changes to production, and an automated canary gates the review.** — The canary runs old and new code on the same traffic for about 10 minutes and compares CPU, latency and error rate. An error-rate increase is a stop signal. The speaker's mental model is that the profiler gives an estimate, the canary verifies it, and the engineer decides. ([20:04](https://youtu.be/CgsWxRUY5Eo?t=1204))
- **Move the catalog left: reviewer agents and coding agents should use it while code is being written, not only after it runs in production.** — The speaker calls the post-production loop reactive and the in-authoring use proactive. The catalog must be indexed hierarchically so agents can navigate it without filling their context window. The trade-off is more tokens and slower writing. ([24:54](https://youtu.be/CgsWxRUY5Eo?t=1494))
- **Build the foundations before adding an LLM: good tests, canary automation, and integration points an agent can call (trigger profiling, download data, run a canary).** — The speaker says poor foundations add friction and production bugs. The agent should only need to call the canary and read its report, and the judgement should rest on the numbers. ([27:42](https://youtu.be/CgsWxRUY5Eo?t=1662))
- **Use an autonomy ladder: a fixed scheduled workflow first, then planning agents only after investing in evals, sandboxing and guardrails.** — Level 1 is an LLM for identification only. Level 2 is a fixed, scheduled workflow (for example weekly) with tools and hooks. Level 3 lets the agent plan and act, which needs strong evals, sandboxing and protection against prompt injection. ([30:31](https://youtu.be/CgsWxRUY5Eo?t=1831))

## Techniques
- **Profile-to-PR agent pipeline** — Feed profiler output (call stack with self and inclusive CPU) to an agent with a skill or prompt. The agent identifies the hot path, checks out the production commit, traces the call path, searches for the pattern, and drafts a code review. *When:* Services that already produce profiler data and have good build-to-commit traceability in production.
- **Central anti-pattern catalog in git** — Store patterns and anti-patterns as markdown in a central repo. Each entry lists trigger symbols, confirming services, and a confidence score that increases with each confirmation. Index it hierarchically so agents can navigate to the relevant entries. *When:* Multi-service organisations where the same performance issues recur across repos and agents need shared memory without a vector store.
- **Cross-repo sweep for recurring patterns** — After one service yields a confirmed anti-pattern, use code search across all repos to find other occurrences, then open reviews to fix them. *When:* Once a pattern is confirmed, to convert one fix into fleet-wide savings.
- **Canary-gated review** — Send the same traffic to the old and new builds for about 10 minutes. Compare CPU, latency and error rate. Open a review only if CPU and latency improve and errors do not rise. The engineer still approves and merges. *When:* Any agent-proposed change to running production code, where business logic could break without tests catching it.
- **Shift-left catalog injection** — Give the coding agent the catalog before it writes code, and give the reviewer agent the catalog to comment on pull requests. *When:* When the reactive loop is working and the catalog has enough confirmed entries to avoid noisy suggestions.
- **Scheduled fixed workflow before autonomy** — Run a fixed pipeline on a schedule (for example weekly): trigger a profile, download it, analyse it, run the canary, and propose a fix. Add planning and reasoning only once evals, sandboxing and security controls are in place. *When:* As the first deployment step, before giving an agent open-ended planning over production systems.

## Hot takes
- Coding agents make code faster to write but more expensive to run, and the gap widens as adoption grows.
- A plain markdown catalog in git is enough agent memory for this job; a vector database is not needed at the start.
- Agents should not push performance changes to production directly; a human must approve every one, even with a canary.
- Start with a fixed, scheduled agent workflow. Only move to agents that plan on their own after heavy investment in evals, sandboxing and prompt-injection defences.

## Tools mentioned
Continuous profilers (sampled call stacks with CPU time), Git and code search across repos, Canary deployment infrastructure, TorchFix (public PyTorch anti-pattern catalog), Spectator (metrics library, named as the source of the counter-object pattern)
