# Stop Telling Agents How

- **channel:** [AI Engineer](../channels/aie.md) · **id:** `7T-gldvgfpo` · [watch](https://youtu.be/7T-gldvgfpo) · **date:** 2026-10-19 · **length:** 49:36 · **format:** talk · **quality:** 3/5 · **depth:** practitioner
- **speakers:** Dan, Raymond, Jose · **orgs:** OpenProse
- **topics:** context-engineering, agent-architecture, multi-agent, evals · **tags:** openprose, declarative-prompting, contracts, markdown-as-code, event-driven-agents, webhooks, cron-jobs, llm-as-verifier, trace-codification, subagents, compliance-docs, spec-driven-development, harness-agnostic

> OpenProse founders argue agents should be given declarative Markdown contracts plus triggers, not step-by-step prompts; the talk is largely a product demo of their hosted runner.

## Summary
Dan (creator of OpenProse), with Raymond and Jose, presents OpenProse, a Markdown-based language for describing multi-agent workflows as declarative contracts (the desired outcome, inputs, outputs, required skills and tools) rather than procedural steps. The runtime and compiler are themselves a large prompt, and the speakers say it is harness-agnostic, so the same contract can run on Claude Code, Codex or a custom harness. Jobs are a contract plus a trigger (cron or webhooks, such as GitHub issues and PRs), and the demo shows a grumpy-reviewer PR job and a quant-model documentation workflow for regulated banks. The speakers argue that verification should happen in fresh sessions checked against the contract, and that an expensive model's successful trace can be codified into pinned steps to cut cost. Much of the talk is a pitch for the hosted run.pros.md service, and most quantitative claims are unbenchmarked.

## Key ideas
- **Name the outcome, do not script the steps** — Speakers frame good agent prompting as writing declarative contracts that state the end state, goal and constraints, and letting a capable model choose the how. Telling the model how to do it wastes cost, because a cheaper model could often find the path itself. Contracts are meant to compose, borrowing composition-over-inheritance from classic software engineering. ([3:37](https://youtu.be/7T-gldvgfpo?t=217))
- **The program is Markdown, and the runtime is a prompt** — An OpenProse program is plain Markdown, read as event-driven multi-agent workflows rather than chat. The compiler and VM are also a large prompt, so the coding agent itself compiles the program. Programs can declare sub-agents, skills and mandatory tools, and the program refuses to run if a declared dependency is missing. ([5:47](https://youtu.be/7T-gldvgfpo?t=347))
- **A job is a contract plus a trigger** — Triggers are cron schedules or webhooks (GitHub issues and PRs, Slack, Stripe-style events). Example jobs: a GitHub issue becomes a commit, and a PR gets an adversarial review. Writing the trigger and the contract together is presented as the unit of an event-driven 'code factory'. ([10:54](https://youtu.be/7T-gldvgfpo?t=654))
- **Codify a successful loose run into a pinned how** — Start with an expensive model and a loose contract. Once it succeeds, capture the agent trace and compress it into explicit, more deterministic procedural steps, which lowers the cost of later runs. The speakers say this moves the spectrum from pure what toward how, but they give no cost numbers. ([15:15](https://youtu.be/7T-gldvgfpo?t=915))
- **Bring your own harness; stay out of the harness** — OpenProse does not want its prompt to be Claude-Code-specific, because Claude Code and Codex have different sub-agent systems. The layer is positioned as a meta-harness compiled by whatever harness the user brings. The runtime prompt is about 70k-80k tokens and is being trimmed. ([18:01](https://youtu.be/7T-gldvgfpo?t=1081))
- **Verify with fresh sessions against the contract** — Reviews are run in new sessions that judge the output against the written contract, not in the session that produced it, which avoids the same model confirming its own work. The demo ran dozens of PRs over a few days; some needed up to 14 review rounds before the reviewer agents passed them. Submitting a PR to a staging server for an agent to use the system and self-test is also shown. ([23:18](https://youtu.be/7T-gldvgfpo?t=1398))
- **Contracts compose into a DAG; templates capture workflow shapes** — Intermediate contracts act as checkpoints in a DAG (like n8n, but with agents flexible on the how). Common multi-agent shapes such as fan-out/fan-in, adversarial review, and loop-until-condition can be written as reusable programs. Plain harnesses need sub-agents and isolated context to support these shapes. ([44:15](https://youtu.be/7T-gldvgfpo?t=2655))
- **Compliance documentation as a contract, with a kernel as index** — A bank use case, documenting quant models for regulators, is treated as a set of regulatory requirements written as an OpenProse program. The agent receives only a public kernel (a Markdown bootloader that indexes other documents and best practices) plus the program, then runs. A SOFR-curve doc was demoed, with no internal data shown. ([34:17](https://youtu.be/7T-gldvgfpo?t=2057))

## Techniques
- **Contract-first workflow spec** — Write a Markdown program that declares the goal, the inputs, the required outputs and the constraints, plus the exact sub-agents, skills and CLIs the run must use (for example, require a specific search CLI and forbid generic web search). Leave the procedure open. Have the program refuse to run if any declared dependency is missing rather than degrading silently. Use an agent that follows a best-practices guide to iterate the contract. The speakers' CLI for this is a pros write command; a pros run command with a kernel path executes a program. *When:* Recurring, auditable, multi-step workflows where you know the outcome but not the path, or where the same contract must run on different harnesses or models.
- **Codify a golden trace into pinned steps** — Run the task once with a strong model and loose contract. Save the session as a golden trace. Turn that trace into explicit procedural steps (the 'how' section) and rerun the workflow on a cheaper model, checking that the output still meets the contract. *When:* Repeated workflows where the first successful run was expensive and you want the same result at lower cost. Measure the cost and quality delta, since the speakers give no figures.
- **Event-driven job = contract + trigger** — Define each job as a contract file plus a trigger: a cron schedule, or a webhook such as a GitHub issue opened or PR filed. In the speakers' setup, GitHub PR webhooks are a one-click configuration. Pick the model for the job from a list in the job settings. Confirm any step that spends money before the job is deployed. *When:* Reactive automation (issue triage, PR review, scheduled reports) where you want no always-on chat session.
- **Fresh-session verifier against the contract** — Do not let the producing session approve its own output. Spawn a new agent session for review, give it only the contract and the artifact (for example, the PR diff), and have it return pass/fail against the contract. Repeat rounds until the reviewer passes, and let the parent agent decide when to exit. *When:* Agent-written code or documents that need an independent check, such as PR reviews or quality gates before shipping.
- **Kernel as a bootloader index** — Keep one public Markdown kernel that tells the agent how to read the program, where the best-practice docs and contract-authoring guide live, and how to find other documents. Start a run by pointing the agent at the kernel, then the program (in the speakers' Codex demo, a boot-the-kernel instruction followed by a run command on the program). The kernel is written for agents, not humans, which the speakers found people objected to when it was formatted for readers. *When:* Shared operating procedures or regulatory documentation that many agents will load, to keep each program small and consistent.
- **Templated multi-agent shapes** — Express a fan-out/fan-in, adversarial review, or loop-until-condition workflow as a program with named sub-agent roles. Example content pipeline: a researcher sub-agent restricted to a chosen search CLI and skill, a writer sub-agent given recent exemplar articles to imitate, and a copy-editor sub-agent. The parent agent loops until the article meets the contract. *When:* Content, research or report pipelines where roles are clear and the quality bar can be written as a contract.
- **Cheap verifier or router (planned, not shipped)** — The speakers plan a small, fast 'Jev' decision model (name as transcribed) to act as a verifier at the end of a job, or as a router that sends GitHub issue events to the issue job and PR events to the PR review job. It would also decide whether upstream state changed, acting as a cheap semantic cache for downstream reruns. They say this is not built yet. *When:* When full LLM runs are too costly for pass/fail checks or change detection; treat as a future design, not a tested pattern.

## Numbers
- Runtime kernel or system prompt for the OpenProse runner is about 70,000 to 80,000 tokens; speakers say they are trying to shrink it. ([18:01](https://youtu.be/7T-gldvgfpo?t=1081))
- Dozens of PRs in a few days were run through the review loop; some needed up to 14 review rounds before reviewers passed them. ([23:18](https://youtu.be/7T-gldvgfpo?t=1398))
- A roughly 100,000-token prefix is mentioned as the scale where text-as-RL-data and gisting become relevant; the speakers say they have not reached that volume. ([28:23](https://youtu.be/7T-gldvgfpo?t=1703))
- A large bank has about 4,000 models that must each be re-documented yearly; the speakers say this costs large banks $10M to $50M a year (speaker's estimate, not sourced). ([37:09](https://youtu.be/7T-gldvgfpo?t=2229))
- The quant documentation output was judged by quants in the room and benchmarked against historical results and team time, but no figures are given. ([37:09](https://youtu.be/7T-gldvgfpo?t=2229))
- Anthropic's dynamic workflows post names six workflow shapes that the speakers say can all be expressed as programs. ([45:42](https://youtu.be/7T-gldvgfpo?t=2742))

## Hot takes
- Mostly a product demo for run.pros.md; the generic ideas are sound, but the speakers give no comparative benchmarks, cost deltas, or failure rates.
- The claim that codifying a golden trace drives costs down is asserted, not measured.
- The bank ROI ($10M to $50M per year, 4,000 models, 'shockingly good' results) is vendor-sourced and unverified.
- Claims 'bring your own harness' and no Claude-Code-specific prompting, while the runtime is a 70k to 80k token prompt, which is a large fixed context cost on every run.
- The speakers concede that the same contract gives different results on different models (Haiku vs Fable) and that a pinned endpoint can change, so reliability is not guaranteed.
- A quality score cap is not triggered (no sponsor segment), but substance is mostly the creator's own product, so the score stays at practitioner level.
