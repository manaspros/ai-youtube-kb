> Walkthrough of a compound-engineering Claude Code plugin (plan, work, review, triage, codify, resolve commands) that persists to-dos and runs parallel review agents. Practical, but the 10X title is unmeasured.

## Summary
The host tries a Claude Code plugin ("compound engineering") that drives a plan-work-review loop through custom slash commands and sub-agents. The plan step takes a PRD and tech stack, launches research agents (research, best practices, framework), and writes a GitHub-issue markdown file that holds the research, the files to create, and six phases. Phases are stored in Claude Code's built-in to-do tool, which the host says survives compaction and session resume, and the work step executes them one at a time, pausing after each phase for review. A review step runs parallel language and concern agents (Python, TypeScript, Rails; security, performance, architecture, data integrity), and triage turns the findings into per-issue markdown files that codify then annotates. A resolve step builds a dependency graph over the to-dos and runs independent ones in parallel, with each feature in its own git worktree. The host's main criticism is a requirements gap that produced a wrong export button, and he concedes the framework is not groundbreaking; its main strength is being an easy-to-install plugin. He compares it unfavourably for large projects to the BMAD method, which he says is more thorough but slower for small ones, without measuring either.

## Techniques
- **Plan, work, review, triage, codify, resolve command loop** — Define each stage as a custom slash command (the video names plan, work, review, triage, codify, resolve, plus a context-usage check). Plan writes a GitHub-issue markdown file with research and phases in a new git worktree. Work runs phases one by one and pauses after each for human review. Review runs parallel sub-agents and returns prioritized issues. Triage asks which to fix and writes one markdown file per issue. Codify appends learnings to those files. Resolve builds a dependency graph and runs independent to-dos in parallel. The loop then returns to plan. *When:* Adding features to an existing codebase when you already have consolidated context, and want reviewable phase checkpoints rather than one long autonomous run.
- **Built-in to-do tool as the phase ledger** — Write each phase as a task in Claude Code's built-in to-do list. Keep the GitHub issue file as the long-lived context document and update it as each phase completes. The host reports that the to-dos survived compaction and an exit-and-resume. *When:* Long multi-phase builds where compaction could otherwise erase the plan. Check whether the persistence holds in your own setup before relying on it.
- **Pause-per-phase human checkpoint** — Have the executing step stop after each phase, summarize what it built, and wait for approval before continuing. *When:* Work where a wrong early phase would compound, such as schema or architecture decisions.
- **Context check before each phase** — Run the Claude Code context command before starting a phase to see how much context remains before the buffer limit. Start a fresh session if a phase would not fit, so compaction does not land mid-phase. *When:* Multi-session workflows where a phase split across two compacted sessions loses continuity.
- **Language- and concern-specific parallel review agents** — Create one review sub-agent per language (the host used Python, TypeScript, Rails) and per concern (security, performance, architecture, data integrity). Run them in parallel and ask for a severity-ordered list of issues. *When:* Reviewing agent-written code where a single generic reviewer tends to miss language-specific problems.
- **Dependency-graph parallel resolution of to-dos** — Give the resolve step all to-do items. Have it infer which items depend on which and run the independent ones concurrently, each in an isolated worktree. *When:* A backlog of small, mostly independent fixes after a review pass.
- **Git ingest for Q&A on a repo** — Convert a git repository into a single LLM-readable file using the git ingest tool, then give it to Claude to ask detailed questions about the codebase. The host did this with the compound-engineering repo. *When:* Learning how an unfamiliar repo works, or giving an agent a whole-repo snapshot for questions.
- **Install as a plugin via marketplace** — Add the plugin marketplace in Claude Code, then install the plugin from it. The host says the commands appear on screen but are not spoken, so exact strings are not in the transcript. Check the video or the plugin repo for them. *When:* Sharing one standardized set of commands, sub-agents, MCP servers and hooks across a team.
