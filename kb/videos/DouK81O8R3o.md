> GEICO's Ford Pryor describes an AI "war room" for legacy code modernization: a roster of decision makers, a driver, and fleet-managed Claude agents that take a major change from goal to approved design and agent-callable APIs, with human gates along the way.

## Summary
Pryor, a senior staff engineer at GEICO's claims tech group, argues that AI coding sped up the inner dev loop but the outer loop (collaboration, decisions, approvals) now limits major changes. GEICO offloads patch and minor work to managed agents and wants engineers on major (v1 to v2) work, which they had only about 25% of bandwidth for. Their answer is a "multiplayer AI-native war room": a roster of SMEs and decision makers, a driver who runs the expensive tools, a comms channel, design tools, and the code repos, all wired to agent skills, MCPs and agent fleets. They ran three code-modernization experiments on a ~millions-of-lines legacy claims system, using the Anthropic Code Modernization plugin's Uplift / Transform / Reimagine taxonomy, and produced an extended rentals API, new damages APIs, and a fully vetted salvage migration plan. The system is a vendor part (harness, model, plugin, Fleet Kit) that can be swapped, plus GEICO's own part that cannot: standards and decision history (context), domain-specific methods (skills), and who can decide what at which gate (judgment), kept in two repos. Lessons: a runaway agent-created cron burned budget, prompt caching was higher than expected, and Sonnet 5.5 matched or beat the model they called Fable on a benchmark against existing golden code. Next steps are stronger gate enforcement and better search over context and automatic transcription of meetings.

## Key ideas
- **The bottleneck has moved from coding to the outer loop: collaboration and decisions on major changes.** — Coding in the inner loop is largely sped up by agents, but major changes are rate limited by getting the right people into rooms at the right time and by the missing intelligence (fact checking, code analysis) needed to decide quickly. ([1:09](https://youtu.be/DouK81O8R3o?t=69))
- **Split the work by semver: agents take patches and minors, engineers keep majors.** — Engineers had roughly 25% or less of their bandwidth for major changes after patch and minor work. GEICO offloads patch and minor work from spec to deployment to managed agents on several harnesses and models, so people focus on major changes. ([2:39](https://youtu.be/DouK81O8R3o?t=159))
- **Build a multiplayer AI-native war room for each major change.** — The war room has a roster of decision makers and SMEs, a driver who runs the expensive AI tools, comms channels, a design studio and code repos. Agent workflows, skills, MCPs and agent fleets do the heavy lifting of fact checking and synthesis. ([4:08](https://youtu.be/DouK81O8R3o?t=248))
- **Use a three-part split of what is replaceable and what is not.** — The vendor side (harness, model, Fleet Kit, code modernization plugin) can be replaced. GEICO's side (context such as standards and decision history, methods as domain-specific skills, and judgment about who decides at which gate) is the part that cannot. Context, methods and judgment sit in two repos that agents and humans both edit. ([7:51](https://youtu.be/DouK81O8R3o?t=471))
- **Fleet Kit is a markdown rules protocol that turns a goal into research, an approval queue and builder work.** — It takes a goal, breaks it down, dispatches leader agents to research and propose an approach, and puts the output in a loop queue (GitHub issues were given as an example) where humans comment and approve. Once approved, it dispatches builder agents. Beads is used to track each agent's state. ([10:26](https://youtu.be/DouK81O8R3o?t=626))
- **Each milestone must produce an artifact, and a deterministic check confirms it.** — The modernization plugin's nine-step process creates worksheets (HTML artifacts that humans fill in and that auto-save) or design docs (draw.io or Figma) at each milestone. Steps that need human approval are flagged. The plugin checks deterministically that the previous step created its required artifacts or files. ([11:40](https://youtu.be/DouK81O8R3o?t=700))
- **Agent-written worksheets were higher quality than expected, and the diagrams were kept.** — The agent asked edge-case questions that the team had not thought of. Teams kept the architecture diagrams afterward because they mapped things nobody had documented. Two agent types were used: cloud 'code dives' crunched legacy DSL code and graphed it, while local agents ran on the driver's laptop with its MCPs. ([13:01](https://youtu.be/DouK81O8R3o?t=781))
- **Cost and model lessons: stop agent-created crons, and benchmark models against your own golden code.** — Do not let the agent set up crons that check on work, because each tick launches a new session and burns budget fast. Prompt caching was much higher than expected. In a benchmark against existing recent code as the golden data, Sonnet 5.5 wrote code as good as or better than Fable. ([15:47](https://youtu.be/DouK81O8R3o?t=947))

## Techniques
- **War room composition for a major change** — Create a mission channel in comms (Slack was used). Invite a roster of decision makers and SMEs relevant to the change. Put one driver in charge of the expensive agent tooling. Wire the comms, design tools and code repos to agent workflows, skills and MCPs. The agent pings people from the roster when information is missing, and asks product owners for product details. *When:* A major (v1 to v2 style) change needs cross-functional decisions before any code is written, and the decision latency is the bottleneck.
- **Three-repo split of enterprise agent context** — Keep a context repo (standards, past decision history, knowledge base in markdown), a methods repo (domain-specific skills and development process), and a judgment repo (who decides what at which gate). Let agents propose edits and humans correct them. Keep the vendor harness, model and plugin separate so each can be swapped. *When:* You need the company's specific knowledge and approval rules to outlive any single vendor harness or model.
- **Goal-to-approval-to-build loop with a queue** — Write fleet rules in markdown that the Claude harness follows. Given a goal, dispatch leader agents to research and propose an approach. Put the output in a queue where humans can comment or approve; GitHub issues were the example. Let other agents add context to queued items. Dispatch builder agents only after approval. Track per-agent state with beads. *When:* Agents do research and design work that needs a human sign-off before implementation, with several agents working in parallel.
- **Milestone artifacts plus deterministic gate checks** — Build each step of a multi-step process so it writes a named artifact: an HTML worksheet that people fill in (auto-saved) or a design doc (draw.io or Figma) that the agent rereads after humans edit it. Mark human-approval steps. Before moving on, run a deterministic check that the previous step produced its required artifacts or files. Steps were forked from the Anthropic Code Modernization plugin and adapted. *When:* A long agent workflow needs human checkpoints and must not advance on missing outputs, as in legacy code modernization.
- **Taxonomy for modernization missions** — Classify each domain as Uplift (a newer version of the same tech), Transform (add new APIs to unlock a larger workflow), or Reimagine (a full redesign). Run one domain end to end per day-long mission, with a graph of the business topology and the legacy code, and aim for one agent-callable API or plan. *When:* Scoping how much to change in each legacy domain before running agents on it.
- **Local bindings file for agents on a laptop** — Write a bindings file that describes what is on the machine (MCP servers, tools, how they work) and how to map them to the fleet kit for work. Give the local agents access to the laptop's MCPs, including ones not yet in production. *When:* Local agents need to use internal or pre-production tools that are not available in the cloud agent environment.
- **Cost guardrails for agent-run work** — Do not let the coding agent create cron jobs that check on work, because every tick starts a new session. Track prompt caching hit rates. Benchmark a cheaper model against existing code as golden data before you switch to it. *When:* A long-running agent project is burning tokens or the team is picking a model for a build step.

## Hot takes
- Software development looks less like playing on a canvas and more like working in a factory.
- Model selection is the win: Sonnet 5.5 matched or beat Fable on their golden-data benchmark.
- Enhanced gate enforcement will be the biggest win, more than model or harness choices.
- A PhD-level fleet manager is needed because running this at scale is expensive.
- Do not let agents set up crons to check on work; it burns budget fast.
