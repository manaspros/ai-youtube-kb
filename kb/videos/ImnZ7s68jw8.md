> Arize's Aparna Dhinakaran argues the AI engineer's job is now building the build-eval-ship-monitor-improve loop itself, with always-on agents consuming telemetry and evals aligned to human judgment.

## Summary
Aparna Dhinakaran (Arize AI) revisits "what does an AI engineer do" at AI Engineer New York, framing the role as moving up an abstraction layer: from writing features, to building the loop that writes features, reviews code, and reads telemetry. She describes Arize's Signal, an always-on agent that reads traces on a cadence or event trigger, detects issues, remembers what it has already seen, and opens PRs when it has repo access. Each run happens in a fresh sandbox reachable only through a single proxy, with all activity traced and only outputs and memory kept afterward. Signal is built to be durable, resuming from the failed step using state stored outside the sandbox, and to be agnostic to harness (Claude Code, Cursor, Codex) and model within a family. She argues the core AI engineer skill is writing evals and "evaluating the evaluators" against golden datasets with human labels before shipping a judge, then running evals offline and online, and tracing coding agents as well as production agents. The talk is a conference talk that doubles as a product pitch for Signal, and the evidence is practitioner experience rather than benchmarks.

## Key ideas
- **The AI engineer's job is shifting from writing AI features to building the loop that does build, eval, ship, monitor and improve.** — Code review, eval writing and metric setup become systems the engineer designs, with agents doing the review and telemetry analysis. ([2:34](https://youtu.be/ImnZ7s68jw8?t=154))
- **Observability data should be designed for agents as the primary consumer, not humans.** — Telemetry becomes the trigger for always-on agents. Signal reads the last N traces on a cadence (e.g. every 3 or 6 hours), on events such as a Slack complaint, or on a metric threshold. ([5:19](https://youtu.be/ImnZ7s68jw8?t=319))
- **Each agent run should happen in a disposable sandbox with a single proxy as the only ingress and egress, and only outputs persist.** — Context, third-party telemetry, repo access and keys go into the sandbox. Everything is traced. Found issues and learned skills are saved, while the sandbox, credentials and repo access are torn down. ([6:41](https://youtu.be/ImnZ7s68jw8?t=401))
- **Durability comes from keeping run state outside the sandbox so a failed run resumes at the failed step.** — If the sandbox or harness dies, a new sandbox and harness pick up from saved state instead of restarting the sweep. ([8:06](https://youtu.be/ImnZ7s68jw8?t=486))
- **Make the agent harness and model swappable so quality and cost can be measured per run.** — Signal supports Claude Code, Cursor and Codex, and multiple Anthropic models. Comparing models lets the team see whether pricier models produce better PRs and whether cheaper ones keep issue-detection rigor. ([9:26](https://youtu.be/ImnZ7s68jw8?t=566))
- **Evaluators need their own evaluation: align the LLM judge with human labels on golden datasets before shipping it.** — Teams ask how to trust an evaluator. Arize checks each judge against human-labelled golden data and only ships it once it agrees with the humans. ([12:13](https://youtu.be/ImnZ7s68jw8?t=733))
- **Run the same evals offline before shipping and online against production traces, and trace the coding agents that build the product too.** — Offline evals gate changes. Online evals run on production telemetry and feed back into the agents that look for problems. Coding-agent sessions (Claude Code, Cursor, Codex) are traced so you can see what the agent factory did. ([13:37](https://youtu.be/ImnZ7s68jw8?t=817))
- **The closed loop is collect data, evaluate it, run agents over the results to find problems, then improve the system.** — She frames the gap between lab conditions and messy business data as the reason AI engineers are needed, and the loop as the way to close it. ([13:37](https://youtu.be/ImnZ7s68jw8?t=817))

## Techniques
- **Telemetry-triggered always-on agent sweep** — Schedule the agent on a cadence (every few hours) over the last N traces, plus event triggers (chat complaints) and metric-threshold triggers. Each run pulls traces, APM logs and metrics, and repo access, then reports findings. *When:* When you want background agents to watch production traffic and surface regressions without a human polling dashboards.
- **Issue memory across agent runs** — Persist every issue the agent flags, including suspected issues that are not yet confirmed. On later runs, check against this history so a recurring issue that grows more severe is escalated, and a one-off is not. *When:* When an agent runs repeatedly over the same data and should not rediscover or re-report the same problem from scratch.
- **Sandbox-per-run with single proxy egress** — Build a fresh sandbox for each agent run, route all inbound and outbound traffic through one proxy, trace everything inside, persist only outputs and learned skills, and tear down the sandbox and credentials afterwards. *When:* When an agent runs unattended with credentials and repo access and you need an audit trail and a clean teardown.
- **Durable agent resume** — Store step-level run state outside the sandbox and harness. On failure, start a new sandbox and harness and resume from the failed step. *When:* For long-running or unattended agent runs where restarting from zero is expensive.
- **Harness and model abstraction with per-run evaluation** — Keep the agent logic independent of the coding harness and model. Run the same task across harnesses and models in the family, and compare PR quality and issue-detection quality against cost. *When:* When you need to pick the cheapest model that still meets your quality bar, rather than defaulting to the most capable one.
- **Evaluator alignment against golden data** — Build a golden dataset labelled by humans. Run the LLM judge on it, measure agreement with the human labels, and iterate the judge until it matches before using it in CI or online scoring. *When:* Before trusting any LLM-as-judge eval to gate PRs or score production traces.
- **Offline plus online evals on the same definitions** — Use the same eval definitions offline as pre-ship regression tests on a dataset, then run them online over production traces to monitor drift. *When:* When you want one definition of quality to cover pre-release testing and production monitoring.
- **Trace the coding agents too** — Instrument Claude Code, Cursor or Codex sessions that build the product, so the factory's own actions are observable and evaluable alongside production agent traces. *When:* When agents write a meaningful share of the code and you need to audit or improve how they work.

## Numbers

## Hot takes
- The "5,000 frontier users" funnel is the speaker citing a tweet and is not verified. Treat it as framing, not data.
- Much of the talk is a pitch for Arize's Signal, and the booth is promoted at the end. The architecture points (sandbox per run, durable resume, eval alignment) are useful regardless of vendor. There are no benchmarks, only practitioner claims.
- Evaluator alignment, meaning checking the LLM judge against human labels before shipping, is presented as the main work of an AI engineer.
