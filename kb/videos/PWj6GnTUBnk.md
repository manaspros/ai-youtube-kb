## Summary
Better Stack introduces Cloudflare Artifacts, a Git-compatible distributed file system for agents that can create, fork and delete very large numbers of repos. The speaker argues GitHub's social features are irrelevant to agents, while Git itself is well represented in model training data. Cloudflare's implementation is a basic Git server written in Zig, compiled to WASM and run inside a Durable Object, so any Git client (isomorphic-git in a Worker, the Git protocol, or HTTP) can talk to it. The demo imports a "baseline" repo, forks it once per task, runs an Anthropic-SDK agent loop in each fork with read, write and commit tools, and returns each fork's remote, token and the agent's summary. The Worker binding lacks pull, commit and push, so the speaker wrote those with isomorphic-git against an in-memory file system. Because the repo lives in the Durable Object's SQLite store, it survives object restarts. The speaker could not run any of it because the product is in private beta, so the code is unverified, and he flags that git diff is missing from both the binding and isomorphic-git.

## Key ideas
- **Cloudflare Artifacts is a Git-compatible store built for agents, not humans, and it is in private beta.** — The speaker's argument is that GitHub's social features (followers, discussion style) add nothing for agents, while agents already know Git from training data. Intended uses: parallel PR reviews, automated refactors across large codebases, and per-session agent workspaces. The speaker had no access, so he worked from the docs. ([0:00](https://youtu.be/PWj6GnTUBnk?t=0))
- **The Git server is a small Zig implementation compiled to WASM and run inside a Durable Object.** — Clients can be anything Git-speaking: isomorphic-git inside a Worker, the native Git protocol, or plain HTTP for non-JavaScript callers. The speaker's point is that the object's SQLite storage holds the repo. ([0:47](https://youtu.be/PWj6GnTUBnk?t=47))
- **Fork-per-task is the core pattern: one baseline repo, one fork per task, each task run by its own agent.** — The worker checks whether a repo named baseline exists and imports a Git repo if it does not. It then forks the baseline for each task in a list and runs the agent in that fork. The result per task is the task name, fork name, remote, token and the agent's final message. ([1:49](https://youtu.be/PWj6GnTUBnk?t=109))
- **The Worker binding covers create/import/fork, but not pull, commit or push, so the agent loop has to handle Git itself.** — The speaker used isomorphic-git inside the Worker and an in-memory file system. The agent gets read, write and commit tools; commit also pushes. Otherwise it is a standard agent loop: run the tool call, feed the result back, continue. ([3:17](https://youtu.be/PWj6GnTUBnk?t=197))
- **Durability comes from the Durable Object, so an agent's changes persist if the object restarts.** — Everything written lands in the object's SQLite database and can be recovered when the object comes back. The speaker presents this as the reason to use Artifacts over an ephemeral file system. ([3:17](https://youtu.be/PWj6GnTUBnk?t=197))
- **The speaker sketches a larger system: an orchestrator agent merging forks after a reviewer agent signs off, plus execution of the changed code.** — Dynamic Workers can run JavaScript changes. Cloudflare Sandboxes cover other languages and shell commands. The Cloudflare browser (Puppeteer) can check front-end changes visually. These are ideas he did not build. ([4:26](https://youtu.be/PWj6GnTUBnk?t=266))
- **There is no git diff in the binding or in isomorphic-git, which is a real gap for review workflows.** — Possible workarounds: walk the commit trees returned by isomorphic-git's log and compare them manually, or use the Git protocol directly. The speaker expects this may be added later. ([5:39](https://youtu.be/PWj6GnTUBnk?t=339))

## Techniques
- **Fork-per-task repo workspaces** — Keep one canonical baseline repo. For each task, fork it under a unique name, run the agent in that fork, and return the fork's name, remote and access token with the agent's summary. Check for baseline first and import the source Git repo only if it is missing. In the video the task list is hard-coded, but he suggests a UI or input could supply it. *When:* Parallel changes to the same codebase where each change needs its own isolated branch to review or merge later, such as parallel refactors or parallel PR reviews.
- **Git-backed agent tools: read, write, commit (commit also pushes)** — Give the model three tools. read and write operate on an in-memory file system holding a clone made with isomorphic-git from the fork's remote and token. commit stages and commits, then pushes. The system prompt tells the agent to make the change and commit it. The loop stops on tool calls, runs them, and continues until the model produces a final message. *When:* When the binding does not expose pull/commit/push and the agent must leave a durable commit on a remote, not just a local edit.
- **Durable Object SQLite as the persistence layer for agent repos** — Host the Git server in a Durable Object so repo state is stored in that object's SQLite database and survives restarts. Use the Worker binding rather than the REST API, since the speaker says it needs fewer round trips. Add the artifacts binding to wrangler.jsonc or wrangler.toml and regenerate types. *When:* When agent workspaces must outlive a single request or process and you want the storage to sit next to the compute.
- **Verification loop idea: run the agent's changed code in a sandbox, and check front-end work in a browser** — After a change is committed, execute it in a Dynamic Worker for JavaScript, or in a Cloudflare Sandbox for other languages and shell commands. For front-end changes, use the Cloudflare browser (Puppeteer) to check the rendered result. This is a suggested design, not something the speaker built. *When:* For agent-written changes where tests or a rendered check should gate the merge into the main repo.
- **Reconstructing a diff without git diff** — Use isomorphic-git's log to find the commits, walk the trees of the two commits, and compare entries. Alternatively, run the diff through the Git protocol directly against the remote. *When:* When you need to review an agent's changes but the Worker binding and isomorphic-git expose no diff command.

## Hot takes
- The speaker could not access the private beta, so the demo code was never run against the real service. Its correctness is unverified.
- The claim that agents are very good at Git because Git is in their training data is asserted, not shown.
- Calling this a Git-compatible store for agents, with no git diff in the binding, means review workflows need extra work.
- Plausible design, but the orchestrator, reviewer, dynamic-worker and browser-check pieces are only described, not built.
