> Kai works through what DeepSeek V4.1 Flash really costs to self-host: 510 GB of resident weights, 23 s/token on a 16 GB Mac, a $18.8k four-Spark cluster, and a roughly four-year break-even against cheap API pricing.

## Summary
The speaker examines running DeepSeek V4.1 Flash (MIT-licensed, open weights) on hardware you own. He grants the benchmark result (74.2 on DeepSWE V1.1, edging Claude Opus 5 and GPT 5.6 Sol as stated) but argues that the mixture-of-experts "active parameter" framing hides the real cost: all 384 routed experts plus a 196B-parameter Engram lookup table must stay resident, so the download is about 510 GB. A 16 GB Mac mini streaming those weights manages roughly 23 seconds per token, and quantization is largely exhausted because the experts already ship at FP4. The only remaining lever is compressing the Engram table from 8 to 4 bits, which takes the footprint from about 475 GB to about 385 GB. The working setup he cites is four NVIDIA DGX Sparks under vLLM at tensor parallel 4, measured at roughly 70 tokens/s for code and 30 for prose, costing about $18.8k before networking and drives. Using off-peak API prices, he computes about 89,500 jobs (roughly four years of 24/7 use) to break even, and he concludes that local deployment is justified mainly by data-residency constraints or by hardware already owned. He says he has not run the model himself, so the performance numbers are secondhand.

## Key ideas
- **Selective computation is not selective storage** — V4.1 Flash activates about 8B params when reading and 16B when writing, but all 384 routed experts plus the shared expert must stay in memory because routing is dynamic. Size the machine for resident weights, not active parameters. ([5:21](https://youtu.be/04ePeOyRN0k?t=321))
- **Engram is a lookup table, not a compute layer** — Two of the 40 layers hold a conditional memory table of about 196B params, indexed by matching sequences of up to four tokens against a 16M-entry vocabulary. It contributes to storage size but not to per-token compute. ([5:21](https://youtu.be/04ePeOyRN0k?t=321))
- **The download is about 510 GB and the OS shows about 475 GB** — The Hugging Face release has 48 files. Sizing a drive from the active parameter count undersizes it by roughly 494 GB, and the gap is partly a GB versus GiB units confusion. ([6:43](https://youtu.be/04ePeOyRN0k?t=403))
- **Local decode speed on a small machine is physics, not misconfiguration** — A 16 GB Mac mini with unquantized weights reportedly took 108 s to the first token and about 23 s per token, because it streams roughly 9.5 GB of scattered weights per token from SSD. ([2:39](https://youtu.be/04ePeOyRN0k?t=159))
- **Quantization is nearly exhausted for V4.1 Flash** — The experts already ship at FP4 with a power-of-two scale per 32-value block, and no 8-bit release exists to compress from. Going below 4 bits is described as unsuitable for serious work. The one remaining lever is the Engram table at 8 bits, which saves about 100 GB (475 to 385 GB). ([7:56](https://youtu.be/04ePeOyRN0k?t=476))
- **The hardware floor moved between versions** — V4 Flash (July, 284B params) ran in about 128 GB as community 4-bit GGUF and fit on two DGX Sparks. V4.1 Flash needs four Sparks. V4 Pro was retired, and its API routes to V4.1 Flash from September 14. ([10:03](https://youtu.be/04ePeOyRN0k?t=603))
- **Break-even against cheap API pricing takes about four years** — At off-peak API prices of $0.15 per million input and $0.60 per million output, a 1M-in/100k-out job costs about $0.21. At 70 tok/s, the $18.8k four-Spark cluster needs about 89,500 jobs (about 35,500 hours), roughly four years of 24/7 use, before adding about $5.3k of electricity. ([11:14](https://youtu.be/04ePeOyRN0k?t=674))
- **Local is justified by compliance or existing hardware, and open weights keep API prices honest** — Data that cannot leave the building (medical, defense, residency rules) makes the API unavailable, so the comparison is local versus no work. Owning idle capable hardware makes the experiment cost only electricity and time. The existence of open weights also caps what providers can charge. ([12:27](https://youtu.be/04ePeOyRN0k?t=747))
- **KV cache is cheaper per token, but that helps multi-tenant serving more than a single user** — The cache is about 890 bytes per token, roughly a quarter of the previous flash, which is a large win for thousands of concurrent sessions but gives a single local user little benefit. The advice is to measure your own tokens per second per output type rather than trust published numbers. ([13:46](https://youtu.be/04ePeOyRN0k?t=826))

## Techniques
- **Size local MoE hardware by resident bytes, not active params** — Compute resident memory as total params times bytes per param across all experts, the shared expert and any lookup tables, plus KV cache. Check the file total against the drive in GB and GiB (the speaker's example: 510 GB in the download, about 475 GiB shown by the OS). Use active params only for per-token compute and bandwidth estimates. *When:* Before buying or allocating storage or GPUs for a sparse MoE open-weight model such as DeepSeek V4.1 Flash.
- **Break-even test for self-hosting versus API** — Define a reference job (for example 1M input and 100k output tokens). Price it at API rates (off-peak here: $0.15/M in, $0.60/M out). Divide hardware cost by cost per job to get the number of jobs needed. Multiply by job duration at measured local tok/s to get hours, then divide by 24 for 24/7 years. Add electricity (kWh times price) separately. The speaker's version left electricity out of the job count. *When:* Deciding between buying local inference hardware and paying per token for a hosted API.
- **Measure decode tok/s by output type, separately from time to first token** — Run the target model with prompts that produce code or HTML, JSON, and prose or planning. Record time to first token and steady-state tokens per second for each. The speaker reports about 70, 45, and 30 tok/s respectively on the four-Spark cluster, and 108 s to first token on the Mac mini. Structured output types slow decode, so one benchmark number is not enough. *When:* Evaluating whether a local model is fast enough for a workload, or planning capacity for a mix of task types.
- **Compress the Engram table, not the experts, when the model is already FP4** — Quantize the conditional memory (lookup) table from 8 to 4 bits, which saves about 100 GB here. Expert weights are already FP4 with per-32-value block scales and are not worth further compression. Offload the table to SSD and shard the rest with tensor parallel 4 under vLLM, as the cited configuration does. *When:* The model's footprint is too large and the remaining room to compress lies in non-expert or lookup parameters.

## Hot takes
- Active-parameter framing is misleading for MoE: selective computation is not selective storage, and sizing by active params is the common mistake.
- Local deployment only makes sense for compliance-bound workloads or hardware already owned; at current API prices the cluster does not pay back for years.
- Open weights act as a price ceiling on hosted APIs, so the availability of the release benefits people who never download it.
- The hardware floor moved between versions: a two-Spark buyer in July is a generation behind on day one.
- Caveat: the speaker says he has not run the model himself; the throughput numbers come from a third-party published configuration, and the break-even math uses his assumed 24/7 utilization at 70 tok/s.
