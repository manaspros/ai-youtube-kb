> Bridgewater and turbopuffer explain how to run vector search over 100M documents with per-document permissions, using cluster-pruned "native filtering" to keep recall and latency acceptable.

## Summary
Aaron Linsky (Bridgewater) and Nikhil Benesch (turbopuffer) present the permissions problem in AI analyst agents: public web documents are shared, but private documents each carry their own access rules. Bridgewater's "Vault" holds about 100M unstructured documents from 135 external sources plus internal research, and its first permission-filtered vector query implementation fell over as the corpus grew. The speaker walks through the math: a brute-force scan of 100M one-kilobyte documents takes about 5 seconds, well above a 100 ms target. Post-filtering a fixed top-K loses recall, and pre-filtering degrades when a user can see half the corpus. turbopuffer's answer is to cluster vectors in the index, select only clusters the caller can access at least partly, then scan inside those clusters. The reported result is roughly 120 ms P90 across namespaces. The talk closes by noting open problems with nested groups and broader isolation features such as regional locks and customer-managed keys.

## Key ideas
- **Permission-aware retrieval is a classic hard IR problem. Public web documents are visible to everyone, but each private document can have its own group and per-user permissions, so the retrieval layer must respect those per query.** — The speaker's example is an analyst agent answering a question about token prices. It pulls facts from the web freely but must filter private documents by who is asking. ([0:08](https://youtu.be/u_jvuCjuvEk?t=8))
- **Bridgewater's Vault is an unstructured store of about 100M documents, mixing 135 external research sources (under legal and license terms) with internal writing, meeting recordings and reports. Humans and agents both read from it and write new research back in.** — The first permission-filtered implementation worked on small data but fell over badly as documents were added. That is what led them to look for another provider. ([3:45](https://youtu.be/u_jvuCjuvEk?t=225))
- **Brute-force search does not scale. Assuming 1 KB per document and about 20 GB/s scan speed, a sequential scan of 100M documents takes about 5 seconds, well above the roughly 100 ms that most search workloads target.** — The napkin math is used to justify adding an index only once the data size requires it. At 10K documents the same scan takes about 0.5 ms. ([8:59](https://youtu.be/u_jvuCjuvEk?t=539))
- **Post-filtering (take the top K nearest vectors, then drop what the caller cannot see) gives poor recall. A user can get 40 results when they should get 100 because the nearest neighbours are mostly hidden from them.** — Pre-filtering (build the set of visible docs first, then scan it) fails the other way. When a user can see 50M of 100M documents, it reverts to a near-sequential scan. ([11:53](https://youtu.be/u_jvuCjuvEk?t=713))
- **The fix that worked is native filtering, which combines both. The index clusters similar vectors, and each cluster is checked against the permissions. Clusters the caller has no access to are dropped entirely, the closest accessible clusters are searched, and only documents inside those clusters are scanned.** — Clusters hold about 200 documents in the current build, and the speaker says this is still being tuned. The reported result is about 120 ms P90 latency across namespaces at 100M-document scale. ([13:42](https://youtu.be/u_jvuCjuvEk?t=822))
- **Application code does not need to know about clusters. It translates its permission model into the vendor's filter language, for example documents where viewers contains the user ID, or groups contains any of a set of groups, and the engine plans the query.** — Nested groups are the known hard case. The speaker asked people with those problems to talk to the team. ([15:56](https://youtu.be/u_jvuCjuvEk?t=956))
- **Permission filters are only one dimension of isolation. The vendor also positions regional data locking, VPC residency, encryption, and customer-controlled encryption keys as part of an isolation-native search engine.** — This was a brief closing mention and was not demonstrated. ([17:11](https://youtu.be/u_jvuCjuvEk?t=1031))

## Techniques
- **Cluster-pruned native filtering for ACL-restricted vector search** — Build a vector index that clusters similar vectors (about 200 docs per cluster in turbopuffer). For each query, first compute the set of clusters the caller can access, meaning clusters containing at least one document they can see. Rank those clusters by distance to the query vector, search the closest ones, and scan sequentially inside them, applying the per-document filter there. *When:* Use it when permissions are per-document or per-group, the visible fraction of the corpus varies a lot across users, and you need both high recall and roughly 100 ms latency at tens of millions to hundreds of millions of vectors. Pure post-filtering or pure pre-filtering both break down in this regime.
- **Avoid fixed top-K then post-filter for access control** — Do not fetch the K nearest vectors and then remove the ones the caller cannot see. The result set shrinks unpredictably and recall drops. *When:* Use it as a warning when access rules are restrictive, because the caller may see few of the nearest neighbours.
- **Express permissions as filter predicates on documents** — Store per-document access lists (for example viewers as a set of user IDs and groups as a set of group IDs). At query time, map the caller's identity and group memberships directly onto predicates such as viewers contains <user>, OR groups contains any of [<groups>], and pass them as the search filter. Let the engine handle the planning. *When:* Use it when permissions can be expressed as set membership on each document. Check nested-group cases separately, because the speaker flagged them as hard.
- **Napkin math before choosing an index** — Estimate bytes per document (for example 1 KB), multiply by corpus size, and divide by realistic scan bandwidth (about 20 GB/s in RAM). Compare the result with the latency target (about 100 ms). Add an index only when the scan exceeds the target, which happens around 10M to 100M documents in this talk. *When:* Use it at design time to justify whether a complex index is needed. It keeps the system from adding complexity that the scale does not require.
- **Object-storage-first tiering for large, bursty corpora** — Keep all data on object storage (S3, GCS or Azure Blob) as the cheap source of truth. Pull namespaces or regions into SSD or memory only when they are queried, so cold data costs object-storage prices and hot data gets cache-level latency. *When:* Use it when the corpus is large (terabytes) and only parts of it are queried at any time. The speaker notes that a cold pull from S3 can take a minute or more, so the approach relies on the hot working set staying small.

## Numbers

- Typical search latency target is about 100 ms. A cold pull of data from S3 can take a minute or more. ([8:59](https://youtu.be/u_jvuCjuvEk?t=539))

- Pre-filtering is nearly sequential when the caller can see about 50M of 100M documents. ([13:42](https://youtu.be/u_jvuCjuvEk?t=822))
- Clusters in the vector index hold about 200 documents each in the current build. ([14:36](https://youtu.be/u_jvuCjuvEk?t=876))
- Reported result: about 120 ms P90 latency across namespaces. The speaker says this covers about 450M vectors built from 100M documents, and that those documents turn into about 400M vectors. These two vector counts do not match. ([14:36](https://youtu.be/u_jvuCjuvEk?t=876))
- Reported result: 1 to 200 ms search latency at 100M-document scale. ([15:56](https://youtu.be/u_jvuCjuvEk?t=956))
- Vendor claim: storing terabytes in traditional systems would cost tens of millions of dollars, and turbopuffer can often do it at about a tenth of that cost with comparable hot-query performance. ([6:32](https://youtu.be/u_jvuCjuvEk?t=392))

## Hot takes
- Vendor co-presentation: the turbopuffer CTO presents the product alongside a customer case study. The architecture is solid, but the numbers are not independently verified and the speaker's own figures conflict (about 400M vs 450M vectors; 120 ms P90 vs 1-200 ms).
- Clustering plus permission-based cluster pruning is a useful general pattern, and the post-filter vs pre-filter failure analysis is a clear way to reason about ACL-filtered ANN. It is worth reproducing with pgvector or any ANN index that supports filtering.
- Nested group membership is explicitly unresolved and is the case most likely to matter for real enterprises. The talk does not give a method for it.
- The 10x cost claim and the 'tens of millions of dollars' figure are vendor marketing and are not backed by a shown benchmark.
