> Three levels of getting non-generic UI from Claude Code: a structured single-page design prompt, a CLAUDE.md plus design.md system for cross-page consistency, and design tests written before the code, including visual TDD with Visly.

## Summary
The AI LABS hosts argue that AI-generated sites look generic because people stop at a single-page prompt. Level 1 is a structured prompt covering intent, non-negotiables, an OKLCH color system, contrast, banned and preferred fonts, symmetry versus asymmetry, sections, responsiveness, and explicit anti-patterns. Level 2 keeps design consistent across pages by moving visual rules into a separate design.md, which is kept short in CLAUDE.md. They lint design.md against Google's open-sourced template and audit it with an externally maintained design-principles skill from Versalab. Level 3 treats design like TDD: every anti-pattern and style rule in design.md becomes a static test, Playwright screenshots drive visual regression, and the Visly CLI runs a local server where the user approves or rejects screenshot diffs, with rejections fed back to the agent. The video is a workflow walkthrough with no benchmarks or before/after evidence, and it includes a sponsored segment for Zilliz Cloud.

## Key ideas
- **Generic output comes from the prompt, not just the model** — The speaker says the model converges on one default style, so a bare prompt like 'make a landing page' produces recognizable output. A structured prompt that states intent, non-negotiables, color system, typography, layout, and anti-patterns can one-shot a distinctive app. ([0:00](https://youtu.be/5lycYTOYbPM?t=0))
- **Use OKLCH for the color system and state contrast explicitly** — OKLCH (lightness, chroma, hue) is recommended over RGB or HSL for perceptual balance and smoother gradients. Contrast should be specified deliberately, since without it the model treats every element as equally important and no visual hierarchy forms. ([1:07](https://youtu.be/5lycYTOYbPM?t=67))
- **Ban the fonts the model defaults to** — Inter and Geist are called AI-slop giveaways because agents reach for them by default. Naming banned fonts in the prompt, and assigning fonts per area of the design, pushes the model toward other choices. ([1:07](https://youtu.be/5lycYTOYbPM?t=67))
- **Anti-patterns matter as much as the positive rules** — The speaker says the most important part of the prompt is listing anti-patterns, such as the centered CTA, Lucide-style icons, and glassmorphism with gradients. These are named as hallmarks of AI slop. ([2:35](https://youtu.be/5lycYTOYbPM?t=155))
- **Keep project context in CLAUDE.md and visual rules in design.md** — CLAUDE.md stays short and holds only project information, because it is loaded into every session and design detail there distracts unrelated work. A separate design.md holds the full visual system: layout, colors, typography, and the Level 1 details. A line at the top of design.md tells the agent to append any new design value it finds, so each session starts from a more refined version. ([4:03](https://youtu.be/5lycYTOYbPM?t=243))
- **Lint design.md against Google's open template and audit it with an external principles skill** — Google has open-sourced a design.md template with commands that cross-check a file against it, and the agent can iterate on those errors. Versalab's design-audit skill is installed per project; it points to an externally maintained set of principles rather than hard-coding them, so the audit tracks current best practice. ([5:30](https://youtu.be/5lycYTOYbPM?t=330))
- **Write design tests before the implementation, as with TDD** — The speaker argues tests written after the code get fitted to it, because the code is already in context. So tests come first and are derived from design.md: every anti-pattern, color rule, spacing constraint, and typography choice becomes a programmatic check. The static tests are paired with Playwright visual regression tests. ([8:01](https://youtu.be/5lycYTOYbPM?t=481))
- **Use Visly's local TDD loop to review visual diffs instead of trusting the agent** — The Visly CLI starts a local server that monitors screenshots. Claude writes Visly-named tests that use Playwright screenshots to push images to the viewer. The user approves or rejects each diff, and rejected diffs become feedback for the next pass. The speaker says the diffs report exact changed pixels with metadata, and that the design converges over a few iterations. ([9:28](https://youtu.be/5lycYTOYbPM?t=568))

## Techniques
- **Structured single-page design prompt** — Write the prompt in this order: (1) the site's intent, (2) non-negotiable elements and how the UI should look, (3) a color system in OKLCH, (4) explicit contrast and hierarchy rules, (5) banned fonts plus which fonts to use in which areas, (6) layout: symmetric for professional, asymmetric for artistic, with negative space, (7) sections, materials, and responsive behavior, (8) an explicit list of anti-patterns. Give it to Claude Code or another agent and let it one-shot the app. *When:* Starting any new landing page or app UI where the default model style would look generic.
- **CLAUDE.md for project context, design.md for the visual system** — Keep CLAUDE.md to project facts only, since it is loaded every session. Put colors (OKLCH), typography, layout, and component rules in design.md. Add a top-of-file line instructing the agent to append any new design value it encounters to design.md. Ask the agent to generate both files from a detailed prompt. *When:* Multi-page apps where the landing page looks good but the dashboard and auth pages drift in buttons, spacing, and type.
- **Lint design.md against Google's open template** — Fetch Google's open-sourced design.md template and its cross-verification commands (the speaker does not name the exact commands). Tell the agent to run the verifier and fix each reported error until design.md passes. *When:* After design.md is first generated, to make sure it follows the expected structure before it is used as a source of truth.
- **Install an external design-principles audit skill per project** — Install Versalab's design audit skill in the project and run it against the UI. The skill points to an externally maintained source of principles instead of embedding them, so the audit reflects current guidance. Apply its fixes, then re-run. *When:* After the UI is built, to raise its quality against current design principles before the first review.
- **Derive design tests from design.md before writing UI code** — Ask Claude Code to write tests first, with design.md as the source of truth. Turn each anti-pattern into a static check, and each color, spacing, and typography rule into a programmatic assertion. Add Playwright visual regression tests and helper scripts such as a scan and report step. Only then implement the UI until the tests pass. *When:* Building UI with an agent where you want the implementation to be checked against explicit design rules rather than against its own output.
- **Visly local visual TDD loop** — Install the Visly CLI using the install command from its docs (the speaker does not show the command), then initialize it. Tell Claude Code to use TDD with the Visly CLI as the test medium. Start the Visly TDD command, which runs a local server that watches screenshots. Claude writes Visly-named tests that use Playwright's screenshot API to push images to the viewer. Approve or reject each diff in the viewer; rejected diffs go back to the agent as feedback for the next iteration. *When:* When you want to review UI changes by pixel diff across several iterations instead of comparing screenshots by eye or trusting the agent's self-check.
