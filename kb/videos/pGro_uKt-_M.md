> AI LABS walks through Claude Code creator Boris Cherny's setup advice: strip your Claude Code setup to a baseline with each new model, keep only what Claude can't infer, and gate work with evals that can fail. Includes a sponsored segment.

## Summary
The host presents tips from an interview with Boris Cherny, the creator of Claude Code, as relayed secondhand. The core advice is to delete your Claude Code setup (CLAUDE.md, skills, hooks, plugins) whenever a new model ships, because that setup is injected into context every session and was often written to correct older models. You then measure a baseline in safe mode, run the context and usage commands, and add back only what Claude cannot work out itself. A recurring "doctor" command is suggested for auditing the setup. The second half covers evals: each task needs a fixed pass/fail check written before building, and such checks expire after two or three model generations. Prompting advice is to describe the outcome, the limits and the definition of done rather than prescribing steps, and to describe style in words instead of pasting an inspiration image. The video ends with a four-level escalation ladder for model mistakes, guidance on CLAUDE.md versus skills versus MCP, and a warning that large multi-agent workflows are expensive and risky, with recurring cloud routines recommended for day-to-day cleanup work. A sponsored segment for Buzzy Canvas sits in the middle.

## Key ideas
- **Delete your Claude Code setup when a new model ships. Anthropic reportedly removed about 80 lines (unit not clear in captions) of Claude Code's system prompt after Opus 5 shipped.** — Everything you add (CLAUDE.md, skills, hooks, plugins) is injected into the context window at launch and stays there for the whole session. Much of it exists only to correct an older model's mistakes, so it becomes dead weight when a new model arrives. A project that is more than a few months old is likely tuned for a model two generations back. ([0:00](https://youtu.be/pGro_uKt-_M?t=0))
- **Measure what the setup costs before keeping it. The usage command shows the share of the five-hour window burned and breaks it down by skill and habit.** — The speaker's team found the main drains were workflows that spawn sub-agents, several sessions at once, and sessions left running without compaction. In an empty session the context command already shows about 3% of the 1M-token window used by Claude's own system prompt and built-in tools, which the user cannot remove. ([1:26](https://youtu.be/pGro_uKt-_M?t=86))
- **Use a safe-mode baseline to decide what earns its place. Run the normal tasks with all user-added clutter switched off and check whether results are still fine. Cut anything not needed.** — The keep rule is 'would Claude have worked this out on its own?' If yes, delete the line. Examples given: a dev-server start command Claude now infers, versus a non-default browser tool or a service that must be running first, which still belongs in CLAUDE.md. Anthropic's doctor command applies the same rule. It returns a health report with a verdict on each piece and proposed changes, and nothing changes until you accept each one. The speaker recommends running it after each model release. ([2:54](https://youtu.be/pGro_uKt-_M?t=174))
- **An eval is a fixed check that can come back as a no. Write it before building, because 'see if it looks better' is guessing.** — Examples: a page fits a phone screen, a wrong password is rejected, text contains no em dashes. Anthropic's own rewrites used three kinds of check. One was a full test suite, one was eight reviewer agents each looking for a single problem class, and one was a parity check that runs each command through old and new versions and compares answers. The speaker's Swift desktop-app rewrite compared screenshots pixel by pixel against the original running in a virtual Mac, and ran for over two weeks because the check kept it going. ([4:21](https://youtu.be/pGro_uKt-_M?t=261))
- **Evals expire. The speaker says checks last about two or three model generations, after which everything passes and the set must be replaced with checks aimed at where the agent now struggles.** — Treat the check set as versioned alongside the model, the same as the setup itself. ([7:07](https://youtu.be/pGro_uKt-_M?t=427))
- **Describe the outcome, the limits and what 'done' means, not the steps. Long, step-by-step prompts were a workaround for older models that went off the rails when given gaps.** — The speaker says experienced engineers are the worst at this because they try to make the model do the task the way they would. Aiming a bit beyond what you think the model can handle is also advised, since heavy detail usually signals an outdated assumption about its limits. ([8:34](https://youtu.be/pGro_uKt-_M?t=514))
- **Do not hand the model an inspiration image or a single good example and ask for 'more like it'. It returns near-copies. Describe the style and look in words so it has to work out the approach itself.** — The speaker's rule: concrete artifacts you supply are treated as things to copy, not things to learn from. ([9:36](https://youtu.be/pGro_uKt-_M?t=576))
- **When the model keeps getting something wrong, pick the cheapest fix that works: first make the instruction or product clearer, then a CLAUDE.md line for things needed every session, then a skill for things you explain repeatedly, then an MCP server only when the information is genuinely out of reach.** — CLAUDE.md is loaded at every session start, so it should stay short and hold only always-true facts. Skills load only when Claude needs them, so long or occasional material goes there, split across files so only the needed part loads. ([9:36](https://youtu.be/pGro_uKt-_M?t=576))
- **Dynamic multi-agent workflows that fan out hundreds of agents are costly and hard to recover from. The speaker's example, a BUN rewrite of about a million lines in under two weeks, reportedly cost about $165,000 at API pricing and left 19 breakages that existing checks missed. The speaker recommends routines instead.** — Routines are recurring cloud jobs that run after the laptop is closed. Anthropic reportedly runs 20 to 30 a day, each defined by a single-sentence prompt. Example prompts: remove dead code and leftovers from removed features; write tests for untested parts; merge places where the same thing was built twice. ([12:31](https://youtu.be/pGro_uKt-_M?t=751))

## Techniques
- **Baseline-then-add-back setup audit** — Launch Claude Code with all user additions turned off (the speaker calls this 'safe mode'; the flag name is not stated in the video, so check the Claude Code docs). In an empty session, run the context command to see the baseline (about 3% of 1M tokens per the speaker). Run your normal tasks and judge the output. Re-add only the CLAUDE.md lines, skills and plugins that change the result. *When:* After each new model release, or when a project has been untouched for months and was tuned for an older model.
- **Usage triage** — Run the usage command to see what share of the five-hour window is used, broken down by skill and by habit. Look for sub-agent fan-out, several parallel sessions, and sessions left uncompacted. *When:* When limits run out faster than expected, before changing the setup.
- **Keep-rule for CLAUDE.md** — For each line in CLAUDE.md, ask whether Claude would work it out from the project. Delete the ones it would. Keep lines where your setup differs from the default: non-default tools, required services that must be running, and areas where the model made mistakes. *When:* Each time you audit CLAUDE.md, especially after a model upgrade.
- **Doctor audit** — Run Anthropic's doctor command on the setup (the speaker names it but does not show the invocation). Review the per-item verdicts and proposed changes. Accept or reject each one individually. Nothing is applied automatically. *When:* Periodically, and after a new model release.
- **Fail-able acceptance checks written first** — Before building, write a binary check that can return no. Examples from the video: the page fits a phone-width viewport; a wrong password is rejected; the text contains no em dashes. For rewrites, run each command through old and new implementations and compare outputs (parity). For UI, screenshot the reference and the new version and compare pixel by pixel. *When:* At the start of any agent task that must reach a defined finish state, especially long runs that would otherwise stall.
- **Built-in headless browser verification** — Per the speaker, Claude Code now launches headless Chrome by default when building UI. It takes screenshots of regions to check for overlap and reviews code against project rules. Only failures that are visible on screen get caught, so add task-specific checks for silent failures. *When:* When building or changing a web UI and you want visual self-checks without writing a prompt line for them.
- **Outcome-first prompting** — State the goal, the constraints the agent must stay inside, and what finished looks like. Do not script the steps. For design work, describe the style in words instead of attaching a reference image. For ideation, do not paste one good example and ask for more like it. *When:* For any task with a model that is recent enough to plan its own route.
- **Escalation ladder for model mistakes** — Work through the four levels in order: (1) clarify the instruction or change the product so the task is clearer; (2) add a short CLAUDE.md line for facts needed every session; (3) write a skill for something you keep explaining, split across files if long; (4) add an MCP server only when the information cannot be reached any other way. *When:* When the model repeatedly gets something wrong and you are deciding where to put the fix.
- **Recurring cloud routines for maintenance** — Create recurring jobs that run in the cloud after the laptop is closed, each defined by a single-sentence prompt. The speaker's examples: remove dead code and leftovers from deleted features; write tests for parts with none; merge duplicated implementations. *When:* For ongoing cleanup and test coverage on a large project, instead of large one-off multi-agent workflows.

## Hot takes
- Deleting your whole setup on each model release is a strong recommendation drawn from one interview and relayed secondhand. The keep-rule ('would Claude work it out on its own') is the most transferable part.
- The claim that prompt injections from third-party skills can no longer get through is a vendor-side assertion, supported in the video only by one anecdote of a skill that asked to send data to a URL and was skipped. Treat it as unverified.
- The $165,000 and 19-breakages figures are the most useful caution in the video. The speaker recommends against swarm-style workflows for shipping, which conflicts with the 'aim higher' advice.
- The sponsored segment (Buzzy Canvas, around 7:07 to 8:34) is inserted in the middle of the tips and is not related to the advice. Per the scoring rules it caps quality at 2 even though the non-sponsored content is practitioner-grade (about 3).
