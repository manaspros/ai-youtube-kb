> Hands-on WorkOS workshop on writing Claude skills: description-based routing, constraints over prose, progressive disclosure, confidence gates, with-and-without-skill evals, and sharing skills.

## Summary
Nick Nisi and Zack Proser (WorkOS developer experience engineers) run a hands-on workshop on writing and using agent skills, building a "Repo Roast" skill as the running example. They argue skills beat always-loaded CLAUDE.md files for anything not relevant to every task, because a skill is a small folder whose description the model uses as a routing rule and whose reference files load only when needed. The core advice is to state a few constraints rather than write a long prescriptive novel, and to use bang-backtick script calls so deterministic data (git log, stale TODOs) is injected instead of guessed. For quality, they recommend a with-and-without-skill eval against a rubric, plus confidence-score gates that make the model ask clarifying questions before acting. Sharing is handled through repo folders, personal skill directories, git-backed plugin marketplaces, and zipped .skill folders for non-technical users. Several demos (a Remotion video, an image-to-video pipeline, the WorkOS CLI installer) show skills wrapping small scripts. Many claims are anecdotal, and the speakers flag some numbers as illustrative.

## Key ideas
- **A skill is a small folder, not just a file, and its description is a routing rule for the model** — The name and description in the front matter decide at runtime whether the skill loads. Descriptions are written for the model, not for humans. Skills are portable across repos and tools, unlike CLAUDE.md, which loads every session and is tied to one repo. ([5:12](https://youtu.be/pFsfax19yOM?t=312))
- **Give a few constraints instead of a long prescriptive document** — Speakers say three firm constraints (e.g. never be vague, always cite a line and commit) outperform a long markdown novel. Over-specifying is a common skill failure mode. Leave the model room where you do not care about the outcome. ([9:16](https://youtu.be/pFsfax19yOM?t=556))
- **Inject deterministic command output with bang-backtick so the model does not guess** — A script call written as an exclamation mark followed by a backtick-wrapped command is executed and its output replaces the placeholder before the model reads it. This gives a fixed input format and saves tokens. The speakers note this works in Claude; another tool needed an extension to match. ([17:06](https://youtu.be/pFsfax19yOM?t=1026))
- **Use a subagent for review loops so the main context stays clean** — The speaker runs verification and review inside a subagent that returns only a list of problems, which the main agent then feeds back into a fix loop. Use this when a task produces a lot of intermediate output and you only need the result. ([33:36](https://youtu.be/pFsfax19yOM?t=2016))
- **Keep the always-loaded instruction file tiny and push specifics into skills** — Global rules such as terse output or package-manager choice belong in CLAUDE.md, but testing or scoring details should sit in skills that only load for that task. The speaker suggests waiting a week, then asking the model to analyse the week's work and propose which skills to split out. ([19:47](https://youtu.be/pFsfax19yOM?t=1187))
- **Progressive disclosure: the skill is a router that points to reference files loaded only when relevant** — A SKILL.md can say to load a specific reference file only for a given task type, such as scoring or one framework's install guide. The WorkOS public skills use a router with a reference map, so an unrelated task never loads the Next.js guide. ([43:53](https://youtu.be/pFsfax19yOM?t=2633))
- **Confidence scoring with a rubric gates action until ambiguity is resolved** — The ideation skill scores its own understanding across fixed dimensions (problem clarity, goal, success criteria, scope, consistency). Below a threshold (around 95 percent) it asks multiple-choice questions before it writes a contract and builds. The speaker says the math is not rigorous, but the loop of clarifying is what helps. ([46:45](https://youtu.be/pFsfax19yOM?t=2805))
- **Test a skill against a no-skill baseline and reject it if it does not beat the baseline** — The WorkOS evals run the same task several times with and without the skill, grade each run against a rubric, and fail the skill when the with-skill grade is lower. The speaker says a skill may add only a few points, and that the baseline keeps changing as new models ship. ([28:12](https://youtu.be/pFsfax19yOM?t=1692))
- **Improve skills from real session transcripts, not from memory** — Claude stores conversations as JSONL logs. Reviewing a week of them shows edge cases, repeated clarifying questions, and tool calls that could be pre-supplied. Meta-skills such as skill-builder can run this review on your own workflow. ([49:26](https://youtu.be/pFsfax19yOM?t=2966))
- **Share skills through a versioned plugin marketplace, zipped folders, and local forks** — Teams publish public skills and internal marketplaces that install via git, so each engineer loads only the marketplaces they need. Zipping a skill folder and renaming it to .skill lets non-technical users drop it into Claude Desktop. Keep secrets out of zips. A personal modified copy can live as a local fork. ([1:04:56](https://youtu.be/pFsfax19yOM?t=3896))
- **Skills can wrap small scripts that call external APIs, making them a thin orchestration layer** — A roughly 30-line skill plus two Python scripts can chain an image-generation call into a video-generation call. Another skill wraps a TypeScript image API. The speaker says the markdown is the orchestration and the scripts do the calls. ([1:12:35](https://youtu.be/pFsfax19yOM?t=4355))

## Techniques
- **Description-as-router** — Write the front-matter description as a trigger for the model, say what the user will type, and test by asking the model when it would load the skill. *When:* Any new skill, and when a skill fails to load or conflicts with another skill.
- **Constraints over prescription** — List a few hard rules (never be vague, cite file and line, cite a commit) and let the model decide the rest, instead of writing step-by-step instructions. *When:* Writing skill bodies where the output needs to be consistent but the method can vary.
- **Bang-backtick command injection** — Put a script call in backticks after an exclamation mark in the skill file so its output is injected at load time. *When:* Anything that must come from current data in a fixed format, such as recent commits, stale TODOs, or git status.
- **Progressive disclosure via reference map** — Keep SKILL.md short. Add a router section saying which reference file to read for which condition, such as scoring, a framework, or a migration source. *When:* Skills with several sub-tasks or large reference material that should not sit in every context.
- **Subagent for verbose checks** — Run review or test loops in a subagent and have it return only the list of problems. *When:* When the check generates much intermediate output and the main context must stay focused.
- **Confidence-gated clarification** — Define a rubric of scored dimensions, have the model score its understanding, ask the user targeted questions below threshold, and proceed only above it. *When:* Vague one-line requests that turn into planning or spec work, such as ideation or feature scoping.
- **With-and-without-skill eval** — Run the task several times with no skill and with the skill, grade each against a rubric, and keep the skill only if the with-skill grade is higher. *When:* Before shipping a skill and when a new model is released.
- **Transcript-driven skill refinement** — After a week of use, review session logs for repeated questions, extra tool calls, and failures, then encode those fixes in the skill. *When:* Iterating on an existing skill, or finding which workflows deserve a skill.
- **Looped connector poll** — Use the loop command to run a prompt on an interval (the speaker uses 15 minutes) that reads Slack via a connector and creates or updates Linear tickets. *When:* Automating recurring triage of requests from chat into a tracker.

## Hot takes
- Skill descriptions are routing rules for the model, not documentation for people.
- Evals of skills are fuzzy math, but a baseline is still better than none.
- Just ask the model why it skipped a step or ignored an override; that is often the fastest debugging path.
- Over-prescribing a skill can make a capable model worse, so the skill can hurt.
- Ask the model to build the skill with skill-builder; a one-turn request is often faster than writing it by hand.
