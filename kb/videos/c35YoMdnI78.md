> Panel debate on whether agent "loops" (Ralph-style, bash-while-true) are hype or working practice; the consensus is loops work for verifiable tasks, need deterministic feedback and human-owned architecture, and are not yet a full software factory.

## Summary
A 1-hour Oxford-style debate hosted by Ali Howe (Insecure Agents podcast) with Dex Horthy (Human Layer), Geoff Huntley (creator of the Ralph loop), Ian Livingstone (Keycard) and Greg Pstrucha (Sentry). The pro-loop side (Huntley, Livingstone) argues loops are a core development pattern that already underlies CI, review and linting, and that they will spread as models get better at verifiable work. The skeptical side (Horthy, Pstrucha) argues the hype outruns the discipline, that non-deterministic verification compounds errors, that token costs are unsustainable at scale, and that humans must keep ownership of architecture. Panelists converge on a few practical points: verifiability decides where loops work, deterministic checks should close the loop, context windows should stay small and fresh per iteration, and teams should start with small incremental loops rather than end-to-end factories. Security and attribution were raised as open problems: agents cannot be trusted to stay aligned, secrets should not sit in files, shared agent memory lacks access control, and Git allows only one signer per commit. The format is entertaining and opinion-heavy, so most value is in the concrete heuristics and the disagreements rather than in hard data.

## Key ideas
- **Loops are not new; development already runs on them** — Ian Livingstone argues software has always been a try-learn-apply loop: CI/CD, PR review, design review, customer feedback and linting are all feedback loops. AI mainly removes human judgment from steps that used to need it, and software is unusually verifiable. ([10:45](https://youtu.be/c35YoMdnI78?t=645))
- **Verifiability decides where loops work** — Pstrucha says loops are reliable when checks are deterministic (types, linters, simulation tests) and cheap. Adding more non-deterministic verification compounds error: a 5% per-step error rate can reach roughly 50% failure after 10 to 20 iterations. ([25:19](https://youtu.be/c35YoMdnI78?t=1519))
- **Make the loop close on your domain rules through feedback the agent can read** — Huntley's approach: pre-commit hooks that print a prompt-style message back to the agent (for example a forbidden dependency boundary) rather than just failing. Humans find hooks slow, but agents do not mind. The engineer's job becomes keeping the loop on the rails. ([22:38](https://youtu.be/c35YoMdnI78?t=1358))
- **Use fresh context per iteration with the file system as state** — Ralph's core pattern is to restart the agent each iteration with the desired state, have it check the current state, do one step, and save progress to disk. Horthy calls the window below roughly 100k tokens the 'smart zone' and says he keeps hard tasks under about 60k. Compaction is lossy, so Huntley avoids it and allocates context deliberately, leaving headroom. ([27:21](https://youtu.be/c35YoMdnI78?t=1641))
- **Watch for dumb-zone symptoms such as test hacking** — Horthy's sign of the dumb zone is an agent that, deep in a session (around 200k tokens), starts hacking tests, dismissing failures as pre-existing, or flailing. The number is a starting guideline; experienced users build intuition for it. ([28:46](https://youtu.be/c35YoMdnI78?t=1726))
- **Models have different tastes, so re-test without your scaffolding for each release** — Huntley runs new models bare, with no skills or markdown, to see their default behaviour. Example: one model became timid when addressed in uppercase while another wanted emphatic prompts. He advises reading model cards for integrators. ([32:50](https://youtu.be/c35YoMdnI78?t=1970))
- **Loops fail loudly, and paying for verification can be a deliberate choice** — Pstrucha disputes the 'fail quietly' claim: builds and checks make failures visible. His team runs security scanning on PRs before and after landing (about $5 per PR) because it catches real issues humans miss. Loops suit well-specified problems with strong test suites, such as ports with existing tests; prototypes should be thrown away and re-specified if kept. ([36:15](https://youtu.be/c35YoMdnI78?t=2175))
- **Shared agent memory and attribution are unsolved; humans keep liability** — Livingstone suggests Markdown files as a memory substrate with per-file access control, noting Git allows only one signer per commit. He argues agents cannot carry liability, so the human who designed the loop is accountable. Pstrucha adds that the profession does not really carry personal liability either. ([39:11](https://youtu.be/c35YoMdnI78?t=2351))
- **Architecture decisions stay with humans because agents add complexity without bound** — Pstrucha says the key human decisions are what not to build and where to spend complexity versus simplicity. Agents keep adding to the stack unless constrained. ([41:48](https://youtu.be/c35YoMdnI78?t=2508))
- **Start with small incremental loops for 2 to 3x gains, not a full factory** — Horthy's warning: teams that spend three months building an end-to-end factory without testing it with users end up with something nobody uses. He advises building small loops throughout the system, aiming for 2 to 3x speed while keeping the code readable and owning the architecture. ([47:59](https://youtu.be/c35YoMdnI78?t=2879))

## Techniques
- **Fresh-context loop with file-system state** — Each iteration starts a new agent session that receives the desired end state, reads the current state from disk (for example a plan file or git), performs one step, saves progress, and exits. A thin non-LLM loop restarts it. *When:* Long unattended runs where context rot or overflow would otherwise degrade work.
- **Back-pressure hooks that talk back** — Pre-commit hooks, linters and type checks return explicit prompt-style guidance (for example a boundary rule the change violated) so the agent can correct itself before the loop is allowed to close. *When:* Agent loops that should not finish until domain and architecture rules hold.
- **Deterministic controller around the LLM step** — Non-LLM code decides whether to continue, assembles small prompts from new inputs such as PR comments, and checks completion. Huntley's idea is a PID-style controller that decides whether the loop should keep running. *When:* Follow-up work triggered by external events, such as review comments that arrive hours after a PR is opened.
- **Context budget with headroom** — Cap each session well below the model's maximum window, around 100k tokens as a starting point. Batch large data into pieces that fit, and do not rely on compaction for fidelity. *When:* Batch processing of large data sets, or any hard task where quality drops in long sessions.
- **Bare-model baseline on each new release** — Strip skills, markdown instructions and custom prompts, then run the new model on a task to see its defaults before re-adding scaffolding. *When:* A new model is released and the team is deciding what instructions to keep.
- **Explicit cost decision for high-value verification** — Run expensive scanners on PRs (about $5 per PR in Pstrucha's case) when they reliably catch real issues that human review misses, and accept the cost as a deliberate choice. *When:* Security or correctness checks on agent-written code where a missed bug is costly.
- **Start small and iterate on real users** — Build small incremental loops inside existing workflows and put them in front of teammates early, rather than designing a full autonomous pipeline in isolation. *When:* Rolling out agent automation to an engineering team.
- **Vendor code and minimise open-source dependencies** — Keep dependencies in the repo so the agent can modify them directly, and generate small utilities to specification instead of importing packages. *When:* Reducing supply-chain exposure, for example to npm attacks.
- **Prefer statically typed languages for agent-maintained code** — Choose languages with strong type systems (the speaker cites Rust and Haskell) because types act as machine-checkable verification for agent changes. *When:* Choosing a stack for a codebase that agents will change heavily.

## Hot takes
- Loops fail loudly, not quietly, so the 'silent failure' critique is wrong (Pstrucha).
- Static types are a form of verification, and building loops in Python or Ruby is a clown show (Horthy).
- Git only allows one signer per commit, which is a problem for agent-written code (Livingstone).
- Engineers do not really carry personal liability, so 'we are engineers' is a stretch (Pstrucha).
- Agents should not be given secrets as files; the most concrete security step is to avoid them (Livingstone).
- Most people should not use coding tools on a laptop as things stand, but the real risk is the existing npm supply chain (Huntley).
- The 'just write loops' advice is not safe to give to millions of people; it only fits people who already know how to tune them (Huntley).
