> Ryan Cooke (WorkOS) on why a sandbox plus coding agent is not a software factory. Build around outcome metrics, webhook-driven product workflows, and an internal MCP gateway.

## Summary
Ryan Cooke of WorkOS argues that the common "sandbox plus agent makes a PR" setup is not enough. Output metrics such as PR count or percentage of AI-written code can hide whether the work changes outcomes, so WorkOS measures feature delivery speed, defect rate, and time to recovery instead. Their first version looked no different from engineers running Claude Code on laptops, so they embedded engineering process into the factory. TARS is the interface, living in Slack, Linear and GitHub and driven by webhooks, and Horizon is the orchestration layer in front of an MCP gateway. A PM agent drafts the product doc from a short brief and, once a human approves it, breaks the work into Linear tickets that TARS then executes in dependency order, re-checking the plan for gaps between tickets. The MCP gateway, which the speaker calls a context engine, carries system prompts and tool descriptions that explain Snowflake semantic tables and internal systems, and it is now used well beyond coding agents, including Slack data queries. The next steps are owning sandbox infrastructure, an evergreen org memory layer, and mining agent sessions to find missing or obsolete skills. Quantitative results are not given; the talk is an architecture and process account with a closing booth pitch.

## Key ideas
- **Measure software factories by outcomes, not output** — PR counts and the share of AI-written code can hide whether work is actually driving results. WorkOS tracks feature delivery speed, defect rate, time to recovery, and whether engineers choose cloud sandboxes over local harnesses. ([1:32](https://youtu.be/HvboD89DyQ8?t=92))
- **A bare sandbox plus coding agent does not beat laptop use** — WorkOS's first factory (a Cloudflare sandbox with a model router) produced output that was hard to tell apart from engineers driving Claude Code locally. Real gains came only after the team's engineering process was encoded into the system. ([3:00](https://youtu.be/HvboD89DyQ8?t=180))
- **Split the factory into a user interface layer and an orchestration layer** — TARS is the interface, embedded in Slack, Linear and GitHub and fed by webhooks so it can track project progress as well as write code. Horizon is the infrastructure orchestration layer that sits in front of an MCP gateway. ([4:00](https://youtu.be/HvboD89DyQ8?t=240))
- **Drive ticket execution from dependency graphs and completion webhooks** — Linear tickets carry blocking relationships. When a ticket completes, a webhook lets TARS pick up the next unblocked ticket, so a planned map of work runs without a human shepherding each step. ([5:34](https://youtu.be/HvboD89DyQ8?t=334))
- **Have the agent re-check the plan between steps** — After each ticket completes, the team asks the agent whether the Linear project is now missing tickets. Plans are kept current because the agent finds gaps while doing the work. ([5:34](https://youtu.be/HvboD89DyQ8?t=334))
- **A PM agent drafts the product doc, and human approval starts the build** — WorkOS has no product managers. Product engineers write a PRD-style doc covering customer input, competitive analysis, early designs and milestones. An agent drafts it from a short brief, and when the doc is approved in Linear, the agent begins implementation. Humans can comment at each stage. ([6:58](https://youtu.be/HvboD89DyQ8?t=418))
- **An internal MCP gateway is the highest-leverage piece** — The gateway connects internal systems and carries system prompts and tool descriptions that say how to use each tool and what it holds, for example which Snowflake semantic tables answer which questions. The speaker says it ended up serving many more teams than the coding agents it was built for. ([12:28](https://youtu.be/HvboD89DyQ8?t=748))
- **Mine agent sessions to maintain the skill library** — With the team owning its infrastructure, agent sessions can be reviewed to find where a skill is missing because the agent made a mistake, and which skills have gone stale as the code changed. The speaker frames this as continuous verification. ([14:51](https://youtu.be/HvboD89DyQ8?t=891))

## Techniques
- **Outcome-based factory metrics** — Track feature delivery speed, defect rate, time to recovery, and voluntary adoption (for example, engineers moving from local harnesses to cloud sandboxes) instead of PR counts or share of AI-written code. *When:* Before funding a dedicated team to automate engineering work, so you can tell whether it changes outcomes.
- **Webhook-driven ticket pipeline** — Model work as a tracker ticket graph with blocking dependencies. Subscribe the agent to ticket-completion webhooks so it starts the next unblocked ticket on its own. *When:* Large features that split into ordered tickets and need little human shepherding between steps.
- **Agent plan refresh after each step** — On each completed ticket, ask the agent to re-read the project and report missing tickets, then add them to the plan. *When:* Plans are expected to change during execution and gaps show up only once work starts.
- **Agent-drafted PRD with human approval gate** — Give the agent a short brief plus customer and competitive context. It drafts the product doc and breaks it into tickets. Humans edit or cut scope, and approval status triggers the next stage. *When:* The blank-page problem slows planning, and an imperfect first draft that engineers edit is cheaper than writing from scratch.
- **Context-rich MCP gateway** — Put one internal MCP server in front of all internal systems. Tool descriptions document each data source's contents and when to query it, and system prompts describe how the tools are organised. *When:* Several agents or teams need the same internal data, and agents otherwise guess which tables or tools to use.
- **Session mining for skill gaps** — Review agent sessions to find recurring mistakes that point to a missing skill, and check whether existing skills are still accurate given code changes. *When:* You own the agent infrastructure and can see session data, and skills are maintained by hand.

## Hot takes
- Percentage of PRs or number of PRs written by AI can mask whether the work drives outcomes.
- A sandbox plus coding agent that opens PRs is roughly indistinguishable from engineers using Claude Code on their laptops.
- An internal MCP gateway with good tool descriptions is worth building before the factory itself.
- Teams should own their sandbox infrastructure rather than rely on sandboxes-as-a-service.
- Product manager roles can be replaced in part by engineers who own the PRD, with an agent drafting it.
