> Better Stack podcast with Resend's DX engineer on getting LLMs to recommend a vendor, scoping per-team AI agents with narrow API keys, and email deliverability basics. Mostly biographical, with a few practitioner nuggets.

## Summary
A Better Stack podcast episode (Ep. 15) with Chris Penningson, DX engineer at Resend, an email API company. Most of the hour covers his background, his YouTube habits, home studio gear and launch-week video production. The practitioner content is in three places. First, he describes how Resend tries to get Claude and other LLMs to recommend it: standard SEO basics, machine-readable pages, Q&A blocks, and a recency effect that favours newer vendors, with a self-reported figure of about 70% of the time. Second, he describes Resend's internal AI agents, each scoped to one team or task, with its own vault and narrowly limited API keys, reporting through Slack and easy to shut off. Third, he gives a deliverability checklist, centred on domain reputation, subdomains, consent and authentication records. The hosts add a hot take that every site should default to Astro. Most of the episode is not transferable engineering material.

## Key ideas
- **Run many narrow agents, one per team or task, instead of one general agent** — Resend's marketing team has its own agent instance with its own password vault, its own Twitter and LinkedIn accounts, and access limited to scoped API keys. Other teams run agents for narrow jobs such as incident summaries. The speaker says the agents were started by a single team and other teams copied the idea after seeing it work. ([27:53](https://youtu.be/8ahyAKK2l9Y?t=1673))
- **API key scoping and easy revocation are the main control, not trust in the agent** — He says the reason to scope keys is so you can give an agent keys for one particular task and nothing more. If a use case looks wrong, the team limits or pulls the key. He says Resend wants to invest more in API scoping for agents, and that scoping matters more as tools like OpenClaw spread. ([30:18](https://youtu.be/8ahyAKK2l9Y?t=1818))
- **Concrete recurring agent jobs: a Monday analytics digest and weekly competitor watch** — A marketing agent runs every Monday and pulls Twitter, LinkedIn, SEO and documentation-question data into a weekly report. A social agent (Hermes, an OpenClaw-based agent) did competitor analysis once a week, and later moved to on-demand use. He says it was poor at writing tweets, so it was kept for research and summaries. ([29:20](https://youtu.be/8ahyAKK2l9Y?t=1760))
- **Use agents for context gathering before writing, not for final output** — He asks an agent to use the GitHub CLI to find who worked on a feature, read the RFC, and return a bullet list of what a changelog should cover. He also has agents scaffold new landing pages from patterns already in the codebase, with the human writing the copy. ([25:33](https://youtu.be/8ahyAKK2l9Y?t=1533))
- **Getting recommended by LLMs is mostly SEO basics plus being early, and it is unstable** — The listed basics are JSON-LD, one H1 per page, llms.txt, a markdown version of key pages (for example, a curl request to the pricing page returns markdown), and Q&A accordions, which he says LLMs favour. He also mentions comparison pages written with other vendors. He attributes part of the effect to a recency bias that favours newer vendors and says models change often, so the work has to be repeated. ([20:13](https://youtu.be/8ahyAKK2l9Y?t=1213))
- **Claimed result: Claude suggests Resend about 70% of the time, with no data shown** — This is a self-reported figure with no measurement method given. He also says Resend has no direct way to tie AI referrals to signups. Growth is credited to word of mouth, Supabase integration traffic as Lovable and similar tools grew, and AI in general. ([21:36](https://youtu.be/8ahyAKK2l9Y?t=1296))
- **Deliverability depends mainly on domain reputation, so isolate sending by subdomain** — He says Gmail mostly tracks the sending domain's reputation rather than the IP's. Send from a subdomain per stream so a problem can be moved without affecting the whole platform. Include unsubscribe links on non-transactional mail, and set SPF, DKIM and DMARC. Mail should only go to people who have opted in, and volume should be steady, not a sudden bulk send. ([39:29](https://youtu.be/8ahyAKK2l9Y?t=2369))
- **Deliverability checks: link and image domains match the sender, avoid spammy wording, and read per-email insights** — Links and images should use the sending domain. Gmail's own spam reasons can guide wording changes. Resend shows deliverability insights for each sent email in its emails table. ([43:13](https://youtu.be/8ahyAKK2l9Y?t=2593))

## Techniques
- **One scoped identity per agent or team** — Give each agent its own instance, its own secret store (he names a 1Password vault), and API keys that only cover the endpoints its task needs. Use Slack as the only interface. Keep the ability to shut an agent off by revoking or narrowing its key. *When:* Any agent that holds credentials for third-party accounts such as social media, analytics, or an incident tool.
- **Scheduled weekly digest agent** — A cron-style job (every Monday) that pulls analytics from Twitter, LinkedIn, SEO and the docs site, plus common user questions, then posts a short report. The speaker gives no implementation details beyond the schedule and data sources. *When:* Recurring reporting where a human otherwise spends time collecting numbers.
- **Weekly competitor watch, on demand** — Have the agent read competitors' recent posts and summarize themes. Ask it for background on a single post when needed. Do not use it to draft final posts. *When:* Market or competitor monitoring. Output is research for a human to act on.
- **Research agent before writing a changelog or post** — Ask the agent to use the GitHub CLI to list contributors to a feature, read the linked RFC, and return a bullet outline of what to cover. Write the text yourself. *When:* Release notes or changelog drafts where the facts are scattered across PRs and RFCs.
- **Scaffold landing pages from existing repo patterns** — Point the agent at an existing landing page or customer story in the codebase, paste in the new copy, and ask for a new page with the same structure. *When:* Repetitive marketing pages that share one layout.
- **LLM-discoverability checklist for a docs or marketing site** — One H1 per page. JSON-LD structured data. An llms.txt file. Make key pages available as markdown so a plain curl returns markdown (he gives the pricing page as an example). Add FAQ accordions with Q&A text. Publish comparison pages that cover peer vendors. Track the result, which he says can change with each model release. *When:* A developer product where AI assistants are likely to pick the tool for the user.
- **Deliverability setup for a transactional email service** — Send each stream from its own subdomain. Use the sending domain for links and images. Add unsubscribe links to non-transactional mail. Configure SPF, DKIM and DMARC. Send only to opted-in addresses. Keep volume predictable. Read per-email deliverability insights after each send. *When:* Any app that sends email at scale, especially from a new domain.
- **Obsidian vault synced to GitHub as a personal task store** — Keep tasks as Markdown in an Obsidian vault, sync the vault to a GitHub repo, and let a personal agent read it. The speaker says the setup is complicated and gives no details. *When:* Personal task management where the agent should read the same task list the human uses.

## Hot takes
- Every website should default to Astro; the speaker says it covers most basic sites and avoids React Server Components' mental-model and security problems. [57:24]
- React Server Components' mental model is hard to explain, and an explanation that needs another framework signals a poor design. [55:59]
- AI agents are not good at writing social posts; they are better for research and competitor watch. [31:36]
