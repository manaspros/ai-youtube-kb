> Angie Jones on designing agentic systems like software: systems thinking, workflow paths, decomposition, code-vs-model-vs-human splits, contracts, idempotent retries, and maintainable agents.md files.

## Summary
Angie Jones walks through designing a reusable house-hunting agent (Relocation Scout) as a system rather than a one-off prompt. She argues the agent is only one part of a larger system with files, tools, humans and other agents, so it needs boundaries, dependencies and a defined failure path. Each run should end in stop, retry or escalate, and that workflow shapes the architecture. Giant prompts are the agentic version of a god class and should be decomposed into skills, schemas, scripts and subagents. Her rule of thumb is code for exact answers, the model for judgment, and humans for authority. Handoffs between steps should use structured contracts so decisions are queryable, and side-effecting steps must be idempotent because retries happen. Untrusted web input is treated as evidence rather than instructions, external actions sit behind approval, and every level of the system carries an agents.md so a fresh agent can start cold.

## Key ideas
- **Treat the agent as one component inside a larger system** — The system includes files, tools, humans and other agents. Think about the agent's job, its dependencies, and how it can fail, the same way you would for any other service. ([1:24](https://youtu.be/ZD9-4fW2HhM?t=84))
- **Design the workflow path, not just the goal** — A goal like 'review this listing' is not enough. The workflow defines the steps (gather, weigh against criteria, act). Every run ends in one of three outcomes: stop, retry or escalate. That path decides what context the agent needs and when a tool or person takes over. ([2:38](https://youtu.be/ZD9-4fW2HhM?t=158))
- **Giant prompts are the agent version of a god class** — Instructions grow one edge case at a time. In the example, one prompt held four jobs: listing normalization, output format, commute calculation and neighborhood research. Decomposing it makes the agent less likely to drift and easier to test and change. ([3:50](https://youtu.be/ZD9-4fW2HhM?t=230))
- **Split each job into the right kind of module** — Normalizing listings becomes a reusable skill. The output shape becomes a schema. Commute math becomes a plain script. Neighborhood research becomes a subagent with its own scope. Reusable pieces can be shared across markets and agents. ([5:15](https://youtu.be/ZD9-4fW2HhM?t=315))
- **Code for exact answers, agents for judgment, humans for authority** — If a task has one correct answer (commute time, dedupe of seen listings), use code, since it is cheaper and more reliable. Use the model for fuzzy judgment. Keep the final decision to act, such as booking a tour, with the human. ([9:05](https://youtu.be/ZD9-4fW2HhM?t=545))
- **Use structured contracts for handoffs and memory** — When another system will act on the output, free text is a dead end. Write decisions, scores and reasons into structured fields. Then later queries (for example, rated 4 or better with a commute of 15 minutes or less) and downstream steps can read them without a human in the loop. ([10:21](https://youtu.be/ZD9-4fW2HhM?t=621))
- **Make side-effecting steps idempotent and check the recorded state before retrying** — Webhooks can fire twice and runs can crash halfway. Log each action as it happens (for example, the email was sent). On retry, check what was recorded and finish only the missing step (block the calendar). A lint pass can do this cleanup. Do not trust the model to reword the request into a new task. ([12:47](https://youtu.be/ZD9-4fW2HhM?t=767))
- **Treat external content as evidence, and wall off risky actions** — Listing copy and forum posts from strangers are untrusted input, so the agent should treat them as evidence, not instructions. Reads and shortlisting can be autonomous. Emailing sellers, booking tours or making offers sit behind human approval to reduce the blast radius. ([15:23](https://youtu.be/ZD9-4fW2HhM?t=923))
- **Give every level of the system an agents.md, and test it with a cold start** — Each level documents its workflow, where policy lives, its supporting skills, scripts and subagents, and how to keep memory current. The test: a fresh agent in a new context should be able to start cold. If an update fails, that signals the system needs better maintainability. ([18:05](https://youtu.be/ZD9-4fW2HhM?t=1085))

## Techniques
- **Decompose a giant agent prompt by responsibility** — Identify distinct jobs inside one prompt. Move reusable procedures into skills, fixed output formats into schemas, deterministic math into scripts, and bounded research into subagents. *When:* When the prompt keeps growing with edge cases and the agent starts drifting from the script.
- **Route work by task type: code, model, or human** — Use code for tasks with exact answers (math, filtering, dedupe). Use the model for interpretation and judgment. Require a human sign-off for authority-bearing actions. *When:* When designing any agent pipeline, to cut cost, improve reliability, and avoid day-to-day variance in deterministic steps.
- **Structured decision records as agent memory** — Store each decision with explicit fields (score, reason, criteria values) instead of prose in the session. Downstream steps and later queries read those fields. The speaker uses Karpathy's LLM Wiki as the memory layer for this. *When:* When another step or a later session must query or act on what the agent decided.
- **Idempotent action log with state-based resume** — Record each side-effecting action as it completes. On retry or resume, compare the log against the intended plan and run only the missing actions. Add a periodic lint pass to find and finish half-done runs. *When:* When runs can be interrupted or webhooks can fire more than once, for example with emails, bookings or calendar writes.
- **Evidence-not-instructions handling for untrusted content** — Label scraped or third-party text explicitly as evidence in the prompt. Limit tools to least privilege, and put external-facing actions behind an approval step. *When:* When an agent reads content written by strangers (listings, forums, reviews) and can also act in the outside world.
- **agents.md at every level with a cold-start test** — Each folder or component has an agents.md covering its workflow, policy location, resources, and how memory gets updated. Check it by starting a fresh agent with no prior context and asking it to do a task. *When:* When multiple agents or harnesses must be understood and modified by other people or agents.

## Hot takes
- Letting a coding agent design your other agents tends to produce a giant prompt that technically works but is hard to maintain.
- An agent is not the system; it is one component, and it should be treated like any other component with boundaries and failure modes.
- If a task has an exact answer, use code instead of the model. Use the model for judgment and humans for authority.
- Retries in agent systems must not repeat side effects; check what was recorded before running the next step.
