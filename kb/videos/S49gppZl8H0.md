> Walkthrough of Anthropic's Claude Code review system, rebuilt as skills: eval.md gates before build, a fresh-context builder/verifier/reviewer loop, risk tiers, and git rollback.

## Summary
The host argues that coding agents declare work done while missing requested items, so verification is the key step. He relays Anthropic's Claude Code team process: checks run during the build, each feature gets strict eval.md pass/fail checks written from a requirements file and approved by a human before building, and a hook blocks "done" until evals pass. A separate reviewer agent with a fresh context checks each change, guided by a review.md rules file linked from CLAUDE.md. A builder/verifier/reviewer loop, tracked in state.md, iterates in rounds until the evals pass and the review finds nothing new. Consequence-based risk tiers set how strict the checks are, and fresh-context agents that cannot read the app's code act as first-time users. Git branches per feature provide rollback, and a fix-a-bug skill reproduces, tests a hypothesis, then fixes. The team figures are secondhand from Anthropic's article, and the host shows the process as skills he built rather than the exact prompts.

## Key ideas
- **Agents declare work done and miss requested items, so checking what was actually built is the core step.** — The host relays Anthropic's claim that its setup produced more than twice as many changes while the share of changes that had to be undone fell by over 40 percent. These are secondhand figures from Anthropic's article, not data shown in the video. ([0:00](https://youtu.be/S49gppZl8H0?t=0))
- **Review cannot be skipped, and rushed review shifts the cost to later when fixes are more expensive.** — Daily changes to review at Anthropic reportedly rose from about 2,500 to over 30,000 in four months. The team says rushed review leads to about twice the total time, counting the later bug fixes. ([1:27](https://youtu.be/S49gppZl8H0?t=87))
- **Reframe review from did someone read the code to what could go wrong and how we would catch it, and run checks during the build.** — Checks now happen while Claude is building, so a change reaches the human already checked and fixed at least once. Human attention goes to the parts most likely to break. ([1:27](https://youtu.be/S49gppZl8H0?t=87))
- **Evals are fixed, strict pass/fail checks written before building, and a human approves them before any code is written.** — Each feature gets an eval.md that is the method the agent uses to check its own work. Feature designs go into a mockup page first, which becomes the target the app is checked against. Without the human review of the evals, the agent should not build. ([2:41](https://youtu.be/S49gppZl8H0?t=161))
- **A hook prevents the agent from marking a task done until its evals pass.** — The hook enforces the gate mechanically rather than relying on the agent's own claim that it is finished. The host created it through a skill. ([2:41](https://youtu.be/S49gppZl8H0?t=161))
- **The reviewer should be a separate agent because the builder agrees with its own decisions.** — The team runs a separate reviewer on every change before a person sees it. Anthropic's lighter version is the code review command, which reads all changes and reports breaking mistakes at a chosen effort level, where low reports only high-confidence findings. ([5:36](https://youtu.be/S49gppZl8H0?t=336))
- **Persistent review rules live in review.md, linked from CLAUDE.md so each session loads them.** — review.md states what counts as a real failure, how severe each one is, how to report, and how the app should be tested. It is not read by default, so the host links it from CLAUDE.md. ([5:36](https://youtu.be/S49gppZl8H0?t=336))
- **A loop of fresh-context subagents (builder, verifier, reviewer) is driven by an orchestrating main agent.** — The builder builds from the requirements. The verifier checks each eval as pass or fail. The reviewer looks for anything the evals missed, using review.md. The loop writes state.md to track the round and what is still failing. ([7:04](https://youtu.be/S49gppZl8H0?t=424))
- **Recurring reviewer findings become standing rules that persist across sessions.** — Claude does not remember earlier mistakes, so each recurring problem becomes a one-line rule in a learned-rules section at the bottom of review.md. The loop proposes the rule at the end, and it is added only after the human approves. ([9:54](https://youtu.be/S49gppZl8H0?t=594))
- **Scale checks by consequence: how bad is it for a customer if this breaks?** — Cosmetic issues are low risk. Features that stop working but lose nothing are medium. Lost money, lockout, or another person's data is high. High-risk changes get stricter evals and the full review, and low-risk changes get a quick one. ([11:11](https://youtu.be/S49gppZl8H0?t=671))
- **Without stop rules, builder and reviewer loops can ping-pong indefinitely, so the team added round caps and delta-only review.** — The team reported one change that looped more than 50 times and found that about 59 percent of reviewer findings had been present since round one. Its three rules: stop after three rounds and have the builder rethink the approach; after round one, review only what the last fix changed; and classify each finding so the builder fixes every instance of that kind. ([11:11](https://youtu.be/S49gppZl8H0?t=671))
- **The host's own loop runs five rounds, stops early if the same problem persists after two, and adds browser-based eval checks.** — The host deliberately departs from the team's three-round cap. Each round builds the feature, checks every eval in the browser, then reviews the code. ([12:39](https://youtu.be/S49gppZl8H0?t=759))
- **A fresh agent that is blocked from reading the app's code can act as a first-time user, and it runs on a temporary database.** — The agent is prevented from reading code directly and also through terminal workarounds. The run reports every place a new user might get stuck and suggests fixes. ([13:47](https://youtu.be/S49gppZl8H0?t=827))
- **Git branches per feature and a fix-a-bug skill make mistakes reversible.** — The CLAUDE.md tells Claude to use a branch per feature and save each working version. A fix-a-bug skill reproduces the bug, checks whether its guess about the cause was right, then fixes and reports it. ([15:15](https://youtu.be/S49gppZl8H0?t=915))

## Techniques
- **Eval-first feature gating** — Keep specs/<feature>/ with a requirements file (transcript says rd.md, possibly a caption error). Use a skill to write eval.md for each feature, using a shared template so every eval has the same structure. If the feature has a design, build a mockup page first and use it as the visual target. Have the agent request human review of the evals and refuse to build until approved. Add a hook that blocks marking the task done until the evals pass. Set the status to draft, then in review after the agent finishes, then reviewed after approval. *When:* Before any agent builds a feature that has acceptance criteria or a visual design, especially when you will otherwise have to check the work yourself.
- **Fresh-context builder/verifier/reviewer loop** — Create a review-loop skill and three subagents. The main agent is the orchestrator. The builder implements from the requirements and eval.md. The verifier marks each eval pass or fail. The reviewer searches for gaps the evals missed, using review.md. The orchestrator writes state.md (round number and open failures), starts each agent with a fresh context, and repeats until all evals pass and the reviewer has nothing new. Run it by invoking the review-loop command with the feature name. *When:* When you need an independent check that does not share the builder's context, so the reviewer does not simply agree with the builder's decisions.
- **Reviewer loop stop rules** — Cap rounds (the team uses 3; the host uses 5). After round one, the reviewer checks only the delta from the most recent fix and does not re-report earlier findings. Require each finding to be tagged with its problem class so the builder fixes all instances, not just the one flagged. After 3 rounds, the reviewer stops listing issues and tells the builder to rethink the approach. The host also stops early if the same problem remains after 2 rounds. *When:* Whenever a builder and reviewer loop might oscillate or spend the token budget on repeated old findings.
- **review.md with a learned-rules section** — Write review.md in the project root with what counts as a real failure, severity levels, the reporting format, and the test methods. Link it from CLAUDE.md so it loads each session. At the bottom, keep a learned-rules section. When a bug escapes review, or a review repeatedly flags something that is not a problem, the loop proposes a one-line rule. Add it only after approval. *When:* For any repo where you run AI code review repeatedly and want the reviewer to stop repeating the same misses or false positives.
- **Consequence-based risk tiering** — Before building, ask one question: what happens to a customer if this breaks? Cosmetic is low. Stops a feature but loses nothing is medium. Loss of money, lockout, or exposure of another person's data is high. Save the rating through a skill. Pass the rating to the eval skill so high-risk features get stricter evals and a full review. Low-risk features get a quick review. *When:* When the review budget is limited and changes differ in how much damage a mistake could cause.
- **First-time-user agent test** — Create a skill that launches sub-agents forbidden from reading the app's source code. Enforce this with a hook that blocks file reads and also terminal-based reads. Point the agent at a temporary database. Ask it to walk through the feature like a new user and report each point where someone might get stuck, along with suggested fixes. Invoke it with the skills command and name the feature. *When:* After a feature passes its evals, to catch usability gaps that the builder, who knows how the feature works, would miss.
- **Git branch per feature with rollback** — In CLAUDE.md, instruct Claude to create a git branch for each feature and save every working version. Create a fix-a-bug skill that takes a problem description, reproduces it step by step, tests the cause hypothesis, applies the fix, and reports the result. To roll back, use git to locate the change that introduced the regression and revert to the last working version. *When:* For any agent-built change where a regression may surface later and you need to undo it quickly.
