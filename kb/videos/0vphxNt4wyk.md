> Philipp Schmid (Google DeepMind) argues skills need evals like code does, and gives a lean eval-harness recipe: trigger tests, regex asserts, repeated trials, and with/without-skill ablations to decide when to retire a skill.

## Summary
Schmid opens with a survey: nearly everyone uses coding-agent skills and almost nobody has evals for them. He says SkillsBench indexed about 50,000 GitHub skills and found almost none had evals, and that AI-written skills often go unchecked. He splits skills into capability skills (temporary, retire as models improve) and preference skills (durable, encode team or company style, so they need evals to guard against regressions). He reports SkillsBench 1.1 found skills improve performance by roughly 15% on average, but AI-generated skills can hurt it, so human-written skills win. His writing advice is to keep the description directive and specific (when, why, how, plus negative cases), keep SKILL.md lean with reference files for details, prefer goals and constraints over step lists (use a script when the workflow is fixed), and remove no-op instructions. His worked example is a Gemini Interactions API skill tested on 117 cases with a JSON file of prompts and checks plus a small runner that calls the Gemini CLI and applies regex asserts, reaching almost 90% valid code. He says DeepMind runs these evals in CI on every skill change and merges only if they improve, and recommends 3 to 6 trials per case, isolated workspaces, outcome-based checks, testing across harnesses, and ablations with and without the skill.

## Key ideas
- **Almost no skills in the wild have evals, and you cannot tell if a failed task is due to a bad skill or a task that is too hard for the model.** — SkillsBench indexed about 50,000 GitHub skills and found almost none had evals. Agents are non-deterministic, so a failure has two possible causes that look the same without a test. ([0:48](https://youtu.be/0vphxNt4wyk?t=48))
- **Split skills into capability skills and preference skills, and treat them differently.** — Capability skills teach something the model cannot yet do reliably, so they are temporary and evals show when to retire them. Preference skills encode team or company workflow and style, are durable, and need evals to catch regressions when agents or models change. ([3:24](https://youtu.be/0vphxNt4wyk?t=204))
- **Skills help on average, but AI-generated skills can hurt, so review and size-limit them.** — SkillsBench 1.1 covers about 100 coding and productivity tasks across models and harnesses, with skills improving results by roughly 15% on average. Human-written skills performed best and AI-generated ones sometimes lowered performance. He suggests keeping SKILL.md under about 500 lines. ([4:19](https://youtu.be/0vphxNt4wyk?t=259))
- **The description is the always-paid part of a skill, so it must be directive and cover when not to fire.** — The description sits in context on every model call, so it should be short but specific. Use directives (use it when building a chat app) over passive prose, state why and how the skill applies, and add negative cases so it does not over-trigger, for example limiting a web-dev skill to React only. ([6:43](https://youtu.be/0vphxNt4wyk?t=403))
- **Use progressive disclosure: keep the body lean and push provider-specific detail into reference files.** — Name and description load first, then the body, then deep reference files. A multi-cloud deploy skill should hold AWS, GCP and Azure details in separate references that the model opens only when relevant. ([7:51](https://youtu.be/0vphxNt4wyk?t=471))
- **Give goals and constraints rather than step lists, and move fixed workflows into scripts.** — If the procedure is always identical, a script saves tokens and the model just calls it. Otherwise describe the goal and constraints and let the model work out the steps. He also recommends deleting no-op instructions that do not change behavior, since they cost tokens on every use. ([9:03](https://youtu.be/0vphxNt4wyk?t=543))
- **The eval harness is cheap: a JSON file of prompts and checks, plus a runner that drives a coding agent and applies regex asserts.** — For the Gemini Interactions API skill he wrote 117 cases from real user prompts, synthetic cases and feedback. Each case has a prompt, a language (TypeScript or Python), a should_trigger flag and expected checks such as the right SDK, model ID and methods, and no old patterns. Regex is cheap enough to rerun on every new model. Reports almost 90% valid Interactions API code. LLM-as-judge is reserved for whole-trace checks. ([12:51](https://youtu.be/0vphxNt4wyk?t=771))
- **Gate skill changes in CI on eval results, and design evals around outcomes, isolation and repeated trials.** — At DeepMind every skill ships with tests that run on each diff, and a change merges only if it improves or adds to the eval set. Use 10 to 20 prompts to start, including about 5 that should not trigger. Test outcomes instead of whether the skill loaded on turn one. Run 3 to 6 trials per case, use isolated workspaces so agents cannot read old chats, and test across harnesses such as Gemini, Codex and Cursor. ([16:44](https://youtu.be/0vphxNt4wyk?t=1004))
- **Retire skills by running ablations with and without the skill, and keep the eval after retiring the skill.** — If the model passes the eval without the skill loaded, the skill can be removed to save tokens and maintenance. Keep the eval so a later regression can bring the skill back. Schmid's homework: pick your most-used skill, write five test prompts, and run it with and without the skill. ([19:10](https://youtu.be/0vphxNt4wyk?t=1150))

## Techniques
- **Trigger and negative-case eval set** — Write 10 to 20 prompts per skill: about half where the skill should load and half where it should not. Check whether the agent loads it, and add real customer or production traces when available. *When:* When creating a new skill or checking whether a model-invoked skill over-triggers or under-triggers.
- **JSON cases plus regex asserts** — Store cases as a JSON or YAML file with prompt, language, should_trigger and expected checks. A Python runner calls the coding agent CLI and applies regex checks to output for SDK, model ID, method names and banned old patterns. *When:* For skills whose correctness can be read from the output text. It is cheap enough to run many times and to update when model IDs change.
- **LLM-as-judge for trace-level checks** — Give a judge model a rubric and the full trace or step list, get pass or fail, then review failures to improve the skill. *When:* When the check depends on the sequence of actions or the whole trace, not on the final output text.
- **CI gate on skill diffs** — Run the skill's eval suite on every change to the skill file and merge only if pass rate stays or improves, or new cases are added. *When:* When skills are maintained by a team and changes can silently degrade behavior.
- **With/without-skill ablation** — Run the same eval set with the skill loaded and with it removed. A skill that adds nothing is a candidate to retire. *When:* To decide whether to keep a capability skill as models improve, or to measure whether a skill is worth its token cost.
- **Isolated, repeated trials** — Run each case 3 to 6 times in a clean workspace with no access to earlier chats or caches, and measure pass rate across trials. *When:* Whenever agent output is non-deterministic, or agents could otherwise look up answers outside the skill.
- **Lean skill plus reference files** — Keep the description short and directive. Keep the SKILL.md body focused, and put variant-specific detail such as per-cloud deploy steps into separate reference files the model opens on demand. *When:* When a skill covers several providers, platforms or variants, or the body is getting long (Schmid suggests under about 500 lines).
- **Goal-and-constraint skills, scripts for fixed workflows** — Describe the desired end state and constraints instead of numbered steps. If the workflow is always the same, put it in a script and have the skill call it. *When:* When writing preference or workflow skills. Use a script for procedures with no decision points, such as staging docs or opening PRs.

## Hot takes
- Almost every skill people ship has no eval, and AI-generated skills can make agents worse.
- Most skill evals can be plain regex; LLM-as-judge is overkill unless the check depends on the whole trace.
- Skills should be retired as models improve, and the eval should outlive the skill.
- Many skill instructions are no-ops that only cost tokens.
