> Better Stack tests Lovable's claim that OJ, a Rust rewrite of Vite's dev server, is 4x lighter and 2x faster to start, finds small gains on a small app and larger gains on a 5000-component app, and summarizes Evan You's critique.

## Summary
The host examines Lovable's OJ ("Orange Juice"), a single Rust binary that runs an existing Vite project's config and plugins while replacing the dev server internals (file watcher, module graph, HMR, React Fast Refresh) with Rust code. He first compares OJ and Vite on a small TanStack Start app, where behavior is nearly identical, with one fast-refresh difference and only a small memory gap (about 320 MB vs 380 MB). He then cites a 5000-component React benchmark where OJ's normal mode is about 1.7x faster to a painted page and uses about a quarter of the memory, and Vite's experimental Bundle Dev Mode is faster than OJ normal mode but not lighter. OJ's design targets AI agents writing many files in bursts: saves are coalesced into one update, and an optional gate holds updates until the agent posts to a flush endpoint. He then reports Evan You's response: OJ solves Lovable's own problem, is built on VoidZero's Rolldown and Oxc, only supports React apps, skips Vite Plugin Checker, and has a benchmark that needs care. The video closes with Evan's prediction that cheap reimplementation will make per-project forks more common, and the host's view that most developers will not need OJ.

## Key ideas
- **OJ is a Rust replacement for Vite's dev server that keeps the existing vite.config and Vite plugins. The watcher, module graph, HMR and React Fast Refresh are reimplemented in Rust.** — The host describes it as one binary you point at an existing Vite project. It reads vite config and still runs Vite plugins, with a JS layer to talk to the plugin API. Built on Rolldown and Oxc (VoidZero projects). ([0:00](https://youtu.be/msSZ4CL_sNg?t=0))
- **On a small TanStack Start app, OJ and Vite behave almost identically, and the memory gain is small.** — SSR, hydration, server functions, dynamic file routes, Tailwind and asset imports all work. One difference: under OJ a counter resets on edit in TanStack Start, while a plain React app kept state. Memory across two processes was about 380 MB on Vite and about 320 MB on OJ. ([0:44](https://youtu.be/msSZ4CL_sNg?t=44))
- **The benefit shows at scale: on a 5000-component React app, OJ is much faster to first paint and uses far less memory than Vite.** — Time was measured from spawning the dev server to the deepest component appearing in a real Chrome DOM, with memory sampled over the process tree. OJ normal mode is about 1.7x faster and about a quarter of the memory. Vite Bundle Dev Mode (experimental in Vite 8.1) gets to 1.18 s, faster than OJ normal, but without the memory savings. OJ bundle mode reaches about 0.89 s. ([2:05](https://youtu.be/msSZ4CL_sNg?t=125))
- **The project exists for Lovable's preview sandboxes, which run around a million Vite dev servers a day, so memory per server matters.** — The host ties the design to Lovable's scale: instant previews that stay light, without giving up the Vite plugin ecosystem. ([2:05](https://youtu.be/msSZ4CL_sNg?t=125))
- **OJ is designed for agents, not people: a burst of saves from an agent is coalesced into one update, and an optional gate holds updates until the agent finishes.** — A human saves one file at a time, but an agent can write about ten files in a burst. Vite treats each as an update. In OJ the watcher, module graph, compiler and HMR form one pipeline, so a burst becomes one update. A gate can hold updates until the agent posts to a flush endpoint, so the preview only applies a complete change. ([3:09](https://youtu.be/msSZ4CL_sNg?t=189))
- **Evan You's critique: OJ is a dev server built for one use case, not a Vite rewrite. Its speed comes from supporting one shape of app.** — OJ only supports React apps, so it avoids the general support Vite needs for every framework and config. Vite deliberately leaves plugins like esbuild and the React plugin as separate packages. Evan also says the benchmark is unfair to Vite: the cold-start test includes Vite Plugin Checker, which OJ does not run. ([3:09](https://youtu.be/msSZ4CL_sNg?t=189))
- **Cheap reimplementation may make per-team forks of libraries more common than upstream PRs.** — Evan predicts 'tailored' projects where each user rebuilds a dependency to fit their constraints, and maintainers get forks instead of many PRs. The host notes the upside for maintainers and the risk of ecosystem fragmentation, and is not sure it is good. ([5:25](https://youtu.be/msSZ4CL_sNg?t=325))

## Techniques
- **Benchmark a dev server by time-to-deepest-component plus process-tree memory** — For each dev server, spawn it, open the page in a real Chrome instance, stop the clock when the deepest component is in the DOM, and sample the memory of the whole process tree (not just the parent). The speaker used a 5000-component React app. Run it for each mode, including Vite Bundle Dev Mode. *When:* Comparing dev servers or bundlers on startup and memory, when single-process numbers would miss child processes.
- **Check fast refresh state preservation with a counter component** — Render a counter, increment it, edit a neighbouring file, and check whether the count survives (HMR) or resets (full reload). Repeat in a plain React app to isolate framework-specific behaviour. *When:* Verifying that a Vite-compatible dev server really does hot updates, rather than full page reloads.
- **Coalesce agent write bursts into one hot update** — Route file watcher, module graph, compile and HMR through one pipeline so that a burst of N file writes produces one update. Optionally hold updates behind a flush signal: the agent posts to an endpoint when its edit is complete, and only then is the change applied. *When:* An agent writes many files in quick succession and the preview should show only finished, consistent states.

## Hot takes
- Memory gains on a small app are negligible (about 320 vs 380 MB); the win is for very large apps or millions of sandboxes, not a typical laptop.
- Evan You says OJ is fast partly because it supports only React apps, and that the benchmark includes a Vite plugin OJ does not run, so the comparison is not like-for-like.
- Forks may replace upstream PRs as the default for open source maintenance, and this may fragment the ecosystem; the host is not sure it is a good outcome.
- The host asks whether Vite is ever slow on a laptop, suggesting OJ is not useful for most developers.
- Quality cap note: the video relies on Lovable's blog and one Evan You tweet, the benchmark is a single run on one synthetic app, and there is no sponsorship. The host's own small-app tests are informal.
