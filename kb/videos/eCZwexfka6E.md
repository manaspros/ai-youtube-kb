## Summary
The video walks through an Alibaba paper, SkillWeaver, that addresses the cost of giving an agent a large tool catalog. The baseline dumps every tool description (2,209 MCP-derived tools) into the prompt, which the speaker says costs about 884,000 tokens per query and picks the right tool category only 21.1% of the time. SkillWeaver splits a task into atomic subtasks, retrieves a short list of candidate tools per subtask with embedding search, and then composes a DAG that orders dependent steps and allows independent ones in parallel. A feedback loop called skill-aware decomposition has the model draft subtasks, check them against retrieved tool names, and revise the wording to match the library's vocabulary. The speaker highlights that a 7B Qwen2.5 model with this pipeline outperformed Qwen Max in the naive setup, and that the larger model over-decomposed tasks. The video is clear about the limits: no error recovery, no released source code (only prompts and the paper), a benchmark built by the same team, and a 76.7% chain-completion result measured against mock executors rather than live APIs. The numbers are presented as the paper's, not independently verified.

## Key ideas
- **Loading the whole tool catalog into context is the hidden cost** — The naive approach puts every tool description into the prompt on each task. The speaker puts that at about 884,000 tokens per query for a 2,209-tool catalog, and the model still picks the right category only 21.1% of the time. ([0:00](https://youtu.be/eCZwexfka6E?t=0))
- **One-shot tool routing fails on compositional tasks** — A single pass over the full catalog fails when a task needs several tools in sequence. The paper calls this the compositional skill routing problem, and the failure is silent: the agent returns confident wrong output rather than an error. ([2:06](https://youtu.be/eCZwexfka6E?t=126))
- **Decompose, Retrieve, Compose pipeline** — The task is split into atomic subtasks first. For each subtask, an embedding model runs semantic search over the library and returns only the top candidates. A planner then checks whether one tool's output can feed the next tool's input. ([3:17](https://youtu.be/eCZwexfka6E?t=197))
- **The output is a DAG, so independent steps can run in parallel** — The composed plan is a directed acyclic graph of dependencies. Independent steps run in parallel and dependent ones run in order. The speaker presents this as an execution plan, not a flat list of tools. ([4:09](https://youtu.be/eCZwexfka6E?t=249))
- **Decomposition vocabulary must match the tool library** — Models tend to write generic subtasks such as 'process the data' that match no indexed tool name. Skill-aware decomposition drafts a plan, retrieves candidates for that draft, and revises the subtasks using the retrieved names as hints. The paper reports decomposition accuracy rising from 51% to 67.7%, and about 50% better accuracy on 4-5 step tasks. ([5:18](https://youtu.be/eCZwexfka6E?t=318))
- **Decomposition granularity matters more than model size, per the paper** — A 7B Qwen2.5 model with the pipeline reached 67.7% tool-category accuracy, against 21.1% for Qwen Max run naively. Without the feedback loop, the larger model over-decomposed into sub-steps that matched no real tool, and it scored below the 7B model. ([6:43](https://youtu.be/eCZwexfka6E?t=403))
- **Real limits: no error recovery, no released code, self-run benchmark** — A failure in step two of a five-step chain breaks the whole chain, and the paper says so. Only the paper and prompt templates are released. CompSkillBench was built by the same team that built SkillWeaver, and the 76.7% chain-completion figure comes from mock executors, not live systems. ([8:01](https://youtu.be/eCZwexfka6E?t=481))
- **Routing is framed as an architecture problem, not a model problem** — The speaker argues the market assumes better models will pick better tools. The paper's evidence, in the speaker's reading, is that structure and vocabulary alignment matter more. The claim is broader than the single benchmark supports. ([9:29](https://youtu.be/eCZwexfka6E?t=569))

## Techniques
- **Decompose-Retrieve-Compose tool routing** — 1) Ask an LLM to split the task into atomic subtasks. 2) Embed each subtask and run semantic search over the tool library, keeping only the top-k candidates per subtask. 3) Give a planner the candidates and have it check whether each tool's output matches the next tool's input. 4) Emit a DAG: parallel where independent, ordered where dependent. The speaker suggests building this with LangChain or LlamaIndex, since the paper's source code is not released (only prompt templates). *When:* Large tool or skill catalogs (hundreds to thousands of MCP tools) where dumping every description into context is too expensive, and tasks that chain several tools.
- **Skill-aware decomposition (SAD) feedback loop** — Draft an initial subtask decomposition. Retrieve tool candidates using that draft. Ask the model to revise the decomposition using the retrieved tool names as vocabulary hints. Run one revision loop. The speaker describes this as a single loop. *When:* When subtasks are too generic to retrieve against the library, for example 'process the data' not matching names such as 'csv-parser'. Most useful on tasks needing 4-5 sequential tools.
- **Right-size decomposition granularity** — Check the number of subtasks against the tool vocabulary. The paper's finding is that over-decomposition into steps that match no tool hurts routing more than a smaller model does. Anchor decomposition to real tool names before scaling up the model. *When:* When a larger model gives worse routing than a small one, or when subtasks fail to match any tool.

## Numbers
- Baseline (dump every tool description into the prompt): about 884,000 tokens per query ([0:00](https://youtu.be/eCZwexfka6E?t=0))
- Baseline right tool category accuracy: 21.1% (CompSkillBench, 300 queries, 2,209 tools, 24 categories) ([1:03](https://youtu.be/eCZwexfka6E?t=63))
- SkillWeaver: about 1,160 tokens per query, described as a 99.9% reduction ([2:06](https://youtu.be/eCZwexfka6E?t=126))
- Skill-aware decomposition raises decomposition accuracy from 51% to 67.7%, and improves accuracy on 4-5 step tasks by about 50% ([5:18](https://youtu.be/eCZwexfka6E?t=318))
- Qwen2.5-7B with SkillWeaver: 67.7% right tool category, against 21.1% for unguided Qwen Max ([6:43](https://youtu.be/eCZwexfka6E?t=403))
- Pilot chain completion: 76.7%, measured on mock executors rather than live APIs ([8:01](https://youtu.be/eCZwexfka6E?t=481))

## Hot takes
- The 99% headline is a token reduction against a naive full-catalog dump, not a quality gain. The speaker says the token numbers are real but the production story is unproven.
- The benchmark, the 2,209 tools and the evaluation are all internal to Alibaba, and the 76.7% completion rate comes from mock executors. The speaker calls the numbers unverified rather than wrong.
- The 67.7% figure is reported both as decomposition accuracy (5:18) and as right-tool-category accuracy (6:43). The transcript does not clarify which is which, so treat the two as ambiguous.
- The 'routing is architecture, not model' conclusion is the speaker's extension. The evidence compares one 7B pipeline against one larger model run naively, on one benchmark.
