> Walkthrough of OpenTelemetry sampling for logs and traces in a local Go app: collector probabilistic sampling, SDK trace samplers, and tail-based sampling with error and probabilistic policies.

## Summary
The video explains head-based sampling (decided before or at collection, cheap) versus tail-based sampling (decided after buffering spans, more informed but memory-heavy) in OpenTelemetry. It runs a Go demo that increments a counter and logs it every second, exporting logs and traces over OTLP to a local collector. For logs, it configures the collector's probabilistic sampling processor at 10% and keys sampling on the record's "value" attribute, with a hash seed for consistency across multiple collectors. For traces, it shows SDK-side samplers (always, never, parent-based, trace-ID ratio) and the collector's probabilistic sampler modes. Tail-based sampling uses the tail sampling processor, with its wait time, trace buffer, and decision cache settings, plus policies: an error-status policy plus a 10% probabilistic policy so error traces keep some surrounding context. It closes by recommending the memory limiter processor, since tail sampling holds data in memory. Log sampling is presented as less mature than trace sampling. A short sponsored segment for Better Stack appears mid-video.

## Key ideas
- **Head-based sampling decides before data is stored and is cheap; tail-based sampling decides after buffering and is more informed but needs collector memory.** — Head-based can run in code or in the collector after ingestion. Tail-based holds all spans in memory until a decision is made, so the collector needs more resources. ([0:00](https://youtu.be/WtX3Nlnjffs?t=0))
- **Log sampling in the collector uses the probabilistic sampling processor keyed on a record attribute.** — Set sampling percentage to 10 (any value works, e.g. 10.1), set the attribute source to record and the from attribute to the log attribute "value". The demo confirms about 10.1% of logs survive. Trace ID is the default source when logs carry trace context. ([1:16](https://youtu.be/WtX3Nlnjffs?t=76))
- **A hash seed makes sampling consistent across multiple collectors.** — With a hash seed, the chosen attribute or trace ID is hashed with FNV and compared to a threshold, instead of using random numbers. The same item gets the same decision on every collector. ([1:16](https://youtu.be/WtX3Nlnjffs?t=76))
- **Logs only get trace-based sampling if the app attaches span context to them.** — The demo creates a span in the counter loop, passes its context into the logger call, and the logs then carry trace and span IDs. After that, a plain percentage works because trace ID is the default sampling key. ([2:43](https://youtu.be/WtX3Nlnjffs?t=163))
- **SDK-side trace sampling has four built-in options, and collector-side trace sampling has three modes.** — SDK samplers: always sample, never sample, parent-based (sample only if the parent was sampled), and trace-ID ratio (0.5 samples half of traces). Collector probabilistic sampler modes: proportional, equalizing (accounts for how much an item was already sampled, using trace context), and hash. ([2:43](https://youtu.be/WtX3Nlnjffs?t=163))
- **The tail sampling processor only supports traces, not logs, and needs at least one policy.** — Settings named: decision wait (seconds since the first span before deciding), num traces (traces held in memory), expected new traces per second (for allocation), and decision cache (remembers sampled and dropped trace IDs after eviction, with sampled and non-sampled cache sizes). The decision is made at wait time regardless of memory pressure. ([4:11](https://youtu.be/WtX3Nlnjffs?t=251))
- **Error-only tail sampling loses context, so add a probabilistic policy alongside it.** — A status-code policy alone keeps only error spans, which the demo confirms. Adding a 10% probabilistic policy keeps some non-error spans around the errors. Policies can also use latency, rate limiting, string, numeric or boolean attributes, sub-policies, or OTTL expressions. ([5:38](https://youtu.be/WtX3Nlnjffs?t=338))
- **Tail sampling needs the memory limiter processor as a guard.** — Because buffered traces sit in collector memory, the video recommends the memory limiter processor to cap memory use. ([7:01](https://youtu.be/WtX3Nlnjffs?t=421))

## Techniques
- **Probabilistic log sampling in the collector** — Use the probabilistic sampling processor with sampling_percentage 10 (fractional values work). Set the attribute source to record and the from attribute to the log attribute to sample on (here "value"). Verify the output rate (about 10.1% at 10.1). Key names are not spelled out in the transcript; the speaker's wording maps to attribute source, from attribute and hash seed, so check the processor docs for exact YAML keys. *When:* High-volume logs where you want a fixed fraction kept and a stable key per record.
- **Consistent sampling across multiple collectors** — Enable the hash seed option on the probabilistic sampler. The sampler hashes the source attribute or trace ID with FNV and applies a threshold, so every collector makes the same decision for the same key. *When:* More than one collector instance handles the same traffic and sampling must agree between them.
- **Trace-correlated logs in a Go app** — Create a tracer, a trace provider and a trace exporter. Inside the hot loop, start a span and pass the returned context into the logger call, so logs carry trace and span IDs. Exports use OTLP to a local collector, with the insecure option for local development. *When:* Before relying on trace-ID-based sampling for logs, or when you want logs to link to traces.
- **SDK head-based trace sampling** — Pass a sampler to the trace provider with the sampler option: always sample, never sample, parent-based, or trace-ID ratio (for example 0.5 for half of traces). *When:* Cutting trace volume at the source when a cheap, uninformed decision is acceptable; parent-based keeps distributed traces whole.
- **Collector probabilistic trace sampling** — Use the probabilistic sampler for traces with sampling percentage and mode set to proportional, equalizing or hash. Equalizing uses the sampling state stored in trace context, so decisions account for earlier sampling by other collectors. *When:* Trace volume reduction at the collector without changing app code.
- **Tail-based trace sampling with policies** — Add the tail sampling processor with decision wait (seconds), num traces (memory buffer size), expected new traces per second, and a decision cache with sampled and non-sampled cache sizes. Define at least one policy. Example: a status-code policy set to error, plus a probabilistic policy at 10% so non-error context is kept. *When:* When sampling must depend on trace content (errors, latency, attributes) rather than just randomness, and the collector has memory to spare.
- **Error-only policy with context** — Emit an error record and error span for some values (the demo uses every value divisible by 5). Configure the status-code error policy and a probabilistic 10% policy together, so error traces appear with some surrounding spans. *When:* Keeping error traces without losing the context needed to debug them.
- **Memory guard for tail sampling** — Add the memory limiter processor to the collector pipeline to cap the memory used while traces wait for a sampling decision. *When:* Any tail-sampling deployment, to avoid collector OOM under bursty traffic.
