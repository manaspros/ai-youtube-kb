> Sonar's hands-on workshop for Guitar, a PR-level verification agent that reviews agent-written code, diagnoses CI failures, auto-fixes and auto-merges. Vendor pitch with a usable setup walkthrough.

## Summary
A sponsored workshop from Sonar (makers of SonarQube) introducing Guitar, a code change verification agent that runs on GitHub pull requests. The speakers argue that AI agents produce more code than humans can review and that agents ignore architecture, standards and business rules, so verification has to be faster and context-aware. The hands-on part forks a sample Python ticketing repo, opens three PRs, and shows Guitar finding a refund/void edge case the existing tests missed, then applying a fix via a "guitar fix" comment. It then walks through business-rule steering with markdown review files and rules, and enabling auto-apply and auto-merge through a GitHub branch ruleset that requires the test check. A CI-failure demo shows Guitar reading logs for a double-scan bug. The closing section lists Pro/Enterprise features (Jira/Linear and Slack context, a "Knowledge" feedback store, cross-repo and cross-PR breakage analysis) without demoing most of them. Treat the product claims as vendor claims; the workflow details are the reusable part.

## Key ideas
- **Agent-written code outpaces human review, and agents lack architecture, standards and business context, so the review bottleneck and incident rate both grow.** — The speakers frame verification as the missing layer for agentic velocity. Guitar is pitched as a PR-triggered agent that reviews, fixes and verifies changes. ([5:05](https://youtu.be/wP3P89YB9fA?t=305))
- **Static analysis and an intent-aware reviewer are complementary, not substitutes.** — Static analysis (SonarQube) traces issues such as SQL injection across many files. It cannot judge whether a change's business logic matches what was intended. The speaker says both layers are needed. ([16:00](https://youtu.be/wP3P89YB9fA?t=960))
- **The demo bug was an edge case in a cancellation path that a one-directional test did not cover.** — A PR let a buyer give a ticket away and then refund the original order, which also cancelled the friend's ticket. An existing test checked that a voided ticket cannot be transferred, but not the reverse. Guitar traced it to orders.py using knowledge of existing cancellation logic, not the diff alone. ([18:42](https://youtu.be/wP3P89YB9fA?t=1122))
- **Fixes are applied as new commits, and Guitar re-verifies them through CI.** — Either click the apply-fix button or comment 'guitar fix' on the PR. Guitar pushes a commit, reruns verification and keeps iterating until the workflow is green. Per the speaker, this costs no extra per PR. ([20:10](https://youtu.be/wP3P89YB9fA?t=1210))
- **Business rules are injected through markdown review context and conditional rules, not code.** — Files in .guitar/review (any markdown) steer reviews. Rules in .guitar/rules fire when a PR meets criteria. The demo rule flags edits to pricing files and asks a reviewer to confirm customer-facing prices are all-in. ([22:31](https://youtu.be/wP3P89YB9fA?t=1351))
- **Full automation depends on branch protection that requires the CI test check to pass.** — The sequence is: enable Allow Auto Merge in repo settings, create a branch ruleset on the default branch, and require the status check named test. Then comment 'guitar auto-apply on' and 'guitar auto-merge on'. Merging only happens once CI is green. ([26:46](https://youtu.be/wP3P89YB9fA?t=1606))
- **CI failure diagnosis reads logs, separates real breaks from flakes, and pushes a fix.** — In the demo, a refactor let an already-used ticket pass the check-in gate (returned 200). Guitar read the failing test log and diagnosed the cause. The speaker says it separates real breakage from flaky or infrastructure noise. ([29:19](https://youtu.be/wP3P89YB9fA?t=1759))
- **Advanced features (functional validation, Knowledge, cross-repo and cross-PR analysis) were described but mostly not demoed.** — Functional validation checks a PR against its Jira or Linear ticket. Knowledge learns from reviewer feedback, weighted by seniority, and the speaker was unsure how external knowledge ingestion works. Cross-PR analysis checks in-flight PRs against each other for combined breakage. Some features are Enterprise-only. ([34:20](https://youtu.be/wP3P89YB9fA?t=2060))

## Techniques
- **Install Guitar as a GitHub app and connect a repo** — Sign in at app.guitar.ai and start the GitHub install. Then in the Guitar dashboard, go to Settings > Configurations and repositories and confirm the repo appears there. The GitHub org that owns the fork must be the one the app is installed in. *When:* Before any repo-level setup. Required for Guitar to read a fork.
- **Fork the workshop repo with all branches and enable Actions** — Fork github.com/sonar-samples/aie-new-york-workshop-guitar. Leave 'copy the main branch only' unchecked, or the stage branches will be missing. Then open the Actions tab on the fork and enable workflows, because GitHub disables them on forks by default. *When:* When you want to reproduce the workshop exercises. The same pattern applies to any fork-based test repo.
- **Open PRs against your own fork, not upstream** — On the PR form, set the base repository to your fork. Open one PR per exercise branch (stage one, two, three). Let Guitar run in parallel instead of waiting on each one. *When:* When testing review behaviour across several PRs at once.
- **Apply Guitar fixes** — Click the apply-fix button on a Guitar review, or comment 'guitar fix' on the PR. Guitar adds a commit, reruns CI and re-verifies it, repeating until green. *When:* After Guitar reports a finding you accept. Use it for CI breakage as well as review findings.
- **Steer reviews with project context in .guitar/review** — Add markdown files to a .guitar/review/ directory in the repo describing business rules, such as 'every price shown to customers is the all-in price'. The speaker says any amount of context works and Guitar ingests it efficiently. *When:* For business rules that are not visible in the code or are not captured by tests, such as wiki or senior-engineer knowledge.
- **Write conditional rules in .guitar/rules** — A rule is a condition plus an action. Demo rule: when pricing files change, list the customer-facing fields edited and ask a reviewer to confirm they are all-in prices. Another example from the speaker: when the PR description contains a Slack link, check the code against that Slack thread. *When:* When a review should trigger on a specific change pattern and produce a checklist, not only a free-form finding.
- **Turn on auto-merge safely with a branch ruleset** — Repo Settings > Rules: enable 'Allow Auto Merge'. Rulesets > New branch ruleset: name it, set it Active, target the default branch, and add 'Require status checks to pass' with the check named 'test'. In the PR, comment 'guitar auto-apply on' and 'guitar auto-merge on'. Auto-apply and auto-merge can be set per repo in the Guitar dashboard. *When:* Only for repos with strong test coverage and CI, because the merge gate is the CI check, not the review.

## Hot takes
- Sponsored vendor workshop: the trial link, 'Pro/Enterprise' gating and product claims are unverified. Quality is capped at 2 under the sponsored-segment rule.
- Claims of 'high signal to noise' and minimal false positives are not measured in the session. The only evidence is one edge-case bug and one CI failure.
- The speaker himself said he was unsure how Knowledge ingestion works, so that feature's behaviour is unclear.
- Auto-merge on agent-written code gates only on CI. The refund bug was caught by Guitar's reasoning, but the CI test only covered one direction, so the merge safety rests on test coverage.
- The framing that static analysis cannot infer business intent, and the need for both layers, is a useful point independent of the product.
