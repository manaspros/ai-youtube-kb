> Hands-on workshop comparing GPT-5.5, Kimi K2.6, DeepSeek V4 Flash and Mistral Large 3 on counting, RAG grounding, vision, tool calling, agent loops, evals and DSPy prompt optimization.

## Summary
Pamela Fox (Microsoft) runs a guided workshop in which the same small test cases are run against four models hosted on Microsoft Foundry. Simple prompts already show large differences: GPT-5.5 and Kimi counted letters correctly, while DeepSeek and Mistral did not, and Mistral only got it right after a chain-of-thought prompt. On RAG, the smaller models were more likely to answer from their weights than from the supplied sources, and prompt changes helped only partly. Vision and tool-calling tests show the same pattern, with Mistral weakest on images and DeepSeek weakest on argument fidelity. The agent section compares tool-call efficiency and parallel tool calls across models and frameworks, and the eval section covers string checks, LLM-as-judge, Microsoft Research's Assert for generating test sets from a YAML spec, and DSPy with GEPA for writing prompts against constraints. The repo and code are described as runnable on Foundry, with an Ollama option added the day before. All results are small demos rather than benchmarks, and the speaker repeats that you need to test on your own scenario.

## Key ideas
- **Identical prompts produce different results across models, so model choice has to be tested per scenario rather than from benchmarks.** — On a letter-counting prompt, GPT-5.5 and Kimi returned 13 (the correct count), DeepSeek V4 Flash returned 6, and Mistral Large 3 returned 8. Mistral reached the correct answer after the prompt was changed to split the sentence into words, count per word, sum, and show reasoning. ([6:02](https://youtu.be/UGjk3Uk0MxM?t=362))
- **Smaller models answer from their weights when the supplied RAG sources do not contain the answer, and prompting only partly fixes this.** — The corpus covered only carpenter bees, but the question asked about honeybees too. GPT-5.5 and DeepSeek said the sources lacked the information. Mistral answered from its weights. Telling it to say 'no source provided' and to attach a source to each claim moved it closer but did not fully fix it. Speaker's takeaway: check whether a model admits what it does not know. ([8:35](https://youtu.be/UGjk3Uk0MxM?t=515))
- **For image understanding, prompt engineering helps little; the model either reads the image or it does not, so test on your own image types.** — On an aurochs image, a crocodile photo and a small-print plant table, GPT-5.5 and Kimi got all three right. Mistral said the crocodiles were alligators and picked a $2.30 plant instead of the 58-cent cheapest one. DeepSeek was excluded because it accepts text only. ([13:03](https://youtu.be/UGjk3Uk0MxM?t=783))
- **Language changes results: asking the crocodile/caiman question in Spanish made the models fail, which matters for bilingual apps.** — Spanish 'caimán' maps to alligator, not the Florida caiman, and the models got confused. The speaker says the mileage varies by language and notes that the Bay Area product context is often bilingual. ([15:20](https://youtu.be/UGjk3Uk0MxM?t=920))
- **Tool calling is prompt engineering: the JSON schema names, descriptions and types are what the model uses to decide how to call the function, and the model only returns a call that the application must execute.** — A create_calendar_event schema is passed with a user request. GPT-5.5 added the user as an attendee, which was not asked for. DeepSeek added the user as an attendee and wrote the location as 'virtual (Microsoft Teams)'. Ambiguity in descriptions shows up as wrong arguments, and the fix is to clarify the description (for example, 'named attendees only'). ([17:45](https://youtu.be/UGjk3Uk0MxM?t=1065))
- **Agent quality should be measured by efficiency (tool calls per goal and parallel calls), not only the final answer.** — On a calculator word problem with a 'do not do math in your head' system prompt, GPT-5.5 used one tool call with one long expression. DeepSeek used four. On a travel-planning agent, GPT-5.5 issued the flight and hotel searches in parallel in turn one, while Kimi did them in two turns and made extra budget calls. Mistral sometimes stopped early or forgot the last step once context grew. ([21:11](https://youtu.be/UGjk3Uk0MxM?t=1271))
- **Automated evals should compare tool name and arguments with exact checks where possible, reserve LLM-as-judge for fuzzy outputs, and calibrate the judge against human labels.** — A single tool call can be checked by string comparison of the tool name and arguments. Date math should be delegated to a tool because models are poor at it. Judges need pass/fail plus a reason, and they need the full trace (tool definitions and call history), not only the input and output. Each judged case costs two LLM calls. The speaker says RAG evals usually need about 200 to 800 cases, so they should not run on every commit. ([31:56](https://youtu.be/UGjk3Uk0MxM?t=1916))
- **Microsoft Research's Assert generates scenarios and judging rubrics from a YAML spec, which helps bootstrap evals before production data exists.** — The spec gives context, a judge model, and dimensions to stratify on (for example budget pressure). Assert produces behavior categories, a scenario set (scenario titles are LLM-generated), simulated users, and violation counts per model where lower is better. GPT-5.5 had the fewest violations on this travel-planner spec. The speaker says the tool is about a week old and used only so far in this demo. ([40:45](https://youtu.be/UGjk3Uk0MxM?t=2445))
- **DSPy inverts prompt writing: the constraints are the code, and an optimizer (here GEPA) writes the prompt that satisfies them.** — A task requires a numbered list with exact word counts per line, where the first letters spell a target word. Constraint checks are written in code, and DSPy iterates until a prompt passes them. The run took about six minutes. The resulting system prompt was used with Mistral, the model that had struggled most, so the approach may let a cheaper model reach the same results. ([45:55](https://youtu.be/UGjk3Uk0MxM?t=2755))

## Techniques
- **Single-variable model swap harness** — Each example file defines one model variable that defaults to GPT-5.5. Uncomment another model line to switch. Run the file through the OpenAI Python SDK pointed at the Foundry endpoint, passing the key from .env. Run with 'uv run examples/<file>' after 'uv sync'. Comment out endpoints in .env when hitting 429 rate limits. *When:* When comparing several models on one scenario, or when a provider might cut off access and you need a fallback that still works.
- **Chain-of-thought decomposition for counting** — Break the sentence into words, count per word, sum the counts, and show reasoning in the prompt. *When:* When a smaller model gets a counting or simple arithmetic task wrong with a direct prompt.
- **Grounded RAG prompt with explicit refusal and citation** — Tell the model to answer only from the provided sources and cite them. Add a fallback phrase such as 'no source provided' for missing information, and require a source for each claim in the answer. *When:* When the knowledge base may not cover the question and the model must not fill gaps from its weights. Test the model's refusal rate, not only answer quality.
- **Tool definitions as prompt engineering** — Write each tool as a JSON schema with a clear name, a description, and typed parameters. Read the actual arguments the model returns, compare them with expected values, and rewrite descriptions to remove ambiguity (for example, exclude the user from attendees and list only named people). *When:* When a model calls the right tool with wrong or unexpected arguments.
- **Low-level tool-call loop** — Send the user message and tools. When the model returns a function name and arguments, the application executes the function, appends the result, and calls the model again. Stop when the model returns plain text. Log each call to count them. *When:* Before adopting an agent framework, to see the raw loop, and to measure calls per task.
- **Force tool use over mental math** — Add a system prompt such as 'do not do math in your head' and give a calculator tool that evaluates expressions. Count tool calls and check whether the model batches the whole computation into one expression. *When:* To measure a model's tool-call efficiency on multi-step arithmetic.
- **Give date math to a tool** — Expose a date-arithmetic tool rather than asking the model to compute dates. Add test cases for leap years and ambiguous durations. *When:* Any agent that schedules, books or computes deadlines.
- **Deterministic checks first, LLM-as-judge second** — For a single tool call, string-compare the tool name and argument values. For fuzzy outputs, use a judge prompt that returns pass or fail plus a reason, given the query, response, context, and tool-call traces. Pre-generate the app outputs so the judge can be changed without rerunning the app. Calibrate the judge against labels from a domain expert. *When:* When the output is free text or depends on a sequence of tool calls, and you need a repeatable eval.
- **Spec-driven eval generation with Assert** — Write a YAML file describing the agent's context, the judge model, and the dimensions to stratify (for example budget tight, ample, or absent). Run the Assert tool to generate behavior categories, rubrics, simulated scenarios, and per-model violation counts. An agent skill is available to help write the YAML. A frontend is provided to view results. *When:* Before production, when there are no real user inputs to build an eval set from.
- **DSPy with GEPA for prompt optimization** — Declare the program's input and output types and the constraints as code, with a check function for each constraint. Set a student model and a reflection model, then run the GEPA optimizer. Save the optimized instruction and reuse it with the target model. *When:* When you need to move to a cheaper or different model and do not want to hand-tune the prompt for each one.
- **Anthropic document citations** — Send sources as structured document blocks (type document, text source) and enable citations. Parse the returned text blocks, which carry their citations, to link answers to sources in a UI. *When:* RAG with Claude where answers must link back to the source passages.

## Hot takes
- Built-in evaluators such as coherence and fluency are rarely what you need; custom evaluators tied to your agent's behavior matter more.
- Most agent frameworks are more similar than different, so the models and the tool-calling loop (the harness) matter more than the framework choice.
- Agents forget earlier steps as context fills, and Mistral often stopped after the first few searches; plan for steering or loop control.
- With DSPy, the prompt becomes a build output, and the spec in code becomes the source of truth.
- The speaker says a trustworthy LLM judge has to be calibrated with human labels; an uncalibrated judge can hide app failures.
