## Summary
The AI LABS team shows how to run several coding agents from different model families (Claude Code with Opus 4.6, Gemini CLI, and others) under one shared chat, using the open-source Agent Chatter tool, which they forked to add a visual layer. Each agent runs in its own terminal, and on macOS or Linux tmux is required; the repo ships per-agent init scripts. Before starting, they recommend initializing the app framework, setting per-agent permissions in settings.json instead of skip-permissions mode, and writing a shared agents.md that both CLAUDE.md and GEMINI.md point to. Agents get names and roles, and rules must be moved from draft to active. A loop guard (default 4 agent-to-agent hops) pauses cross-talk until a continue command. The workflow is planner-first: the planner writes a PRD and specs, a three-phase presenter/challenger/synthesizer review tightens the plan, and then the planner orchestrates parallel UI and backend builds. The speaker notes that the loop-guard setting did not take effect as configured and that agents overwrote each other's files, which they say dedicated git worktrees would prevent.

## Techniques
- **Shared multi-model chat via per-agent tmux sessions** — On macOS or Linux, install tmux. Clone the Agent Chatter repo and run the init script for each agent you want (the repo lists the commands), pasting them into a terminal in the repo folder. Run each agent in its own terminal, then open localhost to see all agents in the chat panel. Create channels (e.g. frontend, backend) like Slack channels. Windows users can run the scripts directly. The tool uses MCP so agents can read and reply in chat. Commands and flags are not shown on screen. *When:* When you want Claude Code, Gemini CLI or Codex to split work by model strength or cost, with the human supervising instead of relaying messages.
- **Per-agent settings.json permissions instead of skip-permissions** — Configure settings.json for Claude Code and for Gemini CLI so routine file edits and build commands run without prompts, and dangerous commands still need approval. Make sure MCP servers are declared in the same config. Exact keys are not shown. *When:* When several agents write to one repo and you want autonomy without any agent being able to wipe another's work.
- **Shared agents.md as the single instruction source** — Create agents.md with role rules, behavior and principles, plus PRD, backend and UI spec templates. Add a rule in CLAUDE.md and GEMINI.md telling each agent to treat agents.md as the key guiding file. Mark each rule active after creating it, since drafts are ignored. *When:* When different agent CLIs read different instruction files and you need the same rules to apply to all of them.
- **Named personas per agent** — Rename each agent in the tool and assign a role, e.g. a Gemini agent named as a UI/UX expert for design work, and a planner, builder or reviewer for the others. Rules then tell each one to stay within its role. *When:* When you want clear ownership of tasks and an easy way to tell agents apart in a shared chat.
- **Loop guard and continue gate** — The loop guard caps agent-to-agent hops (default 4). When hit, agents pause and wait. Send a continue command to resume. Raise the value for longer coordination. Rules refresh every 10 chat triggers (adjustable). Check that the setting is actually applied, since the speaker's value of 8 was not respected. *When:* When agents may get stuck in long cross-questioning loops and you want a hard stop with a human checkpoint.
- **Planner-first with PRD and spec templates** — Send the app idea to the planner in chat. It writes the plan into the PRD template, notifies you, and you approve or request changes. After approval, tell it to proceed. It alerts the UI designer, which implements the UI spec. The planner maintains backend.md. Ask the builder and planner to validate each other's docs before any build. Hold the UI build until you have reviewed the plans. *When:* When the build should only start after the plan has been reviewed by several agents and a human.
- **Three-phase presenter/challenger/synthesizer review** — Set the planner as presenter, who explains what it did. Set a reviewer as challenger, who stress-tests the documents and finds gaps. The planner then acts as synthesizer and produces the final plan. Run it in the tool's planner mode. Other modes (design review, code critique) follow the same pattern. *When:* Before implementation, to catch gaps a single agent would miss.
- **Planner as orchestrator with an ask-don't-assume rule** — Ask the planner to act as orchestrator. It sends green-light messages to the frontend and backend channels so the designer and builder run in parallel. Add a rule that any agent needing something from another asks it directly; the UI designer requested a variable and the builder granted it. *When:* When you want to hand off a multi-agent build and only check progress, while avoiding silent cross-file edits.
- **Git worktrees per agent (suggested, not tested)** — Give each agent its own git worktree, and have one agent merge and review everything as a whole. The speaker proposes this to stop agents overwriting each other's files. *When:* For larger setups where two agents may touch the same files.
- **Initialize the app framework before starting agents** — Scaffold the project (e.g. a Next.js app) before any agent runs, because several agents conflict over initialization even with separate roles. *When:* Before any multi-agent build on a greenfield project.

## Hot takes
