> Kai tests the viral "free 32GB AI server" on Kaggle's two T4s and finds layer-split speed and slow prefill make it a lab, not a daily coder; the TPU VM option is the better free route.

## Summary
The video dissects the popular tutorials that build a free 32GB inference server on Kaggle's free tier, running Qwen3-27B 4-bit via Ollama on two Tesla T4s behind a Cloudflare Quick Tunnel. Because the 4-bit model (about 17GB) does not fit on one 15.3GB T4, Ollama layer-splits it, so the two cards take turns and the pair delivers roughly one card's speed (about 16 tokens/s measured by another creator). The main hidden cost is prefill: a roughly 30,000-token agent system prompt takes about 92 seconds before the first token, which exceeds Cloudflare's 100-second free-tier timeout and causes 524 errors. The speaker reframes the free tier as a quota (about 30 GPU hours per week, 12-hour session cap, idle shutdown around 20 minutes) and converts it to about 1.75M output tokens, worth about $4.31 at OpenRouter's average price. He then highlights a TPU VM accelerator option on the same menu: eight TPU chips running full-precision Qwen3-27B through a vLLM TPU backend project, reported at about 130 tokens/s generation and about 10,300 tokens/s prefill. He lists catches: Kaggle's acceptable-use policy on server farming, quick tunnels having no uptime guarantee so the setup is not really local, and default Ollama having no auth. His verdict: free setups are good for learning and batch eval jobs, while daily coding is better served by a few dollars of hosted credit, and a local GPU is justified when code cannot leave the machine.

## Key ideas
- **The free Kaggle tier is a time quota, not a GPU: about 30 GPU hours per week, a 12-hour cap per session, and idle sessions die after about 20 minutes, which also kills the Ollama process and the tunnel URL.** — Each cold start yields a new public URL, so the agent config needs updating. Cold starts reportedly cost 15 to 30 minutes of the weekly quota. ([6:19](https://youtu.be/IMVjEsKX5UQ?t=379))
- **Two T4s give the capacity of two cards but the speed of one. A 4-bit Qwen3-27B file (about 17GB) exceeds one T4's 15.3GB usable VRAM, so Ollama splits layers across cards and they run sequentially for each token.** — The speaker's bandwidth argument: 320 GB/s over about 17GB caps single-stream decode near 16 to 19 tokens/s. - **Prefill is the hidden latency. Agents must read the whole prompt before the first output token, and the speaker cites about 30,000 tokens of system prompt for Claude Code.** — His scaled estimate for the T4 pair is about 325 tokens/s of prefill, so the first token arrives after about 92 seconds of silence. The 325 figure is his extrapolation, not a measurement. ([3:56](https://youtu.be/IMVjEsKX5UQ?t=236))
- **A 92-second time-to-first-token collides with the 100-second Cloudflare Quick Tunnel timeout, so the first request often fails with a 524. This is why tutorial creators tell viewers to resend the first message.** — The timeout is on Cloudflare's free tier and is not configurable below the enterprise plan. - **Converting the quota to tokens shows the free server's economic value. The best-case assumption is perfect utilization with no setup, idle or reading time. ([7:27](https://youtu.be/IMVjEsKX5UQ?t=447))
- **The under-reported option is the TPU VM accelerator on the same Kaggle menu: eight TPU chips with 16GB each, which lets the full 16-bit model run with the full 262K context.** — vLLM's TPU backend added support for Qwen3's attention type in version 0.28.0 (August). ## Techniques
- **Check whether a model fits per card before adding GPUs** — Compare the quantized model file size with usable VRAM per card. If it does not fit on one card, Ollama splits layers across cards and single-stream decode runs at about one card's speed. Speaker's ceiling estimate: memory bandwidth divided by model size (320 GB/s / about 17GB, about 19 tokens/s). *When:* Before renting or buying a second GPU for interactive chat or coding, where decode speed is the goal. Extra cards help capacity, not latency.
- **Measure prefill (time-to-first-token) separately from tokens/s** — Send a prompt of your real size (agent system prompt plus attached files plus history). Time the wait for the first token and compute prompt_tokens / TTFT. Speaker's estimate: 30,000 tokens at about 325 tokens/s gives about 92 seconds. *When:* For any agent harness with a large system prompt on a slow or remote GPU. Tokens/s benchmarks alone hide this wait.
- **Check proxy and tunnel timeouts against TTFT** — Cloudflare Quick Tunnel drops requests with no response within 100 seconds (free tier, not configurable below enterprise), returning 524. Compare your measured TTFT with every proxy and tunnel timeout in the path before exposing the endpoint. *When:* When exposing a self-hosted endpoint through a tunnel or load balancer, or when you see sporadic 502, 504 or 524 errors on the first request of a session.
- **Convert a free compute quota into tokens and dollars** — Tokens per week (best case) = quota seconds x tokens/s. Value = tokens x hosted price per million output tokens. Speaker's example: 108,000 s x 16.23 tokens/s is about 1.75M tokens, x $2.46 per M, about $4.31. Subtract setup, idle and reading time for a realistic figure. *When:* Deciding whether a free or self-hosted server is worth the operational cost versus buying API credit.
- **Run a 27B model at full precision on Kaggle TPU VM** — In a Kaggle notebook, pick the TPU VM option from the accelerator menu (8 chips, 16GB each, 128GB total). Use a vLLM build with the TPU backend at 0.28.0 or later, which the speaker says is needed for Qwen3's attention type. The speaker points to the Kaggle TPU lab project on GitHub, which launches the server. Use the API key it generates on the endpoint. *When:* When you want a full 16-bit 27B model with long context for a few hours a week for free, such as a lab session or a batch eval, and not for a 24/7 server.
- **Audit launcher code and model provenance before giving tokens** — Read the open-source launcher line by line before supplying a Kaggle API token. Pull the model from the official upstream repository, not an unverified re-upload from a single account. *When:* Any free-tier notebook setup that asks for account credentials, or any model pulled from a third-party mirror.
- **Never rely on a URL as the secret for an Ollama endpoint** — Default Ollama has no login. Do not publish it through a tunnel with the URL as the only protection. Put an API key or auth layer in front of it. This is the speaker's implied fix; he does not name a specific tool. *When:* Before exposing any local model server over the internet, even temporarily.
- **Expect URL churn on idle-killed notebook sessions** — Kaggle sessions die after about 20 minutes idle and cap at 12 hours. Each restart gives a new tunnel URL, so update the agent's base_url config each time, or use a stable endpoint. *When:* Running any agent against a free notebook-hosted endpoint.

## Hot takes
- Free Kaggle GPU hours are a quota with an idle timer, not a server. A week of full use is worth about $4.31 at API prices, so the 'free 32GB server' pitch overstates its value for daily coding.
- The two-T4 layer split adds capacity but no speed, and prefill latency, not tokens/s, is what breaks agent workflows.
- The best free option on that Kaggle menu is the TPU VM, which the viral tutorials skip; the speaker says it gives about 8x decode and 30x prefill over the T4 pair.
- A tunnelled Kaggle endpoint is not local: the code leaves the machine. Local hardware only makes sense when the code cannot leave the desk.
- Kaggle's acceptable-use policy and the idle-timer keep-alive scripts are a gray area that the tutorials never mention.
