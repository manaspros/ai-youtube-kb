> Ten-hour Better Stack build-along of a Hacker News clone on Hono, Bun, Drizzle, Postgres, TanStack Router/Query/Form and Lucia, covering typed APIs, session auth, transactional voting, pagination and optimistic updates, then Fly.io deployment.

## Summary
A long hands-on tutorial (chapters with a commit per step) that builds a Hacker News-style app in one repo: a Bun + Hono API serving the built TanStack front end, Postgres via Drizzle, and Zod validation shared between client and server. The backend walkthrough covers a typed success/error response envelope, a global Hono error handler that hides stack traces in production, username/password sessions with Lucia used as a thin helper, and drizzle-zod schemas refined for post creation. Voting is implemented as a database transaction that toggles an upvote and updates a denormalized points counter, and comment trees use Drizzle self-relations. Pagination is offset-based, with the speaker explaining cursor pagination as the better option for real-time data but more complex. The front end uses TanStack Query with optimistic upvotes (snapshot, cache write, rollback, invalidate) and URL search params as state, and the video ends with Docker and Fly.io deployment. Most of the value is the reproducible setup order and the stated trade-offs; the speaker also says the Lucia library is being deprecated in favor of learning-resource docs.

## Key ideas
- **Stack rationale: Hono for the API (small, web-standards, multi-runtime), Bun as runtime with native TypeScript, Drizzle for typed SQL-like plus relational queries, Postgres for storage, TanStack Router/Query/Form on the client.** — The speaker walks through each library's docs and claims (Hono under 14 KB, Drizzle with zero dependencies and one SQL query per call) to justify the choices before any code is written. ([0:00](https://youtu.be/eHbO5OWBBpg?t=0))
- **One repo, two folders: the Hono server also serves the static build of the Vite-built front end, so the whole app ships as one Docker container.** — In development Vite runs its own dev server; in production the server hosts the built static files. Server and front end each get their own package.json and ESLint config. ([2:07](https://youtu.be/eHbO5OWBBpg?t=127))
- **Shared Zod schemas and drizzle-zod generated insert schemas keep client and server validation in sync.** — Schemas live in a shared folder imported through path aliases. The post insert schema is derived from the table definition, then picked down to title, URL and content, with a refinement requiring either URL or content. ([1:53:20](https://youtu.be/eHbO5OWBBpg?t=6800))
- **API responses use a typed envelope (success flag, message, optional data, optional form-error flag), and a single Hono onError handler maps thrown HTTP exceptions and unknown errors to it.** — Unknown errors return a generic 500 in production and the stack trace in development. The form-error flag tells the client that a validation problem came from form data. ([40:17](https://youtu.be/eHbO5OWBBpg?t=2417))
- **Session auth explained step by step: the server creates a session row, sends its ID in a cookie, and checks the session table on each request; logout invalidates the row and clears the cookie.** — Lucia is a thin helper over this flow. Middleware sets user and session to null on the Hono context when there is no valid cookie, and a logged-in guard middleware returns 401. ([48:13](https://youtu.be/eHbO5OWBBpg?t=2893))
- **Denormalized counters (points, comment_count) are stored on posts and comments so sorting and listing do not need to count upvote rows.** — The speaker acknowledges a reconciliation script could be used if the counters ever drift, but argues the transactional writes keep them in sync. ([1:28:30](https://youtu.be/eHbO5OWBBpg?t=5310))
- **Upvotes are a transaction: read the existing vote, insert or delete it, update the post's points, and return the new count. Throwing an HTTP 404 inside the transaction rolls back every write.** — This is the speaker's example of why transactions suit multi-table changes: either all writes apply or none do. ([2:30:17](https://youtu.be/eHbO5OWBBpg?t=9017))
- **Offset pagination is simple but slows at deep pages; cursor pagination gives stable performance and no skips or duplicates on real-time data but needs a stable sort and cannot jump to arbitrary pages.** — The tutorial uses offset pagination (page times limit) with 10 items per page and a separate count query for total pages, and mentions cursor pagination only as a future upgrade. ([1:46:34](https://youtu.be/eHbO5OWBBpg?t=6394))
- **Optimistic updates with TanStack Query: on mutate, cancel queries and snapshot the cache, write the new state, roll back on error, and invalidate on settle. For infinite lists the cache update has to go inside each page.** — The speaker demos the failure path by throwing an artificial server error, which shows the upvote flip and then reverts with a failure message. He says optimistic updates on infinite queries are the hardest part. ([5:53:57](https://youtu.be/eHbO5OWBBpg?t=21237))

## Techniques
- **Typed API envelope with a global error handler** — Define SuccessResponse<T> and ErrorResponse types in a shared folder, with data present only when T is not void. Throw Hono HTTPException with a cause object for expected errors (e.g. 404 post not found, 401 unauthorized, 409 username taken). In app.onError, return the error envelope for HTTPException, and for other errors return a generic 500 in production or the stack in development. Import the types with `import type` to avoid runtime imports. *When:* Any JSON API consumed by a typed TypeScript front end where you want one response shape and no stack-trace leaks in production.
- **Zod validator middleware with shared schemas** — Put the schema in the shared folder and use @hono/zod-validator (zValidator) on form, json or query input. Read validated data with c.req.valid(...). Use .coerce.number() for route params and pagination values, and a z.literal('') branch for optional URL fields that arrive as empty strings from forms. *When:* Any Hono route whose inputs also need to be validated on the client with the same rules.
- **Derive API schemas from Drizzle tables with drizzle-zod** — Call createInsertSchema(table) to get a Zod schema from the table. Refine individual fields (min length 3, URL check after trim) and use .pick() to expose only the fields the API accepts. Add a .refine() that requires at least one of url or content, with a path on each field for the error. *When:* Schemas that must match DB column constraints but add API-specific rules.
- **Sessions with Lucia as a thin helper** — Use the Lucia adapter for Drizzle with your own users and sessions tables (username and password hash columns added by hand). Register getUserAttributes so the username is on the session. Middleware reads the session cookie, validates it, and sets user and session on the Hono context. Sign up or log in with Bun.password.hash and Bun.password.verify, then append the session cookie with createSessionCookie(...).serialize(). Logout invalidates the session and appends a blank cookie. Use a unique index and catch Postgres error 23505 to return 409 on a taken username. *When:* Username and password auth in a small app where the team wants to own the tables and password handling but avoid writing session code.
- **Transactional toggle with denormalized counters** — Inside db.transaction, select the existing vote for (post_id, user_id). Compute delta as +1 or -1. Update posts set points = points + delta where id = ? returning points. If the update returns nothing, throw a 404 so the transaction rolls back. Then delete the vote if it existed, otherwise insert it. Return the new points value. *When:* Vote, like or follow toggles where the list view needs a cheap counter and the count must not drift.
- **Drizzle relations for self-referencing comment trees without foreign keys** — Define relations() on each table with fields and references. For parent and child comments, use the same table on both sides with a shared relationName (e.g. child_comments). The speaker says Drizzle relations work on providers without foreign keys, such as PlanetScale. Relation names must match on both sides or Drizzle reports it cannot infer the relationship. *When:* Nested comments or threads on a database that cannot use foreign keys, or where you want Drizzle's query API to fetch children easily.
- **Offset pagination with a separate count query** — Accept page (default 1), limit, sortBy, order (default desc), author and site as Zod-validated query params. Use offset = (page - 1) * limit. Build a where clause only for filters that were provided. Run a count(id) with the same where clause, and return data plus a pagination object with totalPages = ceil(count / limit). *When:* Simple lists where page jumps and total page counts matter more than consistency under concurrent writes.
- **Helper to return dates as ISO UTC strings from SQL** — Write a helper that takes a timestamp column and returns a SQL expression that formats it as an ISO UTC string (to_char style, per the speaker's Postgres approach), so the API always returns the same date format. Use it in the select list in place of the raw timestamp. *When:* APIs that must return consistent UTC timestamp strings to the front end.
- **Optimistic mutation with TanStack Query and rollback** — useMutation with onMutate: cancelQueries on the key, snapshot previous data, write the new value into the cache, and return the snapshot as context. onError: restore the snapshot and show an error toast. onSettled: invalidateQueries on the key. For infinite queries, map over pages and update the matching item in each page. *When:* User actions such as upvotes or adding comments where the UI should respond before the server confirms.
- **URL search params as state, with validated search schemas** — Define the sort, order and filter params with a Zod schema on the TanStack Router route, so links carry the view state and back-button and refresh restore it. Keep the same schema for the server query validator, so both sides agree on defaults. *When:* List views (sort, filter, page) where users share links or expect the back button to restore the view.
- **Prettier and ESLint setup per folder** — Install prettier and prettier-plugin-sort-imports, and use a prettier.config.js that groups framework imports first, then third-party, then the path-alias imports. Add package.json scripts 'format' (prettier . --write) and 'format:check' (prettier . --check). Keep a per-folder eslint.config.mjs created with bun create @eslint/config, add @eslint/compat with fixupPluginRules for the Drizzle ESLint plugin, and extend eslint-config-prettier. Ignore generated files such as routeTree.gen.ts. *When:* A monorepo-style single repo where the server and client need different lint rules but one format setup.
- **Docker Compose for local Postgres, Fly.io for hosting** — compose.yml: a postgres:17 service (pin the version, not latest), POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB env vars, a named volume at /var/lib/postgresql/data, port mapping 5432:5432, and a bridge network. Run docker compose up -d. Set DATABASE_URL to postgresql://user:password@localhost:5432/<db>. For hosting: install the fly CLI, run fly auth login, fly postgres create, then fly launch and fly deploy. Keep the DB URL in Fly secrets, not committed config. Pin the Bun version in the Dockerfile ARG. *When:* Local dev parity with production Postgres and a single-container deploy.
- **Drizzle Kit push for schema sync** — Create drizzle.config.ts with defineConfig: dialect postgresql, schema pointing at the schemas folder glob, out folder, and dbCredentials.url from process.env.DATABASE_URL with a non-null assertion. Run bunx drizzle-kit push after each schema change. Run drizzle-kit studio to inspect tables and relations. *When:* Prototyping schema changes without migration files.

## Hot takes
- Speaker says Lucia is being deprecated and turned into a learning resource, and presents the tutorial's use of it as a thin wrapper that the reader could replace with their own session code.
- Speaker argues username-timing leaks don't matter for a public social site, and says two-factor auth and login throttling are needed elsewhere.
- Offset pagination is presented as fine for this app, with cursor pagination recommended for real-time data but described as complex.
- Tutorial is roughly ten hours of live coding that keeps live mistakes in the video and fixes them later, which makes it long but thorough.
- Speaker says the URL should match on hostname rather than the full URL for site search, and lists this as a later improvement.
