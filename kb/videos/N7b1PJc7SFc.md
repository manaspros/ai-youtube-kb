> Together AI's voice AI lead on the cascading STT→LLM→TTS pipeline: per-stage latency budgets, streaming STT, co-locating models to cut network hops, and why speech-to-speech is not yet production-ready.

## Summary
Rishabh Bhargava, who leads voice AI at Together AI, argues that voice agents are now an engineering problem and that the production default is still a cascading pipeline (speech-to-text, then LLM, then text-to-speech) run through an orchestrator. He breaks the pipeline into components and gives the metric that matters for each: word error rate and transcript completion time for STT, time-to-first-token for the LLM, and time-to-first-audio plus real-time factor for TTS. The main architectural point is the latency budget: the LLM takes most of it, then TTS, then STT, and network hops between services count too, so co-locating models and the orchestrator is worth a measurable gain. He covers streaming-native STT encoders, autoscaling that scales up early and drains long-lived connections on the way down, and guardrail or classifier stages that add latency. He calls speech-to-speech models the likely future (full duplex, backchannel, interruptions) but says they still lag on instruction following and tool calling. The eval advice is component-level tests, with tool-call validity near 100% as the baseline and conversation-level full-duplex evals later. The talk is short on benchmarks and methodology, and it doubles as a pitch for Together's hosting.

## Key ideas
- **Human turn-taking is about 300 ms; a voice agent over ~500 ms is noticeable, and at 1-2 s callers hang up. Latency is the first constraint, then intelligence and tool calling, then natural voice, then reliability at 1k-10k concurrent calls.** — The speaker frames voice as a joint problem: every constraint has to hold at once, and a demo with one caller hides the scale failures. ([2:17](https://youtu.be/N7b1PJc7SFc?t=137))
- **The dominant production architecture is cascading: streamed audio goes to an orchestrator (Pipecat or LiveKit, or a homegrown one), then STT, then an LLM that decides on tool calls, then TTS, and audio streams back.** — Each stage streams into the next. The speaker says the components can only be added to, which is why reliability and per-component observability matter more over time. ([4:41](https://youtu.be/N7b1PJc7SFc?t=281))
- **Each stage has its own metric: STT word error rate (about 6% on open benchmarks is state of the art) and transcript completion time (about 100 ms P90 on Together-hosted models); LLM time-to-first-token (about 300 ms target); TTS time-to-first-audio and real-time factor (below 1 so it does not buffer).** — Errors compound. A misheard drug or customer name gets carried through the LLM and TTS, so keyword accuracy matters more than the average WER. ([6:01](https://youtu.be/N7b1PJc7SFc?t=361))
- **Turn detection is still an unsolved problem: the agent must tell a pause from the end of a turn, because starting to speak over a user who is still talking is worse than a slow reply.** — The speaker also flags multilingual turn detection as an important capability and calls it a talk-length topic on its own. ([6:01](https://youtu.be/N7b1PJc7SFc?t=361))
- **Streaming STT is replacing batch models like Whisper, which was trained on 30-second clips and needed padding, chunking and stitching. Newer streaming encoders use small lookahead (about 80 ms to 1 s) and cache activations across frames.** — The speaker cites a recent NVIDIA encoder as the example. The point is avoiding recomputation on each small audio step. ([7:30](https://youtu.be/N7b1PJc7SFc?t=450))
- **The LLM should be around 8-30B parameters to hit roughly 300 ms TTFT. Bigger models blow the latency budget, and smaller ones lose the tool calling and instruction following the agent needs.** — For tool-call accuracy, the speaker says customers fine-tune small LLMs on use-case data so quality rises while the model stays small. ([8:57](https://youtu.be/N7b1PJc7SFc?t=537))
- **Latency and cost budget follows the same order: the LLM takes the largest share, then TTS, then STT. Network latency is also a budget item, and cutting cross-region hops from about 75 ms to about 5 ms was worth roughly 30% on an already optimized setup.** — Co-location means putting the models and the orchestrator in the same data center or building. The London example: a voice agent calling a US-hosted LLM pays a transatlantic hop on every turn. ([12:39](https://youtu.be/N7b1PJc7SFc?t=759))
- **Autoscaling needs asymmetric rules: scale up early, because queued requests hurt more than idle capacity, and scale down slowly, because stateful long-lived connections mean pods cannot be killed mid-conversation.** — The speaker says he has seen teams scale up more aggressively than with asynchronous services. ([11:18](https://youtu.be/N7b1PJc7SFc?t=678))
- **Extra models (guardrails, intent classifiers before the LLM, output checks before TTS) add latency, so each one needs an explicit SLA and independent scaling. The thinker-talker pattern puts a small LLM on the conversation and delegates one tool call to a larger model with more tools and guardrails.** — The thinker-talker example: the small model says 'let me check' while the big model runs, then the small model speaks the cleaned-up answer through TTS. ([19:11](https://youtu.be/N7b1PJc7SFc?t=1151))
- **Speech-to-speech and full-duplex models keep tone and hesitation and allow backchanneling and better interruption handling, but they still struggle with instruction following and tool calling, so teams end up back on the pipeline. Evals then move from per-component checks to whole-conversation full-duplex evals.** — Mentions NVIDIA's VoiceChat and OpenAI's realtime API as examples. Transcription can run alongside the audio as an audit trail. ([13:52](https://youtu.be/N7b1PJc7SFc?t=832))

## Techniques
- **Cascading voice pipeline with streamed hand-offs** — Stream audio chunks into an orchestrator (Pipecat, LiveKit or homegrown). Feed streaming STT output to the LLM, stream LLM tokens into TTS as they arrive, and stream TTS audio chunks back to the caller. Do not wait for full utterances at any stage. *When:* Default for production voice agents today, where tool calling and instruction following must be reliable. The speaker says it is still the dominant pattern.
- **Per-stage latency budget** — Give each model a latency and cost budget, with the LLM the largest share, then TTS, then STT. Track P90 and TTFT per component and fail a stage when it exceeds its share. Add network hop time to the budget as its own line. *When:* When the end-to-end turn latency target (around 500 ms) is at risk and you need to know which stage to fix first.
- **Streaming STT with lookahead-limited encoders** — Use a streaming-native speech encoder with small lookahead (about 80 ms to 1 s) and cached activations, so each new audio frame costs only the incremental compute. Avoid Whisper-style 30 s windows with padding and stitching. *When:* Live conversational transcription where waiting for a long window adds unacceptable delay.
- **Co-locate models with the orchestrator** — Run the STT, LLM and TTS services and the agent orchestrator in one data center or region, or on the same network segment. Prefer a self-hosted open-weight LLM over a distant API when the hop cost matters. *When:* When cross-region hops (around 75 ms) are a large part of the budget, or residency requirements call for regional deployment.
- **Asymmetric autoscaling for stateful voice** — Scale up aggressively and early, before queues build. Scale down by draining: wait for active conversations to finish instead of killing pods, since connections are long-lived and stateful. *When:* Any voice or long-lived streaming service where a killed pod drops live calls.
- **Pre- and post-LLM guardrail and routing stages** — Put a classifier before the LLM to route to specialized agents (for example refunds versus order tracking), and a guardrail after generation before TTS. Give each its own latency SLA and scale it independently. *When:* When one agent is not enough and a single prompt cannot cover all intents or safety checks.
- **Thinker-talker delegation** — A small, fast LLM handles the conversation and produces an immediate spoken acknowledgment. It issues one tool call to a larger model with full instructions, tools and guardrails, then voices the larger model's cleaned-up answer. *When:* When you need a fast spoken response but the correct answer requires a heavier model or more tools.
- **Tiered tool-call evals** — Measure first whether each tool call is well-formed and parseable (target near 100%), then whether it is correct for the use case. Test STT and TTS separately for keyword accuracy and naturalness, with listening tests for voices. *When:* Evaluating the LLM inside a voice pipeline, where the LLM's budget forces a small model that must still call tools correctly.
- **Full-duplex conversation evals** — For speech-to-speech systems, drop per-component text evals and run longer whole-conversation tests that cover turn-taking, backchannelling and interruptions. Keep a parallel transcription stream for audit. *When:* When the pipeline is replaced by a single speech-to-speech model.

## Numbers

- State-of-the-art STT word error rate is about 6% on open benchmarks (speaker's figure, no benchmark named). ([4:41](https://youtu.be/N7b1PJc7SFc?t=281))
- Transcript completion time is about 100 ms P90 for some models run on Together. ([6:01](https://youtu.be/N7b1PJc7SFc?t=361))

- LLM time-to-first-token target is about 300 ms (200-300 ms range). Suitable model size is about 8-30B parameters. ([8:57](https://youtu.be/N7b1PJc7SFc?t=537))
- TTS real-time factor below 1 avoids buffering. Example: 10 s of audio in 5 s gives RTF 0.5. ([8:57](https://youtu.be/N7b1PJc7SFc?t=537))
- Latency and cost budget ranks LLM first, then TTS, then STT. ([11:18](https://youtu.be/N7b1PJc7SFc?t=678))
- Cross-region network latency of about 75 ms (for example US West to Europe) versus about 5 ms co-located. The speaker says this is roughly a 30% reduction on an already optimized 100-200 ms engine-latency setup. ([12:39](https://youtu.be/N7b1PJc7SFc?t=759))

## Hot takes
- Speech-to-speech is the future, but it is not yet production-ready because of instruction following and tool calling; the cascading pipeline stays dominant for now.
- Co-locating models with the orchestrator matters enough to justify self-hosting an open LLM over calling a distant API.
- The talk is a partial vendor pitch: it promotes Together's hosting, shows customer logos and recruits hires, and the latency numbers are the speaker's own platform figures with no methodology.
- Eval guidance is thin: it stops at tool-call validity and says the rest depends on the use case.
