> Bun ported its ~1M-line codebase from Zig to Rust in 11 days using parallel Claude agents with an implementer, two adversarial reviewers and a fixer; the video also covers Zig creator Andrew Kelly's public criticism.

## Summary
The video walks through how Bun rewrote its Zig codebase in Rust between May 3 and May 14, with about 6,502 commits and roughly a million lines added, mostly driven by Claude agents. The stated reason was stability: manual memory management at the boundary with garbage-collected JavaScript values caused use-after-free and double-free bugs, which the Rust borrow checker turns into compile errors. The port was done all at once and as a faithful translation that preserves the Zig architecture, guided by a porting.md pattern map and a lifetimes file. Each file went through one implementer agent, two adversarial reviewer agents that only saw the diff, and a fixer agent. Parallel runs collided through git stash and reset until agents were restricted to committing, and work was sharded across four git worktrees. The test-suite-driven loops brought failing test files from 972 to 23 in about two days, and the port shipped with a binary about 20% smaller and modest speedups, along with some new regressions. Kelly's follow-up blog post argued the rewrite was a relationship and engineering-discipline problem rather than a technical necessity, and the speaker thinks both sides have a point.

## Key ideas
- **Rewrite rationale was memory safety, not style: the borrow checker turns the recurring use-after-free, double-free and error-path leak bugs into compiler errors, which the speaker calls a better feedback loop than a style guide.** — Bun uses manual memory in Zig while sitting on garbage-collected JavaScriptCore values, so GC'd values constantly cross into manually managed memory. ([1:12](https://youtu.be/0TSxrzBVEwQ?t=72))
- **Two up-front decisions: port everything at once (no incremental temporary shims), and do a faithful translation that keeps the Zig architecture rather than an idiomatic rewrite.** — Functions in the Rust output read nearly line for line like the Zig they came from. The speaker notes the TypeScript team used a similar approach for its Go rewrite. ([1:12](https://youtu.be/0TSxrzBVEwQ?t=72))
- **Before any code was ported, the team wrote a porting.md mapping Zig patterns to Rust equivalents and a lifetimes.tsv that records the intended lifetime of each struct field, generated with a Claude prompt.** — These documents act as shared specs that every agent reads, which is what made the per-file workflow consistent. ([2:36](https://youtu.be/0TSxrzBVEwQ?t=156))
- **Per-file workflow: one implementer agent writes the Rust file, two adversarial reviewer agents check only the diff, and a fixer applies their suggestions. Peak throughput was about 1,300 lines per minute.** — Each reviewer is a separate Claude instance that receives only the diff, so reviews are independent of the implementer's reasoning. ([2:36](https://youtu.be/0TSxrzBVEwQ?t=156))
- **Parallel agents broke the shared git repo: one agent ran git stash, another stash pop, another reset. The fix was to forbid any git command except committing, and to forbid slow commands such as cargo. Work was then sharded across four worktrees, each with about 16 agents.** — Separate worktrees for every agent were ruled out because the Bun repo is too large and the disk would run out. ([3:37](https://youtu.be/0TSxrzBVEwQ?t=217))
- **Breaking the code into about 100 crates required removing cyclic dependencies. Errors were then fixed per crate: run cargo check once, group errors by file, save them, and fix them with the same reviewer loop. This surfaced about 16,000 compile errors.** — The agents first stubbed out broken functions to get things to compile, which the team caught. ([4:37](https://youtu.be/0TSxrzBVEwQ?t=277))
- **A rule for reviewers: if a fix needs a paragraph-long comment to justify it, the code is wrong and should be fixed. The speaker calls this a good rule of thumb.** — The agents had started writing long comments that explained away their workarounds. ([5:48](https://youtu.be/0TSxrzBVEwQ?t=348))
- **Test-driven verification: the team looped over each CLI subcommand, then ran 100 test files per agent batch across the worktrees. The failing test-file count fell from 972 to 23 in about two days, and after roughly a day and a half Linux was fully green across 60 shards, with macOS and Windows following.** — The test suite includes memory-leak, hot-reload and stress tests, and the machine crashed several times from disk exhaustion before the suite was made to run cleanly. A human checked for silently skipped tests before merging. ([6:44](https://youtu.be/0TSxrzBVEwQ?t=404))
- **Outcome: the Rust binary was about 20% smaller, 2-5% faster on HTTP and build benchmarks, and free of a per-call memory leak in bun.build. The port fixed 128 known bugs but shipped 19 new regressions, since fixed. Claude Code runs on the Rust Bun and its startup was about 10% faster on Linux.** — About 4% of the code is inside unsafe blocks, around 13,000 unsafe keywords, and 78% of those blocks are one line, usually a pointer coming back from C++. ([7:54](https://youtu.be/0TSxrzBVEwQ?t=474))
- **Kelly's critique: the rewrite was not technically necessary (binary size and LTO were available in Zig), Bun had accumulated hacks and carelessness, and he disputes the claim that the test suite was enough. The speaker thinks both posts hold some truth, and that the real lesson is about tests.** — Kelly's post was revised afterward. The original conclusion was softened, and an apology to Zig users was added. The speaker's conclusion is that the port was a good engineer designing a translation pipeline with docs, lifetime specs and adversarial reviewers, and that tests are what let an AI agent work. ([9:04](https://youtu.be/0TSxrzBVEwQ?t=544))

## Techniques
- **Adversarial review loop per unit of work** — Give one implementer agent a unit (here, one Zig file). Give two separate reviewer instances only the diff, not the implementer's reasoning. Then run a fixer agent that applies only the reviewers' suggestions. Commit after the loop. *When:* Large mechanical translations or refactors where each change must be checked independently, and where compiler or test feedback is slow or insufficient.
- **Porting spec plus lifetime table before code generation** — Write a porting.md that maps source-language patterns to target-language equivalents, and a lifetimes.tsv that records the intended lifetime of every struct field (generated via a Claude prompt). Every agent reads both before writing code. *When:* Cross-language ports where consistency across many agents matters more than idiomatic output.
- **Faithful port over idiomatic rewrite, all at once** — Translate line by line and preserve the source architecture. Keep unsafe where needed, then remove it later once only the target codebase remains. Do not keep temporary bridge code between the two languages. *When:* When the goal is behaviour parity with a large production codebase, and an incremental bridge would become long-lived temporary code.
- **Guardrails for parallel agents on one git repo** — Forbid all git commands other than committing a file (no stash, reset or pop). Forbid slow commands for agents (for example cargo) and run the expensive check once at the start of a phase. Defer git operations to the end of a phase. *When:* When many agents share one repository and the first run shows them fighting over working-tree state.
- **Sharding by git worktree** — Create a small number of worktrees (four here) and run about 16 agents in each. Each shard commits and pushes its own files. Separate worktrees for every agent are not practical for a very large repo because of disk usage. *When:* Large repos where you need parallelism but cannot clone once per agent.
- **Error-driven crate-by-crate loop** — For each unit (crate), run the compiler once, group the errors by file, save them to files, and let an agent fix that unit's errors. Feed the result to the same reviewer and fixer loop. *When:* Compile-error backlogs too large for one agent, where you want bounded, per-unit context.
- **Reviewer rule against justified workarounds** — Tell the reviewers that if a fix needs a long comment justifying it, the code is wrong and must be fixed rather than explained. *When:* When agents tend to stub out, suppress or over-annotate code to make checks pass.
- **Test-file batch loops as the verification step** — Loop over each CLI subcommand first, saving each failing stack trace to a file. Then run batches of about 100 test files per agent, arranged by folder across worktrees, with the same reviewer and fixer loop. Human review before merge checks for silently skipped tests. *When:* Large existing test suites that serve as the correctness oracle for a port.

## Numbers
- Port done in 11 days, May 3 to May 14. About 6,502 commits, roughly 1M lines added. ([0:00](https://youtu.be/0TSxrzBVEwQ?t=0))
- Peak of 64 Claude instances on four git worktrees, up to 58 commits in one minute. The API-equivalent cost of the port is estimated at $165,000. ([0:00](https://youtu.be/0TSxrzBVEwQ?t=0))
- Port covers 1,448 Zig files. Peak throughput about 1,300 lines of code per minute, every line reviewed by two adversarial reviewers. ([3:37](https://youtu.be/0TSxrzBVEwQ?t=217))
- About 16,000 compile errors after the 100-crate split. Cyclic dependencies had to be removed first. ([4:37](https://youtu.be/0TSxrzBVEwQ?t=277))
- Failing test files fell from 972 to 23 in about two days. Linux went fully green across 60 shards, then macOS and Windows. Build 54202 was green on all six platforms on May 14. ([6:44](https://youtu.be/0TSxrzBVEwQ?t=404))
- Total usage: about 5.9 billion uncached input tokens, 690 million output tokens and 72 billion cache reads. The speaker equates this to roughly $165,000 at API prices. The team estimated three engineers would need about a year to do it by hand. ([6:44](https://youtu.be/0TSxrzBVEwQ?t=404))
- Binary about 20% smaller. 2-5% faster on HTTP server and build benchmarks. Repeated bun.build calls previously leaked about 3MB per call, and now memory is constant. ([7:54](https://youtu.be/0TSxrzBVEwQ?t=474))
- 128 known bugs fixed and 19 new regressions shipped from the port, since fixed. Claude Code startup about 10% faster on Linux after switching to the Rust Bun. ([7:54](https://youtu.be/0TSxrzBVEwQ?t=474))
- About 4% of the codebase is inside unsafe blocks, around 13,000 unsafe keywords. 78% of those blocks are one line, usually a pointer returned from C++. ([9:04](https://youtu.be/0TSxrzBVEwQ?t=544))
- Kelly's stated comparison: clean build of 16 seconds and 90 ms incremental edits in Zig, with a claim that the Rust compile times will be much longer. The speaker reports no measured Rust numbers. ([11:15](https://youtu.be/0TSxrzBVEwQ?t=675))
- Speaker's count of Bun's test assertions: about 1.3 million. ([13:23](https://youtu.be/0TSxrzBVEwQ?t=803))

## Hot takes
- The speaker says this was not AI magically rewriting Bun. It was a strong engineer designing a translation pipeline with porting docs, lifetime specs and adversarial reviewers, plus a large test suite.
- Kelly is right that nothing about the Rust rewrite was strictly necessary, since Zig could have had the same memory discipline, tooling and LTO, and Jared is right that 'we could have been more disciplined' is not a strategy.
- The speaker thinks the real lesson is that tests are what let an AI agent work, and that projects removing tests from public repos reflects this.
- Programming language choice is no longer a one-way decision if agents can do a test-validated port of half a million lines in under two weeks.
