> AI LABS rebuilds Shopify's checkpoint-and-gates agent loop as a Claude Code orchestrator skill; the key idea is enforcing gates with a stop hook, not advisory rules.

## Summary
Shopify reportedly rebuilt a roughly 300-screen mobile app with coding agents, using an internal tool called Helix that split work into checkpoints, ran sub-agents with fresh context, and required each checkpoint to pass gates before the next began. Shopify has not released Helix, so AI LABS rebuilt the workflow as a Claude Code skill called an orchestrator and tested it on a demo HR system. The loop is: a human approves a checkpoint plan (JSON, shown in a small webpage viewer), tests are written first and fail, code is written and the tests run until they pass, then a UI gate compares the screen to an HTML prototype, then an adversarial critic/fixer loop reviews the code. A stop hook returning exit code 2 keeps the agent working until each gate passes, and the speaker says this idea is borrowed from the Ralph loop. Human feedback at the end becomes new checkpoints that go through all gates and is written to a learnings file that every agent reads. The speaker's main claim is that gates enforce completion where prompt rules are forgotten. The video is a walkthrough of concepts with little exact configuration.

## Key ideas
- **Shopify rebuilt a roughly 300-screen mobile app with AI coding agents, not by handing over the whole job in one go.** — The internal tool Helix took one old screen as an example and converted it to the new architecture. Shopify has not released Helix; the speaker says they rebuilt the workflow from the published method. ([0:00](https://youtu.be/bBMp5tLxShQ?t=0))
- **Sub-agents are used for most work to get a fresh context window per task.** — Long single-context runs degrade: the agent forgets important earlier details and output quality drops. A separate context per task avoids this. ([1:23](https://youtu.be/bBMp5tLxShQ?t=83))
- **Work is split into checkpoints ordered by increasing complexity, and each one must be complete before the next starts.** — Each checkpoint builds on the previous one, so a wrong early decision is caught while it is still cheap to fix. A human reviews and approves the plan before any building begins. ([2:51](https://youtu.be/bBMp5tLxShQ?t=171))
- **A gate is enforced, unlike a rule, which is only advice the agent can forget.** — A stop hook runs whenever the agent tries to stop and exits with code 2, which the speaker describes as a prompt to keep going, not an error. The agent cannot advance until the gate passes. The speaker credits the Ralph loop (transcribed as RALF) as the source of this idea. ([5:25](https://youtu.be/bBMp5tLxShQ?t=325))
- **Shopify's workflow has four gates: behavior, UI, code review, and final human review.** — The behavior gate runs non-browser tests. The UI gate compares the built screen to a prototype and design.md. The code review gate is an adversarial loop. The final gate is a human check of the finished feature. ([6:24](https://youtu.be/bBMp5tLxShQ?t=384))
- **The behavior gate uses tests planned and written before the code, which initially fail.** — Tests cover what can be verified without a browser, such as permission rules, and act as a fixed standard. Sequence: tests are written and fail, a sub-agent implements the code, another sub-agent runs the tests, and the gate passes when all of them pass. ([7:32](https://youtu.be/bBMp5tLxShQ?t=452))
- **UI review is done against an HTML prototype built as a single clickable file, with two parallel reviewers.** — The prototype follows design.md. Before comparing, the skill puts the prototype and app into the same UI state. One reviewer checks looks and one checks behavior. Neither sees the project instructions, and their results are merged. Shopify itself used Gemini for this gate, chosen for spatial awareness. ([10:18](https://youtu.be/bBMp5tLxShQ?t=618))
- **Code review is an adversarial loop: a critic assumes the code is wrong and a fixer agent repairs what the critic finds.** — The loop repeats until the critic reports no issues. The gate passes only when the critic approves. Shopify used two critics against a written standard; the speaker used one critic and one fixer. ([11:45](https://youtu.be/bBMp5tLxShQ?t=705))
- **Human feedback at the end becomes new checkpoints and is recorded in a learnings file that every agent reads.** — The orchestrator stops for the human only twice: after the checkpoint plan and at the end. It turns feedback into new checkpoints that pass through all gates. ([12:56](https://youtu.be/bBMp5tLxShQ?t=776))

## Techniques
- **Checkpointed build with human plan approval** — Have a planner agent split the feature into small checkpoints ordered by complexity, write them as JSON, and show them in a simple webpage viewer. Ask the planner to use plain wording. A separate sub-agent drafts the test plan in parallel. The human approves or requests changes before building starts. Build checkpoint 1 first and do not start the next until its gates pass. *When:* Large features or rewrites where early wrong decisions are expensive; any time the plan needs human review before agents spend time building.
- **Stop-hook gate** — Register a hook that runs whenever the agent tries to stop. If the gate condition is not met, the hook exits with code 2, which the speaker says tells the agent the work is not done so it keeps going. The video does not show the hook config or the check script. *When:* When a rule in a prompt or CLAUDE.md is being forgotten and completion must be enforced by the harness.
- **Test-first behavior gate without a browser** — Have a TDD-planner skill write tests for everything verifiable without a UI (for example, a manager's approval permission). Run them first so they fail. Have a sub-agent write the implementation. Have another sub-agent run the suite. Mark the gate passed only when all tests pass. *When:* For backend or logic-heavy features where the agent needs a fixed, executable standard before coding.
- **Prototype-driven visual gate** — Build a single-file HTML prototype from design.md first, so the team can click through the intended behavior before UI work. Then compare the built screen to the prototype. Put both into the same UI state before comparing. Launch two independent reviewers in parallel: one for appearance and one for interaction. Give them only the prototype and design.md, not the project instructions, and merge their findings. The video says the comparison ran in a new Claude session launched from the current one. *When:* Visual or design-sensitive work, or converting one UI into another, where pixel-level fidelity matters.
- **Adversarial critic and fixer loop** — Run a critic agent instructed to assume the code is wrong and list issues. Run a fixer agent to address them. Re-run the critic on the fixed code. Repeat until the critic reports no issues; only then mark the gate passed. The speaker's skill that manages this loop is called adversarial loop. *When:* Code review gating on agent-written code, when you want a reviewer that is not the author and will not rubber-stamp.
- **Learnings file for cross-task feedback** — Write each human correction into a learnings file that every sub-agent reads before starting work. Turn requested changes into new checkpoints that go through all gates. *When:* Long-running multi-agent builds where the same mistake should not recur across sub-agents with fresh contexts.
- **Single orchestrator entry skill** — Create one orchestrator skill that is the only prompt the user writes. On start, it launches two sub-agents: one checks the app is running and one runs the checkpoint planner. It opens the viewer for review, then runs the checkpoint loop and gates, and stops only at plan approval and at the end. *When:* To minimise human prompts in a multi-stage agent pipeline while keeping two human approval points.
