> Ben Burtenshaw (Hugging Face) argues coding agents can take on AI systems work: writing CUDA kernels, fine-tuning models, and running a multi-agent automated research lab, using open skills, open Hub repos and an open dashboard data layer.

## Summary
Ben Burtenshaw from Hugging Face argues that coding agents should move from app code toward AI systems and ML engineering, which he frames as going closer to the silicon. He walks through three escalating "bosses": an interactive agent writing a CUDA kernel, a zero-shot agent fine-tuning an LLM from a prompt, and a multi-agent "automated AI lab" for research. For kernels, he says memory bandwidth, not FLOPs, is usually the bottleneck, and that Hub-hosted kernel repos with hardware/CUDA metadata plus file-based skills let agents go from zero-shot to few-shot. He reports one benchmark (a 94% speedup on Qwen3 8B on H100) and presents Upskill, a tool that generates a skill plus an eval and compares models on it. For the research setup, he splits Karpathy's single-agent autoresearch loop into researcher, planner, workers and reviewer/reporter roles that share state through a git repo, an HF bucket, and a Trackio dashboard backed by open Parquet files. His closing point is that agents do best with open primitives, since abstracted APIs without an escape hatch become a ceiling. Most content is a walkthrough with shared repos, so verify the speedup and fine-tuning claims before relying on them.

## Key ideas
- **Coding agents can now write valid, optimized CUDA kernels, so kernel and systems work is reachable for agent-assisted engineers.** — He points to GPU Mode hackathons, an AMD hackathon and the KernelBench paper as evidence that agents produce working, optimized kernels. He presents this as a career move toward systems engineering. ([1:09](https://youtu.be/JomVvNDjGb8?t=69))
- **Memory bandwidth, not compute, is usually the GPU bottleneck, and custom kernels help by raising arithmetic intensity.** — Efficiency splits into compute, memory and overhead. A kernel keeps tensors on-chip and does more math per read/write, so the GPU is not idle waiting on data. Flash attention is his main example. ([3:29](https://youtu.be/JomVvNDjGb8?t=209))
- **Kernels can be distributed as Hub repos with a TOML file that declares hardware and CUDA compatibility.** — The Hugging Face kernels library treats kernels like model repos, so kernel writers can publish them and users can see which GPUs and software versions each one supports. ([4:54](https://youtu.be/JomVvNDjGb8?t=294))
- **Skills are file-based context, and giving an agent kernel examples moves it from zero-shot to few-shot.** — Project maintainers keep skills in their own repos so they stay maintained. Experimental skills go in a separate skills repo. The kernel skill bundles benchmark and test scripts. ([6:17](https://youtu.be/JomVvNDjGb8?t=377))
- **Skill quality should be measured, and Upskill compares cheaper models on the same skill.** — Upskill generates a skill and an eval for it, then runs several models against that eval. The aim is to find cheaper models that keep accuracy and to iterate on the skill. ([7:36](https://youtu.be/JomVvNDjGb8?t=456))
- **Single-agent autoresearch can be split into roles: researcher, planner, workers and a reporter.** — The researcher turns papers into hypotheses, the planner keeps a job queue, workers implement training-script changes and run them as HF jobs, and the reporter monitors jobs and keeps the dashboard current. A reviewer role rejects duplicate or stale ideas. ([11:02](https://youtu.be/JomVvNDjGb8?t=662))
- **Shared state in a git repo and a bucket lets parallel agents coordinate without a bespoke orchestrator.** — Each experiment lives on a branch, the main branch keeps the scores, and an HF bucket holds the training scripts so nothing has to be uploaded or downloaded on every run. Prompts use templates that carry current state, the job list, and what has worked. ([14:00](https://youtu.be/JomVvNDjGb8?t=840))
- **An open data layer, not a closed dashboard, lets agents read results directly.** — Trackio stores runs as Parquet, so an agent can skip the dashboard and build its own charts such as a Gantt view. Events and warnings from agents can feed notifications. ([12:34](https://youtu.be/JomVvNDjGb8?t=754))
- **Agents work best on open primitives; abstractions without an escape hatch cap what they can do.** — His takeaway is to expose well-designed tools that the agent can control directly, and not to hide everything behind an abstracted API. He also says the Hub already has storage, tracking and compute for these workloads. ([16:45](https://youtu.be/JomVvNDjGb8?t=1005))

## Techniques
- **Skill-as-few-shot-examples with bundled benchmark scripts** — Put working kernel examples, plus scripts that benchmark and test them, into a skill file that the agent opens on demand. Keep the skill in the project's own repo so its maintainers own it. *When:* When an agent must write hardware-specific code it has not seen often, such as CUDA kernels, and it needs a measurable correctness and speed check.
- **Skill eval across models (Upskill)** — Generate a skill, generate an eval for it, run several models (including cheap or open ones) against the same eval, and compare accuracy against token use. *When:* Before sharing a skill with others or moving a recurring agent task to a cheaper model.
- **Role-split autoresearch loop** — Use a researcher to draft hypotheses from papers, a planner to keep a job queue, workers to implement and run each change, a reviewer to reject duplicates and stale ideas, and a reporter to monitor jobs and update the dashboard. Each role gets a fixed prompt template with current state, past results and the current scores. *When:* For long-running experiment loops where one agent doing everything serially is too slow, and each experiment yields a verifiable score.
- **Git and bucket as agent shared state** — Keep experiment branches in git, store scores in a data file on the main branch, and keep large artifacts (training scripts) in a shared object-storage bucket that all agents read. *When:* When several agents must coordinate and see one another's results without a central service.
- **Open-format dashboard as an agent data source** — Write run metrics and events to an open format such as Parquet, so the same data drives the dashboard and any ad-hoc analysis an agent wants to do. *When:* When agents need to answer custom questions about run history beyond what a fixed dashboard shows.
- **Verifiable-experiment precondition** — Choose tasks where success is measurable, such as kernel speed, or training loss in bits-per-byte, so the loop can rank experiments automatically. *When:* Before letting agents run unattended experiment loops; without a score the loop has nothing to optimize.

## Numbers
- H100 can do about 1 petaflop/s of compute but has about 3 TB/s memory bandwidth, so the GPU often waits on memory. ([3:29](https://youtu.be/JomVvNDjGb8?t=209))
- Kernel generated by an agent with the kernel skill for Qwen3 8B on H100 gave a 94% speedup. He says this is not state-of-the-art, mainly a compatibility-matrix fix. ([7:36](https://youtu.be/JomVvNDjGb8?t=456))
- Upskill comparison: GPT-OSS slightly less accurate at the same token use; Kimi more accurate with fewer tokens; Haiku slightly more accurate with fewer tokens. Results are anecdotal, not a stated benchmark. ([9:01](https://youtu.be/JomVvNDjGb8?t=541))
- Autoresearch measured experiments by bits-per-byte of the training run, with the best score kept at the end of the process. ([10:00](https://youtu.be/JomVvNDjGb8?t=600))

## Hot takes
- Systems and ML engineering, close to the hardware, is the place for engineers to grow their careers as coding agents take over application code.
- Memory bandwidth, not FLOPs, is usually the real bottleneck in deep learning inference.
- Abstracted APIs without an escape hatch are a ceiling; agents need open primitives they can control directly.
