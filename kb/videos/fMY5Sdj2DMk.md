> Tutorial for writing CLAUDE.md rules that keep Claude Code on task: think-first, simplicity, surgical edits, verifiable goals, git safety, scoped rule files and a corrections log.

## Summary
The video argues that the project instruction file (CLAUDE.md, or AGENTS.md for other agents) decides how well a coding agent follows your intent, and that running /init is not enough. It presents a set of rules it attributes to Andrej Karpathy's skills repo plus the team's own experience: have Claude state assumptions and ask clarifying questions before coding, prefer the simplest solution (rewrite if a 200-line answer could be 50), and make surgical changes that trace only to the user's request while reporting unrelated issues instead of fixing them. It then adds goal-driven execution, meaning Claude turns each task into tests or another verifiable check and iterates until they pass, with browser tools such as the Claude Chrome extension or Puppeteer MCP for UI checks. Other rules cover listing only non-default commands (for example gh instead of git, pnpm instead of npm), appending user corrections to a dedicated learnings file, asking before irreversible git or delete commands, and splitting instructions into path-scoped rule files and per-package CLAUDE.md files in monorepos. Finally it recommends a project description at the top, instructions ordered hard, medium, then low priority, verification (build, tests, lint, types) before reporting done, and keeping the file under about 300 lines. The advice is practical but mostly unmeasured, and a mid-video sponsor segment interrupts it.

## Key ideas
- **The project instruction file is the main lever on agent behavior, and /init alone is insufficient** — The speaker says a structured, project-specific CLAUDE.md (or AGENTS.md for other agents) is what makes the agent perform; without it you keep fighting the agent on every task. Hard rules only matter if the agent actually follows them. ([0:00](https://youtu.be/fMY5Sdj2DMk?t=0))
- **Make Claude state assumptions and surface interpretations before coding** — Add an explicit instruction to think before coding: state assumptions, present multiple interpretations if they exist, and ask questions so the user picks the implementation. The aim is to stop the agent from guessing from training-data patterns and then needing course correction. Attributed to Karpathy's skills repo. ([0:00](https://youtu.be/fMY5Sdj2DMk?t=0))
- **Enforce simplicity with a concrete size threshold** — Ask for the simplest solution and avoid features beyond the request, with proper error handling. The rule of thumb given: if something solvable in 200 lines could be 50, Claude should rewrite it because the approach is wrong. Large verbose solutions are harder to refactor and cost more tokens later. ([1:14](https://youtu.be/fMY5Sdj2DMk?t=74))
- **Surgical changes: every diff line must trace back to the request** — Agents tend to reformat or tidy adjacent code. The rule: check each change against the user's request; if it does not trace back, do not make it. Unrelated dead code should be mentioned, not removed. The speaker says this keeps the agent's attention from being split. ([2:26](https://youtu.be/fMY5Sdj2DMk?t=146))
- **Goal-driven execution: turn each task into a verifiable success criterion** — Have Claude define success criteria and convert tasks into checks, e.g. for input validation write tests for invalid inputs with expected return values, then iterate until they pass. Logic can be verified with tests; UI cannot, so a browser tool is needed for visual checks. ([3:32](https://youtu.be/fMY5Sdj2DMk?t=212))
- **Only document what Claude does not already know** — Skip default dev-server and build commands that Claude already knows. List only the tools and commands you want it to use instead of its defaults, such as gh for GitHub operations instead of git, and pnpm instead of npm when the project uses it. ([4:53](https://youtu.be/fMY5Sdj2DMk?t=293))
- **Treat CLAUDE.md as a living file fed by user corrections** — When the user says an implementation is wrong, Claude applies the fix and then appends the lesson to a dedicated learnings file that it references later, building a do-not and do-this knowledge base over time. Attributed to the Claude Code creator's workflow. ([6:17](https://youtu.be/fMY5Sdj2DMk?t=377))
- **Require confirmation for irreversible git and delete commands** — Instruct Claude not to run irreversible commands without asking: force pushes, resetting the head, merging branches, forced removes. If unsure whether a command is destructive, it should ask rather than assume. ([8:34](https://youtu.be/fMY5Sdj2DMk?t=514))
- **Split instructions into path-scoped rule files and per-package CLAUDE.md files** — Rule files declare their scope on the first line (e.g. API rules) and are referenced from the main CLAUDE.md, so they load only when relevant and avoid context bloat. In monorepos each sub-project gets its own CLAUDE.md, and the root file keeps only broadly applicable rules. ([9:47](https://youtu.be/fMY5Sdj2DMk?t=587))

## Techniques
- **Behavioral rule block for CLAUDE.md (Karpathy-derived)** — Add four rules: (1) think before coding, stating assumptions and presenting interpretations, asking when unclear; (2) simplicity first, no features beyond the request, rewrite if a solution is far larger than needed (speaker's example: 200 lines vs 50); (3) surgical changes, each change must trace to the user's request, mention unrelated dead code instead of deleting it; (4) goal-driven execution, convert each task into a verifiable goal (tests first, then iterate until they pass). Exact wording is not given in the video; it points to Karpathy's skills repo for the originals. *When:* Any project where the agent over-engineers, drifts into adjacent refactors, or starts coding before the requirements are clear. Speaker says it is added to every project, most of all large ones.
- **Verification gate before reporting completion** — Instruct the agent to run every available check (unit tests, linting, type checks, build) and confirm the feature works, not just that the code exists, before declaring a task done. For UI work, require a visual check through a browser tool: the Claude Chrome extension or Puppeteer MCP. *When:* Before trusting agent-reported completion, especially for UI changes that cannot be judged from the code alone.
- **List only non-default tooling** — Omit commands the model already knows (dev server, build). Add explicit lines for the tools the project uses instead of defaults: e.g. use the GitHub CLI (gh) for all operations instead of git commands, and pnpm instead of npm. *When:* When you have installed CLIs or package managers that differ from Claude's defaults, to keep the file short and stop it falling back to defaults.
- **Corrections-to-learnings loop** — Add an instruction: when the user says an implementation is wrong, first apply the correction, then append the lesson to a dedicated learnings file. Reference that file from CLAUDE.md so it is consulted later. The file is a running record of what not to do and the correct approach. *When:* Long-running projects where the same mistakes recur across sessions; the file grows into a project-specific knowledge base.
- **Destructive-command confirmation rule** — State that irreversible commands require explicit user permission first: force push, resetting the head, merging branches, forced removes. Add that if the agent is unsure whether a command is destructive, it must ask instead of assuming. *When:* Any repo where an agent has shell and git access, to keep production and branch state safe.
- **Path-scoped rule files and nested CLAUDE.md** — Create separate rule files for areas like API conventions, with the scope declared on the first line. Mention their location in the main CLAUDE.md so the agent knows they exist. In a monorepo, put a CLAUDE.md in each sub-project and keep only broadly applicable rules in the root file. *When:* Large repos or monorepos where instructions for one area would distract the agent while it works in another.
- **CLAUDE.md structure: description first, priority tiers, length cap** — Place a project description at the very top (what the app does, services, dependencies, how it runs). Order remaining rules as hard (non-negotiable), then medium (important, somewhat negotiable), then low (references). Keep the file under about 300 lines. *When:* Whenever writing or reviewing a project CLAUDE.md; the speaker says performance degrades past roughly 300 lines.
