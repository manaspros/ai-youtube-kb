> Browserbase engineers pitch hosted, forked "verified" Chromium plus the open-source Stagehand SDK for running browser agents at scale on finance portals, with Ramp, Bill and Stripe as case studies.

## Summary
Jay Sahnan and Arik Bird of Browserbase argue that browser agents are the only practical route to data behind logins, anti-bot walls, and portals with no API or MCP, using Ramp (receipt retrieval), Bill (payments across many vendor portals) and Stripe (merchant KYC) as examples. They explain why a stock Chromium in a data center gets blocked (fingerprint, cookies, datacenter IP) and describe their fix: a forked Chromium that drops the automation flag and stays alive between tasks. The core technical idea is Stagehand, an open-source layer over Playwright that mixes deterministic selectors with natural-language observe, act and extract primitives, feeding the model a compact accessibility tree instead of raw HTML. They claim this cuts a sample prompt from about 122k tokens to about 4,000 and that running the controller next to the browser removes round-trip latency. The live demos (100 concurrent browsers, 20 companies across 3 sources, and a Zod-schema extraction) ran over poor Wi-Fi and are only partly convincing. Substance is real but the talk is a vendor pitch and its numbers are self-reported.

## Key ideas
- **Browser agents are the fallback for web work that has no API or MCP server, such as login portals and heavily protected sites. Financial firms' data often lives there.** — Jay frames a browser as the tool an agent needs for anything on the web. Examples given are booking a flight, competitor pricing and finance portals. Ramp, Bill and Stripe are the motivating cases. ([1:09](https://youtu.be/DZ24Xbm9Joc?t=69))
- **Ramp replaced human portal-clicking teams with browser agents that fetch receipts and match them to transactions. The speaker reports 30,000+ manual hours saved and 5x scale.** — Ramp's need was to fetch receipts from many portals at scale. The vendor-reported result is thousands of deployed agents, over 30,000 manual hours saved and a 5x increase in scale. These are self-reported figures. ([2:26](https://youtu.be/DZ24Xbm9Joc?t=146))
- **A stock headless Chromium in a data center is easy to fingerprint. Each launch looks like a new browser with fresh cookies and a datacenter IP.** — On a laptop, a browser has a stable fingerprint (version, OS, fonts, screen, timezone), cookies and a residential network reputation. Moving the same binary to EC2 changes all of these. Proxies help with IP but do not fix the Chromium fingerprint. ([3:40](https://youtu.be/DZ24Xbm9Joc?t=220))
- **Browserbase forks Chromium to present a verified browser. The changes are removing the navigator.webdriver automation flag, reporting as regular Chrome instead of HeadlessChrome, and keeping the browser process alive between tasks.** — They say Chromium changes every two weeks, so they maintain their own fork. Closing windows instead of killing the browser lets sessions be reused. The speaker stresses that the flag and identity changes touch many places in the codebase. ([6:10](https://youtu.be/DZ24Xbm9Joc?t=370))
- **For Bill, the goal is one agent that works across thousands of vendor portals. Hand-written Playwright scripts break whenever a page's DOM or labels change.** — The talk contrasts per-portal Playwright selectors, which break on UI changes, with natural-language instructions that adapt. Stagehand is pitched as Playwright-style control with an LLM fallback. ([10:13](https://youtu.be/DZ24Xbm9Joc?t=613))
- **Stagehand sends the model a compact accessibility tree with direct selectors instead of raw HTML. The speaker claims this cuts a sample prompt from about 122k tokens to about 4,000.** — The comparison is a single example: Playwright with raw HTML versus Stagehand's accessibility tree, both answering where to click. The reduction is the most reusable technique in the talk, and no accuracy or cost-per-task numbers are given. ([12:57](https://youtu.be/DZ24Xbm9Joc?t=777))
- **Run the controller next to the browser to cut round-trip latency. Stagehand runs inside the hosted browser instead of on the agent's side.** — The argument is that sending HTML back and forth for every action is slow. Co-locating the Stagehand logic with the browser removes that per-action network hop. ([13:53](https://youtu.be/DZ24Xbm9Joc?t=833))
- **Stagehand exposes observe, act and extract. Extract takes a Zod schema, which turns messy page content into typed data for the agent.** — Observe finds candidate elements, act performs a natural-language action such as clicking Login, and extract returns structured output. The Stripe KYC use case is checking business registration on secretary-of-state portals. ([15:24](https://youtu.be/DZ24Xbm9Joc?t=924))
- **The same code can run concurrently across many sites. Their demo fanned out to 20 companies across 3 sources with no per-site scripts.** — The demo ran Chipotle, JPMorgan and Goldman Sachs through the same extract flow across investor relations pages, SEC filings and NYSE listings. The live view is for debugging, not for watching every run. ([17:54](https://youtu.be/DZ24Xbm9Joc?t=1074))

## Techniques
- **Accessibility-tree page compaction before the LLM call** — Do not send raw DOM or HTML to the model. Send an accessibility tree that keeps role, label and a selector for each actionable element. The speaker says this reduces a sample prompt from about 122k tokens to about 4k with the same answer. *When:* Any browser or web-scraping agent where page size drives token cost and latency, such as portals, large SPAs or repeated page-state reads.
- **Hybrid deterministic plus natural-language browser control** — Keep stable steps as deterministic Playwright-style calls (click on a known selector). Use natural-language act or observe only for steps that change between sites or over time, such as Find the Learn More button or Click the Login button. *When:* Multi-site workflows where a few steps are stable and others vary. Cuts selector maintenance compared with all-Playwright scripts, and cuts LLM spend compared with all-LLM control.
- **Observe, act, extract as three separate primitives** — observe(instruction) returns candidate elements without acting. act(instruction) performs one action. extract(instruction, zodSchema) returns typed data validated against a Zod schema. *When:* Structured data extraction from unstructured web pages, where you want the output shape enforced and the actions separated from the reads.
- **Schema-first extraction with Zod** — Define the output as a Zod schema, pass it to extract, and let the agent fill it from the page content. The speaker says the schema makes messy web data easy to pass to downstream agents. *When:* Pulling fields such as company metadata, filing data or merchant details from many heterogeneous sites into one typed record.
- **Single code path fanned out across many sites** — Write one script with the list of target URLs or companies and run browser sessions concurrently. The same code runs on every site. Use the live view to debug individual runs. *When:* Research or monitoring over a long list of companies or portals, where per-site scripts would not scale.
- **Keep browser processes alive between tasks** — Do not kill the browser after each task. Close the windows and reuse the process, which the speaker says avoids repeated launch cost and makes the session look more like a long-lived user. *When:* Repeated short automation tasks against the same sites, where cold launches are slow or get fingerprinted.
- **Run the agent-side browser controller next to the browser** — Put the LLM-driven control logic inside or adjacent to the hosted browser so each action avoids a network round trip. The speaker describes Stagehand running as a Chrome extension in the hosted browser. *When:* Latency-sensitive browser agents where many small actions happen in sequence.
- **Copy-prompt onboarding for coding agents** — Browserbase's site offers a copy prompt. The user pastes it into a coding agent, which then sets up the browser integration. The speaker describes it as doing much of the setup work. *When:* Bootstrapping browser automation into an existing codebase with a coding agent.

## Hot takes
- Vendor talk: Browserbase sells the hosted-browser infrastructure and Stagehand is its SDK. The token and hours numbers are self-reported, and the 122k-to-4k token comparison is one example, with no accuracy or cost-per-task data.
- The accessibility-tree compaction is the most reusable idea here and is independent of Browserbase.
- Anti-bot evasion (forked Chromium that hides automation, identity masking, captcha solving) is presented as a feature. The talk does not discuss site terms of service, legality or responsible-use limits. For us that is a governance question.
- The live demos ran over poor Wi-Fi and some steps were pre-set or cut short, so they show the workflow more than reliability.
- Quality is capped at 2 because the talk is product-centred, but it has concrete patterns a reader can reuse.
