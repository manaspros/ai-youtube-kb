> OpenAI's Dominik Kundel walks through what happens when a message is sent to Codex: context assembly, sub-agents, computer use, sandboxing, auto-review, WebSocket transport, goal loops and compaction.

## Summary
Dominik Kundel of OpenAI explains the internals of the open-source Codex harness (Rust, Apache 2) by following one user message through the system. Two protocols are involved: the app server between UI and harness, and the Responses API between harness and inference. Context construction is driven by three pressures: size, flexibility across skills and MCPs, and cacheability. The harness defers tool loading and caps the skills list. Agent actions cover async sub-agents and background terminals, browser use via code in a persistent REPL, and file edits via apply-patch and shell inside an OS-level sandbox. To reduce approval fatigue, an auto-review sub-agent judges escalated actions using authorization context and the transcript. WebSocket mode addresses network overhead once inference became fast. The talk closes with /goal loops, which re-inject a continuation prompt until the model calls an update-goal tool, and server-side auto compaction. The speaker is a product presenter, so the detail is high-level, and he says the state of the art changes quickly.

## Key ideas
- **Two protocols drive a Codex turn** — The app server carries messages from the UI to the harness, and the Responses API carries requests from the harness to inference. Both are designed as open interfaces, so third-party UIs and clients can build on the harness. ([1:14](https://youtu.be/shRR1e2HXMk?t=74))
- **Context construction is governed by size, flexibility and cacheability** — Model instructions are fixed and cache well. Skills and the tool registry grow unpredictably as users add skills and MCP servers, so the harness has to bound them to control cost and avoid contradictory context. ([4:31](https://youtu.be/shRR1e2HXMk?t=271))
- **Deferred tools and a capped skills list keep context small** — Tools can be marked deferred so they stay out of the context window until found by tool search. The skills list is capped at about 2% of the max context window, and descriptions shrink as the list grows. ([5:43](https://youtu.be/shRR1e2HXMk?t=343))
- **Async work runs through spawn, send-input, wait and shutdown tools** — The main agent can spawn sub-agents, send them input, wait on them or shut them down, so it can keep working while they run. Background terminals use the same pattern of sending stdin and waiting for output. ([6:47](https://youtu.be/shRR1e2HXMk?t=407))
- **Computer use is shifting from one-action tools to code execution** — The older computer-use tool allowed one declared action at a time. Browser use now writes JavaScript against a persistent Node REPL that keeps state across turns, so the agent can inspect a page once and then script scraping on later pages. ([8:34](https://youtu.be/shRR1e2HXMk?t=514))
- **Auto-review replaces full-access mode for escalated actions** — When a sandboxed action needs escalation, a separate read-only sub-agent is spun up. It cannot spawn sub-agents and receives the user-authorization context, a risk taxonomy and the transcript with tool calls, then returns a judgment. Routine actions are approved automatically, and data exfiltration is kept out of that path. ([12:34](https://youtu.be/shRR1e2HXMk?t=754))
- **Once inference is fast, the network becomes the bottleneck** — At around 1,000 tokens per second on Cerebras, per-call network overhead dominated. WebSocket mode keeps a persistent connection with stateful context, so only changed items such as new tool results are sent. ([15:18](https://youtu.be/shRR1e2HXMk?t=918))
- **Goal loops re-inject the objective until the model signals done** — With /goal, the harness injects a continuation prompt containing the objective after each pass. The loop ends only when the model calls an update-goal tool. The speaker advises concrete, verifiable goals rather than long essays. ([16:46](https://youtu.be/shRR1e2HXMk?t=1006))
- **Server-side auto compaction keeps long runs going** — Compaction can be triggered manually or automatically on the server, using the way the model was trained for it. It replaces the old context window with a compaction item that carries forward what is needed. ([18:15](https://youtu.be/shRR1e2HXMk?t=1095))

## Techniques
- **Deferred tool loading with tool search** — Mark tools as deferred so they are not in the context window. The model discovers them through a tool-search tool, either the built-in one or your own. The speaker says any tool can be marked deferred in the Responses API since GPT-5.4. *When:* When MCP or plugin installs make the tool registry grow and cost context.
- **Capping the skills list as a share of the context window** — Limit the skills list to a fixed fraction of the max context window, here about 2%. When the list exceeds the cap, shorten the descriptions gradually. *When:* When users may install many skills and the skills list would otherwise crowd out task context.
- **Sub-agent tool set: spawn, send input, wait, shutdown** — Give the agent tools to create child agents, send them new content, wait for them to finish, and shut them down. The same pattern covers background terminals. *When:* When the main agent should keep working while delegated tasks run in parallel.
- **Code-execution computer use with a persistent REPL** — Expose a stateful REPL, such as Node or Python, and let the agent write scripts against the browser or desktop. The agent learns the page structure once and scripts later steps. *When:* When one-action-at-a-time computer-use tools are too slow for multi-step browser tasks.
- **Auto-review sub-agent for escalated actions** — When a sandboxed action needs escalation, start a read-only reviewer that cannot spawn sub-agents. Give it the user's authorization context, a risk taxonomy, the transcript and the pending tool calls, and ask for a risk judgment that decides approve or escalate. *When:* When approval fatigue pushes users to full-access mode and you still need guardrails against exfiltration and destructive actions.
- **Stateful WebSocket transport for agent loops** — Hold one persistent connection to the responses endpoint. After the first request, send only new items such as tool results, not the full history each time. *When:* When a run makes many small tool calls and network round trips dominate latency.
- **Goal loop with an explicit done tool** — Store an objective, re-inject a continuation prompt after each turn, and stop only when the model calls an update-goal tool. Write objectives that are concrete and checkable, so completion is easy to detect. *When:* For long autonomous runs where the agent must keep going until a verifiable condition holds.
- **Server-side compaction item** — Trigger compaction manually or automatically. Replace the old window with a compaction item that holds the needed state for later turns. *When:* For runs that last hours or days and cannot fit in one context window.

- In the WebSocket demo, the continuation sends one item where the HTTP version sent nine items back (demo example, not a benchmark). ([16:46](https://youtu.be/shRR1e2HXMk?t=1006))

## Hot takes
- Once inference is fast, the network round trip, not the model, becomes the bottleneck in agent loops.
- Goal objectives should be concrete and verifiable, not long essays, so the harness can tell when the work is done.
- Approval fatigue is a bigger practical problem than model capability, and a read-only reviewer sub-agent can handle most escalations.
