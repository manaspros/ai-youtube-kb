> Better Stack runs three one-shot coding tasks (portfolio site, HN clone upgrade, three.js voxel game) through OpenCode on Z.ai's GLM 4.5 and Claude Sonnet 4; Claude wins two of three and GLM is pitched as close enough at $3/month.

## Summary
The host compares GLM 4.5 (Z.ai) with Claude Sonnet 4 on three coding tasks of rising difficulty, all run in OpenCode because Claude Code does not switch providers easily. On the easy task (a portfolio site with a contact form and dark mode), both models one-shot a working site, GLM in about 2m20s for roughly $0.12, while Claude cost about three times as much but looked more polished. On the medium task (upgrading a React/Vite Hacker News clone with infinite scroll, caching, live comments and search), Claude produced the stronger result in 10m39s for $0.92, while GLM took 5m28s, failed on load until the console error was pasted back in, and still did not render comments. On the hard task (a three.js Minecraft-like voxel game), GLM produced a playable-ish game in about a minute for about $0.07 and fixed collision and added trees with one follow-up, while Claude's version had inverted, slanting mouse look and a shaking floor and was judged unplayable. The host concludes Claude is slightly better overall, but GLM's coding plan at about $3/month is close enough to recommend for cheap, fast coding; the main gap he names is that GLM 4.5 is not multimodal and the 4.5V variant reads images poorly in OpenCode. The sample is one run per model per task, and the cost figures come from OpenCode's estimates.

## Techniques
- **Same-prompt head-to-head in one harness** — Give identical prompts to each model inside the same agent harness (here OpenCode), record time and estimated cost per run, and judge the result by running it. Use separate runs per model so the results do not leak across sessions. *When:* Choosing a cheaper coding model against a baseline without a formal benchmark, when you care about time, cost and whether the output runs.
- **Paste the runtime error back into the agent** — When a generated app fails to load, copy the full browser console error into the same agent session and ask it to fix that error. The host did this when the GLM build had a missing dependency and a blank page. *When:* Early failures on a one-shot build, where the error message is more useful to the agent than a description of the symptom.
- **Ask for clarifying questions before the build** — Put in the prompt that the agent should ask clarifying questions before it starts, if it has any. Answer them, then let it build. The host used this with GLM and Claude; Claude asked about texture choice and block placement. *When:* Specs that leave design choices open, such as art style, controls or rules, where one-shot output would otherwise guess.
- **Put the spec in a prompt .md file** — Store the task description in a markdown file and tell the agent to run that file as its prompt, instead of typing a long prompt inline. The host did this with Claude on the medium task. *When:* Reusing the same spec across models so the comparison stays fair, or keeping a task description you may rerun.
- **Targeted follow-up prompts for specific bugs, and restart when the bug is vague** — For a concrete bug such as collision or a missing feature, send a short follow-up naming that behavior; the host's GLM collision fix and tree addition worked this way. For bugs you cannot describe precisely (the slanting mouse look, shaking floor), the host advises regenerating from scratch instead of patching. *When:* Deciding between patching generated code and regenerating it, based on whether you can describe the bug in a way the agent can act on.
