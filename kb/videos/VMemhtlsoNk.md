> Mike Spitz (PFF) reports a Jan–Mar 2026 case study where agent-driven spec, design doc, ticket and PR flow cut delivery time and dropped Scrum for a 20-engineer team.

## Summary
Mike Spitz, speaking for PFF (a sports data company with a consumer fantasy and betting arm), describes a case study run from January to March where two strong engineers used an agent-driven workflow. The flow goes from a spec, to an agent interview, to a lightweight design doc (LDD) generated by a skill, to auto-created tickets and PRs. He reports about 25x more deploys and roughly 10x blended output versus a 10-person team, with a feature that was estimated at four months finishing in under two. He caveats that small teams are naturally faster, and says output only matters if customers are happier, citing a survey score of 8.6/10 versus about 7 to 7.5 before. Sprint planning, standups, refinement and project managers were dropped and replaced by huddles, auto-updated tickets and customer-survey retros. He stresses a slow, phased rollout that starts with the best engineers on non-critical systems, verifiable deterministic checks, agent code review for style nits, and composable per-step skills. Humans remain needed for security, product feel and scope control.

## Key ideas
- **Measure output by customer happiness, not PRs or code volume** — PFF blended ticket count with code complexity to get a 10x output figure, but the speaker says the real test is customer satisfaction. Surveys rose to 8.6/10 from about 7 to 7.5 before AI. ([2:26](https://youtu.be/VMemhtlsoNk?t=146))
- **Remove the ceremonies that existed because engineers were the bottleneck** — With engineering no longer the constraint, sprint planning, estimation, standups, refinement and the project manager role were dropped. Huddles every other day with engineers, product and design replaced them. ([5:20](https://youtu.be/VMemhtlsoNk?t=320))
- **Spec and design doc are the real planning layer** — An agent interviews the author about the spec, then a skill writes an LDD that matches past LDDs. The LDD is circulated for engineer feedback, and tickets and PRs are generated from it. ([5:20](https://youtu.be/VMemhtlsoNk?t=320))
- **Let PR state drive ticket state and make tickets non-blocking** — Ticket status follows the PR: open becomes in progress, review updates it, merge closes it. Generated tickets are structured to avoid blocking each other, and any real dependencies are flagged. ([6:46](https://youtu.be/VMemhtlsoNk?t=406))
- **Offload nit-level code review to agents, keep humans on the big picture** — Agents handle style and opinion-based comments that engineers dislike giving or receiving, which removes the emotional friction. Humans still review design and architecture. ([10:25](https://youtu.be/VMemhtlsoNk?t=625))
- **Verifiable deterministic checks come before autonomy** — Tests, feature flags for trunk-based development, and product-specific generated analytics give agents checkable targets. Guardrails should work before autonomous flows run. ([10:25](https://youtu.be/VMemhtlsoNk?t=625))
- **Treat the lifecycle as a factory and turn each step into a composable skill** — Break the flow into small parts such as branch naming, feature flags and an API pattern, then encode each as a skill. Be wary of third-party skills whose opinions conflict with your own engineering standards. ([11:51](https://youtu.be/VMemhtlsoNk?t=711))
- **Post-merge QA agent checks acceptance criteria; self-healing is planned** — Each merge deploys to staging, then a QA agent checks the tickets against acceptance criteria and reports failures. The speaker plans to have an agent turn those failures into fix PRs, but says this is not built yet. ([12:53](https://youtu.be/VMemhtlsoNk?t=773))
- **Start with the best engineers, boring tasks and a slow phased rollout** — Begin with the strongest engineers on tasks people dislike, in non-critical systems first. Giving everyone a coding agent and a hackathon did not work for others, because every org's style is different. ([8:59](https://youtu.be/VMemhtlsoNk?t=539))

## Techniques
- **Agent-interviewed spec then skill-generated LDD** — An agent interviews the author to sharpen the spec. A skill then drafts a lightweight design doc by analysing past LDDs so new work matches existing patterns. Circulate it for feedback before generating tickets. *When:* Use before any agent builds a feature, to stop over-engineering and keep style consistent across a codebase.
- **Auto-generated, non-blocking tickets and PR-driven status** — Generate tickets from the approved LDD and structure them so none block each other, flagging real dependencies. Sync ticket status from PR events (open, review, merge). *When:* Use when a team wants to drop standups and sprint refinement while keeping an accurate board.
- **Agent code review limited to opinion-level nits** — Run an agent over PRs for style, naming and convention issues, and leave architecture and design to human reviewers. *When:* Use when human reviewers spend time on style comments and you want their attention on design.
- **Post-staging QA agent against acceptance criteria** — On merge, deploy to staging, then spawn a QA agent that reads the ticket acceptance criteria and tests each one. It reports failures per item. Planned extension: an agent turns failures into fix PRs. *When:* Use to verify agent-written features automatically before human QA.
- **Composable per-step skills for the delivery lifecycle** — Write one skill per lifecycle step (branch naming, feature flags, API design pattern) and compose them. Review third-party skills for conflicting opinions before adopting them. *When:* Use when you want consistent output across many agents and repos.
- **Customer survey as the primary retro signal** — Run statistically significant customer surveys each cycle and track deploy frequency. Ask engineers to flag problems immediately, not at sprint end. *When:* Use when you need a retro metric that reflects product value rather than activity.
- **Phased, non-critical-first rollout** — Pick the most capable engineers, run proof-of-concept features in low-stakes systems, then move to high-traffic products once guardrails hold. *When:* Use when adopting agents in an existing org with mixed engineering styles.

## Hot takes
- Scrum did not survive the change, and sprint planning and estimation add no value once engineering is no longer the bottleneck.
- Small companies have a structural advantage over large enterprises in rolling this out.
- Engineers who are curious will thrive, while those who need prescriptive specs will struggle.
- Teams will likely need to estimate token spend per feature once vendor token subsidies end.
- Giving everyone a coding agent and a hackathon is why many AI rollouts have stalled.
