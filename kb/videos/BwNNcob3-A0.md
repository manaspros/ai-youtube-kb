> Blind-judged comparison of Claude Fable 5.1 and GPT-6 Astra on the team's own client-style projects: Fable wins quality, interaction and review depth; Astra wins cost, speed, instruction following and long-running builds.

## Summary
The AI LABS team ran Claude Fable 5.1 and GPT-6 Astra on work from their own software projects rather than public benchmarks, then had GPT-5.6 score the outputs without knowing which model produced them. They report an overall score of 86 vs 84 without saying which model got which, and Fable leads on quality (88 vs 84), design interaction (94 vs 85) and review quality (84 vs 78). Astra leads on long-running autonomous builds (93 vs 90), instruction following (96 vs 88), cost (80 vs 66 on the cost score, $27.69 vs $49.18 estimated) and speed (70 vs 67). The speaker's main methodological point is that Fable 5.1 in Claude Code can silently switch to a weaker model when a request hits its safety rules, so a run may not be fully from Fable. The final advice is to pick the model per task, and the segment includes a sponsored Zapier SDK ad.

## Techniques
- **Blind LLM-as-judge on your own tasks** — Run each candidate model on the same real project tasks. Have a separate judge model score the outputs without knowing their source. Score several separate dimensions: code quality, task completion, working features, long-running autonomy, design, cost, speed, tool use, instruction following, and review quality. The team used GPT 5.6 as judge. *When:* When choosing a model for your own codebase and public benchmark scores are not enough. Use it to pick a model per task type.
- **Human-in-the-loop UI review with a per-model viewer** — Build a simple viewer for each model's output so a person can open and use each generated app or design side by side. Judge interaction and usability by hand, and treat the model's self-scoring of design as weak evidence. *When:* When evaluating generated front-end work. A judge model can miss issues such as a sign-out button that is unreachable at normal zoom.
- **Autonomy test with a vague brief written in the model's own prompting guide style** — Give each model a short app idea, following that model's prompting guide, and do not specify details. Record whether it finishes without stopping to ask, whether it recovers from build errors, and whether it runs its own checks. Then review the finished app. *When:* When you want to measure how far an agent can go without guidance on long-running tasks.
- **Track output tokens and tool calls as cost drivers** — Break cost into input, cached-read and output tokens, plus the number of tool calls by the main agent. Estimate API-equivalent cost from token counts when you run on a subscription. Note that output tokens and tool calls can dominate the bill even when per-token prices match. *When:* When comparing models or agent runs by cost and when the price per token is the same.
- **Enforce file-edit tool use and check for violations afterward** — Tell the model to use its own file-edit tool, not shell commands, so changes are tracked and easy to undo. After the run, check for files created by shell commands, for commit or co-author lines the instructions prohibit, and for ignored rules. *When:* When the work must stay auditable or follow repo conventions. Post-run checks are needed because models may ignore rules as work continues.
- **Planted-bug review test with decoys** — Add a known number of bugs to a codebase and also include correct code that looks suspicious. Measure how many planted bugs the model finds, how many extra real problems it finds, and whether it reports the correct code as bugs. Then measure how many confirmed bugs it fixes in a larger project. *When:* When evaluating code-review agents. Recall is measured against known bugs, and false positives are measured against the decoys.
- **Check whether the model changed mid-run** — After a safety refusal or a long run, check which model actually produced the output. The speaker reports that Claude Code can silently switch from Fable to a weaker model when a request hits safety rules, and that users often do not notice. *When:* When trusting outputs from a coding agent, especially on sensitive or long tasks, and when the harness may fall back to another model.

## Hot takes
- Quality is capped at 2 because the video has a sponsored Zapier SDK segment (around 5:32), per the rubric, even though the comparison data is substantive.
- Sample size is small and undisclosed: the team says 'multiple client projects' that they cannot reveal, six runs for cost, and single runs for each design task. Scores are 0-100 values set by the team and by a judge model, with no variance or repeat runs reported.
- The headline 86 vs 84 is never attributed to a model in the video. The closing verdict says Astra is the 'clear winner across multiple categories', but Fable leads on quality and review, so the overall call depends on how the categories are weighted.
- Cost figures are API-equivalent estimates from token counts on a subscription plan, not actual billed amounts.
- The 'silent switch to a weaker model' claim is raised as a concern but not shown with evidence in the video, and the video does not say how often it happened in the tests.

## Relevance to our work
- **agentos** (2/3): Per-model cost, token and tool-call breakdowns and silent fallback to a weaker model are the same issues a multi-provider proxy with budgets and routing has to track. → *Log the model actually served for each request and flag any fallback, then run a blind judge on your own AgentOS tasks before choosing routing rules.*
- **prosharness** (2/3): ProsHarness wraps the Claude Code CLI, and the talk shows the CLI can switch models mid-run and ignore rules such as co-author lines and tool-use restrictions. → *Add post-run checks to ProsHarness that compare the model in the run log with the requested model and scan the diff for banned co-author lines and shell-created files.*
