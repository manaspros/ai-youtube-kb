> Breakdown of "Jeff mode": llama.cpp constrained choice scoring is fast, but its confidence score comes from masking and renormalizing, needs calibration on your own data, and its speed depends on model architecture.

## Summary
Kai explains TypeSafe's "Jeff" structured-classification product, which returns labels plus a confidence score, and an open-source llama.cpp fork that imitates it. The fork skips token-by-token generation: it reads the prompt once, caches it, and scores each allowed answer as a branch in one batched decode. The speed gain is measured (2.6x for compact JSON, 5.5x with a reasoning field), but the confidence number is produced by masking out-of-list tokens and renormalizing, so a confused model can report high confidence. Insider LLM's 47-item benchmark found both approaches under half accurate, yet wrong answers had lower minimum-field probability (about 0.62 vs 0.8), so the score carries signal. A 0.8 escalation gate would send about 62% of traffic to the expensive model, and the threshold must be calibrated on labelled data. Architecture matters: plain attention models batch well, while sliding-window, hybrid, and MoE models lose the speedup. The transcript file ends at about 13:20 of a 14:20 video, so the last minute is not covered.

## Key ideas
- **Forced-choice scoring replaces generation for classification** — Instead of generating JSON token by token, give the model a fixed list of allowed answers. The prompt is read once and cached; each candidate is a short branch off that cache, and all branches are scored in one batched GPU decode. Options sharing a prefix are stored as a tree and split where they diverge. ([2:38](https://youtu.be/Oi4JPj58lUA?t=158))
- **The speedup is measured, and it scales with output length** — Insider LLM's regression: picking costs about 298 ms base, while writing costs about 275 ms plus 26 ms per output token. That is 2.6x faster for compact JSON and 5.5x faster when the output includes a reasoning field, because the reasoning tokens were the expensive part. ([3:48](https://youtu.be/Oi4JPj58lUA?t=228))
- **The confidence number is manufactured by masking** — Example: the model gives billing 30%, technical 10%, and 'I' 60%. Masking everything outside the list and renormalizing turns that into 75% billing even though the model was mostly confused. The number is derived from real probabilities but does not mean what it looks like. TypeSafe's CEO said plain masking is insufficient and claimed RL-based calibration; this was not verified in the video. ([4:57](https://youtu.be/Oi4JPj58lUA?t=297))
- **The score still carries signal, but the benchmark is small and both methods were weak** — On 47 items with a 27B model, picking got 21 right and writing got 23, both under half on a three-field classifier. Wrong answers had an average lowest-field probability of about 0.62, versus about 0.8 for right answers. One item was wrong in all three fields at 98%+ confidence. ([6:16](https://youtu.be/Oi4JPj58lUA?t=376))
- **A 0.8 escalation gate costs most of the savings** — Gating at 0.8 and escalating anything below it caught 21 of 26 wrong answers, but also escalated 8 of 21 correct ones. That sent 29 of 47 items (62%) upstairs. The 18 items kept locally were 72% correct (13 of 18). The creator's own recommended pipeline never tests the threshold. ([7:32](https://youtu.be/Oi4JPj58lUA?t=452))
- **Calibrate on your own labelled data, and use temperature scaling** — TypeSafe's Banking77 benchmark showed 80% accuracy at 88% average confidence, which is overconfident by about 8 points. Temperature scaling cut that calibration error by roughly two thirds. A 1.5B model on an 8 GB M1 gave about 0.8 for nearly every question, which makes a filter useless. Label a few hundred examples, bucket them by confidence, and choose the cut where each bucket meets your target accuracy. ([8:41](https://youtu.be/Oi4JPj58lUA?t=521))
- **Model architecture decides whether batched branches are fast** — Plain attention (a 1.5B Qwen with 28 standard layers) lets 128 parallel sequences share the cache cheaply on an M4 Max. Sliding-window Gemma allocates a window per sequence, so the README caps it at 12 branches on a 12 GB card. Hybrid recurrent models split the batch and a 4B hybrid was no faster than a 12B dense model. MoE models copy expert weights over PCIe on batches above about 30 tokens, so a Qwen 35B-A3B never got under 1 second. ([9:54](https://youtu.be/Oi4JPj58lUA?t=594))
- **Check config.json before benchmarking, since 'dense' may be hybrid** — Insider LLM's '27B dense' model has 48 linear-attention layers and 16 full-attention layers, which makes it a hybrid. Its benchmark may have run on the slow path without anyone noticing. Read the layer config before trusting any numbers. ([10:48](https://youtu.be/Oi4JPj58lUA?t=648))
- **Five practical traps, and the stock server may be enough** — (1) Alternating between two schemas invalidates the single cached prompt and made things 4.5x slower, so group calls by schema. (2) On a 24 GB card with 22 GB of weights, 16 branches failed and the fork fell back to 3. (3) Branches cannot see each other, so on a 30-field schema with dependent fields plain JSON generation won. (4) Cold picking takes about 2 s vs 1.25 s for writing, so warm up before timing. (5) Thresholds near 0.5 flipped between server sessions. For a single yes/no field, the stock llama.cpp server's logprobs/n_probs parameters are enough; NotJeff reports 23 ms median on Qwen3-8B. ([10:48](https://youtu.be/Oi4JPj58lUA?t=648))

## Techniques
- **Forced-choice classification via cached-prompt branch scoring** — Put the schema and the allowed labels in the prompt, read and cache the prompt once, then score each candidate label as a branch and return the highest-probability one. Share branches that have a common prefix. The fork is two llama.cpp commits; the speaker describes a memory sequence-copy call (captioned 'LAMA MemorySecCP') that copies the cached context per branch and reads per-token logits. *When:* Short categorical outputs (labels, intents, yes/no) at high volume on a local model, where output-token count dominates latency.
- **Single-field logprob check on the stock server first** — For one yes/no or single-label field, request token probabilities from the stock llama.cpp server with the n_probs / logprobs parameters and renormalize over the allowed options yourself. The fork only adds batch decoding, multi-token labels and normalized probabilities across the candidate set. *When:* Before adopting a fork: if you only need one field's probability, the stock server may be enough.
- **Calibrated confidence gate with escalation** — Label a few hundred of your own examples. Bucket predictions by confidence and find the cut where each bucket reaches the accuracy you need. Send everything below that cut to a larger model on purpose. Track the escalation rate, since a wrong threshold can send most traffic upstairs. *When:* A cheap local model acts as the first pass and a bigger model handles uncertain cases. Do not use a round number such as 0.8 without testing it.
- **Temperature scaling for post-hoc calibration** — Fit a temperature parameter on held-out labelled data to correct overconfidence, then re-measure accuracy against confidence. The speaker reports this cut Banking77 calibration error by about two thirds. *When:* Confidence scores are systematically too high, as in the Banking77 example.
- **Group requests by schema to keep the prompt cache warm** — Sort the batch so all calls using one schema run together, then switch schemas. Do not interleave schemas, because each switch evicts the single cached prompt. *When:* Serving several classification schemas through one llama.cpp process.
- **Benchmark hygiene for local inference** — Read config.json to identify layer types (full attention, sliding window, linear/recurrent, MoE) before running benchmarks. Warm the cache with one call before timing. Test the fork's branch limit on your own card, since it fell back to 3 branches on a 24 GB card with 22 GB of weights. *When:* Any local benchmark whose result will guide a production decision.
- **Keep dependent fields in plain generation** — If a field depends on another field's answer (for example isAdult depending on age), do not use parallel branches, because branches cannot see each other. Use normal JSON generation for those schemas. *When:* Schemas with inter-field dependencies, where the speaker's 30-field test favored plain JSON generation.

## Hot takes
- The 0.9 or 75% confidence from Jeff-style forced choice is manufactured by masking and renormalizing; it is not a real probability that the answer is right unless the model is calibrated.
- Vendor's calibration claim (RL for calibrated decisions) is unverified; the only evidence shown is TypeSafe's own Banking77 benchmark, which was overconfident by 8 points.
- A 0.8 escalation threshold, which the open-source creator recommends, is never tested in the video and may send most traffic to the expensive model.
- The 27B 'dense' benchmark model is actually a hybrid, so its benchmark may have used the slow path.
- For a single yes/no field, the stock llama.cpp server may be enough and the fork may be unnecessary.
- Quality is capped by a small sample (47 items) and secondhand community benchmarks; the video reports the fork's own readme limits and Reddit reports without independent verification.
