## Key ideas
- **Plan product requirements before any prompt, using a product-focused planner agent rather than Claude's technical planning mode** — A custom planner agent keeps asking questions until the requirements are understood, including MVP scope and an 'anything else?' pass. It then saves a PRD to the project folder, divided into phases with the key design decisions. ([1:06](https://youtu.be/ywIhw15za9Y?t=66))
- **Write CLAUDE.md yourself and keep it to what the agent cannot figure out** — Link the PRD instead of repeating requirements. Include conventions, rules and writing style, not project structure, which the agent can read. The speaker says /init generates the file from the existing code rather than from what the agent needs, and that the file is loaded once and stays in context, so it has to be kept lean and updated over time. ([2:33](https://youtu.be/ywIhw15za9Y?t=153))
- **Set up MCPs, agents and skills before building, with a clear split between them** — MCPs connect external services (Supabase, shadcn/ui, Playwright). Agents get a dedicated context window for tasks like planning, committing with pre-checks and conventional messages, refactoring, and UI verification through the Playwright MCP. Skills cover repeatable workflows that need references or scripts, built with the skill-creator from an open-source repo. ([3:36](https://youtu.be/ywIhw15za9Y?t=216))
- **Add negative constraints because agents are biased toward action** — Positive specs leave gaps that agents fill with extra features or experiments. A docs file listing what not to build or do, linked from CLAUDE.md, closes those gaps. Example: explicitly ban the default purple/blue/white palette rather than only describing the desired one. ([5:03](https://youtu.be/ywIhw15za9Y?t=303))
- **Use path-specific rules for parts of the app, linked from CLAUDE.md** — Each rule file declares the paths it applies to and holds the instructions for that area. CLAUDE.md stays limited to broad principles and points to these rules. The speaker recommends a front-end skill for consistent UI guidelines. ([5:03](https://youtu.be/ywIhw15za9Y?t=303))
- **Keep a progress file and a learnings file that the agent updates during the build** — The progress file gives one place to see what is done and what remains, so the agent does not have to reread the code and docs. The learnings file records each error, its cause and its fix, so the same mistake is not repeated. CLAUDE.md must tell the agent to keep both updated. ([7:32](https://youtu.be/ywIhw15za9Y?t=452))
- **Write tests from the PRD before implementation, not after** — Tests derived from the spec check the required behavior. Tests written after the code tend to fit the implementation, including its gaps. The speaker says open-ended prompts like 'test the application' make the agent optimize for what was built. ([8:56](https://youtu.be/ywIhw15za9Y?t=536))
- **Track issues upfront, with GitHub for technical users and Notion or Trello for everyone else** — Commit after every implementation with detailed conventional messages so the agent can track progress and revert breaking changes. Use git worktrees for isolated experiments. Connect the Notion or Trello MCP and state in CLAUDE.md that the agent should log bugs there, so non-technical teammates can report issues. ([10:14](https://youtu.be/ywIhw15za9Y?t=614))
- **Plan for concurrent users before going to production** — Tell the agent the expected number of users and that they will use the app at the same time. The agent then writes load-test cases. Plan mode maps approaches and asks questions from several angles, aiming for graceful failure and scalable design. ([11:36](https://youtu.be/ywIhw15za9Y?t=696))

## Techniques
- **Agent-led PRD interview** — Create a planner agent whose instructions include a PRD template. Prompt Claude to load it and describe the app. Answer its questions until it has the full picture, then have it save a phased PRD with design decisions to the project folder. The video does not show the agent file or prompt text. *When:* At project start, before any code or implementation prompt, when you want product-level requirements instead of technical planning-mode output.
- **Lean hand-written CLAUDE.md that links the PRD** — Do not generate CLAUDE.md with /init. Reference the PRD instead of restating requirements. Include only conventions, best practices, writing style and rules the agent cannot infer, such as coding conventions. Leave out project structure, which the agent can read. Keep it updated as the project proceeds. *When:* Before implementation starts, and then continuously, since the file is loaded once and stays in context for the whole session.
- **Agent vs skill split** — Make a skill for a repeatable workflow that needs guidance, references or scripts (built with skill-creator, and the open-source front-end skill is one example). Make an agent for a task that needs its own context window, such as a planner, a commit agent (pre-checks plus conventional commit messages), a refactoring agent, or a verification agent that drives the Playwright MCP through UI user flows. *When:* When deciding what to set up before building a project with several repeatable workflows.
- **Path-scoped rules linked from CLAUDE.md** — Create one rule file per part of the app. Each file names the paths it applies to and carries the instructions for that area. Link the rule files from CLAUDE.md so the agent knows to follow them. CLAUDE.md keeps only the broad principles. *When:* When different parts of the codebase need different implementation guidance, such as UI versus backend.
- **Negative-constraints docs file** — Write a docs file listing what the agent must not build or do, such as default colour palettes, unrequested features or extra experiments, and link it from CLAUDE.md. Each constraint is explicit, not implied from the positive spec. *When:* When the agent keeps adding unrequested features or defaults to a generic look, and positive specs are not enough to stop it.
- **Progress file plus learnings file** — Keep one progress file that lists feature status, so the agent can read it instead of rescanning code and docs. Keep one learnings file that records each error, its cause and its fix. In CLAUDE.md, instruct the agent to update both as it works. The video names no file names. *When:* On any multi-feature build where the agent loses track of status or repeats mistakes across sessions.
- **Spec-first test generation** — Point the agent at the PRD and have it derive the expected behaviour and likely failure points, then write the tests before implementation. Run the tests at the end to check the built code against the spec. Avoid open-ended 'test the app' prompts. *When:* Any feature build where tests should check the specification, not the implementation.
- **Commit-per-implementation with worktrees** — Configure the agent to commit after each implementation with detailed conventional commit messages, so the history records what was done and can be reverted if a change breaks the codebase. Use git worktrees to try experiments in isolation. Track issues in GitHub, or connect the Notion or Trello MCP and instruct CLAUDE.md to log bugs there. *When:* Throughout the build, and especially when several people or non-technical reporters are involved.
- **Concurrency-aware load test planning** — Put the expected number of simultaneous users in the prompt. Have the agent write stress or load tests from that figure, then use plan mode to map approaches and ask questions from several perspectives about production failure modes. *When:* Before production, when the app will serve multiple users at once.
