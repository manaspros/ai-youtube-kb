> Better Stack walks through Microsoft Research's Flint, a local MCP chart tool where the LLM writes about 10 lines of semantic JSON and a deterministic compiler emits Vega-Lite, ECharts or Chart.js specs; a research preview with no benchmarks yet.

## Summary
The video presents Flint, a Microsoft Research project for generating charts from AI agents. The core claim is that chart generation mixes two jobs: semantic meaning (which column is a month, which is revenue), which LLMs handle well, and geometry (axis scales, step sizes, label spacing, color ramps), which LLMs get wrong often enough to matter. Flint has the model emit a short JSON spec using one of 70-plus semantic types, and a deterministic TypeScript compiler makes the geometric decisions and outputs a standard Vega-Lite, ECharts or Chart.js spec. The presenter installs it as a local MCP server, renders a heat map from a CSV, and shows an interactive chart panel that stays editable without re-prompting. The speaker is clear that this is a roughly two-month-old research project at v0.28, that the headline token reduction is the author's own unbenchmarked number, and that frontier models already one-shot simple charts, so the case is narrower: small or cheap models, composite charts like waterfalls, and end-user-facing charts. Missing features include maps, 3D, network graphs, layering, accessibility, and a Python package. The most transferable point is the general pattern of an LLM emitting a small, validatable intermediate representation with a deterministic layer doing the rest.

## Key ideas
- **Chart generation is two separate jobs: semantic meaning (what each column is) and geometry (scales, steps, label spacing, color ramps). LLMs are good at the first and unreliable at the second.** — This split is the framing for the whole design; the speaker says geometry is where generated charts usually break. ([0:00](https://youtu.be/xFWhiWe91BE?t=0))
- **Flint's team measured about 80% success on good-looking charts in their own analytics agent, which meant roughly one in five charts shipped to real users was broken.** — This failure rate is the motivation for moving geometry out of the model. The speaker attributes the number to the Flint team's internal measurement. ([0:57](https://youtu.be/xFWhiWe91BE?t=57))
- **Flint splits the work: the model writes about 10 lines of JSON using semantic types (over 70, such as quarter, price, rank, percentage change), and a deterministic compiler emits a real Vega-Lite, ECharts or Chart.js spec.** — The compiler owns every geometric choice, so the model never specifies pixel-level or scale-level details. The output is a standard spec the user can take to any of those backends. ([0:57](https://youtu.be/xFWhiWe91BE?t=57))
- **Changing one semantic type cascades into many correct decisions. Switching a column from quantity to percentage change flips the palette to diverging, changes number formatting, and rescales the axis.** — Demonstrated in the video at 2:19. The speaker's framing: you tell the tool what the data is and never where the pixels go. ([2:19](https://youtu.be/xFWhiWe91BE?t=139))
- **Flint compiles to Vega-Lite rather than replacing it. The motivation is that hand-written Vega-Lite gets verbose fast for things like waterfall charts, while Flint's output stays about 10 lines.** — Mermaid is mentioned as flowchart-only and not suited to customer-facing charts; the speaker contrasts Flint's five local tools with chart MCP servers that expose 26 tools and render on a third-party server. ([3:32](https://youtu.be/xFWhiWe91BE?t=212))
- **Honest caveats: research project, about two months old at v0.28, with cross-renderer inconsistencies (same spec rendering differently in Vega-Lite and ECharts) and a token-reduction claim that is the author's own unbenchmarked number.** — No maps, 3D, network graphs or layering; accessibility is an empty GitHub issue; no Python package yet. The speaker says frontier models already one-shot simple charts, so Flint's value is narrower: small or cheap models, composite charts, and end-user-facing output. ([3:32](https://youtu.be/xFWhiWe91BE?t=212))
- **The most generalizable takeaway is a pattern the speaker says agentic systems are converging on: the LLM emits a tiny, validatable intermediate representation and deterministic code does everything else. You can validate 10 lines of JSON before rendering, but not a hundred lines of generated D3.** — The speaker presents this as the strongest consensus point in the discussion around the project, not as something Flint alone proved. ([4:57](https://youtu.be/xFWhiWe91BE?t=297))

## Techniques
- **Semantic spec plus deterministic compiler** — Have the model emit a small JSON spec that tags each column with a semantic type (e.g. quarter, price, rank, percentage change) and nothing about layout. A deterministic compiler then picks scales, palettes, number formats, label spacing and layout, and emits a standard Vega-Lite, ECharts or Chart.js spec. Validate the JSON before compiling. *When:* Use when a chart is generated by a small or cheap model, when the chart type is composite (waterfall, sunburst), or when end users see the output and 80% correctness is not acceptable. Also a general template for any agent output that must render or execute correctly.
- **Change the meaning, not the geometry** — To alter a chart's appearance, change a semantic tag on the column (e.g. quantity to percentage change) rather than asking for a different palette, axis or format. The compiler re-derives the rest. *When:* When iterating on a chart with an agent and you want fewer reprompts and consistent styling.
- **Local MCP chart rendering** — Install with a one-line MCP add (spoken as claude MCP add flint; the exact package name was not clearly captured in the transcript). The project is pure TypeScript on Node 18. RenderChart returns a PNG into the chat, and CreateChartView opens an editable interactive panel. Rendering happens locally, so the data never leaves the machine. *When:* When you want chart rendering in Claude Code or another MCP client without sending data to a third-party chart server.
- **Validate the IR, not the generated code** — Let the LLM output a small structured artifact that a schema or validator can check before rendering, and keep the generated surface area small enough that errors are caught early instead of surfacing as broken D3 or chart code. *When:* When designing any agent workflow where model output drives rendering, execution or a downstream system.

## Hot takes
- Flint is a 'problem for small or cheap models'; frontier models already one-shot simple charts, so power users with large models may not need it.
- The 100,000-to-200 tokens per chart claim is the author's own unbenchmarked number; the paper is not yet published.
- Chart MCP servers that render on someone else's server are a privacy problem for customer-facing products; a local renderer avoids that.
- Mermaid is for flowcharts, and the speaker says you do not ship Mermaid charts to customers.
- The most agreed-on takeaway in the discussion was not about charts: agentic systems are converging on an LLM-emits-small-IR, deterministic-layer-does-the-rest shape.
