> Walkthrough of Claw Patrol, an open-source agent firewall from the Deno team: a gateway injects real credentials into agent requests, enforces per-action rules, and logs every request.

## Summary
A Better Stack host walks through Claw Patrol, an open-source gateway from the Deno team that sits between AI agents and the internet. The architecture is one gateway server (holding rules, credentials, logs and a dashboard) that agent machines join over Tailscale or WireGuard, with single commands or whole machines routed through it. The presenter frames three problems: access is not action control, agents should not see secrets, and people cannot see what an agent did. Credentials (Postgres users, Anthropic and Codex subscriptions, GitHub, bearer tokens, custom headers) live only on the gateway and are attached to matching requests, so the agent sends a request with no key or a fake password and still succeeds. Rules are written per endpoint in CEL with an approve or deny verdict, so a Postgres DROP TABLE can be denied with a custom message, routed to Slack for human approval, or checked by an LLM judge. Profiles group credentials, endpoints and rules for role-based access, and a test command replays dashboard actions against local rule changes. The presenter says setup was tedious, IP-address endpoints (a local Proxmox host) were not intercepted, and the project is very early; there are no benchmarks.

## Key ideas
- **Three problems the gateway targets: access is not action control, agents should not see secrets, and operators cannot see what agents did.** — Presenter frames Claw Patrol as a security firewall between agents and the internet, with one gateway server holding rules, credentials, logs and dashboard, and agent machines routing traffic through it. ([0:00](https://youtu.be/ZiFoTw6doGI?t=0))
- **Credentials are injected at the gateway, so agents never hold real secrets.** — Agent runs through the claw patrol run wrapper send curl without an API key and a Postgres connection with a fake password. The gateway attaches the real credential when the request matches an endpoint, so logs and prompt injection cannot leak the value. ([1:21](https://youtu.be/ZiFoTw6doGI?t=81))
- **Rules evaluate the action, not just the access: a Postgres DROP TABLE is denied with a custom message.** — The gateway checks each request against rules and returns a custom error (schema changes only via migration PRs). Presenter also notes the same mechanism can route an action to Slack for human approval or to an LLM judge that checks outbound content such as support replies for offensive text or missing greetings. ([2:22](https://youtu.be/ZiFoTw6doGI?t=142))
- **Every request is visible in a dashboard with full command or API detail, active sessions and token usage.** — Clicking a request shows the actual Postgres command or the API request and response, which removes the need to piece together logs from each service the agent touched. ([3:41](https://youtu.be/ZiFoTw6doGI?t=221))
- **Configuration model: an HCL file defines endpoints, credential types are bound to endpoints, and rules use CEL with approve or deny verdicts.** — Credential values are filled in from the dashboard, not the file. Approve-verdict rules let you run an allow-list (deny by default), while the presenter used a block-list. Profiles bundle credentials with their endpoints and rules to give teams different access. A test command reruns dashboard actions against local rule edits to catch changed outcomes or accidental leaks. ([4:39](https://youtu.be/ZiFoTw6doGI?t=279))
- **Honest limits: setup is tedious, IP-address endpoints were not intercepted, and the project is early.** — The presenter wants AdGuard-style click-to-add rules from observed requests. He could not see requests to a bare IP endpoint on a local Proxmox server, which he suspects may be partly misuse. He concludes the tool needs work before it stops interrupting flow. ([6:02](https://youtu.be/ZiFoTw6doGI?t=362))

## Techniques
- **Gateway-side credential injection** — Keep real secrets only on the gateway. Declare each credential with its type and the endpoint it applies to in the HCL config, then enter the value in the dashboard. Run agents through the gateway (claw patrol run <command>, or route the whole machine) and let agents send requests with no key or a placeholder. The gateway attaches the real value on matching requests. *When:* Agents run on machines or in sessions you do not fully trust, or whose logs and prompts might be exposed to injection. Works for HTTP bearer tokens, custom headers and database logins (Postgres, ClickHouse).
- **Action-level rules with a deny-by-default allow-list** — For each endpoint, write a CEL expression over the request (HTTP, Postgres, Kubernetes, and so on) and set the verdict to approve or deny. Use a custom deny message that tells the agent the approved path (for example, schema changes via migration PRs). For allow-lists, deny everything by default and add approve rules for specific actions. *When:* You need to stop destructive or policy-violating actions such as DROP TABLE, sends to customers or leaks of specific content, without trusting the agent's own judgment.
- **Human approval and LLM-judge rules on the gateway** — Attach a verdict that routes the request to a human for approval (currently Slack only) or to an LLM that judges the request or response content against your criteria, such as offensive wording or missing greetings in support replies. *When:* Actions are too risky to auto-approve but too frequent for a human to review in a terminal, or the policy is semantic and cannot be written as a simple expression.
- **Role-based access with profiles** — Group credentials, their endpoints and their rules into named profiles, then assign profiles to developers, support staff or agents so each team gets different credentials and rules. *When:* Several teams or agent types share the same infrastructure and need different access to the same systems.
- **Regression-testing rule changes** — Download the recorded rule actions from the dashboard, edit the rules locally, and run the test command to see which recorded requests change outcome before deploying. *When:* Before tightening or loosening rules, to catch accidental leaks or accidental blocks.
- **Gateway topology over a mesh VPN** — Run the gateway on one Linux server and join agent machines to it over Tailscale (supported out of the box) or WireGuard. Route an OpenClaw gateway through it permanently, and use single-command wrapping on a laptop for ad-hoc sessions. *When:* Agents run across several machines, such as a laptop and a home server, and you want one place for rules and logs.

## Hot takes
- Presenter says the setup process was tedious and he wants click-to-add rules from observed requests, AdGuard-style.
- IP-address endpoints on a local Proxmox server were not intercepted and did not show in the dashboard. He suspects possible misuse on his side, but says fixes are needed.
- The claim that gateway-side checks save you from 'pretty much every other type of AI attack' is hedged with 'theoretically' and was not tested in the video.
- Framing access as action control (verdicts on each request) is a stronger model than IAM-style allow-lists alone.
