> EXO Labs' Alex Cheema argues decode is memory-bound, so local frontier inference is a memory, bandwidth and energy problem. He demos Mac clusters over Thunderbolt RDMA and a Mac plus DGX Spark prefill/decode split.

## Summary
Alex Cheema of EXO Labs argues that running frontier-scale models locally is mainly a decode-phase problem, since decode is memory-bound and a single local user cannot batch requests the way a data center can. He frames the decode limits as three things: the model must fit in memory, memory bandwidth sets speed, and energy per byte moved sets power draw and battery life. He claims gains compound across the stack (kernels, harness, hardware, models), and he projects that a roughly $5,000 box could reach near-frontier performance within about 18 months. Most of the talk is a live demo: four Mac Studios connected by Thunderbolt 5 with RDMA running GLM 5.1 (4-bit, about 400 GB) via tensor parallelism, plus a Mac and DGX Spark setup that splits prefill onto the Spark and decode onto the Mac, streaming the KV cache over 10 GbE. The demo's ~2x end-to-end speedup is on one large prompt, and several demos were disrupted by Wi-Fi and macOS version mismatches. He ends by proposing public, budget-based benchmarks showing a quality-versus-speed Pareto frontier, and he warns against unrigorous auto-research and heavy quantization claims.

## Key ideas
- **Decode is memory-bound and prefill is compute-bound, and a local user runs at batch size 1.** — Cloud providers batch many users to amortize weight reads. A single local user cannot, so decode speed is set by memory capacity and bandwidth. Prefill matters less for local use, though the speaker admits long prompts make it significant. ([11:10](https://youtu.be/ESbWpPT_9-o?t=670))
- **Decode is limited by three things: fit in memory, memory bandwidth, and energy per byte moved.** — If the model does not fit, it loads from disk, which is very slow. Bandwidth sets tokens per second. Energy per byte determines power draw, which matters most on battery devices. He cites a phone example where inference at 10 to 15 W drains a 10 to 15 Wh battery in about an hour. ([12:35](https://youtu.be/ESbWpPT_9-o?t=755))
- **Gains compound across the whole stack, not only the hardware.** — He cites a 5x intelligence-per-watt gain over about two years from hardware and about 3x from models, and says the stack as a whole could reach roughly 100x price-performance. These are the speaker's own projections. ([16:59](https://youtu.be/ESbWpPT_9-o?t=1019))
- **Unnecessary GPU kernel launches are a large, fixable overhead in local inference.** — On Qwen 3.5 on Apple Silicon, measured speed was about 50% below the theoretical rate. The cause was many separate kernel launches. Fusing them gave about a 30% speedup, and the speaker says the same kind of overhead appears in orchestration, communication and the harness. ([8:42](https://youtu.be/ESbWpPT_9-o?t=522))
- **The harness changes performance: the same model behaves differently in different coding harnesses.** — A good harness keeps the prompt prefix stable so the KV cache gets hits. He suggests inspecting the prompt breakdown with the /context command in Claude Code. Most of the prompt (system prompt and tools) does not change between turns. ([10:09](https://youtu.be/ESbWpPT_9-o?t=609))
- **Prefill and decode can run on different devices, with the KV cache streamed between them.** — Prefill is run on a compute-heavy box (DGX Spark) and decode on a bandwidth-heavy one (Mac). The KV cache must move between them, and transfer has to overlap with compute or the split becomes slower. The split only pays off for large prompts. Short prompts show no speedup. ([41:38](https://youtu.be/ESbWpPT_9-o?t=2498))
- **RDMA over Thunderbolt 5 makes tensor parallelism across Macs practical.** — Plain Mac-to-Mac latency was about 300 microseconds. A 60-layer model with tensor parallelism needs two syncs per layer, so about 120 per token, which costs roughly 40 ms per token at that latency. RDMA brings latency to single-digit microseconds. RDMA needs Thunderbolt 5 and a recovery-mode enable step. ([1:09:43](https://youtu.be/ESbWpPT_9-o?t=4183))
- **The cluster uses event sourcing: append-only logs per node that are merged, with full history replayed when a node joins.** — Devices can sleep or leave at any time, so the design keeps request history from being lost. Every node holds the full model weights, because a partial shard would change when a node dies. ([1:20:48](https://youtu.be/ESbWpPT_9-o?t=4848))
- **Judge local setups by a quality-versus-speed Pareto frontier at a fixed budget, not by raw tokens per second.** — The planned public benchmark covers hardware, models, quantizations and pruning, with quality measured via intelligence per joule. The speaker warns that 1-bit quantization or heavy expert pruning often gives worse results than a smaller unquantized model. ([1:32:53](https://youtu.be/ESbWpPT_9-o?t=5573))
- **Auto-research needs the scientific method (hypothesis and controlled tests), or it is only a slot machine.** — He calls brute-force automated search a slot machine that can show false breakthroughs. Quality regressions from automated changes can go unnoticed when only speed is checked. ([1:37:34](https://youtu.be/ESbWpPT_9-o?t=5854))

## Techniques
- **Kernel fusion of redundant launches** — Profile per-token execution, find many small separate kernels, and fuse them into fewer launches, which cut per-token overhead. *When:* Decode is latency-bound and per-token compute is small, so launch overhead is a significant share of step time.
- **Cache-stable prompt prefix in the harness** — Keep the system prompt and tool definitions byte-identical across turns, and inspect the prompt breakdown (the speaker uses /context in Claude Code) to confirm cache hits. *When:* Long multi-turn agent sessions, especially local runs where prefill cost matters and cache hits save it.
- **Prefill/decode disaggregation across devices** — Run prefill on a compute-heavy device, stream the KV cache to a bandwidth-heavy device for decode, and overlap the transfer with compute so it does not stall decode. *When:* Very large prompts (the demo used a roughly 38 KB to 100 KB paper) on heterogeneous hardware with a link fast enough to hide transfer time.
- **Tensor parallelism over RDMA** — Split each layer across machines and sync per layer over a low-latency link. Count syncs per token times per-sync latency to check whether the speedup survives. *When:* A model too big for one machine, with machines connected by a microsecond-latency fabric such as Thunderbolt 5 RDMA.
- **Full-replica weights with append-only event logs for cluster state** — Each node keeps an append-only log that is merged across nodes, and a joining node replays history. Every node holds the whole model so a node failure does not reshape the shards. *When:* Dynamic clusters where devices sleep or leave, and in-flight requests must not be lost.
- **Expose each node over HTTP and reach it through a mesh VPN** — Each device serves an HTTP API. Remote access is through Tailscale rather than a bundled networking layer. *When:* Accessing a home cluster from a phone or another network without managing firewall or NAT setup.
- **Budget-based Pareto benchmarking** — Benchmark each hardware, model, quantization and pruning combination for speed, prefill time and quality, then present the frontier for a given budget. *When:* Choosing local hardware and models for a fixed spend, and tracking progress as software, hardware and models change.
- **Hypothesis-driven auto-research** — Form a hypothesis, run a controlled experiment, check quality as well as speed, and iterate. Do not accept an automated change just because it runs. *When:* Using automated search or agents on performance work, where a silent quality regression is easy to miss.

## Hot takes
- Renting out spare local compute at the hardware layer tends to fail. Rent out tokens or tasks instead.
- Running a large model from SSD or disk is not interesting. The memory-hierarchy problem is the real target.
- Raspberry Pi cluster demos are usually heavily quantized and not useful. Phone inference of frontier models is years away.
- Auto-research without hypotheses and controlled tests is a slot machine that can produce false breakthroughs.
- Most consumer tasks (transcription, summarization, to-do lists) do not need a huge model, so most usage can run locally.
