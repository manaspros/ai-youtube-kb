> AI LABS walks through Claude Code agent teams, an experimental upgrade over sub-agents where teammates message each other directly, and shows three uses plus practical rules for keeping them on track.

## Summary
The video presents Claude Code agent teams as an experimental feature released alongside Opus 4.6. Unlike sub-agents, which report only to the caller and need the orchestrator to relay messages, teammates are full independent Claude Code sessions that share a task list and a mailbox, under a team lead that creates, coordinates and shuts them down. Team state (members and tasks) is stored locally, and the feature is off by default and must be enabled with an experimental CLI flag. The host demonstrates three runs: a parallel code review where one agent finds issues while another fixes them in priority order (critical security first), a four-agent multi-perspective bug hunt that converged on a stale closure in a useEffect in about 2 to 3 minutes, and a six-agent app build where builder agents waited on a foundation agent and the run consumed around 170k tokens. The practical advice is to scope each agent explicitly with prompts or per-task documents, keep teammates off the same files, tell the lead to wait rather than take over slow work, size tasks to be self-contained, and monitor and redirect agents that drift. The evidence is one team's anecdotal experience with demo-style runs, not a benchmark, and the video is a light promotional walkthrough that points to a paid community for the prompts.

## Key ideas
- **Agent teams are an experimental upgrade to sub-agents, launched with Opus 4.6, for tasks that need coordination between agents.** — Sub-agents cannot talk to each other; the orchestrator must relay their output or they write notes to project files. Teams let members message each other directly, which removes that relay overhead. ([0:00](https://youtu.be/MSyWjPDrHJw?t=0))
- **A team is a lead plus independent teammate sessions with a shared task list and mailbox.** — Each teammate is a fully separate Claude Code terminal session with its own context window. The lead creates and closes them, assigns work, and synthesizes results. Team members and task assignments are stored locally, keyed by task name. ([1:16](https://youtu.be/MSyWjPDrHJw?t=76))
- **Parallel review and fix works better as a reviewer-fixer pair than as sub-agents writing report files.** — The reviewer sends findings to the fixer bug by bug, and the fixer starts on them while the reviewer keeps looking. Critical security issues were handled first, then medium-priority ones, and the two ran at the same time. ([2:43](https://youtu.be/MSyWjPDrHJw?t=163))
- **You can steer an individual teammate mid-run, and the lead must shut agents down cleanly.** — Any teammate's task can be reassigned or changed while the team runs. Once work is done, control returns to the main agent, which checks the changes and sends shutdown messages so teammates exit without errors. ([3:46](https://youtu.be/MSyWjPDrHJw?t=226))
- **Multi-perspective debugging: spawn several agents, each assigned one aspect of the app, to hunt a hard bug together.** — Four agents were given similar prompts but different angles. The lead waited, then analysed their findings. All four converged on the same root cause, a stale closure in a useEffect, and the lead verified it by checking itself. The run took about 2 to 3 minutes versus an estimated 5 to 10 for linear checking. ([3:46](https://youtu.be/MSyWjPDrHJw?t=226))
- **Staged builds need explicit blocking: a foundation agent runs first and the lead unblocks the rest.** — Six agents were spawned for a full app build: two for research and foundations (including package installs), and four page builders that waited for the unblock signal. Once unblocked, the builders worked side by side and kept messaging each other for consistency. The whole run used around 170k tokens. ([5:07](https://youtu.be/MSyWjPDrHJw?t=307))
- **Four practical rules: scope explicitly, keep teammates on separate files, make the lead wait, and size tasks correctly.** — Scope each agent by naming files or giving it a task document in the project. Avoid two agents editing the same file. Remind the lead not to take over a slow teammate's job. Tasks that are too small add coordination overhead and tasks that are too large risk wasted work. Monitor agents and halt or redirect any that drift. ([7:35](https://youtu.be/MSyWjPDrHJw?t=455))

## Techniques
- **Enable agent teams behind the experimental flag** — Set the Claude Code CLI experimental flag for agent teams to 1 (the transcript's auto-captions garble the flag name, so check the current docs for the exact variable), then start a new session. Teams only appear in sessions started after the flag is set. Ask for a team in explicit wording, e.g. telling Claude to use an agent team for the job. *When:* Whenever a job is large enough to parallelise and needs agents to coordinate, and you accept that the feature is experimental with rough edges.
- **Reviewer and fixer pair for parallel code review** — Prompt the lead to spawn one teammate to find issues in the codebase and another to fix them. Tell the reviewer to prioritise critical security issues first, then medium ones. Let the reviewer send each finding to the fixer directly, so no intermediate report file is written. Be detailed in the prompt so the team follows the intended direction. *When:* Code review where you want findings fixed as they are found, without the overhead of writing to a shared file.
- **Multi-perspective bug hunt** — Describe the bug and ask for several team members, each assigned a different aspect of the app (for example, a different component or layer). Give them similar prompts with different focus areas. The lead waits for all findings, analyses them, and then checks the conclusion itself before accepting it. *When:* Hard bugs where the cause is unclear and several independent investigations would find it faster than one linear pass. Expect high token use.
- **Staged build with a blocking foundation agent** — In the prompt, assign one agent to install packages and set up the environment, and mark the page-builder agents as blocked until the lead sends an unblock signal. After the foundation is ready, unblock the builders so they work in parallel and keep messaging each other for consistency between components. When each agent finishes, the lead sends it a shutdown message. *When:* Greenfield builds where later parts depend on shared setup such as dependencies or a scaffold.
- **Per-assignment task documents to bound scope** — Create one task document per assignment in the project folder, each defining that agent's job and its boundaries, and point each agent at its document. Keep the assigned file sets disjoint so agents do not overwrite each other. *When:* Any multi-agent run, so each agent can work independently inside a defined scope.
- **Lead supervision rules** — Tell the lead explicitly to wait for teammates rather than doing their work when one is slow. Size tasks so each is self-contained and balanced. Watch the agents during the run, and when one drifts, halt it and give it new instructions. *When:* Any run longer than a few minutes, to avoid redundant work, coordination overhead and wasted effort.

## Hot takes
- Agent teams are a real speed gain for parallel review and debugging but are still experimental, disabled by default, and have teammate-handling bugs.
- Token cost is the main trade-off of running several full sessions in parallel, and the speaker says it has to be watched carefully.
- Sub-agents are not obsolete: teams are only justified when agents must communicate, and parallel independent work can still use sub-agents.
- The video is a light promotional walkthrough that points viewers to a paid community for the prompts, so the reproducible detail is thinner than the title suggests.
