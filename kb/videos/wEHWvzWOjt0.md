## Summary
The host tests GLM 4.6 (Z.ai) against Claude Sonnet 4.5 to see whether a much cheaper coding plan is worth switching to. He first checks the claimed 128k to 200k context expansion and the plan pricing, which he says gives far more messages per hour than Claude Max. In the first test he gives both models the same inventory-management prompt in plain HTML, CSS and JavaScript and judges UX and UI; Sonnet produces a more complete and polished result, while GLM's output is bare and has a misplaced add button and bugs it needed several commits to fix. In the second test he uses the BMAD method (epics split into stories) to build a dual physical and digital inventory app in Svelte 5 with Supabase and shadcn-svelte, with Sonnet implementing the first two epics. For epic 3 GLM produced correct-looking pages and Svelte code but broke on integration, leaving about 10 percent of the work for Sonnet. The host's conclusion is that GLM is a cheap option for React-style work and still needs a stronger model to finish Svelte integration. The evidence is a single run per model with subjective judgments, and the pricing figures are the host's own readings.

## Techniques
- **Same-prompt model bake-off for UI work** — Send the identical requirements-only prompt (user journeys, no technical or design guidance) to each model in separate runs, then judge the output on UX, UI, routing and mistakes. Record each model's commits to see how it fixes its own bugs. Note the billing path for each run, since the subscription and API comparison is not like-for-like. *When:* Quick screening of a cheap model before committing to it for front-end or creative tasks.
- **BMAD epic-to-story decomposition for agent builds** — Plan the project in the BMAD method: split it into epics (foundation, then one epic per feature area), split each epic into stories, and have the agent implement the stories one at a time so each run stays within context. *When:* Multi-feature builds where a model may lose coherence over a long run, or when you want a fair comparison across models with the same planned context.
- **Provision the backend through the database MCP** — Let the agent create the Supabase tables and auth through the Supabase MCP instead of setting them up by hand. The host set up five tables, including auth, this way before the agent built the features on top. *When:* Greenfield apps where the backend schema should be generated by the agent and checked by the user.
- **Commit per fix to attribute regressions to a model** — Commit after each step, including each bug fix, so you can see which model change introduced or fixed an issue. The host used this to show GLM's auth loop fix and its mock-data inconsistency. *When:* Comparing model output on the same task, or auditing an agent's work step by step.
- **Cheap model for most of the build, strong model for integration** — Let the cheaper model implement the isolated pieces, then hand the integration step to a stronger model. The host found GLM did about 90 percent of epic 3 and Sonnet finished the rest. *When:* Cost-sensitive builds where the cheap model is good at self-contained files but weak at wiring them together.
- **Use a stack with thin training data as a stress test** — Pick a framework the models have seen less of, such as Svelte 5, to see how a model handles unfamiliar APIs. The host expects React results to differ, which he has not tested. *When:* Evaluating a model's generalisation beyond its strongest framework.
