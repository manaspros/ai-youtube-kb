> AI LABS walks through GSD (Get Shit Done), a planning-and-execution framework for Claude Code, and compares it with BMAD and Superpowers. Main takeaway: choose the framework by how fixed your requirements are.

## Summary
The host argues that no single AI coding framework fits every project and that the mismatch is a selection problem. GSD suits experimental, uncertain-scope builds because it plans one phase at a time instead of locking the whole roadmap up front. BMAD, with its PRD and sharded task docs, suits fixed, well-specified systems but becomes brittle when requirements change, and Superpowers' TDD suits domains where a wrong action is costly. The walkthrough covers installing GSD per project into .claude (agents, commands, hooks), a questioning phase that writes a short project.md, parallel background research with a Sonnet synthesizer, and per-phase discuss, research, plan, verify and execute steps. Plans are checked by a verifier agent, split into waves that run in parallel where independent, and verified with Playwright and a goal-alignment check before the user approves. The one example app took about 138k tokens for its first iteration. The host concludes GSD is overkill for simple apps. The video is a single run with no benchmarks, and the GenSpark segment is a sponsor read.

## Techniques
- **Choose the framework by requirement certainty** — GSD for uncertain scope and MVPs (plan per phase); BMAD for fully specified conventional systems (upfront PRD and architecture, sharded tasks); Superpowers for high-cost-of-error features (TDD first). A hybrid is possible: build the core with GSD, then add Superpowers for the critical parts. *When:* Before installing any agent framework, to decide between over-planning and under-preparing.
- **Per-project install with project scope** — Copy the install command from the GSD project, paste it in the project folder, pick the agent (Claude), and choose project-level scope. The install adds agents, commands and hooks under .claude. The exact command text is not spoken in the transcript. *When:* When each project may need a different framework configuration.
- **Initialise GSD on existing vs blank codebases** — On a blank template, skip the codebase mapping step. On a real existing codebase, map it first so the agent learns it before planning. *When:* Starting a GSD project inside an existing repo or a fresh scaffold.
- **Keep the planning anchor short** — Store a deliberately brief project.md in .planning/ with description, out-of-scope items, context constraints and key decisions, so that the agents stay focused. Track progress with git commits made through a pre-commit check script. *When:* Any long-running agent project where drift and context bloat are a risk.
- **Per-phase discuss, then concise context file** — Start each phase with an optional discussion session. It writes a short context.md under .planning/phases/. Skip the discussion if the earlier questioning already covers the phase. *When:* Before planning each phase of a multi-phase build.
- **Ground phase research in docs with Context7** — Connect the Context7 MCP server before running phase research, so the research agent looks up library docs instead of using web search. Read research.md for the confidence level of each finding. *When:* When the project relies on current library or framework APIs.
- **Adversarial plan verification and waves** — A planner agent writes the phase plan with dependencies and requirement IDs. A verifier agent returns warnings until the plan is implementable and aligned with the goal. Split the plan into waves, run independent tasks in parallel, and commit after the plan passes. *When:* When you want execution that is checked before any code is written, and independent tasks can run in parallel.
- **Phase verification gates** — After each wave, run Playwright checks and a verifier that compares the result with the phase goal. Approve in the chat, then mark the phase complete. The state is in the planning docs, so the next phase can resume after a context clear. *When:* Any multi-phase build where the user should check progress at each phase boundary.

## Hot takes
- The sponsored GenSpark segment (5:23) caps quality at 2 by rule. The GenSpark claims (a $200M ARR figure and unlimited model access) are sponsor claims, not checked here.
- The host says many context-management techniques 'don't really matter' with a 1M-context model, yet the same video describes compaction signals at 200k. The host does not measure this.
- The video is one run on one toy-scale Next.js app with no benchmarks, so the token and quality claims are anecdotal.
- The host reports that GSD's phase research defaulted to web search with '2025' in the query. That is a sign the framework's research is not grounded by default, which the host fixes by recommending Context7.
- The host's claim that GSD's adversarial planning runs 'without us having to control any of that manually' is not tested in the video.
