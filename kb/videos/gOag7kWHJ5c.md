> A Go tutorial that wires an existing slog logger into OpenTelemetry (bridge, provider, OTLP/HTTP exporter, Collector) so logs can correlate with traces and metrics. Covers only Go; the video says JS and Python were not yet supported.

## Summary
The video shows how to send an existing Go slog logger's output into the OpenTelemetry pipeline so logs can be correlated with traces and metrics. The pipeline has three parts: a bridge that converts slog records into OTel log records, a provider that adds metadata such as trace and span IDs and manages record lifecycle, and an exporter that sends OTLP protobuf data over HTTP to an OTel Collector. The demo runs a Go Fiber article API (logging via slog, requests sent from Bruno) with a Docker Compose OTel Collector that receives OTLP on port 4318 and prints logs through a debug exporter. The code changes are a resource (service name and version), a log exporter with the insecure option for local HTTP, a logger provider, an otelslog bridge, and a context-aware createLogger that returns the logger and provider so the provider can be shut down cleanly. The video stops at console output: it shows the resource, the logs, and any added context values, but does not show a backend or an actual trace-to-log correlation. Its closing claim that correlation becomes possible is therefore not demonstrated. Roughly the last 40 percent of the video is a promotional segment for Better Stack.

## Key ideas
- **Plain logs are disconnected from traces and metrics, and OTel can correlate them automatically once they enter its ecosystem.** — Speaker frames the problem as grepping logs during debugging. OTel log support was limited at recording time, with no JavaScript or Python support yet, so the demo uses Go. ([0:00](https://youtu.be/gOag7kWHJ5c?t=0))
- **The log path has three stages: bridge, provider, exporter.** — The bridge converts existing slog records into OTel log records. The provider adds metadata such as trace and span IDs and manages record lifecycle. The exporter sends OTLP data over HTTP in protobuf format to an OTel Collector, which can forward to Prometheus, Grafana, or Better Stack. ([1:25](https://youtu.be/gOag7kWHJ5c?t=85))
- **The Collector needs only an OTLP HTTP receiver and a debug exporter to start.** — The config defines an OTLP receiver on the HTTP endpoint, a debug exporter with detailed verbosity (without verbosity the logs are not visible), and a logs pipeline from otlp to debug. The speaker suggests checking the config in otelbin, which renders the pipeline. ([2:46](https://youtu.be/gOag7kWHJ5c?t=166))
- **A shared resource identifies the service across all signals.** — newResource merges OTel's default resource with a schema URL, a service name (GoFiberApp), and a service version. The speaker notes traces and metrics would need the same resource to line up. ([4:10](https://youtu.be/gOag7kWHJ5c?t=250))
- **The exporter, provider and bridge are wired together, and the old slog handler is dropped.** — The log exporter uses an insecure option so it sends plain HTTP rather than the HTTPS default, which is fine for testing. The provider takes the resource and the exporter as its processor. The otelslog bridge takes a logger name and a with-source option. Once the provider is connected, the old slog handler is deleted, and the function returns the logger and provider. ([5:31](https://youtu.be/gOag7kWHJ5c?t=331))
- **The provider is shut down on exit, and extra context values attached to log calls are picked up automatically.** — After docker compose up and running the Go app, two API calls (add article, get articles) produce log records in the Collector output that include the resource, the schema URL, and each log message. The speaker says added context values should also appear, though the demo does not show a case with them. ([6:58](https://youtu.be/gOag7kWHJ5c?t=418))

## Techniques
- **OTel log bridge for an existing slog logger (Go)** — 1) Keep the existing slog code. 2) Change createLogger to take a context and return both the slog logger and the logger provider. 3) Build a resource with newResource: the default resource merged with a schema URL, service.name (GoFiberApp) and a service version. 4) Create a log exporter using the OTLP log HTTP package with the insecure option for local HTTP. 5) Create a logger provider with the resource and the exporter as its processor. 6) Create the otelslog bridge with a logger name and the with-source option, and connect it to the provider. 7) Remove the old slog handler and return the logger and provider. 8) In main, create a context and defer a shutdown of the provider. *When:* Adding OpenTelemetry log export to an existing Go service that already logs with slog, without rewriting log call sites. Use it when you need trace and span IDs on logs (the provider adds them) and a shared resource across signals. Note from the video: at recording time this covered only some languages, not JS or Python.
- **Local OTel Collector for log debugging via Docker Compose** — Add an OTel Collector service to docker-compose.yml with the image, a container name, a volume mounting the local collector config into the container, and port 4318 exposed (OTLP over HTTP). Config: receivers.otlp with the HTTP protocol; exporters.debug with verbosity detailed; service.pipelines.logs with receivers [otlp] and exporters [debug]. Start with docker compose up, then run the Go app and watch the Collector output. Paste the config into otelbin to visualize the pipeline. *When:* Verifying OTel log export locally before adding a real backend. The debug exporter prints every received log to the console. The video names no image tag, so pin one yourself.

## Hot takes
- The closing claim that OTel logs enable automatic correlation with traces and metrics is never shown. The demo only prints logs to the console and never displays a trace linked to a log.
- Language coverage is a major caveat: the video says JS and Python were not supported at recording time, which limits this approach for many services. It is mentioned once at the start and never revisited.
- The Better Stack segment (roughly 1:25 to 2:00, plus the closing) reads as a sponsored plug, so quality is capped at 2 by the sponsored-segment rule.
- Substance is thin for a 2025 talk: one toy Go API, debug-exporter output only, and no production concerns such as batching, sampling, or the cost of shipping every log.
