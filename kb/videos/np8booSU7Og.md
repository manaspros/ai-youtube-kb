> Kai Explains walkthrough of a fully local AI stack: llama.cpp behind one OpenAI-compatible endpoint, with AnythingLLM for chat and RAG, Pi as a local coding agent, and n8n for email automation.

## Summary
The video builds a self-hosted AI stack in layers: an inference engine (llama.cpp's llama-server, or LlamaSwap as a fallback), a chat UI (AnythingLLM, Open WebUI as an alternative), a RAG knowledge layer, a local coding agent (Pi, OpenCode as an alternative), and an automation layer (n8n). The organizing idea is that every layer exposes one OpenAI-compatible REST endpoint, so each tool can talk to every other tool without custom integrations. The walkthrough gives concrete settings for each layer, including the Docker, provider and vector-database choices. The n8n example is an hourly workflow that has an agent label important emails through a local model. It closes with ops advice for running the stack as an always-on home lab: a dedicated machine, auto power-on after outage, a container manager, and Tailscale. The speaker is candid that local models trail cloud frontier models on deep reasoning and long context, and frames the trade as privacy and control over raw capability. There are no benchmarks or cost figures, so the value is the architecture and setup recipe.

## Techniques
- **Single OpenAI-compatible endpoint as the integration bus** — Serve the model with llama-server (or LlamaSwap). Set every client's OpenAI base_url to http://<machine-ip>:8080/v1. Use the same URL in chat, RAG, coding agent and automation tools. *When:* Wiring several local tools together without writing per-tool integrations.
- **llama-server router preset mode, with LlamaSwap as fallback** — Start llama-server in model preset mode to use its built-in router. If the router misbehaves, run LlamaSwap on top of llama.cpp with a single config file that defines the models and acts as the router. *When:* Serving several local models behind one endpoint. Use LlamaSwap if llama-server's experimental router is unreliable.
- **Headless AnythingLLM in Docker, configured from the UI** — Take the AnythingLLM Docker Compose file from its GitHub page. Set network mode to host so it can reach other services on the machine. Remove the embedding and model settings from the file. Start it, then go to Settings > Providers > LLM > Generic OpenAI, set the base URL to the machine IP and llama-server port, and set the context window and max token limits. *When:* Running a private chat front end on the same machine as the model server, and keeping model config out of the compose file.
- **Local RAG with AnythingLLM defaults** — Settings > Vector Database: keep the default LanceDB. Check the embedder settings (defaults are fine). Use the Document Upload button in the workspace header to add PDFs, papers or internal docs and let them embed. Set the workspace chat mode from agent to chat. Answers cite the source document. *When:* Grounding answers in your own documents without sending them to a third party.
- **Pi as a local coding agent** — Install Pi with npm. Add the llama.cpp plugin. Open Pi's global settings file and set the llama.cpp URL to http://<server-ip>:8080/v1. Run /models inside Pi to list the models configured in llama-server. Point Pi at a project directory and ask it to analyze the codebase, map the architecture, or fix build and config errors. *When:* Keeping a working coding agent that runs offline on local models, as a backup to cloud coding tools. OpenCode is named as an alternative to compare.
- **n8n email triage with a local model** — Start n8n with its Docker Compose file. Under Credentials, add an OpenAI credential and change its base URL to the local server. Use any string for the API key. Build a workflow: (1) schedule trigger every hour that checks email; (2) pass subject and body to an agent node with a system prompt defining what is important to you; (3) attach an OpenAI chat model node using that credential, with the Responses API option unchecked to use the standard OpenAI-compatible path; (4) add a Gmail tool action that adds a label, with the message ID set to the trigger's dynamic value and a short tool description so the agent knows when to use it. *When:* Running recurring classification or triage on email with the model kept local. The Gmail API still handles the mail itself.
- **Always-on home lab hardening** — Use a dedicated machine that stays on. In the BIOS, set power-on after power loss. Run a container manager such as Portainer or Arcane for a web dashboard instead of the terminal. Install Tailscale for private access from a phone or laptop. *When:* Moving the stack from a laptop to a machine that runs automations around the clock.
