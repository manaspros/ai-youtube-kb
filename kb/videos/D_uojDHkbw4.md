> Explains the "gauntlet loop" (agent builds, critic sub-agents judge against a reference) and its two failure modes, then shows a planning-skill fix: a settled spec and pass/fail answer key the critic checks against.

## Summary
The video explains the "gauntlet loop", a prompt pattern that popularized one-shot builds of games and apps: a main agent splits the goal into sub-agents, each builder gets a critic sub-agent that sends work back until it passes, and a reference product (Call of Duty) is the stop condition. The speaker names two problems: the main agent controls how critics are spawned and what they judge, and the quality bar only works when an existing product exists to compare against, so for new software the critic invents its own standard. The proposed fix is Matt Pocock's Wayfinder planning skill, which turns fog (unsettled decisions) into a map of questions, resolves each by research, prototypes, or a real-world check, and writes a spec. The creator trimmed Wayfinder to two outputs, a map and a pass/fail answer key, ran a 34-question interview on an HR system, then pointed the gauntlet loop at the answer key. The build took 1h33m, used about 40% of a Max session limit, and would have cost about $116 on the API, with the creator reporting that every requested feature worked but some issues remained. The evidence is a single anecdotal build with no measured comparison against a baseline loop.

## Key ideas
- **The gauntlet loop is a main agent that splits the goal into sub-agents, each with its own critic sub-agent that returns work until it passes.** — Matt Shumer's three-line prompt defined the product and quality bar, told the main agent to split work into sub-agents, and attached a critic to each builder. Critics start with no memory of prior rounds and never build anything. A keyword at the end turns it into a dynamic workflow running a fleet of sub-agents, which the speaker describes as a diamond graph: one task, parallel sub-agents, then one synthesizing agent. ([2:43](https://youtu.be/D_uojDHkbw4?t=163))
- **The stop condition in the gauntlet loop is a blind side-by-side comparison against a shipped product.** — The critic is told to compare the agent's output with a reference game without knowing which one the model made, and to pick the better one. Without a real reference the critic has nothing to stop against. ([4:10](https://youtu.be/D_uojDHkbw4?t=250))
- **Problem one: the main agent controls checking, so verification is not concrete.** — The main agent decides how critics are spawned and what their judgment prompts say. The speaker argues checks should be planned explicitly, so that when something breaks you can tell which check failed and why. ([5:38](https://youtu.be/D_uojDHkbw4?t=338))
- **Problem two: for new products there is no reference, so the critic invents a standard and drifts.** — The loop works for games, landing pages and 3D worlds because something close exists to copy. For novel business logic, the critic picks its own bar, and the speaker says a wrong direction can waste many tokens after a big batch of features is built against it. ([7:02](https://youtu.be/D_uojDHkbw4?t=422))
- **Wayfinder fixes the reference problem by turning planning fog into settled decisions and a spec.** — Wayfinder builds a map of open decisions split into ready-to-settle and blocked-by-fog. Fog is cleared by research, a rough prototype to react to, or a real-world job such as signing up for a service. Answers go back onto the map and unblock dependent questions. The output is one spec the critic can use as the bar. ([8:21](https://youtu.be/D_uojDHkbw4?t=501))
- **The creator cut Wayfinder down to two files, a map and an answer key of pass/fail checks, instead of one requirement file per decision.** — The modified skill writes .wayfinder/ with the decision map (decision, reasoning, finished-state) and an answer key where every line is a pass or fail check. The loop is then told the .wayfinder folder is the single source of truth. The modified skill uses Grill Me for questioning, and the speaker says only three skills are needed. ([11:14](https://youtu.be/D_uojDHkbw4?t=674))
- **The build ran in phases: plan, install tools, build a foundation, then launch many agents on separate parts.** — The loop first plans what to build, then the tools to install, then the foundation, and only then fans out parallel agents, each on one part of the system. Every agent checks against the answer key, and the prompt forbids close-enough results and shortcuts. ([12:41](https://youtu.be/D_uojDHkbw4?t=761))

## Techniques
- **Three-line gauntlet loop prompt** — Line 1: what to build plus a quality bar. Line 2: have the main agent split the goal into sub-agents and attach a critic sub-agent to each builder that returns work until it passes. Line 3: a concrete reference for the critic's stop condition, judged by blind pairwise comparison (the critic is not told which output the model made). Add the dynamic-workflow keyword at the end to run a fleet of sub-agents in parallel. Use this only when a shipped reference exists to compare against. *When:* Building something with a close existing analogue such as a game, landing page or 3D scene, where the critic can measure against something real.
- **Swap the reference for a planned answer key** — Run a planning interview first (Wayfinder with Grill Me in the video). The output is a .wayfinder folder: a decision map (each decision, its reasoning, what finished looks like) and an answer key of pass/fail checks. Then ask Claude to rewrite the gauntlet prompt so the source of truth is that folder and the critic checks everything against it. The speaker says the rewrite should keep the loop format and change only what it measures against. *When:* Building new software, business rules or anything with no existing product to copy, where you want the critic to check a spec instead of inventing a standard.
- **Planning fog map** — Keep a map of open decisions. Mark each as settleable now (all dependencies decided) or fogged (waiting on an unknown). For each fogged item, send a sub-task to clear it through research, a throwaway prototype to react to, or a real-world action such as signing up for a service. Write the answer back, unblock dependents, and repeat until no fog remains. Do not let the agent fill gaps with assumptions. *When:* Before a large agent build where the destination is clear but the path has unknowns, so the plan does not look finished while containing invented parts.
- **Phased build order inside one loop** — Direct the loop to produce, in order: a build plan, the tools to install, a foundation the other parts depend on, then parallel sub-agents, each owning one slice of the system, all checked against the answer key. Forbid close-enough results and shortcuts in the prompt. *When:* Multi-part app builds where parallel agents would otherwise start before shared infrastructure exists.
