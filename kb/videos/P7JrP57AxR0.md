> Walkthrough of Vercel's open-source Agent Browser, a headless-Chromium CLI that lets a coding agent snapshot, click and test web pages, with a comparison to Browser Use and the Playwright MCP server.

## Summary
The video introduces Agent Browser, an open-source CLI for driving a headless Chromium browser, built in a weekend by a single Vercel employee (Chris Tate) in Rust and TypeScript. The tool gives an agent CLI commands for an accessibility snapshot with element references, reference-based actions, and semantic locators by ARIA role, text or label. The presenter runs it under OpenCode with the GLM 4.7 model on a small React/shadcn/Vite login page, and the agent fixes a broken dark mode and missing login validation, checking its work with snapshots, screenshots and a bash test that uses eval. The architecture is a Rust binary that turns each command into JSON, sent over a Unix socket to a per-session Node daemon that drives Chromium through Playwright, headless by default. The presenter contrasts it with Browser Use, which can run its own plan-act-observe loop and offers SDKs, a skills marketplace and an MCP server, and with the Playwright MCP server, which supports more browsers and suits agents directly. Agent Browser is simpler and needs an external agent, and it supports only Chromium. The presenter's own verdict is that its simplicity and easy install are the reasons to use it.

## Key ideas
- **Agent Browser is a CLI wrapper that lets any coding agent drive a browser with shell commands, so it works with Claude Code, Cursor, OpenCode and similar tools.** — The agent runs commands such as click on an element reference, and gets JSON output back. There are no slash commands or skills; the agent discovers the commands by running the help output. ([0:00](https://youtu.be/P7JrP57AxR0?t=0))
- **Accessibility snapshots with element references are the core interaction primitive, with semantic locators as a fallback.** — A snapshot returns an accessibility tree with references (e.g. E2) that actions can target. Semantic locators find elements by ARIA role, text content or label when references are not wanted. ([1:12](https://youtu.be/P7JrP57AxR0?t=72))
- **A coding agent used the snapshot-act-screenshot loop to find and fix a visual bug and a validation bug in a web app it had written.** — The dark mode fix was verified by taking a screenshot before and after the change. The validation fix came with a generated bash test that checks empty input, invalid email and the redirect to the dashboard, using eval to run JavaScript in the page. ([2:36](https://youtu.be/P7JrP57AxR0?t=156))
- **The presenter's model choice limited the demo: a text-only model could not read the screenshots the agent took, and he would pick a multimodal model next time.** — The demo ran OpenCode with GLM 4.7. The presenter said he would choose a model with multimodal support so the agent can read its own screenshots. ([2:36](https://youtu.be/P7JrP57AxR0?t=156))
- **The architecture is a three-layer chain, with a per-session daemon so several browsers can be controlled at once.** — A Rust binary parses the CLI command into JSON. The JSON goes over a Unix socket to a Node daemon that manages Chromium. The daemon validates the request and runs the action with Playwright, headless by default, then returns JSON to the agent. ([3:55](https://youtu.be/P7JrP57AxR0?t=235))
- **Browser Use and Agent Browser differ mainly in whether they include the reasoning loop.** — Browser Use runs its own plan, act, observe and re-plan loop and ships Python and TypeScript SDKs, a skills marketplace and an MCP server. Agent Browser has no loop of its own and needs an external agent. ([5:21](https://youtu.be/P7JrP57AxR0?t=321))
- **Compared with the Playwright MCP server, Agent Browser is narrower: Chromium only, while Playwright covers Firefox and Safari too.** — The presenter notes that adding many MCP tools can make an agent pick the wrong one, which is a reason to prefer a single CLI tool when the agent already has many MCP servers. ([5:21](https://youtu.be/P7JrP57AxR0?t=321))

## Techniques
- **Agent-driven UI verification loop** — Tell the agent to test the change in a running app on a given port with agent-browser. The agent runs agent-browser --help to list commands, takes a snapshot to read the page structure, clicks the relevant element, takes a screenshot, then fixes and re-checks. The presenter says there are no slash commands or skills; the agent only needs the CLI on PATH. *When:* After an agent changes UI code, to confirm the change works in a real browser rather than only in unit tests.
- **Install the CLI globally and let the agent discover it** — Install agent-browser globally with npm. Point the agent at the dev server port and ask it to run agent-browser --help to see the commands. The demo does not show any config file. *When:* When you want a no-config browser tool that works with any agent that can run shell commands.
- **Generate a bash regression test from the browser session** — Have the agent write a bash script that runs agent-browser commands in sequence: fill an empty form, click submit, check for the expected error text, enter an invalid value, then a valid one, and check the destination page. For in-page checks, the script uses agent-browser eval to run JavaScript. *When:* To leave behind a repeatable check for a bug fix, not just a one-off manual test.
- **Prefer snapshot references, fall back to semantic locators** — Take a snapshot, which returns the accessibility tree with references such as E2, and act on those references. If references are unstable, locate elements by ARIA role, visible text or label. *When:* When an agent needs to act on page elements and you want a stable target that does not depend on CSS selectors.

## Hot takes
- The presenter says 2026 is the year agents write, review and test all code, and that developers are moving away from IDEs toward the terminal; this is framing rather than evidence.
- Agent Browser is a better fit than Browser Use for simple setups, because it is simpler and easier to install, even though it lacks a built-in agent loop and multi-browser support.
- Tool choice between Browser Use, Playwright MCP and Agent Browser depends on use case; the video gives no benchmark, so the comparison rests on feature lists and the presenter's own preference.

## Relevance to our work
- **prosharness** (1/3): ProsHarness runs Claude Code, and browser-based verification of UI changes is a missing check in long agent runs; this is a lightweight CLI option for it, not a core change. → *Try agent-browser as an optional verification step after a Claude Code run that touches a web UI: run agent-browser --help, snapshot the dev server page, and save the commands as a bash check that the harness can rerun.*
- **agentos** (1/3): Crucible handles sandboxed code execution, and this is a browser-execution tool with a similar split of CLI, daemon and headless browser. It is a candidate tool, not a design change. → *Read the Agent Browser source (Rust CLI to Node daemon over a Unix socket) to see whether its per-session daemon model is worth borrowing for Crucible's sandboxed execution sessions.*
