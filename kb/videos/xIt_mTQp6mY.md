> Kyle Mistele (HumanLayer) argues agent loops should be built as incremental control loops (sensor, controller, actuator) that keep humans reading the code, not blind "Ralph" loops that dump 40k-line PRs.

## Summary
Kyle Mistele, co-founder of HumanLayer, says most loop talk is hype and that blind Ralph-style bash loops produce PRs nobody can review, which fails on teams, critical systems and regulated code. He reframes loops with control theory: a set point, a sensor that measures the gap, a controller that picks a small change, and an actuator that applies it, then re-measure. Sensors can be deterministic (ast-grep rules, lint) or agent-based, and a deterministic sensor is preferred. His worked example is an incremental migration of HumanLayer's RPC procedures to Effect, using an ast-grep scan of main that is committed to version control and checked on each PR to stop regressions. The controller picks one item deterministically, optionally weighted by telemetry, and the actuator is a CLI coding agent running a hand-curated skill with golden examples. A scheduled GitHub Actions workflow runs one iteration per day and opens a PR, with a version-controlled feedback markdown file and a /iterate PR comment so humans can re-steer it cheaply. Flow control skips a run while the loop's last labeled PR is still open, so each loop has at most one open PR, and velocity is raised by batching items or running the workflow in parallel for several people.

## Key ideas
- **Blind loops are the wrong default for real teams** — A bash loop that prompts an agent produces large unreadable PRs. Ralph loops suit solo work on non-critical systems. Teams with customers, regulation and SLAs need loops that keep the code readable. ([0:08](https://youtu.be/xIt_mTQp6mY?t=8))
- **Frame agent loops as control systems** — Use the control-theory loop: a set point (desired state of some code property), a sensor that measures the error, a controller that turns the error into a small change, and an actuator that applies it. Re-measure and repeat. Kubernetes autoscaling and Postgres autovacuum follow the same pattern. ([4:12](https://youtu.be/xIt_mTQp6mY?t=252))
- **Change the system incrementally and make it measurable** — A loop fits when you can measure the property, make changes in small steps, and get feedback on each change's quality. Blind Ralph loops are not incremental, so they tend to overshoot and create huge diffs. ([6:19](https://youtu.be/xIt_mTQp6mY?t=379))
- **Prefer a deterministic sensor, and stop regressions before running the loop** — Use ast-grep rules that are language-agnostic and sit outside the TypeScript and lint config. Scan main once, sort the violations deterministically, commit the list to version control, and add a per-PR check that fails when a branch adds new violations. That check is the disturbance dampener. ([10:23](https://youtu.be/xIt_mTQp6mY?t=623))
- **Feed business signals into the controller, and keep deterministic work out of the agent** — The controller can pick the first or smallest violation with bash, jq or ast-grep. For more leverage, use telemetry (errors, missing instrumentation, APM gaps) to rank items and pass that data to the actuator. He says you should never send an agent to do work that deterministic code can do. ([11:48](https://youtu.be/xIt_mTQp6mY?t=708))
- **Make the actuator an agent plus a carefully written skill, and run it in existing CI** — The skill holds hand-written golden examples and a response template. After the agent runs, the workflow commits, pushes and opens the PR deterministically, using the agent's final message as the description. GitHub Actions runs it on a daily schedule, with no new cluster needed. ([13:03](https://youtu.be/xIt_mTQp6mY?t=783))
- **Keep humans on the loop with a version-controlled feedback file and a comment trigger** — A markdown feedback file in the repo is loaded into the actuator's context on every run. A /iterate comment on the loop's PR triggers a run that loads the diff, comments and description, and updates the feedback file. The loop only responds to PRs carrying its own label. Feedback changes can be diffed and reverted. ([14:24](https://youtu.be/xIt_mTQp6mY?t=864))
- **Flow control: at most one open PR per loop, then scale by batching** — The workflow exits early if the loop's labeled PR is still open, so no PRs stack or conflict while humans are away. To speed up, pick several items per run, run each item in its own phase with its own context window, or run the workflow once per engineer. ([15:44](https://youtu.be/xIt_mTQp6mY?t=944))

## Techniques
- **Sensor, controller, actuator loop for code migration** — Define the set point (e.g. no unmigrated procedures). Build a sensor that lists violations. Have a controller select one item and a context-carrying signal. Have an actuator agent make one change, then re-run the sensor. *When:* Incrementally migrating a codebase pattern, such as an API, library or framework, where each change can be measured.
- **Deterministic baseline plus per-PR ratchet** — Run a full scan on main and commit the sorted violation list to version control. In CI, fail any PR that adds new violations of the pattern so humans cannot undo the loop's progress. *When:* Before turning on any migration loop, so the target pattern stops growing while it is being cleaned up.
- **Ast-grep as the sensor** — Write language-agnostic ast-grep rules with include and exclude paths. Layer more rules over time. Keep the rules out of the TypeScript and lint config so agents cannot disable them with inline comments. *When:* Monorepos that span several languages, or any codebase where agents tend to suppress linter rules.
- **Golden-pattern skill for the actuator** — Write hand-made idiomatic examples before the loop runs, put them in the skill, and add a response template. Iterate on the skill over time, not all up front. *When:* Whenever an agent must reproduce a house style that is not in its training data or the public docs.
- **Scheduled CI workflow as the loop runner** — Run one loop iteration (sense, control, actuate, open PR) on a daily cron in GitHub Actions or a similar CI system that already has code access, secrets and dispatch. *When:* When you want a loop without adding new infrastructure and you want a small, reviewable PR each morning.
- **Feedback file plus comment-triggered re-steering** — Keep a markdown instructions file in the repo, load it into the agent's context on every run, and let a slash command on the loop's PR trigger a run that loads the PR context and updates the file. *When:* When the loop needs frequent human correction and you want that feedback in version control, not in a prompt.
- **Single-open-PR flow control** — Tag each loop's PRs with a label. At the start of each run, exit if a PR with that label is still open. Speed up by batching several items per run, using separate phases per item, or running several workflows in parallel. *When:* When loop output piles up faster than humans review it, or when work could duplicate or conflict across runs.

## Numbers
- Sensor output had about 50 keys per violation, so the speaker kept only four and sorted them deterministically. ([10:23](https://youtu.be/xIt_mTQp6mY?t=623))
- The speaker's team had about 150 RPC procedures to migrate. Doing one at a time, he says, would take about six months. ([15:44](https://youtu.be/xIt_mTQp6mY?t=944))
- The loop runs once a day, so the team receives one small PR each morning. ([13:03](https://youtu.be/xIt_mTQp6mY?t=783))
- The speaker says it took six months to fix Claude Code's terminal flicker, while the OpenCode team wrote a renderer in a fraction of that time. This is his anecdote, not a measured benchmark. ([2:45](https://youtu.be/xIt_mTQp6mY?t=165))

## Hot takes
- Blind Ralph loops are a teaching device that people take too literally, and they produce PRs no one can review.
- Bad code costs more in the age of agents than it ever has, so code review and readability still matter.
- Do not send an agent to do a job that deterministic code can do.
- Designing loops that read the code, not making all code read-only, is the right path for teams.
