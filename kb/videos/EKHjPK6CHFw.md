> Hands-on tutorial on installing Vector, tailing syslog and a FastAPI JSON log file, transforming logs with Vector Remap Language (VRL), and shipping the result to Better Stack over HTTP.

## Summary
The video walks through Vector, a log and metrics pipeline tool, from install on Ubuntu under WSL through to shipping to Better Stack. It installs Vector from the apt repo, runs it manually, and builds a vector.yaml with a file source for /var/log/syslog and a console sink for debugging. It then adds a file source for a FastAPI app's JSON app.log, writes that output to a new file sink, and uses the VRL REPL to parse the nested JSON message and add a derived boolean field. The enriched pipeline is finally sent through an HTTP sink with a bearer token to a Better Stack source, where the nested fields are filtered in live tail. The content is a practitioner tutorial with no benchmarks, and it stays on basic file-to-console, file-to-file and HTTP paths without covering buffering, backpressure or delivery guarantees.

## Key ideas
- **Vector models observability as a pipeline of sources (where logs come from), optional transforms (parse, enrich, sample, aggregate) and sinks (destinations such as S3, Elasticsearch, Prometheus, ClickHouse or Better Stack).** — Each component needs a type plus an inputs list, and the whole topology is defined in one vector.yaml file. The speaker presents Vector as covering both logs and metrics, with programmable transforms. ([1:18](https://youtu.be/EKHjPK6CHFw?t=78))
- **Vector can be deployed as a daemon, a sidecar or an aggregator. It compiles to a single static binary, and on Unix its only dependency is libc, so install is simple.** — The speaker installs it on Ubuntu under WSL through the official apt repo and then manages it with systemctl. He stops the background service to run Vector manually in the foreground during the demo. ([1:18](https://youtu.be/EKHjPK6CHFw?t=78))
- **Use a console sink as a debugging stage before you add a real destination, and run vector validate after each config edit.** — The first working pipeline sends a syslog file source to a console sink with JSON encoding, so the output is visible immediately. vector validate catches the config mistakes shown later. ([10:11](https://youtu.be/EKHjPK6CHFw?t=611))
- **Structure JSON logs in the app and let Vector handle the parsing. The app writes JSON lines to app.log through a Python JSON formatter, and Vector tails that file.** — The FastAPI endpoint logs a 'request received' message with a dict of client IP and request method as extra fields. A file source points at the log path, and a file sink writes the forwarded copy to /var/log/application.log with JSON encoding. ([12:52](https://youtu.be/EKHjPK6CHFw?t=772))
- **Prototype transforms in the VRL REPL (vector vrl --input <file>) before you put them into the config.** — The speaker inspects the event with '.', reads single fields, and sees that .message is a JSON string nested inside the event. Using parse_json! (the ! marks a fallible call) turns that string into an object whose keys can then be read. ([18:29](https://youtu.be/EKHjPK6CHFw?t=1109))
- **Enrich events with derived fields in the same remap step. He adds a boolean from_localhost that is true when the parsed client IP equals 127.0.0.1.** — The remap transform reassigns .message to its parsed form and sets the new key from the IP comparison. The transform takes the file source as input, and the downstream sink must be re-pointed to the transform. Otherwise vector validate reports that the transform has no consumers. ([24:36](https://youtu.be/EKHjPK6CHFw?t=1476))
- **Ship to a hosted store over the HTTP sink with a bearer token, then verify the nested fields there. In Better Stack, the speaker filters on from_localhost = true and on the nested method field.** — He creates a Vector source in Better Stack Logs and Metrics to get a source token, then adds an http sink whose auth strategy is bearer. The check is in live tail: parsed nested fields are queryable, and a POST filter returns nothing because every request was a GET. ([29:43](https://youtu.be/EKHjPK6CHFw?t=1783))

## Techniques
- **Install Vector from the apt repo and manage the service** — Run the two apt commands copied from the Vector install docs: first the command that adds the Vector repo, then apt-get install vector. Check with systemctl status vector, start it with systemctl start, and stop the daemon with systemctl stop so you can run it by hand. The exact repo-setup command is not shown on screen, so copy it from the Vector docs. *When:* Setting up Vector on a Debian or Ubuntu host (including WSL) when you want a package-managed install instead of the static binary.
- **Minimal Vector config: file source to console sink, then validate** — In /etc/vector/vector.yaml, define sources.<name> with type: file and include: [/var/log/syslog]. Define sinks.<name> with type: console, inputs: [<source name>], and encoding.codec: json. Run vector validate, then run sudo vector in the foreground to see the events. *When:* First-time pipeline setup, or when you want to confirm what Vector collects before you ship it to a real destination.
- **Python JSON logging for Vector to tail** — Attach a file handler on the app logger that points at app.log. Use the JSON formatter from the python-json-logger package on the handler, set the logger level to INFO, and log with logger.info(msg, extra={...}) so each record is a JSON line. Run the app with uvicorn <module>:app. *When:* Making a FastAPI or other Python service emit structured logs that Vector can parse without regex.
- **Remap transform for parsing and enrichment (VRL)** — Start with vector vrl --input application.log. Type '.' to see the event, '.message' to see the nested string, and then parse_json!(.message) to get an object. Put the statements in a transform with type: remap, inputs: [<source>], and a source block. Example: .message = parse_json!(.message) followed by a derived field such as .from_localhost = parse_json!(.message).<ip key> == "127.0.0.1". The IP key name is not spoken in the video, so check the logged field name. Then point the downstream sink's inputs at this transform. *When:* Logs whose useful fields sit inside a JSON-encoded string, or when you need computed fields added before storage.
- **HTTP sink to Better Stack with bearer auth** — In Better Stack Logs and Metrics, create a source with platform Vector and copy its source token. In vector.yaml add a remap transform whose input is the enrichment transform, then add an sinks entry with type: http, the ingestion endpoint URI from the Better Stack Vector docs, and auth: strategy: bearer with the token as the credential. Set the sink's inputs to the final transform. Validate, then run sudo vector. *When:* Shipping transformed logs to a hosted log store that accepts HTTP ingestion.

## Hot takes
- Vector is presented as 'the only tool you need' for logs and metrics, but the video shows only file sources, file and console sinks and one HTTP sink. It does not test that claim.
- The destination is Better Stack, the channel's own product, and the video promotes it as the place to centralise logs. This is not labeled as a sponsored segment, but it is a vendor-favourable walkthrough.
- There is no coverage of buffering, backpressure, retries, delivery guarantees or sink performance, which are what matter for an observability pipeline in production.
- The VRL example stores the parsed object back into .message, which changes the schema. Downstream consumers that expected a string will break, and the video does not address this.
