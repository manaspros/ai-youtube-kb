> Samuel Colvin (Pydantic) live-demos optimizing a structured-output extraction prompt with GEPA against a golden dataset, then serving managed prompt variables from Logfire without redeploying. Main takeaway: deterministic golden-set evals plus automated prompt search help most for cheaper models and private data.

## Summary
Samuel Colvin walks through a workshop-style demo of agent prompt optimization using the GEPA library (auto-captioned as "JEPA") on a political-dynasty extraction task built with Pydantic AI. He starts with a golden dataset of MPs and their political relations, a deterministic custom evaluator, and a comparison of a simple prompt (85-87% accuracy) against a hand-written expert prompt (92%). GEPA then proposes and keeps candidate prompts from a Pareto frontier and reaches about 96.7%, though the final prompt becomes verbose and has overfit edge cases such as excluding uncles and aunts. He then shows Logfire managed variables, typed Pydantic config pushed from code and pulled at runtime with percentage targeting, so prompts can change in a running service without redeploying. He closes with caveats: optimization pays off most for cheaper models and large private data, evals are hard when no golden answer exists, and a model change means re-optimizing. Much of the talk promotes Logfire, which tempers the takeaways somewhat.

## Key ideas
- **GEPA is a genetic-style optimizer over a string or structured object. It keeps the best candidates on a Pareto frontier, mixes them, and proposes new ones, so it is closer to breeding the best candidates than to random search.** — The optimized target can be a prompt or a JSON/dict of keyed components. Multiple keys (model, tools, individual prompt lines) can be recombined from the best values seen so far. ([2:33](https://youtu.be/A48uhxfxbsM?t=153))
- **Prefer a deterministic custom evaluator against a golden dataset over LLM-as-judge.** — Speaker calls LLM-as-judge risky ('lunatics running the asylum'). His extractor scores each case against golden answers and reports accuracy, with partial credit for near matches (e.g. 0.9 when the description differs slightly). ([18:39](https://youtu.be/A48uhxfxbsM?t=1119))
- **Baseline numbers: a simple one-line prompt scored about 85-87%, a hand-written detailed prompt about 92%, and GEPA-optimized prompt 96.7%.** — The gain from the human expert prompt was about 5 points before any automated search. The GEPA prompt is noticeably more verbose and more specific about what counts as a relation. ([26:40](https://youtu.be/A48uhxfxbsM?t=1600))
- **Optimization value depends on data privacy and model tier. It matters most for cheaper or faster models and for large private domain data that frontier models were not trained on.** — For frontier models, which often answer correctly from public knowledge, the gain is smaller. The speaker notes that this demo uses public data, which is a weak proxy for private data. ([41:35](https://youtu.be/A48uhxfxbsM?t=2495))
- **Overfitting and the verbose-prompt problem are the main failure modes of prompt search, and the fixes are data and structure.** — Optimizer rewrites produce long prompts. Splitting the prompt into keyed sentences and letting the optimizer pick a subset keeps prompts short. Overfitting needs roughly 2x the data covering the full input space, with separate train and eval sets, plus a final check harness. The optimized prompt excluded uncles and aunts, which the golden set counts as relations, because the training subset probably did not cover them. ([44:15](https://youtu.be/A48uhxfxbsM?t=2655))
- **Managed variables let a running service pick up a typed config change without redeploying.** — A Pydantic model (instructions, model, max tokens, temperature) is pushed from code with a CLI, then edited in the platform. The service reads the variable at call time, and targeting sets what share of calls get which value (A/B style, using the OpenFeature standard). The demo swapped the language of the reply and the model live. ([1:00:31](https://youtu.be/A48uhxfxbsM?t=3631))
- **Implicit user behavior is the best free eval signal for a chat agent.** — If a user retries, rephrases, or says the answer was wrong, that is evidence the response failed. If they move on, the response is probably acceptable. The speaker compares this to Google's old dwell-time signal. Thumbs up/down clicks are rarely used. ([1:11:52](https://youtu.be/A48uhxfxbsM?t=4312))
- **Privacy-preserving evals: record only categorical grades, not raw inputs and outputs.** — Legal-tech customers keep client data inside their boundary and send only categorical performance scores (good/bad or about 50 grades) to the observability platform. Self-hosting in a VPC is the other option. ([1:16:02](https://youtu.be/A48uhxfxbsM?t=4562))

## Techniques
- **Golden-dataset structured-output eval with a custom deterministic evaluator** — Create one case per entity from a golden answer file. Run the agent with the candidate prompt via Pydantic AI's agent override. Score each case with code (exact or partial match on the extracted list). Run cases in parallel with a concurrency cap (5 here), then compare experiments. *When:* Any extraction or classification task where ground-truth answers exist or can be created, before you tune prompts or models.
- **Compare-two-runs error analysis** — Run the baseline and the candidate prompt as separate experiments on the same cases, then look at per-case diffs (false positives like a sports commentator's father counted as a political relation). Turn the recurring mistakes into prompt rules. *When:* When the aggregate accuracy moves but you do not yet know why, or to find the edge cases to write into the prompt.
- **GEPA prompt search with an expert-prompt-engineer proposer** — Use a GEPA adapter whose proposer is a cheap agent. Feed it failed cases and traces, have it propose a new system prompt, evaluate it on the training set, and keep candidates on the Pareto frontier. Use GPT-4.1 as the proposer for speed. The speaker also wrapped the sync library's HTTP client per call to avoid async errors. *When:* When a task has a golden set and a cheaper model needs to match a bigger one, or you need better quality within a fixed cost.
- **Keyed-component optimization instead of free-form prompt rewrites** — Split the instructions into a dict of keyed lines or sentences, or put model and tool choices in the same dict. The optimizer selects a subset of values, so the prompt stays short. *When:* When optimizer output keeps growing in length and latency rises, which the speaker saw with GPT-5 mini.
- **Typed managed variables for live prompt and config changes** — Define the config as a Pydantic model with a code default. Push it with a CLI, then read it at call time. Use percentage targeting to roll out a new value to a share of traffic. Use a separate API key with variable permissions for production. *When:* When prompt or model changes must go out quickly in production or staging without a long CI and deploy cycle.
- **Trace the optimizer itself** — Instrument the library's print output so the optimizer's proposals, evaluations and scores appear as spans. The speaker turned off console logging because the output was too noisy to read. *When:* When an optimization run is long and opaque, and you need to inspect why it chose a candidate.
- **Train/eval split with extra coverage** — Use roughly twice the data needed to cover the input space, split it into a training set for the optimizer and a held-out evaluation set, and add a final check for known systematic errors. *When:* Before trusting an optimized prompt's score, especially when it is high (96%) but wrong on known categories.

## Hot takes
- Observability for AI is a feature that will be absorbed by general observability or by AI platforms; he does not believe in a separate category.
- LLM-as-judge is risky; a deterministic golden-set evaluator is much better when you can write one.
- GEPA-style optimization is 'not actually that groundbreaking' compared with the complexity of the models.
- Most coding-agent teams work mostly on vibes, and most people never run evals.
- Fine-tuning is usually not worth it versus improving the harness and waiting for the next model, except where volume is enormous, as in finance.
