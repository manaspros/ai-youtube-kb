> Matt Pocock on clearing the PR backlog that AI agents create: layer cheap deterministic checks, have an agent review and commit fixes, design deep modules so tests stop being brittle, and run a retro on each session.

## Summary
Matt Pocock argues that agents make software factories push out more PRs than humans can review, so teams need "brakes" before human review. He treats three layers as a stack: deterministic automated checks, automated agent review, and then human review, with the goal of making human review faster by fixing problems in the first two layers. He shows how checks can lie, using tautological tests, tests coupled to file structure, and mocks that make failure impossible. His fix is deep modules with small interfaces, so agents test at the interface. He recommends keeping coding standards out of the implementer's context and giving them to a separate review sub-agent that commits fixes rather than just commenting. For the PR body he proposes a one-way vs two-way door label, a blast-radius "merge danger" summary, and diagram-first explanations. A retro skill then reviews past sessions and suggests new checks, standards, navigation pointers and steering-file cleanup. He is promoting his own skills (version 1.3 shipping that week), so the talk is partly a product pitch.

## Key ideas
- **The PR bottleneck gets worse with agents. Agents start work automatically, so the human review queue grows fast and you end up with a 'slop cannon'.** — Speed without brakes means piles of PRs nobody reads. Brakes are mechanisms that raise code quality so human review can be lighter. ([0:01](https://youtu.be/LlgiOCmFG_w?t=1))
- **Review is three stacked layers: deterministic checks, automated agent review, then human review. The first two exist to make the third faster.** — Raising quality upstream means fewer human interventions. He calls this 'stop the slop' and says it is the first principle. ([2:40](https://youtu.be/LlgiOCmFG_w?t=160))
- **Automated checks can lie. Green CI does not mean the code is ready to merge.** — Failure modes he shows: tautological tests that restate the implementation (e.g. expecting a constant to equal its own value), tests that read source text and check ordering, and mocks that stub out a API so the test can never hit the real error modes. ([4:10](https://youtu.be/LlgiOCmFG_w?t=250))
- **Design for testability with deep modules: a large hidden implementation behind a small interface. Test at that interface.** — Deep modules give fewer structure-sensitive tests, because most internals are hidden. He calls the benefit 'leverage' for callers and 'locality' for changes staying in one place. He has a skill that finds deepening opportunities in any codebase. ([7:58](https://youtu.be/LlgiOCmFG_w?t=478))
- **Do not put coding standards in the implementer's context. Implementation is already overloaded (explore, edit, debug), so the standards get ignored or drown out the task.** — Put standards in a separate coding-standards file read only by a review sub-agent with its own context window. Implement first to make it work, then review to make it good. He compares this to red-green-refactor done in two separate contexts. ([12:21](https://youtu.be/LlgiOCmFG_w?t=741))
- **Build your own automated review instead of buying a third-party bot. A reviewer should commit fixes, not just leave comments.** — Generic reviewers give too many false positives or only suit one language. Team-specific standards are the leverage. If the reviewer commits, the human reviews a cleaner artifact instead of a list of comments to act on. ([14:58](https://youtu.be/LlgiOCmFG_w?t=898))
- **Make PRs easier for humans with a door-and-blast-radius label plus pseudocode or diagrams. Only one-way doors need deep review.** — Most PRs are two-way doors that can be reverted. Expensive migrations, data loss, or an accidental mass email are one-way doors. Each PR gets a 'merge danger' summary, and diagrams replace most prose. ([16:56](https://youtu.be/LlgiOCmFG_w?t=1016))
- **Review the process that produced the code, not just the code. A retro skill looks across sessions and PRs and suggests new checks, standards and steering-file changes.** — Goal: never write the same review comment twice. The retro also checks how easily the agent found information (navigation pointers), tool token economy, and bloat in steering files and skills. ([19:43](https://youtu.be/LlgiOCmFG_w?t=1183))

## Techniques
- **Layered brakes for agent PRs** — Order review as: cheap deterministic checks (lint, types, tests, quality metrics) first, then an agent reviewer, then a human. Add more deterministic checks since they cost CPU, not tokens. *When:* When agents open PRs faster than humans can review them, and you want to reduce human review load.
- **Deep-module design for agent-testable code** — Refactor toward modules with small interfaces that hide complex internals. Write tests against that interface and avoid reaching into internals or reading source files as text. *When:* When agent-written tests are tautological, brittle to renames, or cannot fail. Use this to make tests reflect behaviour.
- **Separate implementer and reviewer contexts** — The implementer agent only works on making the change pass checks. A reviewer sub-agent in its own context reads a coding-standards file (not AGENTS.md or global instructions), reviews the diff, and commits fixes. *When:* When agent code keeps missing team standards, or when the implementer's context is already full of exploring, editing and debugging.
- **Reviewer commits fixes, comments only on open questions** — Configure the automated reviewer so its default output is a commit. Use PR comments only for questions it cannot resolve itself. *When:* When automated review adds work for the human reviewer by producing long comment lists.
- **Door-type and blast-radius PR summary** — Label each PR as a one-way door (irreversible: migrations, data loss, external sends) or a two-way door (revertible). Add a short blast-radius statement and a 'merge danger' line at the bottom of the PR body. *When:* When you need reviewers to decide how deeply to read each PR.
- **Pseudocode and diagram PR explanations** — Describe the change with pseudocode, sequence diagrams, and small visual summaries (for example, a new CLI command with its new flags) instead of prose. He credits a 'show me' skill from the HumanLayer skills repo for this. *When:* When reviewers need to grasp the why of a change quickly.
- **Retro over sessions and PRs** — Feed a single agent session, a PR plus its session, or a week of PRs to a retro skill. It proposes automated checks, coding-standards updates, AGENTS.md navigation pointers, tool-economy fixes and steering-file pruning. *When:* After a batch of agent work, to stop repeating the same review comments and to cut token waste.

## Hot takes
- Do not outsource automated review to a third-party bot. Build your own and share coding standards across the team.
- Do not put coding standards in AGENTS.md or global scope. They drown out the implementer, so they belong in a file only the reviewer reads.
- Stop trying to one-shot good code. Split implement (make it work) from review (make it good).
- Automated reviewers should commit fixes by default, not post verbose comments for a human to act on.
- You do not need to review every two-way door, but every one-way door needs a careful review.
