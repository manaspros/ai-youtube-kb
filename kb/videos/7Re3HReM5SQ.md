> Better Stack walks through Cloudflare Dynamic Workers, V8-isolate workers created at runtime by a parent Worker, as a faster, lighter alternative to container sandboxes for running AI-generated code. The catch is JavaScript only, with no filesystem.

## Summary
The video introduces Cloudflare Dynamic Workers, a lower-level Worker primitive that an existing Worker can create programmatically on V8 isolates. The presenter contrasts them with Cloudflare Sandboxes, which are short-lived Linux containers on Durable Objects that can run any language and binary but are heavier. Dynamic Workers are described as much faster and lighter, but they run only JavaScript and have the same limits as a regular Worker. A Wrangler setup shows a parent Worker creating a child with network access blocked, then reusing it by name so state persists across requests. The presenter then adapts an E2B cookbook agent so Claude calls a Python execution tool inside a sandbox, with the resulting SVG saved to R2 because Dynamic Workers have no filesystem. The last section spawns 50 workers instantly and 10,000 on a deployed parent. The video closes with a caveat that the feature is free now but will not stay free.

## Key ideas
- **Dynamic Workers are Workers created at runtime by an existing Worker, running on V8 isolates. Cloudflare's claims are 100x faster and more memory-efficient than containers, and up to a million per second. The video does not measure either claim.** — Positioned as a cheap primitive for running AI-generated code, dev previews and custom automations, since spawning one is nearly free. ([0:01](https://youtu.be/7Re3HReM5SQ?t=1))
- **Decision rule: use Cloudflare Sandboxes when you need a full OS (filesystem, any language, any binary); use Dynamic Workers when you need speed and scale and can accept JavaScript only with regular Worker limits.** — Sandboxes are short-lived Linux containers on a Durable Object. Dynamic Workers have the same limits as a regular Worker, so the language restriction is the main trade-off. ([0:01](https://youtu.be/7Re3HReM5SQ?t=1))
- **Each child Worker gets its own config (compatibility date sets the runtime version) and a fetch(request, env, ctx) handler, and network access can be turned off. The parent forwards its request to the child and returns the result.** — The presenter describes the child config as a nested Wrangler config. Blocking network access is shown in the code as a deliberate step. ([1:19](https://youtu.be/7Re3HReM5SQ?t=79))
- **Loading a new child on every request gives a fresh sandbox each time. Getting an existing child by a stable name reuses the same instance, so state persists across calls.** — The demo first hits a fresh worker on each curl, then switches to get-by-name (worker1) and sees the same instance on repeat requests. ([1:19](https://youtu.be/7Re3HReM5SQ?t=79))
- **Child workers have no filesystem, though a shell library can create a virtual one. Persistence goes through bindings the parent passes in, such as an R2 bucket for images or SVGs.** — The parent worker reads the child's output, extracts SVG, and writes it to R2, which is then served by URL. ([3:56](https://youtu.be/7Re3HReM5SQ?t=236))
- **Agent-generated code runs as a tool-use loop. The parent calls Claude with a system prompt and a custom Python execution tool, forwards tool calls to the sandbox, and returns the output to the model.** — The E2B cookbook version used Sonnet 3.5 and a Jupyter notebook for PNG output. The Dynamic Worker port uses Sonnet 4.6 and generates SVG instead, and the video shows the response takes a while to produce. ([2:40](https://youtu.be/7Re3HReM5SQ?t=160))
- **Spawning at scale is a loop over IDs from an API, creating or reusing a named worker per index. 50 spawned instantly locally. 10,000 were spawned on a deployed parent with no timing shown. Cost is the caveat: free now, not forever.** — Cloudflare already uses Dynamic Workers for Code Mode and Zyte uses them to run LLM-generated apps, per the presenter. ([5:21](https://youtu.be/7Re3HReM5SQ?t=321))

## Techniques
- **Per-request sandboxed child Worker with network disabled** — In the Wrangler config, add a worker_loaders array with a binding named loader (the name is arbitrary, loader is the convention). In the parent fetch handler, create a child worker with a compatibility date and module code exporting fetch(request, env, ctx), with network access blocked. Call the child's fetch with the parent's request and return its response. Test with wrangler dev and curl localhost. Run the parent's TypeScript types through wrangler types to clear errors. *When:* Running untrusted or model-generated JavaScript per request, where cold-start and memory cost of containers is the bottleneck and the code does not need a filesystem or native binaries.
- **Stable-name reuse for warm sandboxes** — Replace the load call with the loader's get call using a stable name (the video uses worker1). Run the child's code as an async function. Repeated requests then hit the same instance and keep its in-memory state. *When:* Sessions where state must persist across calls, such as a per-user or per-conversation sandbox, or a chat room.
- **Custom bindings and RPC into the child** — Pass a binding such as a Durable Object stub into the child's env and expose a method (the video shows a chat room POST method). The child talks to it over Cap'n Web RPC. The video does not show the full code. *When:* The child needs controlled access to shared state or services without network access.
- **Bundling npm dependencies into a child** — Pass npm packages such as Hono to the worker-creation function so they are bundled into the child's module set. The video does not show the exact call. *When:* The generated or untrusted code needs a library, but the sandbox has no install step.
- **Egress interception for credential injection** — Intercept the child's outbound requests in the parent and add credentials to them, so the child code never sees the secret. The video states this as possible and does not show code. *When:* The sandboxed code must call authenticated APIs without holding the keys.
- **Agent code-execution loop with artifact persistence** — Parent calls the Anthropic SDK with a system prompt and a custom Python execution tool. When the model calls the tool, forward the code to the sandbox and return its output as the tool result. Scan the output for SVG, write it to an R2 bucket through a binding, and return a URL. The demo uses Sonnet 4.6, and the E2B cookbook it adapts uses Sonnet 3.5. *When:* Letting an LLM run analysis code and return artifacts, with the artifacts stored outside the sandbox since the sandbox has no persistent filesystem.
- **Scripted bulk spawn with create-or-reuse** — Loop over an index or IDs from an API. For each one, reuse the named worker if it exists, otherwise create it. Log the ID and respond with it. Measure on the deployed parent, not locally, to avoid overloading the dev machine. *When:* Load-testing sandbox creation, or running one isolated sandbox per user or task at high fan-out.

## Hot takes
- The 100x speed-up and 1M-per-second figures are Cloudflare's announcement claims, and the video does not benchmark either.
- The real limits are JavaScript-only and no filesystem, not raw speed. The presenter calls this out, and it decides whether Dynamic Workers fit a given sandbox workload.
- The presenter says Dynamic Workers are free now and will not be free forever, so the 10,000-worker test should not be read as a cost signal.
- The SVG demo output is trusted without verification (the presenter says he trusts Claude Sonnet's information), so the video shows the pattern but not output correctness.
- Title overstates the content: the substance is a setup walkthrough and one agent demo, with no load or latency measurements.
