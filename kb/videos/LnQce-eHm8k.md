> Oracle's Jeff Smith on locking down agent access to databases: expose curated reports as MCP tools instead of raw NL-to-SQL, give agents a compact schema tool, and enforce identity-based row and column security inside the database.

## Summary
Jeff Smith from Oracle argues that natural-language-to-SQL is risky because LLMs often write queries that return plausible but wrong data, and that agents are expensive when they brute-force a schema. His proposed alternative is to publish a library of existing business reports (parameterized, with descriptions and sample questions) and expose them through a small set of MCP tools such as list-reports and execute-reports, so the LLM chooses a report but never writes the SQL. The MCP server can be configured to allow ad hoc SQL, custom tools and reports only, or a mix, and an authorized user can let the agent read the SQL behind a report to learn the data model. For ops work, he suggests running performance investigations on a read-only standby replica and grouping tools by category (about three or four tools with multiple actions each) instead of creating one tool per task. He also describes a schema-info tool that returns a compressed JSON data dictionary with verbosity modes and keyword filters, plus an annotation tool that pulls documentation from SharePoint into database metadata. Security is the closing theme: agents authenticate through SSO and get roles or scopes, and the database itself strips rows and columns the user may not see. The talk is a vendor pitch for Oracle AI Database and its MCP server, with no benchmarks, but the architectural ideas are concrete and transferable.

## Key ideas
- **Natural-language-to-SQL is dangerous because queries can return plausible-looking data that answers a different question than the one asked. Business users cannot always catch wrong joins.** — The speaker points to the 'if it compiles, ship it' problem: a query that runs and returns rows is not proof that it answered the question. He would not let a general LLM make investment decisions from a single prompt result. ([6:42](https://youtu.be/LnQce-eHm8k?t=402))
- **Expose existing curated reports as callable tools so the LLM picks a report instead of writing SQL. The SQL stays hard-coded, so the model can only choose the wrong report, not generate wrong SQL.** — Each report gets a description, sample questions, what it means, and its parameters. Reports come from SharePoint folders, network drives and BI tools the business already uses. ([9:07](https://youtu.be/LnQce-eHm8k?t=547))
- **Do not create one MCP tool per report, which would blow out the context window. Use a pair of tools, list-reports and execute-reports, where list-reports does a keyword search over the catalogue.** — The speaker's example is 500 reports exposed as two tools, not 500 tools. The catalogue is searched on demand. ([9:07](https://youtu.be/LnQce-eHm8k?t=547))
- **A scoped role can let the agent read the SQL behind a report, which teaches it how the business data model works and improves one-shot query generation later.** — This is gated by OAuth 2 scope or role. The agent receives the report logic as markdown explanation alongside the results. ([10:34](https://youtu.be/LnQce-eHm8k?t=634))
- **Put security in the database, not only in tools. Tool-level checks are bypassed when someone points another client straight at the database.** — The speaker's stated default is that security belongs at the database layer, since tools can be swapped and bypassed. ([13:08](https://youtu.be/LnQce-eHm8k?t=788))
- **Group related actions into a few tools with an action parameter, such as one performance-tuning tool with about six actions, instead of many single-purpose tools. The speaker names AWR report generation and statistics collection as examples.** — This keeps the agent's tool list short while still giving it the operations it needs. ([13:58](https://youtu.be/LnQce-eHm8k?t=838))
- **Give agents a compact schema-information tool instead of letting them discover the schema by running queries. It returns a deterministic compressed JSON dictionary with verbose, slim and medium modes and keyword filters.** — A companion Retrieve Context tool fetches details, and a Generate Annotations tool pulls text from SharePoint PDFs, slides and Word docs into database metadata. The speaker says this helps humans and agents, and that un-annotated schemas like cryptic table names force expensive exploration. ([16:24](https://youtu.be/LnQce-eHm8k?t=984))
- **Authenticate the agent as the human user through SSO, not as a shared database account. Scopes and roles from the identity provider are passed to the database, which then strips the rows and columns that user may not see from the result set before it returns.** — The speaker calls this deep data security. His example is an HR manager who can see everyone's salary while a colleague in another org cannot. ([19:15](https://youtu.be/LnQce-eHm8k?t=1155))
- **Investigate production performance problems on a read-only standby replica, not on production itself. Oracle Data Guard offers this, and the speaker says a performance issue will often reproduce there.** — He does not want an LLM to create or drop indexes in production. He wants advice first, then he acts on it himself. Read-only access is still not enough, so the data itself must be restricted. ([12:05](https://youtu.be/LnQce-eHm8k?t=725))

## Techniques
- **Curated report catalogue exposed through two MCP tools** — Write each report with a description, sample questions, what it means, and typed parameters. Expose them through list-reports (keyword search over the catalogue) and execute-reports (run one by ID with parameters). The SQL under each report is hard-coded. For ad hoc questions, the agent first lists reports, then runs the closest match. *When:* Use it when the business already has trusted reports and the risk of wrong SQL is greater than the cost of building a catalogue. It also works when the catalogue is too large to expose as one tool per report.
- **Three server modes: ad hoc SQL, custom tools and reports only, or both** — The MCP server can accept arbitrary SQL and stored-procedure execution. It can also be restricted to custom tools and reports. The speaker describes the restricted setting as a way to limit the agent to safe paths. *When:* Use the restricted mode for production or business users. Use the ad hoc mode for internal analysts who understand SQL.
- **Reveal report SQL to agents under a privileged scope** — When the OAuth 2 session has the required scope or role, the tool also returns the SQL or logic behind a report as markdown. The agent can then reuse the join and filter patterns when it writes its own queries. *When:* Use it when an agent will need to write novel queries against a schema and you can grant a scope that exposes the report logic. Do not expose it to users who should not see the business logic.
- **Action-grouped tools instead of single-purpose tools** — Create a few tools per domain, such as a performance tool, a schema tool and an ops tool. Each takes an action parameter with about six options (e.g. generate an AWR report, collect optimizer statistics, produce a profile). The tool list stays at three or four entries. *When:* Use it when one domain has many related operations and each one-tool-per-operation design would bloat the agent's context.
- **Compressed deterministic schema-info tool** — Return the schema as a compact JSON dictionary of tables, columns and comments on each call, with the same output every time. Offer verbose, slim and medium modes plus a keyword filter. Pair it with a retrieve-context tool for detail, and with vector search where needed. *When:* Use it so agents do not run exploratory queries such as listing tables or sampling five rows from each table to understand a new environment. The speaker's point is that this saves tokens and time, and that it benefits human users too.
- **Generate schema annotations from enterprise documents** — Point an annotation tool at a SharePoint site or file share. It scans PDFs, slides, spreadsheets and Word files, extracts their text, organises it, and writes it back to the database as plain-English metadata on tables and columns. *When:* Use it when the schema has cryptic names or undocumented units and the knowledge lives in Confluence or document stores. The speaker's example is a workout database whose time and unit conventions were annotated.
- **Identity-driven row and column filtering at the database** — Connect agents through SSO (the speaker names Azure Entra ID). Map the identity's scopes and roles into the database. Define policies so that query results are filtered per user before they are returned to the agent. Do not use a shared database login for agents. *When:* Use it when the same database serves users with different visibility, such as HR salaries or regional data. Enforce it at the database so that other tools pointed at the same database cannot bypass it.
- **Diagnose production performance on a read-only standby** — Replicate production to a read-only standby (Oracle Data Guard in the talk). Let the agent investigate query plans, statistics and tuning options there. A human reviews the advice and applies changes to production. *When:* Use it for database troubleshooting where agents should not write to production. Keep in mind that read access can still expose sensitive rows, so combine it with the access controls above.

## Hot takes
- The talk is a vendor pitch for Oracle AI Database and its MCP server, delivered from a booth-promotion frame (swag, socks, a plush giveaway, and a closing URL). Weigh the claims accordingly.
- The core position is that the model should choose from curated reports rather than write SQL. That trades flexibility for reliability, which is a reasonable choice for business reporting but limits open-ended analysis.
- No benchmarks or measured token savings are given. Claims about token reduction and trustworthiness are qualitative.
- The speaker states that he would not put an LLM or agent into production if he could avoid it, and that he wants advice from the LLM before acting himself.
- Several features are roadmap items (MCP apps GUI later this year, skills delivered via tools), so they should not be treated as shipped.
