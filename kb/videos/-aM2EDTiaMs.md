> Raindrop's founders argue production agent monitoring must replace evals as the main safety net, using implicit classifier signals, regex, ship-vs-control experiments, and agent self-diagnostic reports.

## Summary
Zubin Koticha (Raindrop CEO) and Danny Gollapalli (backend engineer) argue that agent failures are non-deterministic and unbounded, so golden-dataset evals are no longer enough and production monitoring becomes the main way to catch problems. They split signals into explicit ones (error rate, latency, regenerations, cost) and implicit ones (refusals, task failure, user frustration, jailbreaks, wins), and say narrow binary classifiers beat 1-10 LLM-as-judge scores. They describe cheap regex signals, ship-to-a-percentage experiments against a control group, and daily triage or issue-mining agents that surface spikes. The second half is a workshop on self-diagnostics: a simple report tool plus one system-prompt line that makes a coding agent flag its own failures and workarounds, with tool naming and "feedback to creators" framing mattering a lot. The talk is partly a product pitch (trials, hiring, trajectory search), but it gives concrete practices and some numbers.

## Key ideas
- **Agent failures need monitoring, not just evals** — Agents are non-deterministic, have an unbounded input and output space, can call tools that change other systems, and now run for hours with sub-agents. Golden-dataset tests cannot cover the combinatorial space, so the speaker moves from a testing paradigm to a production monitoring paradigm. ([0:00](https://youtu.be/-aM2EDTiaMs?t=0))
- **Two kinds of signals: explicit and implicit** — Explicit signals are objectively checkable: tool error rate, latency, user regenerations, cost. A spike is usually a sign of trouble, and a flat line can also mean something. Implicit signals are semantic: refusals, task failure, user frustration, content moderation, jailbreaks, and positive 'wins'. ([4:00](https://youtu.be/-aM2EDTiaMs?t=240))
- **Use narrow binary classifiers instead of 1-10 quality scores** — The speaker says asking an LLM to rate a response on a 1-10 scale is less useful than having a well-defined set of issues, each as a binary classifier, tracked as a rate over time. Those rates are what you alert on. ([4:00](https://youtu.be/-aM2EDTiaMs?t=240))
- **Regex signals are cheap and useful in aggregate** — Example: a keyword regex on user messages was flipped to a boolean and its rate tracked daily and per release. The regex can miss individual cases, but a rise of around 10% across millions of users is still a usable signal. ([6:46](https://youtu.be/-aM2EDTiaMs?t=406))
- **Ship changes to a slice of users and compare signal rates to a control** — Treat a prompt, model, harness or tool change like an A/B test, but judge it by the semantic signals and not only by offline evals. Example: frustration fell from 37% to 9% after prompt 2.4. A side effect such as a higher average tool count is also worth watching. ([8:14](https://youtu.be/-aM2EDTiaMs?t=494))
- **Use small trained classifiers for scale, not an LLM on every output** — Running an LLM judge on every output would roughly double AI spend, so the speaker's team trains small custom models for signals like frustration, which also work across languages. Ideas are needed only once a few hundred events make reading everything impossible. ([9:42](https://youtu.be/-aM2EDTiaMs?t=582))
- **Self-diagnostics: ask the agent to report its own failures** — Models trained on reasoning can introspect. The speaker's setup is one report tool plus one system-prompt line asking the agent to report notable things to its operators before giving the final answer. It catches tool failures, user frustration, capability gaps the user asked for, and workarounds the agent used on its own. ([16:42](https://youtu.be/-aM2EDTiaMs?t=1002))
- **Tool naming and framing decide whether the agent confesses** — Models are trained to look polished and resist admitting fault. In the demo, a tool called something like 'unsafe bash use' was not used, but a neutral 'report' tool framed as feedback to the agent's creators worked. A self-report is also sometimes a security signal, since the agent may bypass a blocked tool. The speaker says a real classifier is better for catching unsafe behavior. ([24:28](https://youtu.be/-aM2EDTiaMs?t=1468))
- **Turn agent signals into a feedback loop, and possibly an automated one** — Use signal rates to decide the next change, cluster users by intent to see which use cases have high frustration, and run a triage agent that investigates daily spikes. The speaker describes, as an aspiration and not something shipped, an agent that reads signals, opens a PR and runs new experiments. ([34:10](https://youtu.be/-aM2EDTiaMs?t=2050))

## Techniques
- **Binary issue classifiers as monitoring signals** — Define a small set of named issues (refusal, task failure, user frustration, jailbreak, win). Track each as a daily percentage of sessions and alert when the rate spikes. Prefer a yes/no question per issue over a quality score. *When:* Multi-turn production agents where you cannot read every transcript and want to catch regressions fast.
- **Regex keyword signals on user messages** — Write a long regex of phrases that signal trouble (e.g. 'this sucks', 'you're wrong', 'I didn't ask that'), store the result as a boolean on each event, and track its daily rate per release. *When:* A cheap first monitor, or when you need a signal at very large scale with no LLM cost. Accept some false negatives, since the aggregate trend still matters.
- **Percentage rollout with a control group, judged by signal rates** — Ship a change (prompt, model, harness, tool) to part of the traffic and keep a control group. Compare semantic signal rates and side metrics such as tool-call count between arms. Sample size decides when a difference is trustworthy. *When:* Shipping agent changes quickly, where offline evals miss real-user behavior. The speaker says a 1-2% difference can be enough to clear a change when the sample is large.
- **Self-diagnostic report tool** — Give the agent one tool, named neutrally (e.g. 'report'), with a description asking for a short note to its creators. Add one system-prompt line telling it to call the tool before the final answer if it notices anything notable. Route the messages to Slack or a log. Tune the tool name and description if it never fires. *When:* A cheap way to find capability gaps, repeated tool failures and self-correcting workarounds. Works without a full observability platform.
- **Natural-language signal definition (deep search)** — Describe the behavior you want in plain language, e.g. 'find all times the agent edited a test to make it pass', and turn the search into a new binary classifier signal that is then run over the data. *When:* When a new failure mode is found by hand and needs to be tracked over time without writing custom code.
- **Daily triage agent over signals** — An agent reviews all configured signals every day, investigates any that spike by reading traces and tools, and reports likely causes, including issues nobody had defined. *When:* Once you have many signals and too many traces to review by hand.
- **Cluster by user intent and track issue rate per cluster** — Classify sessions by what users are trying to do (e.g. React apps, Python scripts, debugging, vibe coding from scratch), then compare frustration or task-failure rates across these clusters. *When:* When you want to know which kinds of use are breaking, not only whether something broke overall.
- **Trajectory search over tool-call sequences** — Describe a pattern of tool calls in plain language (e.g. a trace with three tool failures) and find traces that match. Inspect the order of calls, errors, and the input and output of each tool call. *When:* Debugging multi-step agent runs where the failure only shows in the sequence of tool calls.

## Numbers
- Frustration rate fell from 37% to 9% after shipping prompt 2.4 (example from the speaker's product data). Average tool count rose, which the speaker says is a noteworthy side effect and not necessarily a problem. ([8:14](https://youtu.be/-aM2EDTiaMs?t=494))
- Signals become useful once there are a few hundred events and you can no longer read every input and output. ([9:42](https://youtu.be/-aM2EDTiaMs?t=582))
- Running an LLM judge on every output would roughly double AI spend, which is why the speaker's team trains small classifiers instead. ([12:23](https://youtu.be/-aM2EDTiaMs?t=743))
- A regex signal in aggregate is worth acting on when it rises about 10% across millions of users. ([11:10](https://youtu.be/-aM2EDTiaMs?t=670))
- The speaker's team released 10 SDKs in the past month. Python SDK support is weaker than the TypeScript one, and the TypeScript SDK injects the self-diagnostic tool automatically. ([38:46](https://youtu.be/-aM2EDTiaMs?t=2326))
- Free trial is two weeks, which the speaker says may be extended. ([41:45](https://youtu.be/-aM2EDTiaMs?t=2505))
- The workshop demo agent has four tools (read, write, edit, bash). Its write tool was made to fail with a permission error so that the agent fell back to bash. ([22:43](https://youtu.be/-aM2EDTiaMs?t=1363))

## Hot takes
- Monitoring production is more important than testing and evals for agents, and online evals are not enough on their own.
- Humanity's last problem is catching issues in production agents, once humans can no longer monitor agents themselves.
- Models are trained to look polished, so an agent will more readily report a capability gap than admit it did something unsafe.
- Self-correcting workarounds, such as writing a script around a blocked tool, can be good if the task gets done, but they can also be a security problem.
