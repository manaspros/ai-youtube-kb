> AWS's Sandhya Subramani demos an agent that writes its own tools and sub-agents at runtime using three built-in tools (editor, shell, load-from-directory) plus a system prompt, then argues that evals and sandboxing are required before trusting it.

## Summary
The speaker shows a Strands Agents setup (auto-captions say "TransAgent") where the agent starts with no tool files, then creates a math calculator and a character counter on the fly and uses them without a restart. The core recipe is a system prompt that defines a tool template, rules for where to write, and a check-before-write rule, plus three tools: editor, shell, and load-tools-from-directory. The same pattern is used to have the agent generate sub-agents for an itinerary task (flight, activities, itinerary), and the speaker says it can also repair its own agent after a max-token error. He lists swarm, graph and workflow as the agent patterns the generated sub-agents can use. The second half argues for trust: eight built-in evals across session goal, trace helpfulness and hallucination, tool choice and parameters, and inter-agent sequencing, plus four guardrails (sandboxed execution, constrained tools and permissions, constrained who can ask, observability). The talk is demo-driven with no benchmarks, and it is also a product pitch for Strands.

## Key ideas
- **An agent can gain capabilities it was never given by writing tool files into a directory and loading them at runtime, without restarting.** — The demo agent has a system prompt, three tools, and zero tool files. Asked for a math calculator, it writes one, loads it, and uses it in the same run. Asked to count characters, it writes a character counter before the speaker finishes talking. ([1:44](https://youtu.be/33Oct2hqGnk?t=104))
- **The whole capability is three generic tools plus one system prompt. The prompt is the spec.** — The three tools are an editor (write files), a shell (see what exists), and a load-tools-from-directory tool (load new tools dynamically). The system prompt carries the tool template, the rules, and the instruction to check whether a tool exists before writing a new one. The speaker says it takes one line of code to wire in. ([5:10](https://youtu.be/33Oct2hqGnk?t=310))
- **The same pattern extends from tools to whole sub-agents.** — With the same three tools and a sub-agent template, the agent writes flight, activities and itinerary sub-agents for a trip request, then calls them. He says sub-agents can be built as swarm (parallel), graph (handoff), or workflow (a mix). ([11:06](https://youtu.be/33Oct2hqGnk?t=666))
- **Runtime self-repair is shown as a live example, with a caveat about autonomy.** — When a run hit a max-token error, the agent recognized the failure, edited its own agent definition, and retried. The speaker says that raises the stakes: an agent that edits itself needs guardrails and evals. ([14:18](https://youtu.be/33Oct2hqGnk?t=858))
- **The speaker's answer to 'can it break things' is eight evals across four levels.** — Session level asks whether the end goal was reached. Trace level asks whether the answer was helpful and not made up. Tool level asks whether the right tool and parameters were used. Multi-agent level checks the order of tool and sub-agent calls and the messages between agents. ([15:31](https://youtu.be/33Oct2hqGnk?t=931))
- **Four guardrails are needed because a meta-agent that can create tools can also modify or delete things.** — They are: sandboxed execution of generated code (he cites a recent Strands sandbox feature, a sandbox around the code the agent runs rather than around the whole agent), constrained tools and permissions, constrained access on who can ask what, and observability (evals, OpenTelemetry, telemetry). ([16:29](https://youtu.be/33Oct2hqGnk?t=989))
- **He frames the trajectory as tools, then agents, then self-editing source code, and says the Python Strands codebase was used to write its TypeScript port.** — This is a single anecdote from the speaker, not a measured result. It is used to motivate the self-evolving agent idea. ([19:09](https://youtu.be/33Oct2hqGnk?t=1149))

## Techniques
- **Meta-tooling bootstrap (three tools + system prompt)** — Give the agent an editor tool, a shell tool to list existing tools, and a load-tools-from-directory tool. Put a tool template (a decorated function spec), storage location, and rules in the system prompt. The agent writes tool files and loads them in the same session. *When:* When you want an agent to fill capability gaps on the fly instead of failing or waiting for an engineering cycle, such as a request outside its built-in tools.
- **Check-before-write rule for generated tools** — The system prompt tells the agent to look for an existing tool first and create a new one only if none fits, which stops duplicate tools from piling up. *When:* Any time an agent is allowed to create tools or agents, so the tool directory does not fill with near-duplicates.
- **Self-repair on error** — When a run fails (the demo case is a max-token error), let the agent read its own agent file, fix it with the editor tool, and retry. *When:* For long-running or customer-facing agents where a crash should trigger a fix attempt rather than a human round-trip. Only with sandboxing and evals in place.
- **Sub-agent topology choice (swarm, graph, workflow)** — Ask the generating agent to split a task into sub-agents that either run in parallel (swarm), pass results along a handoff chain (graph), or combine both (workflow). *When:* When one task has independent parts that can run in parallel, or a fixed sequence where each step needs the last one's output.
- **Layered agent evals** — Score at four levels: whole-session goal, per-trace helpfulness and hallucination, tool selection and parameter correctness, and inter-agent call order and messages. Collect OpenTelemetry-style traces so each level can be checked. *When:* Before letting any agent create or change its own tools, since a single end-to-end pass rate hides which tool or sub-agent went wrong.
- **Four-part guardrail stack for self-modifying agents** — Sandbox generated code execution so it cannot touch the rest of the environment. Limit which tools and permissions are available. Limit who can ask the agent what. Keep full telemetry and evals on every run. *When:* Any time an agent can write code, delete files, or change its own definition.

## Hot takes
- Runtime tool creation is the next step past tool calling: an agent that fails on an unsupported request should build the missing capability instead of erroring out.
- The hard part of self-writing agents is not generation but control: sandboxing, permissions, and evals have to exist before the agent is allowed to edit itself.
- The Python-to-TypeScript port written by the Strands codebase is a sign that agents can edit their own source code, though this is a single anecdote from a vendor talk.
