> A first-principles tour of why agent code needs sandboxes, comparing fork/exec, containers, gVisor and microVMs, then how to add disk snapshots, restore and multi-node scheduling for OpenAI-scale agent sandboxes.

## Summary
The speaker, from OpenAI's RL and agent infrastructure team, argues that code execution is what made models good at verifiable tasks, so model-written code has to run somewhere untrusted. He walks through isolation options from raw fork/exec to containers (namespaces, cgroups, seccomp), gVisor's user-space kernel, and hardware-virtualized microVMs. His conclusion is that every option short of a VM can still reach the host kernel, so he recommends microVMs from the start, with device jailing and Rust-based VMMs. The second half covers persistence: disk snapshots are needed for reliability, long-horizon work, and checkpoint-and-backtrack search. He recommends incremental, block-level snapshots built on copy-on-write base images and changed-extent maps, plus an always-on block device backed by a tiered cache. The last part covers multi-node control planes, startup latency trade-offs (warm pools vs memory snapshots vs hybrid), and scheduling restores onto the node that already holds the most snapshot layers. The talk is conceptual and gives no benchmark numbers.

## Key ideas
- **Code execution is what made models strong at verifiable tasks, and that makes sandboxes necessary.** — Training loops let the model call code tools, and a grader checks the result, so model-written code runs in a harness on a laptop or cloud node. Those environments need protection from intentional or accidental attacks on the host. ([4:05](https://youtu.be/OqM67QG_Ikk?t=245))
- **Containers still share the host kernel, so they are not a real security boundary.** — Namespaces give resource isolation and cgroups cap CPU and memory, but a process inside can still reach the host kernel. Seccomp filters syscalls, but you often do not know the needed syscalls ahead of time, which makes the feedback loop painful. ([12:04](https://youtu.be/OqM67QG_Ikk?t=724))
- **gVisor moves syscall handling to user space but still sits on the host kernel.** — Its user-space kernel shrinks what an attacker can hit directly. Still, a two-step exploit chain from the Sentry or Gofer down to the host kernel stays possible, and models are getting better at finding such chains. ([16:29](https://youtu.be/OqM67QG_Ikk?t=989))
- **Hardware virtualization gives a guest kernel full control inside the guest but none on the host.** — The guest runs in a separate CPU context, so root or kernel exploits inside it do not directly reach the host. The cost is a performance penalty every time the CPU switches between guest and host. ([18:33](https://youtu.be/OqM67QG_Ikk?t=1113))
- **MicroVMs are small because the VMM is small, not because the guest is small, and Rust VMMs with per-device jailing improve on QEMU.** — Rust-based VMMs such as CrossVM, Firecracker and Cloud Hypervisor drop most QEMU devices. Each emulated device runs in its own jail, so compromising one device does not grant access to the others. ([23:15](https://youtu.be/OqM67QG_Ikk?t=1395))
- **Security tricks can hide performance problems but cannot hide security breaches.** — The speaker chooses the more secure option and then works on performance. His advice to startups is to start with microVMs. GPU access is a known weak spot: virtio-GPU is high-level, and VFIO gives direct access but only to one sandbox at a time. ([27:20](https://youtu.be/OqM67QG_Ikk?t=1640))
- **Persistence improves reliability and scale because sandbox state can be checkpointed and restored on another node.** — A long task with many installed packages and files can be checkpointed periodically. It can be restored after node or cluster failure, or moved on purpose during upgrades or A/B tests. Without this, GPU time is wasted and the user loses work. ([30:36](https://youtu.be/OqM67QG_Ikk?t=1836))
- **Snapshots enable checkpoint-and-backtrack search over many rollouts.** — A harness can checkpoint a sandbox, try one branch, backtrack to the checkpoint, and try another. That makes Monte Carlo-style exploration over long horizons possible, but only if snapshot and restore are fast and reliable. ([33:00](https://youtu.be/OqM67QG_Ikk?t=1980))
- **Use incremental block-level snapshots and make the snapshot call return before the upload finishes.** — A copy-on-write base image gets a writable layer. The extent map (FIEMAP) identifies changed blocks, which are compressed and uploaded. The snapshot returns quickly while the upload continues in the background, and restore applies the diffs in lineage order onto the base. ([39:06](https://youtu.be/OqM67QG_Ikk?t=2346))
- **Scheduling and startup latency trade off against each other: warm pools, memory snapshots, or a hybrid.** — Warm pools consume CPU and memory while idle. Memory snapshots can start a microVM in milliseconds on demand. A hybrid keeps a small warm pool and grows it from memory snapshots. The scheduler can also route a restore to the node that already holds the most snapshot layers. ([42:35](https://youtu.be/OqM67QG_Ikk?t=2555))

## Techniques
- **Isolation ladder for untrusted tool execution** — Rank options by how much host-kernel surface they expose: raw fork/exec, then containers with namespaces, cgroups and seccomp, then gVisor's user-space kernel, then hardware-virtualized microVMs. Pick the strongest boundary your latency and GPU needs allow. *When:* Designing or auditing any system that runs model-written code on shared hosts, such as a code-execution tool or a per-user sandbox.
- **Driving a microVM through its VMM API** — The harness starts a VMM binary such as Cloud Hypervisor, which exposes an API over a Unix domain socket. Call create with the rootfs, kernel, CPU and memory, then call start. Talk to an in-guest agent over vsock or the node IP stack. *When:* Building per-task sandboxes that need VM-level isolation but must be started and controlled programmatically.
- **Per-device jailing for emulated devices** — Run each emulated device (block, net) in its own process with its own seccomp or permission set, so a compromised device can only reach its own resource. *When:* Choosing or hardening a VMM where devices are an attack surface.
- **Incremental block-level disk snapshot** — Keep a read-only base image plus a copy-on-write writable layer. On snapshot, use FIEMAP to list changed extents, compress and upload only those, and record each snapshot's parent to form a lineage. On restore, fetch the lineage and apply the diffs onto the base. *When:* Persisting agent workspaces between turns or across node failures without re-uploading gigabytes each time.
- **Acknowledge snapshot before upload completes** — Return a snapshot ID once the changed extents are captured locally, and finish the upload in the background. Restore must wait for pending uploads in the lineage. *When:* The snapshot call sits on the request path and upload latency would hurt the product experience.
- **Tiered always-on block storage** — Expose a block device inside the sandbox over NBD. Back it with a node-local cache that writes back to object storage such as GCS or S3. The speaker prefers block devices to NFS because POSIX-compliant block storage behaves more predictably for models. *When:* Giving sandboxes persistent disk without manual save calls, and needing better file-system behaviour than a shared folder mount.
- **Snapshot-aware scheduling** — When picking a node for a restore, score nodes by how many of the snapshot's layers they already hold, and route to the node that needs the least download. *When:* Running a fleet where restore latency depends on cache locality of snapshot layers.
- **Startup latency hybrid** — Combine a small warm pool for the common case with memory snapshots that start a microVM just in time on a miss, and grow the pool from those snapshots. *When:* Balancing creation latency against idle CPU and memory cost.

## Hot takes
- Start with microVMs from the beginning for any untrusted-code sandbox; containers and gVisor are not enough.
- Security tricks can make up for performance problems, but performance tricks cannot make up for a security breach.
- Storage, specifically snapshot and restore of disks, is the next unlock for agent harnesses, more than compute.
