> Red Hat's Sally Ann O'Malley runs OpenClaw agents in Podman containers, keeps API keys as secret refs, and lifts the same setup to Kubernetes; the talk is a live demo with a pitch for containers as the default agent sandbox.

## Summary
The speaker, a Red Hat engineer, argues that AI agents (here OpenClaw, an MIT-licensed agent project) should run in containers by default, because containers give reproducible environments, portability across laptop and Kubernetes, and an explicit boundary on what the host exposes. She keeps her API keys in Podman secrets, mounts them into the container, and points OpenClaw's secret-ref feature at them so keys never sit in plain config or logs. Her team-level vision is a company baseline image (approved MCP servers, auth, team skills) that individuals then personalize. She demoed a small installer that starts a Podman pod, turns exported env vars into OpenClaw secret refs, sets OpenRouter as the primary model with Anthropic as fallback, and optionally wires OpenTelemetry to Jaeger; she also showed an SSH sandbox option. The live demo ran out of time, so model switching and the Kubernetes side were only partly shown. The Mac limitation (containers there run inside a VM, which makes spawning containers from containers hard) is a useful caveat. Speaker-reported anecdotes include an NVIDIA team running about 10 engineers' OpenClaws in Kubernetes for model evals; the Docker path of the installer was not tested by her.

## Key ideas
- **Run agents in containers by default: reproducible, portable across laptop, x86, Mac and Kubernetes, and the container gives a natural sandbox where host access has to be stated explicitly.** — She says the container boundary is the sandbox and that every host resource (mounts, secrets, network) must be granted on purpose. She treats this as the same argument Red Hat already makes for securing any application. ([3:53](https://youtu.be/F1DYkY1BlfM?t=233))
- **Keep API keys out of the agent's config: store them as Podman secrets, mount them into the container, and have OpenClaw refer to them through its secret-ref feature.** — Each credential becomes a pointer to an outside secret. She admits this is not perfect but says it keeps keys out of logs and visible config. The same pattern carries over to Kubernetes secrets. ([6:18](https://youtu.be/F1DYkY1BlfM?t=378))
- **Develop locally in a container, then lift the same workload to Kubernetes or OpenShift, so the security and scaling story is the same at both ends.** — She cites an NVIDIA contact whose team runs about 10 engineers' OpenClaw instances in Kubernetes, checking in with model evals. This is speaker-reported, not her own measurement. ([8:46](https://youtu.be/F1DYkY1BlfM?t=526))
- **Store all runtime state in a named volume (PVC in Kubernetes) so backup and recovery are simple; she backs hers up nightly with a systemd service.** — Her agent directory (skills, tools, MCP server configs) is also mounted into the container, so the whole setup is up at startup. ([11:11](https://youtu.be/F1DYkY1BlfM?t=671))
- **Team baseline: one curated agent image per company (approved MCP servers, company auth, team skills, access to shared tools), fanned out to new hires and then personalized per person.** — She contrasts this with new hires copying a colleague's repo and assembling the setup by hand. She frames it as team standards, portable environments and reproducible onboarding. ([12:08](https://youtu.be/F1DYkY1BlfM?t=728))
- **Mac caveat: on macOS every container runs inside a VM, so spawning a container from inside a container does not work the way it does on Linux.** — She has not solved this for her Mac setup and says nested containers work on Linux. Her installer runs with npm run dev locally on the Mac when she does not use a container. ([13:32](https://youtu.be/F1DYkY1BlfM?t=812))
- **A one-command installer turns exported env vars into OpenClaw secret refs and sets providers: OpenRouter primary, Anthropic fallback, an optional local endpoint, and an optional OpenTelemetry collector with Jaeger.** — She chose not to test the telemetry option live to save time. She says the installer was written for Podman but intended to work with Docker, and a Docker user has not yet confirmed it. ([16:11](https://youtu.be/F1DYkY1BlfM?t=971))

## Techniques
- **Podman secrets + secret-ref indirection for agent API keys** — Create each API key as a Podman secret, mount it into the container, and configure the agent's provider credentials as secret refs that resolve at runtime, so the raw key never appears in the agent config or logs. *When:* Any containerized agent that calls paid model APIs or other services and needs credentials without putting them in files or env listings.
- **Container as the agent sandbox with explicit host grants** — Run the agent in a container and grant access only through explicit mounts, volumes, secrets and SSH keys, instead of running it natively on the host. *When:* Running agents on a work laptop or shared machine where the agent should not reach the rest of the host.
- **Mount the agent's tool directory at startup** — Keep skills, tools and MCP server configs in one host directory and mount it into the container, so the agent comes up with its full toolset every time. *When:* Reproducible agent setups that need the same skills and MCP servers across machines or restarts.
- **Named volume for runtime state with scheduled backup** — Keep all agent runtime state in one container volume (PVC in Kubernetes) and back it up on a schedule, here a nightly systemd service. *When:* Long-lived agents whose memory, sessions and configuration must survive container restarts or moves.
- **Local-to-Kubernetes lift with the same image** — Build and test the agent container locally, then deploy the same image to Kubernetes or OpenShift with the same secret and volume setup. *When:* Moving an agent from a developer machine to a shared cluster for multiple users.
- **Company baseline image with per-user layer** — Publish one approved agent image with company MCP servers, auth and team skills, then let each person add personal config on top. *When:* Rolling out agents to a team with shared standards and fast onboarding.
- **SSH sandbox for remote execution** — Give the agent SSH keys and known_hosts for a target machine so all its commands run in that remote workspace. *When:* The agent should act on a separate machine rather than the container's own filesystem.
- **Installer that converts env vars to secret refs and sets providers** — A script reads exported API-key env vars, creates OpenClaw secret refs for each, starts a Podman pod with a port and mapped secrets, and sets model providers with a fallback. *When:* Standardizing agent startup across a team so credentials are never typed into config files.

## Hot takes
- Run every agent in containers by default; it is the natural sandbox and the reason to containerize is the same as for any application.
- Podman secrets plus secret refs are better than plain environment variables for API keys, even if the setup is not perfect.
- Agents will run everywhere and talk to each other; the need for security and scale at that point is what Kubernetes is for.
- AI is not replacing engineers; it frees them for more creative work (speaker's view, after saying she has not written code in months).
