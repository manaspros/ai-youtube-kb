> Kai Explains on why local AI on a Mac feels slow: prompt prefill and prefix-cache misses, not memory bandwidth, dominate agent turns, and a settings checklist finds the cache-breaking causes.

## Summary
The video argues that a slow local coding agent on a Mac is usually a prompt-reading problem, not a chip problem. Tokens-per-second counters in LM Studio or Ollama measure decode (writing), but agent sessions are dominated by prefill (reading the system prompt, tool definitions and history), and a prefix cache is what keeps that cheap. The speaker's central comparison is one M5 Pro session where a cache hit gave a 6.1 s first word and a cache miss on about 41k tokens gave 268 s. He then lists silent cache-breakers: a changing token at the top of Claude Code's system prompt (per the speaker, fixed in a June release but still seen in September), Ollama's context-window tiers chosen from the GPU memory macOS exposes, and hybrid-attention Qwen models that can only restart from checkpoints spaced thousands of tokens apart. He adds that frontends differ (OpenClaw showed zero cache tokens where Hermes cached on the same server), that stripping thinking tokens from history breaks the cache, and that the chip still matters for unavoidable cold reads. It closes with a five-step checklist: update Claude Code, check Ollama's context column, raise server log verbosity to find "full prompt reprocessing", test frontends for cache-token counts, and lower Qwen effort to medium. Most evidence is anecdotal and secondhand, so the specific figures are best treated as illustrative.

## Key ideas
- **A reported 8-hour local agent session for about 15 edits on an M5 Max with 128 GB shows the problem is not raw hardware.** — The developer said answers were excellent, but the logs repeated 'forcing full prompt reprocessing due to lack of cache data' on every turn. ([0:00](https://youtu.be/x_qmqqp6d7s?t=0))
- **Memory bandwidth and matrix units are real gains but only explain the decode phase.** — Decode must stream all weights per token: a ~17 GB 4-bit model at 170 GB/s gives ~10 tok/s, and M5 Max at 614 GB/s is ~3.5x faster. M5 put matrix units in every GPU core; llama.cpp benchmarks show prefill about 3.6x faster from M4 Max to M5 Max. ([1:26](https://youtu.be/x_qmqqp6d7s?t=86))
- **A local server does two jobs: prefill (reading the whole prompt and history) and decode (writing). The tokens-per-second counter only shows decode.** — Agent workflows are dominated by prefill, while most public benchmarks measure decode, so buying decisions based on those numbers can mislead. ([2:34](https://youtu.be/x_qmqqp6d7s?t=154))
- **Prefill can be the entire wait. One M1 Max measurement showed a 57 tok/s counter but about 3 tok/s from enter to first word.** — With 8,500 tokens of context loaded, 94% of the wait was prefill, making real speed about 19x slower than the counter. ([3:51](https://youtu.be/x_qmqqp6d7s?t=231))
- **Prefix caching is the decisive variable. Same Mac, model and session, but a cache miss made the first word 44x slower.** — A 158k-token context with 157,600 cached returned the first word in 6.1 s. At 188k tokens with only 147k matching the cache, about 41k tokens were reread from scratch and the first word took 268 s. The speaker says no Apple chip closes that gap. ([5:18](https://youtu.be/x_qmqqp6d7s?t=318))
- **Software choices silently break the cache, and the Claude Code case was a changing token near the top of the system prompt.** — Anthropic's servers stripped the block before caching, but a local server did not, so every turn was a full miss. The speaker says a fix shipped in June (v2.1), yet users still reported 30-minute runs in September, so other breakers remain. ([6:37](https://youtu.be/x_qmqqp6d7s?t=397))
- **Ollama picks the default context window from the GPU memory it can see, and on macOS that is roughly three quarters of unified memory.** — The tiers are under 24 GB gives 4,000 tokens, 24-48 GB gives 32,000, and over 48 GB gives 256,000. A 48 GB Mac lands in the 32k tier, while Claude Code's first request is about 33k tokens, mostly tool descriptions, so the window is full before any prompt. The result is repeated compaction, and each compaction is a cold read. ([8:02](https://youtu.be/x_qmqqp6d7s?t=482))
- **Hybrid-attention Qwen models cache only at sparse checkpoints, and frontends differ in whether they preserve cache at all.** — If a new prompt diverges from the cache with no nearby checkpoint, the server restarts from zero. That log line shows only at verbosity level 4 (default 3). In May, OpenClaw showed zero cache tokens while Hermes cached fine against the same server and model. ([10:15](https://youtu.be/x_qmqqp6d7s?t=615))
- **Stripping thinking tokens from history breaks the cache, and the chip still matters for cold reads.** — Qwen's 27B model preserves thinking by default, and the speaker says its docs say this helps caching. A cold read is unavoidable the first time, so the cache decides how many cold reads you pay and the chip decides what each one costs. ([11:20](https://youtu.be/x_qmqqp6d7s?t=680))

## Techniques
- **Split prefill from decode when measuring** — Time from pressing enter to the first streamed token, separate from the tokens/s counter in LM Studio or Ollama. Compare a fresh conversation with a long-context turn to see prefill dominate. *When:* Before buying hardware or comparing local setups, and when a local agent 'feels slow' even though the counter looks fine.
- **Audit cache-token counts per turn** — Check the server's reported cache-token count on each request. Zero cache tokens deep into a session is the red flag. Keep the prompt prefix stable across turns: no volatile values at the top of the system prompt, and do not rewrite or strip earlier history. *When:* When turns after the first are slow, or after changing frontend, system prompt or proxy.
- **Raise server log verbosity to find cache misses** — On llama.cpp or LM Studio, raise log verbosity or debug level (the speaker says level 4; default 3), run an agent session, then search the logs for 'full prompt reprocessing'. If it appears every turn, the cache is missing on every turn. *When:* When a session is slow and you need to confirm whether prompts are being reread in full.
- **Check Ollama's context window** — Run `ollama ps` and read the context column. On a 48 GB Mac a 32,000 reading is the problem. The speaker says Ollama's docs recommend 64,000 or more. The transcript does not name the config key. *When:* When running Claude Code or another large-prompt agent on Ollama, especially with repeated compaction or unfinished tasks.
- **Pin the Claude Code version and attribution header** — Update Claude Code to at least 2.1.181 (speaker's figure, which conflicts with the June v2.1 fix he describes earlier). If you cannot update, set the Claude Code attribution-header environment variable to 0. The variable name is not spelled out in the transcript. *When:* When pointing Claude Code at a local OpenAI-compatible server, or when every turn is a cold read.
- **Keep thinking tokens in history** — Do not strip reasoning tokens from earlier assistant turns. The speaker says Qwen's 27B preserves them by default for caching. *When:* When using reasoning models with a frontend that trims or rewrites conversation history between turns.
- **Lower reasoning effort on Qwen models** — Set the effort level from the highest tier (xhigh) to medium. The speaker says the highest setting generates 5-6x more thinking tokens, which inflates context and makes the cache harder to maintain. *When:* When local Qwen agent sessions balloon in context or cache hits fall off over a session.
- **Test frontends against the same server before committing** — Run the same model on the same server through each candidate frontend (the speaker compared OpenClaw and Hermes) and compare cache-token counts and first-token latency. *When:* When choosing an agent frontend for local models.

## Hot takes
- The headline 'not the chip' is overstated. The speaker concedes at 11:20 and 12:29 that the chip matters for cold reads.
- Most evidence is anecdotal and secondhand: an unnamed Reddit developer, an M1 Max user, a content creator, and a forum-sourced log. The presenter shows no reproduction, so specific figures are illustrative.
- The 44x comparison is within one session but the context size also changed (158k vs 188k), so it mixes size and cache effects. The roughly 41k reread tokens do account for most of the gap, so the direction is fair.
- Version wording conflicts: the June v2.1 fix described at 6:37 versus the 2.1.181 threshold in the checklist at 12:29.
- 'Amazon Claude code documentation' at 9:05 is likely a caption or attribution error for Anthropic's docs. Unverified.
- Captions garble model and hardware names ('Quen 3.827B', 'Mac Mini M6'). Treat exact model names as unverified.
- The claim that Qwen's documentation says preserved thinking helps caching is relayed secondhand and not shown.
- The checklist says it 'costs nothing', but raising the context window to 64k+ costs memory and latency, and this trade-off is not discussed.
