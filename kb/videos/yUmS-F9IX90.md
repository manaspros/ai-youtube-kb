> Ara Khan (Cline) argues for four maturity levels of agent building: framework, hand-built state machine, Kanban as the UX, and cloud execution. Core warnings: keep prompts minimal, keep agents CLI-testable, and keep architecture human-owned.

## Summary
Ara Khan, who works on Cline, presents a four-level maturity model for building AI agents: start with a framework to test whether an idea works, then build a hand-written agent as an explicit state machine, use Kanban boards as the working interface, and finally run agents in the cloud. The talk is mostly opinion and hot takes, with few measured numbers. The speaker says frameworks lose out once production needs customization. He argues that every instruction added to a prompt can make a frontier model worse, so prompts should be pruned, and that agents should be exposed through a CLI so coding agents can build and test them. He also warns that frontier-lab APIs need exact reasoning-trace handling, which he says is easy to get wrong silently. He says the architecture and state-machine design must be done by a human, even when models write the code. He describes Kanban as the right view for running several parallel agents, with the user acting as an engineering manager. He ends by saying cloud agents, run per task on their own machines and dispatched from a phone, will carry most of the compute. ## Key ideas
- **Use a framework to find product-market fit, not for production** — Frameworks such as LangChain and LangGraph can produce a working agent quickly for a prototype. The speaker says that for production the needed customization, modularity and control usually fall outside what a framework offers, so he writes his agent layer by hand. ([2:31](https://youtu.be/yUmS-F9IX90?t=151))
- **Model every agent as a state machine and always know its current state** — He says every agent is essentially a recursive while loop with a few conditions and end states. For a file-reading task he walks through the states: user task, read tool action, realize the read is done, call the completion tool, task complete. Keeping track of the current state is the mental model he recommends. ([3:54](https://youtu.be/yUmS-F9IX90?t=234))
- **Every instruction added to a prompt can make frontier models worse** — Large system prompts, many edge cases and nested if-else logic can hurt newer models, which perform better with less guidance. He cites the Codex repo, where the prompt for GPT-5.3 is about a third the size of the GPT-5 prompt. His team rewrote Cline from scratch to remove accumulated junk, and he says Claude Code has been rewritten several times. ([5:09](https://youtu.be/yUmS-F9IX90?t=309))
- **Make the agent CLI-testable so coding agents can build and test it** — If an agent can be built and tested through a CLI, other coding agents can change it, run it end to end and iterate on it, including in a long-running background thread. He ties this to a shift in which humans are increasingly guided by AI, and suggests writing AGENTS.md well, using skills, and setting up CI/CD for the agent. ([6:26](https://youtu.be/yUmS-F9IX90?t=386))
- **Architecture must be designed and read by a human, not left to models** — He says the speaker and team learned that design should be thought through carefully and the generated code read, even when an agent writes it. He calls the high throughput of tokens a risk of producing slop and says the state machine should be decided before letting models run. ([7:49](https://youtu.be/yUmS-F9IX90?t=469))
- **Frontier APIs can silently degrade results if reasoning traces are not sent back exactly** — Newer reasoning models expect reasoning traces returned in a precise format across turns. Sending them incorrectly still produces output, but performance drops with no visible error. He says many teams miss the gains from new models for this reason and that an abstraction layer such as OpenRouter is not enough. Each provider's API needs testing. ([8:58](https://youtu.be/yUmS-F9IX90?t=538))
- **Kanban is the right UX for running several agents in parallel** — Agents are inference-bound and can run for 8 to 10 minutes, so the user should run two or three at once. Each task's state should be isolated because agents may mutate the same source. A Kanban board lets the user act as an engineering manager, watching each agent, seeing headline status, and chaining tasks so one starts when another finishes. He says the board shows tasks as in-progress or in review when they need input. ([10:18](https://youtu.be/yUmS-F9IX90?t=618))
- **Move agent execution to the cloud, one isolated machine per task** — Cloud agents avoid local dependencies because each task gets its own machine and can set up its own environment. He sends tasks from his phone, and they can run 15 to 20 minutes or more, including GUI-like testing steps. He also says a shared cloud setup lets many people use and modify the same agent setup. ([12:59](https://youtu.be/yUmS-F9IX90?t=779))
- **Use the four levels as heuristics and move up or down with the effort required** — He suggests starting with the simplest version that works, then moving up or down the levels based on how much effort and rigor the problem needs. He sees Kanban as the UX layer and cloud execution as the shipping layer. ([15:47](https://youtu.be/yUmS-F9IX90?t=947))

## Techniques
- **Agent as explicit state machine** — Write the agent as a loop with named states (user task, tool action, completion) and defined end states. At any point, the state should be identifiable from the trace. *When:* Designing a new agent or debugging one that stalls or loops unexpectedly.
- **Prune the system prompt on every change** — Treat each added instruction or edge-case branch as a possible regression. Remove junk from older versions, compare behavior before and after, and rewrite from scratch when accumulated cruft is larger than the useful content. *When:* Prompts or agent logic have grown through patching, or a newer frontier model is being adopted.
- **CLI-first agent interface for agent-driven development** — Expose build, run and test steps through a CLI, document them in AGENTS.md, and add CI/CD so that other coding agents can test changes end to end without a human setup step. *When:* You want coding agents to iterate on your own agent, or want long background runs that modify and verify it.
- **Exact reasoning-trace round-tripping** — Return reasoning traces to the provider in the exact format it expects across turns. Test each provider's API separately and verify output quality, since failures degrade quietly. *When:* Building multi-turn conversations with reasoning models from frontier labs.
- **Kanban board as the multi-agent control surface** — Give each agent an isolated task state, show every task as a column card (in-progress, review, done), open a task to see its full trace, and chain dependent tasks so downstream work starts automatically. *When:* Running two or three or more agents in parallel that may touch the same codebase.
- **Per-task cloud agent dispatch** — Run each long task on its own cloud machine with its own environment, start tasks from a phone or laptop, and pull the resulting PR later. Shared cloud setups can be modified by several people. *When:* Tasks are long (15 to 60 minutes), numerous, or need to run without local dependencies.
- **Human-owned architecture before code generation** — Before an agent writes code, a human writes down the architecture and state machine, and reviews the generated code instead of letting models run through the codebase unsupervised. *When:* Starting a new agent or making a structural change to an existing one.

## Hot takes
- Most people building for production should not use an agent framework, because they will outgrow its customizability.
- Frontier models do better with shorter prompts, and long system prompts make them worse.
- Architecture and the state machine must be designed by a human even when agents write the code.
- Frontier lab APIs are built to lock users in, and an OpenRouter-style abstraction is not enough to avoid quiet degradation.
- Kanban boards are the future UX for working with agents, and most agent compute will move to the cloud.
