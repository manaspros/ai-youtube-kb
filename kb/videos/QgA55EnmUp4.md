> A hands-on workflow for building a full app with Cursor or Claude Code by splitting context into a PRD-generated docs folder, a short always-on rule, and a staged implementation plan.

## Summary
The host frames context engineering as a broader practice than prompt engineering, covering rules, tools, memory and RAG, and argues that a fuller context window reduces hallucination only if it is managed in pieces. The workflow starts from a PRD listing features and tech preferences, then a "generate" rule expands it into four docs: an implementation plan, a project structure file, UI/UX docs and a bug-tracking file. A small, always-attached "workflow" rule tells the agent which doc to consult for each kind of task, so the always-loaded context stays small. The implementation plan is staged with task lists, and the agent may split a long subtask into its own list. Fresh chats recover state from that plan, which the host demonstrates by running stage one in Cursor and noting the agent verifies each step before moving on. For Claude Code the same generate file becomes a custom slash command, and CLAUDE.md holds code-level notes. The host closes with cautions: models follow instructions literally, so review every generated file (he suggests about an hour) and choose the tech stack yourself. Parallel agents are useful only for independent work such as installs or UI variants.

## Key ideas
- **Context engineering is broader than prompt engineering: it covers everything the model sees (rules, tools, memory, RAG), and the host credits the term to Karpathy while noting the practice predates it.** — Framed as filling the context window with the facts, rules and tools the model needs, rather than phrasing one good prompt. The host says it is not new, only named. ([0:00](https://youtu.be/QgA55EnmUp4?t=0))
- **Apps like Cursor and Claude Code are components of context engineering, not ChatGPT wrappers.** — The host attributes this point to Karpathy's tweet and says the app's tools and workflows matter as much as the underlying LLM. He judges Claude Code the stronger agent today, with Cursor catching up (for example with to-do lists). He says the workflow works in either app. ([1:15](https://youtu.be/QgA55EnmUp4?t=75))
- **Filling the context window hurts accuracy, so context has to be split into pieces and loaded only when needed.** — The host says hallucination rises as the window fills. He recommends against dumping everything into one file and loading each doc on demand. ([2:38](https://youtu.be/QgA55EnmUp4?t=158))
- **The core artifact is a PRD that a generate rule expands into a documentation folder of four files.** — Files: implementation plan, project structure (generated by the agent), UI/UX documentation, and bug tracking. The PRD lists features; tech-stack preferences (his example: Next.js front end, FastAPI back end) can be added. ([2:38](https://youtu.be/QgA55EnmUp4?t=158))
- **Two rules drive the process: a long generate rule that writes the docs, and a deliberately small workflow rule that stays always-attached.** — The workflow rule maps task type to doc (implementing reads the plan, UI reads the UI doc, new files check the structure, bugs check the bug log first). The host keeps it short because it always occupies context, and keeps the implementation plan long because it is only read when needed. ([3:49](https://youtu.be/QgA55EnmUp4?t=229))
- **A new chat can resume the project without history because the implementation plan carries the state.** — The plan opens with what is being built and the tech stack. The host starts a fresh chat for stage one and the agent builds its to-do list from the plan. A subtask gets its own list only if it is long; otherwise the agent just follows the steps. ([5:08](https://youtu.be/QgA55EnmUp4?t=308))
- **Models follow written instructions literally, including conflicting ones, so generated plans need human review.** — His generate file asked for a whole-app plan, so the agent ignored his MVP request, and the generate prompt also set foundations-first ordering. He advises reading every generated file (about an hour) and deciding the tech stack yourself, since the model may pick a provider you cannot use. ([7:01](https://youtu.be/QgA55EnmUp4?t=421))
- **Build order matters: foundations and setup before features, with each step verified before the next.** — In the demo the agent sets up folders, backend and frontend structure and API wiring before core features, and reportedly does not advance until the current step is verified. The host says skipping this leads to rebuilds. ([9:30](https://youtu.be/QgA55EnmUp4?t=570))
- **In Claude Code the generate workflow becomes a custom slash command; parallel agents help only for independent tasks.** — Drag the docs in and run the command. CLAUDE.md holds code-level documentation. Sequential plan steps must run one at a time. Parallel agents suit installs or generating UI variations. ([11:40](https://youtu.be/QgA55EnmUp4?t=700))

## Techniques
- **Four-file documentation set generated from a PRD** — Write a PRD listing features and stack preferences. Run a generate rule that produces: an implementation plan (stages with task lists and subtasks, plus the project purpose and tech stack at the top), a project structure file (initially empty, filled as the agent builds), a UI/UX doc, and a bug-tracking log. Keep them in a documentation folder. *When:* Building a whole app with an AI coding agent where the work will span several sessions and context resets.
- **Small always-attached workflow rule that routes to on-demand docs** — Write a short always-loaded rule telling the agent which doc to read for each task type: implementing reads the implementation plan; UI work reads the UI/UX doc; creating files or commands checks the project structure; any error checks the bug log before debugging. Keep it short. Keep the big docs out of the always-loaded context. *When:* You want the agent to consult project docs without spending the context window on them up front.
- **Staged implementation plan with optional subtask lists** — Organize the plan into stages. Each stage has broad tasks with subtasks. When a subtask is large, the agent creates its own task list for it. Otherwise it follows the listed steps. Start each stage in a fresh chat with a prompt like 'begin stage one' so the plan supplies the state. *When:* Long builds where you want resumability and no reliance on chat history.
- **Put the foundations and scope into the generate prompt** — State in the generate file that the build starts with setup and foundations, then advanced features. Also state scope explicitly (MVP vs full app). Review the output, because the host's MVP request was overridden by the whole-app wording in the same prompt. *When:* Before generating the plan, to control stage order and scope.
- **Claude Code slash command for the generate step** — Save the generate workflow file as a custom slash command (the host calls his 'generate implementation'). Drop in the PRD and run it. Keep code-level notes in CLAUDE.md and multi-file docs rather than one large file. *When:* Using Claude Code instead of Cursor with the same docs workflow.
- **Parallelize only independent work** — Give multiple agents tasks that do not depend on each other, such as dependency installs or several UI variations. Run sequential plan stages one at a time. *When:* Deciding whether spawning subagents will speed up a build.
