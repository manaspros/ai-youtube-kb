> Conceptual walkthrough of the agentic development lifecycle (ADLC), a phase-by-phase SDLC analogue for non-deterministic agents with a validation gate and staged rollout. Thin on code and data, with a sponsor segment.

## Summary
The speaker argues that SDLC treats software as static and deterministic, while AI agents are probabilistic and keep changing in production, so a new lifecycle (ADLC) is needed. He lays out seven phases, each mapped to an SDLC phase: preparation and hypothesis, scoping with a human-agent responsibility model, design, simulation and proof of value, implementation, testing, and deployment with ongoing monitoring and feedback. The advice is mostly process-level: use Claude Code's planning mode to map agent behavior before architecture, write down who is accountable for what, build a ground-truth dataset early, treat the prototype stage as a kill gate, and roll out to a small group first. Concrete tooling is light: planning mode, the "agent's view" for orchestrating several agents, MCP integrations for calendar, email and Notion, and a mention of RAGAS and DeepEval for evaluation. No benchmarks, cost figures, or working code are shown. About 1.5 minutes is a sponsored segment for an app builder (Softr, transcribed as "Softer"). The framework is presented as a community-wide "new framework" without naming an author or source.

## Key ideas
- **SDLC treats software as a static artifact whose behavior is known at planning time. ADLC treats the system as a living one, because agent behavior depends on the prompt, context, model and connected tools.** — The speaker's core premise: the same input does not reliably give the same output, so agents cannot be graded with the deterministic pass/fail metrics used for ordinary software. He argues the old lifecycle has stopped fitting once coding tools like Claude Code and Cursor took over the coding step. ([0:00](https://youtu.be/aMBQB_IJ0dQ?t=0))
- **Non-determinism is the reason for the change. The same inputs never guarantee the same output, so success must be stated as distributions and behaviors.** — He says the decisions an agent makes depend on prompt, context, model, and external tools, and that a prompt cannot be guaranteed to return a fixed result. This is why he frames success differently from SDLC. ([1:01](https://youtu.be/aMBQB_IJ0dQ?t=61))
- **The speaker maps seven ADLC phases onto SDLC phases: preparation and hypothesis, scoping, design, simulation and proof of value, implementation, testing, and deployment with continuous monitoring.** — Each phase is described as a gate or an output the next phase depends on. Phase 1 builds an understanding of the problem and forms testable hypotheses about where agents help. Note the video says seven phases, but the sections it walks through include a separate maintenance and feedback stage at the end. ([2:28](https://youtu.be/aMBQB_IJ0dQ?t=148))
- **Plan the agent's behavior before its architecture. Put the planning tool in plan mode and tell it not to think about code.** — The first step is to have the agent map the workflow, user interactions, failure modes, overhead, and assumptions. The stated goal is that these assumptions guide later architecture decisions instead of jumping straight to implementation. ([3:35](https://youtu.be/aMBQB_IJ0dQ?t=215))
- **Scoping must include a documented human-agent responsibility model that defines the agent's autonomy boundaries and who is accountable when something fails.** — He says a human still has to review decisions, that agents should not be trusted with every decision, and that you cannot blame the model in a failure. The phase ends with workflow steps, KPIs (time, cost, latency, feasibility), and the responsibility model written down. ([4:39](https://youtu.be/aMBQB_IJ0dQ?t=279))
- **The simulation phase is a validation gate. Test the high-risk assumptions on real data, record baselines, and kill the project if the results do not hold.** — Deliverables are measured performance and cost baselines, plus a ground-truth document reused for regression tests and fine-tuning. Failing this gate early is presented as far cheaper than failing in production. ([6:51](https://youtu.be/aMBQB_IJ0dQ?t=411))
- **In agentic systems the logic is spread across code, prompts, models, tools and external services, so any layer can change behavior. Testing has to run during implementation, not only afterward.** — He recommends one orchestration layer (Claude Code's agent view) to coordinate multiple agents instead of many separate sessions. He also warns that large context windows still suffer from context rot, so irrelevant information should be kept out of the context. ([9:26](https://youtu.be/aMBQB_IJ0dQ?t=566))
- **Success metrics change: instead of functional tests that pass or fail, track accuracy distribution, hallucination rate, and cost per outcome, with continuous evaluation of reasoning, safety, and tool use.** — He names RAGAS and DeepEval as evaluation frameworks and says the key correctness check is how the data performs against the metrics defined earlier. Testing types named: functional, non-functional, structural, and load testing. ([10:54](https://youtu.be/aMBQB_IJ0dQ?t=654))
- **Deployment is a controlled activation with continuous observation. Release to a limited group first, watch behavioral metrics, set alerts for quality and safety, then expand gradually.** — The alerting focus is on behavior (quality, safety, drift from model updates and environment changes), not only on system health. The stage also includes continuous monitoring of cost, quality, and backlog. ([13:03](https://youtu.be/aMBQB_IJ0dQ?t=783))
- **Feedback loops are continuous. Thumbs up/down and ranking signals feed back into the system, data sources and embeddings are refreshed periodically, and alignment is monitored against prompt injection.** — He cites ChatGPT and Claude feedback UIs as examples of signal collection. The closing point: keep cost management, quality tracking, backlog, and model upgrades running to keep the system stable over time. ([14:21](https://youtu.be/aMBQB_IJ0dQ?t=861))

## Techniques
- **Behavior-first planning mode** — Enable planning mode in the coding agent and prompt it to map the agent's behavior, not its implementation: user interactions, where the workflow breaks, what could go wrong, overhead, and assumptions. The video gives no exact prompt text; this is a paraphrase. *When:* At the start of a new agent project, before any architecture or code, so the assumptions drive the architecture.
- **Human-agent responsibility model** — During scoping, write down the workflow steps, the KPIs (time, cost, latency, feasibility), the trade-offs that are acceptable, and which decisions require human review, so accountability is explicit for failures. The speaker gives no template. *When:* Before design, for any agent that takes actions or decisions in production (compliance and accountability).
- **Ground-truth dataset plus baselines as a validation gate** — Build a dataset of real-world cases with expected outcomes, prototype the high-risk assumptions, record performance and cost baselines, then keep the dataset as a regression suite and a source for fine-tuning. Continue only if results clear the bar. *When:* After design and before implementation, when deciding whether to build the agent at all.
- **Single orchestration layer for multiple agents** — Use Claude Code's agent view as one orchestration layer that coordinates several agents from a manager prompt, instead of managing many separate sessions by hand. Feature details (invocation and setup) are not shown. *When:* When a system has multiple agents that need to coordinate.
- **Context hygiene against context rot** — Keep only relevant information in the agent's context and check memory contents. Large windows (the speaker cites 1M-token windows in Gemini and Opus) do not remove the need to curate them. *When:* In implementation, as tools and MCP servers are added and the context grows.
- **Staged rollout with behavioral alerting** — Release to a small group of real users first, watch behavioral metrics (quality, safety, drift), set alert rules that fire on those metrics, and expand only after the observation period. *When:* At deployment, for any agent with live users.
- **Feedback signals and periodic data refresh** — Collect thumbs up/down or response-ranking signals, feed them back into the system, refresh data sources and embeddings on a schedule, and monitor alignment and guardrails against prompt injection. *When:* After launch, as an ongoing maintenance loop.
