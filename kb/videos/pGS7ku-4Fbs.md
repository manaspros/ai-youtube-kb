## Key ideas
- **A loop is agents repeating work cycles until a stop condition is met, and the stop condition is the architecture.** — Without a defined stop, a loop keeps running, burns tokens and produces unrequested output. Every loop must end by agent judgment, a predefined definition of done, a timer, or an external event. ([1:15](https://youtu.be/pGS7ku-4Fbs?t=75))
- **The four loop types differ by who decides when to stop.** — Turn-based (Claude judges completion, for one-off work), goal-based (success condition and turn cap, for verifiable exit criteria), time-based (interval triggered, stopped by cancellation or when the underlying work resolves), and proactive (event or schedule triggered routines that run until disabled, for well-defined recurring work like bug triage and dependency upgrades). ([1:15](https://youtu.be/pGS7ku-4Fbs?t=75))
- **skill.md is a verification protocol, not a prompt.** — It encodes the exact checks Claude must run and measure before declaring done. The more quantitative the checks, the harder it is for the agent to fake a pass. The official example in the post is for UI changes. ([2:35](https://youtu.be/pGS7ku-4Fbs?t=155))
- **Goal-based loops use an evaluator model that re-checks the condition on every stop attempt.** — If the condition is unmet, the agent is sent back to work. Conditions should be deterministic (a score threshold, a test count) rather than fuzzy like 'make the UI look better', and the turn cap is a required safety valve. ([3:47](https://youtu.be/pGS7ku-4Fbs?t=227))
- **Time-based loops differ by where they run.** — /loop runs on the local machine and stops when the computer is off. /schedule moves the loop to the cloud so it runs while the user is away, which the speaker calls both the appeal and the risk. ([3:47](https://youtu.be/pGS7ku-4Fbs?t=227))
- **Proactive loops combine a schedule trigger, a goal condition, parallel work trees and an adversarial judge agent.** — The example prompt runs hourly, requires every report in the run to be handled, spawns parallel work trees to explore three solutions, and has a judge agent review output before it ships. The judge is a second agent with fresh context that does not see the first agent's reasoning. ([5:12](https://youtu.be/pGS7ku-4Fbs?t=312))
- **Token control is the main operating risk of proactive loops.** — Dynamic workflows can spawn hundreds of agents. The post advises piloting on a smaller slice first. Monitoring is done with /usage (spend by skills, subagents and MCPs), /goal with no arguments (turn count and tokens mid-run), and /workflows (per-agent token use, with the option to kill a runaway agent). ([6:30](https://youtu.be/pGS7ku-4Fbs?t=390))
- **Match model cost to task: fast model for triage, capable model for judgment.** — A loop running hourly on bug reports does not need the most capable model for every ticket. The docs recommend cheap models for grunt work and reserving the capable model for review. ([7:48](https://youtu.be/pGS7ku-4Fbs?t=468))
- **The progression is a delegation ladder.** — Each step hands one more decision to the system: first the check (skill.md), then the stop condition (/goal), then the trigger (/loop or /schedule), and finally the prompt (the full recurring-work stack). The speaker's framing is that the human has been the stop condition and can stop being it. ([8:49](https://youtu.be/pGS7ku-4Fbs?t=529))

## Techniques
- **Define the stop condition before starting a loop** — Before launching any loop, state what done looks like: a Claude judgment, a measurable condition, a timer, or an external event. Treat the stop condition as the first design decision, not an afterthought. *When:* Any time you move from single prompts to a loop, especially any loop that runs unattended.
- **Write skill.md as a measured verification protocol** — List the exact sequence of checks Claude must execute and measure before it may report success (for example, metrics, test counts, score thresholds for a UI change). Require the agent to run and record each check rather than describe it. The transcript does not show the specific checks used in the official example. *When:* When a turn-based or goal-based loop will otherwise accept Claude's self-reported 'done'.
- **Goal loop with deterministic success criteria and a hard turn cap** — Use the slash goal primitive with one task, one measurable success condition (for example a Lighthouse score or number of passing tests above a threshold), and an explicit maximum number of turns. An evaluator model re-checks the condition on every stop attempt and sends the agent back if it is unmet. Avoid subjective conditions. The exact syntax is not shown in the video. *When:* Tasks with verifiable exit criteria, such as making a test suite pass or reaching a performance threshold.
- **Choose local or cloud for time-based polling** — Use /loop for interval polling on the local machine, which stops when the machine is off. Use /schedule to run the same kind of interval work in the cloud while the user is away. Stop the loop when the underlying work resolves, such as a PR merging or a queue emptying. *When:* Recurring work where only the inputs change (daily summaries), or polling an external system such as PR review or CI.
- **Fresh-context adversarial reviewer** — Run the output through a separate judge agent that does not receive the producing agent's reasoning and evaluates the output independently before it ships. *When:* Proactive loops or any agent-written change that needs an unbiased check before merge.
- **Pilot, then scale, and monitor spend mid-run** — Run a dynamic workflow on a small slice of the work first. During the run, use /usage for spend by skill, subagent and MCP, /goal (no arguments) for turn count and tokens, and /workflows for per-agent token use, killing any runaway agent. *When:* Before scaling any workflow from tens to hundreds of tasks, and whenever a proactive loop is active.
- **Route models by task** — Assign a fast, cheap model to triage and routine steps, and a capable model to review or judgment calls within the same loop. *When:* Recurring loops where per-iteration cost compounds, such as hourly ticket triage.

## Hot takes
- Claude's judgment that a task is done is probabilistic and can be confidently wrong, so verification should be encoded outside the model's own report.
- The stop condition is the architecture, and a loop without one is worse than a failed loop because it keeps spending tokens.
- Proactive loops with hundreds of agents need a hand on the spend controls at all times, not just setup.
- The human has been the stop condition in the loop, and the goal is to stop being it.
- The video's framing is secondary: it summarizes one Anthropic post and adds analogies, with no independent measurements.
