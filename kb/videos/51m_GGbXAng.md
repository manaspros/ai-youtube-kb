> Chrome 144+ lets the Chrome DevTools MCP server auto-attach to your running browser for login-state debugging, element selection and network inspection, plus an experimental CLI alternative that avoids MCP context cost.

## Summary
Better Stack walks through the newer Chrome DevTools MCP features: with remote debugging enabled in Chrome 144 or later, the MCP server can auto-detect and attach to an already-open Chrome session instead of launching a fresh one or requiring a manual debugging port. The agent can then inspect pages behind a login, run Lighthouse audits, read network activity, and act on an element the developer has selected in DevTools, which the presenter uses to restyle a save button in a language-learning app. He notes the MCP server's context cost and points to an experimental Chrome DevTools CLI (found in the skills directory) that wraps the same tooling in a daemon, but the CLI lacks the auto-connect option, so Chrome must be relaunched from the terminal with a remote debugging port and user data directory. The security trade-off is explicit: attaching to your everyday profile exposes cookies and history, while an isolated user data directory keeps the agent out of them at the cost of re-login. Overall this is a short, practical tool walkthrough with no sponsor segment and no benchmarks.

## Key ideas
- **Chrome 144+ with remote debugging enabled lets the Chrome DevTools MCP server auto-detect and attach to your already-running browser session.** — Previously the MCP server could only launch a new Chrome or connect to a manually exposed remote debugging port, which required a lot of setup. The auto-connect path removes that step, so the agent can work with cookies, history and logins you already have. ([0:00](https://youtu.be/51m_GGbXAng?t=0))
- **Attaching to your everyday profile gives the agent your logged-in state; an isolated profile is the security-conscious alternative.** — Auto-connect uses your real browser, so the agent gets cookies, passwords and history. For sensitive use, the MCP server can be given a dedicated user data directory, which keeps the agent out of those and requires logging in again. ([0:00](https://youtu.be/51m_GGbXAng?t=0))
- **Selecting an element in DevTools and asking the agent about it is a faster handoff than describing the page.** — Instead of having the agent replay login and navigation steps to reach a page, the presenter selects the save button in DevTools inspect mode. The agent sees the selected element and restyles it to match another button on the site. ([2:29](https://youtu.be/51m_GGbXAng?t=149))
- **The presenter prefers Claude Code in the terminal, so browser-based AI debugging tools are less necessary.** — Getting live-session debugging into the terminal agent means he no longer needs separate AI browsers or a Chrome extension for this kind of work. The demo runs in OpenCode, which he says supports many agent harnesses. ([1:02](https://youtu.be/51m_GGbXAng?t=62))
- **The MCP server's context cost is the main reason to consider the experimental CLI.** — The presenter dislikes MCP servers because each one consumes context. The Chrome DevTools CLI, documented in the skills directory, is a thin wrapper around the same tooling that the agent can call without loading an MCP server. ([3:52](https://youtu.be/51m_GGbXAng?t=232))
- **The CLI has its own daemon and does not support auto-connect, so it needs a manual Chrome launch.** — The CLI does not reuse a running MCP server. Its default daemon uses a browser URL flag plus headless and isolated options, and there is no auto-connect option. You quit the existing Chrome and relaunch it with a remote debugging port and a user data directory before starting the daemon. ([3:52](https://youtu.be/51m_GGbXAng?t=232))
- **A persistent user data directory keeps cookies and session state between CLI runs.** — Because the user data directory persists, the cookies and browser state from earlier sessions carry over. This is the trade-off for a debugging profile that stays logged in. ([5:11](https://youtu.be/51m_GGbXAng?t=311))

## Techniques
- **Attach the Chrome DevTools MCP server to your running Chrome (auto-connect)** — 1) Install the Chrome DevTools MCP server with the auto-connect option (the presenter uses OpenCode; the setup works with many agent harnesses). 2) In Chrome 144 or later, open the remote debugging page the presenter shows (the URL is not spoken in the transcript) and turn the option on. 3) Connect the MCP server with auto-connect. 4) Ask the agent to do something, such as a performance check. Chrome then shows an 'allow remote debugging' popup and a banner; accept it. You can close Chrome when you are done. *When:* Debugging a page that is behind a login or depends on your current session, and you want the agent to work in your real browser with no launch step.
- **Select an element in DevTools to hand it to the agent** — Use DevTools inspect mode to select the element on the live page, then ask the agent whether it can see the selected element. The agent reads the selection and can edit it, for example by changing its style to match another element. *When:* A UI bug or styling change is hard to describe in words, or reaching the page would require replaying a long sequence of login and navigation steps.
- **Isolated profile for security-sensitive use** — Add a user data directory option to the MCP server configuration that points to a dedicated location. The agent then has no access to your existing cookies, passwords or history, and you must log in again inside that profile. *When:* Running the agent on untrusted pages, in a sandbox, or on anything that should not see your personal browser state.
- **Sandboxed MCP server with an HTTP remote debugging port** — If the MCP server runs inside a sandbox, use the browser URL option that points to the remote debugging port over HTTP, not WebSockets. *When:* The agent runs in a container or sandbox that cannot use the auto-connect path.
- **Chrome DevTools CLI instead of the MCP server** — 1) Find the experimental Chrome DevTools CLI skill in the skills directory of the MCP package; it has install instructions. 2) Quit any running Chrome. 3) Relaunch Chrome with a remote debugging port flag and a user data directory flag (both are required together). 4) Start the CLI daemon and list pages to confirm the connection. 5) Let the agent call the CLI, for example to find out which element is selected in DevTools. *When:* Context budget matters and you do not want an MCP server loaded in the agent harness. Expect manual setup, since the CLI does not auto-connect.
- **Persist the debugging profile across sessions** — Keep using the same user data directory for the CLI. Cookies and browser state stay in it between daemon starts. *When:* You repeatedly debug the same logged-in app and do not want to log in each time, accepting that the profile holds credentials.

## Hot takes
- Browser-based AI debugging tools (AI browsers, the Chrome extension, React Grab) are unnecessary once a terminal agent can attach to your live Chrome session.
- MCP servers consume a lot of context, so a CLI wrapper of the same functionality is preferable when it exists.
- The presenter argues Chrome's auto-connect is the big improvement, but the CLI route is the one he says is worth using today because it is more predictable.
- The presenter wishes Arc had the same feature and says he still uses Arc.
