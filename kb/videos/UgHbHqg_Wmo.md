## Summary
The host presents a tmux-orchestrator setup in which a main Claude Code agent runs inside a tmux session, opens sub-terminals, and briefs separate front-end and back-end teams, each with a project-manager window, a developer window, and a test/server window. The build is driven by a spec folder (main spec with per-phase timings, integration spec, front-end and back-end specs), and the orchestrator checks on each team every 15 minutes and commits changes as restore points. The host gives two required fixes to the cloned repo: hard-coded usernames in paths, and swapping the claude command for the variant with the skip-permissions flag, because otherwise the sub-terminals block on approval prompts (he says the system sat frozen for 15 minutes). He prefers stepping through phases with approval at each checkpoint rather than running all phases unattended. The host reached his usage limit, so the build itself is not shown live; the autonomy claims rest on the walkthrough of setup and a few check-in screens. ## Key ideas
- **tmux lets one Claude Code instance open extra terminals in the same session and send them tasks, so a single agent can coordinate many Claude Code instances.** — The host frames tmux (terminal multiplexer) as the mechanism: the main agent creates sub-terminals and assigns tasks, and the sessions persist, so you return to where you left off. He describes one instance controlling as many instances as it wants. ([0:00](https://youtu.be/UgHbHqg_Wmo?t=0))
- **Scheduling is the second ingredient: agents run tasks at set times and move on without monitoring.** — The host describes timed task assignment as what turns the terminal into a self-running system. Each team is checked every 15 minutes in the setup he shows. ([1:03](https://youtu.be/UgHbHqg_Wmo?t=63))
- **The cloned framework needed two manual fixes before it worked on another machine.** — Paths were hard-coded with the author's username, so the first self-check fails until Claude fixes them. The second fix was replacing the claude command in the scripts with the variant that uses the skip-permissions flag, which the upstream version lacks. ([3:03](https://youtu.be/UgHbHqg_Wmo?t=183))
- **Skip-permissions is needed for unattended multi-terminal runs, and the host says it hung his first run.** — With approval prompts on, each sub-terminal waits for a human. He says his first run stayed frozen at phase 1 for 15 minutes for this reason. He says he used the flag many times without problems, but the video does not discuss the risk of letting every command run unapproved. ([4:13](https://youtu.be/UgHbHqg_Wmo?t=253))
- **The spec folder is the blueprint: the main spec sets per-phase timing, and separate integration, front-end and back-end specs define what gets built.** — Specs are written step by step from a template with default full-stack requirements. The host says the orchestrator is told the full path to the spec folder, starting from the home directory (relative paths are not allowed). Teams are named in the start prompt, and new teams follow the same pattern (his example is an auth team). ([5:41](https://youtu.be/UgHbHqg_Wmo?t=341))
- **Each team gets a fixed window layout and is briefed by a message script, with phase-gated progress.** — Each team has three windows: project manager, developer, and a server that runs tests and error checks. The main agent sends briefings via a 'Send Claude message' script, and after phase 1 it asks permission before phase 2. The host prefers this step-by-step review over automatic progression, though main.md can be set to run all phases. ([8:24](https://youtu.be/UgHbHqg_Wmo?t=504))
- **GitIngest is a practical shortcut for understanding an unfamiliar repo's setup steps.** — Replace github.com with gitingest.com in the repo URL to get an AI-readable text summary, paste it into Claude (he says it did better than ChatGPT for this), and ask for the install and workflow steps. ## Techniques
- **tmux-based agent orchestrator setup** — 1) cd to the target directory and git clone the tmuxorchestrator repo (URL from the video description). 2) cd into tmuxorchestrator and run the setup commands from the repo or description (not shown on screen; they make the scripts executable). 3) Start a named tmux session (he uses one named 'my second agent') and run claude inside it. 4) Give Claude a prompt that runs two checks: can it control other tmux windows, and does the scheduling work. Expect the scheduling/path check to fail until the hard-coded paths are fixed. *When:* When you want one top-level Claude Code agent to run and supervise several parallel Claude Code workers in tmux windows, for example for a full-stack build.
- **Fix hard-coded paths and permission command in the orchestrator** — Ask Claude to find paths containing the original author's username and replace them with your own. Then ask it to go through all commands and replace the claude invocation with the variant that uses the 'dangerously skip permissions' flag (the transcript does not spell out the flag name; it is most likely --dangerously-skip-permissions). Restart the orchestrator session with that flag. *When:* Before the first run of any orchestrator copied from another person's repo, and before any run that needs all sub-terminals to proceed unattended.
- **Spec folder as the build blueprint** — Create an app folder with spec/ and task-manager/ subfolders. Inside spec/, write a main spec with timing for each development phase, an integration spec, and separate front-end and back-end specs; start from the provided template with default full-stack requirements and edit it. For UI work, add a reference folder with a design image and an implementation markdown plan that names the component library (he uses shadcn with its MCP). *When:* When you want agents to build a multi-part app against explicit phase deadlines instead of an open-ended prompt.
- **Team start prompt pattern** — Start Claude with the orchestrator and give one prompt that includes the full home-relative path to the spec folder (no relative paths), then the teams to create. Each team is listed with a project manager and a developer, for example 'a front-end team and a back-end team, each with a project manager and developer'. Add more teams with the same wording (for example, 'create an auth team'). *When:* To kick off a run once the spec is ready and the setup checks pass.
- **Scheduled check-ins with restore-point commits** — The orchestrator checks each team every 15 minutes, reviews progress against the phase timing, updates the to-do list, and commits regularly so there is a restore point. Keep the default phase gating, or set main.md to advance through phases automatically. *When:* When you want to bound agent drift by time and by phase, and keep rollback points during long autonomous runs.
- **Summarize an unfamiliar repo with GitIngest** — Take the GitHub URL, change github.com to gitingest.com, copy the generated text summary, paste it into Claude, and ask it to explain the workflow and install steps in order. *When:* When a repo's README or setup is confusing and you want the commands assembled from its code.
