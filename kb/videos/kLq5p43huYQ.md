## Techniques
- **Install GStack into a Claude Code project** — Install Claude Code and Bun. In Claude Code, paste the GStack install prompt (exact text not shown in the video) or download the skills. Check that CLAUDE.md now contains the added block, that the skills are in the skills directory (commit them to share with teammates), and that the Playwright browser is installed. *When:* Starting a new project or onboarding teammates to a shared Claude Code workflow.
- **Plan-mode CEO scope review before coding** — Start Claude Code in plan mode, invoke the plan CEO review skill, and describe the feature in plain language. Choose a scope mode (the presenter picked scope expansion), accept the recommended architecture decision, and read the resulting plan: scope, out-of-scope list, architecture diagram, key decisions and steps. *When:* Before a feature where scope and value are uncertain. Pair with the plan engineering review skill for architecture and edge cases.
- **Diff-aware review, ship and QA chain** — After implementation, run the review command (checks the diff for edge cases and bugs CI misses, and checks task completeness). Then run ship (sync with main, run tests, resolve Greptile comments, open PR). Then run qa, which starts a local server and tests only pages affected by the diff with screenshots, fixes what it finds, and writes a report. *When:* Feature branches where you want the agent to own the path from implementation to PR with verification.
- **Let the review command resolve PR review comments** — On an open PR with Greptile (or similar) comments, run the review command instead of asking for fixes by hand. It lists the comments, offers fix options, applies the fixes and pushes. Reject false positives explicitly. *When:* Post-PR review rounds on agent-written code.
- **Put tool preferences in CLAUDE.md, not hooks** — Write rules like 'use bun install, not npm' as plain text in CLAUDE.md. The presenter says this replaced a hook he had used to enforce package-manager choice, and reports roughly 90-95% compliance with Opus. *When:* Enforcing project conventions where a hook is overkill. Verify compliance on your own model and rules.
- **Skill template plus generated SKILL.md** — Keep a template markdown with placeholders per skill. A TypeScript generator under scripts reads the templates and writes the final SKILL.md with placeholders replaced. Keep test and source directories alongside the skill when it needs real code. *When:* Maintaining many skills that share boilerplate, or skills that need backing code.

## Hot takes
- The 'Markdown is the new code' idea is mostly right. A structured CLAUDE.md and skills can replace hooks and much manual steering, as long as the model follows them.
- Gary's 100-PRs-in-seven-days claim is not evidence on its own. The video shows one small feature, and the presenter's trial is informal.
- The PR-comment fix loop and the diff-aware QA are the most useful parts. The CEO plan step is harder to judge, since the presenter ran it once.
- Demo-level evidence only: no baseline comparison except his earlier video, no failure cases, and no measured compliance rate for the Markdown rules.
