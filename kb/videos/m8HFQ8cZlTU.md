> Better Stack runs the same one-prompt 3D endless-runner build on Qwen 3.8 (2.4T open-weight) and Claude Opus 5, then argues cost, speed, verbosity and weight access matter more than the 58-vs-63 benchmark gap.

## Summary
The host compares Qwen 3.8's open-weight 2.4T-total model (about 95B active) and its Max variant against Claude Opus 5 on Artificial Analysis, where Qwen scores 58 and Opus 5 scores 63. Both models get the same single-file Temple Run-style endless-runner prompt, with three.js from a CDN, lane switching, jump, slide, procedural obstacles, scoring, and game over/restart. The host says the goal is to judge what the game actually does when played, not how much code was generated, and claims Qwen was slower to start but reasoned through the game systems first. The video's practical argument is that open weights, roughly $2 per million input and $6 per million output tokens hosted, a roughly 1M context window, and a 47-48 tokens-per-second speed matter more for long background agent jobs than the benchmark gap does. The host also flags Qwen's verbosity and overthinking as drawbacks for quick interactive coding. The video never explicitly says which game won, so the head-to-head result is left unstated.

## Techniques
- **Same-prompt, play-the-output model comparison** — Send one identical prompt with identical constraints to each model: single HTML file, three.js from CDN, explicit mechanics (3 lanes, jump, slide, procedural turns/gaps/obstacles, scoring, game over, restart, 30-60s playable). Run both outputs in a browser and check behaviors one by one: lane switching, jump, slide, collisions, whether generated paths create impossible states, death, restart, clean new game. *When:* Comparing coding models on tasks where toy prompts (e.g., a to-do app) can look fine but fail on interaction. Use it when you want a behavioral signal rather than a code-reading signal.
- **Score by behavior, not by code volume** — Do not treat amount of generated code or speed of scene appearance as progress. Judge the artifact by running it against the requirements list in the prompt, mapping each observed behavior back to a prompt requirement. *When:* Evaluating agent-written code, especially when one model produces more code faster.
- **Route by three axes: speed, verbosity, access** — Use a slower, verbose open-weight model for long autonomous background jobs (migrations, multi-file refactors across a big repo) where answer length matters less than correctness. Keep a faster, terser model for interactive editor-side questions. Price per token matters most when the agent makes hundreds of calls. *When:* Choosing which model backs which agent loop: interactive vs background, short vs long calls, cost-sensitive high-call-count pipelines.
- **Hosted open-weight via an OpenAI-compatible endpoint** — Call the open-weight model through a hosted provider that exposes an OpenAI-compatible API (the host names OpenRouter, DeepInfra, Fireworks). The host says the setup matches existing OpenAI-style client code; the video does not show the actual config or model ID. *When:* You want open weights without local multi-node hardware. Verify the exact model id and endpoint in the provider's docs before relying on it.
