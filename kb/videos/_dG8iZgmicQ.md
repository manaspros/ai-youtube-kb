## Summary
The Better Stack presenter builds a minimal financial-assistant agent with Mastra, a TypeScript framework, after installing it with the CLI and deleting the sample weather agent and workflows. The agent is defined by a name, a model, and a system prompt, then registered on a Mastra instance so it appears in the dev playground. A custom tool (getTransactions) with a zod output schema is added to show tool calling on fake data. The video then shows that without memory a follow-up question fails, and fixes this with a memory field backed by an in-memory LibSQL store, plus a working-memory template that the agent updates through a tool call. It closes by attaching tools from a Firecrawl MCP server through Mastra's MCP client and calling the agent over the generated API with a Mastra client. The video covers only basics; it names workflows, RAG, evals and observability but does not show them, and it offers no benchmarks or comparisons beyond opinion.

## Key ideas
- **Mastra bundles many agent concerns (MCP, custom tools, workflows, RAG, storage, evals, observability) in one TypeScript framework; the video only covers the agent basics.** — The presenter says it can feel overwhelming and asks viewers whether they want a follow-up on workflows. The scope is explicitly limited to agents, tools, memory and MCP. ([0:00](https://youtu.be/_dG8iZgmicQ?t=0))
- **A basic agent is just a named class instance with a model and a system prompt, registered on a central Mastra instance so the dev playground can talk to it.** — Agent is created with name, model (picked from Mastra's supported list) and instructions. It is then passed into the Mastra instance exported from index.ts. Running the dev script exposes it in the playground. A more detailed system prompt (role, capabilities) is used for better answers. ([1:26](https://youtu.be/_dG8iZgmicQ?t=86))
- **Tools are defined with createTool (id, description, zod output schema, execute function) and attached through the agent's tools field.** — The example tool getTransactions returns fake transaction data. The agent then answers a spending question by calling the tool and returning the exact amount, which appears in the playground. ([1:26](https://youtu.be/_dG8iZgmicQ?t=86))
- **Without a memory field, the agent cannot answer follow-ups that depend on earlier turns; adding memory with a storage backend fixes this and persists chats.** — The follow-up 'what is 2x that amount' fails before memory is added. After adding a Memory instance with a LibSQL storage store (kept in memory for the demo), the agent answers correctly and chats appear in the playground. ([2:54](https://youtu.be/_dG8iZgmicQ?t=174))
- **Working memory with a template lets the agent store structured user facts (preferred name, currency) that show in the playground's memory tab and are recalled in later sessions of the demo.** — The presenter says the agent writes the values with a tool call. In a later question it combines the stored name and currency preference with the earlier spending figure. The demo does not say how memory persists beyond the running process. ([2:54](https://youtu.be/_dG8iZgmicQ?t=174))
- **MCP servers plug in through Mastra's MCP client: the tools from a server (Firecrawl in the demo) are fetched with getTools and added to the agent.** — The resulting tool list appears in the playground and is used to scrape websites. Mastra's API docs are served as Swagger, and a Mastra client can call an agent programmatically on the server port instead of using the playground. ([3:20](https://youtu.be/_dG8iZgmicQ?t=200))

## Techniques
- **Minimal Mastra agent** — Scaffold with the Mastra CLI, delete the sample weather agent, workflows and weather tool. Create a new agent file (financial agent in the demo) that instantiates the Agent class with a name, a model from Mastra's supported list, and instructions as the system prompt. In index.ts, import Mastra from Mastra core, export a Mastra instance and pass the agent into it. Run the dev script and open the playground. The import paths are not spoken in the video. *When:* Starting any new Mastra project, or checking an agent's behaviour interactively before wiring it into an app.
- **Custom tool with zod output schema** — Create a file in the tools folder. Use createTool from Mastra core with an id, a description the model reads for tool selection, an outputSchema built with zod, and an execute function. The demo's execute returns fixed fake data. Add the tool to the agent's tools field; it then appears in the playground tool list. *When:* Giving an agent a typed capability it should call instead of guessing, such as a data lookup. The demo uses fake data, so swap in a real data source.
- **Persistent chat memory** — Create a Memory instance from Mastra memory with a storage field. The demo uses the LibSQL store class from the Mastra LibSQL package, with the store kept in memory. Attach the memory object to the agent's memory field. Chats are then saved and visible in the playground. Test with a follow-up question that depends on the previous answer. *When:* Multi-turn agents where follow-up questions reference earlier answers. The in-memory store in the demo is not durable; Mastra supports other storage options (not shown).
- **Working memory template** — Enable working memory with a template describing the fields to keep (the demo uses preferred name and preferred currency). The agent writes these values through a tool call and they show in the memory tab of the playground. *When:* Storing a small set of structured user preferences or facts that should be recalled and reused in later answers.
- **Adding MCP server tools to an agent** — Import the MCP client from Mastra's MCP package. Configure a server (the demo uses the Firecrawl MCP server). Call the client's getTools function and pass the result into the agent's tools field. The tools then show in the playground and the agent can call them, for example to scrape a website. *When:* Reusing an existing MCP server's tools in a TypeScript agent instead of writing wrappers.
- **Calling a Mastra agent from code** — Mastra serves Swagger docs for its API endpoints; a raw call returns hard-to-read JSON. Create a Mastra client pointing at the server port, fetch the agent by name, and call it with a prompt. The server port can be changed in the Mastra config (the demo says this is possible; the config key is not shown). *When:* Integrating an agent into an application or script once it works in the playground.
