> BMAD Method tutorial: role-based agents (PO, scrum master, dev, QA) shard a PRD and architecture doc into epics and stories with approval gates, run in Cursor or Claude Code.

## Summary
The host walks through the BMAD Method (Breakthrough Method for Agile AI-Driven Development), an agile workflow packaged as IDE rule files that assign roles such as product owner, scrum master, developer and QA. He first brainstorms and writes a PRD and an architecture doc in a general chat model, using a bundled team file from the BMAD repo, then drops both into a docs folder. The PO agent shards these documents into chunks, and the scrum master generates epics and stories, each starting in draft status. A human manually changes a story to approved, the dev agent implements it and marks it ready for review, and a QA agent flips it to done. He runs each agent in a fresh chat to limit context growth and shows how the scrum master builds a story packet with insights from the previous story. The video ends with the per-project npx installer and its choices. The demo is a single to-do style iOS productivity app, built as 4 epics and 16 stories.

## Techniques
- **Two-document spec bootstrap** — Brainstorm in a general chat model, then run the PRD and architecture workflows (five PRD stages; interactive architecture doc). Save outputs as docs/prd.md and docs/architecture.md (the one manual folder step). Start from the team file in the BMAD repo's dist/teams folder (teamfullstack.txt), uploaded to the chat with an instruction to stay in character. *When:* Before any code, when you want features, stack and components written down so the agents have an explicit spec to shard.
- **Shard then epic/story decomposition** — Activate the PO agent (Cursor: type PO and select it; Claude Code: slash command), run its shard command with the paths to prd.md and architecture.md. Then in the scrum master role, run draft; if epics are missing, accept the suggested epic generation by typing 1. Stories are numbered by epic, for example 1.1, 1.2; he ended with 4 epics and 16 stories. *When:* When a PRD is large enough that one agent session cannot hold all of it; sharding makes it feasible to work one piece at a time.
- **Manual approval gate via story status field** — Stories are created with status draft. A human edits the status line in the story file to approved. The dev agent only builds approved stories and sets status to ready for review on completion. A review/QA agent checks the story's required items in the code and changes the status to done. *When:* When you want a human checkpoint before an agent starts a unit of work, and a separate verifier (not the builder) to decide it is complete.
- **Fresh chat per agent role** — Open a new chat for each agent (PO, scrum master, dev, QA) and for each story, so large spec files do not accumulate in one context. *When:* Any time agents load big shared docs; the speaker argues this avoids confusion and context-length problems.
- **Story packet handoff** — When drafting the next story, the scrum master collects insights from the previous completed story plus architecture context into one packet, which the next dev session receives. *When:* Sequential story implementation where later stories depend on decisions made in earlier ones.
- **Learn an unfamiliar repo by feeding it to an LLM** — Take the GitHub repo URL and replace github with gitingest (the speaker's wording); download the text rendering; upload it to Claude and ask how the workflow runs. *When:* When you want a quick, step-by-step explanation of a framework before installing it.
- **Per-project install with npx** — Copy the npx command from the BMAD GitHub README and run it in the terminal of each project. Answer prompts: project full path; option 1 Install BMAD Agile Core System (creates .bmad core); shard PRD = yes; shard architecture = yes; select IDEs (speaker chose Cursor, Claude Code, Windsurf); pre-built web bundles = no. Restart the IDE if rule files do not show up. *When:* To add the workflow to a specific project; it is not a global install, so repeat it per project.
- **Asterisk commands and role switching** — Inside an agent session, an asterisk prefix triggers built-in commands for the agent (for example the brainstorm command). Role commands switch personas, such as PM for the product manager, then create doc for the PRD workflow. Exact command names are partly garbled in the captions. *When:* Driving each BMAD role in order during the planning phase.

## Hot takes
- The 'ultimate' title and 'works across all IDEs, no matter how big' claims are hype: the only demo is one small iOS to-do style app, and only Cursor is shown running the workflow.
- The real value shown is the process: document handoffs, a status field as the coordination protocol, and fresh contexts. The tooling itself is less important than the discipline.
- The human still has to approve each story by hand, so the workflow is semi-autonomous; the narrator presents it as the entire process being 'handled by AI agents'.
- The speaker says BMAD fixed the lack of documentation in his earlier Claude Code framework, which is a fair point about docs but says nothing about outcome quality.
