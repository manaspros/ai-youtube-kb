> Soheil Feizi (RELAI) argues agents should learn from production failures only through verifiable updates: turn logs into replayable test environments, route fixes to model, harness or memory, and gate each change with regression tests. Second half is a product demo.

## Summary
Soheil Feizi, founder and CSO of RELAI and a University of Maryland professor, frames continual learning for agents as two problems: getting feedback when there is no benchmark, and acting on that feedback. He says a learning change can land in three layers (model weights, harness such as prompts, skills, tools and workflow code, or memory), and the best update is the smallest durable change at the right layer. He argues session logs plus feedback are a single observation and must be lifted into a replayable learning environment with simulated tools, synthetic users and evaluators before any fix can be tested. He proposes "verifiable continual learning" built on four principles (replayability, holisticness, lifelongness, efficiency) and a three-part gate: an executable test of the failure, a measured before/after delta, and a regression run over prior tests. The second half demos RELAI's product, which runs this loop on a fictional support agent and reports a 78% baseline rising to 97% with about 10% average gain from one loop; these vendor numbers are internally inconsistent and unverified.

## Key ideas
- **Agents can learn at three layers: model weights, harness, and memory** — Model layer means changing weights; harness layer means prompts, skills, tools, code and workflow around the LLM; memory layer means session or persistent memory. The speaker names two core problems: getting feedback (how do we know the agent did badly and what it should have done) and acting on it (which layer and how). ([1:04](https://youtu.be/2IxD9OB3XuQ?t=64))
- **Production has logs but no benchmark, so feedback must be generated** — Dev teams use benchmarks with evaluators. In production there are only session logs, so feedback comes from automated judges (other models, code, or the agent critiquing its own log) or from sparse expert review. Automation scales; expert review is small but carries the true target behavior. ([3:31](https://youtu.be/2IxD9OB3XuQ?t=211))
- **Logs plus feedback are one observation, so they must become replayable environments** — A learning environment is a simulation that can be rerun. It needs decisions on real vs mock tools (and mock data), synthetic users inferred from the logs, and evaluators that define success. The output is executable, so agent candidates can be compared inside it. ([4:55](https://youtu.be/2IxD9OB3XuQ?t=295))
- **Make the smallest durable change at the right layer, cheapest layer first** — The speaker ranks cost: weight updates (SFT, RL post-training such as DPO, GRPO, RLVR, or LoRA) are expensive; harness edits (GEPA-style prompt search, trace-to-harness) are moderate; memory writes are cheapest and fastest but usually unverified. ([6:26](https://youtu.be/2IxD9OB3XuQ?t=386))
- **Trace-to-harness and memory writes are hard to verify, and prompt search needs evaluators** — Asking a coding agent to read a log and edit the harness is vibe-based: the fix may not be tested on that sample or others, so hidden regressions can appear. GEPA-style mutate-score-keep search is testable but needs benchmarks and explicit evaluators. Memory writes (facts, corrections, distilled skills) have the same testability gap. ([8:51](https://youtu.be/2IxD9OB3XuQ?t=531))
- **Verifiable continual learning uses a three-step gate: executable test, measured delta, regression suite** — Each failure becomes a replayable test. The update is scored before and after on that test. Prior tests must still pass. The speaker defines the goal as every fix proven to help and proven to break nothing that already worked. ([11:21](https://youtu.be/2IxD9OB3XuQ?t=681))
- **One failure often has several causes and several repairs** — His example: an agent cites a stale policy and skips a required escalation. Causes could be a stale memory fact, an unoptimized prompt, a tool that does not normalize the policy, a workflow missing an escalation gate before refunds, or a weak model. The fix should be routed to the layer that explains the failure. ([12:41](https://youtu.be/2IxD9OB3XuQ?t=761))
- **Regression awareness belongs inside the optimizer, not as a post-hoc check** — Optimize the new failure subject to no regression on the k past learning environments. The speaker says this must not scale linearly with k as it grows, so the efficiency of the loop matters. ([13:51](https://youtu.be/2IxD9OB3XuQ?t=831))
- **The loop's output is a reviewable version update, like a pull request** — RELAI's loop: signals (logs, feedback, or instructions) become replayable environments; root-cause analysis routes fixes to memory, model or harness; regression-aware optimization runs; the result is a reviewable agent version explaining what changed and why. ([15:16](https://youtu.be/2IxD9OB3XuQ?t=916))
- **Instruction-only bootstrap: describe a behavior and generate the test environment with no logs** — Example: a rude, adversarial caller. One command produces personas, intents, mock or real tools and evaluators. The baseline scored 78%, two evaluators were weak, and a few optimize rollouts raised the score. Takeaway: continual learning is not necessarily fine-tuning, and production logs are not learning environments until converted. ([19:08](https://youtu.be/2IxD9OB3XuQ?t=1148))

## Techniques
- **Log-to-replayable-environment lift** — From one session log plus feedback, infer tool behavior (real or mock tools, with mock data drawn from the log), synthetic user personas and intents, and evaluators that define success. Rerun candidate agents in that environment. *When:* Production agent with logs but no benchmark, where you want to test any fix against the failure pattern.
- **Instruction-first environment bootstrap** — Write a plain-language behavior description (for example, a rude or adversarial caller). Generate personas, intents, tools and evaluators from it in one step. Measure the baseline, then optimize with a set number of rollouts. *When:* No logs exist yet and you want to probe or harden a behavior before release.
- **Three-gate fix verification** — Turn each failure into an executable test. Score the candidate change before and after on that test (measured delta). Rerun the accumulated prior tests and reject the change if any prior test regresses. *When:* Accepting any agent update: prompt, skill, memory write, tool change or weight update.
- **Layer routing by smallest durable change** — Root-cause the failure, list candidate layers (stale memory fact, prompt, tool normalization, workflow gate, model), and pick the smallest durable fix, trying cheaper layers first. *When:* Triaging agent failures so you do not reach for fine-tuning by default.
- **Regression-aware optimization** — Put no-regression on past environments as a constraint in the search loop itself, rather than checking after the fact. Keep the cost of the check from growing linearly with the number of past environments. *When:* Many accumulated test environments and frequent updates.
- **Regression trap in benchmark design** — Include tasks that a naive fix to the latest failure is likely to break (his example: generosity beyond refund thresholds), so overfitting shows up in the score. *When:* Building a regression suite for a tool-using support or policy agent.
- **Reviewable change proposal as output** — Have the learning loop emit a versioned agent update that a human reviews like a pull request, with a note on what changed and why. *When:* You want agent self-improvement with human sign-off before deployment.

## Hot takes
- Production logs are not learning environments until they are turned into replayable ones.
- Asking a coding agent to edit the harness from a single log is untestable and can cause hidden regressions.
- Continual learning is not necessarily model fine-tuning; many useful updates happen in the harness and memory layers.
- The frontier is regression-aware continual improvement: verify that fixing a new failure does not break old ones.
