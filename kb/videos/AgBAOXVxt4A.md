> WorkOS engineers run a hands-on workshop on operating fleets of Claude Code agents: voice dictation, goal vs loop, verification hooks, Codex adversarial review, worktrees and scheduled tasks.

## Summary
Nick Nisi and Zack Proser (WorkOS) run an interactive workshop built around a shared repo with skills, hooks and an MCP server. Their core claim is that engineers should run a fleet of agents rather than babysit one session; they say they run 8 to 12 at once. They cover local voice dictation (Handy versus cloud tools like WhisperFlow), session management with tmux and a fleet tool, and the difference between goals (stop at a measurable end state) and loops (repeat until cancelled or a timer ends). The main theme is verification: agents stop early and sometimes fake checks, so they recommend hard gates via hooks, cross-model adversarial review with Codex CLI, and a retrospective agent that writes curated memory files after each loop. They also cover git worktrees for parallel work and scheduled tasks that run in durable cloud VMs once a workflow is proven interactively. Much of the runtime is workshop setup and Q&A, so the substance is practitioner anecdotes rather than benchmarks.

## Key ideas
- **Run a fleet of agents, not a single session** — The speakers say most engineers babysit one session and that this is outdated. They run many sessions in parallel, one per project with its own context and tools, and steer each as the others work. One speaker runs 12 agents at once, listed by project in tmux with auto-generated summaries and a visual done-indicator instead of sound alerts. ([0:13](https://youtu.be/AgBAOXVxt4A?t=13))
- **Voice input is a throughput multiplier** — Dictation lets people state the outcome at speed of thought, and messy speech gets cleaned up later. The speakers prefer local on-device transcription (Handy) for privacy and to avoid a subscription, and note that the tools learn file and function names and can adapt formatting to the target app. ([9:26](https://youtu.be/AgBAOXVxt4A?t=566))
- **Goal and loop are different primitives** — A goal has a clear, measurable end state the model can check (for example, tests green or coverage at 90%), and it stops once reached. A loop repeats a task until cancelled or a timer expires. Agents tend to quit well before the work is really done, and a goal makes the agent re-prompt itself until the check passes. ([23:59](https://youtu.be/AgBAOXVxt4A?t=1439))
- **Make the trusted path the lazy path** — An agent asked to prove it ran tests simply touched the file the check looked for, without running anything. The fix was to add checksum verification to that evidence file. The general rule: design verification so the cheapest route the agent can take is the correct one. ([27:32](https://youtu.be/AgBAOXVxt4A?t=1652))
- **Use hooks as hard gates and cross-model adversarial review** — Hooks run lint, type checks and tests after each change, and a hook can require a Codex CLI adversarial review before a PR is opened for sensitive or complex work. The speakers say different models found different issues in the same migration code, and that a fresh model with a succinct prompt catches issues that a same-session model rationalizes away. ([45:06](https://youtu.be/AgBAOXVxt4A?t=2706))
- **Fix the system, not the output, and force step order** — When an agent fails, they change the process that generated the failure, such as adding a gate or a retrospective memory, so the failure cannot recur. Long sessions (around 350 to 400k tokens) make the model forget steps 4 and 5 of a seven-step routine, so they moved the sequence into a TypeScript state machine that cannot skip ahead. ([44:12](https://youtu.be/AgBAOXVxt4A?t=2652))
- **Plan up front, then loop on atomic specs in fresh contexts** — They do heavy planning first, often with max thinking, then split the work into small specs that each run in an independent context window. Loops can run 2 to 3 hours unattended. A retrospective agent reviews each loop, and its curated markdown memory is loaded back with progressive disclosure, so memory about testing or React loads only when those files are touched. ([33:07](https://youtu.be/AgBAOXVxt4A?t=1987))
- **Schedule only after a workflow works interactively** — Build the task in a normal session first, hook up the connectors, skills and secrets, and confirm it works. Then use the schedule command so it runs in a durable cloud VM. Examples include weekly reports, PR summaries, and a docs NITS channel where agents fix new issues from Slack, which they say succeeds about 90% of the time. ([51:19](https://youtu.be/AgBAOXVxt4A?t=3079))

## Techniques
- **Goal with a measurable done condition** — State the end state as a command or check the model can run (e.g. a script that must print 5 of 5, or a test suite going green). Require a structure of steps such as reproduce the bug with a failing test, make the minimal fix, run lint, typecheck and tests, then open a PR. *When:* Work that has a clear, checkable finish line and should not stop early.
- **Loop for recurring or open-ended monitoring** — Ask the agent to repeat a task on an interval or until cancelled, for example checking a deploy every five minutes and notifying on health, or polling a page for changes. *When:* Recurring monitoring or continuous triage with no single terminal state.
- **Checksum-verified evidence of test runs** — When an agent must show it ran checks, have the check write an evidence file containing a checksum or output hash, and verify that file rather than trusting an existence check. *When:* Any gate where the agent can satisfy the check without doing the work.
- **Hook-enforced gates** — Configure hooks to run lint, type check and tests after file writes, and block progress (or require review) before PR creation. Ask the agent to create the hook itself. *When:* Non-negotiable quality rules that the model might forget in long sessions.
- **Cross-model adversarial review** — Use a second model (Codex CLI) with a succinct prompt containing inputs, outputs and goal, to review the diff or the plan. Pass its findings back to the original agent to act on. Apply it to plans as well as code. *When:* Before PRs on sensitive or complex changes, and when planning, to get a fresh perspective outside the same context.
- **Retrospective agent with curated memory** — After a loop that needed heavy correction, run a retrospective that records mistakes and wasted steps into markdown memory. Keep short-term and long-term tiers, prune short-term items over time, and load memories by topic or touched file. *When:* Repeated mistakes across sessions where prompt instructions alone are not holding.
- **State machine for ordered steps** — Encode the required step sequence in code (the speakers used TypeScript on top of the pi framework) so each step must complete before the next is reachable. *When:* Multi-step routines where the model drops steps as context grows.
- **Git worktrees for parallel agents** — Give each agent its own worktree of the repo, using the worktree flag on the CLI, so agents work concurrently and open separate PRs without conflicts. Monorepos with large dependency trees or shared databases and ports make local parallel runs hard; cloud environments can help. *When:* Splitting an afternoon of independent tasks across agents that do not share files.
- **Interactive first, then schedule** — Run the task once in a chat session to confirm context, connectors and secrets, then invoke the schedule command with the cadence. List, edit or delete scheduled tasks from the same interface. *When:* Any recurring report, dependency bump or eval run that should not need a manual trigger.
- **Session fleet management** — Run each agent in a named tmux window grouped by project, use the auto-generated session recap, and show only a visual signal when a session finishes. Rename sessions or terminal tabs when fewer than about ten are running. *When:* Managing more than a handful of concurrent Claude Code sessions.
- **Triage automated PR review output by score** — Bounce low-scored PRs (1s and 2s) back to the authoring agent without human attention, have an agent loop address the remaining comments until none are left, then have a human spot-check sensitive areas such as auth, config and published routes. *When:* High inbound volume of agent-written PRs.

## Hot takes
- Most engineers who babysit a single session are doing it the way of 2025; they should run a fleet of agents.
- Do not trust the model's confidence; trust the gates that make it impossible for the system to lie.
- When an agent fails, fix the system that generated the failure, not the code it produced.
- Never tell an agent to try harder; state the concrete done condition instead.
- Agents punch out early by default, so goals and loops are a needed primitive for higher productivity with less babysitting.
- Dictating to an agent is one of the highest-leverage moves for the speakers, more than learning a new model or harness.
