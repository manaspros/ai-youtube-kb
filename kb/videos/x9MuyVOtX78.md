> Walkthrough of DFlash, a diffusion-drafter speculative decoding method merged into llama.cpp for Qwen 3.6, with local deployment steps and a self-run benchmark that checks whether the "lossless" claim holds.

## Summary
Kai Explains examines DFlash, a speculative decoding method recently merged into llama.cpp for the Qwen 3.6 family, and tests its claim of large speedups with no quality loss. The video first explains the bottleneck: local decoding is memory-bandwidth bound, so verifying a block of tokens costs about the same wall-clock time as generating one. It then argues that EAGLE-3's autoregressive drafter has to stay tiny to remain cheap, which caps acceptance at around three tokens per cycle. DFlash replaces that with a diffusion drafter that fills a 16-token block in one pass and feeds the target model's hidden signal into every layer instead of only at the start. The speaker deploys it locally via a llama.cpp server in Docker and benchmarks it with greedy decoding at concurrency 1 on an RTX 6000 Pro, using NVIDIA's AIPerf for throughput and MATH-500 for answer agreement. Reported results: about 38 tok/s baseline versus over 400 tok/s on one 3.8-billion-parameter build, a roughly 1% answer difference across 100 MATH-500 problems, 3.75x on tokens overall, and 4.4x at a 36k-token context. The honest costs are about 4 to 5 GB of extra VRAM, a silent clamp of draft tokens at 15, and untested behavior at high concurrency. The verdict is that it is close to free speed for single-user local workloads such as code, math and long reasoning.

## Key ideas
- **Decoding on a local GPU is bound by memory bandwidth, not compute, so verifying a block of tokens costs roughly the same as generating one. That idle time is what speculative decoding exploits.** — Per-token latency is (drafting time + verification time) / tau, where tau is the average number of accepted tokens per cycle. Methods differ only in making drafting cheaper or drafts more accepted. ([1:25](https://youtu.be/x9MuyVOtX78?t=85))
- **EAGLE-3 hits a ceiling because its autoregressive drafter costs grow with every drafted token, forcing the drafter to stay about one transformer layer and limiting acceptance to roughly three tokens per cycle.** — Adding budget past that point barely raises acceptance, while cost keeps climbing, and one wrong token invalidates everything after it. ([2:49](https://youtu.be/x9MuyVOtX78?t=169))
- **A diffusion drafter breaks the ceiling because its cost does not scale with block size: it fills a block of mask slots in a single pass.** — In one comparison the diffusion drafter produced 108 tokens where the autoregressive drafter produced 21, with the same number of steps. ([2:49](https://youtu.be/x9MuyVOtX78?t=169))
- **DFlash's real innovation is where the target model's signal is injected. EAGLE hands the drafter the hidden state once at the start, so it decays through layers. DFlash pins it to every layer, which lets the drafter go deeper without losing signal.** — A deeper drafter guesses better, so the design trades drafter depth for accuracy instead of being stuck with a shallow, weak one. ([2:49](https://youtu.be/x9MuyVOtX78?t=169))
- **Acceptance is roughly equal to MTP's, so the win is wall-clock time. MTP needs seven sequential passes for seven tokens, while DFlash proposes a 16-token block in one pass.** — Acceptance tau is quoted as 67 for MTP versus 73 for DFlash, which the speaker calls close enough to tie. Output is the same, at a fraction of the cost. ([4:12](https://youtu.be/x9MuyVOtX78?t=252))
- **The lossless claim survives a head-to-head check, but only in a narrow sense, with greedy decoding on one machine at concurrency 1.** — On MATH-500 the answers were nearly identical, a 1% difference across 100 problems, and throughput was 3.75x. The speedup grows with context: 4.4x at 36k tokens, where most models slow down. ([5:37](https://youtu.be/x9MuyVOtX78?t=337))
- **The costs are real: about 4 to 5 GB of extra VRAM for the drafter, a silent clamp of draft tokens at 15, and an untested regime at high concurrency where the bandwidth argument can flip.** — The speaker's guidance: use it for low-concurrency local or single-user serving of code, math and long reasoning. Wait for concurrency numbers before changing a high-batch production fleet. ([6:55](https://youtu.be/x9MuyVOtX78?t=415))

## Techniques
- **Lossless-check benchmark protocol for speculative decoding** — Use greedy decoding (temperature 0, top-k 1) and one request at a time so results are reproducible. Measure throughput with NVIDIA AIPerf across input and output lengths from 512 up to 36,000 tokens. Check correctness by running the base model and the speculative config head-to-head on MATH-500 and comparing answers, not just speed. The video does not show exact AIPerf command lines. *When:* Before claiming a speculative decoding setup is lossless or worth deploying. Benchmark at the concurrency you actually serve, not only at concurrency 1.
- **Deploy DFlash locally with llama.cpp server in Docker** — Run a llama.cpp server container that loads the DFlash target model together with its matching drafter. The drafter must be the one the llama.cpp merge added, since loading it is the step that cannot be skipped. Start it with the Docker plugin's run-service action, or with a single command if the plugin is absent. The shipped config already sets context length, model path and drafter path. The video does not show exact flags or file names. *When:* When running a Qwen 3.6-family model locally on one GPU and single-user or low-concurrency latency matters, such as code, math or long reasoning.
- **Side-by-side leaderboard of baseline, MTP and DFlash** — Use the same setup that ships a plain baseline config, an MTP config and a DFlash config. Run all three under the same greedy benchmark and compare them on one table. *When:* To check whether a new speculative method actually beats the existing ones on your hardware instead of trusting a vendor chart.
- **Tune drafter quantization and draft-token count** — A less quantized drafter guesses more accurately but costs more per step. A smaller quantized drafter runs faster but produces weaker drafts. Set the draft token count alongside it. The current DFlash implementation caps the draft count at 15 and clamps silently above that. *When:* When the default drafter is too slow or accepts too few tokens on your workload, and VRAM headroom allows a different quantization.
- **Decide by whether the GPU is idle at your concurrency** — Speculative decoding helps when the GPU is waiting on memory. Estimate the expected gain from per-token latency = (draft + verify time) / tau. Expect the gain to shrink as concurrent users saturate the GPU, so test concurrency sweeps before changing a production fleet. *When:* Choosing between speculative decoding and plain autoregressive serving for a given workload, or deciding whether to wait for high-concurrency numbers.
