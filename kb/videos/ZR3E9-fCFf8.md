# What Would It Cost to Run GLM 5.3 Locally?

> Kai works through the memory and dollar math for running GLM 5.3 locally: MoE active params don't reduce memory, quantization sets the footprint, and renting or the API beats buying hardware for most teams.

## Summary
The speaker explains why a 743B-total, roughly 40B-active mixture-of-experts model needs all of its weights resident in memory, so the active count only sets speed. He lists the GLM weight footprints at BF16, FP8, INT4 and 2-bit dynamic quantization. He then walks through hardware options: a 512 GB Mac Studio M4 Ultra (solo use, 3 to 6 tokens/s), consumer GPUs with CPU offload (single-digit tokens/s), and H100, H200 and B200 nodes sized for INT4, FP8 and 1M context. Rental and purchase costs follow, with a break-even estimate of 150 to 200M output tokens per month for a team. He notes that GLM 5.3 weights were not yet public, with the API and GLM coding plan as the only access, and recommends a hybrid setup where local models handle private, high-volume work and frontier API calls handle heavy tasks. Most benchmark and price figures are quoted without sources, and the video ends with a consulting plug.

## Key ideas
- **MoE active parameters set compute speed, not memory** — Only about 39 to 40B of GLM 5.3's 743B parameters are active per token, but the router can pick different experts for every token, so all 743B must stay in memory. The speaker says he once misread the active count as the memory need. ([1:28](https://youtu.be/ZR3E9-fCFf8?t=88))
- **Quantization level determines the weight footprint** — Weights for the 743B base come to about 1.5 TB in BF16, about 755 GB in FP8, about 372 GB in INT4, and about 239 GB at the most aggressive 2-bit dynamic quantization. GLM 5.3 reuses the 5.2 base, so these figures are expected to carry over until 5.3 checkpoints are published. KV cache and runtime overhead are not included. ([2:50](https://youtu.be/ZR3E9-fCFf8?t=170))
- **A 512 GB Mac Studio is the cheapest credible local option, with limits** — A maximum-config M4 Ultra Mac Studio (512 GB unified memory, roughly $10k to $12k) fits the 2-bit quant at about 3 to 6 tokens per second, which the speaker compares to human reading speed. M2 and M3 Ultra machines and the 256 GB M4 Ultra are too small. He frames this as a solo-developer setup, not a team deployment. ([5:10](https://youtu.be/ZR3E9-fCFf8?t=310))
- **Consumer GPUs with CPU offload are impractical for this model** — RTX 5090 (32 GB), 4090 (24 GB) and 3090 setups would need about four 3090s plus 192 GB of system RAM and MoE offload tuning for the 2-bit model. PCIe bandwidth limits output to single-digit tokens per second. ([6:32](https://youtu.be/ZR3E9-fCFf8?t=392))
- **GPU node sizing follows from the quantization footprint** — Four H100s (320 GB) fall short of INT4 (372 GB), so at least five are needed before KV cache. Eight H100s (640 GB) give INT4 with some headroom but not the full 1M context. Eight H200s (1,128 GB) are the stated production minimum for FP8, and eight B200s (1,536 GB) are needed for the full 1M context. ([6:32](https://youtu.be/ZR3E9-fCFf8?t=392))
- **Rental and API costs favor renting or the API at normal volumes** — An 8x H200 node at about $3.50 per GPU-hour is about $28/hour, or about $20k per month running 24/7, before networking, storage and engineering. Eight B200s at a roughly $8 midpoint come to about $46k per month. The speaker estimates self-hosting pays off only at about 150 to 200M output tokens per month for his team, assuming high utilization. ([7:49](https://youtu.be/ZR3E9-fCFf8?t=469))
- **Weights were withheld at launch, so the API is the way to evaluate now** — Unlike GLM 5.2, which shipped MIT-licensed weights within days, GLM 5.3 was API and coding-plan only at launch. Z.ai cited cybersecurity capability and said weights would be staged after a safety review, about two weeks out. The speaker recommends testing through the API before planning hardware. ([10:28](https://youtu.be/ZR3E9-fCFf8?t=628))
- **Recommended end state is a hybrid of local and API models** — Local models handle private, repetitive, high-volume work that should not leave the premises. Heavy frontier-scale tasks go to the API. The advice is to rent for a couple of weeks, run real workloads, measure, and only then consider buying. ([11:54](https://youtu.be/ZR3E9-fCFf8?t=714))

## Techniques
- **Resident-memory estimate for MoE models** — Multiply total parameters (not active) by bytes per parameter for the chosen precision: 2 bytes BF16, 1 byte FP8, 0.5 byte INT4, about 0.3 bytes for 2-bit dynamic. Then add KV cache and runtime overhead on top. For GLM 5.x, 743B gives about 1.5 TB, 755 GB, 372 GB and 239 GB respectively. *When:* Before buying or renting hardware for any MoE model. Use it to rule out machines whose memory is below the weight footprint, even when the active-parameter count looks small.
- **GPU count from footprint with headroom** — Divide the weight footprint by per-GPU VRAM, round up, and add margin for KV cache and runtime. Example from the talk: 372 GB INT4 on 80 GB H100s needs at least 5 GPUs before overhead, so 8 GPUs (640 GB) is the practical minimum. Check context length separately, since long context needs more KV cache. *When:* When sizing a multi-GPU inference node for a given model, precision and context window.
- **Rent-before-buy evaluation with cost break-even** — 1) Run the model through its API or coding plan on real tasks. 2) Measure tokens per month. 3) Compare API spend with monthly node cost (GPU hourly rate x GPU count x ~720 hours, plus networking, storage and engineering time). 4) Only buy if the break-even volume is within your real usage. The speaker's team break-even was about 150 to 200M output tokens per month. *When:* Before committing to local or self-hosted inference for a frontier-scale open-weight model, especially when utilization may be low.
- **Hybrid local-plus-API routing** — Route private, repetitive or high-volume requests to a local model. Send hard, frontier-level tasks to a hosted API. Keep the routing rule explicit so the local tier can be measured on its own. *When:* When some workloads must stay on-premises for data reasons, and others need the strongest available model and are low-volume.

## Hot takes
- Local hosting of a frontier-scale MoE only makes sense at very high, steady token volume. For most teams the API or a short rental is the better choice.
- The active-versus-total parameter confusion is the most common mistake when sizing local MoE hardware.
- The Mac Studio is the cheapest credible local path for a large model, but it only suits a single developer with patience.
