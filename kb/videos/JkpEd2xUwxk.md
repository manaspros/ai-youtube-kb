> Better Stack's changelog demo of its MCP server, letting Claude Desktop manage incidents, on-call, status pages and query ClickHouse telemetry, plus the setup steps and credential scoping.

## Summary
This is a 7-minute vendor changelog walkthrough of the Better Stack MCP server, shown through Claude Desktop. The presenter uses natural-language prompts to list on-call calendars, find unacknowledged incidents, read incident timelines, draft a status-page update, acknowledge and resolve an incident, and add a comment. The second half covers telemetry: the model lists log sources, calls a tool that returns ClickHouse query instructions, runs queries for recent errors and HTTP 500s, and discovers available metrics. The setup section shows how to add a remote MCP config to Claude Desktop, create a Better Stack API token and a scoped ClickHouse connection, and pass those credentials as environment variables. The presenter recommends including the ClickHouse connection details because the model sometimes hallucinates the username or password on follow-up queries. No benchmarks or quantitative results are given.

## Key ideas
- **An MCP server can turn an incident-management product into LLM-operable tools: list on-call, list unacknowledged incidents, fetch timeline, acknowledge, resolve, comment.** — The demo chains these tool calls from plain-English prompts, with no UI clicks in the vendor app. The presenter uses this for the full incident loop. ([0:00](https://youtu.be/JkpEd2xUwxk?t=0))
- **Status-page drafting is a multi-tool chain: the model lists status pages, fetches resources, finds the downtime on the affected monitor, then writes and posts the report.** — The presenter notes the report text is written by the LLM from tool-fetched data, then the incident is acknowledged. The result is checked on the public status page and in the incident view. ([1:00](https://youtu.be/JkpEd2xUwxk?t=60))
- **Telemetry querying depends on a schema-guidance tool. The model first lists log sources to get IDs, then calls a get-query-instructions tool before writing ClickHouse queries.** — The presenter credits this with letting the model build correct queries. The output is a summary of error breakdowns, observations and recommendations. ([3:06](https://youtu.be/JkpEd2xUwxk?t=186))
- **The model can write query examples as an artifact (recent vs. historical data, count by endpoint, hourly breakdown) that the user can run back through the MCP server.** — This is a text-to-query workflow where the model drafts SQL and then executes it through the same server. ([3:06](https://youtu.be/JkpEd2xUwxk?t=186))
- **Credentials should be supplied in the config, not left to the server. The presenter says the model sometimes hallucinates the username or password on follow-up queries.** — The MCP server can create its own ClickHouse connection if needed, but the presenter recommends passing the connection details so follow-ups are smoother. This is the speaker's experience, not a measured result. ([4:22](https://youtu.be/JkpEd2xUwxk?t=262))
- **Scope the database access the LLM gets: pick one cluster and one team's data, optionally set an IP allowlist, set an expiry, and note the purpose. The password is shown only once.** — The presenter uses a global API token for uptime and telemetry across teams, and a narrower ClickHouse connection limited to one team. Creating a new connection is needed if the password is lost. ([5:25](https://youtu.be/JkpEd2xUwxk?t=325))

## Techniques
- **Incident triage loop via MCP prompts** — Prompt in order: list unacknowledged incidents from today; fetch details and the incident timeline; draft a status-page update for the affected checkout flow; acknowledge; then mark resolved and add a comment such as 'bad rollout, fixed by new release'. Each step runs as one or more tool calls. *When:* Responding to a live incident where you want an LLM to draft updates and keep the incident record current, with a human approving the actions.
- **Schema-first text-to-query over logs** — Let the model call the sources-list tool to get the source ID, then the query-instructions tool that describes how to build the ClickHouse query, then run the query. Ask it to first list fields and metrics before writing queries. Ask for example queries (recent, historical, count by endpoint, hourly) and run the one you want. *When:* Querying an observability store like ClickHouse through an LLM, where a wrong schema guess produces bad SQL.
- **Remote MCP setup for Claude Desktop** — 1) Copy the remote-MCP example config from the Better Stack MCP docs (the docs also list a variant for HTTP-capable clients). 2) In Claude Desktop, open Settings, then Developer, then Edit Config, and paste into the JSON. 3) Create a Better Stack API token under Settings, then API tokens, choosing a global token. 4) In Telemetry, then Dashboards, then Connect remotely, choose ClickHouse HTTP client, select the cluster and team data, set an optional IP allowlist and expiry, add a note, and create the connection. 5) Save the username, password and host. 6) Put the API key and the user, password and host into the config's environment variables. The presenter names the API key variable as the 'production auth token', so check the exact key names in the docs. 7) Restart Claude Desktop. 8) Test with a prompt such as 'fetch my current on-call status'. *When:* Connecting Claude Desktop or another MCP client to Better Stack for incidents and logs.
- **Separate the uptime token from telemetry scope** — Use a global API token when the assistant needs uptime and telemetry across all teams (the presenter's recommendation). Use a per-team ClickHouse connection with an expiry and an IP allowlist for the query path. *When:* Deciding what access an agent should get to observability data.

## Hot takes
- Vendor changelog demo for its own product. The demo is of tool calls working, not of accuracy, latency or cost, so the claims are unmeasured.
- The most useful tidbit is the speaker's report that the model hallucinated ClickHouse credentials on follow-up queries. That is one anecdote, and it is the reason to pass connection details explicitly.
- Recommends a global API token for convenience. This gives broad read access to uptime and telemetry across teams, which conflicts with the narrow scoping the presenter recommends for ClickHouse.
- Quality capped at 2 for vendor pitch framing with thin measurable substance; the setup steps are still concrete enough to reuse.
