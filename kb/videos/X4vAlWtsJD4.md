> A walkthrough of how an AI Labs team now builds app prototypes: actors and constraints first, PRD and architecture files, a Next.js and Supabase prototype with mock data, then a backend added only when needed.

## Summary
The host reacts to a Jenny Wen interview (head of design for Claude at Anthropic, previously director of design at Figma) and argues the old Figma-handoff design process has been replaced. The stated reason the old process existed is that it guarded against building the wrong thing, and AI lowers the cost of that mistake. Per Jenny, designers went from spending 60-70% of their time mocking and prototyping to 30-40%, and vision horizons shrank from two to five years to three to six months. The team's replacement process starts with requirements written as actors (person plus goal) and constraints (what the agent cannot do or cost), not tool choices. A PRD-interviewer prompt produces a PRD markdown file, and a second prompt turns it into architecture.md with pages, modals and user flows. The agent then builds a Next.js app with Supabase and a mock-data prototype, using Anthropic's general frontend-design skill for the UI. Backend work comes after: an API spec is generated from the frontend, the Supabase MCP creates the schema and migrations, and a separate backend layer is added only for payments, notifications, rate limiting or analytics. The last stretch is a sponsored Warp Oz cloud-agent segment, and the video ends with a pitch for the paid AI Labs Pro templates.

## Key ideas
- **The old design-to-build handoff (requirements, then Figma mockup, then front-end conversion, with a back-end API spec written in parallel) was a ritual, and it existed to prevent building the wrong thing at scale.** — The host credits Simon Willison's writeup of Jenny's Berlin talk for the point that AI cuts the cost of building the wrong thing, so the research, personas and specs no longer need to act as protection. This is the host's inference from the talk, not a direct quote from Jenny. ([0:00](https://youtu.be/X4vAlWtsJD4?t=0))
- **Engineering speed changed first, and design had to follow. Engineers running several agents in parallel made the bottleneck engineering-unrelated, not engineering.** — Per Jenny, design time spent on mocking and prototyping fell from 60-70% to 30-40%. Vision work moved from two-to-five-year decks to three-to-six-month prototypes that point people in a direction. ([1:25](https://youtu.be/X4vAlWtsJD4?t=85))
- **Requirements did not change, and most teams still skip them. The host says bad requirements waste the whole build.** — A prototype needs only enough to look and feel real, so the host recommends starting with actors, not features or the tech stack, so the team can get a yes or no fast. ([2:32](https://youtu.be/X4vAlWtsJD4?t=152))
- **Define actors as people with goals, then check where their views split. Different actors need different first screens, and the split often shows up at a shared URL.** — Example: an admin sees a management panel and a regular user sees their dashboard at the same URL. ([2:32](https://youtu.be/X4vAlWtsJD4?t=152))
- **Give the agent constraints (what it cannot do, what it cannot cost), not a list of tools to use.** — The host says the constraints also make later technical decisions easier. ([2:32](https://youtu.be/X4vAlWtsJD4?t=152))
- **Planning artifacts are the spine of the build. A PRD file feeds an architecture.md (pages, modals, user flows), which feeds a persisted task list so the agent does not hallucinate.** — The host ties task persistence and structured files to the agent's ability to build complete prototypes, and says planning first matters for the context window. ([3:49](https://youtu.be/X4vAlWtsJD4?t=229))
- **Use Next.js with a backend inside it by default. Only add a separate Python service for heavy libraries or serious background-job orchestration.** — With Supabase, the frontend talks directly to the database in the early build, which removes a layer of complexity. ([6:37](https://youtu.be/X4vAlWtsJD4?t=397))
- **A dedicated backend API layer is added later, once the prototype already works. It is delegated to a cloud agent for payments, notifications, rate limiting and analytics.** — The sponsored Warp Oz cloud agent took about 15 minutes. Google auth and Stripe were still left to do. ## Techniques
- **Actor-first requirements** — Before any prototype or spec, list each actor as a person with a specific goal. Give each actor its own interface and first screen if their needs differ. Find the points where actors hit the same URL and see different views, then write those down. The host's example is a community platform with a member and a creator (admin) actor. Prompts were on screen only, so the exact wording is not in the transcript. *When:* At the start of any new app, before a PRD, architecture or tech stack is chosen.
- **Constraints instead of tool instructions** — Write the requirements as explicit limits on what the agent cannot do and what it cannot cost. Do not tell the agent which tools or stack to use. *When:* When writing the PRD, so later technical choices follow from the limits.
- **PRD interview prompt** — Run a prompt that makes the agent interview the user against the actor and constraint rules, then write the result to a PRD markdown file. This PRD is intentionally not a full technical spec. The prompt text was on screen only and is not in the transcript. *When:* Right after actors and constraints are written, to turn them into a PRD file that later stages read.
- **Layer prompt to architecture.md** — Give the agent the PRD and have it produce two outputs: the pages and data models for the prototype, and the user flows for each actor, covering actions and navigation. Save them as architecture.md. Describe interaction states and navigation here so the agent can implement them. *When:* After the PRD, before scaffolding, so every page and flow is planned up front.
- **Scaffold Next.js with Supabase, then apply a frontend-design skill** — Ask the agent to install a Next.js app with Supabase, the host's default stack. Before UI implementation, load Anthropic's general-purpose frontend-design skill from their blog, saved as a slash command or skill so the agent can call it. The host says this is why the UI looked good. *When:* When the team wants a polished UI without hand-tuning each screen.
- **Mock-data prototype for sign-off** — Build a working front end with mock data and no database, so the client can click through real flows and approve or reject it. Fixes at this stage take minutes, not days. *When:* Before any backend work, to get a yes or no on direction.
- **Task lists from architecture.md** — Have the agent turn architecture.md into a task list that persists across the session. The host says the structured files let the agent build a well-ordered list that reduces hallucination. *When:* During the build, once the architecture file exists.
- **API spec from frontend code plus PRD plus architecture** — Ask the agent to read the frontend code, PRD and architecture.md, then write an API spec of what the frontend needs from the backend. *When:* Before building any backend, so the backend is shaped by actual frontend needs.
- **Supabase MCP for schema and migrations** — Use the Supabase MCP, not hand-pasted SQL, to have the agent create the project, run the schema queries and apply migrations, based on the three documents (PRD, architecture, API spec). The host's general rule: prefer an MCP for any service the agent works with. *When:* When a Supabase-backed app needs its database set up from specs.
- **Front end talks directly to the database; backend only when needed** — Connect the frontend straight to Supabase in the early build. Add a Python service only when libraries or background-job orchestration require it; otherwise use the Next.js backend. Add a dedicated backend API layer later for payments, notifications, rate limiting and analytics. *When:* When choosing between a Next.js-only backend and a separate service.
- **Delegate the backend layer to a cloud agent** — Create an environment in a cloud agent orchestrator (the host uses Warp Oz, sponsored) and assign the backend API layer as a self-contained task. The host says it took about 15 minutes. *When:* For a well-defined backend task the agent can finish alone.
