> Teardown of Tencent's open-source agent memory plugin: folding tool output into disk files plus a layered memory store. Claims 33% to 50% pass rate with 61% fewer tokens, which the speaker partly rechecked.

## Summary
The video argues that coding agents degrade as the context fills with raw tool output, and that compaction, which replaces the session with a summary, throws away evidence. It walks through Tencent Cloud's open-source (MIT) memory plugin, which does two things: it writes full tool output to markdown files and keeps only a mermaid map with node IDs in the prompt, and it runs a four-layer consolidation memory (raw turns, atoms, scenes, persona) inspired by Tulving's episodic/semantic split. The headline benchmark (WideSearch) goes from 33% to 50% solved while tokens drop from 221M to 86M, but the gains shrink on harder benchmarks. The speaker checked some of the arithmetic and found one row that does not divide out. The persona-memory benchmark rises from 48% to 76%. The speaker flags open problems: per-turn memory injection breaks provider prompt caching (issue 120, unsolved), shared team memory creates a persistent prompt-injection surface, and the project has a managed cloud upsell. The verdict is to try it on a long local session but wait for independent reproduction before relying on it for a team.

## Key ideas
- **Compaction is lossy. The model is stateless and the loop re-sends the transcript, so the orange compact bar replaces the session with a paragraph and the agent then re-reads files and re-asks questions.** — The speaker frames this as the architecture working as designed, not a bug. Each re-sent copy is paid for, and the benchmark run cited was 200 questions at 221M tokens. ([0:00](https://youtu.be/W3yHP9_jYNk?t=0))
- **Bigger windows do not fix attention. Chroma's context-rot study across 18 frontier models found accuracy falls as input grows, starting well before the window is full.** — Attention is a fixed budget shared by every token. Noise next to the one relevant line dilutes it, so cutting noise raises the odds of the signal. Degradation was reported at 30 to 50% on some copy and find tasks, and a 200k window can start degrading around 50k tokens. ([1:13](https://youtu.be/W3yHP9_jYNk?t=73))
- **Fold tool output to disk, keep a map in context. Full logs (search results, stack traces, file dumps) go to markdown files. The prompt keeps a mermaid diagram of steps with an ID on every node, and the agent pulls raw text back by node ID when needed.** — The design constraint is to compress but never lose the path back to the evidence. The speaker contrasts this with a summary, which is lossy and cannot be reopened. ([2:36](https://youtu.be/W3yHP9_jYNk?t=156))
- **Compression scales with context pressure. The plugin folds mildly at about half the window, aggressively at 85%, and caps the map at 20% of the token budget so the map does not consume the space it saves.** — The thresholds are as stated in the video. The speaker did not show the implementation. ([2:36](https://youtu.be/W3yHP9_jYNk?t=156))
- **Gains shrink on harder tasks. On WeBench, the score moves from 58.4 to 64.2 with about a third fewer tokens. On a long financial-filings document test, it moves from 44 to 47.** — The speaker reads this as the approach helping less when the task is deep rather than wide, and says to hold on to that point. ([4:00](https://youtu.be/W3yHP9_jYNk?t=240))
- **Long-term memory as consolidation. The design follows Tulving's 1972 split between episodic and semantic memory, with forgetting as the compression step. Tencent implements this as four layers: L0 raw conversation, L1 atoms (facts, preferences, constraints) extracted every five turns, L2 scenes grouping atoms by project or task type, and L3 a persona rebuilt every 50 memories.** — Recall is top-down: the agent reads the persona first, drops to atoms for specific facts, and drops to raw L0 only when exact wording matters. ([5:26](https://youtu.be/W3yHP9_jYNk?t=326))
- **Preference-change memory is the case that matters. On PersonaMem, which tests whether the model tracks changed preferences across sessions instead of reciting old ones, the baseline scores 48% and the layered version 76%.** — The benchmark is the speaker's pick for the layers, and the video notes the numbers are vendor-published. ([5:26](https://youtu.be/W3yHP9_jYNk?t=326))
- **Generated memory fails silently. A stale auto-generated persona can drift for weeks, and a retrieval miss returns the wrong results with no error. A hand-written memory file never goes stale behind your back.** — The speaker treats this as the main trade-off against a hand-maintained markdown memory file. ([6:50](https://youtu.be/W3yHP9_jYNk?t=410))
- **Injecting memory at the front of the prompt every turn breaks prefix caching. Providers bill cached identical opening tokens at a fraction of the price, so changing the opening each turn can erase part of the saving. The maintainers have issue 120 open and unsolved.** — The speaker calls this the number that actually shows up on the bill, and says caching is where savings survive or do not. ([8:19](https://youtu.be/W3yHP9_jYNk?t=499))
- **Shared memory creates a persistent prompt-injection surface. Version 2 (July) moves memory into a team-shared asset (chat memory, skills, wiki, code graph) with owners and permissions. A poisoned memory now survives the session and is read by colleagues' agents, and the speaker cites an open issue where an unescaped search query lets user input rewrite the query.** — The speaker notes that per-session injection used to end with the session. ([8:19](https://youtu.be/W3yHP9_jYNk?t=499))
- **Verdict: install for long local sessions, wait for independent reproduction for team use. The speaker points out the project is MIT and runs locally on SQLite by default, but ships a Tencent Cloud vector backend and a managed memory service launched four days before the repo existed.** — The speaker asks viewers to report their own token delta and persona-file results. The open portability question is what happens to memory when switching frameworks or leaving the team. ([9:33](https://youtu.be/W3yHP9_jYNk?t=573))

## Techniques
- **Offload tool output to disk with an ID-indexed map in context** — Write full tool output (search results, stack traces, file dumps) to markdown files. Keep only a compact step diagram (mermaid, one ID per node) in the prompt. When an error needs detail, the agent fetches the raw text by node ID. Keep the map capped at about 20% of the token budget. *When:* Long agentic sessions where tool output dominates the context and compaction would lose needed evidence.
- **Pressure-scaled folding** — Fold context mildly at about 50% of the window and aggressively at about 85%, so compression responds to how full the window is. *When:* Any agent loop with a fixed context budget that needs to avoid the abrupt summarization step.
- **Layered consolidation memory** — L0 keeps raw turns. L1 extracts atomic facts, preferences and constraints every five turns. L2 groups atoms into scenes (project, task type). L3 holds a persona rebuilt every 50 memories. At recall time read L3 first, drop to L1 for specific facts, and drop to L0 only for exact wording. *When:* Cross-session assistants where preferences change over time and the agent must track the change rather than repeat an old answer.
- **Persona-first recall** — Put the cheap, summarized persona at the top of the context, and escalate to finer-grained records only when a specific fact is needed. *When:* Limiting per-turn token cost while keeping long-term user context available.
- **Keep the memory prefix cache-stable** — Keep the per-turn injected memory out of the leading prompt tokens so provider prefix caching keeps hitting. The speaker cites this as the open problem in issue 120 and does not show a fix. *When:* Any system that injects dynamic memory into prompts billed through a provider with prefix caching.
- **Treat shared memory writes as untrusted input** — Validate or review what gets written to a store that multiple agents read, and escape inputs used to build queries. The speaker raises the risk and does not describe a mitigation. *When:* Memory or skill stores shared across users or sessions.
- **Recompute vendor benchmark tables** — Divide the printed token columns to check the claimed percentage cuts, and check whether each row reconciles with the others. *When:* Evaluating vendor-published benchmark claims before adopting a tool.

## Hot takes
- Headline gains (33% to 50%, 61% fewer tokens) come from the vendor's own table. The speaker's recomputation found one row that does not reconcile.
- Gains shrink on harder, deeper tasks (+5.8 on WeBench, +3 on financial filings), so the approach may help less where it matters most.
- Per-turn memory injection at the front of the prompt breaks provider prompt caching (issue 120, still open). It can erase part of the claimed cost saving on the bill.
- Shared team memory turns prompt injection from per-session into persistent across users. The speaker says this attack surface has not been tested.
- Open core: local SQLite by default, but the project ships a Tencent Cloud vector backend and a managed memory service.
- A generated memory can drift for weeks and fail silently; a hand-written memory file never goes stale behind your back.
- Speaker's verdict: install for a long local session as a cheap test, wait for outside reproduction before team adoption.
