> Better Stack tutorial on running Django in production with Docker: gunicorn instead of runserver, nginx serving static files, a multi-stage non-root Dockerfile, and Postgres wired together with docker-compose.

## Summary
The presenter containerizes a small Django poll app with three services: Postgres, a gunicorn-served Django app, and an nginx front door on port 8001. He argues most Django Docker guides make three mistakes: they use runserver, they ignore static files so CSS breaks, and they leave the admin broken. The setup reads settings from environment variables (.env.local for development, .env.prod for production), collects static files into a STATIC_ROOT volume that nginx serves, and uses an entrypoint script to run collectstatic and migrate before starting gunicorn. The Dockerfile is multi-stage on python:3.13-slim, copies requirements.txt before the code for layer caching, and runs as a non-root user. The video ends by checking the app and the Django admin on localhost:8001 with CSS loading. It is a practical, reproducible tutorial with no AI content and no sponsor segment seen.

## Key ideas
- **Most Django Docker guides go wrong in three ways: they use runserver (not for production), they ignore static file serving so CSS breaks, and they leave the Django admin unstyled or broken.** — The fix is gunicorn as the app server, nginx to serve /static, and a checked admin page as the acceptance test. ([0:00](https://youtu.be/1v3lqIITRJA?t=0))
- **Read every environment-specific setting (DEBUG, SECRET_KEY, ALLOWED_HOSTS, CSRF_TRUSTED_ORIGINS, DB credentials) through os.getenv with fallbacks; load a local env file with python-dotenv during development only.** — Two env files are used: .env.local (DEBUG true, localhost hosts, CSRF origin on port 8000) and .env.prod (DEBUG false, CSRF origin on port 8001). Docker does not read the local loader. ([1:07](https://youtu.be/1v3lqIITRJA?t=67))
- **collectstatic is the step that makes static files work in containers. It copies them into STATIC_ROOT, and that directory is then shared to nginx through a volume.** — The entrypoint script runs collectstatic and migrate, and gunicorn must be the last command in it. ([3:24](https://youtu.be/1v3lqIITRJA?t=204))
- **Add .env files to .dockerignore before anything else so secrets are not baked into the image.** — The presenter ignores both .env and .env* to be safe, then copies the rest of the ignore file from a template. ([5:33](https://youtu.be/1v3lqIITRJA?t=333))
- **Copy requirements.txt and run pip install before copying the app code, so Docker layer caching keeps dependency installs when only code changes.** — This is paired with a multi-stage build. The builder stage has compilers and build tools. The final python:3.13-slim stage copies only the installed packages and the app code. ([6:36](https://youtu.be/1v3lqIITRJA?t=396))
- **Run the container as a non-root user, and set ownership of /app to that user, so a compromised process has fewer privileges.** — This is presented as a security practice; the presenter does not discuss the threat model in detail. ([7:54](https://youtu.be/1v3lqIITRJA?t=474))
- **The nginx admin CSS problem comes from missing mime types. Include mime.types and set default_type to application/octet-stream, then alias /static to the shared static volume and proxy everything else to the Django service.** — Without the mime types the admin renders with no CSS, and the admin is unusable. The proxy_pass target is the compose service name and port, not localhost. ([11:33](https://youtu.be/1v3lqIITRJA?t=693))
- **In docker-compose, the nginx service depends on the Django web service, both share the static volume, and the Postgres data volume persists database state.** — The published nginx port (8001) must match CSRF_TRUSTED_ORIGINS for production, or form posts will be rejected. The presenter says the port in the transcript as 8001 with some garbled text. ([12:49](https://youtu.be/1v3lqIITRJA?t=769))

## Techniques
- **gunicorn as the app server with entrypoint script** — Add gunicorn (version 23 as stated) to requirements.txt. Create entrypoint.prod.sh at the project root that runs `python manage.py collectstatic --noinput` and `python manage.py migrate`, then as the last line `gunicorn <project>.wsgi:application --bind 0.0.0.0:8000 --workers 3`. Make the script executable and set it as the container ENTRYPOINT. The presenter says `--bind` is port 8000 and `--workers 3` is a reasonable default; the exact flags are as spoken and should be checked against gunicorn docs. The `<project>.wsgi:application` value must match the project's wsgi.py. *When:* Any Django app being deployed in a container. Use it in place of runserver.
- **Environment-driven settings.py with two env files** — In settings.py, `import os` and read SECRET_KEY, DEBUG, ALLOWED_HOSTS and CSRF_TRUSTED_ORIGINS with os.getenv(NAME, fallback). Database settings (engine Postgres, name, user, password, host, port) also come from env vars. For local development only, load the env file with python-dotenv (`load_dotenv('.env.local')`); production uses `.env.prod` via docker-compose env_file. Keep DEBUG=false and CSRF origin on port 8001 in .env.prod. *When:* Keeping one codebase across local and container environments without committing secrets.
- **Static file serving through a shared volume and nginx** — Set STATIC_URL = '/static/' and STATIC_ROOT to a directory (the presenter's name for it is 'static files' under /app). The compose file mounts a named volume `static` on the Django service at that path and the same volume on nginx. nginx has `location /static { alias /static; cache time optional }`. Run collectstatic at container start. *When:* Serving Django admin and app CSS/JS through nginx in a compose stack.
- **nginx config with mime types, static alias and reverse proxy** — In nginx.conf, the http block includes mime.types and sets default_type application/octet-stream. A server block listens on port 80 and maps the published port to 8001 in compose. `location /static` aliases the shared static volume. The catch-all `location /` uses proxy_pass to the Django compose service name and port 8000, and passes the standard forwarding headers so Django sees the right request metadata. *When:* Putting nginx in front of gunicorn and serving static assets from nginx.
- **Multi-stage Dockerfile with cache-friendly ordering and non-root user** — Stage 1 (builder): FROM python:3.13-slim, WORKDIR /app, ENV PYTHONDONTWRITEBYTECODE=1 and PYTHONUNBUFFERED=1, pip install --upgrade pip, COPY requirements.txt only, pip install -r requirements.txt. Stage 2: FROM python:3.13-slim, create a non-root user, mkdir /app and chown it, COPY --from=builder the installed site-packages and binaries, WORKDIR /app, COPY . . with --chown to the app user, reapply the ENV lines, USER <app user>, EXPOSE 8000, chmod +x entrypoint, ENTRYPOINT the script. The presenter names the copy-from paths as shown on screen; they are not repeated in the transcript. *When:* Images that should be small, reproducible, free of build tools, and not run as root.
- **docker-compose three-service stack** — Services: db (Postgres image with env_file .env.prod), web (build: . with env_file .env.prod, depends_on db, volume static mounted at the static path), and nginx (depends_on web, mounts nginx.conf into the nginx config path, mounts the static volume, publishes port 8001). Add a named volume for postgres data and a named volume for static. Set the DB host to the compose service name (`db`), not localhost. Start with `docker compose up`. Verify with the app at localhost:8001 and the admin at localhost:8001/admin. *When:* Local production-like runs or small single-host deployments of Django with Postgres.
- **.dockerignore with env files first** — Create .dockerignore at the project root. Its first entries are `.env` and `.env*`, so no env file is copied into the image. The rest is a template of local-only files that are not needed in the image. Keep it updated whenever a local-only file is added. *When:* Every container build that uses a project directory containing .env files.
