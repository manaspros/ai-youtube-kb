> Walkthrough of Colibri, a one-person C engine that runs the 744B-parameter MIT-licensed GLM 5.2 on a 25GB laptop by streaming MoE experts from disk; honest speed is about 0.05 to 0.1 tokens/s.

## Summary
The video covers GLM 5.2, an MIT-licensed open-weight MoE model released June 13, 2026 (weights three days later), and Colibri, a single-file C inference engine that runs it on modest hardware. The core idea is that only about 40B of the 744B parameters activate per token, so the dense part (attention, shared experts, embeddings, router, about 9.9GB at int4) stays in RAM while the 21,504 routed experts (about 370GB) live on disk and are fetched on demand through a per-layer LRU cache sitting under the OS page cache. Cold decoding reads roughly 11GB from disk per token, so the reference laptop (12 cores, 25GB RAM, WSL2, about 1GB/s random read) manages 0.05 to 0.1 tokens/s; a scaling table gives 0.5 to 1 tok/s on PCIe 4 NVMe with 32GB RAM and 5 to 15 tok/s on a 128 to 256GB workstation. Two speedups are covered: MTP speculative decoding using the model's layer-78 head (about 2.0 tokens per forward, but only if the head stays at int8), and a learning cache that logs which experts a user's sessions route to and pins the hottest ones into RAM at startup. The speaker stresses the speed is not interactive on weak hardware and lists caveats: Ollama's "cloud" tag hits ZAI's API rather than local inference, llama.cpp lacks the sparse attention path, and sustained NVMe reads can overheat soldered SSDs.

## Key ideas
- **GLM 5.2 is MIT-licensed open weights (released June 13, 2026, weights three days later), and the video's premise is that the license plus the weights make local running possible.** — The speaker notes the model's developer was added to the US Commerce entity list in January 2025, yet the license carries no revenue, attribution or regional restrictions. ([0:00](https://youtu.be/_2knU_H8XwU?t=0))
- **MoE sparsity is the hook: the dense core is small and the routed experts are mostly idle per token, so you need the right ~5% of parameters fast rather than all of them.** — 21,504 routed experts across 75 MoE layers; 8 experts per layer are active per token, about 40B of 744B parameters. The dense part (attention, shared experts, embeddings, router) is about 9.9GB at int4 and stays resident in RAM. ([2:51](https://youtu.be/_2knU_H8XwU?t=171))
- **Colibri keeps routed experts on disk and loads them on demand through a per-layer LRU cache, with the OS page cache as a second cache layer.** — Each expert is about 19MB on disk. A cold decode costs roughly 11GB of disk reads per token, which is the bottleneck. Recently used experts stay warm in memory. ([2:51](https://youtu.be/_2knU_H8XwU?t=171))
- **Speed is the honest limit: 0.05 to 0.1 tokens/s on the reference laptop, scaling with NVMe speed and RAM to 5 to 15 tokens/s on a 128 to 256GB workstation.** — The speaker says low-end speeds suit async jobs (queue a request and come back) and only the high end gives interactive use. ([4:01](https://youtu.be/_2knU_H8XwU?t=241))
- **MTP speculative decoding helps only if the MTP head is quantized to int8, not int4.** — The layer-78 MTP head measured 2.0 tokens per forward. At int4 acceptance collapses to 0 to 4%; at int8 it is 39 to 59%. ([4:01](https://youtu.be/_2knU_H8XwU?t=241))
- **A learning cache makes the engine faster the longer one uses it on the same codebase.** — Each session records which experts the real workload routes to; at startup the hottest experts are pinned into spare RAM, and hot experts avoid the 11GB-per-token disk traffic. ([5:22](https://youtu.be/_2knU_H8XwU?t=322))
- **The engine is one readable C file of about 1,300 lines (GCC + OpenMP + AVX2, no Python at runtime, no GPU required), and the speaker claims its forward pass matches the reference model token for token.** — Validated against a transformer oracle; the speaker reports 32 of 32 matching on teacher-forced validation. This is the author's own test, not an independent audit. ([5:22](https://youtu.be/_2knU_H8XwU?t=322))
- **Setup is three steps, and conversion is shard-by-shard so the full FP8 checkpoint never sits on disk at once.** — Run setup.sh in the C directory (checks GCC/OpenMP, builds, runs self-tests); convert downloads each FP8 shard, converts it to int4, and deletes it; a pre-built int4 checkpoint is on Hugging Face. Peak need is about 400GB free NVMe. Context size is auto-set from available RAM. ([6:45](https://youtu.be/_2knU_H8XwU?t=405))

## Techniques
- **Stream MoE experts from disk through a per-layer LRU cache** — Keep the dense part (attention, shared experts, embeddings, router, about 9.9GB at int4) permanently in RAM. Store routed experts on disk (about 19MB each). When a layer routes to an expert, read it from disk if not cached; keep recently used experts in a per-layer LRU and let the OS page cache act as a second level. *When:* A MoE model's total weights exceed RAM but only a few experts activate per token, and you can tolerate low throughput or async jobs. Disk read bandwidth then sets the tokens/s ceiling.
- **Learned hot-expert pinning across sessions** — Log which routed experts each session's real workload selects. At startup, pin the most frequently used experts into spare RAM. Expected to speed up over repeated use on the same codebase. *When:* Repeated workloads with a stable routing pattern, such as the same codebase, and spare RAM beyond the dense core.
- **Quantize the MTP head to int8 for speculative decoding** — Use the model's built-in multi-token prediction head (layer 78 in GLM 5.2) as the drafter; the main model verifies drafts in one batched forward pass. Keep the MTP head at int8 while the body is int4, since int4 acceptance falls to 0 to 4% and int8 runs at 39 to 59%. *When:* A model ships with an MTP head and you run it quantized. Check the acceptance rate, because it can collapse silently at low precision.
- **Shard-by-shard FP8 to int4 conversion with resumable progress** — Download one FP8 checkpoint shard, convert it to int4, delete the shard, then fetch the next. Peak disk need is about 400GB rather than the full 756GB checkpoint, and the job can resume at any point. *When:* Converting a huge checkpoint on a machine with less disk than the full source model.
- **Colibri reproduction steps (from the video)** — 1) Clone the Colibri repo (URL not shown). 2) From the C directory run ./setup.sh (checks GCC and OpenMP, builds the binary, runs architecture self-tests). 3) Run the convert command, which downloads and converts the GLM 5.2 FP8 checkpoint shard by shard. Alternatively, put a pre-built int4 .coli model from Hugging Face in the model directory. 4) Run the chat command. For reasoning mode, set think=1 before real work (exact syntax not clear from captions). Context size is chosen automatically from available RAM. *When:* Trying the engine on a machine with fast NVMe (a PCIe 4 or 5 drive, or RAID 0) and enough RAM. Monitor disk temperature on laptops with soldered SSDs.

## Hot takes
- The title's 'tipping point' is overstated for a 0.05 to 0.1 tok/s reference setup; the speaker admits it is not a daily driver and only useful async on weak hardware.
- Ollama's cloud tag for GLM 5.2 hits ZAI's cloud API, not local inference, and that confusion has burned people.
- Sustained full-duty NVMe reads can overheat soldered SSDs on laptops; an external NVMe or desktop is the saner setup.
- Benchmark numbers (WeBench Pro, AIME 2026, Artificial Analysis) are cited by the speaker without links, and token-exact correctness is the author's own test.
- Quality: single-creator, practitioner-level explainer with concrete numbers and honest caveats, though it is more explainer than deep technical walkthrough.
