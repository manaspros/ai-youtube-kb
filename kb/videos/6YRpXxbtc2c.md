> Better Stack's hands-on review of Nub, a single Rust binary on top of stock Node.js that bundles a TypeScript runner, Node version manager and pnpm-compatible package manager; the speed claims hold up only partly in the host's own tests.

## Summary
Better Stack reviews Nub, a single Rust binary that runs on top of stock Node.js and bundles a TypeScript file runner, a Node version manager, a package manager with pnpm-compatible commands, and package and script runners. The host demos each piece: TypeScript enums, namespaces and parameter properties run under nub where plain Node fails, .env loading with variable expansion works, and a Node version is installed automatically from a version file. For installs, nub adopts existing bun or pnpm lockfiles instead of writing its own, and it is fastest in the vendor benchmark and in the host's 14-dependency test. The vendor's nubx and nub run speed claims (19x and 24x) shrink to much smaller margins in the host's own runs, and plain Node was actually fastest when running a file. Security defaults include a 24-hour minimum release age and build scripts that do not run unless approved. The host says he would use it mainly for throwaway VMs and would keep Bun and pnpm for daily work.

## Key ideas
- **Nub is one Rust binary that works on top of Node rather than replacing it, and covers five roles: file runner, script runner, package runner, package manager and Node version manager.** — Positioned as Bun's best features on stock Node. The author is described as Colin, creator of Zod, who also made a TRPC proof of concept and worked on Bun. Runs on Mac, Windows and Linux. ([0:00](https://youtu.be/6YRpXxbtc2c?t=0))
- **The file runner handles TypeScript beyond Node's type stripping: enums, namespaces and parameter properties run under nub, where Node errors with unsupported TypeScript syntax.** — It also covers tsconfig paths, decorators, JSX (transpiled per tsconfig), the `using` keyword, JSON/YAML/TOML/text imports, and polyfills for newer web APIs on older Node versions. ([1:02](https://youtu.be/6YRpXxbtc2c?t=62))
- **Built-in .env handling loads .env, .env.local and Node's environment-specific files, with variable expansion and .env.local taking precedence.** — Replaces dotenv-style loading in the host's demo: a variable built from DB_USER and DB_HOST resolves automatically, and the API key from .env.local overrides the one in .env. ([1:02](https://youtu.be/6YRpXxbtc2c?t=62))
- **Because nub forwards Node flags, a script that uses only Node-supported features runs the same under nub as under Node. The host's benchmark still found plain Node fastest, nub slightly behind, and TSX slowest.** — Vendor docs claim nub matches Node's run time; the host admits it cannot beat Bun, which is a native runtime. The host's benchmark used a single Mac with no sample size given. ([2:15](https://youtu.be/6YRpXxbtc2c?t=135))
- **The Node version manager installs the version named in a version file, .nvmrc or package.json on run, and covers install, list, uninstall and pinning.** — The demo changes the pinned version from Node 26 to 24 and reruns; nub fetches 24 from Node.js automatically. Pinning writes the version file. ([3:10](https://youtu.be/6YRpXxbtc2c?t=190))
- **The package manager adopts existing lockfiles (bun, pnpm) and updates them in place instead of creating its own, so switching tools in a project is easy.** — Every package-management command matches pnpm's flags, including workspace catalogs. Picks up npm, Bun and Yarn configuration. Uses OBE under the hood, a package manager library by JDX (creator of mise) that Colin worked with to embed in nub; the name is garbled in captions. ([4:26](https://youtu.be/6YRpXxbtc2c?t=266))
- **Install-time security defaults: a 24-hour minimum release age for new package versions, and no build scripts run unless explicitly approved.** — The host frames this as protection against supply-chain attacks, which he says pnpm also took from its own security defaults. ([5:28](https://youtu.be/6YRpXxbtc2c?t=328))
- **nubx and nub run speed claims shrink in the host's own runs. nubx executes the binary from node_modules directly from Rust with no Node wrapper process; nub run uses its binary with no package-manager startup.** — Vendor claims are 19x faster than npx and 24x faster than pnpm run. The host's own runs were smaller: nubx 169 ms against pnpm exec 423 ms on an ES build; nub run was fastest but by a smaller margin than the docs suggest. ([5:28](https://youtu.be/6YRpXxbtc2c?t=328))
- **The host's verdict is cautious: he would use nub for throwaway VMs and simple file running, but not as a daily replacement for Bun and pnpm, and he has never found pnpm too slow.** — He says he is a heavy Bun user with no compatibility issues so far, and may only switch if Bun's Rust port changes things. Also covers a drop-in GitHub Action that replaces setup-node, which is not demoed. ([6:30](https://youtu.be/6YRpXxbtc2c?t=390))

## Techniques
- **Run TypeScript files directly with nub instead of tsx or ts-node** — Run `nub <file.ts>` (e.g. `nub index.tsx`). Handles enums, namespaces, parameter properties, decorators and JSX without a separate transpile step. The author says nub is flag-for-flag compatible with node, so scripts using only Node-supported features can switch between `node` and `nub` with identical results. *When:* Quick scripts, tests and throwaway environments where you want TypeScript features beyond Node's type stripping and do not want to install tsx.
- **Let the env loader handle .env files** — Put values in `.env`, `.env.local` and Node's environment-specific files and run through nub. Variables can reference other variables (e.g. a health check URL built from DB_USER and DB_HOST). `.env.local` overrides `.env`. The demo shows values resolved with no dotenv import. *When:* Projects that currently load env files through dotenv or a similar package and want variable expansion without extra code.
- **Pin the Node version in a version file** — Add a node version file, an `.nvmrc`, or a `node` entry in `package.json`, then run through nub. nub installs the named version from Node.js on first run. Use nub's install, list, uninstall and pin commands; pin writes the version file for you. *When:* Machines or CI runners where Node versions vary by project and you want to drop nvm or fnm.
- **Adopt an existing lockfile in place** — In a project with a bun or pnpm lockfile, run `nub install`. It updates the existing lockfile rather than creating a new one, so the project can move between package managers. pnpm-style flags, including workspace catalogs, are supported. *When:* Trying nub on an existing pnpm or Bun project without a lockfile migration, or switching back and forth.
- **Run package binaries with nubx instead of npx or pnpm exec** — Use `nubx <bin>` in place of `npx` or `pnpm exec`. It resolves to the binary in node_modules/.bin and runs it straight from Rust with no Node wrapper. It is flag-compatible with pnpm exec, including dlx. *When:* Frequent one-off CLI invocations where startup overhead matters, such as build or lint tools in scripts.
- **Use nub run for scripts with lifecycle hooks** — Use `nub run <script>` instead of `pnpm run`. It supports pre/post lifecycle hooks, npm environment variables, argument forwarding and pnpm's monorepo features. *When:* Replacing pnpm run in monorepos where script startup time matters.
- **Harden installs with defaults nub ships with** — nub uses a minimum release age of 24 hours for new package versions and skips build scripts unless they are approved. The host presents this as a defence against supply-chain attacks. The exact settings are not shown. *When:* Projects that want a guard against freshly published malicious package versions and install scripts.

## Hot takes
- The host says nub is 'Bun spelled backwards' and calls it Bun's best features on stock Node, which is marketing framing rather than tested comparison.
- Speed claims rest mainly on vendor docs. The host's own tests were single-machine runs with no stated sample size, and they contradicted the vendor's margins for nub run and nubx.
- The host expects nub to be fastest at install and says it is ahead of Bun, but he does not expect to use it daily because he has not found pnpm too slow.
- No compatibility testing beyond the host's own projects was shown, and the GitHub Action and Node version manager were not demonstrated.
- The author's credentials (Zod, TRPC, Bun) are offered as a reason to trust the project, not as evidence of performance.
