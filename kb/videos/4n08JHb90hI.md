> Akamai hands-on workshop on self-hosting LLM agents on a single GPU with vLLM: memory budgets, prefill vs decode, FP8 quantization, speculative decoding, and finding the concurrency knee.

## Summary
Duan Lightfoot and Khaja Omer (Akamai) run a 1h50m hands-on workshop on owning inference for production agents on dedicated GPUs. They cover the agent loop and its token cost, when owning a GPU beats renting a provider's API, and the memory math (weights plus KV cache) that sets how much context and concurrency one card can hold. Attendees run vLLM on one RTX 4000 Ada per person in a Kubernetes namespace and use load tests to measure throughput and time-to-first-token. The optimization section is the most useful part: FP8 quantization roughly doubled weight size savings and raised peak throughput about 1.4x in their run, but it needs your own evals. A badly matched speculative-decoding drafter cut throughput sharply, so acceptance rate has to be measured. The talk ends with a concurrency-knee sweep and a max-num-seqs change that lifted 64-concurrency throughput from about 800 to 1100 tokens/s. Live cluster problems cut the final demo short, and several numbers are single-run measurements on one card.

## Key ideas
- **Owning inference makes sense when usage is high and steady, data or compliance rules out public providers, and you have the hardware capacity; renting fits bursty or low traffic.** — A GPU you pay for should stay busy. The speaker frames data residency, IP and governance as the main reasons to own, and bursty low-volume use as the reason to rent a provider's model. ([2:41](https://youtu.be/4n08JHb90hI?t=161))
- **An agent is a loop of model calls, tool actions and results, and every turn costs generated tokens and latency.** — Each pass through the model adds tokens and time, so cost and latency grow with the number of tool-call turns. This is the reason the workshop cares about per-token speed and cache reuse. ([1:12](https://youtu.be/4n08JHb90hI?t=72))
- **vLLM is the production choice over Ollama for concurrent agents because of continuous batching and paged KV-cache memory, plus an OpenAI-compatible API.** — Continuous batching lets new requests join while others are still running instead of waiting for a whole batch to finish. Paged memory avoids reserving the longest prompt's space for every request. The speaker says Ollama throttles much sooner under concurrency. Ollama is fine for one agent in development. ([9:02](https://youtu.be/4n08JHb90hI?t=542))
- **GPU memory is weights plus a KV-cache pool, and the KV pool sets how many tokens of context and concurrent requests fit.** — A 4B model in BF16 takes about 8 GB for weights. The remaining VRAM holds KV cache, which grows with every token in every active request, including system prompt, tool definitions and tool results. The speaker computes roughly 37k tokens of KV capacity on their card. ([28:29](https://youtu.be/4n08JHb90hI?t=1709))
- **Prefill is compute-bound and drives time-to-first-token, while decode is memory-bandwidth-bound and sets the tokens-per-second ceiling.** — Decode cannot go faster than the card can read the weights, so only a smaller or quantized model, or more concurrent requests, raises total throughput. The speaker shows a roofline plot with a ridge point near 297 FLOPs per byte. ([39:? ](https://youtu.be/4n08JHb90hI?t=0))
- **Size and tune to tail latency and the concurrency knee, not averages or the median.** — Throughput flattens past a certain concurrency while latency keeps climbing. The useful operating point is just before the throughput plateau, while time-to-first-token is still acceptable. The speaker also argues to optimize against the slowest requests, not the median. ([25:07](https://youtu.be/4n08JHb90hI?t=1507))
- **FP8 quantization halves weight size, frees KV-cache room and speeds decode, but must be checked with your own evals and only on hardware that accelerates it.** — The speaker's example is a pre-quantized Qwen3 4B FP8 checkpoint with partial (dynamic) quantization, so the file is about 5.1 GB rather than 4 GB. Quality issues they name include broken JSON, failed function calls, loops and hallucination. FP8 gains need hardware support, and the speaker says FP4 could slow things down on the RTX 4000 Ada. ([51:10](https://youtu.be/4n08JHb90hI?t=3070))
- **Speculative decoding helps only when the drafter's tokens are accepted often, so measure acceptance rate and treat a mismatched drafter as a likely slowdown.** — A small draft model proposes several tokens and the main model verifies them in parallel. The speaker's drafter, trained for a different model, made throughput collapse (58 to 16 tokens/s at concurrency 1). Draft and target should share precision, the drafter should be trained for the target, and the draft-token count must be tuned. Their home setup reports 2-3x gains, and they note coding benefits more than browser use. ([1:15:07](https://youtu.be/4n08JHb90hI?t=4507))
- **Raising max-num-seqs and changing one flag at a time, with a load test after each change, moved the bottleneck the speaker had found at 32 concurrency.** — Concurrency 64 went from about 800 tokens/s with about 2000 ms latency to about 1100 tokens/s with about 800 ms after raising max-num-seqs from 32 to 128. The speaker also says to tune gpu-memory-utilization (0.7 in the workshop, 0.9 to 0.95 for a single model) and to measure each change rather than stacking them. ([1:47:34](https://youtu.be/4n08JHb90hI?t=6454))

## Techniques
- **Memory budget math** — Weight bytes = params x bytes per param (BF16 = 2, FP8 = 1). Subtract weights from usable VRAM to get the KV pool. Divide by KV bytes per token to estimate max context tokens, then check that concurrency x context fits. *When:* Before choosing a GPU or model size, or when deciding how many agents one card can serve.
- **Concurrency sweep to find the knee** — Run a load test at concurrency 1, 4, 8, 16, 32, 64 and higher. Plot aggregate tokens/s against time-to-first-token. Pick the highest concurrency before throughput plateaus and latency jumps. *When:* When sizing a deployment or after any serving config change.
- **One-flag-at-a-time tuning** — Change one vLLM flag (gpu-memory-utilization, max-num-seqs, max-num-batched-tokens, max-model-len, speculative config), redeploy, rerun the same load test, and keep the change only if the metric you care about improves. *When:* When tuning an inference endpoint against an SLA.
- **Quantize with your own eval set** — Build a small eval set for your task (JSON validity, function-call success, reasoning, looping) and run it on BF16 and the quantized model before switching. Keep a quantized model only if quality holds. *When:* Before deploying FP8, INT4, or any other quantized checkpoint.
- **Validate speculative decoding by acceptance rate** — Confirm the drafter was trained for the same target model and uses the same precision. Sweep the draft-token count (2, 4, 6 and so on), measure acceptance rate and throughput at low and high concurrency, and disable speculation if throughput drops. *When:* When adding a draft model or any other speculative method to a serving stack.
- **Prefix caching for repeated context** — Enable prefix caching so a shared system prompt and tool definitions are reused from the KV cache across requests, rather than recomputed each time. *When:* For agents that send the same long prefix on every turn or from many users.
- **Own-vs-rent break-even** — Count tokens per day, multiply by the hosted per-token price, and compare with the monthly cost of a rented GPU at the measured throughput for the same task. *When:* When deciding between a hosted API and self-hosted inference for a steady workload.

## Hot takes
- Ollama is fine for one developer agent, but use vLLM or SGLang once you run many agents in parallel
- Benchmark numbers from others rarely match your own runs, so measure your own workload
- A drafter model trained badly for the target can make speculative decoding several times slower, with no easy fix
- FP8 is usually safe for simple cases, but JSON and function-call quality can break for specific workloads
- Owning a GPU only pays off when it stays busy
