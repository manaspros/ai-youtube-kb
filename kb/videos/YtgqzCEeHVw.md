> Walkthrough of a vibe-coding workflow: Claude brainstorms and writes a no-code front-end prompt, Replit generates a shadcn-based responsive UI with exposed APIs, and Windsurf builds the FastAPI backend from the exported API docs.

## Summary
The speaker describes a three-tool workflow for building an app without writing code. Claude is used to brainstorm and produce a structured front-end prompt that must list pages and modals, specify the front-end stack, and forbid code generation. Replit then builds the responsive, shadcn-based UI and exposes API endpoints, and the speaker has Replit write API documentation. The project is downloaded as a zip, opened in Windsurf, and the FastAPI backend is implemented from that documentation, using in-memory storage in place of a database. The speaker highlights Windsurf features such as sending console logs and selected elements to Cascade. The video is a product-flavored tutorial with a sponsor-style call to action; the substance is a reusable planning-then-handoff pattern, with the main caveat that the result is a single demo with no evals or failure data.

## Key ideas
- **Split the app across tools by task: an LLM brainstorms, Replit builds the front end, and Windsurf or Cursor builds the backend, so each tool does one job.** — The speaker argues that one-shot full-stack generators (including Replit's own database integration) tend to introduce bugs, so a modular handoff is cleaner. ([0:00](https://youtu.be/YtgqzCEeHVw?t=0))
- **Make the planning prompt explicit about pages and modals, since LLM-generated plans usually omit modals and leave the next tool to guess.** — Ask for a final front-end prompt that lists pages and modals, names the front-end tech stack, and says not to generate code. Undefined modals led to inconsistent structure in the downstream tool. ([1:21](https://youtu.be/YtgqzCEeHVw?t=81))
- **Require the front end to expose its API and generate API documentation, then pass that document to the backend tool as the contract.** — The speaker says the API documentation from Replit let Windsurf implement FastAPI endpoints that matched the UI on the first try; the speaker contrasts this with Cursor leaving features unimplemented. ([4:13](https://youtu.be/YtgqzCEeHVw?t=253))
- **Replit output was judged responsive and well structured, while the speaker found Cursor and Windsurf UIs often were not responsive.** — This is one speaker's subjective comparison from a single project, not a benchmark. ([2:42](https://youtu.be/YtgqzCEeHVw?t=162))
- **Windsurf can send browser console logs and a selected UI element directly to Cascade, which locates the element in the code without a full-codebase search.** — The speaker contrasts this with screenshots, which force the agent to search the whole codebase and overload context. ([5:43](https://youtu.be/YtgqzCEeHVw?t=343))
- **The backend was built with in-memory storage, and a task added in the UI persisted across refresh; a database was deliberately deferred.** — Supabase (with its MCP server) or local Postgres can be added later by asking the agent. ([7:02](https://youtu.be/YtgqzCEeHVw?t=422))
- **Voice dictation was the input for the whole workflow, and the speaker recommends SuperWhisper over the built-in macOS dictation.** — Dictated prompts were messy, but the model still produced a usable plan. ([0:00](https://youtu.be/YtgqzCEeHVw?t=0))

## Techniques
- **Planning prompt with pages and modals** — Brainstorm the app with Claude. Ask for a final front-end prompt that lists every page and every modal (pop-ups), states the front-end tech stack, requires exposed API endpoints, and says the output should contain no code. Do not let the model add extra features such as a database or dashboard that were not in the agreed plan. *When:* Before handing UI generation to a separate tool, to prevent the downstream tool from inventing structure.
- **Front end first, API docs as the contract** — In Replit, have the generated project expose its API endpoints and produce API documentation. Export the project as a zip (open the project, reveal files, use the three-dot menu to download). Extract it, open it in Windsurf, and give Windsurf the API docs to implement the FastAPI backend against. *When:* When the front end is generated by one tool and the backend by another, so the backend has a concrete spec.
- **Dependency and run step for a generated front end** — Tell the agent the project is a pre-built front end that has no dependencies installed. Have it run npm install, then start the dev server. *When:* After importing a downloaded Replit project, which had no node_modules.
- **Send browser context to the agent** — In Windsurf, send console logs to Cascade. Use the select-element tool in the built-in preview to click a UI element and send it to Cascade, which maps it to the source. *When:* When debugging UI issues, instead of attaching screenshots.
- **In-memory storage first, database later** — Ask the backend agent for an in-memory store in FastAPI so the app runs without a database. Later, ask for Supabase (with its MCP server) or local Postgres. *When:* For prototypes where persistence is not yet needed.

## Hot takes
- Replit's generated UIs are responsive and well structured, while Cursor and Windsurf often ship UI that is not responsive.
- Asking a model to plan an app usually omits modals, and that gap is what causes inconsistent results downstream.
- Full-stack one-shot generators tend to introduce bugs, so separating UI generation from backend work is better.
