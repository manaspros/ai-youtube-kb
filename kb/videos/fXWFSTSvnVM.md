> Back-of-envelope memory and concurrency math on what it would take to self-host a frontier-scale open model (Kimi K3 as a stand-in for Claude Fable 5): a Mac Studio or 4xH100 cannot hold it, and serving 100 people is a data-center sizing problem.

## Summary
The host asks what hardware would be needed to run a model in the class of Claude Fable 5 locally. Because Anthropic does not publish Fable 5's size or weights, the video uses Kimi K3 (2.8T parameters, 1M-token context, full weights promised by July 27, 2026) as a published-size stand-in and states plainly that it is not a Fable replacement. Raw 4-bit weights come to about 1.4 TB, which rules out the largest Mac Studio (512 GB) and four H100s (320 GB). An 8xB200 node reaches the weight floor with almost no headroom, while an 8xB300 node leaves room for runtime and KV cache. Kimi recommends 64 or more accelerators for efficient inference, so the realistic answer is at least eight servers. For "100 users," the host argues the right unit is concurrent in-flight requests, not headcount, and that agent workloads push that number up. The video closes with a hybrid pattern (small private model for routine work, cloud frontier model for the hardest tasks) and advises renting hardware for a couple of weeks to test with real users before buying.

## Key ideas
- **Fable 5 cannot be sized directly because its parameter count, architecture and weights are unpublished; Kimi K3 is used as a frontier-scale stand-in with a published size, explicitly not as an equivalent.** — Kimi K3 is cited as 2.8T parameters with a 1M-token context. The host notes Kimi's own blog says K3 still trails the strongest proprietary models, and warns that benchmark scores do not reflect real work. ([1:11](https://youtu.be/fXWFSTSvnVM?t=71))
- **Mixture-of-experts reduces per-token compute, not memory: all 896 experts must stay resident because routing can pick different experts for each token.** — Only 16 experts are active per token, but the serving system must hold all of them since the next token may use a different set. ([2:19](https://youtu.be/fXWFSTSvnVM?t=139))
- **The memory floor is parameters times bytes per parameter. At 4 bits (MXFP4), 2.8T parameters give about 1.4 TB of raw weights, before format overhead, runtime, active sessions and safety margin.** — The host calls this the floor, not the real total. Even a hypothetical 2-bit version would need about 700 GB of weights. ([2:19](https://youtu.be/fXWFSTSvnVM?t=139))
- **Single-box options fail on memory: the largest Mac Studio (512 GB unified memory) and four H100s (320 GB total) cannot hold the weights.** — The host concludes that a Mac Studio can run useful local models but not this one. ([2:19](https://youtu.be/fXWFSTSvnVM?t=139))
- **One 8xB200 server (1.44 TB) reaches the weight floor with roughly 40 GB left, which is not practical. An 8xB300 server (about 2.3 TB) leaves about 900 GB of headroom but still falls short of Kimi's recommended 64+ accelerators for efficient inference, meaning at least eight servers.** — Kimi says 64 or more accelerators is the recommended setup for efficient inference, not the minimum to load the model. The host treats that recommendation as the practical answer. ([3:43](https://youtu.be/fXWFSTSvnVM?t=223))
- **"100 users" is the wrong unit. Load is concurrent in-flight requests, which depends on request rate, how long each request keeps the system busy, prompt length and agent fan-out.** — Example: 100 employees each sending one request every 10 minutes, with 30 seconds of work per request, averages about 5 active requests. Agents can run several jobs at once, and long context adds runtime memory. ([5:03](https://youtu.be/fXWFSTSvnVM?t=303))
- **Operating cost goes beyond compute: power, cooling, networking, storage and staff. The host's pattern from people who already run local setups is local models for private or repetitive work and cloud models for the hardest tasks.** — Eight B300 nodes are cited at about 116 kW before cooling. Compute rental for 8 B200 nodes is estimated around $313k to $577k per month, described as rough scale math, not a quote. ([6:26](https://youtu.be/fXWFSTSvnVM?t=386))
- **The practical test is to rent the hardware for a few weeks and see whether real users find the results good enough, fast enough, and easy to keep running.** — The host cites an LLM-service operator's view that a model that is good enough and can scale beats a stronger model that serves only a couple of people. ([6:26](https://youtu.be/fXWFSTSvnVM?t=386))

## Techniques
- **Weight memory floor estimate** — Weight bytes = parameter count x bits per parameter / 8 (2.8T x 4 bits = about 1.4 TB). Treat this as a lower bound. Add format overhead, KV cache, runtime, serving software and a safety margin, then compare the total against each candidate's total GPU or unified memory. Remember that MoE routing keeps all experts resident. *When:* Before evaluating whether a given open-weight model can be self-hosted on a given box, or before believing a 'run it on X' claim.
- **Concurrency sizing from arrival rate and service time** — Average active requests = requests per second x average seconds each request occupies the system (for example 100 users x 1 request per 600 s x 30 s = about 5). Size for the busiest moment, not the average or the headcount, and multiply for agent fan-out and long prompts (up to the context limit). *When:* When sizing capacity for an internal LLM service, a gateway or a load test profile, and when a team quotes users instead of concurrency.
- **Hybrid local and cloud routing** — Send private, repetitive or extraction-style work (document search, classification, extraction, routine coding) to a small self-hosted model. Send the hardest reasoning tasks to a frontier cloud model. *When:* When designing a model-routing policy that balances privacy, cost and quality.
- **Rent-before-buy pilot** — Rent the candidate hardware for one to two weeks, run real user traffic through it, and measure output quality, latency and the operational effort required to keep it running. Compare against a benchmark chart only as a secondary input. *When:* When deciding whether to buy or reserve GPU hardware for a self-hosted model.
