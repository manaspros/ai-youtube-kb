> Dhruv Batra (Yutori) argues the long-tail web will be driven by pixel-based computer-use agents rather than new APIs, and shows his Navigator model's accuracy and cost per task.

## Summary
Batra argues against the view that agents will get clean APIs for most of the web. He says MCP and protocol proposals help only the most popular sites, while the long tail of institutional and small-business sites will stay as HTML, images, scanned PDFs and JavaScript-rendered pages. He shows examples where the answer is not in the page HTML at all, because it is computed in the browser from async JSON, so the rendered pixels are the real source of truth. His claim is that a general pixels-in, clicks-out model generalises better than hand-written scaffolds. He describes Navigator, which takes screenshots and emits clicks and scrolls, and a later version that can also run JavaScript on demand and fan out to parallel cloud-browser instances. He says the OnlineMind2Web benchmark is saturated at 97% human-eval, and that cost and latency per task (about $0.80 versus $2.30) are the real lever. He ends with a prediction: the web will be "agentified" as a structured task layer, with hundreds of browsers behind it, returning results in under 100 ms for under a penny. Most numbers are his own model's results and are not independently checked.

## Key ideas
- **The web will not get APIs for the long tail, so agents will have to drive the UI.** — He grants that the most popular sites may expose APIs, and that MCP and similar protocols will keep growing (about 20 competing payment protocols, by his count). He still argues that most institutions change too slowly to expose endpoints, and that the long tail will be reached through computer-use models instead. ([0:56](https://youtu.be/Ki980nV0__0?t=56))
- **Many pages do not contain their data in the HTML, so reading the source is not enough.** — On an NBA score page, the initial HTML is an empty placeholder; the browser fetches JSON asynchronously afterwards. On a product page, the in-stock state is computed by a rendering script from a quantity field in JSON, and the text 'sold out' never appears in the source. ([8:28](https://youtu.be/Ki980nV0__0?t=508))
- **Pixels are the source of truth because the web was built for human eyes, and scaffolds do not generalise.** — He frames the page as a rendering engine, closer to a game engine than to text. Hand-written scrapers and wrappers fail on the long tail, so he argues the most general input (screenshots) is the bitter-lesson choice for web agents. ([11:23](https://youtu.be/Ki980nV0__0?t=683))
- **A general navigator model takes screenshots in and emits clicks and scrolls out.** — Navigator's first version (released last November) acted like a human. He demos a discount-code check across a site that needs search, add-to-cart and code application, which takes roughly 20 to 40 steps. He says solvable-in-principle is the test, with accuracy gaps still present in practice. ([12:39](https://youtu.be/Ki980nV0__0?t=759))
- **Adding a run-JavaScript action lets the model batch work, while the screenshot still verifies the result.** — The next version can write a small function to fill several form fields at once, using an execute-JS action in a Chrome extension. He says the screenshot is the check: whether the code ran is not what matters, what the user sees is. ([14:07](https://youtu.be/Ki980nV0__0?t=847))
- **Parallel navigators in cloud sandboxes give superhuman throughput.** — An orchestrator launches many navigator instances at once, each with its own cloud sandbox browser, clicking through many sites in parallel. He says no human could run that many sessions. ([15:08](https://youtu.be/Ki980nV0__0?t=908))
- **Cost and latency per task are the lever, not small accuracy gains.** — His model is a smaller footprint than trillion-parameter frontier models and is much faster. He claims accuracy within statistical noise of Opus 4.7 and GPT 5.5 on browser benchmarks, and about $0.80 per task against $2.30 over 20 to 30 steps. ([17:35](https://youtu.be/Ki980nV0__0?t=1055))
- **He predicts the agentified web will be a structured task layer hidden behind browsers.** — You issue a task in natural language or with parameters, hundreds of browsers click like humans behind the scenes, and you get structured output in under 100 ms for under a penny. He says that is what people will call an API. ([20:12](https://youtu.be/Ki980nV0__0?t=1212))

## Techniques
- **Screenshot-in, action-out computer-use loop** — The model receives the current screenshot and outputs clicks, scrolls and typing. It repeats for about 20 to 40 steps until the task is done. *When:* Sites with no API and no stable DOM structure, where you need a general solution across many unknown sites.
- **Code-on-demand as a browser action** — Give the agent an execute-JS action in the page. It writes a small function for repetitive or batch DOM work, such as filling several form fields in one step. *When:* Batch form entry or repetitive DOM operations where one click per field is slow. The screenshot still checks the outcome.
- **Pixel-based success check** — Judge whether the task succeeded from the rendered screenshot, not from HTML or the agent's own report. *When:* Verifying a browser-agent run finished, since the DOM can hide or compute the data.
- **Parallel sandboxed-browser fan-out** — An orchestrator spawns many agent instances, each with its own cloud sandbox browser, and runs them concurrently on different sites. *When:* The same task must run across many independent sites, such as checking many government procurement pages.
- **Read the async data call, not the initial HTML** — If the page's visible data is missing from the initial HTML, inspect what the browser fetches after load. He points to JSON endpoints and computed states, like a quantity field driving a greyed-out option. *When:* Extracting information from single-page apps or pages that render state with scripts.
- **Cost-per-task as the headline metric** — Measure latency per step and cost per completed task across models, then compare a smaller model against frontier models on the same task set. *When:* Choosing a model for high-volume agent work where small accuracy differences fall within noise.

## Hot takes
- The argument that agents will call clean APIs across the web is delusional for most of the long tail.
- Computer-use benchmarks such as OnlineMind2Web are saturated and should be retired.
- Pixel-in, click-out is the bitter lesson for web agents: scaffolds around existing websites do not generalise.
- Cost and latency per task matter more than small accuracy gains between frontier and small models.
- The future web is a hidden layer of browser agents returning structured results, which people will simply call an API.
