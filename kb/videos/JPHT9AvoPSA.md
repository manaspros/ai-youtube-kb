> A price-and-speed tour of every route to 256GB of memory for running DeepSeek V4.1 Flash locally; the real metric is bits per weight, and a cheap DDR4 plus RTX 3090 MoE-offload build is the surprise pick.

## Summary
The host argues that the memory size on a box matters less than the quantization level it lets you run, and frames every 256GB option around whether it can hold the 3-bit tier of DeepSeek V4.1 Flash, with the 4-bit tier as the upgrade target. He walks through Mac Studio, two Mac-free mini-PC builds (DGX Spark pair, Strix Halo pair), a DDR4 server plus one RTX 3090 build, a full-precision proof of concept, multi-GPU card piles, and used V100 and MI50 servers, quoting prices, tokens/s and prefill speeds mostly from owner reports and forums. A key architectural point is that the model is sparse (about 16B of 552B parameters active per token), so the hot parts can sit on a GPU and the rest in ordinary RAM or on SSD. He measures quantization cost as next-token agreement with the reference model (91.2% at 2-bit, 95.1% at 3-bit, 98.5% at 4-bit). He closes with a break-even comparison against the hosted API, a decision guide by use case (privacy, cheapest, easiest, fastest prompt reads), and a note that the API already serves the full model cheaply. The video is a practitioner comparison built from secondhand benchmarks and live retail prices as of late October 2026, not from the host's own runs.

## Key ideas
- **Bits per weight decide what you actually run, not the raw memory size.** — A 256GB box is only useful if the quantized model fits with room for context; the speaker's rule is to pick the bit level first and then find the cheapest box that reaches it. ([1:23](https://youtu.be/JPHT9AvoPSA?t=83))
- **DeepSeek V4.1 Flash has a large lookup table that does not need fast memory.** — The sparse 'engram' lookup table (about 189GB) is read only a few rows per token, so engines such as the Dwarfstar build (transcribed 'Antiresis Dwarfstar') can keep it on SSD. Stripping it out leaves a 2-bit core of about 152GB. ([2:39](https://youtu.be/JPHT9AvoPSA?t=159))
- **Quantization cost is measured as next-token disagreement with the reference model.** — Unsloth compared quantized builds to DeepSeek's reference and counted how often the next token matched. Agreement was 91.2% at 2-bit, 95.1% at 3-bit and 98.5% at 4-bit, i.e. roughly one mismatch every 11, 20 and 67 tokens. ([3:53](https://youtu.be/JPHT9AvoPSA?t=233))
- **256GB is just enough for the 3-bit tier; 4-bit needs about 300GB.** — Approximate footprints are 165-200GB for 2-bit, 234-262GB for 3-bit and about 298GB for 4-bit. Every 256GB route is competing for the same third bit, and the price of the fourth bit differs widely by route. ([5:01](https://youtu.be/JPHT9AvoPSA?t=301))
- **Apple's default GPU memory limit blocks the 3-bit tier on a 256GB Mac Studio.** — Owners report the GPU starts at roughly 192GB, so the 2-bit build fits but the 3-bit build does not. One terminal command raises the limit to about 248GB, but it resets on reboot and must go in a startup script. The command is not shown in the transcript. ([6:09](https://youtu.be/JPHT9AvoPSA?t=369))
- **The inference engine matters more than the extra GPU cores.** — On the 80-core Mac, a mixed 2/3-bit build with the draft head reached 70-105 tokens/s writing and about 1,800 tokens/s prompt reading. The more common MLX route on the 64-core chip reached 26-29 tokens/s writing and under 500 tokens/s reading, which the host attributes to the engine and build. ([7:23](https://youtu.be/JPHT9AvoPSA?t=443))
- **Sparse MoE models let a small GPU serve the hot path while cheap system RAM holds the rest.** — Only about 16B of the 552B parameters activate per token, so the always-used parts go on a GPU and the bulk sits in DDR4. One RTX 3090 with 256GB of DDR4 and a 200GB SSD ran the model at 26 tokens/s for one user and 41 across four users, for around $6,000. ([13:39](https://youtu.be/JPHT9AvoPSA?t=819))
- **A used DDR4 server is the cheapest path to the fourth bit.** — DDR5 server memory is about $29 per GB, while 64GB DDR4 sticks are about $6.23 per GB. Two more sticks ($798) could give the same machine the roughly 300GB the 4-bit build needs, if the board has free slots. This path has not been published yet. ([14:57](https://youtu.be/JPHT9AvoPSA?t=897))
- **Full-precision weights have run on one box.** — A developer ran the untouched original weights on a 96GB RTX Pro 6000 plus 512GB of DDR4, using 89GB of VRAM and 346GB of RAM. Throughput was 65 tokens/s for one user and 143 across eight users. ([14:57](https://youtu.be/JPHT9AvoPSA?t=897))
- **Multi-GPU card piles hit a ceiling because the fourth bit requires replacing every card.** — Eight PCIe slots leave no room for a ninth card, so the 4-bit upgrade means swapping the whole set. Four 96GB RTX Pro 6000s cost about $64,000 at list price. ([18:18](https://youtu.be/JPHT9AvoPSA?t=1098))
- **The KV cache is small, but first-time prefill of a long prompt is slow.** — DeepSeek V4.1 Flash uses about 890 bytes per token, so a 1M-token context is about 0.93GB. Prefill is the real cost: about 12 minutes for 1M tokens on the Mac, 22-29 minutes on the DDR4 build. Cached turns in the same session run far faster. ([20:37](https://youtu.be/JPHT9AvoPSA?t=1237))
- **Self-hosting is a break-even bet against the cheap hosted API.** — $9,499 buys about 15.8B output tokens at DeepSeek's off-peak API price. A Mac at 35 tokens/s running around the clock takes about 14 years to break even on that basis, and about 6 years at 80 tokens/s. Self-hosting still makes sense when data must stay on the machine, or when the box is busy serving a team. ([21:37](https://youtu.be/JPHT9AvoPSA?t=1297))
- **Decision guide by use case.** — If data must not leave the machine, buy a box. If 3 bits is enough, the cheapest route that keeps getting updates is the DDR4 build. The Mac is the easiest to set up. Two DGX Sparks give the best CUDA compatibility and prompt speed. Otherwise the API already serves all four bits cheaply. ([25:18](https://youtu.be/JPHT9AvoPSA?t=1518))

## Techniques
- **Size the box from bits per weight, not gigabytes** — Estimate footprint per quant tier (about 165-200GB at 2-bit, 234-262GB at 3-bit, about 298GB at 4-bit for this model) plus headroom for context and OS, then pick the cheapest hardware that clears the target tier. *When:* Choosing local hardware for a large open-weight model, before comparing vendors.
- **Measure quantization fidelity as next-token agreement** — Run each quantized build and the reference model over the same prompts, count how often the greedy next token matches, and convert to mismatches per token (for example 95.1% agreement is about one mismatch every 20 tokens). *When:* Deciding whether a 2-bit or 3-bit build is good enough for a workload.
- **Keep the hot parts of a sparse MoE on GPU and the rest in system RAM** — Place the always-active or per-token-hot layers on the GPU and keep the bulk of the experts in DDR4 or on SSD. Engines that support this read only the needed experts per token; the speaker reports a single RTX 3090 serving DeepSeek V4.1 Flash this way. *When:* Running a large sparse model on a small GPU with lots of cheap RAM, especially when concurrency is low.
- **Put a large, sparsely read lookup table on SSD** — Leave the engram/lookup table on disk and read only the rows each token needs, keeping the core weights in memory. The Dwarfstar build keeps about 189GB of it on SSD this way. *When:* A model with a big embedding-style lookup table that is read only a few rows per token.
- **Raise the macOS GPU memory limit and persist it** — A single terminal command raises the GPU memory limit to about 248GB on a 256GB Mac Studio. The value resets on reboot, so put the command in a startup script. The exact command is not shown in the transcript. *When:* Running a model that needs more than the default GPU share on Apple silicon.
- **Enable the model's draft head for speculative decoding** — Turn on DeepSeek's built-in draft head in the engine. On two DGX Sparks it raised writing from 31 to 87 tokens/s on code and to 131 tokens/s on structured output. *When:* Output-heavy local inference where decode speed is the bottleneck and the engine supports the draft head.
- **Break-even against the API before buying hardware** — Divide hardware price by (tokens/s x seconds of use x API price per token) to get payback in years, then compare with a rented GPU per-hour rate. Include electricity and utilization. *When:* Deciding between buying a local box and using a hosted API for the same model.
- **Budget prefill time for long first prompts** — Estimate prefill time as prompt tokens divided by prompt-read speed (for example 1M tokens at about 1,800 tokens/s is about 9 minutes), and expect cached turns in the same session to be much faster. *When:* Loading a large codebase or document set into a local model at the start of a session.

## Hot takes
- The host calls the cheap DDR4 server build the underrated path and says the forums are not talking about it enough.
- The 3-bit tier is the practical floor for a 256GB box, and the fourth bit is the real price driver across every route.
- For most people the hosted API is the right answer, since it already serves all four bits cheaply and self-hosting breaks even only after many years or with heavy use.
- Apple shipping a default GPU memory limit that blocks the 3-bit build is an odd choice.
- Most of the performance numbers come from owner reports and forums rather than the host's own runs, and the host says so; several key builds (the DDR4 4-bit path, two M5 Ultras linked by Thunderbolt 5) have no published results yet.
