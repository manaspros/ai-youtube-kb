> Morgan Stanley's AlphaLab, a multi-agent harness that automates quant research through research, critic-checked eval building, and Kanban-style experiments. Its main lesson: the value sits in strict eval environments and rubrics, not in the harness.

## Summary
Brendan Rappazzo describes AlphaLab, an autoresearch agent built by a Morgan Stanley team of about 30 PhD researchers to automate quant research on prediction tasks. The team built the harness from scratch with Claude writing most of it, using provider-agnostic tool calls and three main tools: shell, web search, and a Slurm abstraction for GPU jobs. The harness runs in three phases: a research phase that builds a to-do list and markdown notes, an eval-building phase where a builder agent is checked by two critics, and a mass-experimentation phase run as a Kanban board with a strategist and worker agents. The team reports that the first version (AlphaLab 1.0, released in April with a 40-page tech report) had failures, and that the fix was opinionated, Kaggle-style evals and environments. For version 2.0, they treat environments as the RL signal, grade rollouts with qualitative rubrics, and let an LLM optimise the harness itself from traces. The speaker's thesis is that general auto-research will become a commodity, so enterprise value comes from building the environments.

## Key ideas
- **Why now: long-horizon automation became feasible around Dec 2025** — The team of about 30 PhD researchers (half applied, half academic) saw quant prediction tasks as Kaggle-shaped. They say the models became good enough for long-horizon work with Opus 4.5 running inside Claude Code and Codex. The aims are P&L, more algorithms in production, and keeping their own enterprise knowledge in the system. ([0:08](https://youtu.be/kiqubc5b5Yo?t=8))
- **Custom three-phase harness, not an off-the-shelf framework** — The harness runs research, then eval/backtest building, then mass experimentation. It is written from scratch, with Claude writing most of the code, to keep full freedom to tweak it. Tools are functional tool calls, which keeps it provider-agnostic. The main tools are full shell access, web search, and a Slurm abstraction where the model requests hardware in a config. ([5:33](https://youtu.be/kiqubc5b5Yo?t=333))
- **Research phase is a to-do list that is re-prompted until complete** — The first phase is like a very thorough CLAUDE.md or init step. The agent is first made to write a to-do list that, once finished, would let it start experimenting. The system re-prompts it whenever it tries to exit early. Each item writes notes to markdown, which feature agents query later to manage their context. This phase uses web search most and takes about 3 to 4 hours. ([8:25](https://youtu.be/kiqubc5b5Yo?t=505))
- **Eval building uses a builder and two critics in a loop** — One agent writes the eval code. A conceptual critic checks for conceptual errors and forward leakage. A programmatic critic writes unit and integration tests. Issues go back to the builder, and the loop runs until both critics are satisfied. The reason given is that LLMs make silly mistakes, and optimising against a bad eval breaks the whole process. ([9:52](https://youtu.be/kiqubc5b5Yo?t=592))
- **Experiments run as a Kanban board with a post-mortem feedback loop** — A strategist agent reads all earlier context and proposes experiments as cards. Worker agents implement each card, write the Slurm config, submit the job, wait, and then check training curves for under- or overfitting plus eval results. They write a post-mortem that goes back to the strategist, so it can learn which families work, for example trees over transformers. Humans can cancel or add cards and chat with the strategist to steer it. ([11:11](https://youtu.be/kiqubc5b5Yo?t=671))
- **Lesson from failures: make the eval a strict, Kaggle-style contract** — The team says the biggest change after failures was being opinionated about the eval. The harness receives data and a description, and its only job is to submit containerised models. It gets public leaderboard feedback, while users also see a private held-out validation score. The speaker says the team now treats eval as data rather than something the agent designs freely. ([15:21](https://youtu.be/kiqubc5b5Yo?t=921))
- **Evals and RL environments are the same thing** — Once there is a strict way to measure, each environment can serve as an RL reward. The team has built 10 to 20 careful environments. They do manual tuning of the harness, and they are moving toward meta-harness optimisation, where an LLM reads traces and results and edits the harness. They are also collecting traces from open-source models for GRPO or on-policy distillation. ([16:44](https://youtu.be/kiqubc5b5Yo?t=1004))
- **Expertise is encoded as rubrics that grade each rollout's process** — Designing verifiable metrics is described as the easy part. The harder part is qualitative rubrics: the team reads traces, defines what a good quant researcher does and what the thought process looks like, and grades every rollout on how well it follows that research process. These rubrics become the learning signal that carries the team's expertise into the system. ([17:59](https://youtu.be/kiqubc5b5Yo?t=1079))
- **Thesis: general auto-research is becoming a commodity, so environments are the moat** — The speaker expects general auto-research to become commoditised and says he has already seen this with GLM 5.2. He argues that enterprise and expert value comes from building environments. In the long run the auto-research process can improve itself, and the team plans to keep releasing its work, since it sees the environment as holding most of the value. ([19:12](https://youtu.be/kiqubc5b5Yo?t=1152))

## Techniques
- **Scaffolded to-do list with re-prompting on early exit** — Have the agent first write a to-do list whose completion means it is ready to act. Re-prompt whenever it tries to stop early. Have each item write markdown notes that other agents can query, so context is managed without loading everything. *When:* Long-horizon research or setup phases where the agent tends to quit before the groundwork is done.
- **Builder plus critics eval loop** — One agent builds the eval. A conceptual critic checks for leakage and logic errors, and a programmatic critic writes unit and integration tests. Loop the issues back to the builder until both critics approve. *When:* Before optimising against any eval an agent wrote, since a bad eval makes the whole optimisation meaningless.
- **Strategist, worker, and post-mortem Kanban loop** — A strategist proposes experiments as cards. Workers implement, submit jobs, and analyse results. Each finished job produces a post-mortem fed back to the strategist. Humans can add, cancel, or steer cards and chat with the strategist. A shared leaderboard tracks the best models. *When:* Running many parallel experiments on a shared compute cluster where you want both automatic learning and human steering.
- **Containerised, Kaggle-style eval contract** — Give the harness only the data, a description of the goal, and a containerised submission format. Show public leaderboard feedback to the agent and keep a private held-out validation set for humans. *When:* When an agent is optimising against a metric and you need to prevent it from gaming or overfitting the evaluation.
- **Environments as RL reward signal** — Build a small set (the speaker mentions 10 to 20) of carefully checked environments, then reuse them both as evals and as RL rewards for training open models with GRPO or on-policy distillation. *When:* When you want one investment in evaluation to also drive training or distillation.
- **Rubric grading of each rollout's process** — Read the traces, write down what a good practitioner's thinking looks like, and grade each rollout on how well it follows that process, not only on its final score. *When:* When outcome metrics do not capture whether the agent reasoned the right way, and you need to encode domain expertise.
- **Meta-harness optimisation by an LLM** — Have an LLM read run traces and results and improve the harness code, rather than having a human tune it by hand. *When:* When you already have a reliable eval and a harness with many design choices you cannot justify by hand.
- **Provider-agnostic harness with functional tool calls** — Write the harness yourself and expose a small set of tools (shell, web search, a compute abstraction) through functional tool calls, so swapping between OpenAI, Anthropic, or open models is easy. *When:* When you want to avoid lock-in to one vendor or one agent framework.

## Hot takes
- You should not be making the harness design decisions by hand. An LLM should do this meta-optimisation as a verifiable loop.
- General auto-research will become a commodity. The enterprise or expert value is in building environments, not in the agent loop.
- A bad eval breaks any automated optimisation, so the eval must be treated as the first thing to get right, and LLMs need critics for it.
