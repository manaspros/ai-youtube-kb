> Why running Xiaomi MiMo V2.6 Pro/Flash locally rarely beats the API on cost: weights already 4-bit, bandwidth caps speed, electricity alone outprices hosted tokens. Only privacy or speed justify it.

## Summary
The host works through the hardware and cost math for running Xiaomi's MiMo V2.6 Pro (about 1T parameters) and Flash locally. Xiaomi already shipped the expert weights in a native 4-bit format (MXFP4), so the usual "quantize it further" advice buys little and quality drops sharply below 4 bits. Memory needs are split between weights and KV cache; MiMo's hybrid attention keeps KV cost per token low, but cold prefill of long prompts is very slow. Hardware tiers are mapped by memory: 128 GB fits only a 2-bit Flash build, 256 GB is the practical Flash target, and Pro needs a roughly 768 GB server. Decode speed is bounded by memory bandwidth divided by bytes read per token, giving a hard ceiling under 16 tokens/s for Pro on a $40,800 EPYC box. Against API pricing ($0.87 per million output tokens for Pro, $0.28 for Flash), local hardware never breaks even on cost, and the host argues speed and data residency are the only real reasons to self-host. The video also flags a default config that caps output at 2048 tokens with sampling disabled, which silently truncates reasoning and causes tool-call loops, and it notes a 9B distilled MiMo variant that runs on a 12 GB GPU. Evidence is mostly secondhand (community benchmarks and forum threads) plus the host's own arithmetic.

## Key ideas
- **The Pro weights are already 4-bit, so further quantization is mostly pointless** — Pro is about 573 GB for roughly 1T parameters, about half a byte per parameter. The experts were trained natively in MXFP4, so the squeeze happened upstream. Community MLX 4-bit and 8-bit builds were both about 169 GB. Reported perplexity penalties: about 2% at 3.5-bit, 7% at 3-bit, 61% at 2-bit. ([1:23](https://youtu.be/3hMEcJCGne0?t=83))
- **MiMo's KV cache is cheap to store but slow to fill** — Most layers use a 128-token window; only 10 of 70 layers on Pro keep full history, about 51 KB per token, so a 1M-token context needs about 54 GB of KV. Prefill is the bottleneck: one report had a cold 1M-token prompt on Flash across two DGX Spark boxes taking 67 minutes before the first output token. Xiaomi's lead researcher reportedly said the next architecture will cut this 5x. ([3:56](https://youtu.be/3hMEcJCGne0?t=236))
- **Memory tier determines which MiMo build is usable at all** — 128 GB machines (DGX Spark about $4,700, Ryzen AI Max desktop about $3,450) only run a 2-bit Flash build, which reportedly hit 32 tok/s on one Spark but froze on a 32K-token llama-bench prompt. Flash needs about 190 GB with real working context, so 256 GB is the target. Options cited: Mac Studio M5 Ultra 256 GB at $11,300, or two linked DGX Sparks at about $9,400 (42-51 tok/s on code, falling to 12 tok/s at 200K context). ([5:17](https://youtu.be/3hMEcJCGne0?t=317))
- **Decode speed is capped by memory bandwidth divided by bytes read per token** — Pro's spec sheet (42B active parameters) hides that attention stays at 8/16-bit while only the experts are 4-bit. Per token the host estimates about 11 GB of expert reads and 26 GB of attention reads, roughly 39 GB total. Dividing a 614 GB/s EPYC server (768 GB DDR5, about $40,800) by 39 GB gives a ceiling under 16 tok/s. Squeezing experts to 2-bit still leaves about 28 GB per token. ([9:08](https://youtu.be/3hMEcJCGne0?t=548))
- **Local hardware never breaks even against hosted API prices** — Xiaomi API prices: Pro $0.87 per million output tokens, Flash $0.28, cached input about $0.003 per million. A local EPYC Pro box at about 9 tok/s and 550 W at $0.18/kWh costs about $2.90 in electricity per million output tokens, more than the API price. An $11,300 Mac Studio running Flash nonstop at 59 tok/s makes about 5M tokens/day, about 21 years to recoup the hardware. ([9:08](https://youtu.be/3hMEcJCGne0?t=548))
- **Self-hosting only makes sense for speed or data residency** — Hosted Pro runs about 18-40 tok/s and one benchmark prompt took over 30 minutes. A rig of two RTX Pro 6000 cards with a patched stack reportedly hit 190 tok/s, cutting one job from about an hour (hosted) or 37 minutes (M3 Ultra) to 11.5 minutes. The host says that rig costs over $30K and never saves money. Data-residency and compliance needs are the other legitimate reason. ([10:26](https://youtu.be/3hMEcJCGne0?t=626))
- **MiMo reasons verbosely, and the default config can silently truncate it** — On one comparison task MiMo used 131,400 reasoning tokens, nearly double DeepSeek V4.1 Flash. The shipped config caps max output at 2048 tokens with sampling disabled; thinking counts toward that cap, so replies get cut mid-thought, and greedy decoding can loop on the same tool call forever. Many tool-call complaints were attributed to serving bugs rather than the model. ([11:37](https://youtu.be/3hMEcJCGne0?t=697))
- **A 9B distilled MiMo variant is the practical local option** — MiMo V2.6 Distilled is a 9B model trained on Pro's answers, reported at 61 on SWE-bench Verified. Someone ran it on a 12 GB RTX 3060 at about 47 tok/s, which the host recommends as the model most people can run on hardware they already own. ([12:45](https://youtu.be/3hMEcJCGne0?t=765))

## Techniques
- **Check whether a release is already quantized before quantizing** — Divide the download size by parameter count. About 0.5 bytes per parameter means already 4-bit (MXFP4-style native experts). Compare sibling releases: if the previous generation was about 2x larger at the same parameter count, the squeeze happened upstream. Only go lower if you accept the quality curve (2% at 3.5-bit, 7% at 3-bit, 61% at 2-bit perplexity loss, per the host). *When:* Before downloading or planning a memory tier for any newly released open-weight model, especially MoE models with native low-precision expert weights.
- **Estimate the decode speed ceiling from memory bandwidth** — Sum the bytes read per generated token, counting active experts and always-active attention/shared weights at their stored precision. Ceiling in tok/s = memory bandwidth (GB/s) / bytes per token. Real throughput is lower. The host's example: 614 GB/s / 39 GB per token is under 16 tok/s. *When:* When sizing local hardware for a large MoE model, or when a quoted tok/s figure looks too good to be true.
- **Compare local vs API on electricity and break-even before buying hardware** — Electricity cost per million output tokens = (watts x hours) x price per kWh, where hours = 1,000,000 / (tok/s x 3600). Hardware break-even days = price / (API price per token x tokens per day - electricity per day). The host's inputs: 550 W, $0.18/kWh, 9 tok/s gives about $2.90 per million tokens. *When:* Deciding whether to self-host a model that has a hosted API price, or when someone claims local inference is cheaper.
- **Raise the output cap for reasoning models and turn sampling back on** — The host says Xiaomi's shipped config caps max output at 2048 tokens with sampling disabled. Thinking tokens count toward that cap. Raise the max output limit well above the default, enable sampling, and watch for repetitive tool-call loops. The exact config keys and file name are not shown in the video, so verify them against the model card. *When:* When a reasoning model's replies are cut mid-thought, or an agent repeats the same tool call indefinitely. Check serving config before blaming the model.
- **Measure prefill and decode separately for long contexts** — Time-to-first-token on a cold long prompt (prefill) can dominate, even when decode speed is fine. The host's example is 67 minutes to read a 1M-token prompt on two DGX Sparks. Benchmark prefill at your real context lengths (e.g. 32K, 64K, 200K) alongside tok/s, since speed can fall from 40 to 12 tok/s as context grows. *When:* When choosing hardware or a serving stack for agent workloads with large codebases in context.

## Hot takes
- Quantizing an already-4-bit native release is pointless and the 'just quantize it' advice from other creators does not apply to MiMo.
- Self-hosting a 1T-parameter MoE for cost savings never breaks even; the only real reasons are speed or data residency.
- Many tool-call loops and cut-off replies are serving-config bugs (2048-token cap, sampling disabled), not model failures.
- The host calls the release's hype and hosted speed issues out directly and says the 9B distilled variant is the most useful one for most people.
- No sponsorship detected. Cost figures rely on quoted prices and a stated electricity rate, and some hardware (M5 Ultra 512 GB) has no price yet. Several key numbers are single anecdotal reports.
