> Xiaomi AI Cube vs DGX Spark: headline specs measure different things. Batch size, concurrency, serving config and the network decide real throughput; the Cube is still unshipped.

## Summary
Kai Explains compares Xiaomi's unannounced AI Cube (D100 chip) with NVIDIA's DGX Spark and argues that the viral spec-sheet comparison mixes incompatible measurements. The video walks through five rounds (capacity, memory bandwidth, batch-size throughput, software configuration, multi-node scaling) and ends with buying guidance by workload. Xiaomi's 1.22 TB/s figure applies only to a small pool bonded next to the compute, and its 330 tok/s is a batch-one result on a 3B model, whereas a Spark developer published 1,095 tok/s across 32 concurrent requests on a 27B model. The speaker says his earlier "memory bandwidth decides everything" framing holds only for one machine and one user; above one box, the network fabric sets the ceiling. He also shows a Spark owner gaining roughly 10x from configuration flags, mainly by enabling prefix caching that the serving stack leaves off by default. Verdict: for one user, a used gaming GPU is faster; for parallel agents or a small team, the Spark works as a cheap server; the Cube has no price, date or public runtime yet.

## Key ideas
- **The headline numbers in the viral Xiaomi post describe different chips and conditions, so the 330 tok/s vs $4,500 Spark comparison is invalid even though both figures are real.** — Each of Xiaomi's five specs belongs to a different component; the speaker sorts them by chip and by measurement condition before any comparison. ([0:00](https://youtu.be/SeQ8qou_i-E?t=0))
- **Capacity is a gate, and Xiaomi's memory figure is unresolved.** — The Spark has a verified 128 GB, in stock at $4,699. Xiaomi's English headlines say 160 GB, but its Chinese copy attaches that to the D100 die ceiling; three readers independently got about 80 GB for the prototype. ([2:41](https://youtu.be/SeQ8qou_i-E?t=161))
- **The 1.22 TB/s figure is the speed of a small near-memory pool, not the bandwidth serving the large model.** — Xiaomi bonds two memory wafers onto the processor face to face at a claimed 1.4 micron pitch (TSMC production stacking about 6 microns, HBM4 about 10). One analyst estimates the pool at 3.5 to 4 GB, which the speaker flags as inference. A 120B model at 4-bit (~60 GB) can't run from that pool, so the demo must have used ordinary memory. ([4:53](https://youtu.be/SeQ8qou_i-E?t=293))
- **Batch size one is the bandwidth-bound regime; batching changes the picture completely.** — Xiaomi's 330 tok/s is a batch-one lab result on its 3B MIMO model. A developer's Spark run on a 27B model published 86 tok/s at 1 concurrent request, 508 at 8 and 1,095 at 32, because one weight read serves all concurrent answers. ([7:28](https://youtu.be/SeQ8qou_i-E?t=448))
- **Serving-stack defaults can leave a box running at a fraction of its capability.** — A Spark owner measured 7.9 tok/s at stock settings on a 27B model. After tuning, the same box hit 58.5 on edit-heavy work and 75 at 4-bit, roughly 10x from flags alone. The main factor was prefix caching, off by default for that model class and not announced at startup; enabling it made shared prompt processing 14 to 22 times faster. ([8:48](https://youtu.be/SeQ8qou_i-E?t=528))
- **Xiaomi has not published a runtime, so there is nothing to benchmark yet.** — No backend in llama.cpp or vLLM, no quantization path and no loading docs. The speaker's signal to watch is an X-ring backend merging into llama.cpp or vLLM; until then he guesses the first customer is a Xiaomi robot. ([10:07](https://youtu.be/SeQ8qou_i-E?t=607))
- **Above one machine, the network fabric decides performance, and memory bandwidth stops being the ceiling.** — A 16-node Spark cluster on a 400 Gb switch runs a frontier-class open model at over 50 tok/s single-stream. Four Sparks reach 124 tok/s on one model where two reach 85. The speaker's earlier framing was corrected: dropping fabric from 200 Gb to 100 Gb cost 2% token generation but 20% prompt processing. ([11:28](https://youtu.be/SeQ8qou_i-E?t=688))
- **Buy by workload: single-user, parallel agents, or capacity for a small team.** — For one person asking one question at a time, a used gaming GPU is 2 to 4x faster on models that fit its VRAM. For parallel agents or a small team, the Spark is an inexpensive server; one buyer estimated about two years to pay back at six concurrent sessions against current API pricing, and never at one request at a time. ([12:52](https://youtu.be/SeQ8qou_i-E?t=772))

## Techniques
- **Normalize vendor throughput claims before comparing** — For each figure, record the chip, model size, precision, batch or concurrency level, and which memory pool it measures. Only compare numbers that match on all of those; mismatched figures get labelled as different products. *When:* Reading or writing any hardware comparison for local inference, or any tokens-per-second claim.
- **Benchmark a box at several concurrency levels** — Run the same model at 1, 8 and 32 concurrent requests and report tok/s per level as a table (the speaker's example: 86, 508, 1,095 tok/s on a 27B model on one Spark). Reading the table shows whether the workload is bandwidth-bound (batch 1) or compute-bound (high batch). *When:* Sizing a local inference box for a team or parallel agents, or deciding whether batching is worth configuring.
- **Check the serving stack's defaults before judging hardware** — Compare stock and tuned runs of the same model (speaker: 7.9 vs 58.5 and 75 tok/s). Look for features that default to off without a startup warning, and prefix caching in particular: enable it when many requests share a prompt prefix (speaker: 14 to 22x faster shared prompt processing). *When:* Benchmarking a local serving stack (vLLM, llama.cpp or similar), or when a box looks slow for its spec.
- **Test network sensitivity before scaling out** — Measure token generation and prompt processing separately while halving the inter-node link speed (speaker: 200 to 100 Gb cost 2% and 20%). Prompt processing is the more fabric-sensitive metric. *When:* Designing a multi-node inference cluster or deciding whether a fabric upgrade is worth it.
- **Fit check and payback arithmetic for a purchase** — Check that the model fits the memory pool it actually runs from (speaker: 120B at 4-bit is about 60 GB, so it cannot run from a 3.5 to 4 GB near-memory pool). Then compare the box's cost against API spend at the expected concurrency: payback at six concurrent sessions was about two years, and never at one request at a time. *When:* Deciding whether to buy a unified-memory box or a GPU for local models versus paying for hosted APIs.

## Hot takes
- Comparing Xiaomi's 330 tok/s with the $4,500 Spark is an apples-to-oranges comparison; both figures are real but measure different things.
- Memory bandwidth decides speed for one machine and one user only; above one box, the network fabric matters more.
- The Spark's throughput at high concurrency (1,095 tok/s on a 27B model) is far higher than its batch-one number, so single-stream benchmarks mislead for multi-user workloads.
- Xiaomi's first customer for the chip is probably a Xiaomi robot (speaker's guess), and its Cube will probably be cheap (speaker's prediction; cites the 5% margin pledge).
- Default serving configurations can leave hardware at a tenth of its capability with no warning (the prefix-caching example).
