> Nishant Gupta (Meta Superintelligence Labs) argues agent evals must score workflow behavior from production telemetry, not model answers or benchmarks, and should run continuously as a control-plane function.

## Summary
The speaker says benchmarks measure model capability while production measures system behavior, so agent teams need to ask whether the system behaved correctly, not whether the answer was right. He describes a failure hierarchy for agents, from memory, retrieval and safety problems at the bottom up to reasoning, planning, tool execution and multi-agent coordination failures. He recommends an SRE-style view that prioritises reliability, latency, cost and recovery over accuracy, and he frames evaluation as a pyramid with benchmarks at the base, scenario-based evals in the middle and production telemetry at the top. Production traces, outcomes, escalations and feedback are presented as the largest and most representative eval data, with humans acting as evaluators who calibrate automated metrics. He argues that agent drift is gradual, so continuous monitoring is needed, and that agent traces should work like distributed tracing. The talk ends with a continuous eval loop and an architecture where evaluation sits in a control plane that observes a separate execution plane. The talk gives no benchmark results, costs or latencies, so its value is in the framing rather than the data.

## Key ideas
- **Benchmarks measure model capability; production measures system behavior** — A model can rise from 90% to 92% on a benchmark and production reliability can still be poor, because benchmarks miss tool failures, API outages, context changes, user variability and long-running workflows. The question shifts from 'was the answer right' to 'did the system behave correctly'. ([0:03](https://youtu.be/vljxQZfJ9wY?t=3))
- **Evaluate workflows, not single outputs, and expect a failure hierarchy** — Agent failures are layered: memory, retrieval and safety at the base; reasoning, planning and incorrect tool execution above; multi-agent coordination failures at the top. Hallucination is only one category, and judging the final output alone misses most production risk. ([1:30](https://youtu.be/vljxQZfJ9wY?t=90))
- **Adopt an SRE mindset and build evals as a pyramid** — Track reliability, availability, latency, cost and recovery rather than accuracy. Benchmarks are at the base (scalable but low value), scenario-based evals in the middle, and production telemetry at the top, which the speaker calls the highest-value signal. ([2:31](https://youtu.be/vljxQZfJ9wY?t=151))
- **Production traffic is the main eval dataset, and humans are evaluators** — Execution traces, user outcomes, escalations, failures and feedback all become eval data. Humans assess correctness, trust, usefulness and safety, and their reviews calibrate automated metrics and expose their blind spots. The speaker rejects treating humans as a fallback. ([4:02](https://youtu.be/vljxQZfJ9wY?t=242))
- **Drift is gradual, so evaluation must run continuously** — Model versions change every few weeks or months, and prompts, tools and user behaviour also change. No single change looks catastrophic, but success rate can decline and escalations and tool failures can rise. Without continuous evaluation, teams often learn about drift only when users complain. ([4:02](https://youtu.be/vljxQZfJ9wY?t=242))
- **Observability and evaluation are one discipline** — Evaluating an agent needs visibility into reasoning paths, tool calls, memory access, execution timelines and state transitions. Plain logs are not enough, so agent traces should work like distributed tracing for microservices. ([5:35](https://youtu.be/vljxQZfJ9wY?t=335))
- **Evaluation is a post-deployment loop, not a pre-release phase** — Telemetry flags issues, humans review the edge cases, feedback updates the datasets, and offline scenarios validate each change before it ships. The speaker says the loop never stops and calls evaluation an operational capability. ([5:35](https://youtu.be/vljxQZfJ9wY?t=335))
- **Map each metric to a business outcome and leave accuracy out** — Task completion measures value delivered, tool success measures reliability, escalation rate measures human burden, and safety violations, latency, cost and recovery rate cover risk, user experience, scalability and resilience. The speaker says accuracy is missing from the list because business success depends on more than accuracy. ([6:38](https://youtu.be/vljxQZfJ9wY?t=398))
- **Put evaluation in a control plane that governs a separate execution plane** — A control plane observes the system, collects telemetry, runs simulations and coordinates human review, while the execution plane does the work. The speaker presents this separation as a foundational pattern for production AI systems, though he gives no implementation details. ([6:38](https://youtu.be/vljxQZfJ9wY?t=398))

## Techniques
- **Scenario-driven offline evals** — Build simulated environments for end-to-end workflows such as customer support, code generation or research. Run the agent inside them and score task completion rate, tool correctness, planning quality and resource usage. Evaluate scenarios rather than individual prompts. *When:* Before shipping model, prompt or tool changes, to check whether a whole workflow still works.
- **Production telemetry as the eval set** — Capture execution traces, user outcomes, escalations, failures and feedback signals from live traffic and treat them as evaluation data. *When:* After deployment, as the main source of signal, and to find failure modes that benchmarks miss.
- **Targeted human review to calibrate automated evals** — Route edge cases and low-confidence or failed interactions to human reviewers. Use their judgments on correctness, trust, usefulness and safety to refresh the datasets and check the automated metrics for blind spots. *When:* When automated metrics may not capture correctness, trust or safety, and to keep the automated judges honest.
- **Continuous evaluation loop** — Telemetry flags issues, humans review them, the feedback updates the datasets, offline scenarios validate the fix, and the change is redeployed. The loop runs continuously. *When:* When models, prompts or tools change often and reliability can drift without anyone noticing.
- **Agent tracing like distributed tracing** — Record reasoning paths, tool calls, memory access, execution timelines and state transitions for each run, in the way a microservice trace records spans across services. *When:* To make evals possible and to debug multi-step or multi-agent failures.
- **Evaluation as a control plane** — Separate the components that observe, simulate, evaluate and review (control plane) from the components that do the work (execution plane). The control plane measures and governs behaviour. *When:* When many agent systems need the same governance and eval layer, rather than a separate one-off test tool per system.

## Numbers
- Illustrative only: a benchmark moving from 90% to 92% is the kind of gain teams celebrate, yet it does not show production reliability. No measured production data is given. ([0:03](https://youtu.be/vljxQZfJ9wY?t=3))
- Agent systems are updated with a new model version every couple of weeks or months, on top of prompt, tool and user-behaviour changes. ([4:02](https://youtu.be/vljxQZfJ9wY?t=242))
- Metrics the speaker lists for production agents: task completion, tool success, escalation rate, safety violations, latency, cost and recovery rate. He gives no target values for any of them. ([6:38](https://youtu.be/vljxQZfJ9wY?t=398))

## Hot takes
- Benchmarks are the lowest-value eval signal, and production telemetry is the highest.
- Accuracy should not be the headline metric for agent systems; business outcomes should be.
- Humans are evaluators, not a fallback for when automation fails.
- Evaluation is becoming production infrastructure, not a testing or QA function.

## Relevance to our work
- **agentos** (2/3): AgentOS has L4 observability and RAGAS evals, but no per-workflow task-completion or recovery signal from live traffic. The control-plane framing fits its proxy and manifest design. → *Have the L1 proxy emit a per-request trace record (tool calls, failure or escalation flag, cost, latency) so that a scenario-based eval set can be built from real traffic.*
- **prosharness** (2/3): Checkpoint and resume, loops and phone-driven approvals already produce the recovery, escalation and tool-failure signals the talk names as production eval data. → *Log per run: resumes that completed (recovery rate), approval prompts sent to the phone (escalations) and tool failures. Replay failed checkpoints as scenarios in an offline eval set.*
- **general** (2/3): Matches the recurring interest in evals for agents. The talk gives a usable split of offline scenarios, production telemetry and human review, but no numbers or method details. → *Use the scenario-over-prompt split (offline scenarios, production telemetry, human calibration) as a checklist when designing the next agent eval harness, and validate its value with your own data.*
