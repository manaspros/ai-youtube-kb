> Kai Explains works through what it would take to run an Opus-class model locally, using open-weight Kimi K3 as a stand-in; the bottleneck is memory bandwidth and the electricity bill, not the hardware price.

## Summary
The host starts from his own Anthropic bill and prices a local Opus 5 setup. Since Anthropic has published no parameter count for Opus 5, he uses Moonshot's open-weight Kimi K3 (2.8T-parameter MoE) as a stand-in, arguing that Opus 5 is at least as hard to run. He stresses that Mixture-of-Experts cuts compute per token but not storage, so the smallest usable quant still needs about 610 GB. He lays out three hardware tiers, from a rented 4xA100 box to seven 96 GB RTX Pro 6000 cards (about $112k at the August NVIDIA listing) to a DGX B300 setup. The one measured run in the video produced 0.1 tokens/s with 0-1% GPU utilization, which he attributes to memory bandwidth rather than compute or capacity. He estimates about $565/month in electricity for the seven-card build (GPUs only) and compares that against API list prices, concluding that breakeven depends on which API price you are trying to replace. He lists four cases where local still makes sense: very high volume, data that cannot leave the building, 24/7 agents, and protection against price or model changes.

## Key ideas
- **Opus 5 has no published parameter count, so the video sizes hardware with Kimi K3 (open weights, published size) as a stand-in and argues Opus 5 is at least as hard to run.** — Kimi K3: 2.8T total parameters, 93 layers, 896 experts per layer, 16 routed per token (about 3.7% active). Released on Hugging Face on July 27 of this year. ([1:20](https://youtu.be/yJCHNdQ8sLs?t=80))
- **MoE reduces compute per token but not storage: every expert must stay resident because the router picks different ones for each token.** — Speaker's warehouse analogy: MoE does not make the warehouse smaller, it means each order visits only 16 of 896 aisles. Quant sizes: 4-bit 1,508 GB, 2-bit 861 GB, smallest usable ~1.5 bits per parameter 594 GB over 14 shards, about 610 GB of memory with KV cache and overhead. ([2:49](https://youtu.be/yJCHNdQ8sLs?t=169))
- **Three hardware tiers: technically runs, actually usable, and no compromises. The tier most people assume they are in is not the one they would be in.** — Tier 1: rented 4xA100 (160 GB VRAM, 2 TB RAM, $3.87/hr), 594 GB quant loaded in about 9 minutes. Tier 2: seven 96 GB RTX Pro 6000 Blackwells (880 GB), about $8,500 at launch and $16,000 on NVIDIA's listing on Aug 13, so about $112k of GPU, 600 W each (4.2 kW). Tier 3: DGX B300 x8 (2.3 TB GPU memory, 10 RU); Moonshot's own blog recommends 64+ accelerators for efficient inference. ([4:07](https://youtu.be/yJCHNdQ8sLs?t=247))
- **The one measured run was limited by memory bandwidth, not compute or capacity: 0.1 tokens/s on four data-center GPUs with 0-1% utilization.** — Only 64 of 160 GB VRAM was occupied. At 0.1 tok/s a 128-token benchmark did not finish in 17 minutes; a 500-token reply projects to about 1 h 23 min. Speaker's framing: VRAM decides whether the weights fit, bandwidth decides how fast each token is produced. ([5:26](https://youtu.be/yJCHNdQ8sLs?t=326))
- **Capacity and bandwidth are sold separately. The machines with the most memory tend to have the least bandwidth.** — Bandwidth figures quoted: RTX 5090 about 1,790 GB/s (32 GB); 512 GB Mac Studio 819 GB/s; DGX Spark 273 GB/s; Ryzen AI Max about 215 GB/s; H100 3.35 TB/s (80 GB). Unsloth cites roughly 20 tok/s on B200-class hardware, about 200x the measured 0.1 tok/s. ([6:52](https://youtu.be/yJCHNdQ8sLs?t=412))
- **Electricity is a real recurring cost. At 18.44 cents/kWh (EIA May figure), the seven-card build costs about $565/month for GPUs alone.** — 4.2 kW x 24 h = $18.59/day, about $565/month, about $6,786/year. Excludes CPU, RAM, PSU losses and cooling; the room must stay under about 30 C. State rates vary: Idaho about 12 cents, Rhode Island and California over 26 cents. ([8:11](https://youtu.be/yJCHNdQ8sLs?t=491))
- **Breakeven is a property of which API bill you are trying to eliminate, not of the rig. Opus-class output at $25/M and DeepSeek at about $0.13/M give opposite verdicts.** — Petrenko (DGX Spark at $4k pays back in 1.6 months vs list API at full utilization; two used 3090s in 3 months) concludes most setups never break even at 80% annual price decline and under 25% utilization. ([10:46](https://youtu.be/yJCHNdQ8sLs?t=646))
- **The four rational cases for local inference: industrial volume, data that legally cannot leave the building, 24/7 agents where the meter never stops, and protection against vendor price or model changes.** — Speaker notes Opus 5 went from $15/$75 to $5/$25 per million tokens within a year, a cut that could reverse. He says the network becomes the bottleneck even after the hardware is solved. ([14:41](https://youtu.be/yJCHNdQ8sLs?t=881))

## Techniques
- **Size the local rig from the smallest usable quant plus KV cache, not from headline parameter count** — Take the actual quantized file sizes (not textbook bits-per-weight estimates), add KV cache and runtime overhead to get the memory floor. For MoE models, count all experts as resident because routing can pick any of them on the next token. Speaker's floor for Kimi K3: 594 GB file, about 610 GB with overhead. *When:* Before buying or renting hardware for any MoE model. Use it to size memory and to read a pruned build (such as a 512 GB 'REAP' variant) as a signal that the model does not fit.
- **Estimate decode speed from memory bandwidth, and compare hardware on bandwidth, not capacity** — Speaker's framing: each token walks the full set of active experts, so decode speed is limited by memory bandwidth. Compare bandwidth numbers across candidate machines (RTX 5090 about 1,790 GB/s, DGX Spark 273 GB/s, H100 3.35 TB/s). He does not state an explicit formula; a common reading is tokens/s is roughly bandwidth divided by bytes read per token, which is an inference from his framing. *When:* When evaluating whether a model is usable on a given box, before benchmarking. A high-memory machine with low bandwidth can hold a model and still be unusable.
- **Diagnose a slow local run by checking VRAM occupancy and GPU utilization** — Speaker's diagnostic: during the slow run, GPU utilization was 0-1% and only 64 of 160 GB VRAM was used. Low utilization with spare memory points to a bandwidth or data-movement limit, not a compute or capacity limit. *When:* When a local model runs far below expected speed and the config looks correct, before changing the quant or the model.
- **Benchmark with a short generation and extrapolate to a target reply length** — Generate a fixed token count (speaker used 128 tokens) and time it, then project to a realistic reply length (500 tokens). Speaker's run took 17 minutes without finishing 128 tokens, which projected to about 1 h 23 min for 500. *When:* As a quick go/no-go test before committing to a long run or a hardware purchase.
- **Compute breakeven against the specific API price you would replace, including utilization and price decline** — Monthly power = kW x 24 x 30 x $/kWh (4.2 kW at 18.44 cents = about $565/month for GPUs only). Compare to tokens per month x the API price of the model you would actually substitute (Opus-class $5/$25 per M in/out, cache reads $0.50, batch halves both; DeepSeek about $0.13/M blended). Include hardware depreciation, utilization (under 25% rarely breaks even per Petrenko), and the price decline rate (Epoch AI median 50x/year as cited). *When:* Before deciding between a local rig and a hosted API, and when two breakeven analyses disagree (check which API each one assumed).
- **Watch interconnect bandwidth when splitting a model across machines** — Speaker's measurement: going from 200 Gb to 100 Gb networking cost about 2% of token generation speed but about 20% of prefill speed. Measure prefill separately from decode when assessing multi-node setups. *When:* When a model is sharded over several boxes, especially for workloads with long prompts where prefill dominates.

## Hot takes
- The punchline is memory bandwidth (walking speed), not GPU price: a rig can hold a model and still produce 0.1 tokens/s.
- Breakeven is a property of which bill you are trying to eliminate: replacing Opus-class output and replacing DeepSeek-class output give opposite answers.
- Electricity is the smaller half of the story; the bigger issue is that the local model (Kimi K3) is not Opus 5, and Opus 5 has no public weights.
- For most individual coding users, none of the four rational cases apply and local economics are indefensible.
- When people prune a model to fit a box (for example, a 512 GB pruned build), the fit is the problem.
