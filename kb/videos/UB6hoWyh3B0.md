> Wells Fargo built a ~1B-parameter transformer pre-trained from scratch on customer transaction data as a reusable backbone; it beat its production XGBoost fraud model on detection rate and false positives.

## Summary
Freddy Lecue of Wells Fargo describes building the bank's first foundation model on tabular transaction data instead of text. The goal is one backbone, pre-trained on billions of debit, credit, digital and check transactions, that can be fine-tuned for fraud, credit line increases, anti-money laundering and marketing. The model is a decoder-only transformer with about 1B parameters, pre-trained from scratch with the next-transaction objective, and the speaker says the tokenization and post-training are the real work. The main hard part was designing the vocabulary: deciding which transaction fields become tokens, how high-cardinality fields like zip codes are grouped, and how to keep the vocabulary trainable. The model replaced hand-engineered features with raw fields, which the speaker says let attention capture relationships between a transaction and the customer's history, something gradient-boosted trees miss unless those relationships are hand-encoded. On fraud classification it beat the XGBoost production model on detection rate and false positives, which the speaker ties to millions of dollars in savings. Latency detail is contradictory in the talk: it is first said to beat XGBoost on latency, then to be about 10x slower but within the 250 ms decline budget. Evidence is a single internal case study with no published baselines or exact figures.

## Key ideas
- **Foundation models need not be language-based; bank transaction data is mostly tabular, and one backbone can serve many downstream tasks.** — Motivation: replace many siloed per-task models (credit scoring, fraud, AML, marketing) with one pre-trained transaction backbone that every team reuses. ([0:08](https://youtu.be/UB6hoWyh3B0?t=8))
- **A transformer on transactions beat the production XGBoost model on fraud detection and latency.** — The speaker says the transformer gave a higher detection rate and fewer false positives than XGBoost. Latency is stated as better here but later as about 10x slower (within the 250 ms budget), so treat the latency claim as unclear. ([2:10](https://youtu.be/UB6hoWyh3B0?t=130))
- **Pre-train from scratch on own data; the next-transaction objective is a means, not the goal.** — They reuse open architectures but no pretrained weights. The next-token/next-transaction pre-training teaches representations, which are then fine-tuned or post-trained per downstream task. ([4:47](https://youtu.be/UB6hoWyh3B0?t=287))
- **Use raw fields, not hand-built features, and let attention learn the interactions.** — Fields are grouped along five dimensions: who (customer/merchant), what, how (channel), when and where. Thousands of engineered features were reduced to a smaller set of raw units. ([6:02](https://youtu.be/UB6hoWyh3B0?t=362))
- **Tokenization is the secret sauce: deciding what each token encodes and keeping the vocabulary trainable.** — Numerical, categorical and high-cardinality fields (zip code, IP, amount, time delta) each need a token scheme. A zip-code-per-token vocabulary is too large, so codes are grouped by distribution. Each transaction maps to token IDs and then embedding lookups. ([8:11](https://youtu.be/UB6hoWyh3B0?t=491))
- **Model size and token budget came from Chinchilla-style scaling, then were tuned empirically.** — They started from the usual 20 tokens per parameter, then found they needed far more tokens per parameter in this domain. The model is about 1B parameters, chosen as the smallest size that gave the largest boost, with an 11B version in progress. ([9:31](https://youtu.be/UB6hoWyh3B0?t=571))
- **Why transformers help fraud: attention reaches the customer's past transactions, which GBDT loses.** — A GBDT only sees the current transaction unless the history is hand-encoded. The transformer attends from the current transaction to past transactions, and at inference the input is the customer's transaction sequence. ([13:22](https://youtu.be/UB6hoWyh3B0?t=802))
- **Results are framed as detection rate and false positives, which map directly to cost.** — A false positive means a blocked legitimate transaction, which costs a support call and lost revenue. The speaker says the gain is millions of dollars, without giving a figure. ([15:38](https://youtu.be/UB6hoWyh3B0?t=938))
- **One pre-trained backbone is now being reused for several downstream tasks across the bank.** — Fraud detection is done. Credit line increase, anti-money laundering and marketing are under investigation on the same foundation. ([16:49](https://youtu.be/UB6hoWyh3B0?t=1009))

## Techniques
- **Transaction tokenization for tabular data** — Map each transaction's fields (numerical, categorical, zip code, IP, amount, time delta) to vocabulary tokens. Use one token for low-cardinality categories (about 8 types) and more tokens or grouped tokens for large domains. Group high-cardinality values such as zip codes by distribution rather than one token each. Then do token ID lookup and embedding lookup per transaction. *When:* Pre-training a foundation model on structured or tabular records where the vocabulary is domain-specific and too big to tokenize naively.
- **Raw-field representation instead of hand-engineered features** — Start from the smallest set of raw information units across dimensions (who, what, how, when, where). Let transformer attention learn the interactions instead of building engineered cross-features. *When:* When existing feature-engineering pipelines are costly, and the model must reuse the same representation across many tasks.
- **Decoder-only pre-training on a transaction sequence, then task fine-tuning** — Pre-train a decoder-only transformer from random init on the next transaction/token, with the context being the customer's prior transactions. Keep the pre-trained backbone and fine-tune or post-train a head per downstream task such as fraud classification, credit line increase or AML. *When:* When one proprietary event-sequence dataset supports many downstream tasks and a single backbone is wanted.
- **Scaling-law sizing with empirical correction** — Start from Chinchilla-style tokens-per-parameter estimates, then run experiments. The speaker found they needed substantially more tokens per parameter than the initial 20x guess. Pick the model size by the smallest size that gives the biggest downstream lift. *When:* Choosing parameter count and training-token budget for a new domain where published scaling curves may not apply.
- **Standard large-scale training recipe** — Mixed precision, distributed data parallel, maximized macro-batch size, RoPE, Flash Attention, activation checkpointing. The auto-captions say Muron (probably AWS Neuron) for faster compute. Evaluate with perplexity on pre-training and accuracy dashboards on downstream tasks. The speaker stresses that this part is not novel. *When:* Baseline recipe for training a transformer of about 1B parameters on a GPU cluster.
- **Benchmark against the production GBDT on business metrics** — Compare the new model to XGBoost on detection rate and false-positive rate at the operating point, plus decision latency against the 250 ms budget. Convert the deltas into cost (blocked legitimate transactions, call-center and lost-revenue effects). *When:* Replacing a production classifier where false positives have a direct cost.

## Hot takes
- For structured transaction data, a domain-specific transformer pre-trained from scratch can beat a tuned GBDT on fraud, and the reason given is that attention reaches past transactions.
- The secret sauce is tokenization and post-training, not the architecture, which the speaker calls nothing fancy.
- Language-model recipes (next-token pre-training, then SFT/RLHF) transfer to structured event data, but the vocabulary has to be designed from scratch.
- Latency claims contradict each other within the talk (better than XGBoost at 2:10; about 10x slower at 14:37). No baseline numbers are given.
