> Walkthrough of Apple's new Container Machines, persistent per-container Linux VMs on macOS built on Apple's open-source container CLI, with benchmarks against OrbStack and Docker Desktop and the main caveats.

## Summary
Better Stack presents Apple's Container Machines, a lightweight persistent Linux environment on macOS built on Apple's container project (a Swift, OCI-compatible Docker alternative released last year). The walkthrough builds an Ubuntu image from a Dockerfile, creates a default machine with the container machine create command, and shows that the host home directory is mounted read-write, so files edited on the Mac are immediately visible in Linux. It notes that dev-server hot reload did not pick up edits made from macOS, and suggests connecting an editor over SSH as a workaround (unverified). The architecture point is that each container gets its own lightweight VM via Apple's Virtualization framework, instead of sharing one Linux VM as Docker Desktop does, which the speaker frames as better isolation, selective mounts and lower memory use. Benchmarks from a linked third-party repo show Apple's tool roughly level with OrbStack and Docker Desktop on CPU and memory throughput, but slower on tiny-container startup (still sub-second). The main caveats are that memory is held until the machine restarts, there is no GPU or USB passthrough, GUI apps are awkward, and the home mount cannot be narrowed to one folder. The speaker says he would still use OrbStack for now, and Apple's tool beats Docker Desktop if OrbStack's paid licence is a problem.

## Techniques
- **Build a dev machine image from a Dockerfile** — Write a Dockerfile on an Ubuntu base image with the common dev tools installed. Build it with Apple's container tool and give it a local tag. The exact build flags are not shown in the transcript. Any OCI image should work, as long as it includes a system init program. *When:* You need a repeatable Linux target on macOS that matches a deployment distro, such as Ubuntu for a server build or a test stack.
- **Create, list and run a container machine** — Run `container machine create` with the image, a friendly name and the default flag. Check it with `container machine list`, which shows IP, CPUs and memory. Enter it with `container machine run`, optionally with a command after it. The transcript shows `run` with no command opening an interactive shell; the create flags are not shown. *When:* You want a persistent Linux shell on the Mac without a Docker-style compose setup, and you want commands to target it by default.
- **Use the Mac project files from inside Linux** — Work in the normal macOS project folder with macOS tools. Run the build or test command from inside the machine with `container machine run`. The home directory is mounted read-write, so no file copy step is needed. Keep Linux-only dotfiles in the machine's separate home volume. *When:* You want to compile or test a Linux binary from a Mac without transferring files.
- **Edit files over SSH for breakpoints and hot reload** — Connect the editor to the container machine over SSH and edit the files there, rather than editing from macOS. Apple's documentation has a tutorial for the setup. The speaker says this is expected to make breakpoints and hot reload work, but did not show it working. *When:* Dev-server hot reload or debugger breakpoints do not update when files are changed from macOS.
- **One machine per distro target** — Create several container machines with different base images, such as Alpine, Ubuntu and Debian, and keep them side by side. Each runs a real init system, so you can run services like Postgres alongside the app. *When:* You need to test cross-distro behaviour or a multi-service stack that must match a Linux production server.
- **Narrow the home mount before running untrusted code** — Container Machines can only mount the whole home directory read-write, read-only, or not at all, with no single-folder option. Use read-only or no mount for any untrusted code. Keep credentials outside the mounted home directory. *When:* Running agent-written or third-party code in a machine that would otherwise expose SSH keys and cloud credentials.

## Hot takes
- Apple's new Container Machines is an early, unpolished option, not a replacement for OrbStack. The speaker says it still lacks dynamic memory release and passthrough.
- The read-write home directory mount is a security problem for anyone running untrusted or agent-written code, since it exposes SSH keys and cloud credentials.
- The 'Apple just built WSL' framing is a headline stretch. The video itself describes fast lightweight VMs that behave like a Linux server, not a WSL clone.
- The editor-over-SSH fix for hot reload and breakpoints is unverified in the video.
