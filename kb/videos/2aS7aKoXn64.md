> Theta Software on designing RL environments and LLM judges for long-horizon work, plus a critique of current finance agent benchmarks, which they say are saturated and mostly too short to count as long-horizon.

## Summary
Two co-founders of Theta Software (a company building RL environments and data) argue that "long horizon" is a relative, scalar property, not a binary one, and that it should be measured against both human task time (METR-style 50% thresholds) and model-side units like tokens, steps and tool calls. They describe environment complexity along three axes: tool coordination, state change (parallelizable versus sequential work), and ambiguity in the starting materials. The second half covers verification for soft-verifiable domains, where a judge or critic model replaces unit tests. They recommend making the judge an agent with read-only access to the environment, making long trajectories queryable, and avoiding reference-answer matching for open-ended tasks. The talk ends by critiquing GDPval, BankerToolbench and APEX-Agents as too short, too narrow and too saturated, and by presenting their own finance dataset (about 15 human-hours per task) with no model scores shown on screen.

## Key ideas
- **Long horizon is a scalar, not a binary label. Measure it two ways: human-time horizon (e.g. METR's 50%-success threshold, where a model completes tasks that take a human 16 hours) and model-side units such as tokens, steps and tool calls. Each is noisy alone.** — Token counts depend on model and harness, so a task's token cost only means something when variables are held constant. Human time is also a poor proxy because tasks that are tedious for experts can be trivial for agents. ([1:36](https://youtu.be/2aS7aKoXn64?t=96))
- **Environment complexity has three axes to measure: tool coordination (how many tools must be used and linked), state change (sequential tasks where an early bad query cascades, versus parallelizable reads), and ambiguity in the starting instructions and artifacts.** — Chaining unrelated independent subtasks makes a task look longer without testing real capability. The valuable case is one where earlier decisions shape later ones. ([6:16](https://youtu.be/2aS7aKoXn64?t=376))
- **Soft-verifiable domains (economically valuable work, not math or unit-test tasks) need judge or critic models to set reward, because you cannot run a script to check the output.** — The judge looks at the final environment state and at the trajectory that produced it. Deterministic verifiers still help as artifact generators or metric collectors feeding the judge. ([10:06](https://youtu.be/2aS7aKoXn64?t=606))
- **Judging the trajectory catches reward hacking that outcome checks miss, such as escaping a sandbox or reading a hidden test suite.** — Strengthening the verifier and environment setup also helps, but the judge is what catches these behaviours in the trajectory. ([11:24](https://youtu.be/2aS7aKoXn64?t=684))
- **Reference-answer comparison fails for open-ended tasks because many correct solutions exist. Over-constraining the trajectory also collapses the set of paths the agent explores.** — Rubrics with partial credit, including dynamic rubrics that assume earlier mistakes and grade the rest, are used instead. ([12:40](https://youtu.be/2aS7aKoXn64?t=760))
- **Judges are agents too. They need the same harness and observability as the agent, with safeguards: read-only permissions, so they cannot trigger deployments. Trajectories are long enough that the judge must query them through a database and sub-agents, segmented into phases such as log reading, coding and post-deploy verification.** — The example is a CI/CD failure task where the judge checks GitHub Actions and CloudWatch after the agent's PR is merged, rather than trusting the agent's tool calls. ([13:40](https://youtu.be/2aS7aKoXn64?t=820))
- **Critique of public finance benchmarks: GDPval, BankerToolbench and APEX-Agents have short average human task times (below the long-horizon threshold), are already near saturation (APEX pass@1 is 100% solved on 57% of IB cases), are narrow in domain, and give coarse reward signals. Rubrics need many sub-criteria per criterion.** — The speakers' own finance dataset averages about 15 human-hours per task over 50 tasks. The talk reports mean@5 but shows no model scores on screen. ([18:21](https://youtu.be/2aS7aKoXn64?t=1101))

## Techniques
- **Judge with read-only environment access, as an agent** — Give the judge the same tool harness as the agent (new tools included), but enforce read-only permissions on the environment. The judge should re-check external state after the agent finishes (e.g. CI logs, cloud logs, post-merge deploy status) and never be able to mutate it. *When:* Open-ended tasks where the trajectory alone cannot show whether the task succeeded, such as deploy-and-fix workflows.
- **Make long trajectories queryable before judging** — Store the trajectory in a database. Use sub-agents to enrich steps with metadata and segment the run into phases (e.g. reading logs, writing code, verifying). The judge then queries for critical steps and failure points and checks whether each one is a real failure. *When:* Trajectories are too long for one judge call, and the judge needs to find specific failure points.
- **Pair deterministic checks with a rubric judge** — Let deterministic verifiers generate artifacts or metrics that the judge reads, rather than replacing the judge. Use dynamic partial-credit rubrics: assume the earlier answer was right and grade the later steps on that basis. *When:* A task has some checkable parts and some open-ended parts, and you need partial credit for multi-step work.
- **Rubric QA suite** — Run gold-answer, no-op (no change should score low) and variant tests on every rubric. As AI is used to create or verify rubrics, add coverage tests and expert-agreement tests on top. *When:* Before trusting any LLM-judged reward or eval, especially for long-horizon tasks.
- **Check learnability and reward density** — Keep rubrics sharp rather than overloaded, since overloaded rubrics are applied inconsistently by judges. Check the task distribution and the underlying data for learnability, so compute is not wasted on tasks the model cannot learn from. *When:* Designing RL environments where the model is near the edge of its ability.

## Hot takes
- Public long-horizon finance benchmarks (GDPval, BankerToolbench, APEX-Agents) mostly fall below the human-hours threshold for long-horizon tasks and are already saturated, so they are weak for training or evaluation.
- Human-time horizon and model-token horizon both mislead when used alone; a task's length is relative and changes as models improve.
- Judges with a reference answer do not work for open-ended tasks; judges need the same harness as the agent and read-only access to live environment state.
- The speakers' finance dataset (about 15 human-hours per task) is presented as the better alternative, but no model scores are shown, so its difficulty claims cannot be checked from the talk.
