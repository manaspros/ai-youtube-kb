> How to do forward deployed engineering: audit a business process before building, sort each step into software, model or human, then eval against real cases. Useful method, but includes a sponsored segment and unsourced stats.

## Summary
The video explains the forward deployed engineer (FDE) role as getting a business to use AI by running it inside the systems the business already has, rather than advising or writing strategy. It presents a refund-approval failure where an undocumented human check was the real policy, to argue that processes must be observed before automation. It cites hiring growth, an MIT study claiming 95% of AI projects show no measurable return, and an unnamed $10M budget burned in three months, none of which is linked to a source. Quoted practitioner Vasuman Moza (described as a former Meta engineer who now runs AI projects in large companies) and OpenAI FDE lead Colin Jarvis are used to support three patterns: pick high-volume work, connect to existing systems via MCP, and keep the old process steps visible so people can verify outputs and budget more time for trust than for building. The core of the video is a five-step roadmap: map every step and ask why it exists, triage each step through three filters (fixed rule, judgment on messy input, cost of error), design for failure modes, evaluate on real labelled cases, and quantify money, cost or risk. It closes with a sponsored job-board segment, an internal chatbot case study, and a suggested first project of auditing a small local business, with a plug for a paid community.

## Key ideas
- **An FDE's job is to get AI running inside existing systems so that work done by hand gets done by software or AI.** — Each task in a process is handled by a human, by rule-based software, or by AI. The FDE decides which of the three owns each task. The narrator frames this as the role's central skill. ([0:00](https://youtu.be/AD-EmZ3v6-g?t=0))
- **Undocumented human workarounds are often the real policy.** — In the refund example, an agent that followed the written policy started losing long-term customers. The person who used to do the job had an unwritten check: purchases on company cards were approved without review. Once that check was made an explicit rule ahead of the model, the problem was addressed. The lesson is to watch the person doing the work before automating it. ([1:24](https://youtu.be/AD-EmZ3v6-g?t=84))
- **Most AI adoption failures are attributed to process problems, not model problems.** — The video cites an MIT study (95% of 300 projects showed no measurable return, which the study blamed on companies) and Moza's view that AI is often added on top of broken processes. Neither figure is linked in the video. ([2:51](https://youtu.be/AD-EmZ3v6-g?t=171))
- **Pick a process with volume, because automating one message saves little.** — The video says the value comes from automating a message sent thousands of times a week. It gives an example of an OpenAI bank project where around 98% of advisors ended up using the tool, and says support history is a good place to find volume. ([5:36](https://youtu.be/AD-EmZ3v6-g?t=336))
- **Connect the agent to the system the business already runs, through MCP, instead of migrating data.** — The Notion example: connect the agent to where the team already works. The finance-system example: one client had spent $5M and five years on their finance system, so the job was to connect everything else to it. ([5:36](https://youtu.be/AD-EmZ3v6-g?t=336))
- **Keep the old process steps visible and budget more time for trust than for building.** — Changing an 11-step process into one step causes people to stop trusting it. The advice is to keep each step, with the agent doing the work inside it, so people can check intermediate outputs. In the bank project, the build took 6-8 weeks, then about four months of pilots and testing before advisors relied on it. ([7:04](https://youtu.be/AD-EmZ3v6-g?t=424))
- **Use a three-filter triage on every step to decide software, model or human.** — Filter 1: a fixed rule that must always be right means ordinary software. Filter 2: messy input that needs a judgment call means a model. Filter 3: if an error is expensive, keep a person in the loop even if a model could do the step. Moza's eight-step example ended with four steps automated, three with human review, and one fully human (a business decision). ([8:31](https://youtu.be/AD-EmZ3v6-g?t=511))
- **Evaluate on a labelled set of real cases, and build for failure, not only the success path.** — Because a model's answers vary, a few test runs will miss rare failures. Take real cases from the documented process where the right answer is known, run the whole set, count the correct answers, then read the misses and fix them. Design for the places the model is unsure, since it gives confident-looking answers either way. ([9:55](https://youtu.be/AD-EmZ3v6-g?t=595))
- **Measure value as money earned, cost removed or risk reduced, and include the cost of wrong answers.** — The Cursor anecdote: a team saw a $2,000/day agent cost and wanted it cut. The agent dispatched engineers to fix broken equipment, and the cost of sending the wrong person out was higher than the agent's cost, which had been the only number being tracked. ([11:22](https://youtu.be/AD-EmZ3v6-g?t=682))

## Techniques
- **Shadow-and-document the process** — Spend about an hour next to the person doing the most repetitive job. Write every step in the order it actually happens. For each step ask why it is done that way; an answer like 'we've always done it' marks a workaround to question. *When:* First step of any AI automation project, before choosing tools or building.
- **Three-filter triage per step** — Filter 1: fixed rule that must be right every time -> keep as ordinary software. Filter 2: messy input needing judgment -> model. Filter 3: expensive failure -> keep a human, even if a model could do it. Record the result per step, expecting a mix of software, model-with-review, and fully human steps. *When:* After the process is written down and before any design work.
- **Connect to existing systems instead of migrating** — Expose the systems the team already uses (for example Notion or a finance system) to the agent with an MCP server, and leave people's tools and habits unchanged. *When:* When the team has significant investment in an existing system that will not be replaced.
- **Keep process steps visible with checkpoints** — Preserve the existing step structure in the UI, and let the agent perform work inside each step, so users can see intermediate results and verify the final answer. *When:* When users will not trust a single final answer that appears with no visible steps.
- **Labelled-case eval loop** — Collect real cases from the documented process where the correct outcome is known. Run the full set against the system, count correct outcomes, read every miss, fix the cause, and repeat. Do not rely on a few runs because outputs vary between runs. *When:* Before letting the system touch real work, and again after each change.
- **Value-and-error-cost accounting** — For each automated use case, record what it earns, what it removes in cost, or what risk it reduces. Also estimate the cost of a wrong output and compare it with the cost of running the agent. *When:* When deciding whether to keep, scale, or drop an agent use case.
- **Process audit as the first deliverable** — For a small local business, observe the most repetitive job, run the five-step method, and write the result up as an audit: one process, the steps to hand to AI, and the money value of each. *When:* When pitching AI work to a business or applying for an FDE role.
