# The State of Model Routing — NVIDIA, Cognition, OpenRouter

- **channel:** [AI Engineer](../channels/aie.md) · **id:** `QHBjufYK8TA` · [watch](https://youtu.be/QHBjufYK8TA) · **date:** 2026-08-18 · **length:** 48:17 · **format:** panel · **quality:** 3/5 · **depth:** practitioner

- **topics:** token-cost-efficiency, multi-agent, inference-serving, infra-cost-scaling · **tags:** model-routing, orchestration, frontier-planner, sidekick, kv-cache, prompt-caching, out-of-distribution, handoff, compaction, openrouter-fusion, devin, pareto-code, nemotron, dynamo, openclaw, dgx-spark

> Panel from Cognition, NVIDIA and OpenRouter on model routing: frontier models plan and delegate to cheaper models, and the hard parts are detecting when a small model is out of depth and keeping cache costs low.

## Summary
Three vendors (Cognition, NVIDIA, OpenRouter) discuss routing work across several models instead of sending every task to one model. Cognition describes its Fusion router, where a frontier model keeps planning and hard decisions while cheaper models do implementation, which they say cuts the cost of frontier-level work by 40%. The panel agrees that routing by task type alone is fragile for agentic work, because task complexity shifts within a single session, so they describe keeping a frontier model in the loop to watch delegated work. Caching drives many of the cost decisions: a persistent sidekick sub-agent keeps its context warm, a cache miss can cost roughly 10x more, and small models can cost more out of distribution because they loop on tool calls. Context handoff should pass file references and short summaries rather than full traces, and compaction alone does not fix cost. The speakers say the field is early, that most of the evidence is vendor-reported, and that routing may centralize at the orchestration layer.

## Key ideas
- **Frontier model plans, cheaper model implements** — Cognition's Fusion keeps the frontier model on planning and hard decisions and delegates implementation work to a cheaper model. They say this cuts the cost of frontier-level work by 40%. The speaker also clarifies they do not claim the router beats the frontier model outright. ([3:27](https://youtu.be/QHBjufYK8TA?t=207))
- **Cheap delegates can explore more deeply** — Because a cheaper model costs less per token, the same budget buys many more tokens. One example is spinning up several sub-agents to explore a codebase, which they say can be more thorough than one frontier model exploring alone. ([4:52](https://youtu.be/QHBjufYK8TA?t=292))
- **Routing by task type is fragile for agents** — A session shifts from questions about the code, to feature work, to live testing and debugging. A small model chosen for the first step can be the wrong model for the later ones, so routing has to follow the phase of the work, not a fixed label. ([8:50](https://youtu.be/QHBjufYK8TA?t=530))
- **Keep a frontier watcher present** — Even when a smaller model does the work, a frontier model keeps watching. Its job is to notice when the delegate is out of depth and move the work somewhere else. The speaker says that always having frontier intelligence present reduces the fragility of these systems. ([10:17](https://youtu.be/QHBjufYK8TA?t=617))
- **Small models can cost more out of distribution** — In-distribution tasks such as classifying names versus organizations suit small models well. Out-of-distribution agentic work can make small models call tools more often and loop, which raises total cost. The speakers say they are still studying where that boundary lies. ([14:22](https://youtu.be/QHBjufYK8TA?t=862))
- **Persistent sidekick instead of stateless sub-agents** — Cognition uses one sidekick sub-agent with a running context instead of spawning fresh sub-agents. Its context stays in the KV cache, so the main agent does not re-send earlier context. They say cached tokens are about 10x cheaper with this setup. ([18:23](https://youtu.be/QHBjufYK8TA?t=1103))
- **Hand back references, not full traces** — Context should move between models as file paths plus a short summary of what was found. The panel contrasts lossy compaction with a non-lossy file system that the model can re-read when needed. Larger models are described as more token-efficient in how they read files. ([22:32](https://youtu.be/QHBjufYK8TA?t=1352))
- **Compaction triggers a cache miss** — Compacting context forces a cache miss, which the speaker puts at about 10x the input cost. The stated main reason to compact is answer quality, since intelligence falls off at long contexts. They advise staying under roughly 100K tokens, and never past 200K. ([30:17](https://youtu.be/QHBjufYK8TA?t=1817))
- **Use the cache refresh as a free check** — Caches expire after about five minutes by default. Because the cache is refreshed on a schedule anyway, a frontier call made at that moment is effectively free. The speaker suggests using it to ask the frontier model whether the small model is going down a rabbit hole. ([33:06](https://youtu.be/QHBjufYK8TA?t=1986))
- **Routing feedback comes from real user behaviour** — Signals such as a user upgrading or downgrading the model, or the system finding it sent a task to the wrong model, can serve as training data for the router. The team wants to replay real prompts against the routing system until it fits production data. Prompt tuning by gradient descent is judged less useful than asking the model why it chose a path and then running regression tests on the prompt. ([40:40](https://youtu.be/QHBjufYK8TA?t=2440))

## Techniques
- **Frontier-planner, cheap-executor split** — The frontier model owns planning and hard decisions and hands implementation to a smaller model. The delegate can spawn several sub-agents to explore in parallel. *When:* When the task has a large implementation or exploration part and the budget is tight, but you still need frontier-quality decisions.
- **Frontier watcher with escalation** — Keep a frontier model observing the delegate's progress. When it judges the delegate out of depth, move the work to another model or back to the frontier model. *When:* For agentic tasks whose difficulty changes mid-session, where static task-type routing breaks down.
- **Persistent sidekick sub-agent** — Keep one helper sub-agent with a running context so its tokens stay cache-warm, and swap the roles of main and sidekick when needed. *When:* When repeated sub-agent calls would otherwise re-send the same context and pay full price for it each time.
- **Reference-based handoff** — The sub-agent returns a summary and file paths, and the orchestrator reads only the parts it needs. The full trace is never passed back. *When:* When passing a delegate's full trace to the main model would be expensive or noisy.
- **Piggyback checks on cache refresh** — Time a frontier check to coincide with the periodic cache refresh that happens anyway, so the check adds little cost. *When:* When the provider's cache expires on a fixed timer and you want a cheap periodic quality check.
- **Hidden-state probes for lost-ness** — Train linear probes or similar classifiers on the model's internal states, such as the prefill vectors, as a proxy for hallucination or confusion. The speaker presents this as an approach being used in the field, with no results shown. *When:* When you can see model internals and want a signal that is more direct than token counts.
- **Routing from production signals** — Log cases where the user upgrades or downgrades the model, or where a task was sent to the wrong model. Replay those prompts as a regression set to tune routing. *When:* Once a routing system is in production and you have real user traffic to learn from.
- **Ask the model why, then regression-test the prompt** — When an agent makes a bad choice, ask the model why it chose that and which prompt caused it. Edit the prompt, then rerun the test set to check for regressions. *When:* When fixing prompt-driven failures in a multi-model agent system.
- **Privacy-aware local/cloud split** — Detect sensitive content in a prompt, keep that work on a local model, and anonymise any part sent to a frontier model. *When:* For hybrid local and cloud setups where some data must stay on-device.

## Numbers
- Cognition says Fusion cuts the cost of frontier-level intelligence by 40%, with the frontier model planning and cheaper models implementing. ([3:27](https://youtu.be/QHBjufYK8TA?t=207))
- A speaker says routing can give up to 10% higher accuracy on a benchmark, depending on the model pool and the task. The benchmark named is LMArena, and no figures are shown. ([7:36](https://youtu.be/QHBjufYK8TA?t=456))
- On TerminalBench, Opus is said to do about 3x better than Haiku, at about one-tenth of Haiku's cost. The wording is ambiguous, as Haiku is cheaper per token, so this is probably a per-task cost claim. ([14:22](https://youtu.be/QHBjufYK8TA?t=862))
- Cognition says the sidekick pattern's cached tokens are about 10x cheaper than the alternative setup. ([18:23](https://youtu.be/QHBjufYK8TA?t=1103))
- A cache miss on input tokens is described as costing about 10x more than a cache hit. ([30:17](https://youtu.be/QHBjufYK8TA?t=1817))
- Advice on context length: intelligence falls off at long contexts, so stay under about 100K tokens where possible and never go past 200K. ([30:17](https://youtu.be/QHBjufYK8TA?t=1817))
- The default prompt cache lifetime is about five minutes. OpenRouter also mentions a case with about two minutes of cache left. ([33:06](https://youtu.be/QHBjufYK8TA?t=1986))
- OpenClaw sends a heartbeat to the selected model every 10 minutes. This is said to drive the demand for routing after its launch in January. ([26:30](https://youtu.be/QHBjufYK8TA?t=1590))

## Hot takes
- Routing by task type alone is fragile for agentic work, and the task changes over the session.
- Small models can cost more than frontier models on out-of-distribution agentic tasks, because they loop and call tools more.
- Compaction alone does not fix cost or throughput problems, because compacting causes a cache miss.
- Routing will likely centralize at the orchestration layer, as traffic routing did on the web.
- Opus is the top model by spend for classification on OpenRouter, which undercuts the case for small models on easy tasks.
