> A hands-on workshop on writing a first LLM-as-judge eval for an agent: why vibe checks fail, how traces feed evals, how to write concrete criteria, and how to build and iterate a judge in a prompt playground.

## Summary
SallyAnn DeLucia (head of product at Arize AI) runs a workshop on writing a first AI eval for a travel-planning agent. She argues that vibe checks break once an agent changes often: you cannot detect regressions, compare prompts or models, or put quality gates in CI. She separates evals from unit tests, since agent outputs have many valid forms and the logic only shows up in traces, so traces are the logs and evals are the tests. The main method is LLM-as-judge, with a short taxonomy of other eval types (decision models, code checks, golden datasets, agent-as-judge, user feedback and business metrics). The core workflow is to write concrete pass/fail criteria with one quality per judge, pick the right spans from traces, and iterate the judge prompt in a playground against a dataset. She ends with alignment against human labels, online evals over incoming traces, and comparing an LLM judge with a decision-model version. Much of the talk is a product walkthrough of Arize, but the eval method is vendor-neutral.

## Key ideas
- **Vibe checks do not scale for agents** — Shipping prompt changes on feel gives no way to prove a fix held or that a regression happened. Evals are what let you detect regressions, compare prompts or models objectively, and set quality gates in CI. ([1:38](https://youtu.be/gv4w23xYj-0?t=98))
- **Traces are the logs for AI, and evals are the tests** — An agent's logic is not readable in code and its outputs have many valid forms, so a unit test with one expected output does not fit. You need observability (traces) before you can run evals. ([3:56](https://youtu.be/gv4w23xYj-0?t=236))
- **LLM-as-judge is the focus eval type, and explanations matter** — A secondary LLM labels one aspect of the output (QA, summarization, relevance) and returns a label plus an explanation. The explanation is the reasoning behind the label and lets you check the judge rather than take the label at face value. ([5:01](https://youtu.be/gv4w23xYj-0?t=301))
- **Eval types differ in cost and where they run** — Decision models are cheap and fast, returning a true/false or label with a probability but no explanation. Code evals suit deterministic checks such as substring, JSON validity, ROUGE or BLEU. Golden datasets, agent-as-judge and user feedback or business metrics are the other types. The first four can run across development and production; the last three are mainly production. ([6:15](https://youtu.be/gv4w23xYj-0?t=375))
- **Define good with concrete criteria and judge one quality per eval** — Replace 'helpful, accurate' with checks like 'follows the user's follow-up', 'matches the requested number of days', 'keeps totals within budget'. LLM judges handle one criterion well, so add more evals over time rather than bundling criteria, except with decision models or agent-as-judge. ([19:16](https://youtu.be/gv4w23xYj-0?t=1156))
- **Start with a few evals and grow them from production data** — The speaker's first evals on the Alex agent were QA correctness, user frustration, jailbreak and toxicity. Alex now runs 32 evals, grown from real production usage. Generic templates are a fine start, but specific evals for the use case are better. ([20:21](https://youtu.be/gv4w23xYj-0?t=1221))
- **Write criteria as task, success, failure, and specific pass and fail bullets** — Capture the task being judged, what success and failure look like, and about three concrete bullets each for pass and fail. The bullets become the judge prompt, so write them as if describing success to a stakeholder. ([21:25](https://youtu.be/gv4w23xYj-0?t=1285))
- **Every stakeholder should define success, and metrics and evals do different jobs** — Product, engineering, support, domain experts and security should all help define success. A metric signals that something might be broken; an eval identifies the actual failure mode. Use both. ([33:15](https://youtu.be/gv4w23xYj-0?t=1995))

## Techniques
- **Six-part criteria template** — Before writing any judge prompt, write: (1) the task being judged, (2) what success looks like, (3) what failure looks like, (4) what exactly the judge scores, (5) about three concrete pass bullets, (6) about three concrete fail bullets. Example from the talk: task 'user sends a follow-up about their trip'; success 'answers the follow-up directly using the trip's details'; failure 'falls back to a generic budget'. *When:* Starting any LLM-as-judge eval, to turn a vague quality goal into something a judge can apply consistently.
- **Judge prompt structure** — Order the prompt as: (a) a role intro that centres the judge on its job, e.g. 'you are evaluating whether an assistant's output accurately captures the details requested in the input'; (b) the pass and fail bullets as criteria; (c) label rules, e.g. 'correct if consistent with input, incorrect if the destination or property type is wrong'; (d) the allowed labels (binary, or multi-label such as correct, partially correct, incorrect, not applicable; the judge returns exactly one); (e) optimization direction (is higher or lower good); (f) a required explanation for each label. *When:* Writing the judge template in the prompt playground or any eval harness, so labels are consistent and each one can be audited.
- **Variable mapping for judge inputs** — Write the judge prompt with generic placeholder variables, not trace attribute names. Map each variable to the real span attribute (input, output, tool result) in the task that uses the eval. Renaming an attribute then means updating the mapping, not every eval. *When:* Reusing one judge across several datasets or applications whose traces use different field names.
- **Span-level dataset selection** — Judge the right unit of work. Root spans (parent_id IS NULL) hold the user input and final output, so use them to check end-to-end behaviour, e.g. does the itinerary match the request. Filter by span name or type to judge a single tool call, such as whether a weather-lookup tool returned the expected data. Add the selected spans to a named dataset. *When:* Choosing what a judge should see: end-to-end quality uses root spans, step-level checks use filtered tool or LLM spans.
- **Iterate the judge in a prompt playground against a dataset** — Create a playground, pick a model (the speaker used a mini OpenAI model; the captions read '401 mini'), attach the judge template, load the dataset, and run it. For each row, check whether you agree with the label and explanation. Edit the prompt, rerun, and repeat. Save the good version as a reusable evaluator. *When:* Tuning a judge's prompt before it runs on production traces. Read explanations, not just labels.
- **Alignment against human labels** — Annotate the dataset rows yourself (or with domain experts) and run the judge on the same rows. Compare judge labels with human labels to measure agreement, then refine the criteria or prompt where they disagree. *When:* Before trusting a judge enough to gate CI or monitor production.
- **Online evals on incoming traces** — Attach saved evaluators to a continuous task so each new trace is scored automatically and the results are posted for monitoring. *When:* Once a judge is aligned with humans and you want ongoing quality monitoring in production.
- **Decision-model comparison** — Rewrite an LLM-as-judge question as a decision-model question (true/false or label with probability, no explanation), run both on the same small set (the speaker suggests about 20 traces, one dimension, one judge), and compare accuracy against human labels. *When:* When you need a cheaper, faster judge and can accept a score without a written explanation.
- **Instrumentation: auto, manual, or hybrid** — Start with auto-instrumentation via OpenInference, which covers many frameworks and sends standard attributes such as input/output values and LLM input messages. Add manual or hybrid instrumentation for custom attributes your evals need. The speaker suggests letting a coding agent do the instrumentation using the platform's skills, nudged along as needed; the exact install command is named 'MPX evals' in the captions and is unclear. *When:* Sending your own agent's traces for evaluation: first check what auto-instrumentation already captures, then add only the attributes your criteria need.

## Hot takes
- Evals are the primary signal for agents, and metrics only say something might be broken while evals name the failure mode.
- Judge one quality per eval. Bundling criteria into one LLM judge is discouraged, though decision models and agent-as-judge can take several.
- Every stakeholder (product, eng, support, domain experts, security) should help define what success looks like, not just the engineer.
- Specific, use-case evals beat generic templates, but generic ones are fine as a start.
- Much of the talk is a product walkthrough of Arize AX, so the method is worth taking and the platform details less so. Quality is 3, not higher, because the workshop is largely vendor-led.
