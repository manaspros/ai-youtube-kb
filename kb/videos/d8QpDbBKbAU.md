> Secondhand summary of how Anthropic reviews Claude Code's own PRs: layered automated review, risk-tiered human sign-off, incident-derived reviewer evals, and round caps for agent-vs-agent loops.

## Summary
Better Stack summarizes an Anthropic write-up on how it reviews code when Claude writes about 90% of Claude Code's own code. The core shift is from asking whether a human read the change to asking what could go wrong and which check, automated or human, catches it. Review is layered: the author's Claude session self-checks, automated multi-agent reviewers run on each PR and only post findings that a voting group agrees on, a security pass runs, and CI gates the merge. Human involvement depends on a classifier-assigned risk tier, with low-risk changes needing none. The reviewer itself is tuned against an eval built from real incident PRs, with noise measured by whether authors fix or dismiss comments. Agent author and reviewer loops got stuck (one PR hit 50+ rounds overnight), and the fix was escalating after three rounds and re-reviewing only new changes. The video's own caveats are that the 40% revert figure is a share, not a count, and that the approach relies on a very large token budget.

## Key ideas
- **Volume makes line-by-line reading unrealistic; the question becomes what could go wrong and which check catches it** — Claude writes about 90% of Claude Code's code. Merges more than doubled June to September while the share of reverted PRs fell 40%. Replaces 'did a human read this' with a risk-based check question. ([0:00](https://youtu.be/d8QpDbBKbAU?t=0))
- **Less human review is only acceptable if reverts and production incidents do not rise** — The stated goal is that most PRs merge with at most one human, who may be the author. Revert rate and production incidents are tracked as the guardrail. ([0:59](https://youtu.be/d8QpDbBKbAU?t=59))
- **Review is a stack of imperfect layers, Swiss-cheese style, with fast rollback as the last net** — Layers: the author's own Claude session self-checks and gets a fresh-context sub-agent diff review; PR-time multi-agent reviewers find bugs in parallel and a separate voting group posts only agreed findings; then a security review, then CI (tests, type checks, lint), then humans as tier requires. ([0:59](https://youtu.be/d8QpDbBKbAU?t=59))
- **Recurring reviewer findings become lint rules or CLAUDE.md lines, not one-off PR fixes** — If Claude keeps using a replaced helper, they add a lint rule or a CLAUDE.md line so the mistake stops at the source. Code owners' review.md files say what failure looks like in that area (docs that lie, config that misroutes e.g. prod instead of staging) and list false positives to ignore. ([2:22](https://youtu.be/d8QpDbBKbAU?t=142))
- **Findings block merge until resolved, and false positives are cleared by closing the thread with a reason** — A PR cannot merge while bug-review or security-review findings are open. The author either fixes the issue or closes the thread with a short reason. The PR template (how tested, how to undo) can be drafted by Claude, but the requester signs off. ([2:22](https://youtu.be/d8QpDbBKbAU?t=142))
- **Human review is tiered by risk, and a classifier agent picks the tier** — Low risk (docs, changes behind a feature flag) needs no human if automated checks pass and the author is trusted. Medium risk (ordinary product changes, sensitive areas like caching) needs one human. Highest risk plus a fixed list of paths needs two. A second agent double-checks whether a human is needed anyway. ([3:40](https://youtu.be/d8QpDbBKbAU?t=220))
- **The reviewer is tested against an eval built from real incident PRs, and changes are kept only if the score rises** — Each incident PR's bug is confirmed by the engineer who knows the code and turned into an eval case, run daily. Gaps are fixed in CLAUDE.md, a skill, or a new check. Any reviewer change is scored against all cases and dropped if the score does not go up. ([3:40](https://youtu.be/d8QpDbBKbAU?t=220))
- **Flagging everything games the eval, so noise is measured by what authors do with each comment** — Tracks whether comments are fixed or dismissed. Noise matters more when the author is an agent: a nitpick on a human PR gets ignored, but an agent will act on it, causing commit and review loops. ([4:49](https://youtu.be/d8QpDbBKbAU?t=289))
- **Agent author and agent reviewer loops need round caps, scoped re-reviews, and whole-class fixes** — One PR went through over 50 review rounds overnight. About 59% of flags were on code present since the first review. After three rounds the reviewer tells the author to rethink the approach. Later re-reviews cover only new changes, and the reviewer flags the whole bug class at once. ([4:49](https://youtu.be/d8QpDbBKbAU?t=289))
- **Humans keep the work machines are bad at, and the author owns what they land** — Humans decide what to build, review risky code such as billing, and own outcomes. Under the 'you land it, you own it' rule, the author usually fixes what breaks. Changes stay small and most mistakes are undone in minutes with flags and reverts. ([6:05](https://youtu.be/d8QpDbBKbAU?t=365))

## Techniques
- **Layered review pipeline with a voting gate** — Author session self-verifies (run tests, build, compare a screenshot to the design), then a fresh-context sub-agent reviews the diff. On PR open, several reviewer agents hunt for bugs in parallel; a separate group of agents votes on each finding and only agreed findings are posted. Then a security reviewer pass, then CI (tests, type checks, lint), then human review as the tier requires. *When:* High PR volume where humans cannot read every line. Use each layer as a partial filter rather than a single gate.
- **Turn repeated reviewer findings into durable rules** — If the reviewer flags the same mistake across several PRs, add a lint rule for mechanical issues, or a CLAUDE.md line so the agent stops writing it. Do not just fix it on each PR. *When:* Recurring agent mistakes such as using a deprecated helper function.
- **Per-directory review.md written by code owners** — Each code owner keeps a review.md that defines what failure looks like in that code (docs: claims that are wrong, like a stated default that is off; config: misrouting, like pointing at prod instead of staging) and lists patterns that look wrong but are fine, so the reviewer stops flagging them. *When:* A reviewer produces false positives in specific areas, or needs domain-specific failure definitions.
- **Merge gate with explicit false-positive dismissal** — Block merge while any bug or security finding is open. Resolution is either a fix or closing the thread with a short reason, which records the false positive. *When:* Automated reviewers should be able to block merges, but authors need a fast way to clear mistakes.
- **Incident-derived reviewer eval with a keep-or-drop rule** — Collect PRs that caused incidents. Have the code owner confirm each bug and convert it into an eval case. Run the reviewer against the full set daily. For any change (prompt, model, rule), score against all cases and keep it only if the score rises. For each miss, decide whether the fix belongs in CLAUDE.md, a skill, or a new check. *When:* Tuning any LLM reviewer or judge, so changes are measured against real past failures.
- **Noise metric from comment outcomes** — Track whether each reviewer comment is fixed or dismissed as wrong. Use this alongside the recall eval, because a reviewer that flags everything will score well on recall alone. *When:* Any automated reviewer whose output is consumed by agents or humans.
- **Round cap, scoped re-review, and whole-class flagging for agent loops** — After about three review rounds, have the reviewer instruct the agent author to stop and rethink the approach. After the first few passes, review only the new changes. When a bug pattern is found, flag every instance in one review so it is fixed everywhere at once. *When:* Agent author and agent reviewer loops that produce many rounds with little new signal.
- **Risk tiering with a classifier agent and a second check** — A classifier agent reads each PR and assigns a risk tier. A second agent verifies whether a human is required anyway. Keep a fixed list of sensitive paths that always require two humans. Tiers: low (no human if checks pass and the author is trusted), medium (one human), high or sensitive path (two humans). *When:* Mixed-risk change volume where most changes are low risk and a few need strict review.

## Hot takes
- The title 'Anthropic Barely Reads Claude's Code Anymore' overstates it: medium and high risk changes still get one or two humans, and humans still own outcomes.
- The 40% revert drop is a share with no absolute counts. With PR volume doubling, the narrator argues total reverts still rise about 20%.
- The approach depends on a very large token budget. The narrator notes Anthropic can afford it and that a reviewer at $15 to $25 per review is expensive for most teams.
- This is a secondhand summary of an Anthropic post, and the video itself says some specifics are unclear. Use the mechanisms, not the headline.
