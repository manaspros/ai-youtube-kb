# Demand-Driven Context: A Methodology for Coherent Knowledge Bases Through Agent Failure

> A staff engineer at IKEA argues enterprise agents fail on undocumented institutional knowledge, and proposes a pull-based loop where agents surface knowledge gaps and curate context blocks before retrieval.

## Summary
Raj, a staff software engineer at IKEA, says enterprise AI agents handle generic and documented work well but fail on institutional knowledge that lives in people's heads. He reports that his earlier approach of building many MCP servers and RAG layers was accurate only some of the time, and that he ended up doing manual data entry and filling gaps himself. He proposes "demand-driven context": give an agent real past work items, let it fail, have it list the information it was missing, have a domain expert fill those gaps, and have the agent save the answers as curated context. He demonstrates this in Claude Code on a root-cause-analysis incident, then runs it over 14 incidents, where his reported confidence score rose from about 1.4 to 4.4. He then describes automating it as a context gap scanner: generate probes from past incidents and tickets, run them against the knowledge base, rank gaps as critical, high or medium, and output a Kanban board. He recommends keeping the curated knowledge in a Git repo for PR review, adding a metamodel that links processes, systems, APIs and jargon, and fixing context before retrieval rather than during live operations. He argues that a team's context (about 96k tokens by his measure) often fits in a long context window and can beat graph RAG at that size.

## Key ideas
- **Enterprise AI stalls on institutional knowledge, not model quality** — Speaker cites a McKinsey figure (as he states it) that 88% of companies use AI but only 6% see value. He sorts Jira tickets into work the LLM already knows, work that needs documented team conventions (skills), and red work that depends on tribal knowledge that agents cannot get. ([4:46](https://youtu.be/_QAVExf_1uw?t=286))
- **Retrieval layers were unreliable and created manual work** — After building 10 to 30 MCP servers or RAG layers, the speaker says the output was right only 10 to 30% of the time. The rest of the time he filled gaps and answered questions, so he did more work than before. ([8:47](https://youtu.be/_QAVExf_1uw?t=527))
- **Pull approach: let the agent fail on real tasks, then capture what it was missing** — Instead of pushing all knowledge in up front, give the agent work items. When it fails, it lists the missing checklist items. A domain expert fills them, and the agent saves the answers in a better structure. Speaker compares this to onboarding a new hire by assigning real tasks. ([13:06](https://youtu.be/_QAVExf_1uw?t=786))
- **TDD framing: failing tasks act as tests for the knowledge base** — Speaker compares the loop to red-green TDD. Work the agent will fail on is the failing test, and each knowledge fix is the code that makes it pass. Over repeated cycles the knowledge base becomes semi-autonomous. ([15:26](https://youtu.be/_QAVExf_1uw?t=926))
- **Replaying past incidents shows undocumented knowledge and raises confidence** — On 14 incidents he answered each gap and the agent wrote back new notes. Reported confidence rose from about 1.4 to 4.4. Each incident also surfaced entities that were never documented. He frames this as moving the agent from a consumer of knowledge to a knowledge manager. ([24:50](https://youtu.be/_QAVExf_1uw?t=1490))
- **Automate the loop with a gap scanner: probes, run, gap analysis** — Scanner generates probes from archived Jira tickets and incidents, runs them against the knowledge base (Confluence, Slack, GitHub or flat files), and reports what is missing, stale, duplicated or tribal. It ranks gaps as critical, high or medium and writes a Kanban board. Speaker says each ticket produces 100 to 150 lines of Markdown detail. ([26:27](https://youtu.be/_QAVExf_1uw?t=1587))
- **Store curated knowledge in Git and model the domain with a metamodel** — A Git repo gives PR review, ownership and merge rules for many agents and teams. A metamodel linking business processes, systems, APIs and jargon acts as a navigation map, so the agent can see which processes and APIs a system change would affect. ([34:06](https://youtu.be/_QAVExf_1uw?t=2046))
- **Fix context before retrieval, not during operations; code vs docs needs an explicit source-of-truth rule** — Speaker recommends curating a team's context ahead of time, since a couple of weeks with a domain expert can reach roughly 60 to 80% quality. When code and Confluence conflict, he added a rule that code in the repo wins. He says the approach is independent of access control, which is left to the organization. ([45:45](https://youtu.be/_QAVExf_1uw?t=2745))

## Techniques
- **Pull-based knowledge capture from failed agent runs** — Give the agent a real work item. Have it list the checklist of information it could not find. A domain expert answers, and the agent writes the answers into a structured knowledge file. Repeat per task. *When:* When institutional knowledge is undocumented and you want knowledge capture to happen as a side effect of real work, not as a separate documentation project.
- **Failing-tasks-as-tests for knowledge bases** — Treat tickets or incidents the agent will fail on as failing tests. Each fix adds knowledge until the agent passes. Track progress across cycles. *When:* When you need a measurable definition of done for knowledge-base quality.
- **Historical-incident replay as a probe source** — Use archived Jira tickets, incidents and support tickets as the probe set. Run each one against the knowledge base to score coverage, freshness and duplication without waiting for live incidents. *When:* When you have a backlog of past work items and want to measure knowledge coverage across a whole team or domain.
- **Three-step gap scanner: probe generation, probe run, gap analysis** — Step 1: generate probes that ask what each incident needs. Step 2: run the probes against the connected sources. Step 3: classify each finding as clean, stale, incomplete, missing or tribal, flag duplicates across versions, rank by severity, and output a Kanban board. *When:* When you need a prioritised backlog of documentation fixes instead of a manual audit.
- **Freshness labels, flagged for human decision** — Use the last-updated date (for example from a Confluence export) to tag each document as active, stale or clean, using a threshold you set. The tool flags stale documents but does not delete or decide. A human decides whether an old document still matters. *When:* When documents can be old but still important, so age alone should not drive decisions.
- **Git-backed curated context blocks with a metamodel** — Store curated context as Markdown in a Git repo with directory layout that mirrors the metamodel (processes, systems, APIs, jargon). Use PRs and review for changes. Publish to Confluence or Slack later if needed. *When:* When many agents and teams contribute to one knowledge base and you need review and conflict handling.
- **80/20 context cache with links to the monolith** — Keep the 20% of documentation that answers most questions as compact context blocks. Leave links to the rest of the knowledge base so the agent fetches it only when the blocks are not enough. *When:* When a full knowledge base is too large or noisy to load into every session.
- **Full-context before graph RAG, for small domains** — Measure the total token count of a domain's documentation. If it fits in the context window (speaker's test: about 96k tokens per domain, none over 100k), load it whole before building a GraphRAG or retrieval pipeline. *When:* When the knowledge base is small enough for the context window and retrieval adds complexity without clear gains.
- **Claude Code skills, rules, agents and hooks as the implementation** — Package the loop as a combination of skills, rules, subagents and hooks, with a knowledge store on disk. The same approach can run on Copilot or other agents. *When:* When you want a repeatable agent workflow that captures knowledge in the normal course of work.

## Hot takes
- Enterprises are focused on model quality, harnesses and retrieval, but nobody will fix your knowledge base for you. Your team has to do it.
- Fix institutional context before retrieval, not during live operations.
- For small domains, a full context window can beat RAG or GraphRAG.
- Keep curated knowledge in Git, not a SaaS tool, until a product is proven. Git gives PR review and ownership for free.
- Engineering teams rarely run evals on their MCP or RAG outputs, even though they should.
