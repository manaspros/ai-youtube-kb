> Better Stack walkthrough of Cloudflare Containers: deploying a Bun + ffmpeg container behind a Worker with a Durable Object, then reviewing limits, beta pricing and a Rivet/Fly cost comparison.

## Summary
The presenter explains Cloudflare Containers as a middle ground between serverless Workers and full container infrastructure, with Durable Objects holding per-instance state and containers scaling to zero when idle. He builds a demo app that removes silences from uploaded videos: a Bun HTTP server in a Docker image with ffmpeg, a static index.html front end on a Worker, and a Worker that proxies requests to a randomly chosen container instance. He deploys with a single wrangler deploy, which builds and pushes the image, then inspects instances, metrics and logs in the Cloudflare dashboard. He closes by listing beta limits (paid Workers plan required, aggregate memory/vCPU/disk caps, 2 GB max image) and the pricing model, then compares a 1 vCPU / 2 GB / 50 GB container cost across Cloudflare, Rivet and Fly Machines. The video is a single-person demo with no sponsor segment and no benchmarks beyond the list prices and limits it reads out.

## Key ideas
- **Cloudflare Containers sit between serverless and full container platforms: containers run close to Workers and are tied to Durable Objects for stateful pieces, with no Kubernetes to manage.** — Containers scale on demand, spin up where and when needed, sleep when idle, and are billed by actual usage. The presenter's point is that the platform fills a gap that Workers alone cannot, because Workers cannot run ffmpeg. ([0:00](https://youtu.be/c6TEXxpUEUw?t=0))
- **The practical motivating case is ffmpeg, which does not run on Workers. Containers let a Worker-hosted static front end forward heavy work to a real binary.** — The demo app is a Worker serving static HTML, with all backend processing (silence removal via ffmpeg) routed through a container. ([1:03](https://youtu.be/c6TEXxpUEUw?t=63))
- **The Durable Object class is the container's control point: it starts and stops the instance, proxies requests on a port, and exposes lifecycle hooks.** — Each container instance has a Durable Object running alongside it. The presenter uses the default port 8080, a sleep-after setting of five minutes, and onStart/onStop/onError hooks that only log. He notes that in larger apps the same object could hold per-user stateful containers, env vars, or hooks. ([2:11](https://youtu.be/c6TEXxpUEUw?t=131))
- **Load balancing is a simple random pick across container instances, and he expects a latency-based option later.** — The Worker fetch handler forwards every request to a randomly selected instance. He calls this a basic load balancer and says Cloudflare has said a latency-based one is planned, which is a beta roadmap item. ([2:11](https://youtu.be/c6TEXxpUEUw?t=131))
- **Deployment is one command. wrangler deploy uploads static assets, deploys the Worker, builds the Dockerfile image, pushes it to Cloudflare, and sets up the container.** — The wrangler config holds the Worker name, entry file, container settings (max instances, class name, image path, instance type), the Durable Object binding, the assets directory, and observability. ([3:28](https://youtu.be/c6TEXxpUEUw?t=208))
- **Operations visibility is built into the dashboard: a Containers section with per-instance CPU, memory and logs, and each instance reports its location.** — In the demo the instance ran in Paris for a user in London, which the presenter attributes to placing the container near the requester. ([4:55](https://youtu.be/c6TEXxpUEUw?t=295))
- **The beta has hard aggregate limits and requires a Workers paid plan, so capacity planning matters before adopting it.** — Limits he reads out apply across all concurrent instances. They are not per-instance caps, and they may grow once the product leaves beta. ([5:34](https://youtu.be/c6TEXxpUEUw?t=334))
- **Price comparison is the main cost point. Cloudflare costs more than Rivet or Fly for the same container size, but Cloudflare's advantage is tight integration with Workers and Durable Objects.** — The presenter cites a Rivet article comparing one vCPU, 2 GB RAM and 50 GB ephemeral storage per month: Cloudflare about $75, Rivet about $29, Fly Machines about $31. He currently uses Fly.io and sees no reason to switch unless he wants the Workers integration. ([7:02](https://youtu.be/c6TEXxpUEUw?t=422))

## Techniques
- **Container server behind a Worker** — Write a small Bun HTTP server with a GET /status health-check endpoint and a /process endpoint that accepts the uploaded file and runs the ffmpeg command via exec/promise. Dockerfile: start from the Bun base image, install ffmpeg with apt-get, copy the server and run it with bun. The Worker forwards all incoming requests to the container. *When:* Running CPU- or binary-heavy work (ffmpeg, media processing) that cannot run on Workers, while keeping the static front end on Workers.
- **Durable Object container class** — Define a class (demo name BetterEditContainer) that extends the Cloudflare Container base class, a Durable Object. Set the default port to 8080, set sleep-after to five minutes so idle containers shut down, and add onStart, onStop and onError hooks (the demo logs in each). In the Worker's fetch handler, pick an instance (demo: random pick from the instance list) and forward the request. *When:* You need a request-driven container that starts on demand, shuts down when idle, and stays cost-free when unused.
- **wrangler config for containers** — In wrangler config, set the Worker name and main entry (src/index.ts). Add a containers block with: max_instances (demo: 3), name, class_name matching the Durable Object class, image (path to the Dockerfile, built and pushed on deploy), and instance_type. Add the Durable Object binding and an assets directory for public/ (the static index.html). Enable observability. Deploy with npx wrangler deploy. *When:* Deploying a Worker with containers in a single step, without managing images or a registry by hand.
- **Monitoring containers** — Open the Cloudflare dashboard, go to the Containers section, select the container to see instance state (active/live), max instances, memory, vCPU and disk. Drill into an instance for its location, CPU and memory graphs, and logs. *When:* Checking that a deployed container is live, verifying placement, and debugging a specific instance.

## Numbers
- Demo container instance type: max instances 3, 4 GB memory, half a vCPU, 4000 MB disk. ([4:55](https://youtu.be/c6TEXxpUEUw?t=295))
- Sleep-after idle timeout set to five minutes. ([2:11](https://youtu.be/c6TEXxpUEUw?t=131))
- Beta account-wide limits across all concurrent instances: 40 GB memory, 20 vCPU, 100 GB disk; max image size 2 GB; total image storage per account 50 GB. ([5:34](https://youtu.be/c6TEXxpUEUw?t=334))
- Pricing includes 25 GB-hours per month; overage is billed per GB-second for memory, with separate CPU and disk rates. The presenter did not state the per-second rate. ([5:34](https://youtu.be/c6TEXxpUEUw?t=334))
- Monthly cost for 1 vCPU, 2 GB RAM, 50 GB ephemeral storage (per the Rivet article he reads): Cloudflare about $75, Rivet about $29, Fly Machines about $31. ([7:02](https://youtu.be/c6TEXxpUEUw?t=422))

## Hot takes
- Vendor-beta product; the presenter says limits and features may change and the latency-based load balancer is not yet available.
- The cost comparison comes from a third-party article the presenter reads from, not from his own measurements.
- He calls the per-GB-second overage rate 'insanely small' but does not state it, so the actual cost of sustained use is unclear from the video.
- The app is trivial (one endpoint doing one ffmpeg command), so the video shows deployment mechanics, not performance, cold-start time or concurrency behavior.
