> Local AI is private, but a stranger's model file can still act on your machine through chat templates, runner bugs, exposed ports and poisoned fine-tunes; the fix is to limit what the model can reach.

## Summary
The host argues that running models locally protects data privacy but not against what an untrusted model file can make the machine do. He walks through five layers (weights file, chat template, runner, network port, weights plus tools) and says security scanners only catch files that execute code, not files that instruct. Concrete incidents cited include a fake Hugging Face repo with an info-stealer README, Jinja chat-template injection (Lama Drama, SGLang), a trigger-phrase template poisoning study, Ollama memory-leak and unsigned-updater bugs, and about 175k Ollama servers exposed on 0.0.0.0. He covers DNS rebinding from the browser and a Project Discovery backdoor that poisoned 1% of tool-calling training rows. He closes with concrete mitigations (loopback binding or Tailscale, patching, official weights only for tool-using setups, keeping secrets out of the agent's working directory, and privilege separation with logging). Several headline numbers come from third-party research and he admits no in-the-wild poisoned template has been documented yet.

## Key ideas
- **The real local-AI risk question is what a model file can make the machine do, not whether data leaves the machine.** — Local weights are numbers and cannot run alone, but the surrounding stack (template, runner, port, tools) runs code and can be attacked. Privacy is not the same as safety once tools are attached. ([0:00](https://youtu.be/3mx84MRj8lY?t=0))
- **Think of a local model setup as five layers, each with its own threat model.** — Layer 1 is the weights file, layer 2 the chat template (Jinja, executed on every prompt), layer 3 the runner (Ollama, LM Studio, SGLang), layer 4 the network port and who can reach it, layer 5 the weights combined with the tools the model can call. Most scanners only check layer 1. ([4:00](https://youtu.be/3mx84MRj8lY?t=240))
- **Standard scanners only detect files that execute code; newer attacks instruct the model instead.** — Pickle and similar scanners answer whether a file runs code on load. SafeTensors was made to fix that specific class. Poisoned templates or weights that change model behavior pass those checks. ([5:21](https://youtu.be/3mx84MRj8lY?t=321))
- **A checksum only proves you got the file the uploader intended, not that the file is safe.** — A fake repo copying a real model card (claimed ~244k downloads, many possibly bot-inflated) pushed a README telling Windows users to run a .bat and others to run a Python loader, which led to an info-stealer. ([5:21](https://youtu.be/3mx84MRj8lY?t=321))
- **Chat templates embedded in GGUF files are executable Jinja code that runs on every message.** — Lama Drama (2024) was an unsandboxed template render in a llama-cpp-python wrapper that allowed arbitrary commands; the talk cites 6,000+ affected models. SGLang shipped a similar bug in April 2026, rated 9.8 and fixed in 0.5.11 (captioned as '0 to 5.11'). ([8:00](https://youtu.be/3mx84MRj8lY?t=480))
- **A template can be poisoned with a trigger phrase so scanners and benchmarks see nothing wrong.** — Pillar Security tested 18 models across llama.cpp, Ollama, vLLM and SGLang. Without the trigger, behavior looked normal; with it, factual accuracy fell from 90% to 15% and attacker links were served over 90% of the time. The model card page can also show a clean template while the downloaded file contains the poisoned one. ([9:22](https://youtu.be/3mx84MRj8lY?t=562))
- **Runner bugs are a category problem: Ollama had a memory-leak bug and an unsigned auto-updater.** — Bleeding Llama let a crafted GGUF with false tensor sizes leak heap memory (API keys, system prompts) through a push-to-registry sequence; fixed in 0.17.1. The Windows auto-updater skipped signature checks in 0.12.10 to 0.17.5, fixed in 0.23.3. The talk says LM Studio, llama.cpp server, vLLM and SGLang share the same parsing exposure. ([10:35](https://youtu.be/3mx84MRj8lY?t=635))
- **Binding Ollama to 0.0.0.0 exposes it to the whole network, and Docker port publishing can bypass host firewalls.** — A January scan over 293 days found 175,108 Ollama servers answering unauthenticated across 130 countries, and over 48% advertised tool calling. Publishing the port in Docker writes its own iptables rules that bypass UFW. ([13:03](https://youtu.be/3mx84MRj8lY?t=783))
- **A malicious web page can reach a localhost-bound model server through DNS rebinding.** — The browser sits inside the network, so a page can rebind its domain to 127.0.0.1 or the LAN IP and issue requests to Ollama. Ollama's host-header check only runs when bound to loopback, so binding to 0.0.0.0 disables that protection. The talk says a template can be rewritten through the API to inject a hidden instruction into every later request. ([15:17](https://youtu.be/3mx84MRj8lY?t=917))
- **A backdoor can be implanted with a tiny share of poisoned rows and triggered by a rare phrase, with the payload fetched from a URL.** — Project Discovery poisoned 15 of 1,500 tool-calling rows (1%) in a 1.5B model. The trigger fired 75 to 98% of the time while normal tool calls stayed at 99 to 100% accuracy. A 7B model needed 20% (125 of 625). The payload was a URL the model fetches and runs, so swapping the URL changes behavior without touching weights. ([16:42](https://youtu.be/3mx84MRj8lY?t=1002))
- **Common defenses do not cover this: allowlists, benchmarks and safety fine-tuning all miss it.** — The fetched script comes from a domain the firewall already trusts; benchmarks never type the trigger; the talk cites Anthropic research and UK AISI work showing about 250 poisoned documents can implant a backdoor across 600M to 13B models, and that safety training does not reliably remove them. ([18:03](https://youtu.be/3mx84MRj8lY?t=1083))
- **Honest base-rate framing: the observed template risk in the wild is low, and the real exposure is tools plus unvetted weights.** — A scan of 185,345 GGUF repos found 130,592 with real templates and 24 dangerous (about 1 in 5,400), all of them PoCs or tests according to the scanner's author. The talk says no poisoned template or backdoored fine-tune has been publicly documented hitting users yet. Obliterated fine-tunes from unknown authors are the bigger concern. ([20:17](https://youtu.be/3mx84MRj8lY?t=1217))
- **Risk tracks what the model can reach, not where it runs, so local versus cloud is not the fix.** — A chat-only setup with official weights, a current runner and loopback is low risk. Tool access, file system access and eval pipelines widen the blast radius, and a backdoored model with shell access does the same damage on a rented server. ([21:31](https://youtu.be/3mx84MRj8lY?t=1291))

## Techniques
- **Keep the model server on loopback; reach it remotely through an encrypted tunnel or an authenticated proxy** — Do not set OLLAMA_HOST to 0.0.0.0. Use Tailscale for device-to-device access, or put a reverse proxy with authentication in front. In LM Studio, enable the 'require authentication' option. In Docker, avoid publishing the port publicly, since published ports bypass UFW rules. *When:* Any time a phone, laptop or other machine must reach a model running on a desktop.
- **Patch the runner before anything else** — Update Ollama, LM Studio, llama.cpp, SGLang and vLLM to current releases. The talk specifically names Ollama 0.17.1 as the Bleeding Llama fix and 0.23.3 as the Windows updater signature fix. Version numbers are inconsistent in the captions, so check the upstream release notes. *When:* As the cheapest first step for any local setup; treat old runner versions as an immediate fix.
- **Use official or established-quantizer weights for any model with tool access** — Prefer weights from the lab or known quantizers (the talk names Bartowski's releases and lab-published GGUFs). Treat merges and obliterated fine-tunes from unknown accounts like an unreviewed pull request from a stranger. *When:* Any agent or tool-calling setup. Chat-only use is lower risk.
- **Inspect the GGUF chat template before serving a model** — Unpack the GGUF, extract the chat template and read the Jinja code by hand. Look for conditional logic keyed on specific trigger phrases or unexpected URLs or commands. Scanners such as pickle or model-scan do not check this. *When:* Before running any third-party GGUF, especially one with many downloads from an unknown account.
- **Keep secrets out of the agent's working directory** — No .env files, SSH keys or cloud credentials in any directory the model or its tools can read. Pass credentials through a separate, narrowly scoped mechanism. *When:* Any agent with file-system or shell access. The talk frames this as limiting damage if the model is backdoored.
- **Split command execution from network access and log the boundary** — Run the process that executes commands separately from the process that has network egress, and log what crosses between them. The talk describes this as basic privilege separation applied to agents. *When:* Agents that run shell commands and can also reach the network, such as coding agents or eval pipelines.
- **Do not rely on hash checks or allowlists alone** — Verify the hash for integrity, but also review what the file does. Allowlisting outbound domains does not stop a payload fetched from a trusted domain such as GitHub. *When:* When evaluating downloaded model artifacts or deciding on egress controls for an agent.

## Hot takes
- Local models are not inherently safe once tools are attached; the risk is about reach, not location.
- Checksums and HF scanners verify integrity and code execution, not intent, so they miss instructive attacks.
- Binding Ollama to 0.0.0.0 is the most common self-inflicted exposure, and it also disables the host-header protection against DNS rebinding.
- The talk frames the real threat as weights poisoned to fetch a payload from a URL, so the weights are not the payload.
- Caveat: the talk admits the observed in-the-wild risk is low (no documented poisoned template or backdoor hitting users yet), though the headline framing is alarmist.
- Caveat: several headline numbers come from third-party research and scans (Pillar, Project Discovery, SentinelOne, Census, a developer's GGUF scan) that were not verified here. Version numbers are inconsistent within the captions (Ollama 0.30.6 vs 0.240.6; 0.17.1 vs 0.10.1 for Bleeding Llama), so check them before acting.
