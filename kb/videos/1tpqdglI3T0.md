> Workshop where attendees attack a Kubernetes-hosted burrito-ordering agent, then add layered infra and AI guardrails (admission, runtime, network, input/output scrubbing, MCP checks) and see which attacks each layer stops.

## Summary
Michael Forrester (Accenture) and Whitney Lee (Datadog) ran a live workshop in which attendees tried to make a Kubernetes-hosted LLM agent exfiltrate data, deploy an arbitrary image, and leak a secret recipe. Model-level refusals were inconsistent: most attacks worked sometimes, and the fork bomb was refused every time. The speakers then walked through a hardened cluster where Kyverno admission rules, runtime enforcement tools, and network policy blocked the infrastructure attacks. For the AI-side attacks they used LLM Guard, first an input guard before the model call and then an output scrubber, which showed the cost and liability trade-offs of each. They closed with an MCP tool-poisoning example and a three-question rubric for when to put an AI step into a workflow. The talk is mostly a demo with live glitches, and the speakers note the IDP repo will be public. The guardrail layering and the cost and PII reasoning are the useful parts.

## Key ideas
- **Naming and framing change model behaviour. Villain-style names like Joker or Megatron made the model assume bad intent and refuse to deploy. Renaming the same image promo-mascot and giving it a marketing story got the deployment approved, even with no system prompt pushing it.** — The speakers say this happened with no pushing system prompt, so it is a real-world test. They also wondered whether positive hero names would be favoured, but did not test it. ([6:15](https://youtu.be/1tpqdglI3T0?t=375))
- **Model-level refusals cannot be the security boundary. Attacks sometimes worked and then stopped working, and the speakers say the same prompt can behave differently across runs. Their advice is to put the guardrails at the infrastructure layer as well.** — The speakers say they are still not sure why refusals varied. Most attacks eventually succeeded within 20 to 30 prompts. The fork bomb was the one exception, and it was refused every time. ([3:56](https://youtu.be/1tpqdglI3T0?t=236))
- **Ordinary Kubernetes and CI/CD security matters more now that an agent can reach the cluster. The speakers say artifact registries, verification, and known SDLC practice cover most of what is needed, and that letting the agent have direct access is the mistake to avoid.** — Kubernetes security is layered and the demo covered only a few parts of it. The speakers say the three possible AI use cases differ in risk, and AI-managed systems are the riskiest. ([13:01](https://youtu.be/1tpqdglI3T0?t=781))
- **Admission control stops bad deployments before they run. Kyverno works as a validating or mutating webhook: it required resource requests and allowed pulls only from the trusted internal registry. Workload identity via SPIFFE or SPIRE can then drive policy about what an agent is allowed to do.** — The speakers call it cluster-level policy, so organisation-specific rules can be written in one place. Challenge two (deploy an external image) was blocked here. ([15:43](https://youtu.be/1tpqdglI3T0?t=943))
- **Runtime tools differ on prevent versus respond. Falco watches the kernel and raises alerts, and Falco Talon can act on them, such as killing the pod. KubeArmor and Tetragon use Linux security modules or eBPF and can block the action before it completes.** — The speakers say an ls command should never run in production. Falco lets it run briefly before a response, while KubeArmor can prevent it entirely. The Falco path failed live, and the team switched tools at the last minute. ([18:00](https://youtu.be/1tpqdglI3T0?t=1080))
- **A fork bomb needs a prevention layer, not a response layer. The speakers say it can spawn many processes in about 200 ms, so detect-then-kill is too slow. Their fix was a kernel-level per-process limit set in a config file.** — The speakers say no model would run a fork bomb, even when told to. Because of that they dropped this as a live challenge and described the fix instead. ([19:23](https://youtu.be/1tpqdglI3T0?t=1163))
- **Excessive agency is the main cause of agent breaches, and it is an infrastructure problem. The usual causes are over-broad scopes and leftover elevated credentials or tokens in the environment. Access, authentication and authorization need to be fixed at the platform level.** — The speakers say a wrong-tenant or process problem can look like a model problem, so the root cause has to be traced rather than assumed. ([23:18](https://youtu.be/1tpqdglI3T0?t=1398))
- **Output scrubbing can be switched on mid-stream and catches sensitive terms as they stream. Its drawback is that the LLM call and its tokens are already paid for. Input guardrails block the request before the model is called.** — The speakers show LLM Guard redacting recipe names and ingredients. The input guard blocks earlier, so there are no model tokens and no PII ever reaches the trace store. The speakers say you probably need both layers, and that the input guard catches about 80 to 90 percent. ([29:47](https://youtu.be/1tpqdglI3T0?t=1787))
- **MCP tool descriptions are an injection channel. In the demo, a weather tool's description told the model to read an internal config and include it in the reply, so the user never saw the exfiltration. The speakers say enterprises should not start by pulling public MCP servers. Tools should come through a registry or gateway.** — The speakers say the attacker could also send the config to an external endpoint. Guardrails on the input side did not reliably stop this attack in the demo. ([41:26](https://youtu.be/1tpqdglI3T0?t=2486))
- **Use a three-question rubric before putting AI in a workflow. Ask whether the system is bounded with known interfaces, whether it is worth the cost, and whether its output can be verified. Software artifacts such as Terraform or Python are good candidates because they can be checked.** — The speakers say these questions matter more than deciding AI is always the answer. They also say the usual non-functional requirements (security, cost, performance, reliability, operational excellence) still apply. ([48:33](https://youtu.be/1tpqdglI3T0?t=2913))

## Techniques
- **Layered guardrails across infra and AI** — Combine Kubernetes admission policy (Kyverno: resource requests, trusted registry only), runtime enforcement (KubeArmor or Tetragon via LSM/eBPF, with Falco for alerting), network policy at L4 and L7, and AI-side input and output guards. Do not rely on any single layer. *When:* Any agent that runs in a cluster or can call tools. Use it when a model refusal is the only thing stopping a bad action.
- **Input guard before the LLM call** — Run cheap regex for known-bad patterns first, then a small (about 8B) classifier such as LLM Guard or NeMo Guardrails. Block the request before the model is invoked. *When:* When each model call costs money, or when users might type PII (card numbers, SSNs) that must never reach traces or storage.
- **Mid-stream output scrubbing** — Turn on an output-scrub rule (LLM Guard) that redacts named sensitive terms while the response streams. It catches the content even after generation has started. *When:* During an incident when you need to stop leakage immediately. Accept that the model tokens for that response are already spent.
- **MCP tool description review and registry allowlists** — Inspect each MCP tool's description for instructions that reference files, config, or other tools. Source tools from a registry or gateway allowlist rather than pulling servers directly from the public internet. *When:* Before connecting any third-party or public MCP server to an agent platform.
- **OpenTelemetry traces for every agent turn** — Instrument the agent and guard proxy with OTel to capture system prompt, tool calls and results, token counts and cost, and the available tool list. Send to any backend (the demo used Datadog). *When:* For auditing agent behaviour, tracing exfiltration attempts, and debugging a single user interaction.
- **Kernel-level prevention for runaway processes** — Set a per-process or per-user process limit in a kernel configuration file so a fork bomb is capped before it exhausts resources. Do not depend on detect-then-kill. *When:* When the agent can execute shell commands and a single runaway loop could take down a node.
- **Agent identity and least privilege** — Give each agent its own workload identity (SPIFFE/SPIRE), write policy against that identity, and remove leftover elevated credentials and tokens from the environment. *When:* Whenever agents are granted cluster or service access, to limit excessive agency.
- **Three-question rubric for AI in a workflow** — Ask: is the system bounded with known interfaces, is it worth the cost, and can the output be verified (for example by tests or a linter)? Prefer workflows where the AI output is checkable. *When:* When deciding whether to add an LLM step to a pipeline or platform.

## Hot takes
- Excessive agency, not model misbehaviour, is the top cause of agent incidents, and it is an infrastructure problem.
- Do not rely on the model to refuse bad actions. Put the guard at the infrastructure layer for every agent in the cluster.
- Do not start an enterprise MCP rollout by connecting public MCP servers. Use a registry, a gateway, or your own servers.
- Input guardrails beat output guardrails for cost and for PII liability, because the data never gets processed or traced.
- Traditional CI/CD and SDLC knowledge is most of what is needed to ship agents safely.
- Regex for known bad patterns should run before any 8B classifier.
