> Why a local Qwen 3.8 27B on a 16GB card often underperforms its leaderboard scores: the reasoning-effort setting, context window, and overthinking. Keep effort at xhigh, size the context to fit, and use the efficiency-tuned Swift 1.5 build.

## Summary
The speaker reproduces a popular claim that Qwen 3.8 27B beats frontier models, then explains why home setups feel weaker. The main cause is the reasoning-effort setting: guides set it to medium, and the chat template gives medium no instruction, while xhigh is the default and the setting the leaderboard runs used. Artificial Analysis data shows the score rising with tokens written (xhigh 34 at about 200M tokens, medium 28 at about 110M, thinking off 20), and GPQA results show the same pattern. The second cause is context: benchmark runs used roughly 250k to 500k token windows, while a 16GB card fits about 110k tokens with 8-bit KV cache and about 128k with 4-bit. The speaker recommends the Swift 1.5 retrain, which cut average thinking tokens by about 42% on GPQA with roughly unchanged accuracy, and treating effort as a per-task dial. He also corrects two circulating numbers and notes that Opus 5.5 at 58 on the same index still leads by 24 points. The video is careful and mostly self-correcting, though its model and benchmark figures come from vendor model cards and one independent tester.

- **Reasoning effort is not a token cap. In the chat template it just adds a line of instruction text: xhigh asks for careful validation and alternatives, low asks for brief thinking, medium gets no instruction, and an unset value defaults to xhigh.** — The speaker opened the template to check this. Examples: a Pac-Man prompt used about 40k thinking tokens at xhigh versus a couple thousand at medium. The speaker says medium is the setting most guides pick and the one with no instruction at all. ([5:56](https://youtu.be/h_KqS4GtU3I?t=356))
- **Artificial Analysis scores rise with tokens written. Across four effort levels, the index tracks output volume.** — xhigh: 34 points, about 200M tokens across the suite. medium: 28, about 110M. low: 26, about 82M. thinking off: 20. Dropping from xhigh to medium gives up 6 points, and medium falls below Opus 4.6 Max, GPT-5.3 Codex and Gemini 3.1 Pro Preview, which xhigh beats. ([7:09](https://youtu.be/h_KqS4GtU3I?t=429))
- **GPQA Diamond shows the same gap in an independent run. medium and low are effectively tied, and both trail xhigh.** — xhigh 88.28%, medium 84.14%, low 84.04%. The author says the leaderboard model runs at xhigh while most home setups run at medium, with the same weights. ([8:17](https://youtu.be/h_KqS4GtU3I?t=497))
- **Common guides cap thinking in ways that defeat the benchmark. A 512-token reasoning budget in llama.cpp cuts thinking to about 3% of the roughly 15k tokens the model averages per GPQA question.** — The speaker says the setup is fast because the frontier behaviour was switched off. It is fine for everyday use, but it does not replicate benchmark scores. ([9:37](https://youtu.be/h_KqS4GtU3I?t=577))
- **Context is the second gap. Benchmarks used 250k-token windows plus about 250k for thinking, and a 500k window for Terminal Bench. A 16GB card runs out first, on long agent sessions with tool calls.** — IQ3 weights with the prediction head are about 12.12 GB. With a 1 GB margin, the card holds about 110k tokens at 8-bit KV cache, or about 128k at 4-bit (one RX 9070 owner at 15.2 GB used). ([10:47](https://youtu.be/h_KqS4GtU3I?t=647))
- **Swift 1.5 is Qwen 3.8 27B retrained to remove overthinking loops (re-checking settled answers). ## Techniques
- **Set reasoning effort on purpose, not to medium by default** — Leave the effort setting at xhigh (the template default) for hard coding, research or multi-step agent work. Use low for easy tasks such as renaming files, and medium for quick factual questions. Do not set a reasoning budget such as 512 tokens if you want benchmark-level answers, since it truncates thinking. Adjust per request; do not fix one value for all work. *When:* Any local run where the answer quality matters more than response time; decide per task by how much failure would cost.
- **Estimate the wall-clock cost of a reasoning run before starting** — Divide expected thinking tokens by measured tokens per second. Example from the video: about 15,000 thinking tokens at 45.6 tok/s is about 5.5 minutes per GPQA question. Terminal Bench averages about 52,000 tokens, which at 31.3 tok/s is about 28 minutes per task. Measure the rate at your real context size, since it drops as the window fills. *When:* Planning a local batch or agent job, or deciding whether to use the hosted endpoint instead.
- **Work out the context budget before loading the model** — Start from the weights size (IQ3 Swift 1.5 is 12.12 GB), subtract about 1 GB for runtime overhead, and fit the KV cache into what remains. Quantize the KV cache to 8-bit (about 110k tokens on a 16GB card) or 4-bit (about 128k on a 15.2 GB-used RX 9070 setup). Set the largest context that fits, since the window is the real limit on long agent sessions. *When:* Loading a large model on a single consumer GPU for agent work that calls tools repeatedly.
- **Free GPU memory before loading the model** — Drive the monitor from the integrated GPU if the CPU has one, because the display stack can hold 1-2 GB on the discrete card. Skip the vision projector unless you need images, since it uses memory that could hold context. *When:* Single-GPU desktops where the discrete card is also the display, or where context is tight.
- **Turn on multi-token prediction** — Enable MTP in the runtime. The speaker credits it for most of the jump to about 45 tok/s from the 30s. Reported on an RX 9070 XT: 43.7 tok/s at 65k context and 37.4 tok/s at 131k. *When:* Speed is the bottleneck on a model that supports MTP.
- **Use an efficiency-tuned build to cut thinking tokens** — Swift 1.5 (UQ AI's retrain of Qwen 3.8 27B, IQ3 with MTP, 12.12 GB on Hugging Face) keeps xhigh and uses fewer thinking tokens. Check its license first: it is UQ AI's own license, not Apache, which matters for commercial use. *When:* You want xhigh-level accuracy with a shorter wait, and the license allows your use.
- **Check which setting a benchmark or guide actually used** — Before comparing a local score to a leaderboard, check the effort setting, context window, quantization, and KV cache precision. Also check whether the number came from a model card, an independent run, or a reused figure. *When:* Reading model-card claims, or repeating a benchmark number in your own docs or decisions.
- **Use hosted inference for long, parallel, or always-xhigh work** — The speaker's rule: rent a hosted endpoint for long agent sessions, full 500k-token windows, all-day xhigh use, or parallel tasks. Hosted Qwen 3.8 27B is $2.20 per million output tokens, which he calls cheap at xhigh. Hosted calls also fail fast on hard problems, where local xhigh can run 25 minutes. *When:* Local hardware runs out of context, or a hard task would tie up the GPU for a long time.

## Hot takes
- Reasoning effort is a prompt instruction, not a token budget, and medium is the one setting with no instruction at all, which is why guides that recommend it lose most of the benchmark gain.
- Speed demos on home cards are often fast because the frontier part of the model was turned off (for example by a 512-token reasoning budget), so they should not be called frontier performance.
- Frontier was never a file size; it is how long the model is allowed to think, which is why the speaker treats effort as a per-task dial.
- Local xhigh is not a free upgrade: on hard tasks it can run for 25 minutes before giving up, and hosted inference is cheaper for long or parallel work.
- Qwen's card-reported gains (for example 58.5% fewer GPQA tokens) overstate the typical case; the average is closer to 42%, and independent coding tests show a small accuracy drop for Swift v1.
