> Explains why the viral RTX GPU "unlock" doubles only one FP16 microbenchmark: real gains land on 16-bit serving, long-context prefill and image/video work, not token decode or GGUF, and power caps can cost more than the unlock gains.

## Summary
The video traces the RTX 4090's marketed 1321 TOPS down to about 165 effective TOPS in a real 16-bit workload through three factors: structured sparsity, 8-bit versus BF16 inputs, and FP32 versus FP16 accumulation, the last of which GeForce cards run at half rate. NVIDIA's own Ampere whitepaper documents the accumulator difference, and an open-source kernel module reportedly flips the two registers before the driver loads. The presenter reports, mostly via other users' measurements, that the unlock doubles only a raw matmul microbenchmark, gives roughly 12 to 34 percent on real matmuls, and does nothing for token decode, which is memory-bandwidth bound. Gains depend on the data path: vLLM prompt processing, image and video generation, and long-context flash attention benefit, while GGUF integer math in llama.cpp, Ollama and LM Studio does not. The most actionable finding is that GPUs capped at 200 to 250 W throttle their clocks so hard that they are both slower and less energy-efficient per token than at a higher limit. The module requires disabling Secure Boot and relies on an exploit of a publicly released debug firmware, so the presenter urges reading the code and weighing the risk. RTX 50-series cards have no known path yet.

## Key ideas
- **The 1321 TOPS box number is a stack of conditions, and a real 16-bit workload gets about 165 TOPS on a 4090.** — Three factors halve the number each time: structured sparsity (assumes half the weights are zero in a fixed pattern, 1321 to 660), 8-bit inputs versus BF16 (660 to 330), and FP32 versus FP16 accumulation, which GeForce runs at half rate (330 to 165). Most models ship BF16 and most real code uses FP32 accumulation. ([1:19](https://youtu.be/VIm73gaY_hM?t=79))
- **The half-rate accumulator is documented in NVIDIA's own Ampere whitepaper, not hidden.** — The appendix lists the RTX 3090 at 142 TFLOPS with FP16 accumulate and 71 with FP32. The RTX A6000, which uses the same silicon and costs about $4,650, is listed at 154.8 TFLOPS in both modes, and the 2018 Titan RTX ran both at full speed. ([4:08](https://youtu.be/VIm73gaY_hM?t=248))
- **The restriction is two register settings, and an open-source kernel module flips them before the driver loads.** — The module changes nothing permanently on the card, and the stock driver is untouched. Removing the boot option and power-cycling restores stock behavior. Ports exist for RTX 40-series (a fork called GPU Unlock Ada) and Turing (2080 Ti). The repo reportedly reached about 10,000 GitHub stars in nine days. ([5:17](https://youtu.be/VIm73gaY_hM?t=317))
- **The microbenchmark doubles, but real workloads gain far less because the clock drops.** — Doing twice the work per tick hits the power ceiling, so a 3090 at 250 W fell from 1531 to 1087 MHz (about 30 percent) while reading a long prompt, and still finished faster. Real FP16 matmul gained 12 to 34 percent, and some BF16 configurations gained nothing. The efficiency gain (20 to 33 percent less energy per token on prompt reading) is the more durable benefit. ([7:35](https://youtu.be/VIm73gaY_hM?t=455))
- **Token decode does not improve, because it is limited by memory bandwidth.** — Each generated token streams the model weights from VRAM, so decode is bound by bandwidth (936 GB/s on a 3090). Stock vLLM decode went from 112.98 to 114.24 tokens/s, which the presenter calls noise. The unlock also adds no VRAM, does nothing for mining, and has not shown frame-rate changes in games. ([10:00](https://youtu.be/VIm73gaY_hM?t=600))
- **The benefit depends on which data path the backend uses.** — GGUF backends (llama.cpp, Ollama, LM Studio) run int8 tensor math, which was never locked, so the gains are roughly zero (0.983x on a modded 4090). vLLM, full-precision image and video generation, and fine-tuning run 16-bit math and benefit. The exception is llama.cpp's flash attention, which uses FP16 accumulation, so the gain grows with context length. ([12:34](https://youtu.be/VIm73gaY_hM?t=754))
- **Cold prefill on a long context is where the unlock saves real wall-clock time.** — On a single 3090 under vLLM at 375 W, a 96K-token cold prefill (after a cache miss on session restart) took 105.7 s stock and 71.4 s unlocked. The presenter's estimate is about 11 minutes per day for 20 restarts. Decode speed barely changed. ([14:51](https://youtu.be/VIm73gaY_hM?t=891))
- **A tight power cap can make a GPU slower and less efficient, which matters more than the unlock.** — A 3090 at 200 W ran at 50 tokens/s with its clock collapsed from about 1380 to 714 MHz, using 3.97 J per token. At 250 W it ran at 76.4 tokens/s and 3.15 J per token. The presenter's advice is to check the power limit first, using one command or slider in the GPU management software. ([16:06](https://youtu.be/VIm73gaY_hM?t=966))
- **The module carries real security costs, so the decision needs to be made with eyes open.** — It is unsigned and requires disabling Secure Boot. It works by exploiting a stack overflow in signature checking in a publicly released debug build of NVIDIA's boot firmware, which is encrypted with a publicly known test key. The Windows version also requires BitLocker off and is tied to one card, board, and BIOS version. A user reported 8 hours of mixed inference at 82 to 86 C, the same as stock, with no errors. ([18:16](https://youtu.be/VIm73gaY_hM?t=1096))
- **Who benefits: Linux users on vLLM, image, video, fine-tuning or long-context coding agents, not Windows Ollama or LM Studio users.** — The presenter's audience split is Windows plus GGUF chat users (no benefit, since the VRAM is the limit) versus Linux 16-bit workloads on dedicated machines (a real gain). RTX 50-series cards have no known fix, because no debug firmware has been found for that generation. ([20:47](https://youtu.be/VIm73gaY_hM?t=1247))

## Techniques
- **Identify the data path before expecting a GPU gain** — Check whether the backend runs GGUF/int8 kernels (llama.cpp, Ollama, LM Studio) or 16-bit tensor math (vLLM, diffusers-style image/video, fine-tuning). Expect 16-bit-accumulate changes to matter only for the 16-bit path, and for llama.cpp only in flash attention at long context. *When:* Before buying, tuning or hacking a GPU for a specific inference or generation workload.
- **Check and raise the GPU power limit before anything else** — Read the current power limit in the GPU management tool and raise it from a tight setting (the video's example is 200 W to 250 W). Measure tokens/s and energy per token (watts divided by tokens/s, a derived check) at each limit, and watch clock speed for throttling. *When:* When the card is capped below stock for noise, heat or electricity reasons, or when decode throughput looks low.
- **Benchmark prefill and decode separately** — Measure time-to-first-token on a long cold prompt (after a restart or cache miss) separately from steady-state decode tokens/s. Run prefill at several context lengths (the video used 0, 32K and 100K tokens) to see how attention scaling changes the picture. *When:* When judging whether a hardware or kernel tweak helps an agent workload with long context and frequent cold starts.
- **Treat unsigned firmware or kernel modules as high-trust code** — Read the short source before loading anything that runs before the OS. Keep the revert path in mind (remove the boot option and power-cycle). Do not disable Secure Boot on a daily-driver machine. Watch for upstream changes that could close the flaw. *When:* Evaluating any community GPU unlock or boot-time hook.

## Hot takes
- Headlines like 'your card doubled' are true only in a raw FP16 microbenchmark. Real gains are narrower and mostly on 16-bit workloads.
- For many users, the power limit is the bigger lever. Capping a 3090 at 200 W makes it slower and less energy-efficient per token than 250 W.
- Disabling Secure Boot and loading an unsigned boot-time module to exploit a public test-key debug firmware is a real security trade-off, and the presenter recommends reading the code first.
- Windows Ollama or LM Studio users with quantized GGUF models get essentially no benefit. The card's real limit for them is VRAM, which the unlock does not change.
- Most figures come from individual GitHub users' benchmarks, not the presenter's own runs, so they are single-source.
