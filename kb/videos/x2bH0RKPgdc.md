> Bilge Yücel (deepset) on building AI under sovereignty constraints: four pillars, what breaks when you move from frontier APIs to self-hosted, and a guardrail-agent-guardrail reference design built on Haystack.

## Summary
The speaker, a developer relations engineer at deepset, defines sovereign AI as an organization's explicit control over data flow, model choice, infrastructure, observability and operations. She splits this into four pillars (data, model, infrastructure, operational) and says sovereignty is a spectrum, so teams should know their level of vendor lock-in rather than aim for full air-gap by default. She lists what typically breaks when a team is asked to go sovereign: model replacement (API translation, prompt rewrites, re-evaluation), splitting data across jurisdictions (search routing across databases), on-prem Kubernetes and GPU networking, and missing observability and version control for the application layer. The talk then pitches Haystack as addressing these with a consistent interface, typed explicit data flow, YAML-serialized pipelines for versioning, and open source code. The reference design wraps an agent in an input guardrail (prompt injection and regulatory checks, routed safe/unsafe), an agent with MCP tools filtered per agent and searchable via BM25, per-tool human confirmation, and an output guardrail for sensitive leaks, all traced via OpenTelemetry. The talk closes with a checklist, including whether models can be swapped without changing application logic and whether incidents can be handled without a hyperscaler vendor. Much of the content is high-level, and the Haystack parts are vendor promotion.

## Key ideas
- **Sovereignty as a technical property: explicit control over data flow, model choice, infrastructure, observability and operations** — The speaker turns the policy definition into four engineering pillars: data, model, infrastructure and operational sovereignty. Each pillar gets a concrete question, such as where data is processed, who controls the running model, where compute happens, and who owns incident response. ([1:03](https://youtu.be/x2bH0RKPgdc?t=63))
- **Data sovereignty covers more than storage location** — Sending data to an embedding API hosted abroad already breaks control, even if the data is stored in-region. Internal access permissions that let staff see data they should not are also treated as a sovereignty breach. ([2:15](https://youtu.be/x2bH0RKPgdc?t=135))
- **Hosting is a spectrum with different compliance trade-offs** — The speaker orders hosting options from air-gapped (tied to EU AI Act safety) through private VPC (GDPR) and sovereign cloud (depends on provider) to SaaS. She says SaaS from a US-headquartered vendor carries CLOUD Act exposure even when it runs in Europe. These are her claims and are not verified here. ([3:24](https://youtu.be/x2bH0RKPgdc?t=204))
- **Model sovereignty means swapping models without changing application code** — Being technically free to switch providers does not help if the codebase cannot switch within a day. Provider outages and price increases are presented as the cost of coupling to one model. ([4:28](https://youtu.be/x2bH0RKPgdc?t=268))
- **Operational sovereignty covers monitoring, human approval and auditable change** — Teams need to watch model inputs and outputs in production, keep a human in the loop for high-stakes domains like HR or finance, and version model and application-layer changes in an auditable way. ([5:40](https://youtu.be/x2bH0RKPgdc?t=340))
- **Going sovereign usually breaks the model layer first, then search, infrastructure and observability** — Replacing a frontier API means translating API logic, updating prompts and re-evaluating from scratch. Splitting private data across jurisdictions makes search routing hard. Moving to on-prem exposes Kubernetes, GPU networking and cloud-managed dependencies, and black-box pipelines have to be made traceable and version-controlled. ([6:50](https://youtu.be/x2bH0RKPgdc?t=410))
- **Guardrail, agent, guardrail is the reference shape for a sovereign agent** — An input guardrail checks for prompt injection and regulatory intent and routes unsafe input out early. The agent is an LLM with a system prompt, tools, knowledge-base search, other agents and MCP servers. An output guardrail checks for sensitive data leaking to the user. Tracing wraps the whole pipeline. ([11:55](https://youtu.be/x2bH0RKPgdc?t=715))
- **Scale tool access with per-agent MCP filtering and BM25 tool search** — The agent gets only the named tools it needs from an MCP server, not the whole catalogue. When there are hundreds of tools, a searchable toolset with BM25 lookup keeps the tool definitions out of the context window. ([15:17](https://youtu.be/x2bH0RKPgdc?t=917))

## Techniques
- **Sovereignty checklist as a design gate** — Ask whether models can be swapped without changing application logic, whether run logs are reproducible and stored compliantly, and whether the team can respond to an incident without a hyperscaler vendor. Also map each system to the four pillars and decide how much control each one needs. *When:* When a working system is asked to become sovereign, or when choosing a provider or hosting tier for a regulated domain.
- **Safe/unsafe router as an input guardrail** — Run a local classifier LLM on the user input, then route it to a safe branch that continues to the agent or an unsafe branch that exits the application immediately. Use a router component to do the classification. *When:* Before any agent step where prompt injection or regulatory-intent checks must run first.
- **Per-agent tool allowlist plus BM25 tool search** — Connect an MCP server, select only the named tools each agent needs, then put the tools in a searchable toolset so the agent searches by BM25 instead of loading every definition into context. *When:* When an MCP server or tool catalogue has hundreds of tools and each agent should see only a subset.
- **Per-tool human confirmation strategies** — Attach confirmation rules to individual tools so that high-impact tools, such as payment requests, need human approval, while other tools run without interruption for the rest of the cycle. *When:* When some agent actions are sensitive and the approval rule should depend on the specific tool.
- **Pipeline serialized to YAML for version control** — Export the full pipeline definition to YAML, commit it to git, and use commit history to recover earlier application versions. *When:* When the application layer must be auditable and versioned like code.
- **Tracer component wrapping the pipeline** — Add a tracer as the first component so every component input and output, and agent tool call, is sent to an LLM observability tool or to OpenTelemetry. *When:* When the pipeline must be auditable, or when a black-box agent needs to be made observable.

## Hot takes
- Replacing the frontier model is usually the first sovereignty step, and it is also what breaks the most.
- SaaS from a US-headquartered company carries CLOUD Act risk even when the application runs in Europe.
- Not every enterprise needs full air-gap sovereignty; the real requirement is knowing your level of vendor lock-in.
- A good orchestration framework cannot solve GPU limits, but it can make swapping and tracing easier.
