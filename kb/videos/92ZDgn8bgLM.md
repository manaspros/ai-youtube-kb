## Summary
The video walks through a framework from an article by Felix Rieseberg, who led engineering for Claude's apps at Anthropic, on getting far more out of Claude Code than a literal task list. Felix's core claim is that agents do exactly what is asked and then stop, so the prompt has to name the result being chased. He describes four ways of going beyond the ask: speed, altitude, depth, and range, with speed being what most people already do. Altitude means stating the end outcome (for example, hiring faster) and asking for diagnosis and recommended actions, not just a dashboard of numbers. Depth means using a meta-prompt that rewrites the task to require what a professional would do, which methods and tools to use, and independent evidence that the result is correct, rather than adopting a persona. Range means describing the product by what it does for people, then spawning specialist sub-agents that review it one after another, each fixing things before the next runs. The video also recommends impossible-sounding goals (make it feel instant, not faster) and an outside judge: a different model or a second non-interactive session reviews the builder's work. Finally, the video stresses that all of this depends on giving the agent the resources to verify itself, such as crash reports via MCP, version-to-code mapping, and a place to reproduce bugs. The exact prompts are only in the linked article and are not in the video.

## Key ideas
- **Agents stop at the literal task; name the result you want, not the task.** — The narrator says agents finish the task and call it done because nothing in the prompt says what it was supposed to achieve. Felix cites a study, not named in the video, that people with a specific hard goal outperform people told only to do a task. ([1:21](https://youtu.be/92ZDgn8bgLM?t=81))
- **Altitude: prompt for the outcome and for diagnosis, not just the artifact.** — Example: a reports dashboard should be built around the goal (hiring faster), explain why the result is not being hit, list problems, and recommend actions. Felix's crash example: ask for the app to be crash-free instead of fixing one issue at a time. The video says this works for outcome-driven work, not creative work. ([2:49](https://youtu.be/92ZDgn8bgLM?t=169))
- **Depth: role personas change tone, not method, so ask for the methods experts use.** — Felix's meta-prompt rewrites the user's task to ask for a deeper version, not a bigger one. It asks what a professional would do that was not requested, what material to start from, which specific methods and tools to use, and what evidence besides the model's own claim would show the result is right. The output is a new prompt to run in a fresh session. ([3:51](https://youtu.be/92ZDgn8bgLM?t=231))
- **Set goals that sound almost impossible so the agent cannot just tweak the existing code.** — Example: instead of 'make the site faster', ask for 'make it feel like the site loads instantly'. The narrator argues a small goal lets the agent make small tweaks, while an unreasonable-sounding goal forces a rethink of how the system works. ([6:45](https://youtu.be/92ZDgn8bgLM?t=405))
- **Never let the builder judge its own work; use an outside judge from a different model.** — The builder made every decision, so it is a poor judge. Options: have Claude run the Codex CLI for an in-depth review, or spawn a non-interactive Claude Code session in the background. The narrator recommends a different model from the one that built the feature. Claude then implements the fixes from the findings. ([6:45](https://youtu.be/92ZDgn8bgLM?t=405))
- **Range: describe the product by the verb (what it does for people), then bring in specialist viewpoints.** — Replace 'what the app is' with 'what it does for people' (example: earn strangers' trust with their next job, and companies' trust with their services). Then ask the agent to spawn sub-agents, each as a specialist role. They run one after another, and each fixes things before the next starts. The narrator says this is slow but gives a much better end result. ([8:13](https://youtu.be/92ZDgn8bgLM?t=493))
- **Each of these approaches only works if the agent can verify its own results.** — Felix gave his agent three things to keep apps crash-free: the crash reports (via an MCP connection to the crash tracker), the context to map versions to code changes, and a machine where it can reproduce each crash and test its fix. The point is to let the agent prove a fix works instead of asserting it. ([9:41](https://youtu.be/92ZDgn8bgLM?t=581))

## Techniques
- **Outcome-first prompt (altitude)** — State the business result you want (example: hire faster). Ask the agent to explain why the current state misses it, list the problems, and recommend actions and key decisions. Do not ask only for the artifact (dashboard, feature). *When:* Outcome-driven work with a measurable goal: dashboards, reliability work, fixing a class of bugs. Not creative work with no single right result.
- **Expert-method meta-prompt (depth)** — Give the agent your task and a meta-prompt that asks it to rewrite the task as a deeper version, not a bigger one. Have it state: what a professional would do beyond the request, what material to start from, which methods and tools experts use, and what evidence beyond its own claim shows the result is correct. Take the generated prompt and run it in a fresh session. The exact prompt is in Felix's article, which is linked in the video description and is not spoken in the video. *When:* When the output should follow expert practice, not just sound like an expert. Use persona prompts only for tone.
- **Impossible-sounding goal reframing** — Replace an incremental target with an outcome that cannot be reached by tweaking (example: 'make it feel like the site loads instantly' instead of 'make it faster'). This forces a redesign rather than small optimizations. *When:* Performance, UX, and reliability goals where the agent would otherwise take the safe, incremental route.
- **Outside judge via a second model** — After the builder finishes, have a separate reviewer do an in-depth review of the new feature. Options named in the video: ask Claude to run the Codex CLI (installed on the machine) for the review and return findings, or spawn a non-interactive Claude Code session in the background. Use a different model from the one that built the feature. Feed the findings back so the builder implements the fixes. *When:* After any agent-written feature where self-review is unreliable. Use it as a quality gate before calling work done.
- **Noun-to-verb role discovery and sequential specialist sub-agents (range)** — Write the product goal as a verb-phrase of what it does for people (example: 'get strangers to trust us with their next job'). Ask the agent to examine the app from as many angles as possible. It should spawn sub-agents, each taking a specialist role relevant to that goal. Run them one after another; each proposes and implements fixes before the next starts, so later agents see earlier fixes. Expect a long run. *When:* When one reviewer's view is too narrow, and when run time does not matter much. The sequential order is the main cost.
- **Verification resources for agents** — Before expecting proof, give the agent: (1) the error or crash data, connected via an MCP server to whatever tracker you use; (2) a way to map deployed versions to code changes; (3) an environment where it can reproduce the failure and run its fix. Require the agent to show that the fix worked by running the reproduction, not by asserting it. *When:* Any bug-fixing or reliability task. Without this, the other techniques cannot be checked.
