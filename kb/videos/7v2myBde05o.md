> A sponsored live demo from Gravitee's CTO showing that agent governance (identity, rate limits, caching, prompt-size and topic gates) belongs in the gateway, not in prompts or policy docs.

## Summary
Sam, CTO of Gravitee, skips slides and runs five live scenarios comparing an agent that enforces policy itself with the same agent behind a gateway. He argues that policy documents and prompt instructions do not hold at runtime, so access should be enforced through a scoped, per-task identity at the gateway. The demos cover prompt-injection-driven deletes (blocked with a 403 while the agent still completes the permitted part), PII exfiltration, a buggy agent looping on requests (rate-limited to 3 per minute), semantic caching of repeated questions, and oversized or off-topic prompts rejected before any downstream LLM call. He closes with a scale argument (about 144 agents per human identity), per-tool trimming of MCP servers, and shadow-AI edge management. The talk is a vendor pitch: he admits the customer data is mocked in places, gives few latency or accuracy figures, and does not explain how the topic-relevance check works.

## Key ideas
- **Enforce agent policy in the infrastructure layer, not in the prompt, skills, or markdown policy files.** — Policy documents are not read at runtime, and models try to be helpful, so they will do what the prompt asks. The speaker's position is that controls belong in the gateway, where the agent's identity is scoped. ([1:16](https://youtu.be/7v2myBde05o?t=76))
- **Prompt injection through a tool the user is allowed to call is stopped by a per-task, scoped identity at the gateway.** — The ungoverned agent deleted every booking when asked, because the user had permission to the tool. The gated agent discovered the same tool, but the gateway returned 403 because the admin token was only valid for the task. The agent then completed the part it could do and said so. ([2:39](https://youtu.be/7v2myBde05o?t=159))
- **Data exfiltration is blocked at the gateway, not after the LLM has already returned the data.** — A request for the full guest list with emails and card details came back in full from the ungoverned agent. The gateway blocked the gated agent's request for lack of permission. The speaker says the data was mocked, and that the 'live' claim covers the flow, not the data. ([5:22](https://youtu.be/7v2myBde05o?t=322))
- **A buggy looping agent gets rate-limited at the gateway, before it spends tokens downstream.** — Eight identical requests, about 1,000 tokens (roughly one cent) in the ungoverned case. The gateway allowed three per minute and blocked the rest, so none reached the LLM. The speaker's point is that per-request cost compounds across many agents. ([6:42](https://youtu.be/7v2myBde05o?t=402))
- **Semantic caching at the gateway serves near-duplicate prompts from Redis.** — Repeated 'list my bookings' requests went from about 1,000 tokens each to about 200 tokens when served from cache. Similarity is a 0 to 1 setting that can be tuned per agent, audience or user. Telemetry can be exported to Datadog, Splunk or Prometheus. ([9:19](https://youtu.be/7v2myBde05o?t=559))
- **Prompt size and topic relevance can be policies at the gateway, rejected before any downstream spend.** — A 2,000-token prompt (10 minutes of chat transcript) was blocked with advice to split the task, so no downstream call was made. An off-topic weather question was also rejected before reaching the model, because it does not match the hotel-booking use case. ([10:40](https://youtu.be/7v2myBde05o?t=640))
- **Agent sprawl makes hard-coded governance unworkable, so a central gateway is required.** — The speaker cites a colleague's figure of about 144 agents per human identity, and argues that agents creating agents make per-agent controls fail. He also argues that logs must be auditable for regulation and retraining. ([12:44](https://youtu.be/7v2myBde05o?t=764))
- **Restricting which MCP tools are exposed reduces both blast radius and token cost.** — A third-party CRM MCP server exposes 64 tools, and all of them go into context on every call. The gateway's MCP studio lets an operator publish a smaller tool set for each agent. ([14:44](https://youtu.be/7v2myBde05o?t=884))

## Techniques
- **Per-task scoped agent identity via token exchange** — The user's request is exchanged for a short-lived JWT whose claims cover only the task being run. Admin-level tools are gated by that token, and the gateway returns 403 for any tool call outside the scope. Identity can come from any IDP or from the gateway itself. The speaker shows this with the request flow, the tool calls and the 200/403 codes in the packet view. *When:* Agents can reach powerful tools (delete, export, admin) and the user is authorized for those tools in general, but not for this specific task.
- **Gateway-level rate limiting on agent requests** — The policy is a per-user or per-permission cap, shown as 3 requests per minute. Requests over the cap are rejected at the gateway, so no LLM call or downstream tokens are spent. *When:* Buggy or looping agents, or any workload where spend should be bounded per user or audience.
- **Semantic cache keyed on prompt similarity** — Similar prompts are matched by a similarity score on a 0 to 1 scale (1 is near-identical), and matches are served from a Redis-backed cache built into the gateway. The threshold can be set per agent, audience or user. Cache hits are logged with the rest of the traffic. *When:* FAQ-style or help-desk workloads where many users ask the same question, and where zero latency and zero LLM cost are worth a small risk of a wrong cached answer.
- **Pre-request prompt size and relevance policies** — Prompt length is checked against a token limit before the request is forwarded. A separate relevance check compares the request to the agent's stated use case and rejects off-topic input. Rejected requests return guidance, such as splitting the task into smaller steps. The talk does not say how the relevance check is implemented. *When:* Users paste huge context, or an agent is used as a general-purpose assistant where costs are not justified by its purpose.
- **Narrowing MCP servers to a per-agent tool subset** — Put a gateway-hosted MCP layer in front of a third-party MCP server, and expose only the tools each agent needs (the talk's example: 64 tools cut down to a few). *When:* Large third-party MCP servers whose full tool list adds significant context and widens what a compromised or confused agent can call.
- **Export gateway telemetry to existing observability stack** — Request and policy events are logged at the gateway and exported to Datadog, Splunk or Prometheus. The speaker mentions OpenTelemetry for following multi-hop A2A and agent-to-agent calls. *When:* You need an auditable record of which agent called which tool under which identity, for compliance or debugging of multi-agent chains.

## Hot takes
- Sponsored talk: the 'live, not scripted' framing is partly undercut by the speaker's own admission that the guest data was mocked. Quality is capped at 2 for this reason.
- The thesis (enforce at the gateway, not in prompts or policy docs) is reasonable. The evidence is five hand-picked demos with no latency overhead, false-positive rate, cache hit-rate or topic-check accuracy reported.
- The speaker says the platform does not lock you in, but the whole argument is for one vendor's gateway, and it is not stated what is open source.
- The 144-agents-per-human figure is second-hand and unsourced in the talk.
