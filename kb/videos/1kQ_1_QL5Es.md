> Walkthrough of Microsoft's Token Economizer, a Claude Code plugin that learns per-project token waste (repeated mistakes, unused tools, stuck loops) and cuts it; reports 21-31% savings and a cold-start caveat.

## Summary
AI LABS presents Microsoft's Token Economizer, a plugin for Claude Code, Codex and other agents that reduces per-request token cost by learning from each project's past sessions rather than building a file map like tools such as Graft. It targets three sources of waste: repeated mistakes (saved as "micro skills" facts injected at session start), tools that go unused (turned off per project after 10 unused messages across at least two sessions), and agents stuck in loops (a model checks for stuckness, nudges once, then asks the user to press Escape). Microsoft's own benchmark (277 bugs across six GitHub projects, five setups) reports lower cost on every setup, for example 23.6% for Sonnet 5 and 30.9% for Opus 4.8 on Claude Code, with no loss in task performance. The speaker's own tests show the tool costs more in early sessions because it has nothing to learn from, so they modified it to seed its state from existing .claude session history. On their demo project, per-message tokens fell from about 34,300 to 24,400, and in a second app a three-task run took 79 steps instead of 99 (about 21% cheaper). Micro skills are off by default because they spend some of the user's limit and because facts derived from command output can carry prompt injection. A sponsored segment (Data Impulse) appears mid-video.

## Key ideas
- **Learns from your own sessions instead of mapping the project** — Unlike map-based token savers (the speaker names Graft), Token Economizer watches each session and the commands the agent runs, tracks where tokens are wasted, and cuts that waste from later sessions. The speaker claims savings grow with use. ([0:00](https://youtu.be/1kQ_1_QL5Es?t=0))
- **Four kinds of per-request waste: instructions, tool list, MCP/skills, and history** — Every request re-sends standing instructions, the full tool list, MCP tools and skills, and the whole conversation. The speaker argues much of this is unneeded on repeat work in the same project, and that agents re-learn the same failures each session. ([2:15](https://youtu.be/1kQ_1_QL5Es?t=135))
- **Repeated mistakes become per-project micro skills** — When the same failing command recurs, the tool writes it down as a project fact. Once a few more sessions confirm it, the fact is saved and handed to the agent at the start of each new session so it stops retrying the failing command. ([3:38](https://youtu.be/1kQ_1_QL5Es?t=218))
- **Unused tools are switched off silently** — A tool not used across 10 messages spanning at least two sessions is disabled for that project. The speaker says this is Microsoft's largest saving because it shrinks the tool list sent on every turn. It happens without notice, so a prune command is provided to inspect and restore. ([3:38](https://youtu.be/1kQ_1_QL5Es?t=218))
- **Stuck detection escalates in two steps** — When a run goes on much longer than the agent's usual response time, the tool asks a model whether Claude is really stuck. If so, it tells Claude once to try something different. If it is still stuck, it tells the user to press Escape. It never stops the agent itself. ([4:43](https://youtu.be/1kQ_1_QL5Es?t=283))
- **Hook-based architecture: start, per-tool, and end** — A session-start hook injects micro skills, a hook after each tool use runs the stuck check, and a session-end hook reviews the whole transcript to learn new facts and count unused tools. ([6:06](https://youtu.be/1kQ_1_QL5Es?t=366))
- **Micro skills are off by default for two reasons** — They cost limit, since a model reads recent sessions every three sessions. They are also a prompt-injection path: a malicious project's command output could insert instructions that Claude treats as facts in every session. The speaker advises enabling them only for projects you wrote. ([7:33](https://youtu.be/1kQ_1_QL5Es?t=453))
- **Cold start makes it cost more at first** — In Microsoft's tests almost every project cost more with the plugin until about the sixth task, because state is per project and starts empty. The speaker's fix is to have Claude Code modify the plugin so the first session after install reads prior session history from the .claude folder (30-day retention) as its starting state. ([8:42](https://youtu.be/1kQ_1_QL5Es?t=522))
- **Measure before trusting the savings** — Run status, microskills, tool prune and tool prune measure to see what was learned, what facts are injected, which tools are off and why, and the per-message token delta. The speaker's demo project went from about 34,300 to 24,400 tokens per message. ([10:09](https://youtu.be/1kQ_1_QL5Es?t=609))

## Techniques
- **Install the plugin for your agent** — Open the GitHub repo for Token Economizer, scroll to the install section, copy the install command for your agent (Claude Code, Codex, etc.), and run it in the terminal. Then open Claude Code and run the plugin command to confirm Token Economizer is listed; it adds commands and hooks. The video does not show the repo name or the exact install string, so take it from the repo. *When:* First-time setup on a machine with Claude Code or Codex.
- **Enable micro skills only for your own projects** — Run the tool's config command (the video says 'token economizer config', auto-caption, exact spelling not shown) and set micro skills to on. Everything else is on by default; micro skills are the one feature that starts off. *When:* Projects you wrote and trust. Keep off for cloned or third-party repos because command output can inject instructions into the facts.
- **Per-project repeated-failure facts** — The tool watches for the same failing command or tool call across sessions. After several confirming sessions it saves the fact for that project and injects it at SessionStart so the agent knows what not to retry. Inspect the injected facts with the microskills command. *When:* Repos where the agent repeatedly runs a broken build, test, or CLI invocation. Relevant to ProsHarness or AgentOS if they want to mine failures into reusable facts.
- **Prune unused tools per project, then restore on demand** — A tool unused across 10 messages over at least two sessions is turned off for that project. List pruned tools with 'tool prune' (shows the message count since last use). Restore one with 'tool prune restore <tool-name>'; restored tools are not pruned again. *When:* Sessions with many MCP servers or built-in tools that inflate every request. Check the prune list whenever Claude suddenly lacks a tool.
- **Measure the tool-definition overhead** — Run 'tool prune measure' to compare tokens per message with all tools versus only the tools in use. The demo reported about 34,300 down to about 24,400 tokens per message on one project. *When:* Before and after pruning, to confirm the saving is real for your project.
- **Two-step stuck escalation** — Use a post-tool hook to detect long runs without progress. Ask a model whether the agent is stuck. If yes, inject one instruction to change approach. If still stuck, surface a message to the human to interrupt. Never auto-kill the run. *When:* Long autonomous coding runs, such as ProsHarness-style checkpointed loops, where tight retry loops burn tokens.
- **Seed a new tool from existing session history** — Ask Claude Code to modify the plugin so the first session after install reads the prior session logs in the .claude folder (30-day retention) and uses them as initial state instead of a blank slate. The speaker says this removed the early-cost penalty in their tests, but offers no numbers beyond the demo. *When:* Adopting a learning-based token tool on a project that already has history.
- **Three-hook layout for an agent harness** — SessionStart injects learned facts. PostToolUse runs the cheap stuck check and tool-usage counting. Session end (Stop) reviews the full transcript to extract new facts and update counters. Keep expensive model calls out of the per-tool path. *When:* Designing hooks for a Claude Code wrapper or harness.
