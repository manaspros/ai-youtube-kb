## Summary
A 4-minute Better Stack review of OpenAI's Codex SDK, which the host describes as the programmatic counterpart to the Codex CLI, IDE extension and web product, and as TypeScript-only. The host builds a minimal script: an API key read from a .env file, a new thread, and a single run that returns the agent's items and a usage object. He shows that a non-reasoning run uses more input and output tokens than a reasoning run, and lists the three sandbox modes (read-only, workspace-write, danger-full-access). He then covers resuming a thread by ID, forcing a structured response with a custom JSON schema or zod, and switching from run to runStreamed to consume typed events in a for-await loop. The demo adds a tool call (a file count), shows command items appearing before the agent message, and wraps everything in an interactive prompt loop with follow-ups. The verdict is that the SDK lacks features he needs (visible selected model, changing the system prompt, custom tools, hooks, custom slash commands), so he stays with the Claude Agent SDK and will watch the Codex SDK for changes. There are no benchmarks and no head-to-head task results behind the "clearly better" claim.

## Techniques
- **Minimal Codex SDK script** — Import the Codex class and construct it with an API key loaded from a .env file. Call the start-thread method to open a conversation, then call run with the prompt and print the result (the transcript shows the result as an items array followed by a usage object). Method names are as captioned: startThread and run. *When:* A first working call to the SDK, or a quick check of what a run returns (items, final response, usage).
- **Choose a sandbox mode per run** — Set the sandbox mode in the run options to one of read-only, workspace-write or danger-full-access. The host uses read-only so the agent cannot change his files. He does not show the option's exact key name. *When:* Review, analysis or read-only automation, where the agent must not write to the workspace.
- **Resume a thread by ID** — Store the thread ID from a previous run and call the resume-thread method with it, so later prompts continue the same conversation. The transcript mentions this but shows no code. *When:* Multi-turn agent sessions that must survive process restarts or be split across steps.
- **Structured response via JSON schema or zod** — Pass a custom JSON schema, or a zod schema, as the response format so the final output is typed data. *When:* Pipelines that parse the agent's answer, such as CI checks that need a fixed shape.
- **Stream typed events with runStreamed** — Replace run with runStreamed, which returns an event stream. Loop over it with for await, log each event, and branch on event.type. Each type carries a different payload (item, thread ID, usage), so read the field that matches the type. *When:* Live progress output, or showing tool calls and reasoning as they happen instead of waiting for the full response.
- **Interactive loop over one thread** — Read a user prompt, run it on the same thread, print the agent message and usage, then ask for the next prompt. The host's demo asks for a file count (tool call), then a follow-up about the line count of index.ts. *When:* A simple chat-style agent in a terminal, to check that follow-up turns keep context.
