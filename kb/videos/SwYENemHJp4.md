## Summary
A casual Better Stack podcast episode with hosts Richard, James and Andrus and guest Bash Bunny, a former maintainer at Charm who streams. Most of the 78 minutes covers personal history: moving from Neovim to Doom Emacs because plugin updates kept breaking the config, using org mode for planning and daily notes, switching from i3 to Sway and hitting Wayland issues, and remote development from a Mac into a Linux box. The AI-related part is the most useful for engineers. The guest describes a week of pure vibe coding in Cursor that left them knowing little about the codebase, argues that hands-off AI use erodes skill and the enjoyment of problem solving, prefers inline tab completion over chat, and says AI-generated low-effort PRs and reports are burdening open-source maintainers. The speakers offer practical learning habits: read the PR that added a feature, stick with one model until it fails, and use docs and DevDocs. No benchmarks or measured data are given, and the claims are personal opinion.

## Techniques
- **Ease into Vim motions with VS Code Vim keybindings, then VimTutor** — Turn on Vim keybindings in VS Code first to get the motions. Then open Vim and run :Tutor (capital T) for the interactive lesson, which the guest describes as gamified. *When:* When you want to try a modal editor without losing day-to-day productivity.
- **Doom Emacs command discovery via M-x** — Press Alt-x (M-x) and fuzzy-search available commands. The palette shows a preview of each command's keybinding, so you learn shortcuts while you use the commands. *When:* When learning a large editor with many commands and little documentation reading time.
- **Org mode task basics** — Write a capital TODO to create a tracked task. Record start times, schedule tasks to specific days, set weekly recurrence, keep separate org files per area (for example work and personal), and view everything in the org agenda, which shows a weekly task list across files. Org export can produce PDF, HTML or Markdown. *When:* When you want tasks, notes and a calendar view in plain-text files without moving data between apps.
- **End-of-day brain dump, one dated file per day** — At the end of each day, write every loose end, open question and project update into a file titled with the date. The next morning, review it. Find old notes with a full-text global search rather than file titles. *When:* To separate work from the rest of the evening and pick up the next day with context.
- **Keep inline completion on, but write the code yourself** — Leave tab completion enabled in the editor. Type your own line, and accept suggestions only when they match what you intended. Avoid waiting on suggestions mid-thought. *When:* Day-to-day coding where you want to keep scope and codebase awareness instead of handing over whole features.
- **Scoped AI questions, then implement by hand** — Ask narrow questions: define an unfamiliar term, explain one function, or summarize the design of a PR in plain English. Then reimplement the feature yourself instead of pasting the output. *When:* Learning a new codebase, a new term, or a feature you do not understand yet.
- **Learn an OSS feature by reading its introducing PR** — Find the pull request that added the feature, read its diff (a small scope), and optionally have AI explain the design. Then rebuild the feature in your own project rather than adding the dependency. *When:* When you want to learn how a feature works in a project you did not write, or avoid a dependency for a single function.
- **Trust filter for OSS learning sources** — Prefer large, established projects and developers you already follow. Treat repos with very few stars as possibly unvetted, and check a developer's GitHub activity and PR history rather than trending repos. *When:* Choosing which open-source code to learn from, especially when many AI-written projects appear.
- **Docs-first, then tweak and break the example** — Open the official docs, copy the hello-world or usage example, run it, change it and break it on purpose, and ask why each change behaves as it does. Use DevDocs (devdocs.io) for offline API docs. *When:* Learning a new library or language, or working without internet (for example on a flight).
- **Remote development from a Mac into a Linux machine** — SSH from a laptop into a Linux desktop or home server (the speaker runs Proxmox at home). Use Tailscale for remote access when away from the home network. Needs a reliable connection; GUI work is awkward. *When:* When you want Linux tooling without running Linux on your main machine, or to code from elsewhere in the house.
- **Time-boxed MVP with visible pain points** — Build the first version quickly without polishing for hypothetical users. Let friction show where change is needed instead of pre-engineering features, and avoid adding AI-suggested features you do not need. *When:* Personal or early-stage projects where over-engineering is a risk.

## Hot takes
- Keeping a tolerance for challenge matters, and AI-only advocacy reads as marketing; shortcuts are fine if taken wisely (guest, 1:13:20).
- Be wary of people with strong, confident opinions online. The smartest person knows what they don't know (speakers, 1:14:36).
- AI made hobby coding less fun because the problems get solved for you (guest, 31:16).
- Mac is the choice for things that just work; Linux rewards configuring the whole machine from the terminal, at the cost of compatibility issues (speakers, 38:15).
