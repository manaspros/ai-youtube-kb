> Hinge Health's AI lead on shipping member-facing health AI: put irreversible decisions in code above the model, strip PHI at ingestion, monitor live traffic, and verify the judge before fixing the agent.

## Summary
Rashi Agrawal, who leads AI and ML at Hinge Health, argues that member-facing healthcare AI needs guardrails built into the architecture before launch. She cites real harms, including a diet-advice chatbot case and a Mount Sinai study finding that a consumer health AI under-triaged emergencies about half the time. Part one covers architecture: strip PHI at the pipeline boundary, keep production and non-production fully separate, and gate access by role and region. She then describes a code layer that runs before the model on every turn and owns irreversible decisions such as emergency escalation, intent routing and identity checks. Part two covers monitoring: continuous judges on live traffic, member thumbs-up/down, and sampled traces with 100% review of high-stakes cases, with humans as the real bottleneck. For disagreements about launches she gives five decision rules (worst case sets severity, severity is not capacity, default to the safer mistake, calibrate to revealed risk tolerance, design for humans in the loop). She closes with a discipline of verifying the judge before changing the agent, using a caffeine example where the judge was wrong in one case and right in another.

## Key ideas
- **Most healthcare AI safety failures are architectural decisions made before any token is generated, not model failures.** — The speaker's first foundation is that the constraint is the architecture. Deterministic rules belong above the model, and safety is a continuous evaluation layer rather than a one-time gate. ([2:31](https://youtu.be/YXEqC05WEI0?t=151))
- **Strip PHI at the pipeline boundary instead of redacting it at runtime.** — PHI is removed at ingestion before it reaches the data lake, so dashboards have nothing to redact. Production and non-production have no connecting pipes, and access depends on both role and geographic region. ([3:34](https://youtu.be/YXEqC05WEI0?t=214))
- **Irreversible decisions go in a code layer that runs first on every turn; the model never gets a vote on high-stakes calls.** — Emergency escalation to 911 or 988, routing a clinical question away from generic tech support, and identity verification are all handled in deterministic code. The model handles the long tail. A model with a system prompt is not treated as a guardrail. ([5:58](https://youtu.be/YXEqC05WEI0?t=358))
- **Prompts are not a security boundary, even at the frontier labs.** — The speaker points to the published authority hierarchy (root, system, developer, user, guideline). Every layer above user can be overridden by prompt injection, so authentication must be a code-level check. ([7:32](https://youtu.be/YXEqC05WEI0?t=452))
- **Monitoring is a first resort that stays on, not a pre-launch checklist.** — Failures come back under new prompts, tools and model shifts, and each fix buys less than the last. Each new production failure should add a new judge. Three signal sources catch different problems: automated multi-dimension judges, member thumbs up/down (which catches tone), and sampled traces with 100% review on high-stakes cases. ([9:40](https://youtu.be/YXEqC05WEI0?t=580))
- **The bottleneck is people who can read the signal and act on it, not compute.** — Judges scale easily. Interpreting patterns and deciding what to do does not, so the design must assume a human in the loop. ([10:41](https://youtu.be/YXEqC05WEI0?t=641))
- **Five decision rules for stakeholder disagreements about launches.** — Worst case sets severity. Severity is never reduced because of team capacity. Only three options are allowed: fix, delay, or accept the risk with explicit sign-off. For safety bugs, hold when unsure; for polish bugs, ship when unsure. Calibrate to the risk tolerance the org has actually shown in production, not the one it states. Fast followers are committed debt, not a backlog. ([12:48](https://youtu.be/YXEqC05WEI0?t=768))
- **Verify the judge before changing the agent.** — When a clinical accuracy score drops from 4.9 to 4.5 and stays there, first check whether the judge is right. In the caffeine example the judge over-called a correct answer (fix the judge), but in a second case the agent really gave an unsafe 1,000 mg answer (fix the agent). Judge prompts are software and should evolve. ([18:07](https://youtu.be/YXEqC05WEI0?t=1087))

## Techniques
- **Code-layer routing above the model** — Run a deterministic code step before the model on every turn. It handles emergency escalation, intent routing to the right capability, and authentication. The model only sees the turn if the code layer lets it through, and it never decides high-stakes routes. *When:* Any agent where a wrong action is irreversible or safety-relevant, such as self-harm signals, clinical versus generic routing, or access to member data.
- **PHI stripping at ingestion with environment and region separation** — Remove sensitive fields at the pipeline entry point so downstream stores never hold them. Keep prod and non-prod with no connecting pipes. Gate raw-data access by role and region. *When:* Regulated data (HIPAA-style) where a single leaked pipe or log is unacceptable and redaction at read time is too late.
- **Layered live scoring of production traffic** — Combine many automated judges across dimensions (clinical accuracy, safety, escalation, relevance, drift, refusal) that keep scoring real conversations, member thumbs up/down, and random samples with 100% sampling on high-stakes flows. *When:* After launch, to catch regressions and slow quality drops that a static golden dataset misses.
- **Judge-first triage before agent changes** — When a judge score moves, test the judge on contrasting cases first (one where the agent is right and the judge flags it, one where the agent is wrong). Fix the judge prompt if it is over-calling, or fix the agent if the judge is correct. *When:* Any time a metric drops and the team is about to change prompts or the agent based on it.
- **Severity triage for launch decisions** — Set severity from the worst plausible outcome, not the frequency. Choose fix, delay, or accept-with-sign-off. Use asymmetric defaults: hold on safety bugs when unsure, ship on polish bugs when unsure. *When:* Go/no-go decisions where stakeholders (clinical, legal, compliance, product, engineering) see different risks.

## Hot takes
- A model is not a guardrail, and a model with a system prompt is not one either.
- Prompts are not a security boundary; authentication is.
- Fast followers are committed debt, not an optional backlog.
- Building guardrails first is slower than bolting them on later, but that slowness is the design.
